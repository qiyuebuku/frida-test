# 逆向排查方法论与部署铁律（2026-08-17/18 生产级调试沉淀）

> 来源：THS 交易 SDK 部署生产 AVD 的两天马拉松排查（跨设备 token、登录链挂起、
> 会话互踢、实例风暴）。全部为实付学费换来的通用规则，适用任何 App 逆向。

## 一、部署铁律

### 1. 增量 `adb install -r` 不杀进程——新代码根本没生效
症状：改了代码、部署"成功"、行为完全不变。增量安装（输出 "Performing
Incremental Install"，几十 ms 完成）只替换 APK 文件，**运行中的进程继续用
旧 dex**。连续两轮排查被此坑浪费。
规则：**每次 install 后必须 `am force-stop <pkg>` + 重新拉起**；验证新代码
在跑的最可靠方法=给关键端点/日志加版本指纹（如响应加新字段）。

### 2. `am force-stop` 不带 --user 时杀全部用户实例
多用户实例环境（一个 App 多 user）：`am force-stop pkg` 杀所有 user 的
实例；只杀一个用 `--user N`。反过来，想全杀时不用加参数。

### 3. 修改 App 私有文件（SP/配置）后要修属主
root 写入 `/data/user/<id>/<pkg>/shared_prefs/*.xml` 后默认 root 属主——
App 可读不可写，SP 回写静默失败甚至整文件失效。**写入后 chown 回 app uid
+ chmod 660**（app uid 从 `dumpsys package | grep userId=` 取）。

### 4. 设备指纹移植的通用三层（服务端设备绑定校验的破法）
客户端上报什么就伪造什么，按成本从低到高：
1. **SP/私有配置文件移植**（首选）：设备 ID 几乎都缓存在私有文件里，直接
   从源设备 `su cat` 读值写入目标设备（注意属主）。
2. **Build 静态字段反射改写**：`Build.MODEL/BRAND/...` 是 public static，
   Android 11 反射可写，一处改动全 App 生效。
3. **native 回调通道字段级合并**：native 模块向 Java 要配置的回调（如
   `getConfigInfo`）是唯一汇总出口——hook 其返回值做 **JSON 字段级覆盖**
   （保留本机动态字段如时间戳/会话 ID，只换身份字段）。
**禁忌**：整串替换配置响应（动态字段过期会破坏协议）；伪造账号体系 ID
（如 THS Userid）——身份字段必须与本机会话体系一致，否则直接被拒。

## 二、观测方法论

### 5. 先解决"看得见"，再排查
- 模拟器/AVD 的 logcat 常常只显示 W/E 级（I 级不可见）→ **诊断探针全部
  用 Log.w**，同时写入内存环形缓冲（HTTP `/logs` 端点导出，绕过 logcat）。
- logcat 环形缓冲会被高频事件刷爆（传感器/行情帧每秒百条）→ 关键事件
  丢失。对策：拉全量到本地文件分析（`logcat -d > file`），**绝不要靠
  head/tail 切片下结论**（本次多次被切片误导，"没有事件"其实在被裁掉的
  中段）。
- 后台长挂观察用 `nohup adb logcat -s TAG > 本地文件 &` 持续捕获。

### 6. 热路径探针必须限频，否则会引发雪崩
高频调用的 hook（每次请求都过的检查点）里做 Log.w+反射，会在多实例环境
放大成 CPU 风暴 → ANR → watchdog 杀进程 → 重启更慢 → 更卡（实测 load 39）。
规则：**热路径探针限频（如 5s 一条）+ 反射 Method 缓存**；限频计时用静态
AtomicLong（跨回调实例），不能放 MethodHook 实例字段。

### 7. "无发送无回调"挂起的终极取证：线程转储
请求发出后既无网络发送日志也无回调时：登录/请求等待期内 `kill -3 <pid>`
取 ANR 转储（`/data/anr/trace_*`），直接看线程栈停在哪个帧。注意 trace
文件按 pid 命名，别拿错进程的（先看文件头 `----- pid N`）。

### 8. 并发竞争的 fail 回调 ≠ 业务失败
同一流程存在多条并发链（自己的主动调用 + App 内部自愈/重登机制）时，
竞争中超时一方的 fail(null) 回调可能打到你的监听器上，而另一条链实际
已成功（实测：报 fail 后 15s 业务查询直接可用）。
规则：**收到 fail 后先轮询权威状态（登录态标志等）5~10s 再定性**；
超时路径同理（超时后查状态，可能"success-after-timeout"）。

## 三、自愈设计模式

### 9. 一次性标志"成功才消耗"
"每进程只执行一次"的保护（seed 重播/初始化），如果在执行前置位，失败后
就永远没有重试机会（实例卡死在坏状态）。**置位移到成功之后**，失败让下
次触发自然重试。

### 10. 读取路径失败 → 重放写入链
持久化数据"写入成功、读取被拒"（读取路径有额外校验/重算，如 livetime
重算导致恒过期）时，不要去攻读取内部逻辑——**把原始材料（明文 seed）也
持久化下来，读取失败时走官方写入链重放一遍**，形成闭环自愈。

### 11. 冷环境重放三件套
把"环境迁移"（新设备/模拟器）需要的全部状态做成可重放的 seed 文件：
账户/配置对象 + 凭证材料 + 失败自动重播。App 自身仓库在该环境不落盘时
（模拟器上底层库未初始化），seed 是唯一持久层。

## 四、环境差异排查法

### 12. 同代码不同结果 → 列环境差异清单
真机通、模拟器不通时，差异只有几类：设备指纹（§4）、配置/数据库初始化
（模拟器上底层库常未初始化）、时序（模拟器慢 5~10 倍，初始化窗口变宽）、
账号会话体系。逐类排除，别在协议层瞎猜。

### 13. 责任链/拦截器链逐点打点
长异步责任链（登录链/过滤器链）中间挂起时：**每个节点的 enter + 基类的
proceed 各打一条**（含线程名+next 字段反射），一次运行即可定位断点。
注意模板方法模式：子类可能只覆写条件方法（a()/b()）而不覆写主流程
（intercept），hook 主流程方法时这类子类不会命中——链上"消失"的下一个
节点可能就是只实现了条件方法的拦截器（详见 THS 案例第 16 章 z9m）。

### 14. 多实例并发的资源互斥要想到"互踢"
多设备/多实例用同一凭证登录同一服务端时，服务端可能单活会话——后登的
踢先登的，触发互相重登风暴（实测 1Hz 循环）。表现为会话间歇失效。
排查时**先停掉其他所有持凭证端**再观察单端行为。

### 15. 分层计时定位法：耗时归属一击必中（2026-08-18 同花顺"20s 慢查询"实测）
端到端慢时，把总耗时拆到各层独立证据上，一次对比即锁定层：
- **链路层**：最轻的端点（/health，设备端 <10ms）打同一条链路 N 次——慢则链路（forward/proxy）问题
- **处理层**：让设备端 handler 在响应里带 `elapsed_ms`（自己计的纯处理时长）——设备快而端到端慢 = 耗时在 handler 之前（排队/等锁/自愈逻辑），设备也慢 = 算法/通道问题
- **对比矩阵**：直连 proxy vs 裸 forward vs 设备内 localhost 三路同测，两分钟分清责任层
本次案例：链路 0s + handler 1.7s + 端到端 20s → 锁定 18s 在 handler 外层的"超时→强制登录→sleep→重试"自愈链——而这段代码注释里自己写着"实测 ~18s"。

### 16. "正常时段才出现"与"异常时段才出现"要分开归档
盘后/维护窗/限流时段的现象（连接周期断开、请求被丢）不要急着当 bug 修，
也不要急着归为"正常"——**两个都要实锤**：现象本身录证据（连接风暴日志），
时段相关性录证据（正常时段全绿样本）。结论写成"现象实锤 + 归因推断 + 待
正常时段复验"。把推断说成定论会在后续排查中误导方向（本次教训：把"券商
收盘清场"说得过于确定，实际断开发起方始终未实锤）。

### 17. 多 bug 叠加时单变量修复会被掩盖（v2→v9 六轮教训）
同一症状可能由多个独立 bug 叠加（中文字节错位 + 部署陷阱 + 响应帧丢失 +
token 到期），修复其中一个看不到改善≠修错。两个纪律：
- 修复前先做**可控复现**（设备内 localhost 直测拿到 7ms 响应，一击证明
  链路/代码层无罪，缩小到传输编码层）
- 外部依赖（token 生命周期）先确认新鲜度再归因代码

## 五、从真机成功到干净环境可重建（2026-08-22）

### 18. “对象非空”不是“业务就绪”
- **现象**：探针显示账户对象已创建、`account_ready=true`，请求构造器也被调用，
  但后续没有业务回调或一直超时。
- **原因**：最小伪造对象只满足了早期空值/类型检查；下游还可能依赖对象图中
  未显式展示的券商模板、营业部规则、账号类型、路由配置和注册状态。
- **方案**：把就绪状态拆成“对象存在 → 语义字段完整 → 已注册/激活 → 通道连接
  → 业务探针成功”。最终只以一个只读业务请求成功作为可用判据，不把布尔变量
  或单例非空当成最终健康状态。
- **适用范围**：账户 SDK、支付 SDK、推送 SDK，以及所有通过反射构造内部对象的逆向。

### 19. 按层定位“已发送但超时”，不要跨层猜根因
- **现象**：请求已进入 builder/serializer，甚至看到 Socket 连接成功或
  `onChannelOk`，但没有业务响应。
- **原因**：代码装载、对象语义、生命周期、路由、传输连接、业务响应是不同层；
  TCP 可连接只证明传输层，不证明券商路由和账户上下文正确。
- **方案**：固定按以下证据链检查：①实际装载的 DEX/APK 版本；②请求对象完整度；
  ③账户注册和生命周期；④网关/路由配置；⑤发送入口和连接；⑥响应帧/回调；
  ⑦权威只读业务结果。明确区分“显式失败”“无发送”“发送后无回调”。
- **适用范围**：长连接、私有二进制协议、异步回调和多路由 SDK。

### 20. 真机是发现环境，干净模拟器是可重建验收环境
- **现象**：同一 Hook 在长期使用的真机或旧数据目录上成功，换全新 Redroid/AVD
  就失败；复用旧目录后又看似恢复。
- **原因**：真机和旧目录积累了官方流程生成的隐含状态，复用它们会掩盖代码、
  配置或初始化步骤的缺失，并可能携带旧 APK、锁文件和过期会话。
- **方案**：先在真机以只读探针捕获官方对象/报文边界，快速验证调用链；再用不可变
  镜像、全新数据卷和外部密钥做冷启动验收。旧数据只归档取证，不作为持续部署依赖。
- **适用范围**：容器化 Android、灾难恢复、批量实例和任何“换机复刻”场景。

### 21. 将重建材料分成三类管理
- **现象**：为了让新实例可启动，团队倾向于复制整个 `/data`，或反过来把所有
  必需材料都当作秘密而只留在生产机。
- **原因**：秘密、稳定协议元数据、临时运行状态混在一起，导致代码无法独立重建，
  同时增加泄密和陈旧状态污染风险。
- **方案**：①账号、密码、token 放 Secret Manager，禁止进 Git/镜像/日志；
  ②券商路由模板等非秘密且稳定的协议元数据进入 Git 并版本化；③锁、缓存、临时
  session 等运行态允许重建。每次冷启动测试验证前两类足以生成第三类。
- **适用范围**：所有需要 CI/CD、容灾和多环境一致性的逆向工程。

### 22. Zygisk DEX 注入的资源边界
- **现象**：普通 APK 测试能读取 `assets`，改成只注入 DEX 后出现
  `FileNotFoundException`；`createPackageContext(Hook包名)` 又报包不存在。
- **原因**：Hook 代码实际运行在宿主 App 进程，`appInstance.getAssets()` 读取的是
  宿主 APK 资源；DEX 被注入不代表 Hook APK 已被 PackageManager 安装或注册。
- **方案**：运行时必需的小型非秘密模板优先编译进注入 DEX；较大资源使用明确、
  可校验的 sidecar 路径并做版本/哈希校验。必须按最终交付形态测试，不能用
  “安装 APK 时成功”代替“DEX-only 注入成功”。
- **适用范围**：Zygisk companion 传 DEX、动态 ClassLoader、插件化和宿主进程注入。

### 23. 结论必须保留证据等级和纠偏记录
- **现象**：某条路径超时后过早归因为特定通道；切换通道仍超时，后续人员却继续
  沿用旧结论。
- **原因**：把相关性或单次对照当成根因，没有记录反证及当前验证状态。
- **方案**：结论标注为“实锤 / 推断 / 已排除 / 待验收”；只有单变量对照改变结果
  才升级为根因。反证出现时保留原假设并明确写“已被何证据推翻”，避免重复走弯路。
- **适用范围**：所有多层异步系统和跨环境逆向排障。

### 24. 业务成功回调不等于对象生命周期已落地
- **现象**：服务端明确返回成功，外层 callback 也收到 success，但后续业务请求仍
  报未登录或没有回调。
- **原因**：SDK 常在外层 callback 前执行“查找对象 → 更新字段 → 绑定依赖 → 写入
  仓库 → 发布登录态”。干净环境缺少仓库索引时，这段内部生命周期可能提前返回，
  外层 success 仍会照常发出。
- **方案**：静态确认 success callback 前的所有副作用；运行时分别验证仓库成员、
  当前对象引用、生命周期状态和只读业务结果。兼容修复应重放完整官方副作用，并
  限定在服务端明确成功之后，禁止只改一个 `loggedIn=true`。
- **适用范围**：账户、支付、授权、推送注册等带本地对象仓库的 SDK。

### 25. 用产物哈希排除“代码没生效”
- **现象**：源码和编译均正确，运行行为却始终像旧版本。
- **原因**：容器 entrypoint、包管理器或启动脚本可能在重启时从镜像重新安装旧产物；
  仅看构建成功和进程重启无法证明新代码被装载。
- **方案**：同时计算本地/远端构建产物、镜像内产物、设备安装产物的 SHA-256，并
  增加无敏感信息的版本特征日志。哈希不一致时先修部署路径，停止业务层猜测。
- **适用范围**：容器化移动端、插件系统、热更新、动态注入和多层制品部署。
