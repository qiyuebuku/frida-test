# 镜像内部调用的验证方法论（复刻 App 请求/登录协议的通用经验）

> 来源：2026-08-19 同花顺交易密码登录破案（详见 `case-ths.md` §19）。
> 适用场景：需要脱离 UI、用 hook/进程内调用复刻 App 的某条请求
> （登录、下单、签名请求等），且服务端会校验请求内容正确性。

## 1. 铁律：反编译读出的字段映射不可信，必须抓一次真实调用

- 反编译能确认**调用链和方法签名**（可信），但 **builder 各 setter 的业务语义
  是靠上下文猜的**（哪个是密码、哪个是账号、哪个恒空），猜错不报协议错——
  服务端按错误字段内容解析，返回**业务级错误**（如"密码错误"），极难归因
- 同花顺案例：密码放错 builder 位置（`S(密码)/R("0")`，实际应为 `R(密码)/S(空)`），
  券商把 "0" 当密码，报"客户交易密码错误"，一度误导去查"密码加密预处理"查了两天
- **正确姿势**：静态分析定位构造终点 → 在终点加探针 → 让 App 真实走一次该流程 →
  拿实测值（全字段 + 线上字节）逐字段对比自己的构造 → 修差异 → 单次验证

## 2. 报文构造终点探针模式（首选捕获点）

选**序列化终点**（把业务对象转成线上 byte[]/JSON 的那个方法）而非入口：

- hook 返回 `byte[]` 的静态方法（通常在"BufferBuilder"类里），afterCall：
  - dump 入参业务对象（如 g6m/r8m）的**全部 public 字段**（反射遍历，
    只取 String/boolean/int/long）——一次拿到完整字段语义对照表
  - dump 返回 byte[] 的完整 hex——可逐 tag 解码，与字段名对上，
    形成权威的"字段→线上 tag"映射表
  - 同时写 logcat 和 filesDir 日志文件（文件不怕 logcat 洪流冲掉）
- 附带收益：这类终点附近往往能拿到网关配置等完整运行时 JSON

## 3. 如何让 App 真实走一次目标流程（触发方式选择）

| 触发方式 | 适用 | 风险 |
|---|---|---|
| UI 自动化（adb input tap/text） | 登录、下单等有 UI 的流程 | 正确凭据登录=零次数消耗；下单需注意真实成交 |
| hook HTTP 端点调用自己复刻的链路 | 调试已复刻的调用 | 消耗服务端尝试次数（见 §5） |
| App 自身后台流程（token 刷新等） | 只读、无 UI | 无 |

UI 自动化要点：
- `uiautomator dump` 拿精确坐标；**动画/刷新会导致 "could not get idle state"
  失败**——重试几次，且 dump 前先 `rm` 旧文件（失败时 cat 到的是上次脏数据，
  极易误判页面状态）
- `input text` **不支持中文**（NullPointerException）——用 ASCII 关键词搜索过滤
  列表（如券商代码 CCZQ），或直接按坐标点列表项
- dump 失败时用截图 + 视觉模型兜底判断页面
- 锁屏：唤醒+上滑通常够；需要 PIN 且未知时等用户，别猜
- WSL 可直接用 Windows 侧 adb.exe（`/mnt/d/.../adb.exe -s <serial>`），
  文件互传走 /mnt/d

## 4. 错误尝试预算管理（密码/验证码有锁定惩罚的协议）

- 先搞清楚惩罚规则（如同花顺券商：错 6 次锁 12h），把剩余次数当硬预算
- **静态分析阶段严禁实测**；所有假设先静态穷尽验证/排除（加密？编码？字段错位？
  开关？逐个排除并记录，防止后人重复查）
- 排查顺序：静态排除 → 探针抓真实值 → 对比修 diff → **单次验证**
- 正确凭据走真实 UI 登录不消耗错误次数——探针触发优先走这条
- 失败后自动机制（warmup/重试）必须能识别"凭据类错误"并停止，防止后台盲试
  烧光预算（同花顺 hook：密码登录 fail 即清密码存储）

## 5. 跨 dex 的短类名混淆解析（jadx 产物不全时）

多 dex 大型 App（同花顺 11 个 dex）常踩：

- **jadx 反编译源可能缺 dex**：先从设备重提全量
  （`adb shell su -c 'cat base.apk'` → unzip classes*.dex），对照 APK 内
  dex 清单和反编译目录，缺哪个补哪个
- 混淆短类名（`Lw0s;`、`Le;`）**没有包前缀**，jadx 归入 defpackage；
  引用处找不到定义 = 定义在别的 dex，别怀疑 jadx 写错
- 定位类定义：`dexdump -d <dex>` 全量 dump 后按
  `Class descriptor  : 'Lxxx;'` 精确匹配；找"谁调用某类"用 dump 里
  `invoke-xxx ... Lxxx;.method` 反查
- `fill-array-data`（如 Base64 字母表）在 dexdump 输出会被 `...` 截断——
  dump 左列是**文件偏移**，直接 `dd if=dex bs=1 skip=$((0x偏移)) | xxd`
  读原始字节
- 判断"神秘短类"的用途：dump 它的父类和常量（如 `Le;` 继承 CharacterEncoder、
  64 字符表 + '=' 填充 → 标准 Base64），不要靠名字猜

## 6. 通用排查节奏（本案验证有效的顺序）

1. 静态追完整调用链（入口→构造→序列化→发送），记录所有可疑变换点
2. 逐个静态排除变换点（读实现：是 UI 控制？是存储逻辑？是别的业务？），
   每个排除项写下来
3. 静态到头仍无解释 → 概率最大的是**自己的复刻与 App 有 diff**（字段映射/
   缺参数/缺 flag），而不是存在未知加密
4. 部署终点探针 + 真实触发一次，拿权威对照数据
5. 逐字段 diff 修复 → 单次验证 → 成功后把映射表写进案例文档，防止再次失传
