## 1. 先识别并发身份域

原生行情或消息 SDK 的请求通常同时经过多层身份：

```text
HTTP/RPC 请求
  -> Bridge 连接
  -> App 进程
  -> SDK Manager
  -> QueryClient
  -> frame/page/channel/route slot
  -> App 自有 TCP 会话
  -> 上游服务
```

并发能力由最窄的共享身份域决定，不由最外层 HTTP 连接数决定。开始优化前必须回答：

- Client 是每次新建，还是 Manager 按 frame ID 返回同一个实例？
- frame/page/channel 在单连接、单 Manager、单进程、单 UID 还是服务端全局唯一？
- 回调根据请求对象、Client、frame ID 还是全局监听器分发？
- `cancel()` 取消单次查询、整个 Client，还是该 frame 下全部请求？
- 不同数据源是否共用同一 SDK 路由槽？

没有这些答案时，不得用增加线程、HTTP 连接或 Bridge 实例来推断 Native 并发。

## 2. 连接、Client 和路由槽不是一回事

### 2.1 多个外层连接不等于多个 Native 通道

如果所有 HTTP/TCP 请求最终进入同一个 App 进程，并调用同一个全局 Manager：

```text
HTTP A --\
HTTP B ----> one App process -> Manager.obtainClient(2312)
HTTP C --/                         -> same QueryClient / route slot
```

即使建立十个外层连接，Manager 仍可能只看到一个 `frameId=2312`。常见结果包括：

- 后发请求覆盖先发请求；
- 回调被错误请求消费；
- 一个请求取消了另一个请求；
- 看似随机的 30/40 秒超时；
- 串行时稳定，并发时成功率骤降。

只有独立 App 进程、独立 SDK Manager 或协议明确支持不同 frame ID，才可能形成真正隔离的 Native Lane。

### 2.2 同一 SDK 的不同请求族可以有不同边界

不能因为某个请求族支持随机 frame ID，就认为整个 SDK 都支持。应分别验证：

- 列表/标签查询；
- 显式证券集合查询；
- 排行页面查询；
- 全量请求；
- 持续订阅；
- Unified/JSBridge 请求。

同一 Hook 路由也可能根据请求体进入不同 Native 数据源，因此限流不能只看 URL，必要时检查请求体中的证券列表、数据源和请求类型。

## 3. 用实验确定真实并发边界

### 3.1 最小实验矩阵

对每个请求族至少执行：

| 实验 | 目的 |
|---|---|
| 相同请求串行 20 次 | 判断基础成功率和残留状态 |
| 不同请求串行执行 | 判断取消和清理是否互相影响 |
| 同 frame ID 并发 | 验证固定路由槽是否冲突 |
| 不同 frame ID 并发 | 验证 frame 是否真的参与路由 |
| 多个外层连接、同 frame | 证明传输连接能否隔离 Manager |
| 直接调用 Hook 与经过代理对比 | 区分 App 耗时与工程排队 |
| 收盘中与收盘后对比 | 识别只在特定市场状态产生的字段 |

每次只改变一个变量。记录成功率、墙钟时间、回调次数、返回对象数量、字段覆盖率和取消结果。

### 3.2 判断 frame ID 是否有效

不要只看请求是否被接受。有效的自定义 frame ID 必须同时满足：

1. 能收到业务回调；
2. 回调内容属于对应请求；
3. 与其他 frame 并发时无串包；
4. `cancel()` 不影响其他 frame；
5. 连续多轮成功率稳定。

如果默认 frame 成功、随机 frame 只进入发送阶段但永远没有回调，说明路由注册或页面生命周期仍绑定默认 frame，不能靠随机 ID 扩容。

## 4. 异步回调的正确完成条件

### 4.1 不要等待“所有请求字段都有值”

某些指标在当前市场状态下合法为空，例如收盘后的即时涨速。若完成条件要求所有可选字段出现，请求会持续收到其他更新却一直等到总超时。

将字段分为：

- **必需字段**：身份、名称、价格/指数、核心变化值；
- **可选字段**：只在特定时段或状态产生的速度、盘口等；
- **推送字段**：快照完成后仍可能持续更新。

推荐完成判定：

```text
所有请求字段已到齐
  -> 立即完成

否则：
必需字段已到齐
且证券集合已停止增长一个 settle window
  -> 返回当前完整快照

否则：
超过总 timeout
  -> 返回明确的不完整状态或失败
```

证券集合稳定应根据“新证券 Key 是否继续出现”判断，不应被同一证券的重复字段更新无限重置。

### 4.2 结果非空不等于完整

验收必须同时检查：

- 期望对象数和实际对象数；
- 每个必需字段的覆盖数量；
- 数据所属请求和分类；
- 上游业务时间；
- 可选字段为空是否符合市场语义。

不得用旧值、零值或推测值填充缺失的实时指标。

### 4.3 订阅 ACK 不等于 Native 初始化完成

Bridge 返回 `subscribed` 通常只表示命令已被接受。若多路订阅在 App 内共享初始化 Frame，仅按 ACK 连续提交仍可能覆盖前一路初始化并导致所有订阅超时。

必须分别观测：

1. Bridge 命令 ACK；
2. Native 首个成功响应；
3. 后续增量事件。

当实验确认初始化 Frame 单飞时，采用响应驱动的逐路初始化：前一路出现首个 Native 成功响应后立即提交下一路。失败只重试当前订阅，不重建已成功订阅。该流程不能用固定 `sleep` 替代，因为网络和市场状态会改变首帧延迟。

同一会话中，初始化完成后的多路持续订阅可以并存；“初始化必须单飞”不等于“运行期只能保留一路订阅”。

## 5. 生命周期和取消

原生页面通常在页面生命周期内复用一个 QueryClient：

```text
page enter -> obtain client -> query/refresh/sort repeatedly -> page exit -> cancel
```

外部一次性 Bridge 可以采用查询后取消，但必须遵守 App 原生线程模型：

- `obtainClient`、`query`、`cancel` 需要时统一投递主 Looper；
- 等待业务完成后再取消；
- 取消必须有界等待，不能让清理无限阻塞 HTTP 响应；
- 超时后确认旧 Client 是否仍持有路由槽；
- 不要在收到第一帧后立即取消多帧结果。

若页面原生实现复用 Client，不要每次重建完整页面级 Ranking 构造器。优先复用最小 QueryClient 数据路径，业务排序放到服务端完成。

## 6. Bridge 与 Client 的职责边界

Hook/Bridge 应暴露原子协议能力和运行时状态，不包装“采集整个市场”之类业务：

```text
Bridge:
  原始参数 -> App 内请求 -> 原始结构化响应

Client:
  选择分类/字段 -> 合并原子响应 -> 标准化 -> 本地排序

Application:
  调度 -> 快照幂等入库 -> 投影
```

同一原始快照能派生多个排行时，只请求一次，在 Client 内共享短时缓存并本地排序。不要为涨幅榜、涨速榜、量比榜重复请求同一证券全集。

## 7. 性能拆解与基准测试

总耗时必须拆为：

```text
排队时间
+ Bridge/代理时间
+ App 主线程投递时间
+ Native 上游时间
+ 多帧收敛时间
+ 清理时间
+ 重试时间
+ 持久化时间
```

推荐输出每个原子请求的：

- queue_ms；
- upstream_ms；
- settle_ms；
- callback_count；
- row_count；
- required_field_coverage；
- retry_count；
- result_status。

基准测试必须：

1. 暂停会竞争同一 Native Lane 的正式任务；
2. 用 `trap` 保证退出后恢复服务；
3. 给远端探针设置总 timeout；
4. 只输出计数、覆盖率和耗时，不打印数 MB 原始行；
5. 同时报告单请求耗时和整批墙钟；
6. 测试后检查临时进程、服务状态和最新数据时间。

## 8. 生产探针安全规则

- 纯查询族和固定路由族使用不同信号量；
- 固定 frame/page 默认容量为 1；
- 只有完成并发矩阵验收后才能提高容量；
- App HTTP 和可独立重放的 Direct HTTP 不占 Native 锁；
- 请求体决定 Native 数据源时，代理按请求体分类，而不是只按路径；
- 局部请求超时不能直接重启仍承载持续订阅的 App；
- 临时探针必须有总 timeout 和退出清理；
- 避免同时启动大量 WSL 包装进程、SSH 探针和远端 Python；长任务只保留一个可等待会话。

## 9. 常见错误结论

- “HTTP 连接不同，所以 App 内请求已经隔离。”
- “直接调用快，经过代理慢，问题一定在代理。”
- “同一个 SDK 有一个接口支持随机 frame，其他接口也支持。”
- “回调还在更新，所以快照尚未完成。”
- “可选指标为空，应该继续等到总超时。”
- “一个 600 行大请求一定比四个分类请求更快。”
- “增加模拟器或 App 实例是第一选择。”
- “把业务集合包装进 Hook 能减少服务端复杂度。”

正确顺序是先确定身份域、路由槽、回调完整性和清理语义，再决定批量大小、并发度和是否需要增加 App 进程。
