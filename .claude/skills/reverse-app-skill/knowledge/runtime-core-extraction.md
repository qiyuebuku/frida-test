## 1. 先定义目标层级

逆向开始前必须明确交付目标，避免把不同完成度混为一谈：

| 层级 | 含义 | 典型用途 |
|---|---|---|
| 页面自动化 | 仍依赖页面，通过点击或 JSBridge 取数 | 快速验证、低频操作 |
| 进程内直接调用 | 不依赖页面，调用 App 内部业务类和通信服务 | 设备侧数据 Sidecar |
| 独立协议 Client | 不依赖 App 进程，独立实现认证、协议和连接状态机 | 服务器正式采集 |

“不打开页面”不等于“脱离 App”。进程内直接调用仍依赖 App 的代码、身份、服务和运行态，
必须如实标记为设备侧方案。

## 2. 识别传输通道

Hybrid App 常同时存在多条链路，不要假设所有数据都经过 OkHttp：

1. 标准 HTTPS：浏览器或 HTTP Client 可以直接重放；
2. WebView JSBridge：JavaScript 只负责传参，真实请求在原生层；
3. 原生长连接：自定义 TCP、二进制帧、订阅协议或推送通道；
4. 本地数据库或缓存：页面读取 App 已落地的数据；
5. SDK/系统服务：通过 Binder、ContentProvider 或厂商服务获取。

先制作“页面模块 -> JavaScript Handler -> Java 接口 -> 请求类 -> 传输层”的映射表，再决定
Hook 点。页面 Network 面板只能证明 Web 请求，不能排除原生通道。

## 3. 从页面适配层追到业务核心

当已定位 JSBridge 时，不要停在 Bridge 代理层。按以下顺序继续向下：

1. 记录 Handler 名、参数和回调格式；
2. 静态搜索 `@JavascriptInterface`、Handler 字符串和回调字段；
3. 从接口实现追踪请求模型、协调器、具体请求类和通信服务；
4. 对混淆类使用构造参数、父类、方法签名、常量字符串和帧号交叉定位；
5. 在运行时只 Hook 候选方法的入口和回调，确认真实调用顺序；
6. 找到最小可调用对象后，绕过 Bridge，直接反射调用业务核心。

jadx 无法完整反编译时，直接检查 DEX 指令。字符串分支附近通常能恢复调试命令、参数数量、
协议常量和状态切换逻辑。不要因类名被混淆就退回到页面自动化。

## 4. 构造最小进程内探针

建议在目标进程内建立窄接口，仅用于调用已经确认的业务核心：

```text
PC/采集器
  -> loopback RPC
  -> 参数校验
  -> App 内部请求对象
  -> 原生通信服务
  -> 标准化结果
```

探针必须满足：

- 默认只监听 loopback，外部访问通过 ADB forward 或受控中继；
- 不记录 Cookie、Token、设备 ID 或完整身份参数；
- 每个请求有超时、唯一日志 ID 和明确错误阶段；
- 不允许调用方任意指定类名和方法名；
- 只暴露经过验证的业务操作。

## 5. 还原隐藏运行状态

能构造请求对象不代表请求能工作。原生通信常依赖：

- Application 已完成初始化；
- 前台/后台阶段标志；
- Service 已启动并绑定；
- 登录、设备身份和用户上下文已就绪；
- 长连接已认证；
- 主线程 Handler 或 Looper；
- 页面打开时注册的订阅或观察者。

比较“正常打开页面”和“冷启动后台 Service”两种日志，找出缺失的状态变更。优先复用 App
已有的公开或反射方法完成初始化，不要直接修改大量字段。每补一个状态就单独验证，避免无法判断
究竟是哪一步有效。

## 6. 正确处理异步回调

长连接回调可能混合：

- 全量数据；
- 订阅成功确认；
- 增量推送；
- 心跳或状态通知；
- 错误回包。

必须根据响应类型、请求 Key 和状态码共同判断完成条件，不能把“第一个回调”当成最终结果。
一次性查询应在获得目标全量数据后立即注销；持续订阅则需要独立生命周期管理。

还要验证：

- Client 的创建、启动和释放是否要求主线程；
- 固定帧号、页面号或路由槽是否允许并发；
- 清理是否会影响下一次请求；
- 超时后是否需要重建连接而不只是重试同一请求。

## 7. 验证无界面运行

按以下顺序逐步降低依赖：

1. 页面打开，Bridge 原始调用成功；
2. 页面打开，进程内直接调用成功；
3. Activity 退到后台，直接调用成功；
4. 不创建 WebView，只保留 App 进程和 Service；
5. 冷启动 Service 后首次请求成功；
6. 多次串行请求成功；
7. 并发请求符合协议能力，或被明确串行化；
8. 息屏、网络切换、进程重启后能恢复。

每一步只改变一个变量。否则即使成功，也无法确定真正依赖项。

## 8. 处理系统与厂商冻结

Android 前台 Service 和 `PARTIAL_WAKE_LOCK` 只解决部分调度问题，不能保证厂商电源管理不会
冻结进程。遇到息屏超时时同时检查：

- 系统进程冻结状态；
- 厂商 freezer/Hans/Doze 状态；
- App UID 对应 cgroup 的 `cgroup.freeze`；
- TCP 连接是否仍存在；
- 解冻后旧连接能否继续收包。

白名单只解决“是否再次冻结”，不等于修复冻结期间已经断开的长连接。必须另行实现连接状态检测、
主动重连和首次请求预热。厂商调试命令的参数不要猜，应从系统服务 JAR/DEX 的命令分发方法中确认
参数数量和含义。

## 9. 生产化边界

进程内原型达到生产候选至少需要：

- 授权和使用边界明确；
- RPC 鉴权、loopback 绑定和敏感日志脱敏；
- App 更新后的类和协议兼容检测；
- 断线重连、健康检查和失败降级；
- 设备重启后自动恢复；
- 多设备容灾；
- 指标字段、单位、时间和来源验收；
- 不把估算值包装为官方确认值。

如果这些条件未满足，必须标记为调研原型或设备侧实验，不能宣称已经形成独立服务器 Client。

## 10. 推荐测试矩阵

| 场景 | 必须验证 |
|---|---|
| 冷启动 | 无 Activity 时首次请求成功 |
| 连续调用 | 多个不同业务 Key 顺序调用无串包 |
| 重复调用 | 同一 Key 多次调用无残留订阅 |
| 并发 | 协议支持并发，或系统明确串行执行 |
| 超时 | 不完整重试，不复用失效 Client |
| 息屏 | 超过厂商冻结阈值后仍可请求或自动恢复 |
| 网络切换 | Wi-Fi/移动网络切换后重连 |
| App 重启 | 类加载、服务和状态自动重建 |
| 设备重启 | 模块、服务和采集链路自动恢复 |
| 上游升级 | 类、方法、帧号和字段变化可被检测 |

## 11. 真机发现与服务器运行分工

不要把“最适合发现协议的环境”和“最适合长期运行的环境”混为一谈。

### 11.1 真机用于发现

真机通常具备真实账号、设备状态、完整功能入口和稳定 UI，是确认页面口径与捕获真实调用链的首选：

1. 先截取目标页面，记录当前值、Tab、字段、单位和更新时间；
2. 清空日志，只执行一次点击、切换或刷新；
3. 对比操作前后的 Hook、网络和请求模型日志；
4. 一次只改变一个 UI 动作，建立“页面控件 -> 请求 -> 响应字段”的映射；
5. 用页面显示值反向验证解析结果，不能只以 HTTP 200 或非空 JSON 作为成功。

当模拟器缺少登录态、功能被裁剪或数据口径与真机不一致时，不要继续在模拟器上猜协议。先在真机确认
正确请求，再把已经确认的最小能力迁移到模拟器。

### 11.2 模拟器用于运行

服务器 Android 虚拟机适合承担无人值守 Sidecar，但它的验收对象是“已确认的业务核心能否稳定运行”，
不是代替真机重新发现页面协议。迁移时依次验证：

1. APK 和目标 ABI 能运行；
2. 注入框架能加载目标进程；
3. 无 Activity、无 WebView 时进程内调用成功；
4. 宿主机只能通过 loopback 代理访问探针；
5. App、虚拟机和宿主机服务重启后自动恢复；
6. 同一组真机样本与模拟器结果字段、单位、时间和口径一致。

如果 ARM APK 通过 Native Bridge 运行在 x86_64 ART 中，Hook 框架的本地库 ABI 可能不兼容。此时应
将 Java Hook 接口适配到虚拟机内可工作的框架，而不是强行加载错误 ABI 的本地库。

## 12. 订阅缓冲区与事件采集

原生行情或消息通道经常返回订阅缓冲区，而不是传统分页列表。常见请求字段包括：

- `action=subscribe/unsubscribe`；
- 订阅 `key`；
- 事件类型列表；
- `max_msg_num`；
- 标的范围。

### 12.1 `max_msg_num` 不是分页

增大 `max_msg_num` 只能扩大单次返回上限，不保证每次返回同一集合，也不代表存在 offset/cursor。后端
可能按分片、市场、连接状态或环形缓冲区返回不同子集。判断方式是连续请求两次并计算：

```text
first_count / second_count / overlap / only_first / only_second
```

如果总数相近但两侧都有独有事件，应按“可轮询的缓冲区”处理，不能把差异误判成重复污染，也不能
期望单次请求获得完整历史。

### 12.2 必须保存事件，而不是只保存响应快照

每次轮询的大 JSON 只适合保留轻量摘要。完整事件应拆成独立记录，并保留：

- 事件时间；
- 市场、标的和事件类型；
- 原始值与单位；
- 来源通道和原始字段；
- 稳定事件 ID；
- 抓取时间与数据新鲜度。

事件 ID 应由稳定业务字段和规范化后的载荷指纹组成。不要把抓取时间、请求 ID、回调序号等易变字段
放进事件身份。重复轮询通过唯一约束幂等更新，新出现的缓冲区成员则补充入库。

### 12.3 订阅生命周期仍要完整清理

即使上层把订阅包装成一次性查询，也必须等待目标业务数据、执行 unsubscribe/remove，并确认清理完成。
固定 frame/page/路由槽在未验证前必须串行；若原生取消订阅是异步的，还要通过实验确定安全静默期。

## 13. 从逆向原型接入正式采集系统

逆向成功只说明“能够取到数据”，正式采集还需要独立完成：

1. Client 将原始响应标准化，但保留来源原文和 provider metadata；
2. 调度任务按数据时效运行，交易时段高频轮询、休市时跳过；
3. 首次接入或历史为空时允许显式 bootstrap，不受交易时段限制；
4. 聚合快照只保存页面当前状态，事件流拆成事件级记录；
5. 数据库唯一键保证重复投递和任务重试幂等；
6. 记录 fetched、valid、saved、error 和来源时间，区分空数据与调用失败；
7. 连续执行两轮，检查业务重复组、集合增量和实际行数，而不是只看任务返回成功；
8. 生产桥接、采集 Worker 和数据库分别做健康检查，避免 App 侧成功但入库链路中断。

## 14. QueryClient 身份域与并发验收

原生查询并发不能根据外层 HTTP/TCP 连接数判断。多个 Bridge 连接进入同一 App 进程后，可能仍共享
同一个 SDK Manager、frame ID、页面号或回调槽。正式提高并发前必须分别验证：

1. 相同 frame 串行与并发的成功率；
2. 不同 frame 是否都能收到业务回调；
3. 一个 Client 的 `cancel()` 是否影响其他请求；
4. 不同请求族是否使用不同数据源和路由域；
5. 必需字段、可选字段和证券集合何时真正完整；
6. 直接 Hook、Bridge、代理和应用 Client 各自消耗多少时间。

固定 frame/page 默认容量为 1。只有随机 frame 的业务回调、隔离取消和连续并发都通过验证后，才能提高该请求族
容量。不同请求族必须使用独立信号量；同一路径根据请求体切换数据源时，代理也必须检查请求体。

完整方法、实验矩阵和完成条件见 `knowledge/native-query-routing-and-concurrency.md`。同花顺的实际边界和性能结果见
`knowledge/case-ths.md` 的“板块 QueryClient 路由与性能优化”。

验收结论必须区分：单次返回稳定、事件身份幂等、缓冲区集合稳定。这三件事不是同一件事。
