# 情绪舆情聚合（重新设计）

## 1. 需求分析

### 1.1 核心需求拆解

**角色重定位**：情绪在决策打分公式中权重为 `sentiment × 0.10`（六个维度里最低档），它的核心价值不在"告诉我买什么"，而在"告诉我不能买什么"——当一个标的/板块讨论过热、涨停潮集中、热股榜反复上同一个代码，这是**风控过热信号**，应反向降权事件结论、收紧下游操作。

因此本模块的最终产出必须同时服务两条消费路径：

- **P1 决策打分层**：为当前市场与单只标的产出 `sentiment_score ∈ [0, 1]`，进入决策引擎的 0.10 项。
- **P2 过热降权层**：当个股 / 板块热度命中过热阈值，产出 `overheat_penalty ∈ [0, 1]`（倍率），由决策引擎在事件 impact 乘入 `(1 − overheat_penalty)`。

只有 L1 原始采集到位不够——那是"数据陈列"；只有 L2 派生信号落成稳定接口，决策引擎才真正能消费情绪。

本模块分两层：

- **L1 原始层**：结构化、可去重的热度/排行/涨停快照（`ft_sentiment`）。
- **L2 派生信号层**：市场温度、个股过热度、板块热度聚类（查询接口 + 未来落表）。

### 1.2 边界与约束

1. **职责边界（避免重复劳动）**：
   - 本模块只处理**热度型、排行型、结构化统计型**数据：股吧人气、涨停池、雪球/腾讯热股、雪球热门话题、个股股吧帖子列表。
   - **不处理新闻/公告文本**——那是 `agg_news` + AI 事件抽取的职责。本模块里的 `guba_posts.posts[]` 是"讨论量原始材料"，若未来需要 AI 情感极性分析，应消费 `ft_sentiment` 的 JSONB 产出，不要在本模块内塞 LLM 调用。
   - **不处理宏观利率 / 汇率情绪**——归 `agg_macro` 的 `external` 维度。
   - **不计算个股 K 线 / 量能**——归 `agg_market` + `agg_fund_flow`。本模块的过热判定只用"热度榜出现次数 + 讨论量 + 涨停上榜"，不交叉价量。

2. **已有基础设施必须复用**：
   - BaseAggregator + SourceDef + ft_collection_state 增量机制已成熟，保持沿用。
   - 统一 UPSERT 走 `SentimentRepositoryImpl.upsert_batch()`，已实现，不再写裸 SQL。
   - `data_type + trade_date + data(JSONB)` 三元组格式稳定，不再扩列（扩 data_type 即可）。

3. **情绪数据的"当天性"**：
   - 情绪是**日内高时效**数据，不需要回填 90 天历史——回填来的老热度榜对当下决策毫无价值。
   - 所有源配置为 `target_days=0 / default_mode=incremental`，`_get_checkpoint` 直接返回 `None`，全量覆盖刷新。

4. **空数据防护（已上线坑点）**：
   - `tencent_hot_stocks` 某些时段返回 `{"5min":[],"1hour":[]}`，是"API 没返空，但内容全空"的伪数据；`limit_pool` 在非交易时段可能返回结构但 `info=[]`。
   - **所有 normalize 函数在写入前必须递归判空**——空 dict、空 list、None、"所有 value 都空的 dict" 都视为无数据，直接返回 `[]`，不入库。当前代码用 `_is_empty()` + 内层 `info/posts/stocks` 再判一次已覆盖此约束。

5. **guba_posts 数据源规模**：
   - 个股股吧帖子源 `guba_posts` 是**基于 watchlist 动态拉取**——不是固定列表。当前从 `checkpoint_store.list_all("watchlist")` 取前 10 只，并发拉取 `get_guba_posts(纯数字代码)`。
   - watchlist 为空时（新装部署）该源产出 `[]`，不报错。
   - 每只股票产出**独立一条** `ft_sentiment`（`data_type=guba_posts`），而不是聚合为一条——下游查询时可按 `data.code` 过滤。

6. **ORM 约束**：所有写入必须走 `SentimentRepositoryImpl`，保留 `on_conflict_do_nothing`（当天同一 data_type 已写入即跳过，避免 15min tick 产生大量历史重复行）。

### 1.3 复杂度判定

**复杂度：中等（拆 4 步）**

- 不算简单：L2 派生信号（市场温度 / 过热降权）是新逻辑，需要阈值设计 + 可回测存证。
- 不算复杂：L1 采集侧 7 源已全部上线，只剩信号合成与对决策引擎的稳定接口——无跨模块架构改动。

### 2.2 关键技术选型及理由

| 决策点 | 选型 | 理由 |
|---|---|---|
| 存储模型 | 单表 `ft_sentiment (data_type, trade_date, data JSONB)` 不拆表 | 情绪数据异构性强（热股是 list、涨停池是多层 dict、热话题是带字段的 obj），拆成 N 张结构化表代价远大于 JSONB 查询性能损失；`idx_ft_sentiment_type_date` 足以支撑决策引擎的当日读取 |
| 增量策略 | 全量覆盖 + `on_conflict_do_nothing` | 情绪是"此刻快照"，不需要增量断点；同一 data_type 同一天重复写入只保留首次，避免 15min tick 爆炸式膨胀 |
| 空数据处理 | normalize 前置判空 + 内层 key（info/posts/stocks）二次判空 | 多个 API 会返回"结构完整但内容为空"的伪数据，如果不在 normalize 过滤掉会污染 DB 并让 `get_market_temperature` 产生偏差 |
| guba_posts 源选择 | 基于 watchlist 前 10 只动态生成 | 无 watchlist 场景不产生调用（节省配额）；watchlist 变化自然驱动采集范围变化，无需额外同步逻辑 |
| 市场温度算法 | 规则打分（v1）| 情绪指标含义直观、样本少（当日一条）、无监督；用规则透明可解释，Phase 4 上线后再用真实持仓后验回测调权 |
| 过热降权输出 | 倍率 `[0, 1]`（不是 `[-1, +1]`）| 降权只在"过热"方向起作用（过冷不会让人更想买）；倍率形式便于决策引擎直接 `raw_impact × (1 − penalty)` 接入 |
| 不接 LLM 情感分析 | 本模块不做文本情感 | 文本情感极性是 `agg_news` + AI 事件抽取链路的能力；本模块只提供**数值热度**，不越权 |

## 3. 数据模型

### 3.1 ft_sentiment（现状，**不改**）

| 列 | 类型 | 说明 |
|---|---|---|
| id | SERIAL PK | |
| data_type | VARCHAR(32) NOT NULL | 数据类型枚举（见 §3.2）|
| trade_date | DATE NOT NULL | 业务日（`date.today()`）|
| data | JSONB NOT NULL | 异构负载，结构取决于 data_type |

**关键约束**：`SentimentRepositoryImpl.upsert_batch` 用 `on_conflict_do_nothing`（目前无唯一约束，依赖 `data_type + trade_date + data` 的应用层去重；首次入库即生效，后续 tick 同一天的覆盖由应用侧自行约束）。

> 历史备注：字段 `captured_at` 已于 2026-04-11 重命名为 `created_at`，与其他聚合表一致。

### 3.2 data_type 枚举（当前 7 种）

| data_type | 来源 | data 结构示意 | 体量 | 用途 |
|---|---|---|---|---|
| `guba_popularity` | EM `get_guba_popularity` | `list[{sc, rk, rc, hisRc}]` | ~100 行 | 人气榜（单股热度/排名）|
| `limit_pool` | THS `get_limit_pool("up"/"down")` | `{info:[...], date, ...}` | 当日涨停/跌停全量 | 涨停/跌停比、涨停原因集中度 |
| `xueqiu_hot_topics` | Xueqiu `get_hot_topics` | `list[{title, count, ...}]` | 20-50 条 | 话题热度（板块情绪）|
| `xueqiu_hot_stocks` | Xueqiu `get_hot_stocks` | `list[{code, name, rank, ...}]` | 20-100 只 | 热股榜 A（过热判定输入）|
| `tencent_hot_stocks` | Tencent `get_hot_stocks` | `{"5min":[...], "1hour":[...]}` | 分时段排行 | 热股榜 B（与 A 做重叠判定）|
| `guba_posts` | EM `get_guba_posts(code)` | `{code, count, posts:[...]}` | watchlist 每只一条 | 单股讨论量（过热判定输入）|

### 3.3 派生信号（🔜 v1 先不落表）

`get_market_temperature()` 和 `get_overheat_set()` 当前**按需计算 + 内存返回**，不建物化表。等 Phase 4 决策引擎上线、确定调用 QPS 后再决定是否建 `ft_sentiment_signal` 快照表。

> ⚠ 若未来决定落表，建议字段：`snapshot_date DATE UNIQUE`、`market_temperature INT`、`market_level VARCHAR(8)`、`overheat_codes JSONB`、`contributors JSONB`。本轮**不创建**，记入 `9. 待优化.md` 作为后续动作。

## 4. 接口设计

### 4.1 L1 原始查询（已上线 ✅）

`SentimentAggregator` 继承自 `BaseAggregator`：

| 方法 | 签名 | 说明 |
|---|---|---|
| `tick()` | `async → {sources_run, total_saved}` | 调度器触发入口，串行 7 源（间隔控制走 ft_collection_state）|
| `query(data_type, trade_date, limit)` | `async → list[dict]` | 通用查询（基类 `_query_table`）|
| `replay(start, end)` | `async → list[dict]` | 从 ft_raw_data 用当前 normalize 重放（基类）|

### 4.2 L2 派生信号（部分已上线）

| 方法 | 状态 | 签名 | 说明 |
|---|---|---|---|
| `get_market_temperature()` | ✅ v1 | `async → {temperature: 0-100, level, signals[]}` | 规则打分，当前消费 `limit_pool_up + xueqiu_hot_stocks + tencent_hot_stocks + guba_popularity`；signals 是人类可读短句 |
| `get_sentiment_score(code=None)` | 🔜 | `async → float ∈ [0, 1]` | 决策引擎消费入口。code=None 时返回市场整体情绪得分；code 非空时返回单股情绪得分 |
| `get_overheat_set()` | 🔜 | `async → {code → penalty ∈ [0, 1], updated_at}` | 过热降权入口，决策引擎拿到后 `raw_impact × (1 − penalty)` |
| `get_leading_theme()` | 🔜 | `async → {theme, confidence}` | 当日市场主线（涨停原因集中度 + 雪球话题 top1 交集）|

### 4.3 对决策引擎的契约（关键）

**契约 1 — sentiment_score（权重 0.10）**：

- 输入：可选 `code`（六位股票代码或 sh/sz 前缀均可，内部归一化）。
- 输出：`float ∈ [0, 1]`，0.5 为中性，>0.5 为情绪偏多，<0.5 为偏空。
- 失败降级：任何数据源缺失 → 返回 `0.5`（中性），不抛异常，不阻塞打分流程。
- 不保证跨日稳定：`trade_date` 翻页前最后一次调用与翻页后第一次调用结果可能跳变，**这是特性不是缺陷**。

**契约 2 — overheat_penalty（降权倍率）**：

- 输入：无（返回当日全量过热 code 集合）。
- 输出：`dict[code, float ∈ [0, 1]]`；`penalty=0.3` 表示对该 code 的事件 impact 打 7 折。
- 上限：任何单只 code 的 penalty 不得 > 0.5（即最多打 5 折，避免把真实利好完全吃掉）。
- 缓存：决策引擎应在单次 batch 内缓存，不应每个事件都调一次。

**契约 3 — 失败降级原则**：
- L2 所有方法任何异常都返回"中性 / 空集"，绝不抛异常给决策引擎。
- DB 连接失败 → 视同"数据缺失" → 返回中性。
- L2 的失败应**只打 warning 日志**，不影响 L1 采集流程。

### Step 3：sentiment_score + overheat_set（🔜 待实施，本轮核心增量）

**目标**：为决策引擎提供稳定的单股/市场情绪得分接口 + 过热集合；通过规则合成多源信号，失败降级为中性。

**涉及文件**：
- `src/domain/collection/services/sentiment.py` — 新增 `get_sentiment_score(code)` / `get_overheat_set()` / `get_leading_theme()` 三个异步方法。
- 可选：新增 `src/domain/collection/services/sentiment_signals.py` — 把信号合成逻辑从 `SentimentAggregator` 拆出，避免单文件过大；若拆分需在原文件导入并转发。

**实现要点**：

1. **market_temperature → sentiment_score(None) 映射**：
   - `temperature ∈ [0, 100]` 归一到 `[0, 1]`：`score = temperature / 100`。
   - 但温度 > 80（extreme）时反向惩罚：`score = 0.6 − (temperature − 80) / 100`（极端过热情绪反而是风险，得分下调到 0.5 以下）。
   - 温度 < 20（cold） 时不下调到 0：`score = max(0.2, temperature / 100)`（极端冷淡时仍保留基础值，避免乘入公式后彻底消灭 sentiment 维度）。

2. **单股 sentiment_score(code) 合成规则**：
   - 基础分 = 0.5（中性）。
   - `xueqiu_hot_stocks` 当日上榜 + 排名前 10 → +0.10。
   - `tencent_hot_stocks` 当日上榜（任一时段）→ +0.10（与雪球独立叠加）。
   - `guba_popularity` 当日排名前 50 → +0.05。
   - `guba_posts` 该 code 帖子数 > 近 7 天均值 1.5 倍 → +0.10（激增）。
   - `limit_pool_up` 当日涨停命中 → +0.15。
   - clip 到 `[0, 1]`。
   - 7 天均值基线：`SELECT avg(jsonb_array_length(data->'posts')) FROM ft_sentiment WHERE data_type='guba_posts' AND data->>'code'=%s AND trade_date BETWEEN current_date-7 AND current_date-1`。

3. **overheat_penalty 判定规则**：
   - 同一 code 同日同时命中**至少 3 条**条件：在雪球热股榜 / 在腾讯热股榜 / 股吧人气前 30 / 涨停命中 / guba_posts 激增。
   - 命中条数 → penalty 映射：3 → 0.15；4 → 0.30；5 → 0.45（硬上限 0.5）。
   - 返回 dict 只放命中股票，不放中性/冷淡股。

4. **主线 leading_theme**：
   - 从 `limit_pool_up.data.info[]` 读各票的涨停原因字段，按原因分组计数。
   - 单一原因占比 > 30% → 产出 `{theme: 原因文本, confidence: 占比}`；否则 `{theme: None, confidence: 0}`。
   - 可选交叉：若该 theme 关键词出现在 `xueqiu_hot_topics` title → confidence ×1.2（封顶 1.0）。

5. **失败降级（必须）**：
   - 所有 L2 方法必须 `try/except Exception` 包住，失败返回中性值（`0.5` / `{}` / `{theme: None, confidence: 0}`）。
   - 失败时打 `logger.warning`，不抛出。

6. **性能控制**：
   - 所有 L2 方法一次调用内最多查 `ft_sentiment` 3 次（按 data_type 过滤，走索引）。
   - 单股 `get_sentiment_score(code)` 在单次决策 batch 内会被大量调用——**必须在 Aggregator 实例里缓存当天的全量 data_type 快照**，避免 N 只股票触发 N × 5 次查询。
   - 缓存失效：`trade_date` 翻页即失效（最简单：按 `(trade_date)` 做 dict key，跨日自动失效）。

**易错点**：
- **热股榜 code 字段不统一**：雪球返回 `SZ000001`，腾讯返回 `sz000001`，股吧人气返回 `000001`。比对前统一规整到**纯 6 位数字 + 大写前缀**（如 `SZ000001`），避免漏匹配。
- **guba_posts 7 天均值计算**：当天已经写入当日那条，做均值时必须 **排除 `current_date`**，否则"激增"永远以自己为基准，永远 1.0x。
- **limit_pool.data.info 字段名不固定**：涨停原因有时叫 `reason_type` 有时叫 `reason_stock_type`，写抽取函数时两种都尝试取。
- **get_sentiment_score 在 ft_sentiment 完全没当日数据时必须返回 0.5**，不能返回 0（否则权重 0.10 项直接归零、公式失衡）。

### Step 4：market_temperature v2（🔜 待实施，增强版）

**目标**：把当前 v1 的"单点值 + 文本 signal"升级为"加权合成 + 方向指示"，并修复已知短板。

**涉及文件**：
- `src/domain/collection/services/sentiment.py` — 改写 `get_market_temperature()`。

**实现要点**：

1. **纳入 limit_pool_down**：
   - 涨停数 / (涨停数 + 跌停数) 作为主指标：> 0.7 → +20，< 0.3 → −20。
   - 原单点阈值（> 80 / < 20）作为次级加权（防止总数太少时比值失真）。

2. **热股重叠度量化**：
   - 雪球热股 top 20 ∩ 腾讯热股 top 20 的交集大小 > 8 → +10（市场聚焦度高）；交集 < 3 → −5（分散，情绪冷）。

   - 当日 `guba_popularity` top 10 中，`rc`（热度值）均值 vs 历史 7 日均值；> 1.5 倍 → +10。

4. **方向指示**：
   - 返回新增 `trend: "rising" | "flat" | "falling"`，与前一个 tick 的温度比较（>+5 为 rising，<−5 为 falling）。
   - 前值缓存：进程内 dict，按 `trade_date` 存，跨日自然清空。

5. **signals 结构化**：
   - `signals` 从 `list[str]` 升级为 `list[{kind, delta, text}]`，保留人类可读 + 程序可过滤。

**易错点**：
- 历史 7 日均值查询若未命中（新部署），直接跳过该子项不加分（不要把它当作 1.0 倍作为"常态"触发加分）。
- `trend` 的前值必须在**函数外部**（实例字段）保存，不能函数内局部变量——否则每次调用都是 flat。
