# 事件反馈聚合（重新设计）

## 1. 需求分析

### 1.1 角色重定位：系统里唯一的"市场验证层"

前 5 个聚合模块（新闻/资金流/宏观/情绪/基础市场）都在回答**同一个问题**："现在发生了什么？" 它们是**输入侧**。事件抽取 + 事件流聚合把这些输入转成事件 → 打分 → 触发买入。

但这只是**开环**。一个买入决策下了以后，系统必须回答另一个问题：

- **下对了吗？** — 事件打分很高，但板块真的涨了吗？（策略复盘 / 胜率回填）
- **消息被消化了吗？** — 板块已经涨了 3%，追高还是放弃？（price-in 检测）
- **还该继续持有吗？** — 触发买入的事件流还在发酵，还是已经衰退？（事件失效止损）

这三个问题的答案不能从"当前输入"里拿，必须等市场**把事件走完**之后回填。这就是事件反馈聚合的唯一存在价值——它是**闭环的最后一块拼图**：

```
事件 (t=0)                市场反应 (t+1, t+3)           策略调整
───────── → ──────────────────────── → ─────────────
打分=0.82    板块 +4.2% / 北向 +18 亿      → 历史类比库 +1 样本（正样本）
下买入单     板块 -0.5% / 北向  -3 亿      → 胜率回归，下调该事件类型权重
                                              事件流衰退 → 止损退出
```

因此本模块的特殊性：

1. **不采集任何新数据**。复用 ft_market_flow / ft_news / ft_sentiment / ft_event_streams 已有数据做**纯 SQL 计算**。
2. **是唯一被时间驱动的聚合**：T+0 写不出结果，必须等到 T+1 盘后。Schedule 走 cron（`30 15 * * 1-5`），不是 interval。
3. **写入对象不是新表**，而是**回填 ft_events 的既有列**（sector_change_1d / north_flow_1d / feedback_at 等）。
4. **与实时决策分离**：trade_monitor（盘中每 5 分钟）做实时衰退止损；本模块做盘后 T+N 回填。两者数据用途不同，不重叠。

### 1.2 当前实际状态（与旧文档的纠偏）

旧文档断言 "ft_events 表未建 → 此 task 静默跳过"。**这已不符实情**。截至本轮：

| 组件 | 旧文档状态 | 真实状态 |
|---|---|---|
| `ft_events` 表 | ❌ 未建 | ✅ 已建（含所有回填列 + feedback_at） |
| AI 事件抽取流水线 | ❌ 未实现 | ✅ 已实装（`agg_event_extraction` + `agg_event_stream`，级联跑通） |
| `EventFeedbackAggregator` 代码 | 🔜 框架就位 | ✅ 框架 + `backfill_market_reaction` + `check_event_stream_decay` 均已实装 |
| 回填 `north_flow_1d` | ❌ | ✅ 已实装（走 `MarketFlowRepositoryImpl.get_northbound_net_flow`） |
| 回填 `sector_volume_change` | ❌ | ✅ 已实装（作为 T+1 板块净流入代理，走 `get_sector_net_inflow`） |
| 回填 `sector_change_1d / sector_change_3d` | ❌ | ❌ 仍未实装，**阻塞在缺 sector K 线数据源** |
| 回填 `reaction_delay_minutes` | ❌ | ❌ 未实装，**阻塞在缺分钟级板块行情** |
| 衰退检测 `check_event_stream_decay` | ❌ | 🟡 v1 已实装但仅用了 2 项信号（news_count_24h + fund_flow_2d），未接 `ft_event_streams.state` 与 `ft_sentiment` |

**核心判断**：本模块不是"等 ft_events 建表解锁"，而是"已部分上线，还剩 2 件事未补齐"——**① 涨跌幅回填缺数据源，② 衰退检测信号不完整**。

> 旧文档里"前置依赖：ft_events 表未建"的表述需要一并清除；真正的阻塞点换成"sector K 线源未并入 collect_market"。

### 1.3 边界与约束

1. **职责边界**：
   - 只"读+回填"，不"采集"。任何需要去外部 API 拉数据的需求都必须先加到对应聚合模块（资金流/基础市场），本模块只消费 ft_* 表。
   - 不负责**实时衰退止损**。那是 `trade_monitor` 的职责（盘中每 5 分钟，已走 ft_event_streams 的 state/momentum）。本模块的衰退检测服务于**盘后复盘 / 离线观察**，不直写决策表。
2. **时序约束**：
   - 回填 T+1 字段：事件 `event_time` 距今 ≥ 24h 才能算（否则 T+1 日还没走完）。
   - 回填 T+3 字段：事件 `event_time` 距今 ≥ 72h 才能算。
   - 回填范围窗口：近 3 天滚动（`find_unfilled_market_reaction(days=3)`）。再老的事件即便 sector_change_1d 为空也不再补（避免全表扫描 + 历史数据没有意义）。
3. **幂等约束**：
   - 单个事件的回填必须幂等：同一事件多次触发只更新一次；`update_market_reaction` 只在有有效字段时写入，配合 `feedback_at` 时间戳作为"已回填"标志。
   - `find_unfilled_market_reaction` 的筛选条件 `sector_change_1d IS NULL` 在 sector_change_1d 补齐之前，永远匹配；当前版本只补 north_flow_1d/sector_volume_change，此条件**会让每次跑都重复选中同一批事件**——这是当前代码的一个**性能坑**（见 §7）。
4. **技术复用**：
   - 不创建新的 Aggregator 基类派生品——`EventFeedbackAggregator` 已派生自 `BaseAggregator`，`sources = []` 表示不走 tick 的源遍历，只在 tick 里直接调业务方法。
   - 所有表读写走 Repository，不写裸 SQL（已有 2 个例外：`get_decay_signals` 用 `text()` 查 `ft_market_flow.sector_flow`，因为涉及 `data::text ILIKE` 模糊匹配；可接受）。

### 1.4 复杂度判定

**中等（拆 3 步）**

- 不简单：涉及新增数据源（sector K 线）+ 补齐回填字段 + 衰退算法升级；
- 不复杂：没有架构级改动，纯在已有 Aggregator / Repository 框架内扩列与补方法。

### 2.2 关键技术选型

| 决策点 | 选型 | 理由 |
|---|---|---|
| 触发方式 | **cron `30 15 * * 1-5`**（盘后 15:30） | T+1 字段必须收盘后才有值；与 `review_decision`（16:00）错峰避免 DB 写热点 |
| `sources = []` 的类派生 | 保留 `EventFeedbackAggregator(BaseAggregator)` 但 override `tick()` | 继承了 `_exec_ddl` / `_query_table` 工具，同时跳过源遍历；简洁且不破坏抽象 |
| "已回填" 标志 | `feedback_at IS NOT NULL` | 比"每列都 not null"更健壮——允许未来新增回填列而不废弃旧记录 |
| 选回填候选 | `sector_change_1d IS NULL AND event_time < now - 1d` | 窗口滚动 3 天；当 sector_change_1d 尚未实装时用 `feedback_at IS NULL` 代替（见 Step 1） |
| 衰退检测的去重 | **本模块不做决策，不写表**；只通过 AppService 暴露查询 | 避免与 `trade_monitor` 重复写 `ft_pending_decisions`，二者用途不同 |
| 正式涨跌幅字段 | 依赖新增 `sector_kline` 数据源入 `ft_market_cache` | 放到 collect_market，保证"板块 OHLC 序列"只在一处维护 |

### 2.3 与 trade_monitor 的职责划分（关键）

两者都"检查事件流衰退"，但角色完全不同：

| 维度 | `trade_monitor`（盘中） | `event_feedback.check_event_stream_decay`（盘后） |
|---|---|---|
| Schedule | 每 5 分钟 | 盘后 15:30 一次 |
| 扫描对象 | 持仓基金反查的 industries | 可指定任意 industries（一般来自已持仓 + 近 3 天高分事件） |
| 判据 | 严格：`stream.state ∈ {decaying, closed}` | 综合：news_count_24h / fund_flow_2d / state / sentiment 多信号加权 |
| 产出 | 直接写 `ft_pending_decisions`（sell 单） | 只返回 JSON 给 API / 复盘报表，**不写决策** |
| 目标 | 快速止损（秒级响应） | 离线复盘、事件库标注（分钟级响应） |

这个分工必须在文档和代码里都写清楚，避免将来有人把 `check_event_stream_decay` 改成直接写决策 → 与 trade_monitor 重复触发卖单。

## 3. 数据模型

### 3.1 ft_events 回填列（已建表，见 `src/infrastructure/persistence/models/extraction.py`）

```
sector_change_1d       double precision    — T+1 行业涨跌幅（%）     🔜 待 sector_kline
sector_change_3d       double precision    — T+3 行业涨跌幅（%）     🔜 待 sector_kline
sector_volume_change   double precision    — T+1 板块净流入（亿）    ✅ 已回填（作为成交量代理）
north_flow_1d          double precision    — T+1 北向净流入（亿）    ✅ 已回填
reaction_delay_minutes int                 — 事件→板块首次显著波动的分钟差  🔜 待分钟级 K 线
feedback_at            timestamptz         — 回填完成时间戳（去重 + 溯源）  ✅ Repository 自动写
```

> 字段语义已由 ORM 注释固定；本模块**不加新列**，只补齐回填逻辑。

### 3.2 不新建表

衰退检测结果**不落盘**。每次调用 `check_event_stream_decay(industries)` 都是现场计算，返回 JSON。原因：

1. 输入是动态的（持仓基金列表每日变化）；持久化一份 snapshot 会立刻过期；
2. 同样的数据已在 `ft_event_streams`（state/momentum）和 `ft_sentiment`（情绪趋势）里存在，额外落盘只是冗余；
3. 真要追踪历史趋势，走 `ft_event_streams` 的 `updated_at` 时序查询即可。

### 3.3 `sector_kline` 新增数据要求（落在 collect_market 侧）

为解锁 `sector_change_1d/3d` 和 `reaction_delay_minutes`，需要 `collect_market` 增加一个源：

| 字段 | 要求 |
|---|---|
| 数据类型 | `data_type = "sector_kline"` 存在 `ft_market_cache` |
| 粒度 | 日 K（涨跌幅）+ 分钟 K（反应延迟） |
| 覆盖 | 至少涵盖 `ft_events.industries[0]` 中出现过的所有行业名（以 `industry_mapping` 里的标准名为准） |
| TTL | 日 K 保留 7 天足够；分钟 K 保留当日即可 |

**由 collect_market 扩列维护**；本模块只负责**消费**。若该源不落地，本模块对应字段就持续为空，不影响 north_flow_1d / sector_volume_change 正常回填。

## 5. 实现步骤

### Step 1：修补当前代码的两个既存缺陷（独立于新功能，先做）

**目标**：让 `backfill_market_reaction` 不再重复处理同一批事件，并把"未回填"的定义从"某一列 NULL"改为"feedback_at NULL"，以支持后续渐进补齐字段。

**涉及文件**：
- `src/infrastructure/persistence/repositories/event_repository_impl.py` — `find_unfilled_market_reaction`
- `src/domain/extraction/services/event_feedback.py` — `_compute_reaction` 返回 None 时的处理

**实现要点**：

1. **筛选条件改写**：
   - 当前：`sector_change_1d IS NULL AND event_time < now - 1d`
   - 改为：`feedback_at IS NULL AND event_time < now - 1d`
   - 这样一旦一条事件跑过 `update_market_reaction`（哪怕只写了 north_flow_1d 一个字段），`feedback_at` 就会自动填入，下一轮不再重复选中。sector_change_1d 后续补齐时用另一条专门的 backfill 路径（见 Step 2）。
2. **"所有字段都拿不到" 时也要写 feedback_at**：
   - 当前 `_compute_reaction` 若 reaction dict 为空则返回 None，`update_market_reaction` 被跳过，feedback_at 永不写入 → 该事件每天被反复选中。
   - 改为：即便所有数据源都没拿到值，也调用 `update_market_reaction(event_id, {"feedback_at_only": True})`，让 `update_market_reaction` 仅写 feedback_at。
   - `update_market_reaction` 需同步调整：当入参 dict 只剩 feedback_at_only 时，也允许 `update_set = {"feedback_at": func.now()}` 而不是报 "no valid fields"。
3. **窗口下限**：`find_unfilled_market_reaction` 保留近 3 天滚动。**不要**把 days 调大到 7/30；超过 3 天没回填上通常是因为 industries[0] 映射错了或板块数据缺失，自动重试只是浪费时间，交给"待优化"处理。

**易错点**：
- `feedback_at` 的语义从"所有回填完成"变为"首次尝试回填"。文档、schema 注释、代码注释都要同步更新，避免将来有人把它当作"完整回填完成"标志（**易错点 1**）。
- 改筛选条件后，**老数据（已手工写过 north_flow_1d 但 feedback_at 还是 NULL 的历史行）** 会被重跑一次——这是一次性副作用，可接受。
- `update_market_reaction` 当前 `valid_fields` 白名单里没有任何"空列"的占位；Step 1 必须放开"仅写 feedback_at"的路径，否则流量会绕回老问题。

**测试用例**：

| 用例 | 输入/操作 | 预期结果 |
|------|-----------|----------|
| T1 | 造 1 条 ft_events（event_time = now - 36h, industries=["AI"]），ft_market_flow 存在对应日期的 northbound | 跑 1 次 backfill → 事件 north_flow_1d 有值、feedback_at 非空 |
| T2 | 同一条事件，立即再跑 backfill | 该事件不再出现在 `find_unfilled_market_reaction` 结果中 |
| T3 | 造 1 条 ft_events，industries=["不存在的行业"]，ft_market_flow 查不到任何值 | 跑 backfill → 所有回填列仍为 NULL 但 feedback_at 非空；下一轮不再选中 |
| T4 | 造 1 条 event_time = now - 6h 的事件（还没到 T+1） | `find_unfilled_market_reaction` 不返回该行 |
| T5 | 手动把某行 `feedback_at` 置空后再跑 | 该事件被选中并重新回填 |

**验收标准**：
- [ ] T1–T5 通过
- [ ] 连续跑 10 次 `backfill_market_reaction()`，第 2 次起 filled 恒为 0（幂等）
- [ ] 生产运行一晚后 `select count(*) from ft_events where feedback_at is null and event_time < now() - interval '1 day'` 为 0

**完成后检查点**：确认以上验收标准全部通过后再进入下一步。

### Step 2：补齐 `sector_change_1d / sector_change_3d / reaction_delay_minutes` 三个字段

**目标**：解锁**涨跌幅反馈**这一核心回填字段——这才是下游 reflection 和 price-in 过滤的主要输入。

**涉及文件**：
- `src/domain/collection/services/market.py` — 新增 `sector_kline` 源（日 K + 分钟 K），写入 `ft_market_cache(data_type='sector_kline')`，由 collect_market 的 1 分钟 Schedule 驱动。
- `src/infrastructure/persistence/repositories/market_cache_repository_impl.py` — 新增 `get_sector_change_pct` / `get_sector_first_spike_minute`。
- `src/domain/extraction/services/event_feedback.py` — `_compute_reaction` 增加 3 个字段的读取逻辑。

**实现要点**：

1. **sector_kline 源的接入位置**：放在 collect_market（每 1 分钟触发），不放本模块。理由：
   - 本模块 cron 仅盘后跑一次，无法拿到分钟级实时 K 线。
   - 其他决策链路（如将来要做的"板块 3d/5d 过热过滤"）也需要该数据，统一在 market 模块维护。
   - 本模块只做**读消费**，保持单一职责。
2. **sector_change_1d** 计算：读 `ft_market_cache[data_type=sector_kline]` 中 `trade_date = event_time.date() + 1d` 的日 K 线，取 `pct_change` 字段。
3. **sector_change_3d** 计算：读 T+1、T+2、T+3 三天日 K，**累乘**（`(1+p1)*(1+p2)*(1+p3) - 1`）而不是**累加**——累加对 3% 以上的日涨跌幅误差不可接受。
4. **reaction_delay_minutes** 计算：
   - 从 `event_time` 开始，在 `sector_kline` 的分钟 K 序列里滚动，找**首次** 累计涨跌幅绝对值 ≥ 1.0% 的分钟点。
   - 如果当日交易时段内都没突破，返回 `None`（意味着"市场未显著反应"或"事件发布在非交易时段"）。
   - 阈值 1.0% 是粗估，后续可调参；进"待优化"记一条。
5. **多 industries 选择**：事件的 `industries` 是列表，可能多个板块。本轮只用 `industries[0]`（已是代码现状）。如果 `industries[0]` 在 sector_kline 里不存在则尝试 `industries[1]`，还不存在则该事件的 3 个字段都留空（不报错）。
6. **event_time 在非交易时段的处理**：夜间/周末发布的事件，T+1 应该取**下一个交易日**。直接 `event_time.date() + 1d` 会错。需要从 `ft_market_cache[data_type=market_overview]` 或新增一个交易日历工具拿"下一个交易日"。若怕引入新依赖，先用粗策略"跳过周末"（周五晚事件 → T+1 = 下周一）；节假日误差认为可接受 v1。

**易错点**：
- 累计涨跌幅用**累乘**不是**累加**（**易错点 1**）。
- 交易日历缺失导致节假日 T+1 取成假日，查表为 None → reaction 丢失。v1 接受、记入待优化（**易错点 2**）。
- 分钟 K 线数据量大（每板块每日约 240 条），`ft_market_cache` 的 JSONB 列不适合放整段序列；更好的做法是 `data_type='sector_kline_min'` 下存单条分钟，但这需要 `ft_market_cache` 支持多行 per (trade_date, data_type)——查 schema 确认是否允许多行。若不允许，临时在 JSONB 里存 array。
- sector 名称必须与 ft_events.industries[0] 严格对齐。若 collect_market 用的板块名来自东财接口（如"人工智能板块"），而 AI 抽取用的是"AI"，要在 `industry_mapping` 表加标准化；**由 industry_mapping 模块负责**，本模块不做。

**测试用例**：

| 用例 | 输入/操作 | 预期结果 |
|------|-----------|----------|
| T1 | 造事件 event_time = 某周三 10:00，industries=["AI"]，ft_market_cache 有周四 AI 板块 +2.3% 日 K | sector_change_1d ≈ 2.3 |
| T2 | 同上，ft_market_cache 有 T+1~T+3 涨跌幅 +2.3% / -1.0% / +0.5% | sector_change_3d ≈ (1.023*0.99*1.005 - 1) * 100 ≈ 1.78 |
| T3 | 同上，分钟 K 线 event_time + 35min 首次累计 +1.2% | reaction_delay_minutes = 35 |
| T4 | event_time 是周五晚上 20:00 | T+1 取下周一，不取周六 |
| T5 | industries[0]="不存在板块", industries[1]="AI" 存在 | 走 industries[1]，字段有值 |
| T6 | sector_kline 源暂停 / 无数据 | 三字段全 None，但 feedback_at 写入、不抛异常 |

**验收标准**：
- [ ] T1–T6 通过
- [ ] collect_market 的 sector_kline 源入库成功且日更新
- [ ] 随机抽 10 条 T+1 事件，手工 SQL 验算 sector_change_1d 误差 < 0.1%
- [ ] reaction_delay_minutes 非空率 > 50%（剩余为非交易时段或真无反应）

**完成后检查点**：确认以上验收标准全部通过后再进入下一步。

### Step 3：衰退检测升级 v2（接入 ft_event_streams + ft_sentiment）

**目标**：把 `check_event_stream_decay` 从"2 信号粗打分"升级为"4 信号加权综合评分"，使其在**盘后复盘**场景下比 trade_monitor 的严格判据更敏感、更早发出"事件开始衰退"的警报。

**涉及文件**：

**实现要点**：

1. **4 个信号**（与分值贡献）：

   | 信号 | 来源 | 触发条件 | 贡献分 |
   |---|---|---|---|
   | 新闻密度低 | `ft_news` ILIKE %industry% | `news_count_24h < 3` | +0.25 |
   | 连续 2 天板块净流出 | `ft_market_flow.sector_flow` | 近 2 天 net_amount < 0 | +0.30 |
   | 事件流状态恶化 | `ft_event_streams` | `state ∈ {decaying, closed}` | +0.30 |
   | 情绪由正转中性/负 | `ft_sentiment` 近 3 天趋势 | `sentiment_trend ∈ {falling, negative}` | +0.15 |

   `decay_score = min(1.0, sum(贡献分))`，signals 列表为命中的信号人类可读描述。

2. **行业名规范**：与 Step 2 相同，以 `industry_mapping` 的标准名为准；未标准化的行业一律只用 ILIKE 模糊匹配（当前 `get_decay_signals` 已在这样做）。

3. **情绪趋势计算**（`get_sentiment_trend`）：
   - 读 `ft_sentiment` 中 data_type 为 `guba_posts` / `xueqiu_hot_stocks` / `tencent_hot_stocks` 的近 3 天行，筛选含 industry 关键词的记录；
   - 每天算一个均值（字段名如 `mood_score` 需依 ft_sentiment 实际 JSONB 结构调整，本步需先 `\d` 看一眼）；

4. **本模块不直接写决策**：
   - `check_event_stream_decay` 返回 `[{industry, signals, decay_score}]` 即可；
   - 若将来有人想"高 decay_score 触发卖单"，让他走 `trade_monitor` 通道，本模块保持只读。**这一点必须在函数 docstring 里显式声明**。

**易错点**：
- `ft_event_streams` 中同一 industry 可能有多条（历史 + 当前），必须取 `last_event_at DESC LIMIT 1`（**易错点 1**）。

## 下游消费契约（供 reflection 模块等下游使用）

### feedback_at 语义

- `feedback_at` 为"首次尝试回填"的时间戳，**不是**"完整性标志"。
- `feedback_at IS NULL` 表示"从未尝试过回填"（事件尚未进入回填窗口或任务尚未执行）。
- `feedback_at IS NOT NULL` **不保证**任何反应字段非空（可能全部为 NULL，原因包括：该事件无关联板块、外部接口失败、K 线数据源尚未覆盖等）。

### 下游字段完整性判断

下游（reflection 等）若依赖某些字段，必须**显式校验目标列非空**：

```python
# 正确
if event.sector_change_1d is not None and event.north_flow_1d is not None:
    do_reflection(event)

# 错误（会把"已尝试但字段为空"的事件当作可用样本）
if event.feedback_at is not None:
    do_reflection(event)
```

### 字段填充来源对照表

| 字段 | 数据源 | 未填充的可能原因 |
|------|--------|-----------------|
| north_flow_1d | ft_market_flow / northbound | 接口失败 / 非交易日 |
| sector_volume_change | ft_market_flow / sector_flow | 事件无关联行业 / ILIKE 未命中 |
| sector_change_1d/3d | ft_market_cache / sector_kline | sector_kline 源未覆盖该板块 |
| reaction_delay_minutes | sector 分钟 K（按需查询） | 分钟 K 未采集 / 非交易时段事件 |
