# Claude CLI tmux会话池LLM代理层实施方案

> **文档定位**：这是 `AI事件抽取`、`金融知识图谱 / GraphRAG`、`KG compiler` 共用的 LLM 基础设施方案。  
> 目标是把真实 Claude 客户端包装成稳定的 OpenAI-compatible API，让上层只调用 HTTP 接口，不感知 Claude TUI、tmux、JSONL、确认弹窗和会话管理。

---

## 0. 一句话结论

> **使用真实 Claude 客户端，通过 tmux 维护一个预热会话池；每个请求独占一个会话，完成后执行 `/clear` 清理上下文，并从 Claude JSONL 会话文件读取本次新增输出。**

经测试，Claude 的非交互 print 模式在当前 GLM-5.1 路线下会触发 429 风控，已弃用。后续不再围绕该路线设计。

最新实现补充：

- 当前主路径为 `tmux_pool`，生产配置已验证 `pool_size=10` / `max_concurrency=10` 可启动。
- GraphRAG 长 prompt 不再直接完整粘贴进 Claude TUI；超过阈值后先写入沙盒任务文件，再让 Claude 使用 `Read` 工具读取。
- 对 Claude 的提示词不得写成“我是 OpenAI-compatible API 后端”或“纯 LLM 后端”。这类措辞既没有必要，也会污染模型语境。
- 代理层对外可以是 OpenAI-compatible API，但对内给 Claude 的指令应是中性的“独立文本任务”。

---

## 1. 总体链路

```text
GraphRAG / KG compiler / L1a / L2 / L3
  -> OpenAI-compatible HTTP API
  -> LLM Proxy
  -> tmux Claude 会话池
  -> 借出一个 idle Claude 会话
  -> 短 prompt: bracketed paste 发送 prompt
  -> 长 prompt: 写入 request-context 文件，只 paste 文件读取指令
  -> 等待 Claude 回到 idle prompt
  -> 读取 JSONL 中本次新增 assistant 输出
  -> 执行 /clear
  -> 归还会话到池
```

上层看到的是：

- `GET /api/llm-proxy/health`
- `POST /v1/chat/completions`

上层不应该知道：

- 是否使用 tmux。
- Claude 会话如何启动。
- TUI 是否弹过确认框。
- JSONL 文件在哪里。
- 会话是否被复用。

---

## 2. 为什么必须做会话池

一次性 tmux 会话已经验证过链路可行，但不适合作为生产形态。

原因：

1. 每个请求都启动 Claude 客户端，延迟高。
2. 频繁创建和销毁会话不符合真实用户使用方式，可能增加风控风险。
3. GraphRAG、KG compiler、L1a 都可能产生批量请求，冷启动成本会被放大。
4. Claude 启动阶段可能出现 onboarding、权限、安全确认，不应该进入每次请求的关键路径。

因此生产形态必须是：

```text
服务启动时预热 N 个 Claude 会话
请求到来时借出一个
请求结束后 /clear
会话健康则归还
会话异常则销毁重建
```

建议从 `pool_size=2` 开始验证，稳定后再逐步扩大。当前已验证 `pool_size=10` 能启动并可被 GraphRAG 查询链路使用，但上游仍可能出现 429，因此并发不是越大越好，需要配合限流和错误治理。

## 3. 会话池模型

### 3.1 会话状态

每个 Claude 会话至少有这些状态：

| 状态 | 含义 |
|---|---|
| `starting` | 正在启动 Claude 客户端 |
| `idle` | 可接收请求 |
| `busy` | 正在处理请求 |
| `clearing` | 正在执行 `/clear` |
| `unhealthy` | 出现异常，等待销毁重建 |
| `closed` | 已关闭 |

### 3.2 借出规则

请求只能借出 `idle` 会话。

借出后：

1. 标记为 `busy`。
2. 记录本次请求 id。
3. 记录 JSONL 文件当前 offset 或最后 message id。
4. 发送 prompt。
5. 等待结果。

同一个 Claude 会话同一时间只能处理一个请求。

### 3.3 归还规则

请求成功后：

1. 解析本次新增 assistant 输出。
2. 执行 `/clear`。
3. 等待 Claude 回到 idle prompt。
4. 更新 JSONL offset / message id。
5. 标记为 `idle`。

请求失败时：

- 超时：销毁重建。
- 未知弹窗：销毁重建。
- `/clear` 失败：销毁重建。
- JSONL 解析失败：销毁重建。
- Claude 进程退出：销毁重建。

## 4. Claude 启动策略

每个会话启动真实 Claude CLI：

```text
claude --dangerously-skip-permissions --session-id {session_id} --model {model} --setting-sources ""
```

启动要求：

| 项 | 要求 |
|---|---|
| `HOME` | 指向隔离目录 |
| `XDG_CACHE_HOME` | 指向隔离目录 |
| `XDG_CONFIG_HOME` | 指向隔离目录 |
| `XDG_STATE_HOME` | 指向隔离目录 |
| workdir | 指向代理层隔离 workdir |
| env | 从 `.env` 注入 provider 配置 |
| settings | 尽量避免读取本机 Claude project 设置 |

隔离目标：

- 不读取当前项目上下文。
- 不读取历史会话。
- 不带入 Claude project 记忆。
- 减少无关 token 消耗。
- 降低输出被本地上下文污染的概率。

## 5. Prompt 发送方式

必须使用 tmux bracketed paste：

```text
tmux paste-buffer -p
```

原因：

- OpenAI messages 会被映射成多行 prompt。
- 普通 paste 可能把换行当成多次 Enter。
- 这会导致半截 prompt 被提前提交。

发送流程：

1. 把 prompt 写入临时文件。
2. `tmux load-buffer`。
3. `tmux paste-buffer -p`。
4. `tmux send-keys Enter`。

### 5.1 长上下文处理

GraphRAG 的 prompt 可能包含社区报告模板、JSON Schema、实体表、关系表和 grounding rules。把这类长 prompt 直接粘贴到 Claude TUI 有两个问题：

1. TUI 处理长文本更慢，容易出现等待、误判 idle、超时。
2. Claude Code 是 agent 形态，长上下文更适合通过文件和 `Read` 工具渐进读取。

因此代理层采用阈值策略：

```text
len(rendered_prompt) <= CLAUDE_PROXY_FILE_CONTEXT_THRESHOLD_CHARS
  -> 直接 paste

len(rendered_prompt) > CLAUDE_PROXY_FILE_CONTEXT_THRESHOLD_CHARS
  -> 写入 /tmp/smart-fund-claude-proxy/request-contexts/{request_id}.md
  -> paste 短指令：读取该任务文件并按文件要求输出
```

任务文件内容包含：

- system instructions
- user prompt
- JSON Schema / response format 约束
- max_tokens 提示

给 Claude TUI 的短指令必须满足：

- 只要求读取本次任务文件。
- 不联网。
- 不读取或搜索其他本机文件，除非任务文件明确要求。
- 不提及代理层、API 包装、OpenAI-compatible 等实现细节。

实测结果：

- 强制长 prompt 已生成 `request-contexts/*.md`。
- Claude JSONL 中可观察到 `Read` 工具调用。
- GraphRAG local query 已触发该路径，任务文件约 17KB，回答正常。
- 会话中已确认不再出现旧的 `OpenAI-compatible` / `纯 LLM 后端` 文案。

## 6. JSONL 读取方式

不要从 tmux 屏幕读取最终答案。

正确来源是 Claude 会话 JSONL：

```text
{HOME}/.claude/projects/**/{session_id}.jsonl
```

必须读取：

- assistant text
- tool_use
- usage
- model
- session_id

会话池模式下必须增量读取：

1. 请求开始前记录 JSONL offset 或最后 message id。
2. 请求完成后只读取新增 assistant 消息。
3. usage 只统计本次新增 assistant 消息。
4. `/clear` 不会删除 JSONL 历史，所以不能读取全文件拼接。

如果不做增量边界，会污染响应：

- 上一次回答混入本次结果。
- usage 统计膨胀。
- GraphRAG 收到错误上下文。

## 7. `/clear` 策略

每个请求结束后执行：

```text
/clear
```

目的：

- 清理 Claude 当前对话上下文。
- 避免下一个请求继承上一个请求。
- 保留客户端进程，减少冷启动。

要求：

1. 只有结果解析成功后才执行 `/clear`。
2. `/clear` 后必须等待 idle prompt。
3. `/clear` 失败则销毁该会话。
4. 请求超时或异常时不归还会话，直接销毁重建。
5. 会话达到最大请求数或最大存活时间后主动轮换。

注意：

> `/clear` 只清理 Claude 客户端上下文，不清理 JSONL 历史文件，所以必须配合 JSONL 增量读取。

## 8. 自动确认弹窗

Claude TUI 可能弹出确认界面。代理层采用：

> **白名单自动确认，未知弹窗快速失败。**

自动确认范围：

| 弹窗 | 处理 |
|---|---|
| 主题选择 | Enter |
| Security notes | Enter |
| Dangerous bypass warning | 选择 `Yes, I accept` |
| Trust folder | Enter |
| Do you want to proceed | Enter |
| Do you want to create / overwrite | Enter |
| command approval | Enter |

未知弹窗：

1. 停止当前请求。
2. 捕获最近 TUI 屏幕内容。
3. 标记会话 unhealthy。
4. 销毁重建。
5. 人工判断是否加入白名单。

不能盲目对所有弹窗按 Enter。

## 9. 对外 API

### 9.1 Health

```text
GET /api/llm-proxy/health
```

建议返回：

```json
{
  "status": "ok",
  "provider": "tmux_pool",
  "model": "sonnet",
  "pool_size": 2,
  "idle_sessions": 2,
  "busy_sessions": 0,
  "unhealthy_sessions": 0
}
```

### 9.2 Chat Completions

```text
POST /v1/chat/completions
```

要求：

- 兼容 OpenAI chat completions 基本响应结构。
- `stream=true` 第一版不支持。
- `messages` 映射成 prompt。
- `system` 单独作为 system 段。
- `response_format=json_schema/json_object` 时追加 JSON 输出约束，并在代理层解析。

## 11. 与 GraphRAG 的关系

GraphRAG 只接 OpenAI-compatible endpoint：

```text
Microsoft GraphRAG
  -> /v1/chat/completions
  -> LLM Proxy
  -> tmux_pool Claude session
  -> JSONL result
```

GraphRAG 不需要知道：

- tmux 会话池。
- Claude TUI。
- `/clear`。
- JSONL offset。
- provider 具体实现。

但 GraphRAG 有一个关键特征：

- indexing 阶段会产生长 prompt，尤其是 `extract_graph`、`create_community_reports`。
- query 阶段的 Local / Global / DRIFT 也可能携带大量上下文。

因此 GraphRAG 接入时必须启用长上下文文件策略，避免把大型 prompt 直接粘贴进 TUI。

当前实测结论：

- `generate_text_embeddings` 不是主要瓶颈，真实 embedding 调用耗时很低。
- 慢点主要在 LLM completion，尤其是 `extract_graph`、`create_community_reports` 和查询阶段。
- `pool_size=10` 可以提高可用并发，但小语料无法吃满 10 个会话。
- 上游 GLM-5.1 在多会话并发下仍可能出现 `429 code=1302`，代理层可能将后端失败包装成 HTTP 502。
- 后续应把 429、超时、无有效输出分别映射为更准确的错误类型，而不是全部返回 502。

## 12. 与 L1a / KG compiler 的关系

L1a：

```text
ft_news
  -> L1a
  -> LLM Proxy
  -> structured event JSON
  -> ft_events / KG compiler
```

KG compiler：

```text
document / evidence
  -> LLM Proxy
  -> alias / related_to / causal_hint candidates
  -> ontology / evidence / confidence validation
  -> kg_edges
```

所有调用都必须走 LLM Proxy，不允许各模块直接操作 Claude CLI。

## 13. 与 embedding 的边界

本代理层只负责 completion。

| 能力 | 当前边界 |
|---|---|
| completion | LLM Proxy + tmux_pool |
| GraphRAG embedding | T0 只确认能力边界 |
| 业务 semantic_search | Phase 3 在混合召回里实现 |
| Milvus / 专用向量库 | 当前不引入 |

completion 和 embedding 不混在一个实现里。

## 14. 验证结论

已经验证：

1. 真实交互式 Claude 可以正常返回。
2. tmux pool 链路已跑通。
3. `/v1/chat/completions` 可返回结构化 JSON。
4. 底层模型为 `glm-5.1`。
5. 多行 prompt 已用 bracketed paste 修复。
6. 已知 Claude TUI 确认弹窗可以自动处理。
7. `pool_size=10` / `max_concurrency=10` 已验证可启动。
8. 长 prompt 文件上下文策略已验证，Claude 会通过 `Read` 读取任务文件。
9. GraphRAG local query 已通过该代理层成功返回。

当前剩余优化：

- 错误码治理：区分上游 429、tmux 超时、JSONL 无有效输出。
- 压测治理：根据上游限流情况决定 `pool_size`、`max_concurrency`、`MIN_INTERVAL` 和 GraphRAG rate limit。
- session id 治理：返回给调用方的 session id 应指向本次实际处理请求的 JSONL，而不是 `/clear` 后的新会话文件。

## 15. 风险与处理

| 风险 | 处理 |
|---|---|
| `/clear` 失败 | 会话销毁重建 |
| JSONL 边界解析错误 | 请求前记录 offset / message id，只读新增 assistant |
| 未知 TUI 弹窗 | 快速失败，销毁会话，人工加入白名单 |
| 会话长期复用状态漂移 | max requests / max age 后主动轮换 |
| tmux session 泄漏 | 由会话池登记和统一清理 |
| GraphRAG 批量请求过多 | pool size、全局并发、GraphRAG rate limit 联合控制 |
| 长 prompt 直接粘贴导致卡顿 | 超过阈值写入任务文件，让 Claude 用 `Read` 读取 |
| 上游 429 被包装成 502 | 后续细化异常类型与 HTTP 映射 |
| 返回 session_id 指向 `/clear` 后会话 | 后续保留 request_session_id 和 post_clear_session_id |

## 16. 实施顺序

1. 实现 `tmux_pool`。
2. 支持会话预热、借出、归还、销毁重建。
3. 支持 JSONL 增量解析。
4. 支持请求结束 `/clear`。
5. 支持 pool health。
6. 先用 `pool_size=2` 压测。
7. 稳定后再逐步扩大，最多不超过 `10`。
8. 接 GraphRAG completion 真实请求。
9. 加入长上下文文件策略。
10. 针对 GraphRAG indexing/query 分别压测并发与限流。

---

## 17. 最终结论

本方案主题是：

> **Claude CLI tmux 会话池代理层。**

核心不是某个 CLI 参数，而是：

- 对上提供稳定 OpenAI-compatible API。
- 对下复用真实 Claude 客户端。
- 用 tmux 管理会话池。
- 用 JSONL 增量解析结果。
- 请求后 `/clear` 清理上下文。
- 异常会话销毁重建。

这才是后续 GraphRAG、KG compiler、L1a 应该依赖的统一 LLM 基础设施。
