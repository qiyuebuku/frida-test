### 2.4 数据聚合的关键 bug 修复

#### ft_news 表结构不匹配
- **问题**：旧版 ft_news 用 `text[]` 类型的 tags，代码写入 JSONB，静默失败 → 入库 0 条
- **修复**：drop 重建 ft_news 表，统一 JSONB 结构

#### summary/content 双字段设计
- **问题**：早期 ft_news 只有 content 字段，且 sina 列表页 summary 对同一会议的多篇文章返回相同内容，污染事件抽取
- **修复**：
  - 新增 `summary` 字段（列表页摘要，短）
  - `content` 字段改为详情页真实正文（长，AI 抽取用）
  - `BaseClient._fetch_article_html()` + `_extract_article_text()` 通用工具
  - sina/ths/eastmoney/pboc 都添加 `fetch_article_content()` 方法
  - get_news 方法的 `with_content=True` 参数并发抓取所有详情页

#### HTML 正文提取算法
- **问题**：`<div id="artibody">(.*?)</div>` 非贪婪匹配遇到嵌套 div 时截断
- **修复**：按 `<div>/</div>` 嵌套深度配对提取，剥离 `<script>/<style>`，截断"新浪声明"等尾巴噪音

#### 桌面端 User-Agent
- **问题**：BaseClient DEFAULT_HEADERS 是 Android 手机 + 同花顺 Referer，访问 sina 详情页返回空或移动版
- **修复**：新增 `BaseClient.ARTICLE_HEADERS`（桌面 UA + 财经 Referer），`_fetch_article_html` 强制覆盖

#### ft_raw_data 写入失败
- **问题**：字符串标量（如空字符串 `""`）直接存入 jsonb 字段，不是合法 JSON 字面量
- **修复**：`raw_data.save_raw` 中所有数据类型都走 `json.dumps()`

#### PDF 二进制污染
- **问题**：gov client 遇到 PDF URL 时抓到二进制内容，写入 jsonb 失败报 `Unicode escape sequence` 错误
- **修复**：`_fetch_article_html` 按扩展名预判（`.pdf/.doc/...`）+ `Content-Type` 检测，非 HTML 直接返回空

#### 批次内 content hash 去重
- **问题**：sina 编辑把同一次发言拆成多篇不同标题的文章，fingerprint 精确去重无法识别
- **修复**：`NewsAggregator._save()` 计算 `SHA256(content)`，同内容只保留第一条

#### 字段命名统一
- **问题**：`ft_market_flow.captured_at` / `ft_sentiment.captured_at` 与其他表 `created_at` 不一致
- **修复**：统一为 `created_at`，代码同步更新

### 3.1 stock_flow 硬编码单只股票

**现状**：
```python
SourceDef(
    "stock_flow",
    lambda cp: clients.tencent.get_stock_fund_flow("sh600519"),  # 硬编码贵州茅台
```

**问题**：
- 只采集一只固定股票，数据覆盖面严重不足
- 决策引擎无法判断"基金重仓股的资金流向"
- 原设计是采集 `000300` 沪深 300 指数，但腾讯接口对指数返回空数据

**目标方案**：
```python
async def fetch_stock_flow_dynamic(cp):
    """从 ft_positions 读取持仓基金的所有重仓股，批量采集"""
    from src.infrastructure.db.fund_db import get_held_stocks

    results = await asyncio.gather(*[
        clients.tencent.get_stock_fund_flow(code) for code in codes
    ], return_exceptions=True)
    return [r for r in results if not isinstance(r, Exception)]
```

**工作量**：2-3 小时

### 3.4 跨源标题相似度去重未实现

**现状**：只有同源 `fingerprint = SHA256(title + source)` 精确去重。

**问题**：同一条新闻被 cls + eastmoney + sina 重复入库（措辞略有不同）。

**目标方案**：
```python
# 在 NewsAggregator._save() 中，入库前做一次跨源相似度检查
def _dedupe_cross_source(self, items):
    from difflib import SequenceMatcher
    today = date.today().isoformat()
    # 查今天已入库的所有标题
    existing_titles = self._query_today_titles(today)
    filtered = []
    for item in items:
        is_dup = False
        for exist_title in existing_titles:
            if SequenceMatcher(None, item["title"], exist_title).ratio() > 0.85:
                is_dup = True
                break
        if not is_dup:
            filtered.append(item)
            existing_titles.append(item["title"])
    return filtered
```

**优先级**：P2
**工作量**：3-4 小时

### 4.2 实施顺序

**步骤 1：建表 DDL**
- `ft_events`（含 embedding 字段，bytea 或 pgvector）
- `ft_news` 新增字段：`event_extracted BOOLEAN DEFAULT FALSE`（避免重复抽取）
- `ft_event_streams`（事件流状态机）

**步骤 2：预筛选逻辑**
- 目的：过滤掉"广告/行情播报/纯数据"类新闻，避免每条都调 AI 浪费 token
- 方法：
  - 关键词过滤（白名单：政策/支持/发布/启动/...）
  - 长度过滤（content < 100 字跳过）
  - 按 source reliability 阈值
  - 可选：先用本地 embedding 计算与"已抽取事件"的相似度，高相似度跳过

**步骤 3：AI 抽取 task**
```python
@router.task(queue="agg_event_extraction", max_retries=2)
async def agg_event_extraction():
    # 1. 查 ft_news where event_extracted=false, limit=50
    news_list = db.query_unextracted_news(limit=50)

    # 2. 预筛选
    candidates = [n for n in news_list if should_extract(n)]

    # 3. 批量调 Claude Haiku（便宜）
    #    prompt 强制返回 JSON schema
    events = await claude_batch_extract(candidates)

    # 4. 校验 schema + 写 ft_events
    for event in events:
        if validate_schema(event):
            save_event(event)

    # 5. 标记 ft_news.event_extracted=true
    mark_extracted([n.id for n in news_list])
```

**步骤 4：Embedding 生成**
- 选项 A：sentence-transformers（本地，免费，速度慢）
- 选项 B：OpenAI `text-embedding-3-small`（便宜，快，要网络）
- 选项 C：阿里通义 embeddings（国内速度快）
- 存储：`ft_events.embedding BYTEA`（numpy tobytes）或 `pgvector`

**步骤 5：事件流聚合 task**
- 按 `industry` + 时间窗口（24-72h）聚类事件
- 计算 momentum（新闻密度一阶导数）
- 写入 `ft_event_streams`
- 状态机：emerging → fermenting → peak → decay → expired

**步骤 6：激活 agg_event_feedback**
- ft_events 表建好后代码自动生效
- 盘后 15:30 扫描近 3 天事件，回填 `sector_change_1d/3d`、`north_flow_1d`

**优先级**：**P0（最高）**
**工作量**：5-7 天

### 5.2 task 链路设计

```
agg_event_stream (每 10 min) ──→ ft_event_streams (momentum=increasing)
                                         │
                                         ↓
trade_decision (每 1 min) ── 扫描发酵中的事件流
                              ├─ 硬过滤：certainty/novelty/event_age/sector_rise
                              ├─ 查映射表：industry → index → fund
                              ├─ 历史类比：embedding topK → 过去 T+1/T+3 收益
                              ├─ 打分：impact × 0.35 + novelty × 0.15 + ...
                              ├─ 动态仓位：base × winrate_factor × market_factor
                              └─ 写 ft_decisions (status=pending_execution)
                                         │
                                         ↓
trade_execution (每 30s) ── 扫描 pending 决策
                             ├─ 再次检查：总仓位/日内交易数/同行业限制
                             ├─ 调 clients.trade.buy_fund(code, amount)
                             ├─ 写 ft_trades
                             ├─ 更新 ft_positions
                             └─ 标记 ft_decisions.status=executed
                                         │
                                         ↓
trade_monitor (每 5 min) ── 扫描 ft_positions
                             ├─ 检查硬止损：loss < -3% → 卖
                             ├─ 检查事件流衰退：关联的 ft_event_streams.momentum=decreasing
                             ├─ 检查加仓条件：profit > 2% AND event_strength_increasing
                             └─ 触发买/卖/加仓
                                         │
                                         ↓
review_decision (盘后 16:00) ── 扫描当日 executed 决策
                                ├─ 计算收益（对账 ft_trades）
                                ├─ 判断 correct/wrong/neutral
                                ├─ 更新胜率统计
                                └─ 写 ft_reviews（驱动下次的 winrate_factor）
```

### 5.3 关键设计决策

#### 决策幂等性
同一事件 + 同一基金不能下两次单：
```sql
CREATE UNIQUE INDEX idx_decisions_unique ON ft_decisions(event_id, fund_code, decision_date);
```

#### 资金限额接入
`ft_fund_limits` 表已存在（存放基金限购状态），决策引擎必须先查：
```python
async def check_fund_limits(fund_code):
    row = db.query("SELECT status, daily_limit FROM ft_fund_limits WHERE fund_code=%s", fund_code)
    if row and row["status"] == "suspended":
        return False  # 暂停申购
    return True
```

#### 风控硬约束
- 单次最大仓位 30%
- 同行业最大仓位 40%
- 总仓位上限 60%（永远留 40% 现金）
- 日内最大交易数：3 笔
- 连续 2 笔亏损 → 暂停 1 天

**优先级**：**P0**（解锁核心价值）
**工作量**：3-5 天

## 六、架构层面的优化建议

### 6.1 定时轮询 vs 事件驱动

**当前模式**：所有聚合 task 都是定时轮询（scheduler 每 N 分钟触发一次）。

**问题**：
- 决策 task 如果每 1 分钟扫描整个 `ft_events` 表，数据量大后会变慢
- 新事件入库到决策触发之间有最高 1 分钟延迟

**建议**：对**决策链路**改用**事件驱动**：

```python
# 事件入库后立即触发决策检查
@router.task(queue="agg_event_extraction")
async def agg_event_extraction():
    events = await extract_events()
    save_events(events)

    # ★ 新事件入库 → 立即发消息触发决策
    if events:
        await app.send([
            TaskMessage(queue="trade_decision", kwargs={"event_ids": [e.id for e in events]})
        ])

@router.task(queue="trade_decision")
async def trade_decision(event_ids: list):
    """被动触发：只处理新事件（而非扫描全表）"""
    events = db.query_events(event_ids)
    ...
```

**好处**：
- 决策延迟从"1 分钟级"降到"秒级"
- 数据库扫描压力从 O(N) 降到 O(新增事件数)
- jettask 的消息队列天然支持这个模式

### 6.2 决策的并发安全

**问题**：如果多个 worker 并发消费 `trade_decision` 队列，同一事件可能被打分两次，甚至下单两次。

**方案**：
- `trade_decision` worker 并发数设为 1（串行）
- 或在 `ft_decisions` 上加 `UNIQUE(event_id, fund_code)` 约束 + `ON CONFLICT DO NOTHING`

### 6.3 股票扩展

**当前限制**：只能交易基金（天天基金 client）。

**用户明确提到**："不仅仅是基金交易哦"，暗示未来要扩展到股票。

**扩展路径**：
1. **Client 层**：新增 `infrastructure/clients/broker.py`（券商交易 API，如华泰/国泰君安/同花顺交易）
2. **决策层**：在 `ft_industry_mapping` 中同时映射 ETF 基金和个股
3. **执行层**：`trade_execution` task 按 `decision.asset_type` 分发到 `buy_fund` 或 `buy_stock`
4. **风控层**：股票有涨跌停限制、T+1 限制、单笔最小金额，需要单独的规则分支

**评估**：架构层面 OK，主要工作量在 broker client（实盘账户 + API 权限）。

### 6.4 幂等性 + 可重放

**当前数据已经做到可重放**（`ft_raw_data` 永久保留），但决策和执行没有。

**建议**：
- `ft_decisions.source_events` JSONB 字段保留打分时用的所有事件 ID
- `ft_trades.decision_id` 外键
- 任何一次错误交易都能从"原始新闻 → 事件 → 决策 → 执行"完整回溯

## 七、推荐的实施路径

按"最大化解锁 / 最小化阻塞"排序：

### 🔥 路径 A（快速跑通端到端，7-10 天）

核心思路：**先做最小可用的自动交易闭环，再补齐细节**。

1. **Day 1-2**：建 `ft_events` / `ft_event_streams` / 3 张映射表
2. **Day 3-5**：实现 `agg_event_extraction` task（用 Claude Haiku，简单 prompt）
3. **Day 6-7**：实现 `trade_decision` task（只做硬过滤 + 简单打分，不做历史类比）
4. **Day 8**：实现 `trade_execution` task（接入天天基金 buy_fund）
5. **Day 9**：实现 `trade_monitor` task（只做硬止损）
6. **Day 10**：上线观察 + 调参

**风险**：跳过了预筛选/embedding/动态仓位，初期策略粗糙。但能跑通，能产出数据。

### 🎯 路径 B（稳扎稳打，15-20 天）

核心思路：**每个模块都做到可用再上下一个**。

1. **Day 1-3**：Phase 2 补齐（stock_flow 动态 / guba_posts / 3d 涨幅 / 跨源去重）
2. **Day 4-6**：建 ft_events 表 + 预筛选 + AI 抽取
3. **Day 7-8**：Embedding 生成 + 事件流聚合
4. **Day 9-11**：映射表 + 决策引擎（含动态仓位）
5. **Day 12-13**：交易执行 + 监控
6. **Day 14-15**：历史类比查询 + 复盘接入
7. **Day 16-20**：调参 + 测试 + 上线

### 🚀 路径 C（激进推进，5-7 天）

核心思路：**砍掉非核心特性，只保证最小闭环**。

1. **Day 1**：建表（ft_events + 映射表硬编码 5-10 个行业）
2. **Day 2-3**：最简 AI 抽取（单条调用，不做批量）
3. **Day 4**：最简决策（规则硬编码 + 打分）
4. **Day 5**：接入交易
5. **Day 6-7**：观察 + 调整

**适用**：快速验证方向，小规模实验。

### 推荐：路径 A

理由：
- 最快拿到端到端数据（可以真正验证策略有效性）
- 每个模块的工作量都控制在 1-3 天，风险可控
- Phase 2 补齐可以并行或延后（不阻塞核心链路）

## 九、总结

### 方向评价

**✅ 架构方向正确**：数据采集 → 聚合清洗 → 事件抽取 → 决策 → 交易 → 复盘，这个五段式设计完全符合"事件驱动交易系统"的本质。

**✅ 技术选型合理**：jettask + PostgreSQL + Redis + 规则引擎（AI 做抽取不做决策），每个选择都有明确理由。

**✅ 分层清晰**：interfaces → application → domain → infrastructure，依赖方向单向流动。

### 主要风险

1. **价值断点**：数据端完美但决策端空白，"看得到米，吃不到饭"。需要 5-10 天集中攻关才能打通。
2. **AI 幻觉**：必须严守"AI 只做抽取和打分，不做决策"的原则，规则引擎兜底。
3. **策略未验证**：所有的打分公式、仓位因子都是"先验合理"但"后验未知"，必须通过历史回测 + 小仓位实盘验证。
