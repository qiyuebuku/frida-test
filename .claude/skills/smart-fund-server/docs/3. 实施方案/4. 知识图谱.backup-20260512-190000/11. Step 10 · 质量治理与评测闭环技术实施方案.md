---

## 0. 一句话说清楚

Step 10 建立质量闭环：

```text
compile checks
  -> graph quality scan
  -> retrieval evaluation
  -> bad case capture
  -> review / feedback
  -> recompile / reindex
```

没有质量治理，KG 结果不能进入交易硬逻辑。

---

## 1. 质量检查层次

### 1.1 Compile-time checks

编译时检查：

- source required fields。
- node type 是否声明。
- relation type 是否声明。
- source/target 方向是否正确。
- active edge 是否有 evidence。
- confidence/status 是否允许。
- stable ID 是否冲突。

### 1.2 Post-compile checks

入库后检查：

- 孤岛节点。
- 超级节点。
- 弱边泛滥。
- alias 冲突。
- 同源重复事件。
- 过期持仓。
- evidence 缺失。

### 1.3 Query-time checks

查询时检查：

- answer_context 是否证据不足。
- hard score 是否使用了弱关系。
- 路径是否包含 low confidence edge。
- Wiki 是否陈旧。

### 1.4 Feedback-time checks

反馈时检查：

- 用户纠错。
- 人工复核。
- L1/L2/L3 Bad Case。
- 复盘验证。

反馈必须转成 `feedback_record` 或 review item，不直接手改事实。

---

## 2. Review Queue

需要进入 review 的情况：

| 情况 | 处理 |
|---|---|
| alias_of 高风险合并 | 人工确认 |
| LLM 推断高影响关系 | 人工确认 |
| 同一实体多个强 ID | conflict |
| 同一 source 内容变化 | conflict |
| active edge 缺 evidence | reject |
| 弱边短期暴增 | review batch |
| L3 Bad Case | 回放路径和证据 |

Review 输出：

```text
approve
reject
downgrade
merge
split
deprecate
request_more_evidence
```

## 4. 评测集

必须维护固定评测集：

```text
tests/fixtures/knowledge/eval/
  toy_quality_cases.json
  financial_quality_cases.json
  retrieval_queries.json
  expected_contexts.json
  bad_case_replays.json
```

评测场景：

1. 无 evidence active edge。
2. 弱关系进入 hard score。
3. alias 冲突。
4. 过期基金持仓。
5. 重复事件归并错误。
6. 查询上下文缺证据。
7. Wiki 陈旧。

---

## 5. 重建和回放

必须支持：

```text
recompile source batch
rebuild wiki
rebuild indexes
replay bad case
compare compile result
```

任何规则修改后，都要能用 fixture 和 Bad Case 回放验证没有退化。

## 7. 验收标准

Step 10 完成必须满足：

1. 质量扫描能覆盖 compile、graph、query、feedback。
2. review queue 能记录和处理高风险问题。
3. Bad Case 能回放。
4. 规则修改后能比较前后输出。
5. hard score 不消费弱关系。
6. active edge evidence coverage 为 100%。
