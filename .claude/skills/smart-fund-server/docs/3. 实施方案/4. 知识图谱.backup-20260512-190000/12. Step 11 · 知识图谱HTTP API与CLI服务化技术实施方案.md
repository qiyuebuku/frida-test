# Step 11 · 知识图谱HTTP API与CLI服务化技术实施方案

> 对应设计文档：`../../5. 设计方案/1. 知识图谱/5. 知识图谱对外服务接口设计方案.md`  
> 架构约束来源：`../../2. 架构设计/系统架构.md`、`../../2. 架构设计/业务架构.md`  
> 前置步骤：Step 4-10 的核心能力已具备应用服务层调用能力。  
> 本步骤目标是把知识图谱核心能力封装成符合现有架构风格的 HTTP API 和 CLI，使 L1/L2/L3、任务调度和外部工具能稳定调用。

---

## 0. 一句话说清楚

Step 11 不是重写知识图谱，而是把已有应用层能力服务化：

```text
FastAPI route / CLI command
  -> KnowledgeService application use case
  -> domain knowledge / financial adapter
  -> infrastructure repository
```

接口层只做协议适配，不能直接操作 Compiler、Adapter、Repository 或数据库。

---

## 1. 目标

### 1.1 必须完成

| 能力 | 验收目标 |
|---|---|
| HTTP health | `/api/kg/health` 能返回 route、DB、能力状态 |
| HTTP compile | `/api/kg/compile` 能用 fixture 编译并入库 |
| HTTP rebuild wiki | `/api/kg/rebuild-wiki` 能重建 Wiki 页面 |
| HTTP rebuild indexes | `/api/kg/rebuild-indexes` 能重建 graph adjacency 和 evidence chunks |
| HTTP research context | `/api/kg/research-context` 能返回节点、边、证据和上下文 |
| HTTP quality scan | `/api/kg/quality-scan` 能扫描并写入 review queue |
| CLI 同等能力 | `python -m src.interfaces.cli.main kg ...` 能跑通最小闭环 |
| 架构守卫 | route 不直接 import repository、compiler、financial adapter |

### 1.2 暂不做

- 暂不实现复杂权限系统。
- 暂不实现完整异步任务队列。
- 暂不开放直接 node/edge/evidence CRUD。
- 暂不让 HTTP API 直接调用 LLM 生成最终回答。
- 暂不引入全站统一 response envelope。

## 3. Step A：应用层 DTO 和 Adapter Registry

### 3.1 新增 DTO 文件

新增：

```text
src/application/dto/knowledge_dto.py
```

建议 DTO：

```text
KnowledgeCompileCommand
KnowledgeCompileResultDTO
KnowledgeRebuildWikiCommand
KnowledgeRebuildWikiResultDTO
KnowledgeRebuildIndexesCommand
KnowledgeRebuildIndexesResultDTO
KnowledgeResearchContextCommand
KnowledgeResearchContextDTO
KnowledgeQualityScanCommand
KnowledgeQualityScanResultDTO
KnowledgeReviewActionCommand
```

DTO 只表达 use case 输入输出，不携带 FastAPI `Request`、click context 或 SQLAlchemy session。

### 3.2 DTO 字段设计

第一版 DTO 要覆盖 HTTP 和 CLI 共用字段：

| DTO | 关键字段 | 说明 |
|---|---|---|
| `KnowledgeHealthDTO` | `status`、`database`、`adapters`、`implemented` | health 返回 |
| `KnowledgeCompileCommand` | `adapter_name`、`records`、`target`、`dry_run`、`request_id` | 编译请求 |
| `KnowledgeCompileResultDTO` | `adapter_name`、`run_id`、`nodes`、`edges`、`evidence`、`failed_records`、`warnings` | 编译结果 |
| `KnowledgeRebuildWikiCommand` | `adapter_name`、`target`、`scope` | Wiki 重建请求 |
| `KnowledgeRebuildWikiResultDTO` | `adapter_name`、`run_id`、`pages`、`issues` | Wiki 重建结果 |
| `KnowledgeRebuildIndexesCommand` | `adapter_name`、`target`、`index_types`、`scope` | 索引重建请求 |
| `KnowledgeRebuildIndexesResultDTO` | `adapter_name`、`run_id`、`graph_adjacency`、`evidence_chunks` | 索引重建结果 |
| `KnowledgeResearchContextCommand` | `adapter_name`、`target`、`query`、`graph_depth`、`graph_limit`、`wiki_limit`、`evidence_limit`、`max_chars` | 检索上下文请求 |
| `KnowledgeResearchContextDTO` | `query`、`hits`、`matched_nodes`、`matched_edges`、`evidence_refs`、`hard_score_edges`、`explanation_edges`、`context_text` | 检索上下文结果 |
| `KnowledgeQualityScanCommand` | `adapter_name`、`target`、`persist_review` | 质量扫描请求 |
| `KnowledgeQualityScanResultDTO` | `adapter_name`、`run_id`、`ok`、`metrics`、`issues`、`review_items` | 质量扫描结果 |
| `KnowledgeReviewActionCommand` | `review_id`、`action`、`operator`、`reason` | 复核动作 |

默认值：

| 字段 | 默认值 |
|---|---|
| `adapter_name` | `financial` |
| `target` | `test`，生产由后续权限策略控制 |
| `dry_run` | `false` |
| `persist_review` | `true` |
| `graph_depth` | `3` |
| `graph_limit` | `20` |
| `wiki_limit` | `10` |
| `evidence_limit` | `20` |
| `max_chars` | `5000` |

### 3.3 新增 Adapter Registry

新增：

```text
src/application/services/knowledge_adapter_registry.py
```

职责：

- 注册 `financial` adapter。
- 校验未知 adapter。
- 后续支持新增 adapter 时只改 registry。

接口形态：

```text
get_adapter(adapter_name: str) -> DomainAdapter
list_adapters() -> list[str]
```

不要在 route 或 CLI 中散落 `if adapter_name == "financial"`。

### 3.4 Service 工厂

在应用层提供 service 组装入口：

```text
create_knowledge_service(target: str | None = None) -> KnowledgeService
```

它负责创建 repository，实现：

```text
target -> KnowledgeRepositoryImpl(target=target)
```

这样 interfaces 层不直接依赖 infrastructure。

### 3.5 应用层方法补齐

`KnowledgeService` 当前已有底层用例方法，但对 API/CLI 更友好的方法应该返回 DTO，而不是原始领域对象。

需要新增或整理这些应用层方法：

```text
health(target=None) -> KnowledgeHealthDTO
compile_kg(command: KnowledgeCompileCommand) -> KnowledgeCompileResultDTO
rebuild_wiki_for(command: KnowledgeRebuildWikiCommand) -> KnowledgeRebuildWikiResultDTO
rebuild_indexes_for(command: KnowledgeRebuildIndexesCommand) -> KnowledgeRebuildIndexesResultDTO
build_research_context_for(command: KnowledgeResearchContextCommand) -> KnowledgeResearchContextDTO
quality_scan_for(command: KnowledgeQualityScanCommand) -> KnowledgeQualityScanResultDTO
list_reviews(status="open", target=None) -> list[dict]
apply_review_action(command: KnowledgeReviewActionCommand) -> dict
```

保留原有更底层的方法给内部代码使用，但 HTTP/CLI 优先调用这些用例级方法。

### 3.6 测试

新增单元测试：

```text
tests/unit/knowledge/test_knowledge_adapter_registry.py
tests/unit/knowledge/test_knowledge_dto.py
```

测试：

1. `financial` adapter 可解析。
2. 未知 adapter 抛出明确异常。
3. DTO 默认值正确，范围约束正确。
4. DTO 不依赖 FastAPI/click/SQLAlchemy。
5. `create_knowledge_service(target="test")` 能创建可用 service。
6. 应用层 DTO 可以序列化为 dict。

## 4. Step B：HTTP API

### 4.1 Route 文件

改造：

```text
src/interfaces/api/routes/knowledge.py
```

使用现有风格：

```text
router = APIRouter(prefix="/api/kg", tags=["知识图谱"])
```

Route 只做：

- Pydantic 请求模型。
- 参数范围校验。
- 调用 application service。
- 返回普通 dict。
- 抛出 `HTTPException`。
- 把 API 请求模型转换为应用层 command DTO。

### 4.2 第一版接口

必须实现：

```text
GET  /api/kg/health
POST /api/kg/compile
POST /api/kg/rebuild-wiki
POST /api/kg/rebuild-indexes
POST /api/kg/research-context
POST /api/kg/quality-scan
```

建议同步实现：

```text
POST /api/kg/financial/resolve-entities
POST /api/kg/financial/paths
GET  /api/kg/reviews?status=open
```

### 4.3 Pydantic 请求模型

Pydantic 模型放在 `src/interfaces/api/routes/knowledge.py` 内部即可，第一版不单独拆 `schemas`，避免过度设计。

建议模型：

```text
KGCompileRequest
KGRebuildWikiRequest
KGRebuildIndexesRequest
KGResearchContextRequest
KGQualityScanRequest
KGResolveFinancialEntitiesRequest
KGFinancialPathsRequest
KGReviewActionRequest
```

模型字段：

| 模型 | 字段 |
|---|---|
| `KGCompileRequest` | `adapter_name`、`records`、`target`、`dry_run`、`request_id` |
| `KGRebuildWikiRequest` | `adapter_name`、`target`、`scope` |
| `KGRebuildIndexesRequest` | `adapter_name`、`target`、`index_types`、`scope` |
| `KGResearchContextRequest` | `adapter_name`、`target`、`query`、`graph_depth`、`graph_limit`、`wiki_limit`、`evidence_limit`、`max_chars` |
| `KGQualityScanRequest` | `adapter_name`、`target`、`persist_review` |
| `KGResolveFinancialEntitiesRequest` | `text`、`target`、`limit` |
| `KGFinancialPathsRequest` | `seed_node_ids`、`target`、`max_depth`、`limit` |
| `KGReviewActionRequest` | `action`、`operator`、`reason` |

字段约束：

| 字段 | 约束 |
|---|---|
| `adapter_name` | 第一版只允许 `financial`，但实现通过 adapter registry 校验 |
| `target` | `test` / `prod`，默认 `test` |
| `records` | 非空 list，元素是 dict |
| `query` / `text` | 非空字符串 |
| `graph_depth` | 1-4 |
| `graph_limit` / `wiki_limit` / `evidence_limit` | 1-100 |
| `max_chars` | 500-20000 |
| `index_types` | 只允许 `graph_adjacency`、`evidence_chunks`，未来扩展 `fts`、`vector` |

### 4.4 接口明细

#### 4.4.1 Health

```text
GET /api/kg/health
```

实现：

```text
route -> KnowledgeService.health()
```

返回：

| 字段 | 说明 |
|---|---|
| `status` | `ok` / `degraded` / `error` |
| `database` | 数据库连通状态 |
| `adapters` | 已注册 adapter |
| `implemented` | 已启用能力 |

验收：

- 服务启动后返回 200。
- 返回中必须包含 `financial` adapter。

#### 4.4.2 Compile

```text
POST /api/kg/compile
```

实现：

```text
KGCompileRequest
  -> KnowledgeCompileCommand
  -> KnowledgeService.compile_kg()
  -> KnowledgeCompileResultDTO
```

请求字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `adapter_name` | 是 | 第一版 `financial` |
| `records` | 是 | 领域原始记录数组，由 Adapter normalize |
| `target` | 否 | `test` / `prod`，默认 `test` |
| `dry_run` | 否 | 只编译不写入，默认 `false` |
| `request_id` | 否 | 调用方幂等 ID |

返回字段：

| 字段 | 说明 |
|---|---|
| `adapter_name` | adapter |
| `run_id` | 编译批次 ID |
| `nodes` | 新增或更新节点数量 |
| `edges` | 新增或更新边数量 |
| `evidence` | 新增或更新证据数量 |
| `failed_records` | 失败记录数量 |
| `warnings` | 警告摘要 |

注意：

- `records` 不能是 node/edge/evidence DTO，必须是领域原始记录。
- `dry_run=true` 时不写 `kg_*`，但仍返回编译结果摘要。
- 如果 `failed_records > 0`，响应必须包含失败原因摘要。

#### 4.4.3 Rebuild Wiki

```text
POST /api/kg/rebuild-wiki
```

实现：

```text
KGRebuildWikiRequest
  -> KnowledgeRebuildWikiCommand
  -> KnowledgeService.rebuild_wiki_for()
```

请求字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `adapter_name` | 是 | 目标 adapter |
| `target` | 否 | `test` / `prod` |
| `scope` | 否 | 第一版仅支持 `all`，后续支持 `changed` / node ids |

返回字段：

| 字段 | 说明 |
|---|---|
| `adapter_name` | adapter |
| `run_id` | 运行 ID |
| `pages` | 生成页面数量 |
| `issues` | Wiki lint 问题数量 |

注意：

- Wiki lint 出现 error 时返回 400 或 500，不能静默成功。
- Wiki 是索引，不是事实源。

#### 4.4.5 Research Context

```text
POST /api/kg/research-context
```

实现：

```text
KGResearchContextRequest
  -> KnowledgeResearchContextCommand
  -> KnowledgeService.build_research_context_for()
```

请求字段：

| 字段 | 必填 | 说明 |
|---|---|---|
| `adapter_name` | 是 | 第一版 `financial` |
| `target` | 否 | `test` / `prod` |
| `query` | 是 | 查询文本 |
| `graph_depth` | 否 | 图扩展深度 |
| `graph_limit` | 否 | 图召回上限 |
| `wiki_limit` | 否 | Wiki 召回上限 |
| `evidence_limit` | 否 | 证据召回上限 |
| `max_chars` | 否 | 上下文字符预算 |

返回字段：

| 字段 | 说明 |
|---|---|

| `matched_nodes` | 命中节点 |
| `matched_edges` | 命中关系 |
| `evidence_refs` | 可回溯证据 |

### 4.5 返回风格

保持项目现有 API 风格，直接返回业务 JSON：

```json
{
  "adapter_name": "financial",
  "nodes": 12,
  "edges": 8,
  "evidence": 20,
  "failed_records": 0,
  "warnings": []
}
```

错误通过 `HTTPException`：

```json
{
  "detail": "adapter_name 必须是 financial"
}
```

不在知识图谱局部引入 `{"ok": true, "data": ...}` 这种全新 envelope。

### 4.6 错误映射

Route 将应用层异常映射为 HTTP 状态：

| 场景 | HTTP 状态 | detail |
|---|---|---|
| 请求字段非法 | 422 | FastAPI 默认 |
| adapter 不存在 | 400 | `adapter_name 不支持: xxx` |
| source contract 不合法 | 400 | 缺失字段或类型错误 |
| wiki lint error | 400 | lint error 摘要 |
| quality gate failed | 200 | `ok=false`，因为扫描成功但质量不通过 |
| 数据库错误 | 500 | 简短错误，不泄露连接串 |
| 未知异常 | 500 | 简短错误 |

## 5. Step C：CLI

### 5.1 CLI 文件

改造：

```text
src/interfaces/cli/knowledge.py
```

CLI 不能重新实现业务逻辑，只能调用 application service。

### 5.2 第一版命令明细

必须实现：

```bash
python -m src.interfaces.cli.main kg health
python -m src.interfaces.cli.main kg compile --adapter financial --file tests/fixtures/knowledge/financial/stock_basics.json --target test
python -m src.interfaces.cli.main kg rebuild-wiki --adapter financial --target test
python -m src.interfaces.cli.main kg rebuild-indexes --adapter financial --target test
python -m src.interfaces.cli.main kg query --adapter financial --query "固态电池政策利好会影响哪些基金" --target test
python -m src.interfaces.cli.main kg quality-scan --adapter financial --target test
```

建议同步实现：

```bash
python -m src.interfaces.cli.main kg resolve-financial --text "宁德时代和固态电池"
python -m src.interfaces.cli.main kg reviews --status open
```

### 5.3 参数设计

通用参数：

| 参数 | 适用命令 | 说明 |
|---|---|---|
| `--adapter` | compile/rebuild/query/quality | 默认 `financial` |
| `--target` | 所有读写命令 | 默认 `test` |
| `--json` | 所有命令 | 输出完整 JSON |

命令专属参数：

| 命令 | 参数 |
|---|---|
| `compile` | `--file`、`--dry-run`、`--request-id` |
| `rebuild-wiki` | `--scope` |
| `rebuild-indexes` | `--index-type` 可多次传入、`--scope` |
| `query` | `--query`、`--graph-depth`、`--graph-limit`、`--wiki-limit`、`--evidence-limit`、`--max-chars` |
| `quality-scan` | `--persist-review/--no-persist-review` |
| `resolve-financial` | `--text`、`--limit` |
| `reviews` | `--status` |

### 5.4 文件输入规则

`kg compile --file` 支持两种 JSON：

单文件数组：

```json
[
  {"source_type": "stock_basics", "payload": {}}
]
```

单文件对象：

```json
{
  "records": [
    {"source_type": "stock_basics", "payload": {}}
  ]
}
```

如果需要一次加载多个 fixture，第一版先通过多次执行 `kg compile` 完成，不在 CLI 中引入目录递归和 glob 逻辑。

### 5.5 输出风格

CLI 默认输出可读摘要：

```text
adapter=financial nodes=12 edges=8 evidence=20 failed=0
```

加 `--json` 时输出完整 JSON，方便脚本和测试使用。

### 5.6 错误处理

CLI 错误处理：

| 场景 | 行为 |
|---|---|
| 文件不存在 | 退出码非 0，输出 `file not found` |
| JSON 解析失败 | 退出码非 0，输出解析错误 |
| adapter 不支持 | 退出码非 0，输出 adapter 错误 |

| 应用层异常 | 退出码非 0，输出简短错误 |

## 7. 风险和处理

| 风险 | 处理 |
|---|---|
| route 变厚 | 增加架构守卫测试，禁止 route import repository/compiler/adapter |
| API 和 CLI 逻辑分叉 | 两者必须调用同一 application service 和 DTO |
| 未来 adapter 扩展困难 | 使用 adapter registry，不把 financial 写死在 route |
| 返回结构和现有 API 不一致 | 保持直接 JSON + HTTPException，不局部引入 envelope |
| 长任务阻塞 HTTP | 第一版先同步，保留 run_id；第二版再接任务队列 |
| 测试污染生产库 | 所有集成测试默认 `target=test` |
