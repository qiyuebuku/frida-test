## 0. 一句话说清楚

Step 3 的目标是定义一套稳定的 Adapter SDK，让任意领域都能接入通用知识基础设施：

```text
raw domain records
  -> DomainAdapter.normalize()
  -> KnowledgeInput
  -> node drafts / edge drafts / evidence drafts
  -> adapter-level validation
```

这一步只实现协议、ontology spec、Toy Adapter 和纯单元测试。  
不写数据库，不实现 Compiler 编排，不接真实金融数据，不接 LLM，不接 embedding。

## 4. Adapter Spec 设计

### 4.1 EntityTypeSpec

字段：

```text
name: str
description: str
stable_id_fields: list[str]
required_properties: list[str]
alias_fields: list[str]
allow_auto_create: bool
allow_auto_merge: bool
requires_review_on_merge: bool
```

校验规则：

- `name` 不能为空。
- `name` 在一个 Adapter 内唯一。
- `stable_id_fields` 可以为空，但如果为空，Adapter 必须能提供 `stable_key`。
- `required_properties` 只校验 properties，不修改平台 Node 协议。

### 4.2 RelationTypeSpec

字段：

```text
name: str
description: str
source_types: list[str]
target_types: list[str]
allow_inferred: bool
requires_evidence: bool
allow_multiple: bool
has_validity_window: bool
allowed_confidence_labels: list[ConfidenceLabel]
allowed_statuses: list[EdgeStatus]
```

校验规则：

- `name` 不能为空。
- `source_types` 和 `target_types` 不能为空。
- `source_types` 和 `target_types` 必须引用已声明 entity type。
- 如果 `requires_evidence=True`，active 边必须有 evidence。
- 如果 `allow_inferred=False`，`ConfidenceLabel.INFERRED` 不能用于该关系。

### 4.3 SourceTypeSpec

字段：

```text
name: str
input_type: InputType
description: str
required_fields: list[str]
```

用途：

- 说明某类原始输入如何映射到平台 `KnowledgeInput`。
- Step 3 只定义 spec 和校验，不实现复杂 source router。

### 4.4 ConsumptionRule

字段：

```text
consumer: str
allowed_confidence_labels: list[ConfidenceLabel]
allowed_edge_statuses: list[EdgeStatus]
max_depth: int | None
requires_human_review: bool
```

用途：

- 不同消费方可以使用不同置信等级。
- Step 3 只定义规则对象，不实现业务消费。

### 4.5 ReviewRule

字段：

```text
trigger: str
severity: ValidationSeverity
description: str
relation_types: list[str]
node_types: list[str]
```

用途：

- 标记哪些实体合并、关系新增、冲突情况需要进入复核。

### 4.6 WikiPageSpec

字段：

```text
page_type: str
subject_types: list[str]
sections: list[str]
requires_evidence: bool
```

用途：

- 领域 Adapter 告诉通用 Wiki Builder 适合生成哪些页面。
- Step 3 只定义页面 spec，不生成页面。

### 4.7 AdapterSpec

字段：

```text
name: str
version: str
entities: list[EntityTypeSpec]
relations: list[RelationTypeSpec]
sources: list[SourceTypeSpec]
consumption_rules: list[ConsumptionRule]
review_rules: list[ReviewRule]
wiki_pages: list[WikiPageSpec]
```

校验规则：

- `name` 不能为空。
- `version` 不能为空。
- entity name 不允许重复。
- relation name 不允许重复。
- source name 不允许重复。
- relation 引用的 source/target entity type 必须存在。
- consumption/review/wiki 引用的 relation/node/page 类型必须可解释。

## 5. DomainAdapter 协议

### 5.1 接口形式

建议使用 `typing.Protocol`，而不是抽象基类。

原因：

- Adapter 实现不必继承固定基类。
- 测试时更容易构造轻量对象。
- 协议边界清楚，不引入运行时复杂性。

协议：

```text
DomainAdapter
  spec: AdapterSpec
  normalize(raw: Any) -> list[KnowledgeInput]
  extract_node_drafts(item: KnowledgeInput) -> list[NodeDraft]
  extract_edge_drafts(item: KnowledgeInput, nodes: list[NodeDraft]) -> list[EdgeDraft]
  extract_evidence_drafts(item: KnowledgeInput) -> list[EvidenceDraft]
```

第一版不要求异步。

### 5.2 为什么不在这里实现 confidence assignment

总方案里曾提到：

```text
assign_confidence(edge, evidence)
```

Step 3 暂不把它做成必须实现的方法，而是先通过 `RelationTypeSpec.allowed_confidence_labels` 和 draft 内的 `confidence_label/confidence_score` 表达。

原因：

- confidence 的最终策略会和 Compiler、Evidence、Review 联动。
- 过早把它设计成必选方法，会让 Adapter 接口膨胀。
- Toy Adapter 只需要证明关系校验和输出协议。

后续如果 Step 5 发现需要集中置信策略，可以增加可选 protocol。

## 6. 校验函数

### 6.1 validate_node_against_adapter

输入：

```text
adapter_spec: AdapterSpec
node: NodeDraft
```

输出：

```text
ValidationResult
```

校验：

1. `node.node_type` 必须在 `adapter_spec.entities` 中。
2. `required_properties` 必须在 `node.properties` 中存在。
3. 如果 `allow_auto_create=False`，候选新节点应返回 warning 或 error。

### 6.2 validate_edge_against_adapter

输入：

```text
adapter_spec: AdapterSpec
edge: EdgeDraft
source_node: NodeDraft
target_node: NodeDraft
```

输出：

```text
ValidationResult
```

校验：

1. `edge.relation_type` 必须在 `adapter_spec.relations` 中。
2. source node type 必须在 relation spec 的 `source_types` 中。
3. target node type 必须在 relation spec 的 `target_types` 中。
4. confidence label 必须在 `allowed_confidence_labels` 中。
5. status 必须在 `allowed_statuses` 中。
6. 如果 `allow_inferred=False`，不能使用 `INFERRED`。
7. 如果 `requires_evidence=True`，active 边必须有 evidence。

### 6.3 ValidationResult

字段：

```text
ok: bool
issues: list[ValidationIssue]
```

便利方法：

```text
ValidationResult.success()
ValidationResult.error(message, object_type=None, object_ref=None)
ValidationResult.warning(message, object_type=None, object_ref=None)
```

## 7. ToyProjectAdapter

### 7.1 目标

Toy Adapter 用于证明：

- 平台没有绑定金融场景。
- Adapter 协议能表达任意领域。
- node / edge draft 能通过 adapter-level 校验。
- 非法关系能被拒绝。

### 7.2 Ontology

实体：

```text
person
project
document
```

关系：

```text
owns(person -> project)
references(document -> project)
blocks(project -> project)
```

source：

```text
toy_record: structured_record
```

### 7.3 输入 fixture

文件：

```text
tests/fixtures/knowledge/toy_records.json
```

内容：

```json
[
  {
    "source_type": "toy_record",
    "source_id": "toy-001",
    "observed_at": "2026-04-24T10:00:00+08:00",
    "payload": {
      "owner": "Alice",
      "project": "Alpha",
      "document": "Design Note",
      "references": ["Alpha"],
      "blocks": ["Beta"]
    },
    "raw_text": "Alice owns Alpha. Design Note references Alpha. Alpha blocks Beta."
  }
]
```

### 7.4 期望输出

文件：

```text
tests/fixtures/knowledge/toy_adapter_expected.json
```

只校验 Step 3 需要的内容：

```json
{
  "node_types": ["document", "person", "project"],
  "relation_types": ["blocks", "owns", "references"],
  "input_count": 1
}
```

不校验 compiled IDs，因为编译和 ID 绑定不是 Step 3 的主目标。

## 8. 测试方案

### 8.1 test_adapter_contract.py

测试项：

1. `AdapterSpec` 缺少 name 校验失败。
2. 重复 entity name 校验失败。
3. 重复 relation name 校验失败。
4. relation 引用不存在的 source entity 校验失败。
5. relation 引用不存在的 target entity 校验失败。
6. `validate_node_against_adapter` 能接受合法节点。
7. `validate_node_against_adapter` 能拒绝未知 node type。
8. `validate_edge_against_adapter` 能接受 `owns(person -> project)`。
9. `validate_edge_against_adapter` 能拒绝 `owns(project -> person)`。
10. `validate_edge_against_adapter` 能拒绝未声明关系。
11. `requires_evidence=True` 时 active 边缺 evidence 会失败。
12. `allow_inferred=False` 时 inferred 边会失败。

### 8.2 test_toy_adapter.py

测试项：

1. Toy Adapter 能加载 fixture。
2. Toy Adapter 能把 raw dict normalize 成 `KnowledgeInput`。
3. Toy Adapter 能抽出 `person/project/document` 节点草稿。
4. Toy Adapter 能抽出 `owns/references/blocks` 边草稿。
5. Toy Adapter 能抽出至少一条 evidence draft。
6. Toy Adapter 输出不依赖数据库、LLM、embedding。
7. Toy Adapter 的 ontology 与 expected fixture 一致。

## 11. 失败判定

出现任一情况，Step 3 视为失败：

| 失败情况 | 原因 |
|---|---|
| Adapter 协议中出现具体金融字段 | 通用协议被金融场景污染 |
| `relation_type` 被平台枚举固定 | 领域扩展能力被破坏 |
| Toy Adapter 需要数据库才能运行 | Adapter 边界越界 |
| Toy Adapter 调用 LLM | Step 3 提前进入抽取阶段 |
| API/CLI 可以直接执行 Adapter 编译 | Step 3 边界被提前打破，应等 Step 5 以后接入 |
| 未声明关系也能通过校验 | ontology 校验失效 |
| `owns(project -> person)` 能通过校验 | 关系方向校验失效 |
