> 对应设计文档：`../../5. 设计方案/1. 知识图谱/2. 通用知识基础设施设计方案.md`  
> 前置步骤：Step 1、Step 2、Step 3  
> 本步骤目标是建立唯一事实源。没有 Fact Store，就不能开始正式 Knowledge Compiler。

---

## 0. 一句话说清楚

Step 4 要把通用知识事实落到 PostgreSQL：

```text
CompiledNode / CompiledEdge / CompiledEvidence
  -> repository
  -> kg_nodes / kg_edges / kg_evidence / kg_edge_evidence / kg_versions
```

这一步不做金融 Adapter，不做检索排序，不做 Wiki 文本生成。  
只解决一个问题：**事实如何被可靠、幂等、可审计地保存。**

## 3. 表设计

### 3.1 kg_nodes

保存实体节点。

核心字段：

```text
node_id
adapter_name
adapter_version
node_type
stable_key
canonical_name
aliases
external_ids
properties
status
version
created_at
updated_at
```

约束：

- `node_id` 主键。
- `adapter_name + node_type + stable_key` 唯一。
- `aliases / external_ids / properties` 使用 JSONB。
- `node_type` 不做平台枚举约束，具体类型由 Adapter 定义。

### 3.2 kg_edges

保存关系边。

核心字段：

```text
edge_id
adapter_name
adapter_version
source_node_id
target_node_id
relation_type
properties
confidence_label
confidence_score
status
valid_from
valid_to
version
created_at
updated_at
```

约束：

- `edge_id` 主键。
- `source_node_id`、`target_node_id` 引用 `kg_nodes.node_id`。
- `relation_type` 不做平台枚举约束。
- active edge 是否必须有 evidence 由 repository 或 Compiler 前置校验保障，数据库层可用集成测试覆盖。

### 3.3 kg_evidence

保存证据。

核心字段：

```text
evidence_id
adapter_name
source_type
source_id
evidence_type
content
payload
span_start
span_end
observed_at
created_at
```

约束：

- `evidence_id` 主键。
- `payload` 使用 JSONB。
- 同一 source 可以对应多条 evidence。

### 3.4 kg_edge_evidence

保存 edge 和 evidence 的多对多关系。

核心字段：

```text
edge_id
evidence_id
created_at
```

约束：

- `edge_id + evidence_id` 唯一。
- 删除 edge 不物理删除 evidence。

### 3.5 kg_versions

保存 schema、adapter、compiler、规则版本。

核心字段：

```text
version_id
adapter_name
adapter_version
schema_version
compiler_version
rules_hash
prompt_hash
created_at
metadata
```

### 3.6 kg_review_items

保存需要复核的节点、边或冲突。

核心字段：

```text
review_id
object_type
object_id
severity
reason
status
payload
created_at
updated_at
```

### 3.7 kg_compilation_runs

保存每次编译运行。

核心字段：

```text
run_id
adapter_name
adapter_version
source_batch_id
status
started_at
finished_at
input_count
node_count
edge_count
evidence_count
failed_count
metadata
```

## 4. Repository 设计

建议定义通用 repository 接口：

```text
KnowledgeRepository
  upsert_nodes(nodes)
  upsert_edges(edges)
  upsert_evidence(evidence)
  attach_edge_evidence(edge_id, evidence_ids)
  create_compilation_run(run)
  finish_compilation_run(run_id, result)
  get_node(node_id)
  get_edge(edge_id)
  find_nodes(...)
  find_edges(...)
  get_edge_evidence(edge_id)
```

实现位置：

```text

```

领域层不能 import repository 实现。

## 5. Upsert 语义

### 5.1 Node upsert

同一 `node_id` 重复写入必须幂等。

规则：

- `canonical_name` 可以更新。
- `aliases` 合并去重。
- `external_ids` 合并。
- `properties` 合并，以新版本覆盖同名字段。
- `status` 按 Compiler 结果更新。
- 保留 `created_at`，更新 `updated_at`。

### 5.2 Edge upsert

同一 `edge_id` 重复写入必须幂等。

规则：

- `confidence_score`、`status`、`valid_from`、`valid_to` 可更新。
- `properties` 合并。
- evidence 通过 `kg_edge_evidence` 追加关联。
- `REJECTED/deprecated` 不能被低权限流程重新 active。

### 5.3 Evidence upsert

同一 `evidence_id` 重复写入必须幂等。

规则：

- content 和 payload 不应被静默改写。
- 如果同 ID 内容不同，应进入 conflict/review。

## 7. 验收标准

Step 4 完成必须满足：

1. 所有 `kg_*` 表存在。
2. repository 能写入和查询 node / edge / evidence。
3. 重复 upsert 同一 fixture 不产生重复记录。
4. edge 能追溯 evidence。
5. domain 层不依赖 SQLAlchemy 或数据库驱动。
6. 通用层不出现金融字段。
7. 集成测试可重复运行。
