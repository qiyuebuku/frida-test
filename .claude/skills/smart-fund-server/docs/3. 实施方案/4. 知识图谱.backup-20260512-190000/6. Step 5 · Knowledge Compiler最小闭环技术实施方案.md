## 0. 一句话说清楚

Step 5 实现通用 Knowledge Compiler 最小闭环：

```text
raw records
  -> DomainAdapter.normalize()
  -> node / edge / evidence drafts
  -> resolve
  -> validate
  -> compile IDs
  -> bind evidence
  -> repository upsert
  -> CompileResult
```

这一步仍然不接金融数据，不接真实 LLM，不接 embedding。

## 3. Compiler 模块

文件：

```text
src/domain/knowledge/compiler.py
src/domain/knowledge/resolver.py
src/domain/knowledge/relation_compiler.py
src/domain/knowledge/evidence.py
src/application/services/knowledge_service.py
```

### 3.1 KnowledgeCompiler

职责：

```text
compile(adapter, raw_records) -> CompileResult
```

流程：

1. 调用 `adapter.normalize(raw_records)`。
2. 对每条 `KnowledgeInput` 抽取 evidence drafts。
3. 抽取 node drafts。
4. 根据 stable_key 编译 node_id。
5. 抽取 edge drafts。
6. 根据 source/target/relation/evidence 编译 edge_id。
7. 运行 Adapter ontology validation。
8. 检查 active edge evidence。
9. 写入 repository。
10. 返回 CompileResult。

### 3.2 Entity Resolver

第一版只做确定性解析：

| 输入 | 处理 |
|---|---|
| `stable_key` 存在 | 直接生成稳定 node_id |
| 同 adapter + node_type + stable_key 重复 | 视为同一节点 |
| alias | 只写入 node aliases，不自动合并 |
| 歧义 | 进入 failed_records 或 review |

不做模糊合并。

### 3.3 Relation Compiler

第一版只做：

- relation type 是否在 AdapterSpec 中声明。
- source/target node type 是否符合方向。
- confidence label 是否允许。
- status 是否允许。
- active edge 是否有 evidence。

### 3.4 Evidence Manager

第一版只做：

- evidence draft 转 compiled evidence。
- evidence_id 稳定生成。
- edge evidence refs 绑定。
- source_id/source_type 可追溯。

## 4. Application Service

`KnowledgeService` 负责应用层编排：

```text
compile_with_adapter(adapter_name, raw_records)
get_compile_run(run_id)
```

注意：

- service 可以依赖 repository 实现。
- domain compiler 不直接依赖数据库。
- CLI/API 只调用 service。

## 6. 验收标准

Step 5 完成必须满足：

1. Toy Adapter 能端到端 compile 入库。
2. CompileResult 能返回节点、边、证据、失败记录。
3. 所有 active edge 都有 evidence。
4. 重复 compile 幂等。
5. domain compiler 不依赖数据库实现。
6. 金融词不进入通用层。
