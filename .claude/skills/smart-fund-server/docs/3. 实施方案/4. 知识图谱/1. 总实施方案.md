# 知识图谱总实施方案

> 对应设计文档：`../../5. 设计方案/1. 知识图谱/`  
> 本目录承接最终设计方案：自研通用 Knowledge Infrastructure，把金融知识图谱作为第一个领域适配器落地。  
> 本文档只定义实施阶段、依赖顺序、产物和验收标准；每一步的细节由独立 Step 文档展开。

---

## 0. 一句话说清楚

知识图谱实施不是先做金融规则，也不是先接 GraphRAG，而是按下面顺序建立可复用地基：

```text
架构边界
  -> 通用模型
  -> Adapter 协议
  -> PostgreSQL Fact Store
  -> Knowledge Compiler
  -> Wiki / Index
  -> Hybrid Retrieval
  -> Financial KG Adapter
  -> Financial News Extraction Strategy
  -> L1/L2/L3 与投研问答接入
  -> 质量治理和评测闭环
  -> HTTP API / CLI 服务化
```

最终目标：

```text
Raw Source
  -> Domain Adapter
  -> Knowledge Compiler
  -> kg_nodes / kg_edges / kg_evidence / kg_versions
  -> Wiki / FTS / Vector / Graph Index
  -> Hybrid Retrieval Runtime
  -> L1 / L2 / L3 / 投研问答
```

## 1. 实施总原则

### 1.1 事实源原则

唯一事实源是 PostgreSQL `kg_*` 表。

这些是事实源：

```text
kg_nodes
kg_edges
kg_evidence
kg_edge_evidence
kg_versions
kg_review_items
kg_compilation_runs
```

这些不是事实源：

```text
Wiki
FTS
Vector Index
Graph Index
graphify export
NetworkX analysis result
LLM summary
```

索引可以删除重建，事实库不能被索引反向污染。

### 1.2 通用层原则

`src/domain/knowledge` 是通用层，不能出现具体金融业务字段。

禁止进入通用层的概念包括：

```text
stock
fund
industry
concept
policy
market
trade
L1/L2/L3
affected_stocks
affected_concepts
```

这些只能存在于 Financial KG Adapter、测试 fixture 或金融消费文档中。

### 1.3 写入时编译原则

本系统采用“写入时编译，查询时复用”。

写入侧要沉淀：

- entity。
- relation。
- evidence。
- confidence。
- version。
- Wiki material。
- search index material。

查询侧不应每次重新从原始文本推理整条知识链。

### 1.4 LLM 使用原则

结构化数据能确定的事实必须规则抽取。

LLM 只处理：

- 文本语义关系。
- 歧义解释。
- 候选因果链。
- Wiki 摘要。
- 复杂查询中的 Agentic 检索。

LLM 输出不能无 evidence 进入 active edge。

### 1.5 测试原则

每个步骤都必须有测试。

| 测试类型 | 用途 |
|---|---|
| unit test | 纯 Python 逻辑、模型、ID、规则、融合算法 |
| integration test | 数据库、repository、CLI/API、compile 入库、检索 |
| golden fixture test | 固定输入输出，防止图谱漂移 |
| negative test | 无 evidence、非法关系、歧义实体、低置信消费边界 |
| smoke test | CLI/API 最小链路可运行 |

测试目录固定：

```text
tests/unit/knowledge/
tests/integration/knowledge/
tests/fixtures/knowledge/
tests/unit/knowledge_adapters/financial/
tests/integration/knowledge_adapters/financial/
tests/fixtures/knowledge/financial/
```

## 3. 依赖顺序

实施顺序不能打乱：

```text
Step 1 架构定位
  -> Step 2 通用模型
  -> Step 3 Adapter 协议
  -> Step 4 Fact Store
  -> Step 5 Compiler
  -> Step 6 Wiki / Index
  -> Step 7 Retrieval
  -> Step 8 Financial Adapter
  -> Step 8 补充 Financial News Extraction Strategy
  -> Step 9 L1/L2/L3 接入
  -> Step 10 质量治理
  -> Step 11 API / CLI 服务化
```

关键约束：

- Fact Store 没完成，不要做正式 Compiler 入库。
- Compiler 没跑通，不要做金融 Adapter 集成测试。
- Retrieval 没跑通，不要改造 L1/L2/L3。
- 金融 Adapter fixture 没稳定，不要接真实生产数据。
- 质量治理没接入，不要让 KG 结果进入交易硬逻辑。
- API / CLI 服务化没完成，不要让外部系统绕过应用层调用 repository 或手写 Python 脚本接生产链路。

---

## 4. 阶段验收总清单

最终完成必须满足：

1. 通用层不含金融字段。
2. Toy Adapter 能端到端 compile 入库。
3. `kg_*` 是唯一事实源。
4. active edge 全部有 evidence。
5. Wiki、FTS、vector、graph index 可从 Fact Store 重建。
6. Hybrid Retrieval 能返回结构化上下文。
7. Financial Adapter 能跑通固定 fixture。
8. 能从 `ft_news` 投影的 `news_articles` 生成可解释的 mentions/affects candidate。
9. 能检索 `event -> concept/industry -> stock -> fund` 路径。
10. L1/L2/L3 只通过 KG 服务消费知识，不直接写事实表。
11. Bad Case 和人工反馈能回写 review/feedback。
12. HTTP API 和 CLI 能按现有架构风格调用 KG 最小闭环。
