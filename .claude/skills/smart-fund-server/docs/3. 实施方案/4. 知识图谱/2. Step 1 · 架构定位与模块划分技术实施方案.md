## 0. 一句话说清楚

Step 1 不实现知识抽取、不建表、不接 LLM、不接 embedding。

这一步只做一件事：

> **把 Knowledge Infrastructure 在现有系统里的架构位置、模块边界、依赖方向、扩展点和测试守卫先定死。**

只有这一步完成后，后续 Step 2 才允许开始写通用领域模型和枚举。

---

## 1. 为什么第一步必须先做架构定位

知识图谱不是一个普通功能模块。它会被后续很多系统依赖：

- AI 事件抽取。
- 事件流和主线识别。
- 基金影响映射。
- 投研问答。
- 复盘反馈。
- 未来其他领域 Adapter。

如果一开始没有把模块边界定清楚，后面很容易出现三类问题：

| 问题 | 后果 |
|---|---|
| 通用层混入金融字段 | 后续换代码知识库、企业知识库、个人记忆时必须重写 |
| domain 层直接依赖数据库 | 编译器、Adapter、质量规则无法做纯单元测试 |
| API/CLI 直接写库 | 绕过 Compiler，证据、版本、置信度协议失效 |

所以第一步的产物不是业务功能，而是架构护栏。

## 2. 本步骤范围

### 2.1 本步骤要做

1. 确认 `Knowledge` 是系统第五个领域模块。
2. 确认业务架构从 `客户端层 -> 聚合层 -> 业务层` 扩展为 `客户端层 -> 聚合层 -> 知识层 -> 业务层`。
3. 确认代码四层落位：
   - `interfaces`
   - `application`
   - `domain`
   - `infrastructure`
4. 创建知识图谱通用层目录骨架。
5. 创建测试目录骨架。
6. 编写架构守卫测试。
7. 确保架构文档已同步维护。

### 2.2 本步骤不做

| 不做 | 原因 |
|---|---|
| 不定义 `Node` / `Edge` / `Evidence` 具体字段 | 这是 Step 2 |
| 不建 `kg_*` 表 | 这是 Step 4 |
| 不实现 Compiler | 这是 Step 5 |
| 不实现 Financial KG Adapter | 这是后续金融适配器实施方案 |
| 不接 LLM / embedding | 这些是查询和语义召回阶段的能力 |
| 不改 L1/L2/L3 业务逻辑 | 等通用层和金融 Adapter 稳定后再做 |

## 3. 架构落位

### 3.1 代码分层

Knowledge Infrastructure 必须遵守现有简化 DDD 分层：

```text
src/interfaces
  -> src/application
  -> src/domain
  -> src/infrastructure
```

具体落位：

| 层 | 目标文件/目录 | 职责 |
|---|---|---|
| interfaces | `src/interfaces/api/routes/knowledge.py` | FastAPI 薄路由，只做参数校验、调用应用服务、格式化响应 |
| interfaces | `src/interfaces/cli/knowledge.py` | CLI 薄入口，只解析参数、调用应用服务 |
| application | `src/application/services/knowledge_service.py` | 编排 compile、search、wiki rebuild、quality scan 等用例 |
| domain | `src/domain/knowledge/` | 通用模型、Adapter 协议、Compiler、Resolver、Evidence、Retrieval、Wiki、Quality |
| infrastructure | `src/infrastructure/persistence/models/knowledge.py` | SQLAlchemy model，后续承载 `kg_*` 表 |
| infrastructure | `src/infrastructure/persistence/repositories/knowledge_repository_impl.py` | PostgreSQL repository，后续承载事实库读写 |
| tests | `tests/unit/knowledge/` | 单元测试 |
| tests | `tests/integration/knowledge/` | 集成测试 |
| tests | `tests/fixtures/knowledge/` | fixture 和 golden output |

### 3.2 依赖方向

允许：

```text
interfaces -> application
application -> domain
application -> infrastructure
infrastructure -> domain
```

禁止：

```text
domain -> infrastructure
domain -> interfaces
interfaces -> infrastructure/persistence
interfaces -> SQLAlchemy model
interfaces -> psycopg2 / asyncpg
```

解释：

- `domain/knowledge` 必须是纯 Python 领域逻辑，不能连接数据库。
- `application/knowledge_service.py` 可以编排 domain 和 infrastructure。
- `interfaces` 不能绕过 application，否则会产生“API 直接写事实库”的风险。
- `infrastructure` 可以 import domain schema，把数据库结果转换回领域对象。

## 4. 模块划分

### 4.1 domain/knowledge

第一步只创建目录和空模块，不写业务逻辑。

目标结构：

```text
src/domain/knowledge/
  __init__.py
  schemas.py
  enums.py
  ids.py
  adapter.py
  compiler.py
  resolver.py
  relation_compiler.py
  evidence.py
  retrieval.py
  wiki.py
  quality.py
```

职责边界：

| 文件 | 后续职责 | Step 1 是否实现 |
|---|---|---|
| `schemas.py` | 通用输入、节点、边、证据、版本 schema | 否，仅占位 |
| `enums.py` | 通用状态和置信度枚举 | 否，仅占位 |
| `ids.py` | 稳定 ID 生成策略 | 否，仅占位 |
| `adapter.py` | 自定义领域 Adapter 协议 | 否，仅占位 |
| `compiler.py` | 通用编译流程 | 否，仅占位 |
| `resolver.py` | 实体归一 | 否，仅占位 |
| `relation_compiler.py` | 关系编译和校验 | 否，仅占位 |
| `evidence.py` | 证据绑定 | 否，仅占位 |
| `retrieval.py` | 检索协议、RRF、上下文预算 | 否，仅占位 |
| `wiki.py` | Wiki 页面协议 | 否，仅占位 |
| `quality.py` | 图质量规则 | 否，仅占位 |

### 4.2 application

目标文件：

```text
src/application/services/knowledge_service.py
```

Step 1 只允许写服务类占位，不实现真实用例：

```text
KnowledgeService
  compile()
  search()
  rebuild_wiki()
  quality_scan()
```

这些方法第一步可以抛出 `NotImplementedError`，但不能连接数据库、不能调用 LLM。

### 4.3 interfaces

目标文件：

```text
src/interfaces/api/routes/knowledge.py
src/interfaces/cli/knowledge.py
```

Step 1 只允许提供最小 health 或占位入口。

禁止在接口层：

- import `knowledge_repository_impl`
- import `knowledge.py` SQLAlchemy model
- 直接执行 SQL
- 直接写 `kg_*`

### 4.4 infrastructure

目标文件：

```text
src/infrastructure/persistence/models/knowledge.py
src/infrastructure/persistence/repositories/knowledge_repository_impl.py
```

Step 1 只创建占位文件，不定义表结构。  
表结构从 Step 4 开始写。

## 5. 金融边界

通用层禁止出现金融专用词。

第一批禁止词：

```text
stock
fund
industry
concept
policy
market
trade
affected_stocks
affected_concepts
L1
L2
L3
```

说明：

- 这些词可以出现在 `docs/` 的金融 Adapter 文档里。
- 后续可以出现在 `src/domain/knowledge_adapters/financial/` 或等价金融适配器目录里。
- 不能出现在 `src/domain/knowledge/` 通用层里。

### 7.2 单元测试：架构边界

文件：

```text
tests/unit/knowledge/test_architecture_boundaries.py
```

测试目标：

1. `src/domain/knowledge` 不能 import `src.infrastructure`。
2. `src/domain/knowledge` 不能 import `src.interfaces`。
3. `src/domain/knowledge` 不能 import `sqlalchemy`。
4. `src/domain/knowledge` 不能 import `psycopg2`。
5. `src/domain/knowledge` 不能 import `asyncpg`。
6. `src/interfaces/api/routes/knowledge.py` 不能 import repository。
7. `src/interfaces/api/routes/knowledge.py` 不能 import SQLAlchemy model。
8. `src/interfaces/cli/knowledge.py` 不能 import repository。

建议实现方式：

- 使用 `ast` 解析 Python 文件。
- 提取 `Import` 和 `ImportFrom`。
- 对 forbidden prefix 做断言。

伪代码：

```python
FORBIDDEN_DOMAIN_IMPORTS = [
    "src.infrastructure",
    "src.interfaces",
    "sqlalchemy",
    "psycopg2",
    "asyncpg",
]

FORBIDDEN_INTERFACE_IMPORTS = [
    "src.infrastructure.persistence",
    "sqlalchemy",
    "psycopg2",
    "asyncpg",
]
```

通过标准：

```bash
pytest tests/unit/knowledge/test_architecture_boundaries.py
```

必须通过。

## 10. 失败判定

出现任一情况，Step 1 视为失败：

| 失败情况 | 原因 |
|---|---|
| `domain/knowledge` import 了 `src.infrastructure` | 通用领域逻辑被数据库污染 |
| `domain/knowledge` 出现 `stock/fund/industry` 等词 | 通用层被金融 Adapter 污染 |
| API route 直接 import repository | 接口层绕过应用层 |
| 第一阶段开始定义 `kg_nodes` SQLAlchemy 表 | 过早进入 Step 4 |
| 第一阶段接入 LLM 或 embedding | 过早进入查询/语义层 |
| 架构文档没有同步 | 实施方案与整体架构脱节 |
