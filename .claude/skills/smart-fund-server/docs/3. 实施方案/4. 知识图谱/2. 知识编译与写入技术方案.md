# 知识编译、标准化与写入技术方案

## 1. 模块目标

本模块对应设计文档：

`docs/5. 设计方案/1. 知识图谱/3. 知识编译、标准化与写入设计方案.md`

本模块负责把投影层产出的统一 Source Record 编译为可写入知识图谱事实层的实体、关系、证据和版本数据，并在写入前完成标准化、去重、关系合法性校验、证据绑定和质量门禁。

这里的“写入”只指事实层写入，即 `Node / Edge / Evidence / Version / Review`。面向检索的 `Retrieval Document`、BM25 文档、向量文档、facets 和排序特征属于可重建的检索层派生数据，不直接并入事实层。知识编译完成后只输出事实变更集合和可追溯证据，供后续检索索引模块构建 Retrieval Document。

核心目标：

1. 编译核心只消费统一 Source Record，不直接读取业务表。
2. 编译核心只理解通用内容形态，不硬编码金融 source type。
3. 领域语义由领域适配器解释，业务来源标签只在适配器内消费。
4. 结构化确定性事实优先规则抽取，不交给 LLM 猜。
5. LLM 只在规则无法可靠解决的语义不确定场景中产出候选事实。
6. 所有候选事实写入前必须经过实体标准化、关系合法性校验、证据绑定和质量门禁。
7. 编译写入后默认走增量刷新，不把全量 rebuild 作为日常路径。
8. 事实层和检索层逻辑解耦，检索增强字段先落到可重建 Retrieval Document，不污染主事实。
9. 所有实现优劣以后续真实回放、bad case 和质量指标为准，不因历史设计保留低效方案。

## 2. 模块边界

### 2.1 分层对齐原则

本模块必须遵循项目整体的简化 DDD 分层：

```text
interfaces -> application -> domain
application -> infrastructure
domain -> common
domain -X-> infrastructure
interfaces -X-> domain / repository / DB / external client
```

对应到知识编译：

1. `interfaces` 只负责 HTTP / CLI / task 薄入口，把请求转换成 application DTO。
2. `application` 负责用例编排、工厂装配、事务边界、repository 实现注入、LLM 实现注入、增量刷新触发。
3. `domain` 负责通用知识编译规则、领域适配器协议、候选事实模型、实体和关系校验规则。
4. `infrastructure` 负责 PostgreSQL Fact Store、LLM Proxy、Embedding、Milvus、文件缓存等外部能力实现。

禁止：

1. `interfaces` 直接实例化 `KnowledgeCompiler`、领域适配器、repository 或 LLM client。
2. `domain` 直接导入 `src.infrastructure.*`。
3. `domain` 直接读取环境变量、SQLAlchemy session、FastAPI request、click context。
4. `Compiler Core` 直接调用 LLM Proxy。
5. `Compiler Core` 直接理解金融 `source_type`。

### 2.2 本模块覆盖

本模块覆盖：

- Source Record contract 校验。
- Knowledge Compiler Core 通用编排。
- 领域适配器调度。
- 结构化事实规则抽取。
- LLM 候选事实抽取接口。
- 候选实体、候选事件、候选关系后处理。
- 实体标准化和去重入口调用。
- 关系合法性校验。
- Evidence 生成、证据片段绑定和 evidence metadata 透传。
- Fact Store 写入。
- 增量索引刷新触发。
- 输出事实变更集合，供检索层构建 Retrieval Document。
- 明确事实层字段和检索层派生字段的边界。

### 2.3 本模块不覆盖

本模块不覆盖：

- 从业务表读取 Raw Row。
- Raw Row 到 Source Record 的投影。
- 领域本体全集设计。
- 标准化规则的自动治理闭环。
- Wiki 页面内容策略。
- 检索排序和问答上下文拼装。
- Retrieval Document 的排序字段、BM25 权重、向量文本生成策略和 rerank 规则。
- Retrieval Quality Evaluation 的指标计算和策略回放实现。
- HTTP API 和 CLI 的接口细节。

## 4. 依赖方向和装配方式

### 4.1 依赖方向

知识编译的代码依赖必须保持：

```text
interfaces/api|cli
  -> application/services/knowledge_service.py
  -> domain/knowledge/compiler.py
  -> domain/knowledge_adapters/*
  -> domain/knowledge/*

application/services/knowledge_service.py
  -> infrastructure/persistence/repositories/knowledge_repository_impl.py
  -> infrastructure/llm_proxy
  -> infrastructure/vector_store / embedding
```

领域层只能依赖领域协议：

```text
domain/knowledge_adapters/financial/news_extraction.py
  -> domain/knowledge/extraction.py
  -> domain/knowledge/schemas.py
  -> domain/knowledge_adapters/financial/ontology.py
```

领域层不能这样依赖：

```text
domain/knowledge_adapters/financial/news_extraction.py
  -X-> infrastructure/llm_proxy/service.py
  -X-> infrastructure/config/settings.py
  -X-> infrastructure/persistence/*
```

### 4.2 LLM 端口装配

LLM 是基础设施能力，但 LLM 抽取决策属于领域适配器。因此需要用端口隔离：

```text
Domain:
  LLMFactExtractionPort
    async extract(request) -> CandidateFactPackage / LLMFactExtractionResult

Application:
  KnowledgeLLMExtractionService implements LLMFactExtractionPort
    -> 调用 infrastructure LLMGatewayService
    -> 处理模型方案、缓存、超时、重试、日志

Infrastructure:
  LLMGatewayService
    -> deepseek / claude_tmux / future providers
```

装配规则：

1. `create_knowledge_service()` 负责创建 infrastructure repository 和 LLM port adapter。
2. `KnowledgeService` 负责把 LLM port 注入 adapter registry 或 adapter factory。
3. `KnowledgeCompiler` 只接收已经装配好的 adapter，不关心 LLM 实现。
4. 单元测试可以传入 fake LLM port，不需要真实 API key。
5. 没有配置 LLM port 时，适配器应走规则路径或记录语义候选缺失，不能在领域层自行创建基础设施服务。

### 4.3 Candidate Fact Package 装配

文本抽取、规则抽取和后续新领域抽取都应统一输出 Candidate Fact Package。金融适配器负责把候选包中的 entities、events、relations、uncertainties、rule_suggestions 转换为领域 NodeDraft / EdgeDraft 所需信息。

兼容字段 `mentioned_entities`、`affected_entities` 可以继续被读取，但新 LLM 抽取结果不能只写入这些字段。否则候选关系、歧义项和规则建议无法进入通用治理链路。

### 4.4 Repository 装配

Fact Store 也必须遵循同样规则：

1. `domain/knowledge/repositories/knowledge_repository.py` 定义协议。
2. `infrastructure/persistence/repositories/knowledge_repository_impl.py` 实现 PostgreSQL 写入。
3. `KnowledgeService` / 工厂负责注入实现。
4. `KnowledgeCompiler` 只依赖 repository 协议或由应用层控制写入，不直接创建 SQLAlchemy session。

### 4.5 扩展性要求

后续扩展时必须优先扩展边界点：

| 变化 | 扩展点 | 不应该修改 |
| --- | --- | --- |
| 新增数据源 | 投影 repository + projector | Compiler Core |
| 新增领域 | 新增 domain adapter | Knowledge Compiler Core |
| 新增 source type | 对应领域 adapter handler | Compiler Core |
| 新增 LLM provider | infrastructure llm_proxy provider | Domain Adapter |
| 新增模型选择方案 | application `knowledge_llm_config.py` | Domain Adapter |
| 新增 Fact Store 实现 | infrastructure repository implementation | Domain schemas |
| 新增检索索引 | application 增量刷新编排 + infrastructure index impl | Compiler Core |
| 新增 Retrieval Document 字段 | 检索索引模块和 Retrieval Document builder | Node/Edge/Evidence 主事实表 |

### 4.6 事实层和检索层解耦约束

本模块必须维护以下约束：

1. `Node / Edge / Evidence` 只保存事实、证据、来源、版本、置信度和必要的稳定属性。
2. `search_text`、`key_phrases`、`readable_relations`、`answer_candidate_type`、BM25 text、vector text、rerank features 默认属于检索层派生数据。
3. 编译写入完成后输出 changed nodes、changed edges、changed evidence、stale evidence cleanup，供索引刷新构建 Retrieval Document。
4. Retrieval Document 必须能从事实层重建，不能成为唯一事实来源。
5. Retrieval Document 可以保存生成 prompt、生成版本、字段覆盖率、来源 evidence 和置信度，用于质量回放。
6. 如果真实评估证明某个检索字段长期稳定并具有事实语义，例如 `event_type` 或 `impact_direction`，可以单独设计提升为事实属性，但必须经过 schema 和质量门禁评审。

这样做的目的不是为旧设计让步，而是让检索增强可以快速 A/B 测试、回滚和重建，同时避免 AI 派生字段污染事实层。

## 5. Source Record 技术协议

### 5.1 统一输入要求

编译核心只接受 Source Record 列表。Source Record 必须表达：

| 字段 | 说明 |
| --- | --- |
| `source_id` | 投影层生成的稳定来源 ID，同一原始数据重复投影必须一致。 |
| `source_type` | 领域语义标签，例如 `news_articles`、`derived_signal`；只由领域适配器解释。 |
| `record_kind` | 通用内容形态，例如 `text_document`、`structured_signal`、`entity_snapshot`、`relation_assertion`、`event_assertion`。 |
| `observed_at` | 业务观测时间或事实时间。 |
| `payload` | 结构化内容载体。 |
| `raw_text` | 可选，文本或可读化内容。 |
| `metadata` | 来源表、来源主键、分类原因、可信度、投影规则版本等元数据。 |

### 5.2 兼容策略

当前已有 Source Record 可能只有 `source_type`，没有显式 `record_kind`。第一阶段编码需要支持兼容推断：

| 旧标签 | 推断 record kind |
| --- | --- |
| `news_articles` / `policy_news` | `text_document` |
| `derived_signal` 且 payload 含 `signal_type` / `value` | `structured_signal` |
| `stock_basics` / `fund_basics` / 类似基础资料 | `entity_snapshot` |
| `fund_holdings` / `industry_components` / `concept_components` | `relation_assertion` |
| `l1_events` / `event` 类输入 | `event_assertion` |

后续投影层应显式输出 `record_kind`，避免长期依赖推断。

### 5.3 校验规则

编译前必须校验：

1. `source_id` 非空。
2. `source_type` 非空。
3. 能得到明确 `record_kind`。
4. `observed_at` 可解析或可降级到证据创建时间。
5. 文本材料至少有 `raw_text` 或 payload 中的可读文本。
6. 结构化信号至少有可解释 payload。
7. metadata 至少能追溯来源表和来源主键；如果来源不是业务表，也要有外部来源标识。

校验失败的 Source Record 进入 failed records，不阻断整批。

## 6. 编译核心设计

### 6.1 Compiler Core 职责

Compiler Core 负责通用流程：

1. 接收 Source Record 批次。
2. 为每条 Source Record 建立 evidence 草稿。
3. 按 adapter name 调用领域适配器。
4. 收集适配器输出的候选节点、候选关系和 evidence 引用。
5. 调用实体标准化与去重入口。
6. 调用关系编译器做合法性校验。
7. 绑定关系和 evidence。
8. 汇总节点、关系、证据、失败项和告警。
9. 交给 repository 写入 Fact Store。
10. 返回可用于增量刷新索引的变更集合。

Compiler Core 不能：

1. 读取 `ft_news`、`ft_market_flow` 等业务表。
2. 根据 `source_type == news_articles` 之类条件写金融逻辑。
3. 直接调用 LLM。
4. 绕过领域适配器创建领域实体和领域关系。
5. 在没有 evidence 的情况下写入强关系。

### 6.2 编译数据流

```text
KnowledgeCompileCommand
  -> KnowledgeService.compile_kg()
  -> KnowledgeCompiler.compile(adapter, records)
  -> Source Record validation
  -> EvidenceDraft creation
  -> adapter.compile(record)
  -> Candidate package
  -> EntityResolver
  -> RelationCompiler
  -> Fact Store upsert
  -> ChangedFactSet(nodes, edges, evidence, stale_evidence)
  -> Incremental index refresh
  -> Retrieval Document / evidence chunk / wiki / vector index rebuild for changed facts
  -> KnowledgeCompileResultDTO
```

其中 `ChangedFactSet` 是事实层和检索层的交接对象。它只包含事实对象 ID、证据 ID、版本和清理信息，不包含最终 BM25 文本、向量文本或排序特征。检索层根据它回读事实层并生成可重建 Retrieval Document。

### 6.3 批处理与失败隔离

批处理必须支持单条失败隔离：

1. 单条 Source Record 校验失败，只记录 failed record。
2. 单条适配器抽取失败，只记录 failed record。
3. 单条 LLM 调用失败，只影响该 Source Record 的语义候选，不影响结构化规则候选。
4. 单条关系校验失败，只跳过该关系，不丢弃整条 evidence。
5. repository 写入失败属于批次级失败，需要抛出并保留日志。

### 6.4 幂等要求

同一 Source Record 重复编译时：

1. Evidence ID 必须稳定；如果 Source Record metadata 或 payload 中存在 `fingerprint` / `source_fingerprint` / `content_fingerprint`，Evidence ID 优先使用该 fingerprint 作为版本身份，避免因为 payload 结构或抽取结果字段变化导致同一源数据重复生成 evidence。
2. 规则生成的强实体 ID 和强关系 ID 必须稳定。
3. LLM 候选可能有表达差异，但经过标准化后的主图 ID 应尽量稳定。
4. 已存在节点和关系使用 upsert，不重复插入。
5. 证据 metadata 允许随投影规则版本更新，但必须能追踪来源。
6. `kg_evidence` 必须有 `active / superseded / inactive` 状态。写入同一 `adapter + source_type + source_id` 的新 active evidence 时，旧 active evidence 必须标记为 `superseded`，并记录 `superseded_by`。
7. 被旧 evidence 支撑的旧 edge 必须标记为 `deprecated`，旧 evidence chunks 必须删除，图邻接和索引重建默认只消费 active/latest evidence。
8. 需要提供独立清理入口，用于扫描历史重复 evidence，并按同一 source 只保留最新 active 版本。

## 7. 领域适配器设计

### 7.1 Adapter 职责

领域适配器负责领域语义：

1. 理解 `record_kind` 和 `source_type`。
2. 根据领域本体选择抽取策略。
3. 对结构化 Source Record 执行规则抽取。
4. 对 Source Record 执行规则前置分流，识别强确定、弱确定、语义不确定和不可处理输入，并决定是否调用 LLM。
5. 输出候选实体、候选事件、候选关系、证据片段和不确定项。
6. 不直接写入 Fact Store。

### 7.2 Adapter 内部分发

适配器内部建议按 `record_kind` 分发，再结合 `source_type` 选择 handler：

```text
record_kind = text_document
  -> text semantic extraction handler

record_kind = structured_signal
  -> structured signal rule handler
  -> optional semantic explanation handler

record_kind = entity_snapshot
  -> entity snapshot rule handler

record_kind = relation_assertion
  -> relation assertion rule handler

record_kind = event_assertion
  -> event assertion validation handler
```

编译核心不参与该分发逻辑。

### 7.3 语义确定性评估

领域适配器不能凭感觉决定是否调用 LLM，也不能先调用 LLM 来判断“要不要调用 LLM”。它必须先执行一轮规则驱动的确定性评估，输出评估结果，再根据评估结果进入规则路径、LLM 路径或跳过路径。

这层评估是一个轻量的前置分流器，不做语义生成，不访问模型，只读取 Source Record、领域本体、规则配置、别名/类型词表和已有实体索引的确定性匹配结果。

评估输出建议包含：

| 字段 | 说明 |
| --- | --- |
| `decision` | `rule_only` / `llm_candidate` / `skip` / `fail`。 |
| `confidence` | 0 到 1 的确定性分数。 |
| `reasons` | 命中的确定性或不确定性原因。 |
| `missing_fields` | 缺失的关键字段。 |
| `ambiguous_items` | 歧义实体、歧义关系、歧义方向或歧义指标。 |
| `required_llm_tasks` | 如果调用 LLM，需要它完成哪些任务。 |

评估输入包括：

| 输入 | 用途 |
| --- | --- |
| Source Record 基础字段 | 判断 `source_id`、`record_kind`、时间、来源和 evidence 是否完整。 |
| `payload` / `raw_text` 元信息 | 判断是强结构化数据、弱结构化数据还是自然语言材料。 |
| 强 ID 字段 | 股票代码、基金代码、行业代码、外部事件 ID 等能否直接锚定实体。 |
| 领域本体 | 判断实体类型、关系类型、关系方向是否在允许范围内。 |
| 规则命中结果 | 判断已有规则是否能唯一生成候选事实。 |
| 别名和类型索引 | 判断一个名称是否可能命中多个类型或多个候选实体。 |
| 关键词和句式信号 | 判断是否存在“利好、承压、驱动、约束、受益、受损”等需要解释的关系语义。 |

这些输入都来自本地规则和数据库索引，不需要 LLM。

第一阶段可用规则如下：

| 判定 | 条件 | 处理 |
| --- | --- | --- |
| 强确定 | 有强 ID、字段齐全、关系类型和方向能由规则唯一确定。 | `rule_only`。 |
| 弱确定 | 规则能生成事实，但缺少部分非关键解释字段。 | `rule_only`，记录 warning 或低置信 metadata。 |
| 语义不确定 | 存在文本语义、复杂 payload、名称歧义、关系方向歧义、影响口径歧义。 | `llm_candidate`。 |
| 不可处理 | 缺少 source_id、时间、payload/text、证据来源等关键字段。 | `skip` 或 `fail`，不调用 LLM。 |

语义不确定的识别方式不是“看起来复杂”，而是命中明确的不确定性信号：

| 不确定性信号 | 示例 | 处理 |
| --- | --- | --- |
| 名称多类型命中 | “并购重组”同时可能是政策、主题、事件或概念。 | 进入 LLM 候选路径，要求输出候选类型和证据片段。 |
| 名称多实体命中 | 同名公司、机构、地区或概念同时存在。 | 进入 LLM 候选路径或降级为弱提及。 |
| 关系方向不唯一 | “A 受 B 影响”“A 带动 B”“B 因 A 承压”。 | 进入 LLM 候选路径，要求判断 source/target 和方向。 |
| 影响口径不唯一 | “利好成长资产”“压制估值”“风险偏好提升”。 | 进入 LLM 候选路径，要求给出关系类型、正负方向和依据。 |
| 文本中主体缺失 | 标题只有“重大利好落地”，正文才说明对象。 | 进入 LLM 候选路径或跳过，取决于 evidence 是否充分。 |
| 复杂 payload 口径不清 | JSONB 有嵌套字段，但字段含义不是固定指标。 | 进入 LLM 候选路径，要求解释候选事实，不直接写入。 |
| 规则命中冲突 | 多条规则给出不同实体类型或关系类型。 | 进入 LLM 候选路径或写入 quality issue，不能静默选一个。 |

典型强确定场景：

1. `stock_basics` 里有股票代码和名称，可以规则生成股票实体。
2. `fund_holdings` 里有基金代码、股票代码和持仓比例，可以规则生成持有关系。
3. `industry_components` 里有行业代码和成分股代码，可以规则生成属于关系。
4. `macro_indicator` 里有指标名、周期和值，可以规则生成结构化信号。

典型语义不确定场景：

1. 新闻正文里提到多个公司和行业，但关系方向不明确。
2. 标题表达“利好”“承压”“驱动”等影响语义，但目标实体和影响方向需要上下文判断。
3. 复杂 JSONB payload 中包含嵌套对象，字段名稳定但业务口径不清楚。
4. 同一名称可能对应公司、行业、概念或政策，规则无法高置信归类。
5. 上游事件断言缺少摘要或主线，需要语义补全但不能直接写强事实。

禁止把以下情况交给 LLM 兜底：

1. 缺少主键、来源、时间等基础字段。
2. 关系类型不在领域白名单中。
3. 结构化字段已经能唯一确定实体或关系。
4. 只是为了生成最终 ID 或绕过标准化规则。
5. 没有可绑定 evidence 的输入。

建议阈值：

1. `confidence >= 0.85`：规则路径。
2. `0.45 <= confidence < 0.85`：如果存在明确语义任务，进入 LLM 候选路径。
3. `confidence < 0.45`：通常跳过或降级，除非有足够 evidence 且 LLM 任务边界清晰。

置信度来源应可解释，不是模型打分。第一阶段可以按规则加权计算：

1. 强 ID 命中、字段完整、关系唯一确定会提高置信度。
2. 缺少非关键字段、只有名称没有代码、来源弱可信会降低置信度。
3. 多类型命中、多实体命中、关系方向冲突、影响口径冲突会显著降低置信度，并触发 `llm_candidate`。
4. 缺少基础字段或 evidence 时直接 `skip` / `fail`，不进入 LLM。

### 7.4 金融适配器第一阶段处理范围

第一阶段金融适配器至少覆盖：

| record kind | source type 示例 | 处理方式 |
| --- | --- | --- |
| `text_document` | `news_articles` / `policy_news` | LLM 候选抽取 + 规则校验。 |
| `structured_signal` | `derived_signal` / `market_flow.*` / `sentiment.*` | 优先规则抽取，必要时 LLM 解释复杂 payload。 |
| `entity_snapshot` | `stock_basics` / `fund_basics` | 规则生成实体候选。 |
| `relation_assertion` | `fund_holdings` / `industry_components` / `concept_components` | 规则生成关系候选。 |
| `event_assertion` | `l1_events` / 上游事件输入 | 规则校验或轻量语义补全。 |

## 8. LLM 候选抽取设计

### 8.1 调用位置

LLM 只能由领域适配器调用，Compiler Core 不直接调用 LLM。

这里的“领域适配器调用 LLM”指调用领域层定义的 LLM 抽取端口，不是直接调用 `src.infrastructure.llm_proxy`。实际模型路由、供应商调用、缓存、超时和重试都由 application port adapter 与 infrastructure 实现处理。

允许调用的条件：

1. 语义确定性评估已经输出 `decision=llm_candidate`。
2. 需要从文本或复杂 payload 中抽取候选事实。
3. 需要歧义判断、关系方向判断或影响口径解释。
4. 输入已经过 Source Record 标准化，不是原始业务表整行。
5. 有明确输出 schema 和候选事实边界。
6. `required_llm_tasks` 非空，且任务边界可验证。

禁止调用的情况：

1. 股票代码、基金代码、持仓比例、行业成分等确定性关系。
2. 仅为补齐可以由规则确定的字段。
3. 没有 evidence 片段约束的事实创造。
4. 直接决定最终主键、最终归一结果或最终写入。
5. 为了判断是否需要 LLM 而调用 LLM。

### 8.2 LLM 输入包

领域适配器调用 LLM 时，应构造受控输入包：

| 输入 | 说明 |
| --- | --- |
| `source_id` | 用于追踪和缓存。 |
| `record_kind` | 通用内容形态。 |
| `source_type` | 领域标签。 |
| `observed_at` | 时间上下文。 |
| `text` | 标题、摘要、正文或 payload 可读化内容。 |
| `payload_summary` | 复杂结构化 payload 的摘要。 |
| `allowed_entity_types` | 当前领域允许的实体类型。 |
| `allowed_relation_types` | 当前领域允许的关系类型。 |
| `known_candidates` | 可选，已有实体、别名、代码、词表约束。 |
| `evidence_policy` | 要求输出证据片段和置信度。 |

### 8.3 LLM 输出包

LLM 输出必须是结构化候选包：

| 输出 | 说明 |
| --- | --- |
| `entities` | 候选实体，含名称、类型、别名、证据片段、置信度。 |
| `events` | 候选事件，含标题、摘要、时间、相关实体、证据片段、置信度。 |
| `relations` | 候选关系，含关系类型、source、target、方向、证据片段、置信度。 |
| `uncertainties` | 歧义说明、候选解释、降级建议。 |
| `rule_suggestions` | 可选，新模式下的规则候选，不直接生效。 |

输出不满足 schema 时，该 LLM 结果丢弃或进入 failed record，不能被宽松解析后写入主图。

### 8.4 LLM 缓存与成本控制

LLM 抽取必须支持缓存：

1. cache key 至少包含 model、prompt/schema version、source_id、输入内容 hash。
2. 同一 Source Record 重复编译时优先命中缓存。
3. 缓存命中不应跳过后处理校验。
4. 模型、prompt、schema 升级后可以通过版本变化自然失效。

## 9. 后处理与写入

### 9.1 实体标准化

所有候选实体必须经过实体标准化与去重治理模块：

1. 强 ID 优先，例如股票代码、基金代码、官方机构代码。
2. 系统规则和数据库规则优先。
3. LLM 候选只提供别名、语义解释和歧义信息，不直接决定最终 ID。
4. 无法高置信归一的实体可以写为候选状态或降级处理，不能伪装成强事实。

### 9.2 关系合法性校验

所有候选关系必须经过 Relation Compiler：

1. relation type 必须在领域白名单中。
2. source node type 和 target node type 必须符合本体约束。
3. 方向必须明确。
4. 强关系必须绑定 evidence。
5. 不合法关系进入 failures，不写入主图。

### 9.3 Evidence 绑定

Evidence 是关系入图的最低要求：

1. 每条 Source Record 至少生成一条 evidence。
2. Source Record metadata 必须透传到 evidence metadata。
3. LLM 候选关系必须保留证据片段。
4. 结构化规则关系必须能回溯到 payload 字段或来源记录。
5. Evidence chunk 后续由索引模块派生，不是主事实。

### 9.4 Fact Store 写入

写入顺序：

1. upsert evidence。
2. upsert nodes。
3. upsert edges。
4. 写入 edge-evidence 绑定。
5. 记录编译 run 信息。
6. 返回本次变更的 node IDs、edge IDs、evidence IDs。

Fact Store 是事实源。Wiki、Milvus、graph adjacency、hybrid chunks 都是派生数据。

### 9.5 增量刷新

编译成功后，应用层触发增量刷新：

1. 更新变更节点和关系的 graph adjacency。
2. 为新增 evidence 生成 evidence chunks。
3. 刷新相关实体页、关系页、时间线页等 Wiki 页面。
4. 更新 hybrid retrieval chunks。
5. 记录刷新统计和 warnings。

全量 rebuild 只用于规则大改、历史清理、索引损坏或质量基线重跑。

### 9.6 Retrieval Document 交接

本模块不直接定义 Retrieval Document 的排序字段，但必须为检索层提供稳定输入。

交接要求：

1. 编译结果必须返回本次变更的 node IDs、edge IDs、evidence IDs。
2. evidence 版本清理必须返回被 supersede 或 inactive 的 evidence IDs，供检索层删除旧索引。
3. edge 必须绑定 evidence，否则检索层无法生成可追溯 readable relation。
4. node aliases、external_ids、properties 中的稳定字段可以作为检索层输入。
5. evidence content、payload、metadata 必须足够生成 evidence summary、source_type_tags 和 search_text。
6. 检索层生成的 key_phrases、search_text、answer_candidate_type、rerank features 不回写 Fact Store。

如果后续真实评估证明某个检索增强字段应提升为事实属性，必须走新的 schema / 设计变更，而不是让索引模块反向修改主图事实。

## 10. 错误处理与降级策略

| 场景 | 处理 |
| --- | --- |
| Source Record 缺少必要字段 | 单条 failed record，不阻断批次。 |
| 无法推断 record kind | 单条 failed record，并提示投影层补字段。 |
| Adapter 不支持某个 record kind | 单条 failed record 或 skipped，记录原因。 |
| LLM 调用失败 | 保留规则抽取结果，LLM 候选为空，记录 warning/failure。 |
| LLM 输出 schema 不合法 | 丢弃该 LLM 输出，记录 failure。 |
| 关系校验失败 | 跳过该关系，保留 evidence 和其他合法事实。 |
| 实体归一低置信 | 降级为候选状态或跳过强关系，记录 quality issue。 |
| repository 写入失败 | 批次级失败，抛出异常，不静默吞掉。 |
| 增量索引刷新失败 | 主事实已写入时不回滚事实，记录 index warning，并允许后续补刷。 |
| Retrieval Document 生成失败 | 不回滚事实层，记录 index warning，并进入补刷队列或手动 rebuild。 |
| 检索增强字段被误写入事实字段 | 视为实现偏差，记录到 `9. 待优化.md` 并制定迁移或清理方案。 |

如果实现中出现以下降级，必须记录到 `9. 待优化.md`：

1. 编译核心仍硬编码金融 source type。
2. Compiler Core 直接调用 LLM。
3. Domain Adapter 直接导入 `src.infrastructure.*`。
4. Source Record 仍长期缺少 `record_kind`，只能靠推断兼容。
5. LLM 输出没有严格 schema 校验。
6. LLM 生成的候选没有证据片段也被写入。
7. 增量刷新覆盖不完整，只能依赖全量 rebuild。
8. Retrieval Document、BM25 文本、rerank features 等检索字段直接污染 Node/Edge/Evidence 主事实。

## 12. 真实场景验收

### 12.1 真实库回放

使用：

```text
docs/6. 使用说明/知识图谱/3_kg_real_replay_quality_baseline.py
```

验收内容：

1. 真实业务表先经过统一 Source Record 投影。
2. 投影结果进入 compile 链路。
3. 编译结果写入 Fact Store。
4. 增量索引刷新完成。
5. deterministic replay 检索用例通过。

### 12.2 最小质量门禁

第一阶段至少要求：

1. 单批 Source Record 编译不因单条失败整体中断。
2. `news_articles` / `policy_news` 能走文本候选抽取和后处理。
3. `derived_signal` 能走结构化规则路径。
4. 每条写入关系都能追溯 evidence。
5. LLM 候选不能绕过关系校验。
6. 编译核心不直接调用 LLM。
7. 编译核心不硬编码金融 source type。
8. 领域层不直接导入 infrastructure。
9. 新增数据默认增量刷新，不强制全量 rebuild。
10. 编译链路不把 retrieval-only 字段写入事实层。
11. Retrieval Document 可以通过事实层变更集合重建。

## 13. 验收标准

本模块完成的标准：

1. 编译器只接收 Source Record，不读取业务表。
2. Source Record 有明确或可兼容推断的 `record_kind`。
3. Compiler Core 不硬编码金融 source type。
4. Compiler Core 不直接调用 LLM。
5. Domain Adapter 不直接导入 infrastructure。
6. LLM 通过领域端口和 application adapter 接入。
7. 领域适配器可以基于明确场景调用 LLM。
8. LLM 输出是候选事实包，并经过 schema 校验。
9. 所有候选事实经过实体标准化、关系校验和证据绑定。
10. 证据缺失或关系非法的事实不会写入主图。
11. Fact Store 写入具备幂等能力。
12. 增量刷新能覆盖本次变更的 graph adjacency、evidence chunks、Wiki 和 hybrid chunks。
13. 检索层派生文档能从事实层重建，且保留 source fact refs。
14. retrieval-only 字段不会污染 Node/Edge/Evidence 主事实。
15. 单元测试、集成测试、真实库回放测试都有对应覆盖。

## 14. 已知偏差与待优化

当前模块如出现以下情况，必须补充到 `9. 待优化.md`：

- 现有代码尚未显式支持 `record_kind`，只能通过 `source_type` 推断。
- 金融适配器 handler 分发仍和旧 source type 逻辑耦合。
- Domain Adapter 仍直接导入 `src.infrastructure.llm_proxy`。
- LLM 候选抽取 schema 暂不完整。
- LLM 调用缓存、prompt/schema version 或失败降级未完成。
- 增量刷新覆盖不完整，只能依赖 rebuild。
- 真实库回放脚本仍未完全走统一 Source Record 投影入口。
- Retrieval Document、BM25 text、rerank features 等检索增强字段直接写入主事实。
- 检索层索引无法从事实层重建，只能依赖某次临时生成结果。
