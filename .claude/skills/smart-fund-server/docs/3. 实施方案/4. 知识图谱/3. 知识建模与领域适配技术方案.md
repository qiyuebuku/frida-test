# 知识建模与领域适配技术方案

## 1. 模块目标

本模块负责通用知识模型、领域适配器协议和金融适配器落地。

核心目标：

1. 保持通用知识基础设施不写死金融语义。
2. 通过 Adapter 协议接入不同领域。
3. 金融适配器第一版覆盖投研闭环所需实体、关系、置信和消费规则。
4. 为编译、治理和检索提供稳定模型边界。
5. 明确事实模型和检索派生模型边界，避免 retrieval-only 字段进入通用事实模型。

## 2. 模块边界

本模块覆盖：

- 通用 Node、Edge、Evidence、Source Record 模型。
- Candidate Fact Package 通用候选事实模型。
- Adapter 协议。
- 金融领域 ontology。
- 金融 source mapping。
- 金融置信策略和消费边界。
- 事实属性、候选属性和检索派生属性的建模边界。

本模块不覆盖：

- 数据如何读取和编译写入。
- 标准化规则如何落库和自动维护。
- Wiki、Retrieval Document、索引和查询接口实现。
- BM25 文本、向量文本、rerank features 和 coverage facets 的字段设计。

## 4. 数据流

1. Application Service 根据 adapter name 获取领域适配器。
2. Adapter 接收 Source Record。
3. Adapter 根据 source type 选择规则抽取或文本抽取。
4. 规则或 LLM 产出 Candidate Fact Package。
5. Adapter 将 Candidate Fact Package 转换为实体草稿、关系草稿和证据引用。
6. Compiler 消费草稿并进入后续标准化和写入流程。
7. 写入完成后，检索层根据 changed facts 生成 Retrieval Document；Adapter 不直接输出最终 BM25 文本和 rerank features。

## 5. 技术决策

### 5.1 通用模型保持领域无关

`src/domain/knowledge` 不能引入金融专有概念。架构测试需要检查通用层不依赖 `knowledge_adapters/financial`。

### 5.2 金融本体由适配器维护

金融实体、关系、source type、置信策略放在 `knowledge_adapters/financial` 下。金融适配器可以迭代，不影响通用模型。

### 5.3 稳定 ID 不能只依赖展示名称

稳定 ID 应结合 adapter、实体类型、外部 ID、标准名和必要上下文。对事件类实体，不能假设相似标题一定生成同一 ID，事件主线归并应由治理规则处理。

### 5.4 消费边界显式化

金融关系需要区分：

- 可参与硬评分的高置信结构化关系。
- 可用于解释和候选召回的语义关系。
- 需要进一步验证的候选关系。

### 5.5 Candidate Fact Package 一等化

LLM 和规则抽取的新结果必须先形成通用 Candidate Fact Package，再由领域适配器转换为 NodeDraft / EdgeDraft。

禁止把新抽取结果只折回金融历史字段，例如 `mentioned_entities`、`affected_entities`。这些字段可以作为兼容输入继续被金融适配器读取，但不能作为通用候选事实协议。

### 5.6 事实属性和检索派生属性分离

通用模型和领域适配器必须区分三类字段：

| 类型 | 例子 | 落点 |
| --- | --- | --- |
| 事实属性 | code、exchange、event_type、relation_type、direction、source_time、evidence metadata | NodeDraft、EdgeDraft、EvidenceDraft。 |
| 候选治理属性 | confidence、uncertainties、rule_suggestions、normalization hints | Candidate Fact Package 或 review/quality payload。 |
| 检索派生属性 | search_text、key_phrases、readable_relations、answer_candidate_type、BM25 text、vector text、rerank features | Retrieval Document 或检索索引，不进入事实模型。 |

Adapter 可以提供足够的事实属性和证据引用，帮助检索层生成高质量 Retrieval Document；但 Adapter 不负责直接生成最终检索索引文本。

如果真实质量评估证明某个检索派生字段应固化为事实属性，需要先更新本体和写入设计，再进入 NodeDraft / EdgeDraft / EvidenceDraft。

## 6. 错误处理与降级策略

1. Adapter 不支持的 source type 应返回明确 failure，不应静默忽略。
2. 非法实体类型或非法关系类型应在编译前被拦截。
3. 金融适配器新增类型时必须同步测试 ontology、source mapping 和消费策略。
4. 如为了快速接入临时把金融逻辑写进通用层，必须记录到 `9. 待优化.md`。
5. 如果 Adapter 把 retrieval-only 字段塞进 NodeDraft / EdgeDraft / EvidenceDraft，必须记录为实现偏差并清理。

## 8. 验收标准

1. 通用层不依赖金融适配器。
2. 金融适配器可以独立定义实体、关系和 source mapping。
3. 新增金融 source type 有明确抽取和测试覆盖。
4. 置信和消费策略能区分硬消费、解释消费和候选消费。
5. 事件、主题、行业等边界问题不会靠通用层硬编码解决。
6. LLM 抽取结果以 Candidate Fact Package 进入适配器转换链路，不再只能依赖金融历史 payload 字段。
7. `search_text`、`key_phrases`、`readable_relations`、`answer_candidate_type`、rerank features 等 retrieval-only 字段不会进入 NodeDraft / EdgeDraft / EvidenceDraft。
8. Retrieval Document 作为检索层派生模型，可以引用事实层对象，但不能成为事实源。

## 9. 已知偏差与待优化

当前模块如出现以下情况，必须补充到 `9. 待优化.md`：

- 金融字段进入通用模型。
- 为了测试方便绕过 Adapter 协议。
- 新实体类型缺少 ontology 和消费策略。
- 稳定 ID 规则无法覆盖真实事件主线，只能临时按标题生成。
- retrieval-only 字段混入通用事实模型或金融 ontology。
- Adapter 直接生成最终 BM25/vector/rerank 文本，绕过检索层 Retrieval Document builder。
