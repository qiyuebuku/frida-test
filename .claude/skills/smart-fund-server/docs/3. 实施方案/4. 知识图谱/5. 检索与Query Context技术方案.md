# 检索与 Query Context 技术方案

## 1. 模块目标

本模块负责把知识图谱中的 Node、Edge、Evidence、Wiki 派生页和向量索引结果组织成统一的 Query Context，供投研问答、事件解释、策略复盘和质量回放消费。

当前目标不是再增加一个普通向量检索入口，而是把现有多通道召回升级为可控的 KG-RAG 检索链路：

```text
Query
 -> Hard Constraint Extractor
 -> LLM Anchor Parser
 -> Anchor Validator
 -> Query Routing Decision
 -> deterministic_plan 或 agentic_arag
 -> deterministic_plan: 多通道宽召回 -> Candidate Package Builder -> LLM Candidate Judge -> Controlled Graph Expansion
 -> agentic_arag: Retrieval Controller -> search/find/open/summarize -> Candidate Package Builder -> LLM Candidate Judge -> Working Set
 -> Evidence / Wiki / Chunk Window Read
 -> Query Context
```

核心目标：

1. 支持实体解析、图搜索、语义 hybrid search、Wiki search、证据回读和 chunk window。
2. 在多通道召回前识别 Query Anchor，明确查询核心事件、实体、主题、时间和关系意图。
3. 在图谱扩展前做候选裁判，避免无关 semantic hit 带出自己的 node/edge。
4. 用三段式路由决定走 `deterministic_plan` 还是 `agentic_arag`，并支持低质量自动升级。
5. 支持 parent evidence、sibling chunk 和 window expansion，避免孤立 chunk 被直接消费。
6. 支持真实库坏例回放，能识别“目标 evidence 命中但上下文污染”的失败。
7. 保持 HTTP API、CLI、Python 服务层返回同一套 Query Context 语义。

## 2. 模块边界

本模块覆盖：

- Query Anchor 识别。
- Query Routing Decision。
- Retrieval Plan 生成与执行。
- `deterministic_plan` 检索链路。
- `agentic_arag` 受控工具循环。
- 实体解析、图搜索、语义 hybrid search、Wiki search、chunk read。
- Candidate Judge / Rerank。
- Controlled Graph Expansion。
- Evidence parent / sibling / window expansion。
- Query Context DTO、trace、warnings。
- 检索坏例回放和质量基线。

本模块不覆盖：

- 原始业务表如何投影成 Source Record。
- Source Record 如何编译写入主图。
- 实体标准化规则如何生成和迁移。
- 领域 ontology 如何定义。
- Wiki 页面如何生成；本文只说明 Wiki 如何作为检索通道和上下文来源被消费。
- API 字段版本治理和权限控制；这些属于服务化接口实施方案。

## 4. 数据流

### 4.1 确定性检索链路

`deterministic_plan` 用于明确、低成本、可回放的问题：

```text
query
 -> Query Anchor
 -> Fast Router 选择 deterministic_plan
 -> entity_resolve / graph_search / semantic_hybrid_search / wiki_search / chunk_read
 -> Candidate Merge
 -> Candidate Package Builder
 -> LLM Candidate Judge
 -> Controlled Graph Expansion
 -> Chunk Window Expansion
 -> Query Context
 -> Post-check Router
```

如果 Post-check Router 判断上下文质量不足，则自动升级为 `agentic_arag`。

### 4.2 Agentic 检索链路

`agentic_arag` 用于复杂、多跳、长文档、候选冲突或确定性检索低质量的问题：

```text
query
 -> Query Anchor
 -> Query Routing Decision 选择 agentic_arag
 -> Retrieval Working Set 初始化
 -> Agent Loop
    -> search
    -> Candidate Package Builder
    -> Candidate Judge
    -> find / open
    -> Candidate Package Builder
    -> Candidate Judge
    -> summarize
    -> Working Set 更新
 -> Query Context
```

Agentic 检索不是自由搜索。每轮工具调用都必须受 Query Anchor、Candidate Judge、Working Set、预算和停止条件约束。

## 5. Query Anchor 技术方案

### 5.1 数据结构

新增领域对象：

```text
QueryAnchor
  query: str
  core_event: str | None
  core_entities: list[AnchorHint]
  core_topics: list[AnchorHint]
  relation_intents: list[str]
  time_hints: list[AnchorHint]
  source_hints: list[AnchorHint]
  negative_boundaries: list[str]
  inferred_hints: list[AnchorHint]
  hard_constraints: list[HardConstraint]
  confidence: float
  warnings: list[str]

AnchorHint
  text: str
  hint_type: entity | event | topic | time | source | relation
  strength: strong | weak | inferred
  confidence: float
  source: hard_constraint | llm | validator

HardConstraint
  value: str
  constraint_type: source_id | evidence_id | instrument_code | date | exact_title
  must_preserve: bool
```

设计原则：

- LLM Anchor Parser 的结构化输出是最终语义判断来源。
- Hard Constraint Extractor 不做语义理解，只提取低歧义硬标识。
- Anchor Validator 不重新解释 query，只做校验、补漏、降级、告警和必要 retry。
- 现有代码中如已有 `guard_constraints` 字段，实施迁移时应保留兼容读取，但新语义统一命名为 `hard_constraints`。

### 5.2 Hard Constraint Extractor

Hard Constraint Extractor 只提取不会错或很少错的硬标识，不承担关键词过滤、模糊匹配、黑名单、白名单或语义相关性判断。

- `source_id` / `evidence_id`：例如 `ft_news:77543`、`kg_ev:*`。
- 代码：领域内强标识代码，例如金融适配器中的证券代码、基金代码等。
- 日期和时间范围：明确日期、年份、季度、今日、最近、近一周。
- 精确引用标题：用户明确粘贴的完整标题或引号中的标题片段。

Hard Constraint Extractor 不做以下事情：

- 不从全库模糊匹配实体名。
- 不用 query 长短语作为保留/丢弃候选的规则。
- 不根据关键词判断候选相关或不相关。
- 不直接决定最终 `keep`、`weak_keep`、`drop`。

Hard Constraint Extractor 输出会作为 LLM Anchor Parser 和 Candidate Package 的输入特征，而不是最终 Anchor，也不是候选裁判结果。

### 5.3 LLM Anchor Parser

LLM Anchor Parser 通过 LLM Proxy 调用模型。知识图谱场景通过模型方案配置决定使用哪个模型，例如测试期可用 `deepseek-v4-flash`，复杂查询可切到 `deepseek-v4-pro`。

输入：

- 原始 query。
- Hard Constraint Extractor 输出。
- 精确实体候选。
- 当前检索模式。
- 输出 JSON Schema。

输出必须是结构化 Query Anchor，不允许自由文本作为主结果。

LLM 需要判断：

- query 的核心事件是什么。
- query 的核心实体是什么。
- query 的核心主题是什么。
- 用户问的是影响、原因、受益、风险、传导还是关联。
- 哪些内容是排除边界，例如“不应扩展到无关公司、股票或产业链事件，除非候选证据明确说明该事件对这些对象有影响”。

LLM Anchor Parser 不直接选择最终 evidence，也不直接改写检索结果。

### 5.4 Anchor Validator

Anchor Validator 校验 LLM 输出：

1. Hard Constraint 中 `must_preserve=true` 的 source id、代码、日期、精确标题必须出现在 Anchor 或 `hard_constraints` 中。
2. LLM 输出 query 外实体时，如果该实体不在候选实体中，降级为 `inferred_hint`，不能作为 strong anchor。
3. LLM 改写 source id、代码、日期时，触发一次 retry；retry 后仍冲突则保留 Hard Constraint 并记录 warning。
4. LLM 输出置信度低于阈值时，保留可校验部分，并提示 Candidate Judge 降低 Anchor 权重。
5. Validator 不重新做语义判断，不把规则结果覆盖 LLM 的核心事件和关系意图。

## 6. Query Routing 技术方案

### 6.1 路由结果模型

新增领域对象：

```text
QueryRoutingDecision
  requested_mode: str | None
  initial_mode: deterministic_plan | agentic_arag
  final_mode: deterministic_plan | agentic_arag
  complexity: simple | medium | complex | unknown
  confidence: float
  reasons: list[str]
  max_tool_calls: int
  upgraded: bool
  upgrade_reason: str | None
  metrics: RetrievalQualityMetrics | None

RetrievalQualityMetrics
  anchor_coverage: float
  keep_candidates: int
  drop_ratio: float
  evidence_refs: int
  topic_conflict: bool
  forbidden_hit: bool
  context_precision: float
```

### 6.2 Fast Router

Fast Router 不调用 LLM，只做低成本初筛：

1. 用户显式指定模式时，显式模式优先。
2. query 中存在 source id、evidence id、领域内强标识代码、完整标题片段等强约束时，优先选择 `deterministic_plan`。
3. query 明确包含复杂意图时，直接选择 `agentic_arag`。
4. 其余情况进入 LLM Router。

复杂意图词包括但不限于：为什么、如何影响、传导、归因、对比、复盘、分别影响、受益对象、受损对象、多跳推理、候选冲突、长文档精读。

Fast Router 的规则只决定“是否明显简单或明显复杂”，不试图完整理解 query。

### 6.3 LLM Router

LLM Router 只在 Fast Router 无法明确判断时触发。

输入：

- 原始 query。
- Query Anchor。
- Hard Constraint Extractor 硬约束。
- 用户请求预算。
- 默认工具调用预算。

输出：

```json
{
  "mode": "deterministic_plan | agentic_arag",
  "complexity": "simple | medium | complex | unknown",
  "confidence": 0.0,
  "reasons": [],
  "max_tool_calls": 6
}
```

如果 LLM Router 置信度低于阈值，保守选择 `deterministic_plan`，再由 Post-check Router 根据真实检索质量决定是否升级。

### 6.4 Post-check Router

`deterministic_plan` 执行后必须产出质量指标。只要出现以下任一情况，就自动升级到 `agentic_arag`：

- `evidence_refs == 0`
- `keep_candidates == 0`
- `anchor_coverage < 0.5`
- `drop_ratio > 0.6`
- `topic_conflict == true`
- `forbidden_hit == true`
- `context_precision < 0.7`
- Query Anchor confidence < 0.65

Post-check Router 的升级结果必须写入 Query Context trace，避免出现“为什么突然变慢、为什么调用 LLM”的黑盒行为。

## 7. Candidate Judge / Rerank 技术方案

### 7.1 数据结构

```text
CandidatePackage
  package_id: str
  query_anchor: QueryAnchor
  hard_constraints: list[HardConstraint]
  candidate: RetrievalCandidate
  related_nodes: list[NodeSummary]
  related_edges: list[EdgeSummary]
  related_evidence: list[EvidenceSummary]
  graph_paths: list[GraphPathSummary]
  deterministic_features: CandidateFeatures
  risk_flags: list[str]

RetrievalCandidate
  candidate_id: str
  candidate_type: evidence | node | edge | wiki | path | chunk
  title: str
  text: str
  node_refs: list[str]
  edge_refs: list[str]
  evidence_refs: list[str]
  source_channel: str
  raw_score: float

CandidateJudgement
  candidate_id: str
  decision: keep | weak_keep | drop
  role: direct_answer | support | background | noise
  relevance_score: float
  can_expand_graph: bool
  anchor_coverage: dict
  intent_match: bool
  path_validity: valid | weak | invalid | unknown
  evidence_support: strong | weak | none
  topic_drift: bool
  risk_flags: list[str]
  reason: str
  judge_source: llm | deterministic_exact | fallback
```

### 7.2 Candidate Package Builder

Candidate Judge 不能裁判孤立字符串，也不能只看单个 chunk。进入裁判前必须先构建 Candidate Package。

Candidate Package Builder 负责：

- 合并同一 evidence、node、edge、wiki、chunk 的多通道召回结果。
- 补齐候选关联的 node、edge、evidence、source channel、raw score。
- 查找候选与 Query Anchor 之间的可解释图路径。
- 标记路径跳数、关系类型、方向、是否经过 hub node。
- 标记 evidence 是否支撑路径上的边。
- 写入 Hard Constraint 命中情况，但不据此直接裁判候选。

Candidate Package Builder 不负责判断候选是否相关，只负责把 LLM Candidate Judge 需要看的信息准备完整。

### 7.3 确定性特征标记

确定性逻辑只输出特征和风险，不作为自然语言查询的最终语义裁判。

- `anchor_overlap_score`：候选标题、正文、node name、wiki title 是否覆盖核心 Anchor。
- `entity_overlap_score`：候选是否共享 LLM Anchor Parser 识别出的核心实体。
- `source_constraint_score`：候选是否满足 source/evidence 约束。
- `relation_intent_score`：候选关系是否匹配影响、原因、受益、传导等意图。
- `topic_drift_penalty`：候选主题是否明显偏移。
- `graph_support_score`：候选 node/edge 是否由相关 evidence 支撑。
- `hub_path_risk`：候选是否通过宽泛 hub node 到达。
- `path_evidence_missing`：路径上的边是否缺少 evidence 支撑。

确定性逻辑可以直接裁判的场景只限于低歧义精确查询：

- 用户明确查询某个 `source_id` / `evidence_id`，且候选精确命中该 id。
- 用户明确查询某个证券代码，且候选是该证券主节点或直接绑定 evidence。
- 候选路径缺少 evidence、穿过高风险 hub 且没有直接证据时，可以标记为 `requires_llm` 或 `high_risk`，但不应仅靠字符串 overlap 直接 `keep`。

### 7.4 LLM Candidate Judge 主路径

LLM Candidate Judge 是自然语言查询候选相关性判断的主路径。它只裁判已经召回并打包好的 top-K Candidate Package，不做全库搜索，不生成新事实，不修改主图。

触发条件：

- query 是自然语言问题，而不是精确 id 查询。
- 候选来自语义检索、Wiki、chunk 或二跳图扩展。
- 候选通过 hub node 到达。
- 候选只间接关联 Query Anchor。
- 确定性特征出现 topic drift、path evidence missing、intent mismatch 等风险。
- 回放中命中 negative expectation 或 forbidden hit。

输入：

- Query Anchor。
- Hard Constraint 列表。
- Candidate Package。
- 关系意图和领域适配器提供的关系解释。
- 历史 bad case negative expectation。

输出：

- `decision`：`keep`、`weak_keep`、`drop`。
- `role`：直接回答、间接支撑、背景、噪声。
- `intent_match`。
- `path_validity`。
- `evidence_support`。
- `can_expand_graph`。
- `risk_flags`。
- 简短 `reason`。

程序必须校验 LLM judgement：

- judgement 引用的 node、edge、evidence 必须存在于 Candidate Package。
- LLM 不能把 Hard Constraint 改写成另一个 id、代码或日期。
- LLM 不能创造候选包外的新事实。
- LLM 输出结构无效时，进入 fallback，不允许直接放开所有候选。

### 7.5 Fallback 策略

LLM Candidate Judge 失败时，fallback 只能保守保留低风险候选：

- 精确 source/evidence 查询命中的候选可以 `keep`。
- 一跳、关系意图匹配、evidence 完整支撑的候选可以 `keep`。
- 语义检索命中但路径不清楚的候选最多 `weak_keep`。
- hub 二跳、证据不足、主题漂移候选必须 `drop` 或不进入主 Query Context。

fallback 结果必须写入 warning 和 trace，不能伪装成正常 LLM 裁判。

### 7.6 Candidate Judge 与 Query Context

Query Context 必须返回：

- Anchor 摘要。
- 每个保留候选的 judgement。
- 被丢弃候选数量和主要原因。
- Agentic Retrieval 下的 Working Set 摘要。
- Agentic Retrieval 下的 controller decisions 和工具 trace。
- channels_used。
- warnings。

这能让后续真实回放定位：到底是 Anchor 错了、召回错了、Judge 错了，还是 graph expansion 错了。

## 8. Controlled Graph Expansion 技术方案

当前问题是 semantic hit 一旦进入上下文，就可能通过 evidence 带出自己的 node/edge。改造后，graph expansion 必须受 Candidate Judge 控制：

1. 宽召回候选先归并成 RetrievalCandidate。
2. Candidate Package Builder 补齐候选的 node、edge、evidence、graph path 和 deterministic features。
3. Candidate Judge 输出 judgement。
4. 只有 `keep` 且 `can_expand_graph=true` 的候选可作为 expansion seed。
5. `weak_keep` 只可进入低置信背景区，不允许触发 evidence 回读、graph fan-out、Wiki 扩展或 sibling chunk 扩展。
6. `drop` 不允许扩展 node、edge、wiki 或 sibling chunk。
7. 扩展出的 node/edge 必须保留 seed candidate id 和 judgement reason。
8. 通过 hub node 产生的候选必须重新构建 Candidate Package 并进入 LLM Candidate Judge，不能默认进入上下文。

需要改造的位置：

- `HybridRetrievalRuntime.build_answer_context_async`
- `RetrievalPlanExecutor`
- `graph_search` / `chunk_read` 的结果合并逻辑
- Query Context DTO 和 trace 输出

## 9. Chunk Window 技术方案

### 9.1 Chunk 层级

Evidence chunk 是索引单元，不是最终消费单元。后续 chunk payload 需要支持：

```text
document_id
parent_evidence_id
chunk_index
prev_chunk_id
next_chunk_id
chunk_role: document_summary | passage | entity_index | relation_index
```

第一阶段不强制重构所有历史 chunk，可以先做到：

- 单 evidence 生成 document_summary chunk。
- 长 evidence 支持 passage chunk。
- 命中 passage 后回读 parent evidence。
- 同一 evidence 内按 chunk_index 取前后 sibling。

### 9.2 Window Expansion

命中 chunk 后默认扩展：

- 父 evidence。
- sibling chunk window，例如前后各 1 个 chunk。
- document summary chunk。
- 直接绑定的 node/edge。

如果 sibling 不存在，记录 `chunk_window_partial` warning，不阻断检索。

## 10. Agentic Retrieval 技术方案

### 10.1 领域对象

```text
  target_candidate_ids: list[str]

  dropped_candidates: list[CandidateJudgement]

```

### 10.2 Retrieval Controller

Retrieval Controller 通过 LLM 编排，但不是自由 Agent。它只能根据 Query Anchor、Working Set、上一轮 Candidate Judge 结果、预算和缺口选择下一步工具。

输入：

- 原始 query。
- Query Anchor。
- Retrieval Working Set 摘要。
- 上一轮 dropped / weak_keep / keep 统计。
- 当前 evidence 覆盖和缺失 Anchor。
- 剩余工具调用预算。
- 可用工具列表和工具约束。

输出必须是结构化 `RetrievalControllerDecision`。不允许输出自由文本作为执行依据。

Controller 决策规则：

- 如果缺少核心证据，优先 `search` 或 `find`。
- 如果候选 evidence 命中但上下文不足，优先 `open` 父 evidence 或 sibling chunk。
- 如果候选冲突，优先 `open` 关键 evidence 或 `find` 对比信息。
- 如果上下文接近预算上限，优先 `summarize`。
- 如果 evidence 已覆盖 Query Anchor，或连续两轮无新增有效 evidence，输出 `stop`。
- Controller 不能直接把候选加入 Query Context，必须经过 Candidate Package Builder 和 Candidate Judge。

### 10.3 LLM 调用预算与自动状态推进

Agentic Retrieval 不应把每个状态判断都交给 LLM。真实回放已经暴露出一个问题：普通 query 如果经历 `controller -> judge -> controller -> judge -> stop controller`，LLM 调用会成为主要耗时来源。

实施规则：

1. 普通 query 默认最多执行 1 次 LLM Controller 和 1 次 LLM Candidate Judge；这是默认预算，不是硬性上限。
2. LLM Controller 只负责生成初始 `search`，或在证据不足、候选冲突、长文档缺口时决定下一步补证据策略。
3. LLM Candidate Judge 只裁判程序预筛后的 top-K Candidate Package，默认 top-K 为 12，可配置范围为 8-15。
4. 如果 LLM Judge 后 Working Set 已经有足够 `keep` evidence，系统自动生成 `open` 工具调用，不再请求 Controller 决定是否 open。
5. 如果核心 evidence 已打开，Anchor coverage 达标，且没有 topic conflict / forbidden hit，系统自动 `stop`，不再请求 Controller 输出 stop 理由。
6. 第二轮 LLM Controller 只在以下条件触发：`keep_evidence_count == 0`、`anchor_coverage < 阈值`、核心 relation intent 未覆盖、候选冲突、打开 evidence 后仍缺少答案关键对象。
7. 第二轮 LLM Judge 只在新增候选或新打开证据改变 Candidate Package 时触发；同一批候选不得重复 judge。
8. 复杂 query、低置信 query 和质量门槛不达标的 query 可以突破默认预算，但必须在 trace 中记录继续调用 LLM 的原因。

继续进入第二轮的质量门槛：

| 条件 | 处理 |
| --- | --- |
| 第一轮没有 `keep` evidence | 允许 LLM Controller 决定补搜或 find。 |
| `keep` 候选只是背景或实体页 | 允许 open / find / search 补直接证据。 |
| `anchor_coverage < anchor_coverage_stop_threshold` | 不允许自动 stop。 |
| 核心 relation intent 未覆盖 | 不允许自动 stop，允许补搜。 |
| 候选冲突或证据冲突 | 允许 open 关键 evidence 或 find 对比信息。 |
| open 后正文不足或缺少核心答案对象 | 允许第二轮 Controller。 |
| LLM Judge 低置信或大量 `weak_keep` | 允许补第二批候选或重新 search。 |
| 出现 topic conflict / forbidden hit / Context Purity 不足 | 不允许自动 stop，进入补证据或降级路径。 |

建议默认阈值：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `judge_top_k` | 12 | 进入 LLM Candidate Judge 的候选数量。 |
| `judge_top_k_max` | 15 | 普通查询上限。 |
| `min_keep_evidence_to_auto_open` | 1 | 有至少 1 条高置信 evidence 即可自动 open。 |
| `min_keep_candidates_to_auto_stop` | 2 | 有至少 2 个 keep 候选且 evidence 已 open 时可自动 stop。 |
| `anchor_coverage_stop_threshold` | 0.8 | 自动 stop 的 Anchor 覆盖阈值。 |
| `max_llm_calls_normal_query` | 2 | 普通 query 的默认 LLM 调用预算。 |

top-K 预筛不能简单取向量分数前 12。预筛器需要先做候选归并和多样性保留：

1. 同一 evidence、node、edge、wiki 多通道命中合并为一个 Candidate Package。
2. 每类通道保留必要名额，避免 entity、graph、evidence、wiki、semantic 互相挤掉。
3. 有 evidence 支撑、关系意图匹配、路径清晰的候选优先。
4. 覆盖不同实体、事件、行业、资产或关系意图的候选优先。
5. hub 节点、mention-only、无证据支撑或明显背景候选降权。
6. 如果第一批 top-K 的 `keep` 很少或 Anchor 覆盖不足，允许补第二批候选进入 LLM Judge。

自动 `open` 的目标选择顺序：

1. LLM Judge 判定为 `keep` 且带有 evidence_refs 的 candidate。
2. 能覆盖核心 relation intent 的 evidence。
3. 与核心实体、事件或 source hard constraint 直接关联的 evidence。
4. 已经 open 过的 evidence 不重复打开。

自动 `stop` 的判断顺序：

1. Working Set 中存在可回答 query 的 keep evidence。
2. 已 open 核心 evidence 或 evidence 本身已经足够完整。
3. Query Anchor 的核心实体、主题或关系意图已覆盖。
4. 新增候选没有显著提升，或继续 search 的 expected gain 低。
5. 没有 forbidden node/evidence/topic 或 topic conflict。

这些自动状态推进必须写入 trace，字段包括：

- `auto_action`: `open` / `stop`
- `auto_action_reason`
- `llm_calls_used`
- `llm_call_budget`
- `judge_top_k`
- `auto_open_evidence_refs`
- `auto_stop_metrics`

### 10.4 Retrieval Working Set 更新规则

每轮工具执行后必须更新 Working Set：

- `keep` 且 `can_expand_graph=true` 的候选进入主证据区。
- `keep` 但 `can_expand_graph=false` 的候选进入可引用证据区，但不能继续扩图。
- `weak_keep` 进入低置信背景区，不能触发 search/open/find 的目标扩展。
- `drop` 进入丢弃区，并记录原因用于后续避免重复搜索。
- `opened_windows` 记录打开过的 parent evidence、sibling chunk、Wiki 页面和图路径。
- `missing_anchor_items` 根据 Candidate Judge 的 anchor coverage 更新。
- 如果本轮没有新增 keep evidence，`no_gain_rounds += 1`。

Working Set 只存在于单次查询生命周期，不写入主图，不作为后续查询事实来源。

### 10.5 工具集合

第一版只开放知识检索相关工具：

- `search`：面向知识库做多查询宽召回，可组合实体、图、语义、Wiki 和证据通道。
- `find`：在指定 evidence、Wiki、文档或候选集合内做精确定位。
- `open`：按窗口打开父 evidence、相邻 chunk、Wiki 页面、图谱路径或完整证据内容。
- `summarize`：当上下文接近预算上限时压缩历史检索过程，但保留引用证据和关键判断。

工具约束：

- `search` 输出必须进入 Candidate Package Builder。
- `find` 只能在 Working Set 已知候选、指定 evidence、Wiki 或文档范围内定位，不能变成全库关键词过滤。
- `open` 只能打开已知候选关联的 parent evidence、sibling chunk、Wiki 页面或图路径。
- `summarize` 只能压缩已验证 trace 和 evidence，不得生成新事实。
- 不允许 Agentic Retrieval 直接修改主图、写入规则、调用外部业务动作或绕过 Candidate Judge。

### 10.6 工具预算

默认预算：

- 普通复杂查询：最多 6 次工具调用。
- 高复杂度查询：最多 10 次工具调用。
- 单轮工具失败允许降级，但不允许无限 retry。

停止条件：

- evidence 已充分覆盖 Query Anchor。
- 达到工具调用上限。
- 达到上下文预算上限。
- 连续两轮没有新增有效 evidence。
- Candidate Judge 判断新增候选均为 drop。
- 工具失败或超时，回退到 deterministic_plan 可用上下文。
- Retrieval Controller 输出 `stop` 且置信度达标。

### 10.7 Trace 要求

每轮工具调用必须记录：

- tool name。
- tool input。
- controller decision reason。
- raw candidate count。
- Candidate Package 数量。
- keep / weak_keep / drop 数量。
- 新增 evidence_refs。
- Working Set 的缺口变化。
- 是否触发 graph expansion。
- stop reason。

Trace 是回放和调试的必要输出，不能只保留最终答案。

LLM trace 需要额外满足：

- 使用纯文本摘要格式，便于人工和 AI 快速阅读。
- parsed payload 成功时，不重复记录完整 raw JSON；只有解析失败时保留 raw response。
- 每次 LLM 调用记录 stage、model、duration_ms、usage、候选数量、keep/weak_keep/drop 统计。
- Query Context 组装阶段不能覆盖 Agentic 阶段真实 LLM judgement；如果需要重算 metrics，只更新 metrics，不重写 `candidate_judgements`。
- 性能 profile 默认只输出超过阈值的慢步骤；完整 START/event 日志只在 verbose 模式打开，避免回放日志不可读。

## 13. 错误处理与降级

1. Hard Constraint Extractor 失败：返回空 hard constraints，继续 LLM Anchor Parser，并记录 warning。
2. LLM Anchor Parser 失败：使用 Hard Constraint 生成低置信 Anchor，并记录 `anchor_parser_degraded`。
3. Anchor Validator 发现硬约束冲突：触发一次 retry；仍冲突则保留 Hard Constraint，丢弃冲突字段。
4. Fast Router 无法判断：进入 LLM Router。
5. LLM Router 失败：先走 deterministic_plan，并记录 `router_degraded`。
6. deterministic_plan 低质量：Post-check Router 自动升级 agentic_arag。
7. Candidate Package Builder 失败：该候选不能进入主 Query Context，只记录 warning 和原始 hit。
8. Candidate Judge 失败：使用保守 fallback，不允许直接放开所有候选。
9. LLM Judge 超时：只保留低风险精确命中和一跳 evidence 支撑候选，其余降级为 `weak_keep` 或 `drop`。
10. Retrieval Controller 输出非法工具或非法目标：丢弃该决策，触发一次 retry；仍失败则停止 agentic loop 并记录 `controller_invalid_decision`。
11. Retrieval Controller 试图引用 Working Set 外候选：拒绝该工具调用，要求重新决策。
12. Agentic 工具失败：记录工具失败并尝试其他工具；达到失败阈值后回退 deterministic_plan。
13. Chunk window 缺失：回读 parent evidence，记录 `chunk_window_partial`。
14. 某个检索通道失败：保留其他通道结果，并在 Query Context warnings 中记录通道失败。
15. LLM 调用预算耗尽：禁止继续请求 Controller/Judge，使用 Working Set 中已验证 keep evidence 自动 open/stop；如果没有可用 evidence，则返回低置信上下文并记录 `llm_budget_exhausted`。
16. Judge 候选数量超过 top-K：先按通道优先级、图路径支撑、evidence 支撑、原始召回分数和去重结果预筛；超出候选只保留摘要计数，不进入 LLM prompt。
17. LLM parsed payload 成功：trace 不记录完整 raw JSON；只有解析失败时才保留 raw response 便于排障。

## 15. 验收标准

1. Query Context 返回 Query Anchor、Query Routing Decision、candidate judgements、channels_used、warnings。
2. Hard Constraint Extractor 只提供硬标识，不承担 query 语义理解，不做关键词过滤、模糊匹配、黑名单或白名单。
3. LLM Anchor Parser 是 Anchor 语义主力，但输出必须通过 Validator。
4. Fast Router、LLM Router、Post-check Router 能形成完整三段式路由。
5. 明确复杂 query 能直接进入 agentic_arag。
6. deterministic_plan 低质量时能自动升级 agentic_arag，并记录升级原因。
7. Candidate Package 是 LLM Candidate Judge 的输入单元，不能裁判孤立字符串或单个 chunk。
8. 自然语言 query 的候选相关性必须经过 LLM Candidate Judge 或保守 fallback，不能只由字符串 overlap 决定。
9. 军演 query 不应把宁德时代/固态电池作为 top context。
10. 无关 semantic hit 不可触发 graph expansion。
11. `weak_keep` 不可触发 graph expansion、evidence 回读、Wiki 扩展或 sibling chunk 扩展。
12. 命中 chunk 后能回读 parent evidence；具备 sibling window 扩展能力。
13. Agentic Retrieval 有 Retrieval Controller 和 Working Set；Controller 只能选择 `search/find/open/summarize/stop`，不能直接写上下文。
14. Agentic Retrieval 的每一步都有 trace、引用证据、Working Set 变化和停止原因。
15. 回放能识别“目标命中但上下文污染”的失败。
16. LLM Anchor/Router/Judge/Controller 失败时有明确降级路径，不会直接放开所有候选。
17. HTTP API、CLI 和 Python 服务层返回的 Query Context 结构一致。
18. 普通 query 默认不超过 1 次 LLM Controller + 1 次 LLM Candidate Judge；证据充分后的 open 和 stop 由程序自动完成。
19. LLM Candidate Judge 默认只裁判 top 12 个 Candidate Package，最多不超过 top 15，禁止把 30 个以上宽召回候选直接塞给模型。
20. Query Context trace 能区分 LLM judgement、deterministic fallback 和自动 open/stop；后续组装 Query Context 时不能覆盖真实 LLM judge trace。

## 16. 已知偏差与待优化

如果实现中出现以下情况，必须记录到 `9. 待优化.md`：

- LLM Anchor Parser 暂时未接入，只能用 Hard Constraint 低置信降级。
- Query Routing 只有 Fast Router，暂未接入 LLM Router 或 Post-check Router。
- Candidate Judge 只有确定性规则，或 LLM judge 已接入但没有 top-K 预筛和调用预算。
- 检索 runtime 仍使用字符串 overlap、关键词、黑白名单或硬编码前缀作为最终候选判断。
- 尚未构建 Candidate Package，只在孤立 hit/chunk 上做裁判。
- graph expansion 仍然从未裁判候选扩展。
- agentic_arag 仍然只是一次性检索，没有 search/find/open/summarize 工具循环。
- agentic_arag 没有 Retrieval Controller 和 Working Set，只是固定流程。
- Agentic 工具结果没有重新进入 Candidate Package Builder 和 Candidate Judge。
- 普通 query 出现多轮无必要 LLM controller/judge，导致单 case 耗时超过可接受阈值。
- LLM judge 直接裁判全量宽召回候选，没有 top-K 预筛和候选包压缩。
- Query Context 组装阶段覆盖了 Agentic 阶段真实 LLM judgement，只留下 deterministic fallback trace。
- chunk 仍然只有 evidence 单 chunk，没有 parent/sibling/window。
- demo 只验证命中率，不验证上下文污染。
- 为了短期效果硬编码金融 source id、表名或 demo 前缀过滤噪声。
