# Agentic 检索候选排序优化技术方案

## 1. 模块目标

本文是《7. Agentic 检索候选排序优化方案》的技术实施方案，目标是把当前 `recall_pool -> judge topK` 的规则预筛改造成可评估、可回放、可替换的排序级联。

当前要解决的核心问题不是日志不清楚，而是质量闸口不可靠：宽召回拿到 30 个候选后，系统只把 topK 候选送给 LLM judge。如果 topK 是由未评估的规则排序选出来的，好候选可能在第 9 到第 30 位被截断，后续 judge、open、expand、stop 都无法补救。

实施目标：

1. 先在写入和索引刷新阶段生成独立的 `Retrieval Document`，为 keyword/BM25、semantic、rerank 和日志解释提供稳定输入。
2. 建设系统级 `Retrieval Quality Evaluation`，能评估召回、预筛、judge、open/expand、stop 每个阶段的质量。
3. 补齐独立 `Keyword Retrieval`，不能继续把关键词召回混在 `entity_resolve` 或 `wiki_search` 里。
4. 用 `Rank Fusion -> Feature Rerank -> Coverage Selector -> Judge Preselect` 替代“规则分数直接 topK”。
5. 让 `retrieval_controller.search_plan` 进入召回、排序、coverage 和 stop verifier，而不是只写入日志。
6. 增加 `Stop Verifier`，防止枚举型、方向型、证据型条件误停。

本文不把神经 reranker 作为第一版必选依赖。神经 reranker 指 cross-encoder、ColBERT/late interaction、LLM batch pre-judge 或 learning-to-rank 这类对 `query + candidate` 成对打相关性分的模型化精排器。第一版先实现写入期检索增强、Keyword/BM25、RRF、Feature Rerank、Coverage Selector、Stop Verifier 和评估闭环；后续只有在固定评估集证明仍存在明显 `feature_miss` 或 `coverage_miss` 时，才接入模型化 reranker 做策略对比。

## 2. 模块边界

本模块覆盖：

- Retrieval Document 领域对象和生成入口。
- keyword/BM25 召回通道。
- Recall Pool 快照。
- Candidate Package 标准化补强。
- RRF / 加权 RRF。
- Feature Rerank。
- Coverage / Diversity Selector。
- Judge Preselect 和动态 topK。
- Stop Verifier。
- Retrieval Quality Evaluation、人工标注、策略回放和指标计算。
- 排序相关 trace event 和人类可读日志。

本模块不覆盖：

- Source Record 投影的事实口径；详见《1. 数据源投影与 Source Record 技术方案》。
- Node / Edge / Evidence 的事实写入规则；详见《2. 知识编译与写入技术方案》。
- 领域本体和 Adapter 的主事实模型；详见《3. 知识建模与领域适配技术方案》。
- LLM Candidate Judge 的语义裁判 prompt 全量重写；本文只规定 judge 前候选如何选、judge 后结果如何归一化。
- 最终回答生成。Query Context 只消费通过 judge/open/stop verifier 校验后的内容。

关键边界：

| 对象 | 所属层 | 是否事实源 | 说明 |
| --- | --- | --- | --- |
| Node / Edge / Evidence | 事实层 | 是 | 主事实存储，必须稳定、可追溯。 |
| Retrieval Document | 检索层 | 否 | 从事实和 evidence 派生，可重建、可版本化、可 A/B。 |
| Candidate Package | 检索视图 | 否 | 给排序、judge、日志使用的候选表达。 |
| Rank Feature | 排序特征 | 否 | 可调权重，不写回事实层。 |
| LLM Judgement | 检索决策 | 否 | 只影响当前 Query Context，不新增事实。 |
| Stop Verification | 检索决策 | 否 | 判断是否满足当前问题，不生成事实。 |

RetrievalDocument

  source_fact_id: str
  evidence_refs: list[str]

  time_tags: list[str]
  source_type_tags: list[str]

  confidence: float
  generated_by: rule | llm | hybrid

约束：

- `RetrievalDocument` 只引用事实对象，不反向成为事实源。

- 同一事实可以生成多个版本的 Retrieval Document，用于 A/B 回放。
- 删除或 supersede evidence 后，相关 Retrieval Document 必须失效或重建。

## 4. 数据流

### 4.1 写入期到检索层

```text
Source Record
 -> Compile / Normalize
 -> Fact Store 写入 Node / Edge / Evidence
 -> Changed Fact Set
 -> Retrieval Document Builder
 -> kg_retrieval_documents
 -> keyword/BM25 index
 -> semantic/vector index
```

实现要求：

1. `knowledge_service._refresh_incremental_indexes` 在刷新 graph adjacency、evidence chunks、wiki pages 后，增加 Retrieval Document 生成和 upsert。
2. Retrieval Document Builder 从 Changed Fact Set 读取变更的 node、edge、evidence，并补齐可读关系、证据摘要、facets。
3. Retrieval Document 生成失败不能回滚事实写入，但必须记录 warning 和待重建任务。
4. 所有检索增强字段必须能追溯到 `source_fact_id` 和 `evidence_refs`。

这是本方案第一实施优先级。原因是排序和评估都依赖入库后的可检索形态：没有 `search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary`、`event_type`、`relation_intents`、`impact_direction`、`asset_classes` 和 `time_tags`，keyword/BM25、semantic、RRF、Feature Rerank 和 Coverage Selector 都只能在贫弱候选上工作。

Retrieval Document 必须显式表达关系，但不能替代 graph：

```text
title: 宁德时代海外产能扩张带动储能供应链订单
readable_relations:
  - 宁德时代海外产能扩张带动储能供应链订单 affects 宁德时代
  - 宁德时代海外产能扩张带动储能供应链订单 affects 新能源车产业链
evidence_summary:
  宁德时代推进欧洲和东南亚海外产能扩张，储能电芯、快充电池和新能源车产业链订单预期改善。
```

这样 keyword/BM25 能命中关系表达，graph_search 继续负责验证结构化边和 evidence 绑定，semantic/vector 负责语义扩展，Feature Rerank 负责融合这些信号。

### 4.2 查询期排序级联

```text
query
 -> Query Anchor
 -> Retrieval Controller Decision(search_plan, query_rewrites)
 -> keyword / entity / graph / wiki / semantic 多通道召回
 -> recall_pool snapshot
 -> Candidate Package Builder
 -> Rank Fusion
 -> Feature Rerank
 -> Coverage Selector
 -> Judge Preselect
 -> LLM Candidate Judge
 -> judgement normalization
 -> auto open / auto expand
 -> Stop Verifier
 -> stop 或 second batch judge / controller next action
```

执行规则：

1. `query_rewrites` 必须全部执行，除非配置明确限制。
2. 每条 query rewrite 默认进入 keyword、entity、graph、wiki、semantic 通道；通道超时或禁用要记录原因。
3. recall pool 默认保留 30 个候选，但质量快照必须保存更多原始命中计数和截断原因。
4. Judge Preselect 的 topK 不再等同于 recall pool 数量；日志必须说明“召回 30，送 judge 8/12/15”的选择过程。
5. LLM judge 前只使用 `candidate_key`，系统内部维护 `candidate_key -> candidate_id`。

### 4.3 Stop Verifier 流程

```text
judge results
 -> answer/support/background/drop 归一化
 -> edge answer 降级为 support
 -> evidence answer 映射父事件/政策/资产/主题
 -> coverage requirement 解析
 -> 数量 / 枚举 / 方向 / 时间 / evidence type / anchor 覆盖校验
 -> satisfied 或 missing requirements
```

Verifier 未满足时：

- 不允许输出 `auto_stop_context_sufficient`。
- 记录 `auto_stop_skipped`。
- 如果剩余 ranked candidates 能补缺口，优先 second batch judge。
- 如果候选池本身缺失，交给 controller 继续 search/find/open。
- 如果预算耗尽，最终 Query Context 带 `budget_stop_condition_unmet` warning。

## 5. 排序实现细节

### 5.1 Keyword Retrieval

第一版实现建议：

1. 第一版固定基于 PostgreSQL `pg_trgm` 词项/短语匹配实现独立 keyword 通道。
2. 检索对象优先是 `kg_retrieval_documents.search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary`。
3. 命中结果必须返回 `matched_terms`、`matched_fields`、`source_channel=keyword`、局部 rank。
4. 当前 `HybridRetrievalRuntime.keyword_search()` 只是 `entity_resolve()` 兼容 wrapper，正式实现后必须改为真正 keyword 通道。
5. `RetrievalToolRegistry.available_tools` 不一定暴露独立 `keyword_search` 给 LLM；可以作为 `search` 工具内部通道执行，避免工具面过宽。

关键约束：

- Keyword Retrieval 是 PostgreSQL lexical 通道，不是普通 dense vector search 的别名。
- Milvus 在第一版只承担 semantic/vector 通道，不承载 keyword 通道。
- 普通 dense vector search 不能替代 keyword 通道；它不保证稳定命中股票代码、source_id、公告关键词和精确事件短语，也不擅长解释命中了哪个字段。
- Keyword Retrieval 不负责完整关系理解。关系理解由 `readable_relations` 文本命中、`graph_search` 结构化关系验证、semantic/vector 语义扩展和 Feature Rerank 融合共同完成。

验收重点：

- `300750`、`宁德时代`、`海外产能扩张`、`资金净流入`、`监管处罚`、`重大合同` 这类词能被 keyword 通道稳定命中。
- keyword 命中进入 recall pool 和 RRF，不只是日志展示。

### 5.2 Rank Fusion

实现函数放在 `retrieval_ranker.py`：

```text
rank_fusion(
  candidates_by_query_channel: dict[query, dict[channel, list[RecallCandidate]]],
  channel_weights: dict[str, float],
  rrf_k: int = 60,
) -> list[RankedCandidate]
```

规则：

- 每个 query/channel 内部先按该通道局部排序。
- `fusion_score = sum(channel_weight / (rrf_k + rank_in_channel))`。
- 同一候选被多 query、多 channel 命中时合并加分。
- 原始 score 只作为同通道 tie-break，不跨通道直接比较。
- 输出必须保存分数组成，供日志和评估使用。

### 5.3 Feature Rerank

第一版使用线性加权，权重配置放在代码配置或 adapter 配置中：

```text
feature_score =
  anchor_score
  + answer_type_score
  + evidence_score
  + relation_score
  + plan_score
  + time_score
  + source_score
  - negative_penalty
  - duplication_penalty
```

特征来源：

| 特征 | 来源 |
| --- | --- |
| `anchor_score` | Query Anchor、hard constraints、candidate title/aliases。 |
| `answer_type_score` | candidate type、Retrieval Document `answer_candidate_type`。 |
| `evidence_score` | evidence_refs、supporting_evidence_excerpt。 |
| `relation_score` | relation_intents、readable_relations、graph path。 |
| `plan_score` | search_plan answer_targets / expected_evidence。 |
| `time_score` | time_tags、published_at、query time hints。 |
| `source_score` | source_type_tags、source reliability。 |
| `negative_penalty` | negative_boundaries、topic drift。 |
| `duplication_penalty` | 相同 evidence、相同父事件、相同 wiki 派生页。 |

硬过滤只用于确定性错误：

- 证券代码冲突。
- 明确时间范围不满足。
- 证据已 inactive。
- source/evidence hard constraint 明确不匹配。

其他情况只降权，不直接丢弃。

### 5.4 Coverage Selector

`coverage_mmr_select()` 输入 reranked candidates，输出 judge topK。

选择目标：

- 保留核心 anchor 候选。
- 优先保留 answer 类型候选。
- 补齐 `answer_targets`。
- 补齐 `expected_evidence`。
- 覆盖 `relation_intents`。
- 限制 wiki/background 占比。
- edge 默认 support，不挤占 answer 配额。
- 同 evidence、同父事实、同 wiki 派生页降权。

建议默认配额：

| 配额 | 默认 |
| --- | --- |
| answer quota | `ceil(topK * 0.5)` |
| support quota | 至少 1 到 2 个 |
| background quota | 不超过 `floor(topK * 0.2)` |
| evidence quota | 至少 1 个直接 evidence 或父 evidence 映射候选 |
| edge quota | 默认 support 配额内，不作为 answer quota |

### 5.5 动态 topK 和二批 judge

topK 选择逻辑：

| 问题类型 | 第一批 topK |
| --- | --- |
| 单实体、单关系、明确目标 | 8 |
| “哪些/影响哪些/覆盖哪些” | 12 |
| 枚举覆盖、多资产、多行业、多方向 | 15 |

第二批 judge 触发条件：

- Stop Verifier 缺 `answer_count`。
- 缺枚举覆盖项。
- 缺 expected evidence 类型。
- 第一批 wasted slots 过高。
- `remaining_high_potential` 中有能补缺口的候选。
- LLM 预算仍允许。

第二批候选从 `remaining_high_potential` 中按缺口选择，不是简单取第 9 到第 16。

### 5.6 Judgement 归一化

LLM judge 返回后统一归一化：

- `edge + answer` 降级为 `support`，记录 `role_normalized=edge_answer_to_support`。
- `wiki + answer` 必须能映射原始 evidence 或事实；不能映射则降级为 `background`。
- `evidence + answer` 优先映射到父事件、政策、资产、行业或主题；记录 `answer_normalization`。
- `decision=None` 不允许进入最终 trace；缺失时按 role 推导或标为 invalid fallback。
- `expand=True` 只对 answer/support 生效，background/drop 不扩展。

## 6. Retrieval Quality Evaluation 实施

### 6.1 快照采集

每次采样查询保存：

| 快照 | 关键字段 |
| --- | --- |
| query snapshot | query、anchor、controller decision、search_plan、constraints。 |
| recall snapshot | query_rewrite、channel、candidate id、rank、raw score、matched terms、耗时。 |
| package snapshot | candidate package 文本、meaning、evidence、relations、Retrieval Document 覆盖情况。 |
| ranking snapshot | fusion score、feature score、coverage bonus、redundancy penalty、topK 选择原因。 |
| judge snapshot | judge 输入、输出、role、decision、score、expand、归一化结果。 |
| context snapshot | opened evidence、final hits、stop verifier 结果、warnings。 |

- `avg_judge_tokens`

### 6.4 策略回放

同一批 trace 至少支持对比：

- `baseline_rule_priority`
- `keyword_added_baseline`
- `rrf_only`
- `rrf_feature_rerank`
- `rrf_feature_coverage`
- `oracle_topk`

策略回放必须使用同一份 recall snapshot，避免把召回变化误判成排序变化。

### 6.5 失败归因

失败归因枚举：

| failure_stage | 含义 |
| --- | --- |
| `ingestion_enrichment_miss` | Retrieval Document 缺必要关键词、别名、事件类型、关系意图。 |
| `recall_miss` | recall pool 里没有好候选。 |
| `keyword_miss` | keyword/BM25 未命中精确词或事件短语。 |
| `package_miss` | 候选包丢失语义、证据或关系。 |
| `fusion_miss` | RRF 没把多通道好候选提上来。 |
| `feature_miss` | 业务特征或权重不合理。 |
| `coverage_miss` | topK 没覆盖子目标或证据类型。 |
| `judge_miss` | LLM judge 误判。 |
| `stop_miss` | Stop Verifier 误停或误判缺口。 |

## 7. 错误处理与降级策略

1. Retrieval Document 生成失败：事实写入成功，检索增强标记为 stale，记录 `retrieval_document_build_failed`。
2. keyword index 不可用：继续 entity/graph/wiki/semantic，但质量快照标记 `keyword_channel_unavailable`，该 run 不可作为 keyword 策略验收。
3. semantic/Milvus 网络异常：记录 WARNING 和 DEBUG profile，业务链路允许降级到 keyword/entity/graph/wiki。
4. Ranker 配置缺失：使用 `baseline_rule_priority`，并记录 `ranker_fallback_baseline`。
5. LLM judge 失败：保守 fallback，只保留精确 anchor、有 evidence、有一跳关系支撑的候选。
6. Stop Verifier 解析不了 stop condition：退化为最小规则，但不能自动声称枚举覆盖已满足。
7. 二批 judge 预算不足：记录 `second_batch_judge_skipped_budget` 和未满足条件。

## 9. 验收标准

1. 系统能保存 recall pool 30 个候选的完整快照，并能解释为什么只送 8/12/15 个给 judge。
2. keyword/BM25 是独立召回通道，结果进入 recall pool 和 RRF。
3. Retrieval Document 包含 `search_text`、`key_phrases`、`aliases`、`event_type`、`relation_intents`、`impact_direction`、`asset_classes`、`time_tags`、`source_type_tags`、`readable_relations`、`evidence_summary`、`answer_candidate_type`。
4. Rank Fusion 不直接跨通道比较原始 score。
5. Feature Rerank 输出分数组成和 rank reasons。
6. Coverage Selector 能控制 wiki/background/edge 占坑，并覆盖 search_plan 子目标。
7. LLM judge 请求中使用 `candidate_key`，不要求模型输出数据库 id。
8. `edge` 默认不能作为 distinct answer；如果 LLM 判为 answer，系统归一化为 support。
9. evidence answer 能映射父事实后再计数，避免重复或低估。
10. Stop Verifier 支持数量、枚举、方向、时间、证据类型和 anchor 覆盖；未满足时不能自动 stop。
11. `preselect_recall@8/12/15`、`answer_recall@8/12/15`、`wasted_slots@8/12/15`、`coverage@8/12/15` 能在评估报告中输出。
12. 新排序策略必须用固定 bad case 证明优于 `baseline_rule_priority`，不能只靠单次日志判断。

## 10. 分阶段实施计划

### 10.1 阶段一：Retrieval Document 和写入期检索增强

交付：

- Retrieval Document Builder。
- repository upsert/list/delete。
- incremental index refresh 接入。
- `search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary`、`event_type`、`relation_intents`、`impact_direction`、`asset_classes`、`time_tags`、`source_type_tags`、`answer_candidate_type`。
- 字段覆盖率日志和重建版本记录。

验收：

- 每条核心 evidence、event、edge 都能生成可读检索文本。
- 检索增强字段不写入 Node / Edge / Evidence 主事实。
- `readable_relations` 能把结构化边转成可检索文本，并保留原始 edge/evidence refs。
- Retrieval Document 生成失败不回滚事实写入，但有 stale/rebuild 记录。

### 10.2 阶段二：质量评估和快照

交付：

- `RetrievalTraceSnapshot` 数据结构。
- recall/package/ranking/judge/context 快照保存。
- 人工 label 表结构和 repository 写入接口。
- baseline 规则策略的 `preselect_recall@k`、`wasted_slots@k`。

验收：

- 能回答“30 个候选里有哪些好候选没进 judge”。
- 能区分 ingestion enrichment miss、recall miss、keyword miss、预筛 miss、judge miss、stop miss。

### 10.3 阶段三：Keyword Retrieval

交付：

- 独立 keyword/BM25 通道。
- matched_terms / matched_fields。
- search 工具内部多通道执行。

验收：

- 股票代码、公司简称、事件短语、公告关键词稳定命中。
- keyword 结果进入 recall pool 和 RRF。

### 10.4 阶段四：RRF 和 Feature Rerank

交付：

- RRF / weighted RRF。
- Feature Rerank。
- ranking trace。
- 权重配置。

验收：

- RRF 分数、feature 分数、最终分数可解释。
- 不再用通道原始 score 直接混排。

### 10.5 阶段五：Coverage Selector 和动态 topK

交付：

- coverage target 从 search_plan 解析。
- MMR/coverage topK。
- dynamic topK。
- remaining high potential candidates。

验收：

- topK 不被 wiki/edge/重复 evidence 占满。
- “哪些/影响哪些”默认能送 12 个或 15 个候选。

### 10.6 阶段六：Stop Verifier 和二批 judge

交付：

- Stop Verification Result。
- answer normalization。
- second batch judge。
- auto_stop_skipped 日志。

验收：

- 枚举覆盖不足时不能自动 stop。
- 缺口能传回 controller 或 second batch judge。

### 10.7 阶段七：更强 reranker

前置条件：

- 已有稳定 label 集。
- baseline、RRF、feature、coverage 指标长期可比。
- Retrieval Document 和 Keyword/BM25 已稳定，能证明候选池不是贫弱输入。
- LLM token 和延迟成本可控。

可选实现：

- LLM batch pre-judge。
- 中文金融 reranker、cross-encoder 或 ColBERT/late interaction。
- learning-to-rank。

更强 reranker 必须用同一批评估集证明它相对 `rrf_feature_coverage` 有净收益，并评估延迟、token 或推理成本。不能用它替代写入期增强、Keyword/BM25、graph_search 或 Stop Verifier。

## 11. 已知偏差与待优化

当前实现和本方案仍有差距，实施时必须记录到 `9. 待优化.md`：

1. `HybridRetrievalRuntime.keyword_search()` 当前只是 `entity_resolve()` 兼容 wrapper，不是真正 keyword/BM25。
2. 现有部分测试仍断言 `RetrievalToolRegistry` 不暴露 standalone keyword tool；这可以保留，但 search 工具内部必须有 keyword channel。
3. 当前 `retrieval_eval.py` 更偏 bad case 结果检查，不足以评估 recall pool、preselect、ranking 和 stop verifier。
4. 当前 candidate package 已有人类可读增强，但还没有完整 rank feature 和 selection reason。
5. 当前 agentic 自动停止已有基础逻辑，但 stop condition 的枚举、方向、证据类型覆盖仍需 Stop Verifier 统一治理。
6. 当前写入期还未形成独立 Retrieval Document 表和版本化评估闭环。
