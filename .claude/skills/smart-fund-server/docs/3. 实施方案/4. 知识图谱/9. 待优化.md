## 当前记录

## DeepSeek 前缀缓存友好的批量与会话化 LLM 调用尚未系统化（2026-05-17 记录）

**问题：** DeepSeek 的上下文硬盘缓存是服务端前缀缓存，不是业务语义缓存。只有请求消息前缀完全一致或高度稳定时，才能命中 `prompt_cache_hit_tokens`。当前系统已把 JSON Schema、固定规则和稳定 contract 尽量前置，减少了无谓 miss；但更高收益的调用形态尚未系统化：同类问题仍可能分散成多次独立请求，controller/judge/extraction 的批量调度、稳定 message history、以及“同一轮对话中连续询问多个相似任务”的机制还没有设计完成。

**最佳方案：** LLM 调用层应提供缓存友好的任务编排能力：

- 对同类任务采用稳定 system prompt + 稳定 schema/contract + 变量 payload 后置的消息结构，禁止把当前时间、随机 ID、trace metadata、候选顺序抖动等内容放进前缀。
- 对多个同类候选判断、多个新闻抽取、多个 query 评估，优先使用 batch JSON 输入，在一次请求里处理 N 个 item，摊薄固定 prompt 成本，并最大化 DeepSeek 前缀缓存收益。
- 对确实需要多轮的场景，维护不可变历史消息前缀，只在尾部追加新 user/tool 消息；不得重写、重排或重新序列化历史内容。
- 在 LLM usage 和全量日志中持续记录 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、batch size、per-item 成本和延迟，用真实指标判断是否值得扩大 batch 或会话化。

**当前方案：** 已完成第一层工程约束：DeepSeek JSON 模式会把固定 JSON 指令和 Schema 放在 system message；检索 controller/judge 的 prompt 已调整为固定规则、工具 contract、decision schema 前置，query、working set、candidate list 等变量内容后置；日志会输出 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。但当前仍主要是单请求处理单个 controller decision、单个 candidate judge 批次、单条新闻抽取；没有统一的 batch 调度器，也没有跨请求的稳定 conversation/session 编排。

**影响范围：** 功能正确性不受直接影响，但成本和延迟仍可能偏高。尤其是 100 条真实新闻写入、多个 replay case、二批 judge 或未来 LLM batch pre-judge 时，如果每次都重复发送固定 schema/规则，会浪费 token，并降低 DeepSeek 服务端缓存命中率。相同任务的 prompt 只要前缀因为字段顺序、时间、metadata 或候选排序轻微变化，就会错失缓存收益。

**整改条件：** 先在真实回放日志中收集各任务的 `prompt_cache_hit_tokens / miss_tokens` 基线；再设计 `LLMBatchTaskRunner` 或等价批量调用接口，优先覆盖 `financial_news_extraction`、`kg_candidate_judge`、`quality_review` 这类同构任务；同时为 multi-turn 场景定义不可变 message history 规范和测试，确保历史消息字节级稳定。上线前用同一批真实库回放比较 batch/会话化前后的耗时、token、缓存命中率和输出质量。

**优先级：** P2。

## Keyword Retrieval 已有 lexical v1，但数据库侧字段加权排序仍待完成（2026-05-17 记录）

**问题：** 当前写入期已经生成 `kg_retrieval_documents` 检索增强字段，数据库也已经为 `title`、`search_text`、`evidence_summary`、`key_phrases`、`aliases`、`readable_relations` 建立 `pg_trgm` GIN 索引；`search_retrieval_documents()` 也不再只是 `entity_resolve()` 兼容 wrapper，而是能独立消费 Retrieval Document。但是当前实现仍主要通过多字段 `ILIKE` 召回候选，再在 Python 侧用 `retrieval_document_query_score()` 做排序。这是可用的 keyword/lexical v1，不是最终的数据库侧可解释字段加权排序。

**最佳方案：** Keyword Retrieval 的正式版本应在数据库侧完成可解释 lexical rank：`title`、`aliases`、`key_phrases` 权重最高，`readable_relations`、`evidence_summary` 次之，`search_text` 作为兜底；同时叠加 `answer_candidate_type`、`source_fact_type`、`relation_intents`、时间标签和实体锚点的结构化 boost。检索结果必须返回 `matched_terms`、`matched_fields`、`source_channel=keyword`、`local_rank` 和 score components，供 candidate package、日志和质量评估解释。中文场景下不直接把 PostgreSQL `tsvector/ts_rank` 当作默认答案；只有在中文分词、索引和评估集验证优于当前 trigram lexical rank 后，才替换或并入正式排序。

**当前方案：** 第一版先落地 Retrieval Document 写入字段、`pg_trgm` 索引、多字段 lexical 召回和 Python 侧字段权重排序。为了避免 `document_id` 顺序过早截断候选，当前预取规模已扩大到 `max(limit * 20, 200)`，再由 Python 侧排序。这能支持当前小规模回放和人工验证，但排序不在 SQL 侧完成，局部 rank 和 score 组件也还没有完整落库或进入标准日志。

**影响范围：** 数据量较小时可用，但随着 `kg_retrieval_documents` 增长，数据库召回候选池和 Python 排序之间仍可能出现截断误差；排序解释也不够标准化，难以长期评估“30 召回到 top-K judge”的漏召率。当前方案已经比空壳 keyword 通道强，但还不能标记为完整 PostgreSQL lexical retrieval。

**整改条件：** 实现 SQL 侧字段加权 lexical rank，补充 `matched_terms` / `matched_fields` / score components 输出；为 `search_retrieval_documents()` 增加排序单元测试、`EXPLAIN ANALYZE` 基线和回放评估；用同一套质量评估表比较 SQL lexical rank、当前 Python rank 以及后续可能引入的 reranker。

**优先级：** P1。

## Coverage Selector 目前未真正拉开候选多样性（2026-05-17 记录）

**问题：** 当前日志中虽然出现 `top_k_reason=enumerated_coverage`，但入选候选的 `coverage_bonus` 基本为 `0.000`，`coverage_terms` 也为空。实际效果更接近 RRF + feature score 排序，Coverage Selector 没有明显把不同事件、不同证据类型、不同 answer target 拉开。

**最佳方案：** Coverage Selector 应基于结构化 coverage units 工作，而不是依赖松散文本片段。候选应显式标注覆盖的 `answer_target`、`event_cluster`、`evidence_type`、`relation_intent`、`anchor_entity`、`time_bucket` 等维度；top-K 选择应在相关性达标的前提下奖励新增 coverage，并在日志中输出每个入选候选新增了哪些 coverage units。

**当前方案：** 当前已有 coverage selector 的调用入口和日志字段，但 coverage unit 提取不足，导致 bonus 很弱或为空。排序主要仍由 RRF、keyword feature score 和基础候选类型权重决定。

**影响范围：** “哪些事件”“覆盖哪些资产类别”“多因素影响”这类枚举型问题容易被相似候选占据 judge slot，导致 30->topK 阶段遗漏高价值但排名稍低的不同维度证据。

**整改条件：** 在 candidate package 生成阶段补齐 coverage units；在 preselect 阶段实现 marginal coverage gain；回放日志输出 `new_coverage_units`、`missing_coverage_units`、`coverage_bonus` 和入选原因；用宁德时代、中东冲突、低利率等 case 验证 top-K 多样性。

**优先级：** P1。

## 多通道融合被 Keyword 过度主导，缺少通道贡献诊断（2026-05-17 记录）

**问题：** 最新宁德时代回放中，3 个 query 的 source counts 基本由 keyword 占据，graph/wiki 很少，semantic 的增益不明显。写入期 Retrieval Document 已经起效，但 RRF 可能退化成 keyword 排序，无法确认 semantic、graph、wiki 是否带来新增信息。

**最佳方案：** 多通道融合应保留各通道的独立贡献指标：`keyword_only`、`semantic_only_added`、`graph_confirmed`、`wiki_confirmed`、`multi_channel_confirmed`、`channel_agreement_count`。RRF 之外还应区分“新增召回”和“交叉确认”，避免单一通道因为候选量大而支配 top-K。

**当前方案：** 当前 `agentic_search_plan_result` 能展示 source counts，但缺少通道间去重后的贡献分析，也没有在 ranker summary 中明确说明某个候选是 keyword-only、semantic 新增，还是 graph/wiki 确认。

**影响范围：** 召回质量难以判断。keyword 变强后可能掩盖 semantic/graph 失效；反过来，如果 semantic 能补充关键证据，也可能因为融合权重和候选量问题无法进入 judge。

**整改条件：** 在融合前后记录 per-channel candidate ids、去重映射和最终 top-K channel contribution；加入通道消融评估，至少输出 keyword-only、semantic-only-added、graph-confirmed 三类指标；根据评估结果调整 RRF 和 channel boost。

**优先级：** P1。

## 股票精确查询的 Anchor 约束仍不够强，泛词 evidence 会挤占 judge slot（2026-05-17 记录）

**问题：** 宁德时代问题中，“中东冲突”这类明显偏题 evidence 因命中“影响”等泛词，并且具备 evidence/answer_type 特征，被 feature score 推到较高位置。虽然 Candidate Judge 后续可以 drop，但这会浪费 top-K judge slot。

**最佳方案：** 对包含股票代码、公司名等强 anchor 的查询，preselect 阶段应设置硬性或强惩罚约束：候选必须命中 `300750`、`宁德时代`、其别名，或通过图谱关系与 anchor 有可解释路径；只命中“影响”“事件”“最近”等泛词的非 anchor evidence 不应进入高位。泛词只能作为 intent signal，不能作为相关性主体。

**当前方案：** 当前 Query Anchor 已能抽取 `300750` 和 `宁德时代`，但 feature score 对 anchor miss 的惩罚不足，泛词命中、answer_candidate_type 和 evidence 类型加分可能把非 anchor 事件推高。

**影响范围：** 精确实体查询会出现无关宏观事件、其他公司事件或泛行业事件进入 judge，增加 LLM 成本，并可能在 top-K 过小的时候挤掉真正相关证据。

**整改条件：** 在 ranker/preselect 中增加 anchor gate 或强惩罚；日志输出 `anchor_match_type`、`anchor_path`、`generic_term_only`、`anchor_penalty`；评估集中加入股票精确查询负例，要求非 anchor 泛词 evidence 不进入 judge top-K。

**优先级：** P1。

## Stop Condition 解析仍偏噪声，枚举覆盖校验不够结构化（2026-05-17 记录）

**问题：** 当前 stop verifier 会把自然语言 stop condition 拆出很多不稳定片段，例如“如原油”“货币等”“具体产业链环节如上游材料”。这些噪声 terms 会影响 Coverage Selector 和停止判断。现在机制能避免部分误停，但还不是可靠的结构化枚举覆盖校验。

**最佳方案：** Stop condition 应先被规范化为结构化 coverage schema，例如 `min_answer_count`、`required_categories`、`required_entities`、`required_relation_intents`、`required_evidence_types`、`forbidden_topics`。只有这些结构化字段参与 stop verifier；自然语言原文只作为 trace 展示和回退解释。

**当前方案：** 当前已经从 stop condition 中提取 coverage terms 并记录 missing terms，但提取仍偏字符串启发式，缺少类型化枚举、同义归并和噪声过滤。

**影响范围：** 枚举型问题可能误停或误判未满足；coverage selector 也会被噪声 terms 干扰，导致 top-K 多样性奖励不稳定。

**整改条件：** 增加 stop condition parser，输出 typed coverage schema；对 controller 的 `search_plan.stop_condition` 增加 schema 化约束；用中东冲突、低利率、跨资产覆盖类 case 验证 required categories 是否严格满足。

**优先级：** P1。

## 检索日志缺少 case 级最终摘要，人工判断成本过高（2026-05-17 记录）

**问题：** 当前日志信息已经很全，但分散在 `search_plan_result`、`ranker_preselect`、`candidate_judge`、`auto_expand`、`auto_stop` 等多个块里。人工判断一次检索质量需要跨块比对 query rewrites、通道贡献、30->topK、judge、opened evidence 和 stop verifier，成本过高。

**最佳方案：** 每个 replay case 应在末尾输出一个稳定的 `case_summary`。摘要只保留人工判断必须的信息：query、query rewrites 是否执行、每个通道贡献、30->topK 依据、judge keep/drop 统计和代表候选、opened evidence、stop verifier 是否满足、是否 budget stop、主要风险提示。

**当前方案：** 当前已有细粒度 trace 和部分 human_summary，但缺少跨阶段聚合的最终摘要。日志适合调试单个模块，不适合快速判断整条检索链路是否符合设计初衷。

**影响范围：** 用户和开发者每次分析大日志都需要手工拼接上下文；回放结果难以批量审阅，也不利于沉淀质量基线。

**整改条件：** 在 replay/agentic retrieval 结束时生成 `case_summary`，同时写入 trace 文件和控制台关键摘要；后续可落库到检索质量评估表，支持按 case 汇总检索质量。

**优先级：** P2。

## 检索路由第一版尚未接入 LLM Router（2026-05-15 记录）

**问题：** 当前检索入口已经支持 `auto`、Fast Router、Post-check Router 和 Query Routing Decision trace，但 Fast Router 无法明确判断的 query 暂时会保守走 `deterministic_plan`，还没有接入设计方案中的 LLM Router 来判断复杂度、置信度和工具预算。

**最佳方案：** Fast Router 只处理显式模式、强约束和明显复杂意图；不确定 query 应调用 LLM Router，输入原始 query、Query Anchor、Guard Extractor 结果和预算，输出结构化路由建议。低置信 LLM 输出再降级到 `deterministic_plan`。

**当前方案：** 为了先把通用 core、Query Anchor、候选裁判、Post-check 自动升级和测试闭环落地，本轮没有让默认查询频繁调用 LLM Router。当前不确定 query 会先走 deterministic，再依靠 Post-check 根据 evidence、Anchor 覆盖和候选裁判结果决定是否升级 agentic。

**影响范围：** 对明显简单和明显复杂 query 影响较小；对语义复杂但没有明显复杂关键词的 query，首次路径可能偏保守，需要 deterministic 低质量后才升级，速度和效果可能不如直接 agentic。

**整改条件：** LLM Router prompt、JSON Schema、缓存和超时策略稳定后，新增 `knowledge_query_router_service.py` 并接入 `build_research_context_for`。

**优先级：** P1。

## Agentic Retrieval 第一版仍沿用现有检索工具名，尚未完全抽象为 search/find/open/summarize（2026-05-15 记录）

**问题：** 设计方案要求 Agentic Retrieval 暴露 `search/find/open/summarize` 四类通用工具；当前代码仍复用已有 `entity_resolve`、`semantic_hybrid_search`、`graph_search`、`wiki_search`、`chunk_read` 白名单工具。

**最佳方案：** 在 `retrieval_tools.py` 上增加一层通用 Agentic 工具抽象：`search` 组合多通道召回，`find` 在候选集合或文档内定位，`open` 打开父 evidence / sibling chunk / wiki / path，`summarize` 压缩过程上下文，并让每轮结果进入 Candidate Judge。

**当前方案：** 为避免一次性重写过大导致检索链路不稳定，本轮先把 Candidate Judge 和 Query Context trace 接到现有工具链上，并收紧工具预算。工具语义抽象暂未完成。

**影响范围：** Agentic 模式已经能受白名单工具和预算控制，但工具层表达力还不够清晰，复杂长文档检索时不如 `find/open/summarize` 模型直观。

**整改条件：** Candidate Judge 在 deterministic 链路稳定后，重构 `retrieval_tools.py` 为通用工具层，并补充 agentic loop 集成测试。

**优先级：** P1。

## LLM Candidate Judge 已接入，但调用预算和 top-K 预筛仍需优化（2026-05-15 更新）

**问题：** LLM Candidate Judge 已进入 Agentic Retrieval 链路，可以判断候选是否真正回答 query，并能把区域归属边、无关 mentions、主题漂移候选判为 drop。但最新真实回放显示，普通 query 仍可能出现 `controller -> judge -> controller -> judge -> stop controller` 这类过度调用，且一次 judge 会裁判 30 个宽召回候选，导致单 case 耗时接近 1-2 分钟。

**最佳方案：** 普通 query 默认最多 1 次 LLM Controller + 1 次 LLM Candidate Judge，但这只是默认预算，不是硬性上限。Candidate Judge 只处理程序预筛后的 top 10-15 个 Candidate Package；如果 judge 后已有足够 keep evidence，系统自动 open 核心 evidence，并由程序自动 stop。只有证据不足、候选冲突、Anchor 覆盖不足、关系意图未覆盖、打开 evidence 后仍缺口明显，或 Context Purity 不达标时，才允许第二轮 LLM Controller/Judge。

**当前方案：** 已接入 `LLMCandidateJudge` 和 `LLMAgenticRetrievalStrategy`，并把 LLM request/response 写入纯文本 trace。Query Context 组装阶段已调整为保留 Agentic 阶段真实 judgement，不再用 deterministic judgement 覆盖 trace。但 top-K 预筛、自动 open、自动 stop 和普通 query LLM 调用预算还未完整产品化。

**影响范围：** 相关性已经明显改善，能降低无关 evidence/node/edge 混入；但成本和延迟不可接受，且多轮 search/judge 可能带来不必要的候选扩散。真实库回放和人工调试会受慢查询影响。

**整改条件：** 实现候选预筛 top-K、LLM 调用预算、质量门槛续跑、Working Set 自动 open/stop、trace 中记录 `llm_calls_used` / `judge_top_k` / `auto_action` / `continue_reason`，并补充 `test_agentic_retrieval_auto_open_stop.py`、`test_llm_candidate_judge_top_k.py`、真实回放耗时基线。

**优先级：** P1。

## Agentic Retrieval 停止条件仍过度依赖 LLM Controller（2026-05-15 记录）

**问题：** 最新 trace 中，第一轮 judge 已经找到足够回答 query 的高置信事件后，Controller 仍继续发起第二轮 search；最终 stop 也需要再调用一次 LLM Controller。这个流程在语义上可解释，但工程上浪费调用，并且显著拉长耗时。

**最佳方案：** Working Set 应有程序化停止判断：当 keep evidence 数量、Anchor coverage、relation intent 覆盖、opened evidence 状态和噪声指标都达标时，直接自动 stop。证据足够但尚未 open 时，自动 open 核心 evidence，而不是请求 LLM Controller 决策。

**当前方案：** LLM Controller 可以输出 search/open/stop，但自动 open/stop 状态机尚未完整实现。当前 trace 已能暴露 controller_duration_ms、judge_duration_ms 和每轮决策原因，方便定位多余调用。

**影响范围：** 普通 query 会变慢；LLM 成本增加；多余 search 还可能引入新的噪声候选，增加 judge 成本和上下文污染风险。

**整改条件：** 在 Agentic Retrieval Loop 中增加 `auto_open_if_sufficient_evidence` 和 `auto_stop_if_context_sufficient`，并将自动动作写入 trace。

**优先级：** P1。

## Evidence Chunk 只有单片段索引，缺少父文档和相邻片段上下文扩展（2026-05-14 记录）

**问题：** 当前 evidence chunk 生成仍是第一版简化实现：一条 evidence 基本只生成一个 `kg_chunk:{evidence_id}:0`，内容由标题、来源、实体提示和 evidence content/payload 拼接而成。这样暂时绕开了“同一文档被切成多个 chunk 后相邻上下文丢失”的问题，但没有真正解决长文档检索的上下文问题；长新闻会出现语义稀释，未来一旦改成多 chunk，也没有 sibling chunk / parent evidence / document summary 的回读机制。

**最佳方案：** 建立多层 chunk 体系：文档级 summary chunk 用于整篇材料召回，片段级 passage chunk 用于精细语义召回，实体/关系索引 chunk 用于结构化召回。命中任一 chunk 后，应能回读父 evidence、相邻 chunk、相关 node/edge 和必要 Wiki 摘要，并在 Query Context 中按预算合并输出。

**当前方案：** 当前 `kg_evidence_chunks` 和 Milvus hybrid index 主要以 evidence 为单位生成单个检索 chunk；`chunk_read` 根据 evidence_id 回读整条 evidence。这个方案可以跑通链路，但它不是成熟的 chunk window / parent document retrieval 设计。

**影响范围：** 对短文本和结构化信号影响较小；对长新闻、公告、研报摘要和多段材料，可能出现两个问题：一是大 chunk 语义被无关内容稀释，导致召回不准；二是未来细粒度切分后，如果没有相邻片段扩展，可能召回到局部片段但缺少完整上下文，或者目标内容在相邻片段中而没有被召回。

**整改条件：** 在“检索与 Query Context”技术方案中补充 chunk 层级设计，并改造 evidence chunk schema、Milvus payload、检索 runtime 和 `chunk_read`：支持 `document_id`、`chunk_index`、`parent_evidence_id`、`prev/next` 或等价顺序字段；检索命中后支持 parent + sibling expansion；配套增加长文档真实库回放测试。

**优先级：** P1。

## 检索召回缺少通用相关性重排，容易混入语义相似噪声（2026-05-14 记录）

**问题：** 当前 `deterministic_plan` 检索链路会融合 `entity_resolve`、`semantic_hybrid_search`、`graph_search`、`wiki_search`、`chunk_read` 的结果，但缺少一个通用的二阶段相关性重排/裁判层。真实回放中，查询“俄就波法联合军演发出警告：欧洲对俄全面对抗正在回归”时，结果能命中目标新闻，但也会混入“固态电池政策支持带动宁德时代产业链预期”“宁德时代”等语义相似但业务无关的 demo/CATL 内容。

这说明当前系统已经完成“数据进入知识图谱的组织方式”和“写入治理”，但检索侧还没有完成从多通道 RAG 到 KG-RAG 的关键跃迁。当前链路更接近：`Raw Data -> Source Record -> LLM/规则抽取 -> Node/Edge/Evidence 入库 -> Wiki/Milvus/图邻接索引 -> 多通道 RAG 召回`。图谱目前更多在写入和上下文组织阶段发挥作用，还没有在检索阶段形成足够强的约束和裁判能力。

**最佳方案：** 保持第一阶段多通道宽召回，但在进入最终上下文前增加通用候选重排层。重排层应基于 query、候选 evidence、node、edge、wiki、图谱路径和证据文本做统一评分，判断候选是否真正回答当前问题；必要时由 LLM 参与 top-K 候选裁判，但不能在通用知识库核心层硬编码金融表名、`ft_news:*` 这类 source_id 规则。

目标检索链路应调整为：`多通道召回 -> 候选归并 -> Query Anchor 识别 -> 候选 evidence/node/edge 相关性裁判 -> 保留相关候选 -> 从相关 anchor 做图谱扩展和证据回读 -> Query Context`。其中 Query Anchor 需要识别 query 的核心事件、实体、时间、主题和关系意图；候选裁判需要判断候选是否覆盖核心事件、是否共享关键实体、是否只是语义相似但主题偏移、是否能解释当前问题。

**当前方案：** 目前检索阶段主要是确定性 planner + Milvus 语义/BM25 + 图谱扩展 + Wiki/Chunk 读取；LLM 主要参与写入阶段的实体、事件、关系抽取，不参与 `deterministic_plan` 的候选相关性裁判。`semantic_hybrid_search` 是全库相似召回，只要向量或 BM25 认为片段相似，候选就可能进入结果；`chunk_read` 又会根据 evidence_id 回读 evidence，并通过 evidence 关联的 edge 带出 node，导致无关 evidence 一旦进入候选，就可能放大成无关实体和关系。为了避免破坏通用知识库边界，本次没有把 `ft_*` source_id 正则过滤写入通用 runtime。

**影响范围：** 在生产数据量较大、存在 demo/历史/相似主题噪声时，检索上下文可能包含无关 evidence、node 和 edge，进而影响后续问答、解释、投研结论生成和质量评估。该问题不会导致目标 evidence 完全不可检索，但会降低上下文纯度。

**整改条件：** 需要先补充“候选重排/裁判”设计与技术方案，再实现可插拔 reranker。第一版可先做确定性特征重排；第二版接入 LLM rerank/judge，只对 top-K 候选做低成本判断；后续如果调用方需要强约束，应通过结构化 filter 参数传入，而不是从自然语言 query 中写死解析某类业务 source_id。

**优先级：** P1。

## 知识图谱演示脚本的检索评估口径过宽（2026-05-15 记录）

**问题：** `2_kg_compile_and_write_demo.py` 的 Step 6.5 会把 Step 6 本批写入的所有 evidence 都放进 `expected_evidence_ids`。当一批写入两条真实新闻时，查询其中一条新闻，另一条新闻的 evidence 也会被算作 expected。这样会造成“expected_evidence_hit=True”，但实际 Query Context 已经混入无关 evidence、node 和 edge，评估结果容易显得比真实效果更好。

**最佳方案：** 每条 query 应该绑定它对应的 Source Record 和 expected evidence，而不是绑定整批写入结果。真实回放应按 case 粒度记录：query、expected source_id、expected evidence_id、必须命中的 node/edge、禁止出现的噪声主题、最小通道要求和上下文纯度指标。

**当前方案：** Demo 主要用于演示 Source Record 编译写入后能被检索消费，不是严格质量评估脚本；因此目前只检查“本批 evidence 是否至少有一个被命中”，没有判断每条 query 是否只命中了对应 evidence，也没有把无关 evidence 作为失败条件。

**影响范围：** Demo 输出会误导人工判断，尤其是在全库噪声较多时，可能把“目标 evidence 命中但上下文污染严重”的情况判成成功，掩盖检索重排和上下文裁判缺失的问题。

**整改条件：** 修改 demo 或新增专门质量回放脚本：按 Source Record 生成独立 case，expected evidence 只包含当前 query 对应 evidence；增加 negative expectations，例如查询俄波法军演时不应出现宁德时代/固态电池；输出 precision、noise evidence count、unexpected node count 等指标。

**优先级：** P1。

## Milvus 旧向量物理清理已支持 evidence 粒度删除，仍需观察大批量性能（2026-05-15 更新）

**问题：** evidence 版本治理会把旧 evidence 标记为 `superseded`，检索层也会过滤 inactive/superseded evidence；如果旧 evidence chunks 曾经写入 Milvus，增量链路必须同步删除对应旧向量，否则 Milvus 会持续保留不可消费的脏向量。

**最佳方案：** Milvus 向量库支持按 evidence_id 删除旧 chunk 向量；evidence supersede 时同步删除旧向量，避免向量库持续膨胀。

**当前方案：** 已实现 `MilvusHybridStore.delete_evidence()`、`MilvusSemanticHybridRetriever.delete_evidence()`，`kg cleanup-evidence` 会在 PostgreSQL 中废弃旧 evidence/edge 后，按 stale evidence_id 删除 Milvus hybrid 向量；增量写入刷新也会执行 stale evidence cleanup，并把 `stale_hybrid_vectors_deleted` 写入 index_refresh 摘要。全量 rebuild 不再是清理旧向量的唯一手段。

**影响范围：** 默认检索正确性更稳定，Milvus 中旧 evidence 向量不会长期堆积。当前删除实现为了兼容 Milvus filter，按 evidence_id 逐条删除，大批量历史清理时可能比批量表达式慢。

**整改条件：** 如果后续一次 cleanup 涉及大量 evidence，需要评估 Milvus `in` filter 的兼容性和性能，必要时改成批量删除表达式或后台分片清理任务。

**优先级：** P3。

## 历史实体重新归一已有迁移计划，但尚未实现自动改写主图（2026-05-15 记录）

**问题：** LLM 写入期可以生成标准化规则，质量扫描可以审计规则和隔离项，但历史脏数据的真正迁移仍然没有自动执行。例如库里同时存在 `红利资产` 和 `高股息` 时，系统现在能识别迁移需求，但不会直接改写旧 node、edge、wiki、chunk 和向量。

**最佳方案：** 建立完整的历史重新归一工具链：基于 active rule 生成 migration plan，按强合并/软合并/阻断合并分别执行主图改写；改写前记录审计快照，改写后重建受影响 adjacency、evidence chunks、wiki 和 hybrid vectors；整个过程支持 dry-run、分批执行、失败回滚和结果复盘。

**当前方案：** 已新增只读迁移计划能力：`kg normalization-migration-plan --adapter financial --target prod --json`。它会基于 active alias rule 扫描 raw/canonical 节点，输出待迁移 action、受影响 edge、跨类型阻断原因和 quarantine evidence。该命令不修改主图，避免在规则闭环尚未稳定前批量污染历史数据。

**影响范围：** 系统已经能发现历史脏数据迁移范围，但旧节点在真正执行迁移前仍会存在，检索和 Wiki 中可能继续出现重复实体或旧 canonical name。好处是不会因为 LLM 规则误判而直接破坏主图。

**整改条件：** 在迁移计划稳定、真实库回放样本通过后，再实现 `normalization-migrate --dry-run/--apply`：先支持同类型 hard merge，再支持 soft merge 别名挂接，最后处理跨类型阻断和批量重建。

**优先级：** P1。

## 结构化信号投影第一轮覆盖已补齐，后续跟踪新增 data_type（2026-05-15 更新）

**问题：** `ft_market_flow`、`ft_market_cache`、`ft_sentiment` 到 `derived_signal` 的初版投影只识别常见的 `value` / `score` / `net_amount` / `net_flow` 等字段，遇到嵌套 JSONB、列表型快照和情绪榜单时会跳过。

**最佳方案：** 针对真实库中每个高频 `data_type` 建立明确 mapping，包含 target_ref、signal_type、value、unit、window 和解释字段，配套真实库覆盖率统计。

**当前方案：** 已补充结构化信号投影规则版本 `financial_source_projection_v2`，支持嵌套路径取值、列表聚合、龙虎榜 `net_amt`、市场快照 `sector_ranking / market_environment / market_overview / global_index / forex / futures_*`、情绪表 `guba_posts / guba_popularity / limit_pool / xueqiu_hot_stocks / xueqiu_hot_topics` 等真实库常见形态。投影服务已输出 coverage，包含每个 source/data_type 的 total/projected/skipped、projection_rate 和 skip_reasons。2026-05-15 使用真实库结构化表验证：`ft_market_flow=732/732`、`ft_market_cache=7/7`、`ft_sentiment=53/53`、`ft_macro_indicators=861/861`，当前样本 skip 为 0。

**整改条件：** 后续每次新增结构化采集源或发现 coverage 中 skipped > 0 时，按 skipped 分布补 mapping，并补单元测试和真实库 smoke test。

## source_type 误判后的历史数据矫正链路暂缓实现（2026-05-13 记录）

**问题：** 如果 `ft_news` 在投影阶段把 `source_type` 识别错，后续编译、关系抽取、证据绑定、检索过滤都会基于错误输入继续传播。目前系统还没有正式的“重投影 -> 重编译 -> 废弃旧 evidence/edge -> 审计”的矫正链路。

**最佳方案：** 以原始业务表为事实来源，按最新 projection rule version 重新投影受影响 source_id；如果 source type 或关键 metadata 发生变化，生成 correction plan，废弃旧 evidence 和无法被新 evidence 支撑的边，重新 compile 并增量刷新索引，同时记录 correction audit。

**当前方案：** 第一版以跑通完整链路为优先，不实现历史矫正。质量扫描只输出疑似误分统计和样本；前期测试数据如果污染明显，允许清空测试 KG 后按新规则重跑。该能力暂不进入当前开发主线。

**整改条件：** 当投影规则频繁调整、历史误判样本开始明显影响检索质量，或者进入生产级批量重跑阶段时，再增加 projection rule version、quality scan 误分检测、correction plan、旧 evidence/edge 废弃策略，以及相关单元测试和真实库回放测试。

**优先级：** P3。

## LLM 候选事实包一等化第一阶段已完成，仍需固化跨领域转换协议（2026-05-15 更新）

**问题：** `CandidateFactPackage` 已经从“LLM 输出形态”提升为领域层一等对象，金融新闻抽取也不再把 LLM 候选事实折回 `mentioned_entities` / `affected_entities`。但跨领域协议还没有完全固化：Adapter 还没有显式声明“支持哪些候选事实类型、候选关系类型、歧义项和规则建议”，新领域适配器也还没有通过真实业务数据验证。

**影响范围：** 金融新闻链路已经不再被旧 payload 字段绑定，但新领域接入时仍可能出现 Adapter 各自解释候选事实包的问题。如果不继续固化协议，后续多个领域适配器会产生不同转换口径，影响跨领域复用和质量评估。

**整改条件：** 在第二个真实领域适配器接入前，补充 Adapter capability 声明，明确每个 Adapter 支持的 candidate entity / event / relation 类型、降级策略、拒绝原因和规则建议落库方式，并补充跨领域适配器契约测试。

**优先级：** P2。
