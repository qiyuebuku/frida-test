## 当前记录

## 原子 Card 与 Relation Probe 单请求质量竞争已整改（2026-07-19 记录，2026-07-19 整改）

**问题：** 当前一次 LLM 请求同时生成原子 Card、证据引用和 Relation Probe。真实长文回放显示，继续增加 Probe 约束会在两种失败之间摆动：约束偏松时出现同指标历史值、机械否定或未经依据的未来结果；约束偏紧时 Probe 全部为空，并增加 Card 过度拆分和 reasoning token。提示词从 v81 到 v85 的同样本回放未得到稳定优于 v81 的结果。

**最佳方案：** Card 与原文明示的同 Chunk Relation 在读取完整原文的一次调用中完成；Relation Probe 在 Card 和 Relation 冻结后，沿用第一次调用的不可变消息历史继续追问。Card 与 Probe 的完整固定规则从第一次请求起都位于 System Prompt，但 Probe 规则通过阶段门禁在首轮禁用。第二轮只追加已接受的 assistant 输出和一句简短阶段切换指令，不重新发送 Probe 规则，也不重新序列化 Cards、Focus Evidence 或 Relations，从而隔离响应职责并让固定规则进入稳定缓存前缀。

**当前方案：** 已移除 Card 项中的 Probe 输出，并删除独立 `kg_cognitive_card_relation` 追问。`kg_cognitive_card` 按 `cards -> relations -> skip_reason` 一次输出事实和同文关系；随后 `kg_relation_probe` 复用原 system、原文 user 和实际通过校验的 assistant 输出，只追加简短阶段切换指令，结果校验后回填 PG manifest。System Prompt 明确要求首轮严禁思考、规划或输出 Probe。Card/Relation 规则已收敛为一次性的“事实元组 -> 严格蕴含去重 -> 事件链端点 -> 原文连接映射”流程，Probe 使用与 Summary 核心谓词不同的增量门槛，不再通过重复禁令驱动模型反复检查。单元测试覆盖阶段门禁、短追问、消息历史复用、修复后输出续问和 Card 完整覆盖。

**影响范围：** Card/Relation 与 Probe 的职责竞争已消除。Relation Probe 本身仍受模型随机性影响，需要通过固定评测集持续衡量 precision 和 Positive Pair Recall@K。

**整改条件：** 已完成调用结构整改；后续仅依据固定评测集调整 Probe Prompt，不再把 Probe 合回 Card 提取响应。

**优先级：** P1。

## PG Evidence Chunk 文本过渡回退已整改（2026-05-23 记录，2026-06-03 整改）

**问题：** 新检索架构要求 Milvus 负责语义搜索和按 `target_id` 精准取回 chunk/card text，PG 只维护事实、关系和 chunk manifest。旧实现中 `kg_evidence_chunks` 曾保留 chunk content，容易导致 PG 和 Milvus 两套可读文本不一致。

**最佳方案：** PG 只保存 `chunk_id`、`evidence_id`、source、chunk_index、offset、hash、chunker_version 等 manifest；可读 chunk/card text 只进入 Milvus。查询链路中，node/edge/evidence 命中后通过 manifest 或 evidence refs 解析出 `target_id`，再由 Milvus `get_by_ids()` 精准取回可读文本。没有 Milvus 文本时应显式失败或进入重建索引流程，而不是静默回退到 PG 大文本。

**当前方案：** 已删除 `kg_evidence_chunks.content/payload` 写入边界，PG chunk 表只保存 manifest。repository 回表时通过 `kg_evidence.content` 和 offset 重建 `EvidenceChunk.content`，并从 `kg_evidence.payload` 回补 `published_at/source_id/source_type` 等元数据供 graph delta 和 Milvus rebuild 使用；Milvus Evidence Chunk 文档负责保存标题、摘要、实体搜索词和可读 chunk text。

**影响范围：** 数据边界已收敛为 PG 事实/指针、Milvus 可读检索文本。后续风险主要在索引刷新失败时需要显式暴露，而不是从 PG 静默回退。

**整改条件：** 已完成。后续如发现旧库残留列，应通过 `schema/10_drop_kg_evidence_chunks_content.sql` 清理历史库。

**优先级：** 已完成。

## Recursive Chunk 与 chunk manifest 已完成数据边界收敛（2026-05-23 记录，2026-06-03 整改）

**问题：** 新写入方案要求 evidence 先经过 Recursive Chunker，生成 `chunk_index`、offset、previous/next、`text_hash`、`chunker_version` 等 manifest，再把完整 chunk text 写入 Milvus。旧版本曾把标题、source、实体词混入 chunk 文本，导致 offset 不再相对 `kg_evidence.content`。

**最佳方案：** 写入链路应先按段落、换行、中文标点、空格、字符兜底的递归策略切 chunk；PG 只保存 manifest 和引用；Milvus 保存完整 chunk text 和 embedding。查询命中任一 chunk 后，可以按预算补 previous/next 或 parent evidence context。

**当前方案：** chunker 只基于 `kg_evidence.content` 生成 offset，标题、摘要、source、实体搜索词进入 Milvus Evidence Chunk 文档，不再污染 offset。`kg_evidence_chunks` 只写 manifest 字段；repository 通过 evidence 原文和 offset 重建 chunk 内容，供 Milvus rebuild 和 graph delta 使用。

**影响范围：** chunk offset 与 evidence 原文重新一致；Milvus 语义检索仍保留标题、摘要、实体词等增强信息。

**整改条件：** 已完成。表名仍沿用 `kg_evidence_chunks`，但语义已在 ORM 注释和 schema 中明确为 chunk manifest。

**优先级：** 已完成。

## AI 抽取归一与 type registry 流水线仍需升级为独立 prompt runner（2026-05-23 记录，2026-05-25 更新）

**问题：** 目标写入方案要求先从 chunk 抽取 raw entity / raw relation，再用 embedding 召回相似候选，让 AI 判断复用、新建或建议新 type，并在允许 type 列表和定义约束下扩展 type registry。当前代码已做到 chunk-first fan-out，但仍主要复用既有金融新闻抽取包校验和修复逻辑，还没有把三类 prompt 固化为独立 prompt runner。

**最佳方案：** 写入侧应固定三类 prompt：`chunk_entity_relation_extract_prompt`、`entity_relation_normalize_with_candidates_prompt`、`type_registry_suggestion_prompt`。每次抽取都带 allowed types、definitions、examples；每次归一都带 embedding 召回候选；最终由 Resolver 执行 AI 决策并写入 PG/Milvus。

**当前方案：** 当前已经有 LLM 抽取、质量修复和关系校验；存在 chunk hints 时会按 chunk 分别调用抽取 prompt，再合并 candidate package。compile 过程中已经先物化 evidence metadata、PG chunk manifest 和 Milvus chunk target，再进入 node / edge 抽取。抽取输出已支持 `evidence_spans.chunk_id`，PG 写 `kg_edge_evidence_chunks` 时会优先使用显式 chunk_id。写入侧归一化服务已接入真实 Milvus semantic candidate provider，允许 AI 返回 `reuse_semantic_candidate` 后生成 alias rule；`mentioned_entities`、`affected_entities` 和 `candidate_fact_package.entities` 中未命中确定规则的实体都会进入 semantic candidate + AI normalize，不再按强类型直接跳过。归一后会同步改写 relation source/target。`candidate_fact_package.relations` 已接入 relation semantic candidate provider，AI 可在 `reuse_semantic_candidate` / `keep_current_relation` / `suggest_new_type` 中自动决策，低置信度时保留当前关系而不是进入人工 pending。AI normalize prompt 已携带 active type registry，返回 `suggest_new_type` 时会自动写入 active type rule；active type registry 已回灌到金融 adapter spec、抽取 JSON Schema 和抽取 prompt。尚未完成的是更细粒度 endpoint constraint 冲突治理，以及把现有复用式实现整理成独立 prompt runner。

**影响范围：** 跨批次实体和关系命名仍可能漂移；相近实体可能变成多个 node；新 type 发现与约束还不够系统化。查询侧即使已经追溯到 chunk，也可能受上游事实归一质量影响。

**整改条件：** 已完成 AI normalize prompt 的真实 semantic candidate 入口、实体和关系 `reuse_semantic_candidate` 单测、`suggest_new_type` 最小闭环单测、chunk-first fan-out 抽取单测、抽取 `chunk_id` 保留、edge -> chunk 精确引用单测、candidate package entity 归一与 relation endpoint 改写单测、type registry schema 回灌单测；后续还需补充 endpoint constraints、错误 type 合并治理和真实回放。

**优先级：** P1。

## 跨 Chunk Relation Discovery 按 Card 串行导致批量回放耗时过长（2026-07-14 记录）

**问题：** 当前 `RelationDiscoveryService` 为保证 pair 去重和写入顺序确定，会逐张 Card 执行多路召回、rerank、Summary 初筛和原文核验。真实两条新闻回放生成 6 张 Card 后，完整 workflow 超过 120 秒；负分 rerank 截断已经减少无效 LLM 调用，但存在多个正候选时仍会线性累积延迟。

**最佳方案：** 在保留同源、同 Chunk 排除和 unordered pair 唯一归属的前提下，为 Card 发现增加有界并发。调度前先确定每个 pair 的唯一 owner，任务内并发处理不同 source Card，最终按稳定 pair key 合并决定并批量写入，避免共享可变 `seen_pairs` 造成重复核验。

**当前方案：** 继续使用串行处理保证结果确定性；rerank 分数低于 `KG_RELATION_RERANK_MIN_SCORE` 的候选会在 LLM 前丢弃，所有候选均低于阈值时不调用初筛。尚未为了测试速度引入不安全的并发写入。

**整改条件：** 建立至少 20 张 Card 的真实批量基准和重复 pair 数据集后，实现 pair owner 预分配与有界并发，并验证 Edge 幂等、Worker 中断恢复和端到端耗时。

**优先级：** P2。

## Graph Index Dirty Subgraph 定点构建升级记录（2026-05-27 记录，2026-05-30 已整改）

**问题：** 实施方案要求新增事实进入后定位 dirty subgraph，计算 Community Change Score，只对受影响 community、子图和父链路做局部更新。此前代码已经能识别 affected communities 和 scoped replace，但构建阶段仍先全图 build。

**最佳方案：** 写入 nodes / edges / chunks 后同步维护基础分析图和社区成员映射；增量阶段根据 changed node/edge/chunk refs 找到 affected communities，计算 member delta、edge weight delta、novelty、cross-community ambiguity、evidence delta 等分数；低分只更新 refs/activity，高分才局部重跑 community detection 和 report/finding。

**当前方案：** 已整改。增量 compile 后先执行 `plan_graph_index_refresh()` 输出 dirty scope / score / action；如果 action 是 `full_rebuild`，通过 `replace_graph_index()` 全量替换；如果 action 是轻量或局部重算，则展开 affected community 的 parent / child closure，从全量 facts 中投影出 dirty subgraph，并只把 scoped nodes / edges / chunks 交给 `build_graph_index()`。持久化阶段通过 `replace_graph_index_scope()` 只替换 dirty scope，并删除 Milvus 中对应 stale community/finding/delta target。

**影响范围：** 当前实现已经避免“全图 build 后截取”的问题。后续仍需通过真实数据观察局部边界是否过窄或过宽，但这属于参数调优，不属于能力缺失。

**整改条件：** 已完成 dirty subgraph 子图读取、局部 community detection、scoped replace 和单测。

**优先级：** 已整改。

## Graph Index 自动全局校准调度尚未固化（2026-05-31 记录）

**问题：** Graph Index 已支持手动 `scope=all` 和 `scope=projection:<projection_name>` 的全局校准，并且会归档历史版本。但“什么时候自动触发全局校准、按什么周期跑、如何按真实质量指标调阈值”还没有固化为后台调度策略。

**最佳方案：** 基于真实 replay 和线上观测建立自动校准策略：按 projection、adapter、source/time scope 分批执行；触发条件来自 community 抖动、finding 证据覆盖下降、dirty subgraph 长期过宽、query 命中质量下降和 token 成本异常；每次校准必须记录明确原因、scope、旧版本归档和质量前后对比。

**当前方案：** 主链路已完整支持增量 light/local review/local recompute，以及手动全局校准。自动调度暂不写死，避免在缺少真实回放基线时用拍脑袋阈值造成无意义重建。

**影响范围：** 功能完整性不受影响；需要定期人工触发或通过后续任务系统触发全局校准。长期运行后如果没有自动调度，可能出现 projection 权重、prompt 或 schema 变化后未及时全局重建。

**整改条件：** 完成一批真实 replay 质量基线后，确定全局校准触发阈值、周期、scope 策略和回滚策略，再接入 scheduler / task runner。

**优先级：** P2。

## DeepSeek 前缀缓存友好的批量与会话化 LLM 调用尚未系统化（2026-05-17 记录）

**问题：** DeepSeek 的上下文硬盘缓存是服务端前缀缓存，不是业务语义缓存。只有请求消息前缀完全一致或高度稳定时，才能命中 `prompt_cache_hit_tokens`。当前系统已把 JSON Schema、固定规则和稳定 contract 尽量前置，减少了无谓 miss；但更高收益的调用形态尚未系统化：同类问题仍可能分散成多次独立请求，controller/judge/extraction 的批量调度、稳定 message history、以及“同一轮对话中连续询问多个相似任务”的机制还没有设计完成。

**最佳方案：** LLM 调用层应提供缓存友好的任务编排能力：

- 对同类任务采用稳定 system prompt + 稳定 schema/contract + 变量 payload 后置的消息结构，禁止把当前时间、随机 ID、trace metadata、候选顺序抖动等内容放进前缀。
- 对多个同类候选判断、多个新闻抽取、多个 query 评估，优先使用 batch JSON 输入，在一次请求里处理 N 个 item，摊薄固定 prompt 成本，并最大化 DeepSeek 前缀缓存收益。
- 对确实需要多轮的场景，维护不可变历史消息前缀，只在尾部追加新 user/tool 消息；不得重写、重排或重新序列化历史内容。
- 在 LLM usage 和全量日志中持续记录 `prompt_cache_hit_tokens`、`prompt_cache_miss_tokens`、batch size、per-item 成本和延迟，用真实指标判断是否值得扩大 batch 或会话化。

**当前方案：** 已完成第一层工程约束：DeepSeek JSON 模式会把固定 JSON 指令和 Schema 放在 system message；检索 controller/judge 的 prompt 已调整为固定规则、工具 contract、decision schema 前置，query、working set、candidate list 等变量内容后置；日志会输出 `prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`。但当前仍主要是单请求处理单个 controller decision、单个 candidate judge 批次、单条新闻抽取；没有统一的 batch 调度器，也没有跨请求的稳定 conversation/session 编排。

**影响范围：** 功能正确性不受直接影响，但成本和延迟仍可能偏高。尤其是 100 条真实新闻写入、多个 replay case、二批 judge 或未来 LLM batch pre-judge 时，如果每次都重复发送固定 schema/规则，会浪费 token，并降低 DeepSeek 服务端缓存命中率。相同任务的 prompt 只要前缀因为字段顺序、时间、metadata 或候选排序轻微变化，就会错失缓存收益。

**整改条件：** 先在真实回放日志中收集各任务的 `prompt_cache_hit_tokens / miss_tokens` 基线；再设计 `LLMBatchTaskRunner` 或等价批量调用接口，优先覆盖 `financial_news_extraction`、`kg_candidate_judge`、`quality_review` 这类同构任务；同时为 multi-turn 场景定义不可变 message history 规范和测试，确保历史消息字节级稳定。上线前用同一批真实库回放比较 batch/会话化前后的耗时、token、缓存命中率和输出质量。

**优先级：** P2。

## Coverage Selector 旧预筛方案已被 chunk-pool + rerank 取代（2026-05-17 记录，2026-05-23 更新）

**问题：** 这是旧 candidate preselect 链路下的记录。新查询方案不再让裸 node / edge / wiki candidate 直接进入 LLM judge，而是先把多入口召回统一追溯为 evidence chunk pool，再交给 rerank 和 Agent。继续增强旧 Coverage Selector 会让排序责任重新分散。

**最佳方案：** 覆盖和多样性应该发生在 chunk pool 合并、去重、预算控制和 rerank 之前：同一 chunk 合并多通道来源，按 evidence/source/chunk 去重，再由 rerank 处理语义相关性。枚举型覆盖可以作为 rerank 前的预算控制特征，但不再作为独立规则排序器。

**当前方案：** 主链路已经迁到 chunk-pool + rerank；旧 Coverage Selector 相关 trace 只应作为历史链路诊断，不应继续扩展。

**影响范围：** 如果旧链路还在 baseline 中运行，仍可能出现 candidate 重复和覆盖不足；OpenAI Agent RAG 主链路应以新 rerank 结果为准。

## 多通道融合被 Keyword 过度主导，缺少通道贡献诊断（2026-05-17 记录）

**问题：** 最新宁德时代回放中，3 个 query 的 source counts 基本由 keyword 占据，graph/wiki 很少，semantic 的增益不明显。写入期 Retrieval Document 已经起效，但 RRF 可能退化成 keyword 排序，无法确认 semantic、graph、wiki 是否带来新增信息。

**最佳方案：** 多通道融合应保留各通道的独立贡献指标：`keyword_only`、`semantic_only_added`、`graph_confirmed`、`wiki_confirmed`、`multi_channel_confirmed`、`channel_agreement_count`。RRF 之外还应区分“新增召回”和“交叉确认”，避免单一通道因为候选量大而支配 top-K。

**当前方案：** 当前 `agentic_search_plan_result` 能展示 source counts，但缺少通道间去重后的贡献分析，也没有在 ranker summary 中明确说明某个候选是 keyword-only、semantic 新增，还是 graph/wiki 确认。

**影响范围：** 召回质量难以判断。keyword 变强后可能掩盖 semantic/graph 失效；反过来，如果 semantic 能补充关键证据，也可能因为融合权重和候选量问题无法进入 judge。

**整改条件：** 在融合前后记录 per-channel candidate ids、去重映射和最终 top-K channel contribution；加入通道消融评估，至少输出 keyword-only、semantic-only-added、graph-confirmed 三类指标；根据评估结果调整 RRF 和 channel boost。

**优先级：** P1。

## 股票精确查询的 Anchor 约束仍不够强，泛词 evidence 会挤占 judge slot（2026-05-17 记录）

**问题：** 宁德时代问题中，“中东冲突”这类明显偏题 evidence 因命中“影响”等泛词，并且具备 evidence/answer_type 特征，被 feature score 推到较高位置。虽然 Candidate Judge 后续可以 drop，但这会浪费 top-K judge slot。

**最佳方案：** 对包含股票代码、公司名等强 anchor 的查询，preselect 阶段应设置硬性或强惩罚约束：候选必须命中 `300750`、`宁德时代`、其别名，或通过图谱关系与 anchor 有可解释路径；只命中“影响”“事件”“最近”等泛词的非 anchor evidence 不应进入高位。泛词只能作为 intent signal，不能作为相关性主体。

**当前方案：** 当前 Query Anchor 已能抽取 `300750` 和 `宁德时代`，但 feature score 对 anchor miss 的惩罚不足，泛词命中、answer_candidate_type 和 evidence 类型加分可能把非 anchor 事件推高。

**影响范围：** 精确实体查询会出现无关宏观事件、其他公司事件或泛行业事件进入 judge，增加 LLM 成本，并可能在 top-K 过小的时候挤掉真正相关证据。

**整改条件：** 在 ranker/preselect 中增加 anchor gate 或强惩罚；日志输出 `anchor_match_type`、`anchor_path`、`generic_term_only`、`anchor_penalty`；评估集中加入股票精确查询负例，要求非 anchor 泛词 evidence 不进入 judge top-K。

**优先级：** P1。

## Stop Condition 解析仍偏噪声，枚举覆盖校验不够结构化（2026-05-17 记录）

**问题：** 当前 stop verifier 会把自然语言 stop condition 拆出很多不稳定片段，例如“如原油”“货币等”“具体产业链环节如上游材料”。这些噪声 terms 会影响 Coverage Selector 和停止判断。现在机制能避免部分误停，但还不是可靠的结构化枚举覆盖校验。

**最佳方案：** Stop condition 应先被规范化为结构化 coverage schema，例如 `min_answer_count`、`required_categories`、`required_entities`、`required_relation_intents`、`required_evidence_types`、`forbidden_topics`。只有这些结构化字段参与 stop verifier；自然语言原文只作为 trace 展示和回退解释。

**当前方案：** 当前已经从 stop condition 中提取 coverage terms 并记录 missing terms，但提取仍偏字符串启发式，缺少类型化枚举、同义归并和噪声过滤。

**影响范围：** 枚举型问题可能误停或误判未满足；coverage selector 也会被噪声 terms 干扰，导致 top-K 多样性奖励不稳定。

**整改条件：** 增加 stop condition parser，输出 typed coverage schema；对 controller 的 `search_plan.stop_condition` 增加 schema 化约束；用中东冲突、低利率、跨资产覆盖类 case 验证 required categories 是否严格满足。

**优先级：** P1。

## 检索日志缺少 case 级最终摘要，人工判断成本过高（2026-05-17 记录）

**问题：** 当前日志信息已经很全，但分散在 `search_plan_result`、`ranker_preselect`、`candidate_judge`、`auto_expand`、`auto_stop` 等多个块里。人工判断一次检索质量需要跨块比对 query rewrites、通道贡献、30->topK、judge、opened evidence 和 stop verifier，成本过高。

**当前方案：** 当前已有细粒度 trace 和部分 human_summary，但缺少跨阶段聚合的最终摘要。日志适合调试单个模块，不适合快速判断整条检索链路是否符合设计初衷。

**影响范围：** 用户和开发者每次分析大日志都需要手工拼接上下文；回放结果难以批量审阅，也不利于沉淀质量基线。

**整改条件：** 在 replay/agentic retrieval 结束时生成 `case_summary`，同时写入 trace 文件和控制台关键摘要；后续可落库到检索质量评估表，支持按 case 汇总检索质量。

**优先级：** P2。

**最佳方案：** Fast Router 只处理显式模式、强约束和明显复杂意图；不确定 query 应调用 LLM Router，输入原始 query、Query Anchor、Guard Extractor 结果和预算，输出结构化路由建议。低置信 LLM 输出再降级到 `deterministic_plan`。

## Agentic Retrieval 通用工具层已落地，仍需继续压缩旧 baseline 语义（2026-05-15 记录，2026-05-25 更新）

**问题：** 设计方案要求 Agentic Retrieval 暴露 `search/find/open/summarize` 四类通用工具。主工具层已经落地，但旧 hand-written baseline 和历史 trace 中仍存在旧工具名/旧语义，容易和新 OpenAI Agent 工具层混淆。

**最佳方案：** `retrieval_tools.py` 作为唯一通用工具注册表：`search` 组合 PG deterministic + Milvus 多集合语义召回并追溯为 chunk pool；`find` 在已知 evidence/chunk 内定位；`open` 按 evidence/chunk/candidate 打开证据并支持 neighbor window；`expand` 基于 node/edge/chunk/finding seed 走 PG graph；`summarize` 压缩候选池或已打开证据；`rerank` 统一走外部 reranker。

**当前方案：** 通用 `RetrievalToolRegistry` 已暴露 `search/scoped_search/find/open/expand/summarize/rerank`。`open` 支持 `chunk_ids + include_neighbors`，`expand` 支持 `seed_node_ids / seed_edge_ids / seed_chunk_ids / seed_finding_ids / relation_filters / hop_limit`，`summarize` 已从占位信号升级为可读的候选/证据摘要。剩余问题是旧 baseline 路径、历史日志和部分文档仍保留旧工具名。

**影响范围：** OpenAI Agent 主链路已经能使用清晰工具协议；旧 baseline 仍可能让调试人员误判当前正式链路。

**整改条件：** 清理或明确标注旧 hand-written baseline-only 工具名；Langfuse / trace 输出统一展示新工具协议字段；补齐真实 replay 下的 agent tool sequence snapshot。

**优先级：** P2。

## LLM Candidate Judge 已接入，但调用预算和 top-K 预筛仍需优化（2026-05-15 更新）

**问题：** LLM Candidate Judge 已进入 Agentic Retrieval 链路，可以判断候选是否真正回答 query，并能把区域归属边、无关 mentions、主题漂移候选判为 drop。但最新真实回放显示，普通 query 仍可能出现 `controller -> judge -> controller -> judge -> stop controller` 这类过度调用，且一次 judge 会裁判 30 个宽召回候选，导致单 case 耗时接近 1-2 分钟。

**最佳方案：** 普通 query 默认最多 1 次 LLM Controller + 1 次 LLM Candidate Judge，但这只是默认预算，不是硬性上限。Candidate Judge 只处理程序预筛后的 top 10-15 个 Candidate Package；如果 judge 后已有足够 keep evidence，系统自动 open 核心 evidence，并由程序自动 stop。只有证据不足、候选冲突、Anchor 覆盖不足、关系意图未覆盖、打开 evidence 后仍缺口明显，或 Context Purity 不达标时，才允许第二轮 LLM Controller/Judge。

**当前方案：** 已接入 `LLMCandidateJudge` 和 `LLMAgenticRetrievalStrategy`，并把 LLM request/response 写入纯文本 trace。Query Context 组装阶段已调整为保留 Agentic 阶段真实 judgement，不再用 deterministic judgement 覆盖 trace。但 top-K 预筛、自动 open、自动 stop 和普通 query LLM 调用预算还未完整产品化。

**影响范围：** 相关性已经明显改善，能降低无关 evidence/node/edge 混入；但成本和延迟不可接受，且多轮 search/judge 可能带来不必要的候选扩散。真实库回放和人工调试会受慢查询影响。

**整改条件：** 实现候选预筛 top-K、LLM 调用预算、质量门槛续跑、Working Set 自动 open/stop、trace 中记录 `llm_calls_used` / `judge_top_k` / `auto_action` / `continue_reason`，并补充 `test_agentic_retrieval_auto_open_stop.py`、`test_llm_candidate_judge_top_k.py`、真实回放耗时基线。

**优先级：** P1。

## Agentic Retrieval 停止条件仍过度依赖 LLM Controller（2026-05-15 记录）

**问题：** 最新 trace 中，第一轮 judge 已经找到足够回答 query 的高置信事件后，Controller 仍继续发起第二轮 search；最终 stop 也需要再调用一次 LLM Controller。这个流程在语义上可解释，但工程上浪费调用，并且显著拉长耗时。

**最佳方案：** Working Set 应有程序化停止判断：当 keep evidence 数量、Anchor coverage、relation intent 覆盖、opened evidence 状态和噪声指标都达标时，直接自动 stop。证据足够但尚未 open 时，自动 open 核心 evidence，而不是请求 LLM Controller 决策。

**当前方案：** LLM Controller 可以输出 search/open/stop，但自动 open/stop 状态机尚未完整实现。当前 trace 已能暴露 controller_duration_ms、judge_duration_ms 和每轮决策原因，方便定位多余调用。

**影响范围：** 普通 query 会变慢；LLM 成本增加；多余 search 还可能引入新的噪声候选，增加 judge 成本和上下文污染风险。

**整改条件：** 在 Agentic Retrieval Loop 中增加 `auto_open_if_sufficient_evidence` 和 `auto_stop_if_context_sufficient`，并将自动动作写入 trace。

**优先级：** P1。

## Evidence Chunk 只有单片段索引，缺少父文档和相邻片段上下文扩展（2026-05-14 记录）

**问题：** 当前 evidence chunk 生成仍是第一版简化实现：一条 evidence 基本只生成一个 `kg_chunk:{evidence_id}:0`，内容由标题、来源、实体提示和 evidence content/payload 拼接而成。这样暂时绕开了“同一文档被切成多个 chunk 后相邻上下文丢失”的问题，但没有真正解决长文档检索的上下文问题；长新闻会出现语义稀释，未来一旦改成多 chunk，也没有 sibling chunk / parent evidence / document summary 的回读机制。

**最佳方案：** 建立多层 chunk 体系：文档级 summary chunk 用于整篇材料召回，片段级 passage chunk 用于精细语义召回，实体/关系索引 chunk 用于结构化召回。命中任一 chunk 后，应能回读父 evidence、相邻 chunk、相关 node/edge 和必要 Wiki 摘要，并在 Query Context 中按预算合并输出。

**当前方案：** 当前 `kg_evidence_chunks` 和 Milvus hybrid index 主要以 evidence 为单位生成单个检索 chunk；`chunk_read` 根据 evidence_id 回读整条 evidence。这个方案可以跑通链路，但它不是成熟的 chunk window / parent document retrieval 设计。

**影响范围：** 对短文本和结构化信号影响较小；对长新闻、公告、研报摘要和多段材料，可能出现两个问题：一是大 chunk 语义被无关内容稀释，导致召回不准；二是未来细粒度切分后，如果没有相邻片段扩展，可能召回到局部片段但缺少完整上下文，或者目标内容在相邻片段中而没有被召回。

**整改条件：** 在“检索与 Query Context”技术方案中补充 chunk 层级设计，并改造 evidence chunk schema、Milvus payload、检索 runtime 和 `chunk_read`：支持 `document_id`、`chunk_index`、`parent_evidence_id`、`prev/next` 或等价顺序字段；检索命中后支持 parent + sibling expansion；配套增加长文档真实库回放测试。

**优先级：** P1。

## 检索召回缺少通用相关性重排，容易混入语义相似噪声（2026-05-14 记录）

**问题：** 当前 `deterministic_plan` 检索链路会融合 `entity_resolve`、`semantic_hybrid_search`、`graph_search`、`wiki_search`、`chunk_read` 的结果，但缺少一个通用的二阶段相关性重排/裁判层。真实回放中，查询“俄就波法联合军演发出警告：欧洲对俄全面对抗正在回归”时，结果能命中目标新闻，但也会混入“固态电池政策支持带动宁德时代产业链预期”“宁德时代”等语义相似但业务无关的 demo/CATL 内容。

这说明当前系统已经完成“数据进入知识图谱的组织方式”和“写入治理”，但检索侧还没有完成从多通道 RAG 到 KG-RAG 的关键跃迁。当前链路更接近：`Raw Data -> Source Record -> LLM/规则抽取 -> Node/Edge/Evidence 入库 -> Wiki/Milvus/图邻接索引 -> 多通道 RAG 召回`。图谱目前更多在写入和上下文组织阶段发挥作用，还没有在检索阶段形成足够强的约束和裁判能力。

**最佳方案：** 保持第一阶段多通道宽召回，但在进入最终上下文前增加通用候选重排层。重排层应基于 query、候选 evidence、node、edge、wiki、图谱路径和证据文本做统一评分，判断候选是否真正回答当前问题；必要时由 LLM 参与 top-K 候选裁判，但不能在通用知识库核心层硬编码金融表名、`ft_news:*` 这类 source_id 规则。

目标检索链路应调整为：`多通道召回 -> 候选归并 -> Query Anchor 识别 -> 候选 evidence/node/edge 相关性裁判 -> 保留相关候选 -> 从相关 anchor 做图谱扩展和证据回读 -> Query Context`。其中 Query Anchor 需要识别 query 的核心事件、实体、时间、主题和关系意图；候选裁判需要判断候选是否覆盖核心事件、是否共享关键实体、是否只是语义相似但主题偏移、是否能解释当前问题。

**当前方案：** 目前检索阶段主要是确定性 planner + Milvus 语义/BM25 + 图谱扩展 + Wiki/Chunk 读取；LLM 主要参与写入阶段的实体、事件、关系抽取，不参与 `deterministic_plan` 的候选相关性裁判。`semantic_hybrid_search` 是全库相似召回，只要向量或 BM25 认为片段相似，候选就可能进入结果；`chunk_read` 又会根据 evidence_id 回读 evidence，并通过 evidence 关联的 edge 带出 node，导致无关 evidence 一旦进入候选，就可能放大成无关实体和关系。为了避免破坏通用知识库边界，本次没有把 `ft_*` source_id 正则过滤写入通用 runtime。

**影响范围：** 在生产数据量较大、存在 demo/历史/相似主题噪声时，检索上下文可能包含无关 evidence、node 和 edge，进而影响后续问答、解释、投研结论生成和质量评估。该问题不会导致目标 evidence 完全不可检索，但会降低上下文纯度。

**整改条件：** 需要先补充“候选重排/裁判”设计与技术方案，再实现可插拔 reranker。第一版可先做确定性特征重排；第二版接入 LLM rerank/judge，只对 top-K 候选做低成本判断；后续如果调用方需要强约束，应通过结构化 filter 参数传入，而不是从自然语言 query 中写死解析某类业务 source_id。

**优先级：** P1。

## 原子 Card 请求输出膨胀会阻塞整批编译（2026-07-14 记录）

**问题：** `--limit 5` 真实回放中，部分短新闻的 `kg_cognitive_card` 请求超过 120 秒，个别输出达到 8623 tokens 后仍未通过 Schema，需要再次修复。当前批量提取使用 `asyncio.gather`，任一请求长时间不返回会使整批 Card 无法持久化；强制终止后还会留下 Evidence/Chunk 和 180 秒 Redis 锁 TTL。

**最佳方案：** 单条 Card 提取应设置与业务 SLA 匹配的输出上限和请求超时；批处理应按 Chunk 独立提交结果、隔离失败并保留明确重试状态，不能让一个异常输出阻塞整批。Schema 修复应限制在较小输出预算，并记录首次失败原因、修复结果和最终状态。

**当前方案：** Card 与 Probe 默认关闭思考模式，并预留 20000 output tokens；正常路径保持一次 Cards-first 业务调用和一次同会话 Probe 追问。未显式指定模型时，根据输入 Ref 数量和正文字符数执行确定性分级：简单输入使用 `deepseek-v4-flash`，复杂输入使用 `deepseek-v4-pro`，同一 Chunk 的 Card 与 Probe 固定使用同一模型；显式 `model` 覆盖会关闭动态路由。不同模型、厂商和思考模式使用相互隔离的前缀预热状态。DeepSeek 返回 `length` 或空正文时只允许一次携带上一轮完整 `reasoning_content` 和已有正文的 Prefix Completion，禁止同参数完整重试；续写再次截断时，Gateway Schema repair 和 Card 业务 repair 都会停止，避免继续放大 Token。验证脚本已按 Chunk 隔离超时和失败，并输出每条 Chunk 的路由等级与实际模型。2026-07-20 使用最新 20 条新闻真实 A/B：15 条简单输入使用阿里云 Flash 后，该子集估算费用由全 Pro 的 0.110 元降至 0.046 元，但模型累计耗时仅由 172.7 秒降至 166.5 秒；5 条复杂输入仍贡献绝大部分输出和费用。复杂长文 `ft_news:109551`、`ft_news:109552` 单次可生成 70 至 79 张 Card，且相同 Pro 配置重跑时 `109552` 从 38 张波动到 70 张，说明路由只降低简单输入成本，尚未解决长文过拆和随机输出膨胀。Flash 还出现每张 Card 强行生成 Probe，以及把一条白银行情拆成“跌幅”和“报价”两张 Card 的质量回退。模型偶发输出 `[s0001]` 形式时会在领域入口做通用 Ref 格式归一化，不再为纯格式差异触发 LLM 修复。前缀预热 Owner 异常退出后，等待者会在锁过期后重新竞争；生产持久化阶段仍需继续验证部分 Chunk 成功、部分失败时的任务恢复语义。

**整改条件：** 建立包含短讯、列表型长文和因果分析长文的固定评测集，分别约束 Card 原子性、Probe 有效率、同 Chunk Relation precision 和重跑方差；只有 Flash 在简单集达到不低于 Pro 的质量门槛后才能继续扩大简单路由范围。复杂长文需要从抽取目标和提示词结构上抑制“每个数字、每个短语各建一张 Card”，不能依赖更高输出预算兜底。生产链路还需将提取结果改成 per-chunk success/failure envelope，分批持久化成功项并把失败项交给 jettask 重试，并补充超时、超长输出、修复失败和进程中断恢复测试。

**优先级：** P1。
