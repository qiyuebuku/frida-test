# 金融知识图谱实施方案 · 总览

> **文档定位**：这是一份承接 `5. 设计方案/1. 金融知识图谱/1. 金融知识图谱构建设计方案.md` 的实施总览。  
> 它的作用不是替代设计文档，而是把“应该做什么”转成“按什么顺序落地、每一阶段要产出什么、如何验收”。  
> 这份文档是 `3. 实施方案/4. 金融知识图谱/` 目录下的第一个文档，后续可以继续拆成 DDL、V0 冷启动、KG compiler、GraphRAG 接入、质量治理等多个实施子文档。

---

## 0. 一句话说清楚

> **金融知识图谱的实施，不是一次性把图谱做完，而是按“GraphRAG 接入预检 → 地基冻结 → V0 冷启动 → 增量编译 → 双索引导出 → 下游接入 → 质量闭环”七个阶段推进。**

实施过程中的核心原则只有一条：

> **先把事实层和协议做对，再接查询层和下游消费层。**

---

## 1. 这份实施方案解决什么

设计文档已经明确了：

- 金融知识图谱是 L1/L2/L3 之前的前置地基
- 事实层采用 PostgreSQL
- 生产查询目标能力采用 Microsoft GraphRAG BYOG
- graphify 作为本地调试、Wiki、MCP、路径查看工具
- completion 通过统一 LLM 代理层接入
- embedding 通过统一 LLM 代理层的 `/v1/embeddings` 接入项目 `.env` 中配置的远程 Qwen3-Embedding 服务
- LLM 代理层主路径为真实 Claude CLI tmux 会话池，`claude -p` 已因 429 风控弃用
- GraphRAG 长 prompt 通过任务文件 + Claude `Read` 工具处理，避免直接完整粘贴进 TUI
- A-RAG 的核心思想以“混合召回协议”形式吸收，不在当前阶段引入 Milvus

因此实施阶段真正要解决的是：

1. **先落什么，后落什么**
2. **哪些内容必须一次定死**
3. **哪些内容可以延后细化**
4. **每一阶段的产物和验收标准是什么**

---

## 2. 实施范围

当前 `金融知识图谱` 实施专题，建议覆盖以下 6 类内容：

1. **事实层实施**
   - `kg_nodes`
   - `kg_edges`
   - `kg_edge_evidence`
   - `kg_build_runs`
   - `kg_communities`
   - `kg_wiki_pages`

2. **V0 冷启动实施**
   - 股票、行业、概念、基金持仓、宏观指标、政策机构词表入图

3. **KG compiler 实施**
   - 结构化事实编译
   - 文本关系候选编译
   - evidence / confidence / version 协议落库

4. **双索引导出实施**
   - Microsoft GraphRAG parquet
   - graphify JSON / Wiki / MCP
   - PostgreSQL FTS
   - PostgreSQL `pgvector` 语义召回基线
   - keyword / semantic / graph / chunk_read 四类召回能力
   - RRF / 去重 / token budget
   - `retrieval_context_builder`

5. **下游接入实施**
   - L1 事件抽取接 KG
   - L2 主线识别接 KG
   - L3 决策打分接 KG

6. **质量治理实施**
   - 歧义边复核
   - 社区质量监控
   - 增量与全量校准

## 3. 不在第一阶段实施范围内的内容

为了避免实施时范围失控，下面这些内容不应作为第一阶段阻塞项：

1. **Neo4j / 图数据库迁移**
2. **专用向量库引入**
   - 包括 Milvus；当前只吸收 hybrid search / RRF 思想，不引入新存储
3. **完整覆盖所有金融资产和所有关系类型**
4. **一开始就做完所有 L1/L2/L3 重构**
5. **一开始就做完所有 GraphRAG query tuning**

第一阶段只需要证明：

- 事实层稳定
- 编译链条可重放
- 可以导出 GraphRAG / graphify
- L1/L2 能围绕这套事实层开始重构

## 4. 总体实施顺序

建议按 7 个阶段推进。

### Pre-Phase：GraphRAG 接入预检

目标：

- 在大规模实施事实层之前，先确认 Microsoft GraphRAG 能否按预期接入当前系统
- 先验证 LLM 代理层、BYOG workflow、查询链路这几个高风险点

为什么这一步要提前：

1. `5. 设计方案/1. 金融知识图谱/1. 金融知识图谱构建设计方案.md` 已经明确：
   - 生产查询目标能力采用 Microsoft GraphRAG BYOG
   - GraphRAG 前期就纳入系统设计
2. 当前 LLM Proxy 已经通过真实 Claude CLI tmux 会话池跑通，并提供 OpenAI-compatible completion / embedding 接口。
3. 如果 GraphRAG 对接方式、completion provider、GraphRAG 自身 embedding 能力边界存在阻塞，越晚发现，后面的事实层实施越容易返工。

这一阶段不追求做完知识图谱，只做技术预检。

预检内容：

1. **LLM 代理层可用性**
   - `GET /api/llm-proxy/health`
   - `POST /v1/chat/completions`
   - 验证结构化输出、超时、基础稳定性

2. **GraphRAG completion 接入**
   - 验证 GraphRAG 能通过当前代理层调用 completion
   - 确认 OpenAI-compatible 接口映射可用
   - 确认长 prompt 会走任务文件 + `Read`，不直接塞进 Claude TUI

3. **BYOG 最小样例**
   - 人工构造极小 `entities / relationships / text_units`
   - 跑通最小 GraphRAG workflow

4. **查询模式预检**
   - 至少验证 community reports
   - 至少验证一条 Local / Global 查询链路

5. **GraphRAG embedding 能力边界确认**
   - GraphRAG embedding 不使用 mock
   - 通过 `/v1/embeddings` 复用 `.env` 中的 `EMBEDDING_URL / EMBEDDING_DIM`
   - 确认 Global / Local / Basic / DRIFT 对 embedding 的具体依赖和启用条件

产出：

- GraphRAG 接入预检记录
- completion 接入方式确认
- GraphRAG embedding 能力边界确认
- BYOG 最小样例跑通结论

验收：

- 能通过代理层成功完成一次 GraphRAG completion 调用
- 能用最小 parquet 样例跑通 BYOG workflow
- 能明确当前哪些 GraphRAG 能力已可接入，哪些仍依赖后续实现
- 能说明 GraphRAG completion 的性能瓶颈、上游 429 风险和代理层 502 包装问题

边界：

- 这一步**不是**正式构建金融知识图谱
- 这一步**不是**替代 Phase 0 的 ontology / DDL 冻结
- 它的定位是：**先把 GraphRAG 技术接入风险前置验证掉**

当前实测补充：

- `graphrag==3.0.9` 临时环境已可运行。
- completion 已能通过 `/v1/chat/completions` 调用 tmux pool。
- embedding 已能通过 `/v1/embeddings` 调用远程 Qwen3-Embedding，返回 1024 维真实向量。
- GraphRAG 默认 workflow 已能完成 index，并生成 entities / relationships / communities / community_reports / lancedb。
- Global / Local / Basic 查询已跑通；Local 查询已验证长 prompt 任务文件策略。
- DRIFT 能启动并调用真实 embedding，但默认链路过重，暂不作为第一阶段生产验收标准。
- `pool_size=10` 可启动，但上游 GLM-5.1 会在多会话并发下出现 429，需要后续做限流和错误码治理。

### Phase 0：地基冻结

目标：

- 冻结 ontology
- 冻结 `node_id` / `relation_type` 规则
- 冻结 evidence / confidence / version 协议
- 冻结 PostgreSQL 事实层 schema
- 冻结混合召回协议：`keyword_search` / `semantic_search` / `graph_search` / `chunk_read`
- 冻结 `retrieval_context_builder` 的输入输出边界

产出：

- DDL 初版
- 节点类型清单
- 关系类型清单
- 证据与版本字段定义
- 混合召回协议说明
- `retrieval_context_builder` 职责边界说明

验收：

- 能回答“哪些边可以硬用，哪些只能加权，哪些只能提示”
- 能回答“什么是事实源，什么是可重建索引”
- 能回答“GraphRAG、关键词、语义、图路径、原文精读分别在查询链路里承担什么职责”

### Phase 1：V0 冷启动

目标：

- 构建第一版静态事实图
- 为 L1 提供稳定实体词表和基础连接关系

优先数据：

- 股票基础信息
- 行业映射
- 概念成分股
- 基金持仓
- 宏观指标
- 政策 / 监管机构词表

产出：

- 第一版 `kg_nodes`
- 第一版 `kg_edges`
- 第一版 `kg_edge_evidence`

验收：

- 股票可追到行业
- 股票可追到概念
- 基金可追到持仓股票
- 所有基础边有来源

### Phase 2：KG compiler 落地

目标：

- 把“图谱构建”从手工脚本变成一条正式 compiler pipeline

核心步骤：

1. entity normalization
2. node identity resolution
3. deterministic relation compile
4. textual candidate extraction
5. evidence attach
6. confidence scoring
7. ontology validation
8. upsert facts

产出：

- 结构化事实编译器
- 候选关系编译器
- 统一 upsert 入口

验收：

- 同一实体不会反复漂移出多个 `node_id`
- 结构化事实不经过 LLM 重判
- 文本候选边必须带 evidence

### Phase 3：双索引与混合召回

目标：

- 同一份事实层能稳定导出到不同查询层
- 同一条查询能从 GraphRAG、关键词、语义、图路径和原文精读多路召回候选
- 用统一融合协议把候选压缩成有限上下文，避免单次向量 Top-K 成为瓶颈

导出对象：

1. **GraphRAG BYOG**
   - `entities.parquet`
   - `relationships.parquet`
   - `text_units.parquet`

2. **graphify**
   - `graph.json`
   - `wiki/`
   - `GRAPH_REPORT.md`
   - MCP 可查询图

3. **检索索引**
   - PostgreSQL FTS
   - PostgreSQL `pgvector`
   - 结构化字段精确匹配

4. **混合召回层**
   - `keyword_search`
   - `semantic_search`
   - `graph_search`
   - `chunk_read`
   - RRF / weighted merge / dedupe
   - token budget 控制
   - `retrieval_context_builder`

验收：

- 同一事实层能同时导出 GraphRAG 和 graphify
- 导出产物可删除并重建
- graphify 能本地查邻居、路径和子图
- keyword / semantic / graph 三路候选能被统一融合
- `retrieval_context_builder` 能输出带证据、带来源、受 token budget 控制的上下文
- 不依赖 Milvus 也能跑出 A-RAG 思想下的最小混合召回闭环

### Phase 4：事件图谱接入

目标：

- 让 L1 产出的事件不再是孤立记录，而是图上的动态事实

核心动作：

- `ft_events` -> `event` 节点
- `event_affects_stock`
- `event_affects_industry`
- `event_relates_to_concept`
- `event_supported_by_doc`

产出：

- 事件增量更新链路
- `kg_incremental_update`

验收：

- 新事件入库后可展开为子图
- 可从事件回链到新闻证据
- 新概念能以候选方式进入图谱

### Phase 5：GraphRAG / 下游接入

目标：

- GraphRAG 开始消费这套图
- L1/L2/L3 开始围绕这套图重构

具体包括：

1. GraphRAG BYOG workflow
2. community reports
3. Local / Global / DRIFT 基础验证
4. 混合召回上下文接入 GraphRAG / L2 / L3
5. L1 输出升级为图谱感知事件
6. L2 改为图社区 / 路径强度主导
7. L3 接多跳路径打分

验收：

- GraphRAG 查询链路跑通
- `retrieval_context_builder` 能作为 L2/L3 的共同检索入口
- L2 能利用图路径而不是只靠标签重叠
- L3 能拿到 `event -> concept -> stock -> fund` 路径

### Phase 6：质量闭环

目标：

- 让图谱从“能跑”变成“可维护”

内容：

- 每日盘后全量校准
- AMBIGUOUS 边复核清单
- 社区质量巡检
- 孤立节点、超级概念、虚假因果监控
- 反馈写回 alias / rejected / weight 调整

验收：

- AMBIGUOUS 边比例下降
- 社区稳定性提升
- 路径可解释率提升

## 6. 每一阶段的依赖关系

实施时不能并行乱做，依赖顺序应固定：

```text
Pre-Phase GraphRAG 接入预检
  -> Phase 0 地基冻结
  -> Phase 1 V0 冷启动
  -> Phase 2 KG compiler
  -> Phase 3 双索引与混合召回
  -> Phase 4 事件图谱接入
  -> Phase 5 GraphRAG / L1 / L2 / L3 接入
  -> Phase 6 质量闭环
```

特别说明：

- **Phase 0 没冻结，不要开始大规模编码**
- **Pre-Phase 没完成，不要默认 GraphRAG 接入细节已经没风险**
- **Phase 1 没完成，不要让 L1 直接依赖临时字符串实体**
- **Phase 2 没稳定，不要急着做复杂 GraphRAG query tuning**

---

## 7. 当前建议的最近实施顺序

结合你现在的文档和代码状态，我建议近期优先顺序是：

1. **先做 GraphRAG 接入预检**
   - 利用当前已经跑通的 LLM 代理 API
   - 先确认 GraphRAG completion / BYOG / 最小查询链路可行

2. **再补 Phase 0 文档**
   - 把 DDL、ID 规则、证据协议写死

3. **再补 Phase 1 文档**
   - 明确 V0 冷启动到底从哪些表入图

4. **再补 Phase 2 文档**
   - 把 KG compiler 变成可编码的实施说明

5. **最后再写 GraphRAG / graphify 导出与混合召回实施**
   - 因为预检解决的是“能不能接”，不是“正式数据怎么导”

换句话说：

> **金融知识图谱的正式建设仍然从事实层 schema 和 V0 冷启动开始，但在这之前，应先做一次 GraphRAG 技术接入预检。**

## 9. 最终结论

金融知识图谱不适合继续作为一个单独设计文件被引用，它已经是一个独立专题，实施上也应该有自己的专题目录。

因此在 `3. 实施方案` 下建立：

- `4. 金融知识图谱/`

是合理的，后续也应沿着这个目录继续细分多个实施阶段文档。

当前这份文档的结论很简单：

> **先立专题，再按阶段拆文档；先做 GraphRAG 接入预检，再冻结事实层地基；先做 V0 冷启动，再做正式导出和下游接入。**
