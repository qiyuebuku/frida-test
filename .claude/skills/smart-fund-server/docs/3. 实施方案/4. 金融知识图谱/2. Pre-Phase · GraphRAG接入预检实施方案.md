# Pre-Phase · GraphRAG接入预检实施方案

> **文档定位**：这份文档不是正式构建金融知识图谱的实现说明，而是正式建设开始前的技术预检文档。  
> 它要解决的问题只有一个：**在投入事实层、KG compiler、V0 冷启动之前，先确认 Microsoft GraphRAG 能按当前架构稳定接入。**

---

## 0. 一句话说清楚

> **Pre-Phase 的目标不是建图，而是把 GraphRAG 接入风险前置暴露出来，并在正式实施前确认 completion、BYOG、query workflow 和 GraphRAG 自身 embedding 能力边界没有方向性阻塞。**

---

## 1. 为什么这一步必须放在前面

`5. 设计方案/1. 金融知识图谱/1. 金融知识图谱构建设计方案.md` 已经明确：

1. **GraphRAG 前期即纳入系统设计**
2. **生产查询目标能力采用 Microsoft GraphRAG BYOG**
3. **completion 通过统一 LLM 代理层接入**
4. **embedding 通过统一 `/v1/embeddings` 接入真实远程 Qwen3-Embedding 服务**

这意味着，如果不先做 GraphRAG 接入预检，后面会有三类高概率返工：

1. **completion 接口对不上**
   - 代理层虽然能单独调用，但 GraphRAG 实际接入时可能存在协议差异

2. **BYOG workflow 理解偏差**
   - `entities / relationships / text_units` 的最小字段、格式和调用顺序如果理解错了，后续导出层会返工

3. **GraphRAG embedding 能力边界未定**
   - Local / DRIFT / Basic Search 对 embedding 的依赖如果没有提前确认，后面查询层设计会失真

所以这一阶段的定位很明确：

> **不是提前写业务代码，而是提前验证技术前提。**

---

## 2. 预检范围

这一阶段只覆盖下面 5 件事：

1. **LLM 代理层可用性确认**
2. **GraphRAG completion 接入确认**
3. **BYOG 最小样例跑通**
4. **community reports / Local / Global 最小查询链路验证**
5. **GraphRAG embedding 能力边界确认**

不在本阶段范围内的内容：

1. 金融 ontology 设计细化
2. PostgreSQL 事实层 DDL 落地
3. V0 冷启动正式建图
4. KG compiler 正式编码
5. L1/L2/L3 正式迁移

---

## 3. 当前已知前置条件

结合当前项目状态，以下条件已经具备：

1. **统一 API 服务已启动**
   - `python -m src.interfaces.cli.main api`

2. **LLM 代理层健康检查已通过**
   - `GET /api/llm-proxy/health`

3. **OpenAI-compatible completion 接口已打通**
   - `POST /v1/chat/completions`

4. **代理层已支持硬隔离沙盒**
   - `hard sandbox`
   - 不依赖项目工作目录上下文
   - 不读取持久化会话作为正式输入

5. **代理层已支持 GraphRAG 长 prompt 文件化**
   - 超过阈值后写入 `/tmp/smart-fund-claude-proxy/request-contexts/*.md`
   - Claude TUI 中只发送短指令
   - Claude 使用 `Read` 工具读取任务文件
   - 不再向 Claude 声明“OpenAI-compatible API 后端”或“纯 LLM 后端”

6. **真实 embedding 已接入**
   - `/v1/embeddings` 底层复用 `.env` 的远程 Qwen3-Embedding 服务
   - 返回维度为 `EMBEDDING_DIM=1024`
   - T0 不使用 mock embedding

也就是说，这个阶段不是从零开始，而是：

> **以已经可用的 LLM 代理层为基础，继续验证 GraphRAG 能否把它当成正式 completion provider 使用。**

---

## 4. 预检目标

Pre-Phase 完成后，必须明确回答下面 6 个问题：

1. **GraphRAG 能否通过当前代理层稳定调用 completion**
2. **GraphRAG 需要的 completion 协议细节有哪些额外要求**
3. **BYOG 最小样例是否能按当前理解跑通**
4. **community reports 能否成功生成**
5. **Local / Global 至少各有一条查询链路能跑通到可读结果**
6. **GraphRAG 所需 embedding 能力当前如何处理**
7. **GraphRAG 长 prompt 是否能稳定进入 Claude Code agent 形态**

如果这些问题里有任何一个答不清，就不应该进入 Phase 0 和 Phase 1 的正式建设。

当前阶段性结论：

| 问题 | 当前结论 |
|---|---|
| completion 怎么接 | 走 LLM Proxy `/v1/chat/completions`，主 backend 为 Claude CLI `tmux_pool` |
| `claude -p` 是否保留 | 不作为主路径，经测试当前 GLM-5.1 路线会触发 429 |
| 长 prompt 怎么处理 | 走任务文件 + Claude `Read`，避免完整粘贴进 TUI |
| embedding 是否 mock | 不 mock，走 `/v1/embeddings` + 远程 Qwen3-Embedding |
| pool 是否可扩大 | `pool_size=10` 可启动，但要受上游 429 限制 |
| 502 如何理解 | 多数是代理层包装后端失败，不等价于 Claude 或 GraphRAG 原生 502 |

---

## 5. 分阶段预检内容

### 5.1 Step A：Completion 接入预检

目标：

- 确认 GraphRAG 能把当前代理层当成可用的 completion provider
- 确认 GraphRAG 长 prompt 能走任务文件 + `Read`

要验证的点：

1. GraphRAG 配置是否能指向当前代理层
2. 请求协议是否与当前 `/v1/chat/completions` 对齐
3. 结构化输出是否会被 GraphRAG 正常消费
4. 超时、重试、并发限制是否需要额外适配

验收：

- GraphRAG 能成功发出至少一次 completion 请求
- 代理层日志中能看到来自 GraphRAG 的请求
- 响应内容能被 GraphRAG workflow 正常继续消费
- Claude JSONL 中不再出现旧的 `OpenAI-compatible` / `纯 LLM 后端` 提示词

说明：

- 这一步不要求结果质量已经很好
- 只要求调用链路真实可用

### 5.2 Step B：BYOG 最小样例预检

目标：

- 确认当前对 GraphRAG BYOG 输入结构的理解正确

建议的最小样例规模：

- `entities`：3 到 8 个节点
- `relationships`：3 到 10 条边
- `text_units`：2 到 5 段文本

建议样例内容：

1. 一个政策或新闻事件
2. 一个概念
3. 两到三个股票
4. 一到两个文本证据

这里不要追求金融覆盖，只追求：

- 字段正确
- workflow 能跑
- 结果可观察

验收：

- 最小 parquet 输入能被 GraphRAG 接受
- 能生成 community 或 report 相关产物
- 不存在因为字段理解错误导致的系统性失败

### 5.3 Step C：查询链路预检

目标：

- 验证 GraphRAG 不是只能索引，至少能做最小查询

本阶段建议最低要求：

1. **community reports 可生成**
2. **Global Search 至少完成一条查询**
3. **Local Search 至少完成一条查询**

如果 DRIFT Search 成本较高，可以放到本阶段后半段确认，但不能完全不看。

建议验证问题：

1. “当前图里最主要的主题是什么”
2. “某个概念和哪些股票相关”
3. “某个事件为什么会影响某个概念”

验收：

- 至少能得到一条不是报错、不是空结果的 Global 查询结果
- 至少能得到一条可读的 Local 查询结果
- 结果可以回链到实体、边或文本证据

### 5.4 Step D：GraphRAG embedding 能力边界确认

目标：

- 明确哪些 GraphRAG 能力需要 embedding
- 明确 GraphRAG 不使用 mock embedding，而是通过 LLM Proxy 的 `/v1/embeddings` 接入 `.env` 中配置的远程 Qwen3-Embedding 服务
- 明确 GraphRAG 当前需要确认的是 embedding 服务可用性、维度一致性、batch/timeout 配置和查询模式启用条件

这一节必须形成明确结论，不能只写“后续再看”。

要输出的判断：

1. completion 使用当前 LLM Proxy（主 backend 为交互式 `tmux + Claude CLI`）
2. embedding 使用当前 LLM Proxy 暴露的 OpenAI-compatible `/v1/embeddings`，底层复用 `EMBEDDING_URL`
3. 第一阶段先支持哪些 query mode
4. 哪些 query mode 依赖 GraphRAG embedding 能力才能正式启用

验收：

- 形成一份明确的能力边界结论
- 不再把这件事留到 Phase 3 之后才讨论

---

## 6. 推荐的执行顺序

Pre-Phase 内部顺序建议固定：

```text
先验证代理层健康
  -> 再验证 GraphRAG completion 接入
  -> 再跑 BYOG 最小样例
  -> 再验证 community reports / Global / Local
  -> 最后确认 GraphRAG embedding 能力边界
```

不要反过来做。原因很简单：

- completion 没通，后面所有 GraphRAG workflow 都没有意义
- BYOG 样例没通，正式导出设计就没有可信基础
- GraphRAG embedding 能力边界没定，查询模式规划就会失真

---

## 7. 本阶段产物

完成 Pre-Phase 后，至少应有下面这些产物：

1. **GraphRAG 接入记录**
   - 记录 completion provider 接法
   - 记录成功与失败点

2. **最小 BYOG 样例**
   - 可以重复执行
   - 可以作为后续导出联调样例

3. **查询链路验证记录**
   - community reports
   - Global Search
   - Local Search

4. **GraphRAG embedding 能力边界记录**
   - 说明 `/v1/embeddings` 已接入 `.env` 配置的 embedding 服务
   - 说明远程 embedding 服务不可用时 GraphRAG Local / Basic / DRIFT 不允许进入生产验收
   - 说明哪些查询模式暂时启用，哪些后续启用

5. **LLM 代理层稳定性记录**
   - 说明 `pool_size=10` 只是本地会话池能力，不代表上游无限并发
   - 说明上游 `429 code=1302` 已实测出现
   - 说明 HTTP 502 可能是代理层包装后端失败，需要后续错误码细分
   - 说明长 prompt 必须使用文件上下文策略

6. **问题清单**
   - 哪些是已解决问题
   - 哪些是进入 Phase 0 前必须关闭的问题

---

## 8. 通过标准

只有满足下面这些条件，Pre-Phase 才算通过：

1. **GraphRAG 能通过当前代理层完成真实 completion 调用**
2. **最小 BYOG 样例能跑通**
3. **community reports 至少一次成功生成**
4. **Global / Local 至少各有一条查询成功**
5. **GraphRAG embedding 能力边界已明确**
6. **长 prompt 文件上下文策略已被 GraphRAG 查询链路验证**
7. **没有发现会推翻现有 KG 设计方向的基础性阻塞**

如果只验证了 health 接口和普通 completion，而没有验证 GraphRAG 自身 workflow，这个阶段不能算完成。

---

## 9. 与后续阶段的边界

Pre-Phase 结束后，后续阶段边界应保持清晰：

### 它解决什么

1. GraphRAG 能不能接
2. 怎么接 completion
3. BYOG 最小样例理解是否正确
4. query workflow 大体能不能跑

### 它不解决什么

1. 金融知识图谱正式表结构
2. 正式 node_id 规则
3. 正式 relation_type 清单
4. 正式证据协议
5. V0 冷启动入图范围
6. KG compiler 编译流程细节

这些内容都应该留到：

- `3. Phase 0 · DDL与基础协议实施方案.md`
- `4. Phase 1 · V0冷启动实施方案.md`
- `5. Phase 2 · KG Compiler实施方案.md`

---

## 10. 当前最务实的结论

对于当前项目，Pre-Phase 的价值不是“试试看 GraphRAG”，而是：

> **在大规模开始金融知识图谱实施之前，先确认最关键的外部依赖链条已经具备可落地性。**

当前已经知道：

- 代理层已经跑通
- OpenAI-compatible completion 接口已经可用
- 硬隔离沙盒已经具备
- 真实 embedding 已接入并可被 GraphRAG 使用
- GraphRAG 长 prompt 已确认可以通过任务文件 + `Read` 处理

所以现在最合理的下一步不是继续讨论抽象架构，而是：

> **正式把 GraphRAG 接入预检做完，然后再进入 Phase 0。**
