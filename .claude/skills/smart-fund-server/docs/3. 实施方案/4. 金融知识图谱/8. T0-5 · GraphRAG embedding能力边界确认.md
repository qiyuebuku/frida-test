# T0-5 · GraphRAG embedding能力边界确认

> **任务定位**：这一步不是建设业务侧 embedding 流程，而是明确 GraphRAG 自身能力边界。**

---

## 1. 任务目标

状态：`已完成`

本任务要确认：

1. T0 阶段 GraphRAG embedding 通过 `/v1/embeddings` 接入项目 `.env` 中配置的远程 embedding 服务
2. GraphRAG 哪些查询模式依赖 embedding
3. 当前阶段哪些查询模式可以先启用
4. 哪些能力要放到后续阶段再开启
5. A-RAG 思想下的 `semantic_search` 与 GraphRAG embedding 的边界如何区分

---

## 2. 已经确定的原则

当前原则已经明确：

1. completion 走当前 LLM Proxy（主 backend 为交互式 `tmux + Claude CLI`）
2. embedding 也走当前 LLM Proxy，对外暴露 OpenAI-compatible `/v1/embeddings`
3. `/v1/embeddings` 底层复用 `.env` 中的 `EMBEDDING_URL / EMBEDDING_DIM / EMBEDDING_BATCH_SIZE / EMBEDDING_TIMEOUT`
4. A-RAG 的 `keyword_search / semantic_search / graph_search / chunk_read` 不在 T0 全量实现
5. Phase 3 需要补 PostgreSQL `pgvector` 语义召回基线，并接入 `retrieval_context_builder`

---

## 3. 与 A-RAG 混合召回的关系

本任务只确认 GraphRAG 自身 embedding 能力边界，不等于否定后续业务侧 `semantic_search`。

边界如下：

| 阶段 | embedding 用途 | 是否实施 |
|---|---|---|
| T0 | GraphRAG 官方 workflow 自身所需 embedding | 通过 `/v1/embeddings` 接入远程 Qwen3-Embedding 服务 |
| Phase 3 | `semantic_search` 作为 A-RAG 四类召回能力之一 | 实施 PostgreSQL `pgvector` 基线 |
| 后续扩展 | Milvus / 专用向量库 hybrid search | 仅在 PostgreSQL 方案被证明不足后考虑 |

因此当前结论调整为：

> **T0 不使用 mock embedding；GraphRAG 通过统一代理层复用 `.env` 配置的远程 embedding 服务。Phase 3 再把同一 embedding 能力沉淀到 PostgreSQL `pgvector` 语义召回基线；Milvus 暂不引入。**

当前实测结论：

- `/v1/embeddings` 已返回真实向量，不再使用 mock。
- 向量维度为 1024，与 `EMBEDDING_DIM=1024` 一致。
- GraphRAG index 的 `generate_text_embeddings` 已调用真实 embedding。
- GraphRAG Local / Basic 查询已调用真实 embedding。
- embedding 调用耗时明显低于 completion，不是当前主要性能瓶颈。
- DRIFT 查询会大量使用 embedding 和 completion，能启动但默认链路过重，后续需要单独调优。

---

## 4. 完成标准

满足以下条件才算完成：

1. 不再反复讨论是否复用现有业务 embedding 服务
2. T0 阶段的查询模式启用边界已明确
3. 后续 Phase 3 不再重新定义同一个问题
4. 能说明 GraphRAG embedding、业务 `semantic_search`、Milvus 三者的阶段边界
5. `/v1/embeddings` 可被 GraphRAG / LiteLLM 正常调用，返回维度与 `EMBEDDING_DIM` 一致

验收状态：

> **已完成。T0 阶段 GraphRAG embedding 统一走 `/v1/embeddings`，底层复用远程 Qwen3-Embedding 服务；不再使用 mock。**
