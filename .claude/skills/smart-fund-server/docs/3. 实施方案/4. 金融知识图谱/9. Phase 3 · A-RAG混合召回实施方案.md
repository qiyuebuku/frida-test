# Phase 3 · A-RAG混合召回实施方案

> **任务定位**：本文档承接 `5. 设计方案/1. 金融知识图谱/1. 金融知识图谱构建设计方案.md` 中的 A-RAG 思想修正。  
> 它不是要求当前引入 Milvus，而是把 A-RAG 的多工具、多粒度、混合召回思想落实为本系统 Phase 3 的实施方向。

---

## 1. 一句话说清楚

> **不使用 Milvus 也可以吸收 A-RAG 的核心思想：用 PostgreSQL FTS、pgvector、KG 图查询和原文精读组成四类检索工具，再由 `retrieval_context_builder` 统一融合成有限上下文。**

这里要避免两个极端：

1. 不要退回“单次 embedding Top-K”。
2. 也不要把所有检索决策都交给 LLM 每次临场选择。

本系统采用更稳的工程路线：

```text
问题分类
  -> 多路并行召回
  -> RRF / 去重 / 预算控制
  -> 结构化上下文
  -> GraphRAG / L2 / L3 / agent 消费
```

---

## 2. 当前阶段不引入 Milvus

Milvus 文章的价值在于说明 hybrid search 的工程形态，而不是要求我们现在立刻迁移存储。

当前明确：

| 项 | 决策 |
|---|---|
| 是否当前引入 Milvus | 不引入 |
| 是否吸收 Milvus hybrid search 思想 | 吸收 |
| 第一版混合召回存储 | PostgreSQL FTS + `pgvector` + `kg_*` |
| 第一版融合方式 | 应用层 RRF / weighted merge |
| 未来是否可替换为 Milvus | 可以，但必须保持上层接口不变 |

后续只有在 PostgreSQL 方案被真实证明不足时，才考虑 Milvus：

- 向量规模或并发成为明确瓶颈。
- PostgreSQL FTS + `pgvector` + 应用层 RRF 无法满足召回质量。
- 需要原生 sparse BM25 + dense vector hybrid search。
- 多模态或十亿级语料进入系统。

## 3. 四类检索工具

### 3.1 `keyword_search`

目标：

- 精确命中股票代码、基金代码、政策名、公告号、机构名、专有概念。

第一版实现方向：

- PostgreSQL FTS。
- 结构化字段 exact match。
- 必要时补 trigram / alias 表匹配。

返回内容：

- 命中的实体、文档、证据片段。
- 命中字段和匹配词。
- 来源表和主键。

### 3.2 `semantic_search`

目标：

- 召回语义相近新闻、历史事件、政策文本、community report。

第一版实现方向：

- PostgreSQL `pgvector`。
- 向量对象优先覆盖 `text_units`、事件摘要、community reports。
- T0 已通过 `/v1/embeddings` 接入 `.env` 配置的远程 embedding 服务；Phase 3 负责把该能力落到 PostgreSQL `pgvector` 索引和混合召回协议中。

返回内容：

- 相似文本片段。
- 相似度分数。
- 时间、实体、事件类型等过滤条件。

### 3.3 `graph_search`

目标：

- 查询图邻居、最短路径、社区、影响链。

第一版实现方向：

- `kg_edges` 查询。
- NetworkX / graphify 快照。
- GraphRAG Local / DRIFT 可作为生产查询补充。

返回内容：

- path。
- relation_type。
- confidence_label / confidence_score。
- evidence refs。

### 3.4 `chunk_read`

目标：

- 对候选文档、text_unit、wiki、community report 做完整读取。

第一版实现方向：

- 按 `doc_id` / `text_unit_id` / `page_key` 精读。
- 不把长文本一开始全部塞进 prompt。
- 只对融合后高价值候选精读。

返回内容：

- 完整或裁剪后的原文。
- 摘要。
- 可回链证据。

## 4. `retrieval_context_builder`

`retrieval_context_builder` 是 Phase 3 的关键交付物。

它不是一个简单搜索函数，而是统一上下文编排层。

职责：

1. 识别问题类型：
   - 精确实体问题
   - 市场主线总结
   - 影响链 / 因果传导
   - 原文证据查找
   - 历史类比

2. 选择默认召回组合：
   - 精确实体：keyword + graph + Local Search
   - 市场主线：community reports + Global Search + semantic
   - 影响链：graph path + DRIFT + chunk_read
   - 原文证据：keyword + chunk_read
   - 历史类比：semantic + graph community + time filter

3. 融合候选：
   - RRF。
   - 去重。
   - 按证据质量、关系置信度、时间、来源加权。

4. 控制上下文预算：
   - 路径优先。
   - 证据其次。
   - 社区摘要最后。
   - AMBIGUOUS 只提示，不进入硬结论上下文。

5. 输出结构化上下文：
   - candidates。
   - paths。
   - evidence。
   - reports。
   - excluded / low confidence items。

## 5. 与 GraphRAG 的关系

GraphRAG 仍然是生产 GraphRAG 查询能力，不被混合召回替代。

关系如下：

| 能力 | 职责 |
|---|---|
| GraphRAG Local / Global / DRIFT | 生产图谱型问答和 community report 查询 |
| `retrieval_context_builder` | 多路候选融合，服务 GraphRAG、L2、L3 和 agent |
| graphify | 本地路径、邻居、Wiki、MCP 调试 |
| PostgreSQL FTS / pgvector | 关键词和语义召回基础设施 |

也就是说：

> **GraphRAG 是查询引擎之一，`retrieval_context_builder` 是系统级上下文编排入口。**

---

## 6. 与 L2/L3 的关系

L2 和 L3 不应该各自发明一套检索逻辑。

L2 使用：

- `graph_search` 找事件之间的路径和社区。
- `semantic_search` 找历史相似事件。
- `keyword_search` 精确回链政策、公告、股票。
- `chunk_read` 精读关键证据。

L3 使用：

- `graph_search` 找 `event -> concept -> stock -> fund`。
- `keyword_search` 确认基金、股票、公告、持仓事实。
- `semantic_search` 找历史类比。
- `chunk_read` 精读影响链证据。

统一要求：

- EXTRACTED 可进入硬逻辑。
- INFERRED 只进入加权项。
- AMBIGUOUS 只进入提示和复核。

## 7. Phase 3 交付物

### T4-5 PostgreSQL `pgvector` 语义召回基线

交付：

- `text_units` / event summary / community reports 的向量召回基线。
- 时间、实体、类型过滤策略。

### T4-6 图路径与社区召回接口

交付：

- 邻居查询。
- 最短路径查询。
- 社区节点查询。
- 关系置信度过滤。

### T4-7 `chunk_read` 原文精读接口

交付：

- 按文档、text_unit、wiki、community report 读取完整内容。
- 支持 token budget 裁剪。

### T4-8 RRF / 去重 / token budget 融合协议

交付：

- 多路候选统一排名。
- 重复证据合并。
- 高低置信度分层。
- 上下文预算控制。

### T4-9 `retrieval_context_builder` 第一版

交付：

- 面向 GraphRAG / L2 / L3 / agent 的统一上下文构建入口。
- 输出结构化上下文，不只输出拼接字符串。

---

## 8. 验收标准

Phase 3 结束时，至少要满足：

1. 同一问题能同时从 keyword、semantic、graph 三路召回候选。
2. 能对候选做 RRF / 去重 / token budget 控制。
3. 能对高价值候选执行 `chunk_read`。
4. 输出上下文带来源、证据、置信度、类型。
5. L2/L3 不再直接各自查询 FTS / pgvector / graph，而是通过统一上下文入口获取候选。
6. 不依赖 Milvus，也能完成最小 A-RAG 思想闭环。

---

## 9. 不做什么

第一版不做：

- 不引入 Milvus。
- 不做完整 agent 自主工具规划。
- 不让 LLM 每次决定所有检索路径。
- 不把 GraphRAG 替换成自研 RAG。
- 不让 embedding Top-K 成为默认唯一召回。

---

## 10. 结论

本文档的核心结论是：

> **A-RAG 给我们的不是一个必须使用 Milvus 的技术选型，而是一套检索架构约束：多工具、多粒度、混合召回、精读证据、统一融合。**

当前实施路线：

```text
PostgreSQL FTS
  + pgvector
  + kg_edges / graphify / GraphRAG
  + text_units / wiki / community reports
  -> retrieval_context_builder
  -> GraphRAG / L2 / L3 / agent
```

等这一层接口稳定后，如果 PostgreSQL 真的不够，再替换底层检索引擎。
