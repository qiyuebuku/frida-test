# 知识图谱实体标准化与去重治理优化方案

> 本文档解决当前真实数据入图后暴露出的实体重复、类型摇摆、主题泛化和事件主线拆散问题。
> 目标不是让 LLM 直接“猜测合并”，而是在入图前、编译中、入图后三个阶段建立稳定的知识治理机制。

---

## 1. 背景问题

当前 `ft_news -> KG` 链路已经可以跑通，检索质量基线也能通过，但真实结果里已经出现明显的数据质量问题：

```text
并购重组
并购重组主题
concept:并购重组
policy:并购重组

新能源车产业链 同时出现 concept 和 industry
高股息资产 出现多个节点
海外产能 出现多个 concept
```

这说明当前系统已经具备“抽取和检索能力”，但还缺少稳定的“实体标准化和去重治理能力”。

如果不解决，数据越多，图谱会出现：

- 同一实体被拆成多个节点。
- 同一主题在不同类型之间摇摆。
- 检索结果命中很多节点，但有效信息重复。
- 图路径变长、噪声变多，影响 L1/L2/L3 消费。
- 后续事件主线、行业影响、基金映射都会被重复节点干扰。

---

## 2. 设计目标

本优化方案要达到：

1. **减少重复节点**
   - 同义词、别名、主题后缀、轻微名称差异不应生成多个独立节点。

2. **稳定实体类型**
   - 同一个业务概念不能一会儿是 `concept`，一会儿是 `industry`，一会儿是 `policy`。

3. **保留证据和可追溯性**
   - 合并不是删除历史，而是保留原始证据、来源和合并记录。

4. **LLM 只做候选判断**
   - 不能让 LLM 直接决定最终主键。
   - 强 ID、规则、词表、历史反馈和质量阈值优先。

5. **支持全自动分级治理**
   - 系统必须能在无人值守场景下持续运行，不能把中低置信数据堆给人工审批。
   - 不确定合并不应强行写入主图，而应自动降级为软合并、检索侧归并、隔离降权或质量审计记录。
   - 人工只做离线抽样、规则维护和评估集更新，不参与每条数据的在线审批。

---

## 3. 核心原则

### 3.1 强 ID 优先

有天然 ID 的实体，必须使用强 ID：

| 实体 | 主 ID |
|---|---|
| 股票 | exchange + code |
| 基金 | fund_code |
| 正式行业 | taxonomy + industry_code |
| 政策文件 | source + document_id / 文号 |
| 采集文档 | source_table + source_pk / url fingerprint |

这些实体不应该依赖名称合并。

### 3.2 名称标准化先于 stable_key

对于概念、主题、机构、地区、商品等弱 ID 实体，必须先标准化名称，再生成 `stable_key`。

错误方式：

```text
stable_key = LLM 原始名称
```

正确方式：

```text
raw_name
  -> normalize_name
  -> canonical_name
  -> stable_key
```

例如：

```text
并购重组主题 -> 并购重组
海外工厂 -> 海外产能
海外基地 -> 海外产能
高股息资产 -> 高股息
红利资产 -> 高股息
新能源车产业链 -> 新能源车产业链
```

### 3.3 类型边界必须明确

实体类型不是 LLM 自由发挥的结果，而应由 Adapter 规则约束。

| 类型 | 定义 |
|---|---|
| `industry` | 正式行业分类、可映射到行业体系 |
| `concept` | 题材、主题、策略、交易线索 |
| `policy` | 具体政策文件、会议、监管表述或有来源的政策事件 |
| `event` | 具体新闻、公告、行情触发、L1 事件 |

特别规则：

```text
名称包含 “产业链 / 供应链 / 生态链” 的，默认归为 concept，taxonomy=industry_chain。
只有来自正式行业分类表时，才归为 industry。
```

### 3.4 泛化 policy 不允许自动创建

LLM 不能因为文本里出现“并购重组政策”“资本市场改革政策”，就创建：

```text
policy:并购重组
policy:资本市场改革
```

没有明确政策文件、监管机构、会议来源或文号时，应抽取为：

```text
concept:并购重组
event:某次监管表态
institution:证监会 / 交易所
```

### 3.5 合并必须可回溯

重复节点治理不能直接删除节点。

正确策略：

```text
保留主节点
重复节点 status = merged
properties.merged_into = 主节点 node_id
边迁移或查询时重定向到主节点
证据保留
记录 merge_audit / quality_issue / lineage
```

## 4. 三层治理架构

### 4.1 入图前标准化

入图前标准化发生在 Adapter 生成 `NodeDraft` 之前。

```text
原始文本 / LLM 抽取实体
  -> 金融术语标准化
  -> 类型修正
  -> alias 补全
  -> stable_key 生成
  -> NodeDraft
```

这一层解决最常见的重复：

- 后缀归一：`并购重组主题 -> 并购重组`
- 同义词归一：`红利资产 -> 高股息`
- 产业链类型归一：`新能源车产业链 -> concept:industry_chain`
- 泛化 policy 降级：`policy:并购重组 -> concept:并购重组`

这里的“标准化”不能理解成提前写死一套固定规则。正确做法是：

```text
抽取出的原始实体
  -> 召回已有 active 规则和相似 canonical entity
  -> 把规则、候选实体、原始上下文交给 LLM 判断
  -> LLM 决定使用已有规则、创建新规则、创建新实体或阻断入图
  -> 规则和实体一起写入数据库
  -> 再进入 EntityResolver
```

也就是说，写入前必须先完成标准化决策。

如果已有规则适用，就复用已有规则；如果已有规则不适用，就由 LLM 基于当前上下文生成新规则或新 canonical entity，并将这次决策记录到规则表和审计信息中。不能先把明显不确定的数据写进主图，再指望后续扫描修复。

### 4.2 编译期确定性合并

编译期由 `EntityResolver` 处理。

它只合并确定相同的实体：

```text
adapter_name + node_type + stable_key 相同
```

这一层不做模糊判断，不做语义猜测。

它的价值是稳定、可解释、不会误合并。

### 4.3 入图后规则审计与迁移治理

入图后治理不是第一道防线，而是第二道审计机制。

它的目标不是“发现所有脏数据再补救”，而是：

- 审计写入前生成的新规则是否稳定。
- 发现规则之间是否冲突。
- 观察某条规则关联的数据分布是否异常。
- 对历史规则进行合并、废弃、迁移和索引刷新。
- 发现少量写入前没有识别出来的异常。

入图后定期扫描规则、节点和检索结果，生成候选治理项：

| 候选类型 | 示例 | 处理方式 |
|---|---|---|
| same_name_same_type | concept:高股息资产 重复出现 | 高置信自动合并 |
| alias_match | 红利资产 vs 高股息 | 规则强命中自动合并，弱命中写入 alias candidate / soft cluster |
| same_name_different_type | concept:新能源车产业链 vs industry:新能源车产业链 | 按类型边界规则处理 |
| similar_name_same_type | 海外产能 vs 海外产能扩张 | 高置信自动合并，中置信只做软合并 |
| generic_policy | policy:并购重组 | 自动降级为 concept；无法确定则隔离为 candidate |
| event_storyline | 多篇新闻描述同一事件主线 | 高置信自动归并，中置信进入 storyline candidate cluster |

这一层必须全自动运行，但自动动作要分级，不能把不确定关系强行写成确定合并。

建议策略：

```text
高置信规则命中 -> 自动强合并
中置信规则/语义命中 -> 自动软合并 / 检索侧归并，不改主节点
低置信 -> 保留原节点但降权或隔离，仅写质量报告
冲突命中 -> 自动阻断强合并，写入 quality_issue / merge_audit
```

### 4.4 测试阶段脏数据清理与重放

当前知识图谱还处在规则验证阶段，现有入库数据主要来自：

```text
docs/6. 使用说明/知识图谱/kg_real_replay_quality_baseline.py
```

这类数据本质上是测试回放产物，不应该当成长期生产事实保留。

因此在实体标准化、类型边界、关系编译规则调整后，推荐策略不是在旧脏数据上做补丁式修复，而是：

```text
按 adapter/target 清空现有 KG 测试数据
  -> 清空 Wiki / 图邻接 / evidence chunks / Milvus hybrid scope
  -> 使用最新规则重新读取真实业务表
  -> 重新 compile / incremental index
  -> 跑固定质量基线
```

这样做的原因：

- 旧规则生成的重复节点、错误类型和错误关系不会继续污染新结果。
- 能直接验证“最新规则从零构建”的真实效果。
- 避免把测试阶段的脏数据治理逻辑误当成生产迁移逻辑。
- 让每次规则修改后的质量基线更可信。

清理边界必须限定在 KG 生成物，不清理原始业务表：

| 可以清理 | 不应清理 |
|---|---|
| `kg_nodes` | `ft_news` |
| `kg_edges` | `ft_raw_data` |
| `kg_evidence` | `ft_events` |
| `kg_edge_evidence` | `ft_positions` |
| `kg_wiki_pages` | `ft_watchlist_data` |
| `kg_graph_adjacency` | 原始采集表 |
| `kg_evidence_chunks` | 业务交易表 |
| `kg_compilation_runs` | 业务持仓/决策表 |
| Milvus KG scope | Embedding 服务本身 |

进入生产后不能默认全量清空，应改为版本化迁移：

```text
新规则写入新 version
  -> 新旧版本并行评估
  -> 通过质量基线后切换 active version
  -> 旧版本延迟归档
```

## 5. 标准化规则维护设计

### 5.1 规则维护的根本原则

实体标准化不能长期靠代码里的硬编码，也不能靠人工逐条维护。

正确边界是：

```text
代码负责执行规则
数据库负责保存规则
LLM 负责生成候选规则
质量回放负责决定候选规则能否自动生效
人工只做离线抽样、规则方向调整和评估集维护
```

也就是说，标准化规则本身要成为一类可治理的数据，而不是散落在代码、JSON 或 prompt 里的临时逻辑。

### 5.2 规则唯一来源

标准化规则的唯一在线来源应是数据库表：

```text
kg_normalization_rules
```

不应再引入 JSON fallback。原因是：

- JSON fallback 会让运行结果依赖本地文件状态，生产和测试容易不一致。
- 多环境部署时，文件规则难以审计、版本化和回滚。
- LLM 自动维护规则时，最终也必须落到数据库，JSON 反而会形成第二套真相。
- 规则需要 `candidate / active / rejected / deprecated` 生命周期，文件不适合承载。

建议字段：

| 字段 | 说明 |
|---|---|
| rule_id | 规则 ID，支持幂等 upsert |
| adapter_name | 适配器，例如 `financial` |
| rule_type | 规则类型 |
| raw_value | 原始值，例如 `红利资产` |
| canonical_value | 标准值，例如 `高股息` |
| status | `active` / `candidate` / `rejected` / `deprecated` |
| confidence | 规则置信度 |
| source | `structured_seed` / `quality_scan` / `llm_candidate` / `baseline_seed` / `system` |
| version | 规则版本 |
| payload | 解释、证据、命中次数、失败原因、坏例来源等扩展信息 |

第一版规则类型：

| rule_type | 作用 | 示例 |
|---|---|---|
| `alias` | 同义词或别名归一 | `红利资产 -> 高股息` |
| `weak_suffix` | 可剥离弱后缀 | `主题`、`概念`、`板块`、`方向` |
| `preserved_suffix` | 必须保留的业务后缀 | `产业链`、`供应链`、`生态链` |
| `generic_policy_suffix` | 泛化政策后缀识别 | `政策` |
| `concrete_policy_hint` | 具体政策文件提示词 | `意见`、`通知`、`办法`、`规定` |
| `concept_taxonomy` | 概念分类映射 | `industry_chain -> industry_chain` |

### 5.3 基础规则自举行为

系统不允许以空规则进入正式编译链路。

如果 `kg_normalization_rules` 中没有任何 `active` 基础规则，系统必须在 Adapter 加载前自动完成规则自举：

```text
启动 / 首次加载 Adapter
  -> 检查 kg_normalization_rules 是否存在 active 基础规则
  -> 不存在则写入系统内置 baseline normalization rules
  -> 再重新加载 active 规则
  -> 使用规则进入 compile / retrieval 链路
```

这里的“系统内置 baseline rules”不是测试脚本的一部分，而是知识图谱基础设施的一部分。

原因很明确：

- 空规则会让弱 ID 实体按原始名称和原始类型生成 `stable_key`，后续会产生大量重复节点。
- 一旦脏节点进入图谱，再靠后处理修复成本更高。
- 规则表为空不是可接受业务状态，而是系统尚未初始化完成。
- 测试脚本只负责调用系统能力，不应该承担系统初始化职责。

因此运行时要求是：

```text
规则表不存在 -> 自动建表
active 基础规则不存在 -> 自动写入 baseline active 规则
baseline active 规则写入失败 -> 阻断 KG 编译并报错
```

允许降级的范围只限于：

- 健康检查可以报告 `normalization_rules=missing`。
- 管理命令可以单独执行初始化。
- 测试可以显式关闭自举以验证坏例，但默认不能关闭。

正式编译、真实数据入图和检索链路都必须依赖已加载的 active 规则。

### 5.4 规则种子与自动增长

第一版必须提供系统级 baseline 规则自举能力。

baseline 规则的作用是让知识图谱具备最低可用的实体治理能力：

- 提供基础 alias。
- 提供弱后缀规则。
- 提供保留后缀规则。
- 提供泛化 policy 识别规则。
- 提供概念 taxonomy 默认映射。
- 支持重复运行，使用 upsert 保持幂等。

这批 baseline 规则可以来自代码内置常量、迁移脚本或初始化服务，但最终必须写入 `kg_normalization_rules`，运行时只从数据库读取。

测试脚本不应该维护规则内容。测试脚本最多只能触发：

```text
ensure_baseline_normalization_rules(adapter_name)
```

但是规则的定义、写入、版本和审计应属于系统能力。

baseline 只能解决第一批已知问题。长期规则来源应扩展为：

| 来源 | 示例 | 用途 | 是否直接 active |
|---|---|---|---|
| 结构化业务表 | 股票基础信息、基金基础信息、行业分类、概念成分 | 强 ID、正式名称、官方分类 | 可直接 active |
| 真实采集数据 | `ft_news`、公告、研报、行情信号 | 发现高频别名、简称、主题词 | 不直接 active |
| KG 质量扫描 | 重复节点、同名跨类型、alias 冲突 | 生成候选规则和风险报告 | 不直接 active |
| 检索回放坏例 | 某个 query 缺少目标节点或命中重复节点 | 反推需要补充的规则 | 不直接 active |
| LLM 候选建议 | 同义词判断、类型边界解释 | 生成 candidate 规则 | 不直接 active |

### 5.5 写入前 LLM 标准化决策闭环

LLM 自动维护规则的主入口应该发生在写入前，而不是等数据写脏后再扫描补救。

当系统要写入一批新数据时，流程是：

```text
采集原始数据
  -> 投影为 KG source record
  -> LLM/规则抽取 raw entities / raw relations
  -> 按 raw name、type、上下文召回相关 active rules
  -> 召回相似 canonical entities 和历史规则使用记录
  -> 把 raw entity、原文上下文、候选规则、候选实体交给 LLM
  -> LLM 输出 normalization decision
  -> 系统校验 decision 是否字段完整、无冲突、可追溯
  -> 写入新规则或复用旧规则
  -> 用标准化后的 canonical entity 写入 KG
```

LLM 输出不应该是自由文本，而应该是结构化决策：

| decision | 含义 | 后续动作 |
|---|---|---|
| `use_existing_rule` | 已有规则适用 | 复用 rule_id，写入标准实体 |
| `create_new_alias_rule` | 当前名称是某个 canonical 的新别名 | 写入 active 规则，记录 evidence 和 batch_id |
| `create_new_canonical_entity` | 当前实体不是已有概念 | 创建新 canonical entity，并写入自规则 |
| `create_type_boundary_rule` | 当前类型需要固定边界 | 写入类型规则，再写入实体 |
| `quarantine` | 无法判断或冲突明显 | 不写主图，写 quality_issue / quarantine evidence |

关键要求：

- 每个写入主图的弱 ID 实体，都必须能追溯到 `rule_id` 或本次 `normalization_decision_id`。
- 新规则可以在写入前生成并立即使用，但必须记录 `source=llm_write_time`、上下文 evidence、置信度和适用范围。
- 如果 LLM 判断不充分，不能把数据写入主图；应进入隔离区或低权重 observation。
- LLM 不是直接改 `node_id`，而是输出标准化决策；最终 ID 仍由系统按 canonical entity 生成。

例如一批新闻里出现：

```text
高股息资产
红利资产
红利策略
风险资产
```

系统应召回已有规则和上下文，让 LLM 判断：

```text
高股息资产 -> 高股息：create_new_alias_rule 或 use_existing_rule
红利资产 -> 高股息：create_new_alias_rule 或 use_existing_rule
红利策略 -> 高股息：视上下文决定是否 alias 或新 concept
风险资产 -> 风险资产：create_new_canonical_entity，不应合并到高股息
```

这比提前写死“资产是弱后缀”可靠，因为它允许新类型、新术语和新上下文进入系统，而不是被固定规则误伤。

LLM 适合在写入前做：

- 判断两个名称是否可能同义。
- 提供别名候选。
- 判断名称里的后缀是否是弱后缀。
- 解释类型冲突，例如为什么 `新能源车产业链` 不应归入正式 `industry`。
- 给出规则风险等级和适用范围。
- 判断是否应该创建新 canonical entity。
- 判断是否应该拒绝写入主图。

LLM 不允许做：

- 直接决定最终 `node_id`。
- 直接删除节点。
- 把无证据、低置信或冲突决策写入主图。
- 无证据地把 `industry`、`concept`、`policy` 强行合并。

### 5.6 入图后规则审计闭环

写入前标准化不能替代后续审计。

系统应定期扫描 `kg_normalization_rules` 和规则关联的数据分布，而不是只扫描节点表本身：

```text
扫描规则表
  -> 找到每条规则关联的 nodes / edges / evidence / queries
  -> 观察命中分布、类型分布、时间分布、检索表现
  -> LLM 判断规则是否过宽、过窄、冲突或需要拆分
  -> 生成规则调整计划
  -> dry-run 迁移受影响数据
  -> 通过质量回放后执行迁移
```

审计可以产生的动作：

| 动作 | 说明 |
|---|---|
| `add_rule` | 新增 alias / type boundary / taxonomy rule |
| `merge_rules` | 多条规则指向同一 canonical，合并规则 |
| `split_rule` | 一条规则过宽，需要拆成多个作用域 |
| `deprecate_rule` | 规则不再适用，停止新数据使用 |
| `migrate_entities` | 已写入数据按新规则迁移 |
| `rebuild_indexes` | 刷新受影响 Wiki / graph / hybrid index |

### 5.7 规则生效标准

规则生效分两种路径。

第一种是写入前即时规则。

它用于当前批次必须立即做标准化的场景：

```text
raw entity 当前没有可用规则
  -> LLM 判断需要创建新 alias / 新 canonical / 新 type boundary
  -> 系统完成结构校验、冲突校验、证据绑定
  -> 写入 active 规则并立即用于当前批次
```

这类规则必须满足更严格的即时校验：

| 条件 | 说明 |
|---|---|
| evidence 绑定 | 规则必须绑定当前原文、source_id、batch_id |
| 作用域明确 | 规则必须限制 adapter、entity_type、taxonomy 或上下文范围 |
| 无强 ID 冲突 | 不能覆盖股票、基金、正式行业等强 ID |
| 无 active 规则冲突 | 不能和已有 active 规则产生相反 canonical |
| 置信度达标 | 低置信直接 quarantine，不写主图 |
| 可回滚 | 规则必须能定位关联数据，后续可迁移或废弃 |

第二种是离线候选规则。

它来自规则表审计、检索坏例和历史数据分布分析。

候选规则能否自动变成 `active`，必须由指标决定。

最低晋级条件：

| 条件 | 说明 |
|---|---|
| 程序化校验通过 | rule_type、字段、作用域、冲突检查全部通过 |
| 固定回放不下降 | 已有 deterministic quality baseline 不能失败 |
| 重复指标改善 | duplicate / cross_type_duplicate 指标下降 |
| 关键实体不丢失 | 固定 case 中要求命中的节点仍能命中 |
| 关系不劣化 | 关键 relation type 不丢失 |
| 无黑名单冲突 | 不命中禁止合并或强类型边界冲突 |

自动晋级策略：

```text
高置信 + 回放通过 -> active
中置信 + 回放通过 -> active，但 payload 标记 risk=medium，检索侧保守应用
低置信 -> candidate，只用于 soft mapping 或后续批量评估
冲突 -> rejected，并记录原因
```

这里的“中低置信”不进入人工审批队列，因为系统必须无人值守运行。

人工只参与：

- 离线抽样看规则质量。
- 更新固定质量回放 case。
- 调整阈值和黑白名单。
- 处理系统性错误，不处理每一条数据。

### 5.8 规则应用位置

规则应在三个位置生效。

第一，入图前：

```text
raw entity
  -> load active normalization rules
  -> normalize name/type/taxonomy
  -> generate stable_key
  -> NodeDraft
```

第二，编译期：

```text
NodeDraft
  -> EntityResolver
  -> adapter_name + node_type + stable_key 确定性合并
```

第三，检索侧：

```text
query
  -> alias expansion
  -> canonical search
  -> merged/soft-merged result redirect
  -> duplicate display collapse
```

入图前规则负责减少新增脏数据，检索侧规则负责缓解历史数据残留，入图后质量扫描负责发现下一轮规则候选。

### 5.9 示例规则

示例 active 规则：

| rule_type | raw_value | canonical_value | 说明 |
|---|---|---|---|
| `alias` | 并购重组主题 | 并购重组 | 主题后缀归一 |
| `alias` | 红利资产 | 高股息 | 投资策略别名 |
| `alias` | 高股息资产 | 高股息 | 弱后缀归一 |
| `alias` | 海外工厂 | 海外产能 | 场景同义归一 |
| `alias` | 海外基地 | 海外产能 | 场景同义归一 |
| `weak_suffix` | 主题 |  | 可剥离弱后缀 |
| `weak_suffix` | 概念 |  | 可剥离弱后缀 |
| `preserved_suffix` | 产业链 |  | 不能剥离 |
| `preserved_suffix` | 供应链 |  | 不能剥离 |
| `generic_policy_suffix` | 政策 |  | 泛化 policy 识别 |
| `concrete_policy_hint` | 通知 |  | 具体政策文件提示 |

注意：`资产` 不能简单作为全局弱后缀无脑剥离。

```text
高股息资产 -> 高股息
风险资产 -> 风险资产
数字资产 -> 数字资产
```

这类规则应该优先通过 alias 明确维护，而不是把 `资产` 放进全局弱后缀。

## 6. 类型边界优化

### 6.1 industry 与 concept

当前最需要稳定的是 `industry` 和 `concept`。

建议规则：

```text
来自行业成分表 / 行业分类表 -> industry
来自新闻、研报、LLM 文本抽取 -> concept
名称包含产业链/供应链/生态链 -> concept, taxonomy=industry_chain
如果新闻抽到“半导体设备”这类正式行业名，可通过行业词表映射为 industry
```

这样可以避免：

```text
新能源车产业链 同时是 concept 和 industry
```

### 6.2 policy 与 concept

`policy` 只能表达具体政策材料或政策事件。

允许：

```text
新能源汽车高质量发展政策
国务院常务会议关于资本市场改革的表述
证监会并购重组审核规则
```

不允许：

```text
policy:并购重组
policy:低利率环境
policy:高股息资产
```

这些应该分别进入：

```text
concept:并购重组
macro_indicator:低利率环境
concept:高股息
```

### 6.3 event 与 concept

`event` 表示具体发生的事情；`concept` 表示可复用主题。

例如：

```text
event:宁德时代海外产能扩张带动储能供应链订单
concept:海外产能
concept:储能供应链
stock:宁德时代
```

不要把“海外产能扩张”每次都作为新的 concept，也不要把所有“海外产能”新闻合成一个 event。

---

## 7. 事件主线归并

事件归并不能依赖标题完全一致。

建议拆成两层：

```text
document / evidence
  表示一篇新闻、公告、研报或采集记录

event / storyline
  表示真实世界中的事件或事件主线
```

当前系统更接近：

```text
一篇新闻 -> 一个 event
```

后续应演进为：

```text
多篇新闻 / 公告 / 信号
  -> 归并到一个 event_cluster / storyline
```

事件主线判断依据：

- 核心实体是否相同。
- 事件类型是否相同。
- 时间窗口是否接近。
- 影响对象是否相似。
- 语义 embedding 是否相似。
- 图邻域是否相似。

LLM 只参与“是否可能同一事件主线”的候选判断，不生成最终主键。

---

## 8. 检索侧去重

即使写入侧还没完全治理，检索侧也需要先做展示去重。

### 8.1 结果合并

检索结果展示时，应按以下规则合并：

```text
同 canonical_name + 同 node_type -> 合并展示
merged 节点 -> 展示主节点
alias 命中 -> 展示 canonical_name
同证据多条边 -> 合并证据展示
```

### 8.2 类型冲突提示

如果同一个名称存在多个类型：

```text
concept:新能源车产业链
industry:新能源车产业链
```

检索结果不应静默混在一起，应提示：

```text
存在类型冲突，已按置信度降权或隔离，建议后续通过规则/词表修正。
```

### 8.3 质量指标

检索回放应增加实体质量指标：

| 指标 | 含义 |
|---|---|
| duplicate_name_count | 同名重复节点数量 |
| cross_type_duplicate_count | 同名跨类型数量 |
| merged_node_hit_count | 命中已合并节点数量 |
| governance_candidate_count | 检索结果中需要自动治理的候选项 |

## 9. 落地顺序

### 阶段一：DB 规则底座与入图前标准化

目标：先把规则从代码中移出去，形成可审计、可版本化、可自动维护的数据库规则底座。

要做：

1. 建立 `kg_normalization_rules`。
2. Adapter 启动时按 `adapter_name + status=active` 加载规则。
3. Adapter 加载前必须执行 baseline 规则自举。
4. active 基础规则不存在时自动写入，写入失败则阻断编译。
5. `entity_stable_key()` 必须基于标准化后的名称和类型生成。
6. 产业链类实体统一归为 `concept:industry_chain`。
7. 泛化 policy 自动降级为 concept 或 event，不创建伪 policy。

验收：

```text
规则表为空时，首次加载 Adapter 会自动写入 baseline active 规则
baseline active 规则缺失且无法写入时，compile 必须失败
写入 active 规则后，不改代码即可改变归一结果
并购重组 / 并购重组主题 合并为 concept:并购重组
新能源车产业链 不再同时生成 concept 和 industry
高股息资产 / 红利资产 合并为 concept:高股息
海外工厂 / 海外基地 / 海外产能 合并为 concept:海外产能
```

### 阶段二：写入前 LLM 标准化决策

目标：在数据写入主图前完成标准化决策，避免先写入错误节点再后处理补救。

要做：

1. 对每个 raw entity 召回相关 active rules。
2. 召回相似 canonical entities、历史 alias 和规则使用记录。
3. 将 raw entity、原文上下文、候选规则、候选实体交给 LLM。
4. LLM 输出结构化 normalization decision。
5. 系统校验 decision，无冲突后写入新规则或复用旧规则。
6. 用 canonical entity 生成 stable_key 并写入 KG。
7. 无法判断的数据进入 quarantine，不写主图。

验收：

```text
新增术语不需要改代码即可标准化入图
每个弱 ID 实体都能追溯到 rule_id 或 normalization_decision_id
LLM 判断已有规则适用时复用已有规则
LLM 判断不适用时可创建新 canonical entity 或新 alias 规则
低置信或冲突数据不会进入主图
```

### 阶段三：规则表审计与自动优化闭环

目标：定期审计规则表和规则关联数据，发现规则过宽、过窄、冲突和迁移需求。

要做：

1. 扫描 `kg_normalization_rules`。
2. 通过 rule_id 关联 nodes / edges / evidence / queries。
3. 统计每条规则的数据分布、命中分布和检索表现。
4. LLM 判断规则是否需要新增、合并、拆分、废弃或迁移。
5. 生成 rule optimization plan。
6. dry-run 迁移受影响数据。
7. 质量回放通过后执行规则调整和数据迁移。

验收：

```text
能定位每条规则影响了哪些实体、边、证据和检索结果
能发现规则过宽导致的误归一
能发现规则过窄导致的重复实体
规则可以自动新增、合并、拆分、废弃
规则变更能触发受影响数据迁移和索引刷新
```

### 阶段四：自动合并与软合并机制

目标：对已经入图的历史重复实体进行自动治理，且不依赖人工逐条审批。

要做：

1. 生成 merge candidate、confidence score 和 risk level。
2. 高置信自动 strong merge，并设置 `merged_into`。
3. 中置信自动 soft merge / alias / retrieval redirect，不修改主节点归属。
4. 低置信 quarantine / report only，避免污染主图。
5. 保留 evidence、merge_audit、quality_issue 和 lineage。
6. 人工只基于审计报告做离线抽样评估和规则阈值维护。

验收：

```text
高置信重复节点自动不再作为独立主结果展示
中低置信节点不污染主图，但可在检索侧合并展示或降权
边和证据仍可追溯
无人值守运行时不会堆积人工审批任务
```

### 阶段五：事件主线归并

目标：解决多篇新闻描述同一真实事件的问题。

要做：

1. 引入 document/event/storyline 分层。
2. 用实体集合、事件类型、时间窗口、embedding、图邻域召回候选。
3. LLM 判断候选是否属于同一主线。
4. 高置信自动归并，中置信进入 storyline candidate cluster，低置信保留独立事件并降权。

验收：

```text
同一事件多篇新闻能聚合到同一 storyline
不同事件不会因为标题相似被误合并
```

## 10. 与现有系统的关系

本方案不是替换现有 KG 编译器，而是在现有链路上增加治理层：

```text
Source Projection
  -> Text Extraction
  -> Rule/Canonical Candidate Recall
  -> LLM Normalization Decision
  -> Rule Upsert / Rule Reuse
  -> Entity Normalization
  -> EntityResolver
  -> RelationCompiler
  -> Fact Store
  -> Rule Usage Audit
  -> Rule Optimization / Data Migration
  -> Retrieval Dedup
```

现有 `EntityResolver` 仍然保留，它负责确定性合并。

新增能力负责：

- DB 规则加载和版本化维护。
- 写入前 LLM 标准化决策。
- 新规则写入和旧规则复用。
- 类型边界规则。
- 规则使用记录和规则审计。
- 规则合并、拆分、废弃和数据迁移。
- 自动合并、软合并、隔离和审计。
- 检索侧去重展示。

---

## 11. 结论

当前问题不是“检索能力不行”，而是“入图实体治理还不够”。

最优先的优化不是继续加更复杂的 RAG，而是先把实体标准化和去重治理补上。

第一阶段应该优先做：

```text
kg_normalization_rules 作为规则唯一来源
Adapter 启动时加载 active 规则
Adapter 加载前自动确保 baseline active 规则存在
baseline 规则写入失败则阻断编译
写入前召回已有规则和相似 canonical entity
LLM 输出结构化 normalization decision
新规则或新 canonical entity 在写入 KG 前落库
entity_stable_key 使用标准名和标准类型
产业链类统一归 concept:industry_chain
泛化 policy 禁止自动创建
deterministic quality baseline 验证规则效果
```

这几项能把问题挡在写入前，而不是先污染主图再靠后处理补救。后续规则表审计和数据迁移只负责持续优化，不应该承担第一道质量防线。
