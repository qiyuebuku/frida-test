# 自定义领域适配器设计方案

> 本文档定义任何领域如何接入通用知识基础设施。金融、代码、企业、法务、医疗、个人记忆都应该通过同一套 Adapter 协议接入。

---

## 0. 一句话说清楚

Adapter 是领域和平台之间的边界。

```text
业务数据 / 业务规则 / 业务 ontology
  -> Domain Adapter
  -> 通用 Knowledge Infrastructure
```

Adapter 的职责不是重新实现知识图谱系统，而是告诉平台：

- 本领域有哪些实体。
- 本领域有哪些关系。
- 哪些数据源能产生这些实体和关系。
- 文本材料需要如何抽取领域实体和关系。
- 如何做实体归一。
- 如何给关系分配置信度。
- 哪些事实能被哪些业务场景消费。

---

## 1. Adapter 必须提供什么

| 能力 | 说明 |
|---|---|
| Entity Ontology | 实体类型、字段、强 ID、alias 规则 |
| Relation Ontology | 关系类型、方向、约束、是否允许推断 |
| Source Mapping | 原始数据源如何映射成平台输入协议 |
| Extraction Strategy | 文本、半结构化材料和 LLM 输出如何转换成领域节点、关系和证据 |
| Resolver Rules | 实体归一规则 |
| Relation Rules | 结构化关系、文本关系、统计关系、推断关系的生成规则 |
| Confidence Policy | 不同来源关系如何赋置信度 |
| Validation Policy | 哪些节点和边允许进入主图 |
| Consumption Policy | 哪些业务可以消费哪些置信等级的关系 |
| Review Policy | 哪些情况必须人工复核 |
| Wiki Policy | 本领域适合生成哪些 Wiki 页面 |

---

## 2. Entity Ontology

Adapter 要定义实体类型，但不能修改平台 Node 协议。

示例：

| 领域 | 实体类型 |
|---|---|
| 金融 | stock、fund、industry、concept、policy、event |
| 代码 | repo、file、module、class、function、issue、pr |
| 企业 | person、team、project、document、meeting、decision |
| 法务 | law、clause、case、party、contract、obligation |

每个实体类型至少要说明：

- 稳定 ID 来源。
- 名称和别名规则。
- 是否允许自动创建。
- 是否允许自动合并。
- 是否需要人工确认。

---

## 3. Relation Ontology

Adapter 要定义关系类型，但不能绕过平台 Edge 协议。

每类关系至少要说明：

- 方向。
- 是否允许多条并存。
- 是否允许推断。
- 是否需要证据。
- 是否有有效期。
- 是否能被业务硬逻辑消费。

示例：

| 领域 | 关系 |
|---|---|
| 金融 | holds、belongs_to、affects、benefits_from、related_to |
| 代码 | imports、calls、defines、modifies、depends_on |
| 企业 | owns、blocks、references、decided_by、supersedes |
| 法务 | applies_to、requires、violates、references、amends |

---

## 4. Source Mapping

Source Mapping 负责把领域数据转成平台输入协议。这里要区分两层：

```text
业务侧 Source Mapping
  -> 只处理具体业务库、字段名、分页、增量游标

Domain Adapter Source Contract
  -> 定义标准 source_type、required fields、identity、evidence policy
```

Adapter 不应该直接耦合某个业务库表名。例如金融 Adapter 不应该直接读取 `ft_news`。业务侧可以把 `ft_news` 转成 `news_articles` record，Adapter 再根据 `news_articles` contract 编译知识。

同一个平台输入协议可以承载不同领域：

| 平台输入 | 金融示例 | 代码示例 | 企业示例 |
|---|---|---|---|
| `structured_record` | 基金持仓 | 代码符号表 | HR 系统组织架构 |
| `semi_structured_record` | 新闻标题 | Issue 标题 | 会议纪要摘要 |
| `document_chunk` | 公告正文 | README / 设计文档 | 项目文档 |
| `event_record` | L1 事件 | CI 失败事件 | 项目风险事件 |
| `derived_signal` | 热度、资金流 | 调用频率、变更频率 | 项目延误信号 |
| `feedback_record` | 复盘修正 | code review 结论 | 人工知识修正 |

每个 source mapping 必须写清楚：

| 项 | 要求 |
|---|---|
| source name | 数据源名称，必须稳定 |
| input type | 对应平台输入类型 |
| required fields | 缺失后不能进入编译的字段 |
| optional fields | 可参与增强但不能作为主键的字段 |
| primary identity | 去重和幂等编译依据 |
| observed_at | 事实观察时间 |
| valid window | 事实有效期，如果领域需要 |
| evidence policy | 哪些字段或片段可作为 evidence |

如果 source contract 没写清楚，后续 Compiler 只能靠猜字段，实施方案就没有价值。

---

## 5. Extraction Strategy

Adapter 还必须定义领域抽取策略，尤其是 `semi_structured_record` 和 `document_chunk` 这类文本材料。

通用 Text Extraction Pipeline 只负责执行流程；Adapter 负责提供：

| 项 | 要求 |
|---|---|
| extraction target | 需要抽取哪些实体、关系、属性和证据 span |
| prompt policy | LLM prompt、输出 JSON schema、禁止事项 |
| deterministic pre-rules | 代码、ID、别名、显式字段等不需要 LLM 的规则 |
| output schema | LLM 输出如何映射为 node draft、edge draft、evidence draft |
| confidence policy | 哪些结果是 `EXTRACTED`，哪些只能是 `INFERRED` |
| review policy | 哪些抽取结果必须进入复核 |
| failure policy | 解析失败、低置信、无证据时如何降级 |

典型链路：

```text
business table row
  -> 业务侧映射成标准 source record
  -> Adapter.normalize()
  -> Adapter extraction strategy
  -> NodeDraft / EdgeDraft / EvidenceDraft
  -> Generic Compiler
```

这意味着领域 Adapter 不是被动搬运别人已经抽好的实体关系。它应该承担本领域的语义抽取、关系生成、置信度和消费边界定义。

---

## 6. Confidence Policy

平台提供通用置信标签，但 Adapter 决定业务解释。

例如同样是 `INFERRED`：

- 金融里不能直接触发交易。
- 代码里可以作为候选依赖关系。
- 企业知识库里可以作为候选关联文档。
- 法务里可能必须进入人工复核。

因此 Adapter 必须明确：

| 问题 | 必须回答 |
|---|---|
| 哪些来源默认高置信 | 结构化字段、官方文档、人工确认等 |
| 哪些关系允许 LLM 推断 | 语义相似、候选因果、隐含关联等 |
| 哪些关系必须人工确认 | 高风险 alias、业务硬逻辑、合规关系等 |
| 哪些关系只能用于召回 | 弱相关、共现、低置信推断等 |

Adapter 必须区分“关系如何产生”和“关系如何被消费”：

| 关系来源 | 典型处理 |
|---|---|
| deterministic | 由结构化字段或规则确定，通常可 active |
| extracted | 从原文明确表达抽取，需 evidence |
| statistical | 多来源共现或模型评分，通常 candidate |
| inferred | LLM 或图邻域推断，通常 candidate/review_required |
| human_verified | 人工确认，可提升为 active |
| rejected | 人工或规则否定，不能再进入 active |

---

## 7. Consumption Policy

Adapter 还要定义消费边界。

同一条边在不同业务中风险不同：

| 消费方式 | 风险 |
|---|---|
| 用于搜索召回 | 低 |
| 用于解释说明 | 中 |
| 用于自动聚类 | 中 |
| 用于业务打分 | 高 |
| 用于自动执行动作 | 最高 |

Adapter 必须规定：

- 哪些置信等级可用于召回。
- 哪些置信等级可用于解释。
- 哪些置信等级可用于自动打分。
- 哪些必须人工确认后才能进入硬逻辑。

建议每个 Adapter 都维护一张消费矩阵：

| relation_type | search | explanation | clustering | scoring | action |
|---|---|---|---|---|---|
| strong structured relation | allowed | allowed | allowed | allowed | adapter 决定 |
| text extracted relation | allowed | allowed | allowed | threshold required | forbidden by default |
| weak related relation | allowed | allowed | limited | forbidden | forbidden |
| inferred relation | allowed | limited | limited | forbidden by default | forbidden |

---

## 8. Review Policy

这些情况通常应进入复核：

- 高价值实体合并。
- 高影响关系新增。
- 两个事实互相冲突。
- LLM 推断链缺少直接证据。
- 弱关系短时间大量出现。
- 用户或业务系统反馈错误。

Review 不是平台特有或金融特有能力，而是所有领域都需要的质量闸门。

---

## 9. Wiki Policy

Adapter 需要告诉平台哪些页面值得沉淀，而不是让平台猜页面结构。

每类 Wiki 页面至少声明：

- `page_type`
- subject entity type
- 页面章节
- 需要展示的关系类型
- 是否必须带 evidence
- 是否允许保存查询结果为页面
- stale 判定规则

Wiki 页面不是 Adapter 的私有文件。Adapter 只定义页面偏好，通用 Wiki Builder 负责生成、更新、lint 和重建。

---

## 10. Golden Fixture

Adapter 设计必须配套 golden fixture。否则“设计是否完整”无法验证。

每个 Adapter 至少需要：

```text
tests/fixtures/knowledge/<adapter>/
  source_records.json
  expected_nodes.json
  expected_edges.json
  expected_evidence.json
  expected_context.json
```

fixture 必须覆盖：

1. 正常输入。
2. 缺字段输入。
3. 重复输入。
4. 歧义实体。
5. 非法关系方向。
6. 无 evidence 的候选关系。
7. 人工反馈修正。

设计文档如果没有 fixture 口径，实施方案大概率会变成“边写边想”。

---

## 11. Adapter 的边界

Adapter 可以做：

- 定义领域 ontology。
- 定义领域规则。
- 提供 prompt 模板。
- 提供解析和校验策略。
- 决定业务消费边界。
- 将标准 source record 中的文本语义抽取为领域节点、边和证据。

Adapter 不应该做：

- 直接读取具体业务库表，例如 `ft_news`、`jira_issues`、`contracts_raw`。
- 自己保存一套事实库。
- 绕过 Evidence Manager。
- 绕过 Version Manager。
- 直接把 LLM 输出写入主图。
- 修改平台通用数据模型。

---

## 12. 验收标准

一个 Adapter 合格的标准：

1. 可以清楚列出实体类型和关系类型。
2. 每种数据源如何进入平台协议清楚。
3. 每类关系的证据和置信规则清楚。
4. 文本材料如何抽取实体、关系和 evidence span 清楚。
5. 哪些事实可以被哪些业务消费清楚。
6. 移除该 Adapter 后，平台层仍然可以服务其他领域。
7. 有 golden fixture 证明输出稳定。
8. 能说明哪些知识写入 Fact Store，哪些只进入 Wiki/索引。
