# 金融领域适配器设计方案

> 本文档只讨论 Financial KG Adapter。
> 金融适配器是通用知识基础设施的第一个落地 Adapter，不是平台本身。
> 本文档的目标是把金融图谱第一版“到底怎么成图、怎么验证、怎么被 L1/L2/L3 消费”讲清楚，避免后续实施时边写边猜。

---

## 0. 一句话说清楚

Financial KG Adapter 负责把金融世界翻译成通用知识基础设施能处理的协议：

```text
股票 / 基金 / 行业 / 概念 / 政策 / 事件 / 行情 / 资金 / 情绪
  -> Financial KG Adapter
  -> KnowledgeInput / NodeDraft / EdgeDraft / EvidenceDraft
  -> 通用 Knowledge Compiler
  -> Fact Store / Wiki / Hybrid Retrieval
```

它不负责建表，不负责绕过 Compiler 写事实，不负责把 LLM 推断伪装成硬事实。

它也不应该直接读取业务库表，例如 `ft_news`、`ft_market_flow`。业务侧只负责把这些表映射成标准 source record；金融 Adapter 负责理解这些 source record 的金融语义。

---

## 1. 设计结论

金融 Adapter 第一版不追求覆盖全部金融世界，只追求跑通事件驱动投研最关键的一条链：

```text
新闻 / 公告 / 政策 / L1事件
  -> event / policy
  -> concept / industry
  -> stock
  -> fund holding
  -> fund exposure
```

这条链必须满足：

1. 每个节点有稳定 ID 或明确候选状态。
2. 每条 active 边有 evidence。
3. 结构化关系由规则编译，不能交给 LLM 重判。
4. 新闻、公告、政策等文本材料由金融 Adapter 提供抽取策略，而不是由 Notebook 临时抽完再喂给平台。
5. L1/L2/L3 消费的是 KG 查询能力，不再各自维护一套金融规则。
6. Wiki 和检索索引只是可重建索引，不是事实源。

---

## 2. 第一版闭环边界

### 2.1 第一版必须完成

| 能力 | 最小目标 |
|---|---|
| 静态事实冷启动 | 股票、行业、概念、基金持仓、政策机构词表入图 |
| 动态事件入图 | 新闻/公告/政策/L1 事件形成 event/policy 节点和候选影响边 |
| 影响链查询 | 能查到 `event -> concept/industry -> stock -> fund` |
| 投研上下文 | 能返回 keyword、graph、wiki、evidence 混合上下文 |
| 质量闸门 | 无 evidence 的 active 边不能进入主图 |
| 反馈回写 | 人工修正能更新 alias、关系状态和置信度 |

### 2.2 第一版不做

- 不做完整产业链手工精细建模。
- 不做高频实时交易图谱。
- 不覆盖全部资产类别。
- 不把弱相关关系用于自动交易。
- 不让 Microsoft GraphRAG 进入生产主路径。
- 不引入专用向量库作为第一版阻塞项。

## 3. 金融实体 Ontology

### 3.1 核心实体

| node_type | 说明 | 稳定 ID | 第一版要求 |
|---|---|---|---|
| `stock` | 股票、上市公司、证券代码 | exchange + code | 必须 |
| `fund` | 基金产品 | fund_code | 必须 |
| `industry` | 行业分类 | taxonomy + industry_code/name | 必须 |
| `concept` | 题材、概念、产业链节点 | taxonomy + canonical_name | 必须 |
| `event` | 新闻、公告、政策、行情触发事件 | source_id 或 l1_event_id | 必须 |
| `policy` | 政策、会议、监管表述 | source + document_id | 必须 |
| `institution` | 公司、监管、交易所、券商、媒体 | external_id 或 canonical_name | 第一版部分 |
| `macro_indicator` | 利率、汇率、通胀、PMI 等 | indicator_code | 第一版部分 |

### 3.2 预留实体

| node_type | 用途 | 第一版处理 |
|---|---|---|
| `commodity` | 有色、能源、农产品等 | 只预留 ontology |
| `person` | 高管、专家、监管人物 | 只预留 ontology |
| `region` | 地域政策、产业集群 | 只预留 ontology |
| `supplier` | 供应链公司或环节 | 暂不建 |
| `product` | 产品、技术路线、设备 | 暂不建 |

预留实体不能阻塞第一版闭环。只有当事件链路需要时，才作为候选节点进入。

### 3.3 实体归一规则

| 实体 | 强规则 | 弱规则 | 复核条件 |
|---|---|---|---|
| stock | exchange + code | 简称、公司名、曾用名 | 同名不同代码、简称冲突 |
| fund | fund_code | 基金简称、产品别名 | 同名不同份额、A/C 类混淆 |
| industry | taxonomy + code | 行业标准名 | 不同分类口径冲突 |
| concept | taxonomy + canonical_name | 同义词、上位词、简称 | 概念过宽、概念重名 |
| event | source_id / l1_event_id | 标题相似、时间相近 | 多来源重复事件合并 |
| policy | document_id | 标题、发布机构、日期 | 草案/正式稿冲突 |

强规则能确定的实体直接 active。弱规则只能辅助召回或候选合并，不能自动替代强 ID。

## 4. 金融关系 Ontology

### 4.1 核心关系

| relation_type | 方向 | 说明 | 消费限制 |
|---|---|---|---|
| `belongs_to` | stock -> industry / stock -> concept / concept -> concept | 归属、成分、主题层级 | 高置信可硬用 |
| `holds` | fund -> stock | 基金持仓 | 可硬用，但有报告期 |
| `mentions` | event/policy -> entity | 文档或事件提到实体 | 召回和解释 |
| `affects` | event/policy -> entity | 事件影响实体 | 高置信可打分 |
| `benefits_from` | stock/industry/concept -> event/policy/concept | 受益关系 | 需证据和阈值 |
| `hurt_by` | stock/industry/concept -> event/policy/concept | 受损关系 | 需证据和阈值 |
| `upstream_of` | concept/industry -> concept/industry | 上游 | 用于影响传播 |
| `downstream_of` | concept/industry -> concept/industry | 下游 | 用于影响传播 |
| `alias_of` | entity -> entity | 别名、简称、同义 | 必须严格复核 |
| `related_to` | entity -> entity | 弱相关、共现 | 只用于召回 |
| `causal_hint` | event/entity -> entity | 候选因果链 | 只用于解释和候选 |

### 4.2 关系产生方式

| relation_type | 主要来源 | 生成方式 | 默认状态 |
|---|---|---|---|
| `belongs_to` | 行业/概念成分表 | 规则编译 | active |
| `holds` | 基金持仓表 | 规则编译 | active |
| `mentions` | 新闻、公告、政策、L1 事件 | NER + alias 规则 + 文本位置 | active 或 candidate |
| `affects` | 原文明确影响、L1 事件结果 | 文本抽取 + 规则校验 | candidate，明确证据可 active |
| `benefits_from` | 政策/事件/主题分析 | 抽取 + 复核 + 统计验证 | candidate |
| `hurt_by` | 政策/事件/主题分析 | 抽取 + 复核 + 统计验证 | candidate |
| `upstream_of/downstream_of` | 产业链资料、人工维护 | 规则或人工确认 | active 或 review_required |
| `alias_of` | 词表、人工反馈 | 规则 + 人工复核 | review_required |
| `related_to` | 共现、语义相近、图邻域 | 统计或 LLM 辅助 | candidate |
| `causal_hint` | LLM 推理、复盘结论 | LLM/人工反馈 | candidate/review_required |

关键原则：

- `belongs_to`、`holds` 这类结构化关系不能交给 LLM 决定是否成立。
- `affects`、`benefits_from`、`hurt_by` 如果来自 LLM 推断，默认不能 active。
- `related_to` 永远不能进入硬评分。
- `alias_of` 错误会污染实体归一，默认进入复核。

## 5. 数据源契约

### 5.1 股票基础数据

| 项 | 设计 |
|---|---|
| input_type | `structured_record` |
| required fields | `code`、`name`、`exchange` |
| optional fields | `company_name`、`aliases`、`list_date`、`status` |
| 产物 | `stock` node、alias、external_ids |
| evidence | 结构化字段 evidence |
| 幂等键 | `exchange + code` |

### 5.2 行业/概念成分

| 项 | 设计 |
|---|---|
| input_type | `structured_record` |
| required fields | `taxonomy`、`component_name/code`、`member_stock_code` |
| optional fields | `weight`、`source`、`effective_date` |
| 产物 | `industry/concept/stock` node、`belongs_to` edge |
| evidence | 成分表字段 evidence |
| 幂等键 | `taxonomy + component + stock + effective_date` |

### 5.3 基金持仓

| 项 | 设计 |
|---|---|
| input_type | `structured_record` |
| required fields | `fund_code`、`stock_code`、`report_date` |
| optional fields | `holding_ratio`、`market_value`、`rank` |
| 产物 | `fund` node、`stock` ref、`holds` edge |
| evidence | 持仓字段 evidence |
| 有效期 | 从 `report_date` 到下一期持仓披露或显式废弃 |
| 幂等键 | `fund_code + stock_code + report_date` |

### 5.4 新闻标题和摘要

| 项 | 设计 |
|---|---|
| input_type | `semi_structured_record` |
| required fields | `source_id`、`title`、`published_at` |
| optional fields | `summary`、`source_name`、`url`、`symbols` |
| 产物 | `event` candidate、`mentions`、`affects` candidate |
| evidence | 标题、摘要、URL |
| 幂等键 | `source_id` |

业务侧只需要把具体表映射到这个 contract。例如：

```text
ft_news.id           -> source_id = ft_news:{id}
ft_news.title        -> title
ft_news.summary      -> summary
ft_news.content      -> text
ft_news.published_at -> published_at
ft_news.source_name  -> source_name
```

业务侧不需要预先把 `mentioned_entities` 和 `affected_entities` 全部抽好。金融 Adapter 应提供新闻抽取策略，基于标题、摘要和正文生成这些字段对应的节点和边。

### 5.5 公告/政策正文

| 项 | 设计 |
|---|---|
| input_type | `document_chunk` |
| required fields | `document_id`、`chunk_id`、`text`、`published_at` |
| optional fields | `issuer`、`page`、`section`、`url` |
| 产物 | `policy/event` node、`mentions`、`affects` candidate、evidence chunk |
| evidence | 正文 span、页码、段落 |
| 幂等键 | `document_id + chunk_id + text_hash` |

政策和公告正文同样由金融 Adapter 提供抽取策略。区别是政策类文本默认生成 `policy` 节点，普通新闻默认生成 `event` 候选节点。

### 5.6 L1 事件

| 项 | 设计 |
|---|---|
| input_type | `event_record` |
| required fields | `event_id`、`event_type`、`event_time`、`evidence_refs` |
| optional fields | `mentioned_entities`、`affected_entities`、`confidence` |
| 产物 | `event` node、`mentions`、`affects` candidate |
| evidence | L1 原始 evidence 和上游 source evidence |
| 幂等键 | `event_id` |

### 5.7 行情/资金/情绪

| 项 | 设计 |
|---|---|
| input_type | `derived_signal` |
| required fields | `target_ref`、`signal_type`、`observed_at`、`value` |
| optional fields | `window`、`rank`、`zscore` |
| 产物 | 验证信号、热度属性、时间衰减依据 |
| 限制 | 不直接生成硬因果边 |
| 幂等键 | `target_ref + signal_type + observed_at + window` |

### 5.8 复盘和人工修正

| 项 | 设计 |
|---|---|
| input_type | `feedback_record` |
| required fields | `target_type`、`target_ref`、`action`、`reason` |
| optional fields | `reviewer`、`new_confidence`、`replacement_ref` |
| 产物 | alias 修正、edge 状态变化、confidence 调整、rejected 记录 |
| evidence | 人工反馈 evidence |
| 幂等键 | `target_ref + action + reviewer + timestamp` |

## 6. 置信策略

| 来源 | confidence_label | score 建议 | 默认 status | 可消费范围 |
|---|---|---:|---|---|
| 股票代码、基金代码、官方行业分类 | `EXTRACTED` | 0.95-1.00 | active | hard |
| 基金持仓 | `EXTRACTED` | 0.95-1.00 | active | hard，但受报告期约束 |
| 公告/政策原文明确陈述 | `EXTRACTED` | 0.80-0.95 | active/candidate | scoring/explanation |
| 新闻文本抽取 | `INFERRED` | 0.60-0.80 | candidate | retrieval/explanation |
| 多事件统计共现 | `INFERRED` | 0.40-0.70 | candidate | retrieval |
| LLM 语义推断 | `INFERRED` | 0.30-0.70 | review_required/candidate | retrieval/explanation |
| 人工确认 | `HUMAN_VERIFIED` | 0.95-1.00 | active | hard/scoring |
| 人工否定 | `REJECTED` | 0.00 | deprecated | 不消费 |

硬约束：

- active edge 必须有 evidence。
- `REJECTED` 不能 active。
- `related_to` 默认最高只能 candidate。
- `causal_hint` 默认不能进入 hard/scoring。
- `benefits_from` / `hurt_by` 用于 L3 打分时必须满足 evidence、score、status 三重条件。

## 7. 编译流程

Financial Adapter 的第一版编译流程：

```text
raw source
  -> source contract validation
  -> normalize to KnowledgeInput
  -> deterministic field extraction
  -> financial text extraction strategy
  -> deterministic node draft
  -> deterministic edge draft
  -> evidence draft
  -> adapter validation
  -> generic compiler
```

`raw source` 不是具体业务表行，而是业务侧已经映射好的标准 source record。具体业务表读取逻辑不属于 Adapter。

### 7.1 规则抽取

规则抽取覆盖：

- 股票节点。
- 基金节点。
- 行业/概念节点。
- `belongs_to`。
- `holds`。
- 结构化 alias。
- 明确 source_id / external_id。

这些不需要 LLM。

### 7.2 LLM 辅助抽取

LLM 只处理：

- 文本中未显式结构化的实体提及。
- 原文对影响方向的语义表达。
- 候选 `benefits_from` / `hurt_by`。
- 候选 `causal_hint`。
- Wiki 页面摘要和对比。

LLM 输出必须携带：

- 原文 span 或 source chunk。
- confidence。
- reason。
- 是否需要复核。

没有原文证据的 LLM 输出不能进入 active edge。

### 7.3 金融新闻抽取策略

金融 Adapter 第一版必须内置一套可复用的新闻/公告/政策抽取策略，作为 `news_articles`、`policy_news`、`document_chunk` 的标准处理方式。

输入 contract：

| 字段 | 说明 |
|---|---|
| `source_id` | 外部源稳定 ID，例如 `ft_news:83904` |
| `title` | 标题，必填 |
| `summary` | 摘要，可选 |
| `text` | 正文或拼接文本，可选 |
| `published_at` | 发布时间，必填 |
| `source_name` | 来源名称，可选 |
| `url` | 原文链接，可选 |
| `symbols` | 业务侧已知股票代码，可选，作为强 hint |

抽取输出：

| 输出 | 说明 |
|---|---|
| `mentioned_entities` | 原文明确提到的股票、基金、行业、概念、机构、宏观指标 |
| `affected_entities` | 原文明确影响的实体，必须包含 direction、confidence、reason |
| `evidence_spans` | 支撑实体或关系的标题/摘要/正文片段 |
| `relation_candidates` | `affects`、`benefits_from`、`hurt_by`、`causal_hint` 等候选关系 |
| `quality_flags` | 低置信、无 span、实体歧义、方向不明等质量标记 |

处理原则：

1. 已有强 ID 的字段优先，例如 `symbols`、股票代码、基金代码，不交给 LLM 重判。
2. LLM 只补充文本中隐含但有证据的实体和影响方向。
3. `mentions` 可以在有原文 span 时进入 active；`affects` 默认 candidate，只有原文明确表达且置信度足够时才允许 active。
4. `benefits_from`、`hurt_by`、`causal_hint` 默认 candidate 或 review_required。
5. 所有 LLM 输出必须绑定原文 span；没有 span 的结果只能丢弃或进入复核，不能写成事实边。
6. 抽取失败不能阻断结构化事实编译；该 source 应保留 evidence，并记录 warning。

这套策略的目标是让 Financial Adapter 真正承担“把普通新闻翻译成金融知识”的职责，而不是只搬运业务侧已经抽好的实体关系。

### 7.4 写入时沉淀

借鉴 llm-wiki 和 LightRAG 的思路，金融 Adapter 不应只等查询时再拼上下文。写入时应沉淀：

- 实体页材料。
- 事件页材料。
- 概念/行业页材料。
- 影响链索引。
- 查询可复用的上下文片段。

但这些都是索引材料，事实源仍是 `kg_*`。

## 8. L1 接入

L1 事件识别应消费 KG，但不能自己维护一套独立知识规则。

### 8.1 KG 给 L1 的输入

- 标准实体 ID。
- alias 和歧义候选。
- 概念/行业邻域。
- 已知政策、事件、机构词表。
- 可解释的候选影响对象。

### 8.2 L1 给 KG 的输出

- `event_record`。
- L1 evidence。
- `mentions`。
- `affects` candidate。
- 需要复核的实体或关系。

### 8.3 禁止事项

- L1 不能直接写 `kg_edges`。
- L1 不能维护独立金融 ontology。
- L1 不能把 `affected_stocks` 当成无证据 active edge。

---

## 9. L2 接入

L2 事件流和主线识别不再只靠标签重叠，而应使用图结构：

| 信号 | 来源 |
|---|---|
| 共享实体 | event -> mentions |
| 共享概念/行业 | event -> concept/industry |
| 图路径 | event -> concept -> stock / policy |
| 社区 | graph analytics |
| 时间连续性 | event_time / observed_at |
| 证据来源 | evidence source |
| 弱边过滤 | confidence/status |

L2 可以产出：

- 主线候选。
- 事件归并反馈。
- 弱关系降权反馈。
- 主题 Wiki 页面候选。

这些产出必须通过 `feedback_record` 或 Adapter 输出回写，不能直接改事实库。

---

## 10. L3 接入

L3 基金映射和交易信号通过 KG 做影响传播：

```text
event / policy
  -> concept / industry
  -> stock
  -> fund holding
  -> fund exposure
```

### 10.1 可进入硬评分的关系

- 高置信 `holds`。
- 高置信 `belongs_to`。
- 人工确认的关键产业链关系。
- 原文明确影响且 evidence 充分的 `affects`。

### 10.2 只能进入候选或解释的关系

- `related_to`。
- `causal_hint`。
- 低置信 `benefits_from` / `hurt_by`。
- 仅由 LLM 推断的影响链。

### 10.3 L3 输出要求

L3 的每条影响链必须返回：

- path。
- relation_type。
- confidence。
- evidence_refs。
- 哪些边用于 hard score。
- 哪些边只用于 explanation。

## 11. 投研问答和混合检索

金融问答同时支持两种检索模式：

| 模式 | 默认场景 | 说明 |
|---|---|---|
| Agentic A-RAG | 交互式投研、复杂归因、多跳探索 | Agent 在工具白名单和预算约束内自主选择检索工具、迭代读取证据 |
| Deterministic Hybrid | 批处理、评测回放、交易硬逻辑前置筛选 | 固定 plan 执行，便于复现、压测和审计 |

Agentic A-RAG 默认工具链：

```text
query
  -> intent classification
  -> entity_resolve
  -> keyword_search / semantic_hybrid_search
  -> graph_search
  -> wiki_search
  -> chunk_read
  -> RRF / rerank / dedupe
  -> evidence-bounded context
```

Agentic 检索适用于：

- 多跳影响链验证。
- 主线归因。
- 两个概念或基金的差异分析。
- 某政策对一组基金的间接影响。
- 用户没有给出精确实体、需要系统自主探索相关证据的问题。

Agentic 检索必须受工具白名单、调用次数、graph depth、chunk 数量和 context budget 约束。Agent 输出只能作为投研上下文和候选证据，不能直接生成 hard-consume 交易关系。

## 12. 金融 Wiki

金融 Adapter 定义页面结构，通用 Wiki Builder 负责生成和维护。

| page_type | subject | 核心内容 |
|---|---|---|
| `stock_page` | stock | 基本信息、行业概念、近期事件、影响链、基金暴露 |
| `fund_page` | fund | 持仓、风格暴露、近期受影响事件、风险敞口 |
| `concept_page` | concept | 定义、成分股、上下游、历史事件、政策敏感点 |
| `industry_page` | industry | 核心公司、产业链、政策敏感点、资金关注 |
| `event_page` | event | 摘要、证据、影响实体、后续验证 |
| `policy_page` | policy | 政策内容、发布机构、受益/受损方向、证据 |
| `theme_page` | concept/event group | 主线、核心节点、时间演化、分歧点 |

Wiki 页面必须保留：

- source/evidence 引用。
- 更新时间。
- confidence summary。
- 冲突或待复核标记。

Wiki 允许成为 Agent 的主要阅读入口，但不能替代事实库。

## 13. 质量治理

金融 KG 的高风险点：

| 风险 | 治理方式 |
|---|---|
| 股票简称歧义 | 强 ID 优先，alias 复核 |
| 概念过宽 | 限制 `related_to`，监控超级概念 |
| LLM 过度推断 | 默认 candidate/review_required |
| 事件重复 | source_id + 标题相似 + 时间窗口归并 |
| 持仓过期 | report_date 和 valid window |
| 政策影响误判 | 原文 evidence + 人工复核 |
| 弱边污染 L3 | consumption policy 禁止硬评分 |

质量指标：

- active edge evidence 覆盖率。
- candidate/review_required 比例。
- alias 冲突数量。
- `related_to` 占比。
- `event -> stock -> fund` 可解释路径比例。
- L1/L2/L3 Bad Case 回写率。

金融 Adapter 第一版必须提供固定 fixture，不依赖真实外部 API。

```text

  industry_components.json

  policy_news.json
  l1_events.json
  feedback_records.json
  expected_nodes.json
  expected_edges.json

  expected_paths.json
  expected_context.json
```

fixture 必须覆盖：

1. 股票基础信息入图。
2. 股票属于行业/概念。
3. 基金持仓到股票。
4. 政策新闻提到概念和股票。

9. alias 冲突进入复核。

## 15. 验收标准

Financial KG Adapter 合格的标准：

1. 金融实体和关系只存在于金融 Adapter，不进入平台硬编码。
2. 每类金融数据源的 required fields、幂等键和 evidence policy 清楚。
3. 结构化关系和 LLM 语义关系的边界清楚。
4. 每类关系的默认 status、confidence 和 consumption policy 清楚。
5. 能通过 fixture 生成稳定 nodes / edges / evidence。
6. 能经通用 Compiler 写入 `kg_*`。
7. 能检索 `event -> concept/industry -> stock -> fund` 最小影响链。
8. 投研问答能返回 keyword / graph / wiki / chunk_read 混合上下文。
9. active edge 全部有 evidence。
10. L1/L2/L3 只消费 KG，不绕过 KG 写关系。

## 16. 与实施方案的关系

只有本文档补完整后，后续技术实施方案才有价值。

实施顺序应是：

```text
通用事实库
  -> 通用 Compiler 最小闭环
  -> 通用 Retrieval / Wiki 最小闭环
  -> Financial KG Adapter
  -> L1/L2/L3 接入
```

金融 Adapter 不应该早于通用闭环编码，但金融设计必须提前定清楚，因为通用闭环要能支撑真实金融落地需求。
