# 知识图谱对外服务接口设计方案

> 本文档解决一个明确问题：知识图谱核心能力已经在应用服务层跑通，但外部系统还不能通过稳定 HTTP API 或 CLI 使用。
> 下一阶段应优先把“编译图谱、重建 Wiki/索引、检索上下文、质量扫描、复核队列”封装成正式对外服务。

---

## 0. 一句话说清楚

知识图谱对外服务层的职责是把内部 `KnowledgeService` 能力变成稳定、可测试、可运维的入口：

```text
src/interfaces/api/routes/knowledge.py
src/interfaces/cli/knowledge.py
  -> src/application/services/knowledge_service.py
  -> Knowledge Compiler / Wiki / Retrieval / Quality
  -> PostgreSQL kg_* Fact Store
```

它不重新实现图谱逻辑，不绕过 Compiler，不直接让调用方写 `kg_nodes` / `kg_edges` / `kg_evidence`。

---

## 1. 必须遵循的架构约束

知识图谱 HTTP API 必须遵循项目当前的简化 DDD 分层架构：

```text
interfaces -> application -> domain -> infrastructure
```

对应到代码边界：

| 层 | 代码位置 | 知识图谱职责 |
|---|---|---|
| interfaces | `src/interfaces/api/routes/knowledge.py`、`src/interfaces/cli/knowledge.py` | 只处理 HTTP/CLI 入参、调用应用服务、返回 JSON 或命令行输出 |
| application | `src/application/services/knowledge_service.py`、`src/application/dto/knowledge_dto.py` | 编排 use case、选择 adapter、组装 repository、转换 DTO |
| domain | `src/domain/knowledge/`、`src/domain/knowledge_adapters/` | 编译、归一、关系、证据、Wiki、检索、质量规则 |
| infrastructure | `src/infrastructure/persistence/repositories/knowledge_repository_impl.py`、`src/infrastructure/persistence/models/knowledge.py` | SQLAlchemy model、PostgreSQL repository、事务与持久化 |

### 1.1 Route 必须保持薄层

`src/interfaces/api/routes/knowledge.py` 只能做这些事情：

- 定义路由、summary、tags。
- 使用 Pydantic 校验 HTTP 请求体和 query 参数。
- 调用 application service。
- 把应用层 DTO 转成 `dict` 返回。
- 把已知异常转换成 `HTTPException`。

Route 不能做这些事情：

- 不能直接实例化 `KnowledgeCompiler`。
- 不能直接导入 `KnowledgeRepositoryImpl` 操作数据库。
- 不能直接导入 `FinancialKGAdapter` 写金融业务规则。
- 不能自己拼 node、edge、evidence。
- 不能把 query/rebuild/quality 的业务逻辑写在 route 函数里。

### 1.2 Application Service 负责用例编排

应用层是接口层和领域层之间的唯一入口。知识图谱对外 API 应统一落到 `KnowledgeService` 或其同层 facade 上。

应用层可以：

- 根据 `adapter_name` 选择 Adapter。
- 根据 `target` 或默认配置创建 repository。
- 调用 compile、rebuild、retrieval、quality 等领域能力。
- 生成稳定 DTO。
- 控制同步/异步模式的用例边界。

应用层不应该：

- 写 FastAPI `Request` / `Response` 相关逻辑。
- 依赖 CLI click 对象。
- 把 HTTP 状态码写入领域逻辑。

### 1.3 Domain 保持领域纯度

`src/domain/knowledge` 是通用知识基础设施，不能因为 HTTP API 增加而引入 FastAPI、click、SQLAlchemy session、环境变量读取等依赖。

金融相关规则继续放在 `src/domain/knowledge_adapters/financial`，不能写到通用 route 或通用 compiler 里。

### 1.4 Infrastructure 只做技术适配

PostgreSQL 的表结构、SQLAlchemy model、repository 实现留在 `src/infrastructure/persistence`。外部服务接口不直接依赖这些实现细节。

如果 route 需要选择 test/prod 目标，也只能把 `target` 传给 application service，由 application service 组装基础设施依赖。

---

## 2. 为什么这部分必须优先实现

当前核心能力虽然已经实现，但调用方式还是 Python 应用服务层。这会带来几个问题：

| 问题 | 后果 |
|---|---|
| 只能写 Python 调用 | L1/L2/L3、任务调度、外部工具无法稳定接入 |
| 没有统一请求协议 | 每个调用方都可能自己拼 adapter、records、options |
| 没有统一错误语义 | 数据错误、规则错误、质量错误、系统错误难以区分 |
| 没有任务状态 | 编译、重建索引、质量扫描可能耗时，调用方无法追踪 |
| 没有 API 级测试 | 核心能力通过了，但服务能力无法验收 |

因此下一阶段优先级应调整为：

```text
先补齐对外服务层
再继续扩展更多金融规则和更复杂检索能力
```

否则后续即使内部能力继续增加，也很难被系统稳定消费。

---

## 3. 设计边界

### 3.1 服务层应该负责

- 参数校验。
- 适配器选择。
- 调用应用服务。
- 返回统一响应。
- 记录运行任务。
- 暴露健康检查、编译、重建、检索、质量扫描、复核队列接口。
- 为 CLI 提供同等能力。

### 3.2 服务层不应该负责

- 不直接写数据库表。
- 不重新实现实体归一和关系编译。
- 不把业务规则写在 API route 里。
- 不让调用方直接上传任意 SQL 或内部模型对象。
- 不把 Wiki 或索引当作事实源。

---

## 4. 调用方

第一版主要服务这些调用方：

| 调用方 | 使用能力 |
|---|---|
| 手动调试 | CLI 编译 fixture、重建索引、跑查询、跑质量扫描 |
| 定时任务 | 周期性编译新增数据、重建受影响索引 |
| L1 事件识别 | 识别前查实体候选、识别后写事件入图 |
| L2 事件流 | 查询事件路径、社区、相似事件和证据链 |
| L3 基金映射 | 查询 `event -> concept/industry -> stock -> fund` 影响链 |
| 投研问答 | 获取结构化 research context |
| 质量治理 | 查看 review queue、执行人工确认/拒绝 |

---

## 5. 接口设计原则

### 5.1 用例接口，不是表接口

API 应该围绕业务用例设计：

- compile
- rebuild wiki
- rebuild indexes
- build research context
- quality scan
- review action

不应该暴露：

- insert node
- insert edge
- delete evidence
- update arbitrary properties

节点、边、证据必须由 Compiler 和 Adapter 生成，不能让外部调用方绕过治理链路。

### 5.2 Adapter 显式选择

所有接口必须显式指定 `adapter_name`：

```text
financial
toy
future_code
future_enterprise
```

第一版只支持 `financial`，但接口不能写成金融专用。金融相关的业务快捷接口可以单独挂在金融命名空间下。

### 5.3 同步接口与异步任务并存

按耗时分两类：

| 类型 | 处理方式 |
|---|---|
| health、查询、review list | 同步返回 |
| compile、rebuild wiki、rebuild indexes、quality scan | 支持同步小任务，也支持异步 run |

第一版可以先实现同步接口，但请求和响应结构要预留 `run_id`，避免后续改协议。

### 5.4 与现有 API 风格保持一致

当前项目已有 API 多数返回直接 JSON 对象，并通过 `HTTPException` 表达错误。因此知识图谱 API 不引入强制的全局 envelope，不要求所有接口都包一层 `ok/data/error`。

知识图谱接口应该返回“用例结果对象”，风格类似：

```json
{
  "adapter_name": "financial",
  "run_id": "kg_run_xxx",
  "nodes": 12,
  "edges": 8,
  "evidence": 20,
  "failed_records": 0,
  "warnings": []
}
```

失败时使用 FastAPI 当前通用风格：

```json
{
  "detail": "adapter_name 必须是 financial"
}
```

如果后续要引入统一 envelope，应该作为全站 API 中间件或统一响应规范推进，而不是只在知识图谱 API 局部制造另一种风格。

### 5.5 幂等和可追踪

写入类接口必须支持：

- `source_id` 幂等。
- `request_id` 去重。
- `run_id` 追踪。
- 编译结果写入 `kg_compilation_runs`。
- 返回节点、边、证据数量和失败记录数量。

## 6. 对外能力设计

本设计方案只定义对外服务要暴露哪些“能力”，不在这里展开每个 HTTP 字段和 CLI 参数。字段级请求/响应、Pydantic 模型、curl 示例和测试用例放到实施方案：

```text
../../3. 实施方案/4. 知识图谱/12. Step 11 · 知识图谱HTTP API与CLI服务化技术实施方案.md
```

### 6.1 能力分组

| 能力组 | 对外能力 | 设计目的 |
|---|---|---|
| 健康与能力发现 | health、capabilities | 让调用方知道服务是否可用、支持哪些 adapter 和操作 |
| 写入侧编译 | compile | 把原始/聚合材料通过 Adapter 和 Compiler 写入 KG 事实库 |
| 可重建索引 | rebuild wiki、rebuild indexes | 从事实库重建 Wiki、图邻接、证据 chunk 等索引 |
| 查询侧上下文 | research context、entity resolve、path search | 给 L1/L2/L3、投研问答和外部工具返回结构化上下文 |
| 质量治理 | quality scan、review queue、review action | 发现坏数据、冲突和高风险候选事实，并形成复核闭环 |
| 任务追踪 | run status | 为后续异步编译和重建提供追踪能力 |

第一版优先完成：

```text
health
compile
rebuild wiki
rebuild indexes
research context
quality scan
```

第二版再补：

```text
financial resolve entities
financial paths
review action
async runs
```

### 6.2 API 形态原则

HTTP API 使用统一前缀：

```text
/api/kg
```

接口命名按“用例”组织，不按表组织：

```text
compile / rebuild-wiki / rebuild-indexes / research-context / quality-scan
```

禁止暴露表级 CRUD：

```text
insert-node / update-edge / delete-evidence
```

### 6.3 CLI 形态原则

CLI 与 HTTP API 使用同一批应用层 DTO 和 `KnowledgeService`，只作为本地调试和运维入口：

```text
python -m src.interfaces.cli.main kg ...
```

CLI 不允许重新实现业务逻辑，也不允许直接操作 repository。

---

## 7. 模块划分设计

为了降低耦合，HTTP API 和 CLI 不应该各自实现一套知识图谱调用逻辑。建议按下面方式拆分：

| 模块 | 职责 |
|---|---|
| `src/interfaces/api/routes/knowledge.py` | FastAPI route，薄层 HTTP 入口 |
| `src/interfaces/cli/knowledge.py` | click 命令，薄层 CLI 入口 |
| `src/application/dto/knowledge_dto.py` | 应用层输入/输出 DTO，供 API 和 CLI 共用 |
| `src/application/services/knowledge_service.py` | 知识图谱用例编排入口 |
| `src/application/services/knowledge_adapter_registry.py` | adapter 注册和选择，屏蔽金融 adapter 细节 |
| `src/domain/knowledge/*` | 通用知识领域逻辑 |
| `src/domain/knowledge_adapters/financial/*` | 金融 adapter 规则 |
| `src/infrastructure/persistence/repositories/knowledge_repository_impl.py` | repository 技术实现 |

### 7.1 API 与 CLI 共用应用层 DTO

API 的 Pydantic 请求模型可以放在 route 文件内或接口层 schema 文件中，但进入应用层后应转换为应用 DTO 或普通 dict，不能把 FastAPI/Pydantic 对象一路传入 domain。

CLI 也应调用同一批应用层方法，不能重新写一套：

```text
HTTP request -> route model -> application DTO -> KnowledgeService
CLI args     -> command      -> application DTO -> KnowledgeService
```

### 7.2 Adapter Registry

Adapter 选择必须集中管理：

```text
adapter_name = financial
  -> FinancialKGAdapter()
```

不要在每个 route 或 CLI 命令里散落 `if adapter_name == "financial"`。这样未来增加 `code`、`enterprise`、`legal` adapter 时，只扩展 registry，不修改每个接口。

### 7.3 Repository 组装位置

Repository 的组装应该在 application service 或 application factory 中完成：

```text
KnowledgeService.for_target(target="test")
  -> KnowledgeRepositoryImpl(target="test")
```

接口层只传 `target`，不直接依赖 `KnowledgeRepositoryImpl`。

## 8. 错误类别设计

| code | 含义 |
|---|---|
| `VALIDATION_ERROR` | 请求参数或 source contract 不合法 |
| `ADAPTER_NOT_FOUND` | adapter 不存在 |
| `ADAPTER_VALIDATION_FAILED` | adapter ontology 或输入校验失败 |
| `COMPILE_FAILED` | 编译失败 |
| `WIKI_LINT_FAILED` | Wiki lint 存在 error |
| `INDEX_REBUILD_FAILED` | 索引重建失败 |
| `QUALITY_GATE_FAILED` | 质量门槛未通过 |
| `REVIEW_ACTION_FAILED` | 复核动作执行失败 |
| `DATABASE_ERROR` | 数据库错误 |
| `INTERNAL_ERROR` | 未分类内部错误 |

错误响应必须保留可排查信息，但不能泄露数据库密码、API key、完整环境变量。

## 9. 权限和安全

第一版可以先使用内网服务假设，但接口语义要区分风险等级：

| 风险等级 | 接口 |
|---|---|
| 低 | health、research-context |
| 中 | rebuild-wiki、rebuild-indexes、quality-scan |
| 高 | compile、review action |

高风险接口后续必须支持：

- 调用方标识。
- 操作审计。
- 请求大小限制。
- 超时限制。
- 幂等键。
- 写入目标限制。

## 10. 测试验收

每个外部接口都必须有测试，不能只测内部 service。

### 10.1 单元测试

- 请求 schema 校验。
- adapter_name 校验。
- route 返回结构与现有 API 风格一致。
- 错误码映射。
- CLI 参数解析。
- route 不直接 import repository、compiler、financial adapter。

### 10.2 集成测试

- `POST /api/kg/compile` 使用 fixture 编译成功。
- `POST /api/kg/rebuild-wiki` 能生成页面。
- `POST /api/kg/rebuild-indexes` 能生成图邻接和 evidence chunks。
- `POST /api/kg/research-context` 能返回节点、边、证据。
- `POST /api/kg/quality-scan` 能写入 review queue。
- CLI 命令与 API 能力一致。

### 10.3 真实场景验收

至少保留 3 类金融真实问题：

1. 政策事件影响行业、概念、股票。
2. 股票影响基金持仓暴露。
3. L1 事件写入后能被 L2/L3 查询到。

验收标准不是“返回非空”，而是：

- 返回实体正确。
- 路径可解释。
- evidence 可回溯。
- 弱关系不会进入硬评分。
- 质量扫描能发现明显坏数据。

## 11. 分阶段实施建议

### Step A：应用层接口固化

先做：

- `knowledge_dto.py`
- adapter registry
- service factory / target repository 组装
- 错误类型和应用层结果对象

这一步的目标是让 HTTP 和 CLI 未来都调用同一套应用层入口。

### Step B：最小 HTTP/CLI 闭环

先实现：

- health
- compile
- rebuild-wiki
- rebuild-indexes
- research-context
- quality-scan

这一步完成后，知识图谱才算真正可被系统调用。

### Step C：金融快捷接口

再实现：

- financial resolve entities
- financial paths
- L1 event write
- feedback write

这一步完成后，L1/L2/L3 可以开始接入。

### Step D：任务化与运维

最后实现：

- async mode
- run status
- request_id 幂等
- operation audit
- review action 完整闭环

这一步完成后，知识图谱服务才适合长期运行。

---

## 12. 最终判断

当前缺口不是“核心能力没有写”，而是“核心能力还没有变成服务能力”。

因此下一步最优先的工程目标是：

```text
把 KnowledgeService 封装成稳定 HTTP API + CLI
并用 API/CLI 级集成测试证明编译、重建、检索、质量扫描全部可用
```

只有完成这一步，知识图谱才真正能被事件抽取、投研问答、任务调度和外部工具使用。
