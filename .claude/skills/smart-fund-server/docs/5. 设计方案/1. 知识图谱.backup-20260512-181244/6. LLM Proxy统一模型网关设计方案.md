# LLM Proxy 统一模型网关设计方案

> 本文档解决一个更底层的问题：`llm_proxy` 不应该只是 Claude CLI 或 DeepSeek 的临时适配层，而应该成为整个项目统一的模型代理层。
>
> 后续所有业务方只面向统一入口传 `model`、`messages`、`response_format` 等标准参数，不关心底层到底是 Claude CLI tmux 会话池、DeepSeek HTTP API、GLM、OpenAI 还是其他 Provider。
>
> 本文档不记录任何真实 API key。所有 key 必须只放在 `.env` 或运行环境变量中。

---

## 0. 一句话说清楚

LLM Proxy 的目标不是“接入某一个模型”，而是提供一个统一模型网关：

```text
调用方
  -> POST /v1/chat/completions
  -> LLM Proxy Gateway
      -> Model Router
          -> claude_tmux provider   # glm5.1 / Claude CLI 订阅机制 / tmux pool
          -> deepseek provider      # deepseek-v4-flash / deepseek-v4-pro HTTP API
          -> future providers       # OpenAI / GLM HTTP / local vLLM / etc.
  -> OpenAI-compatible response
```

外部使用者只需要知道：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [...]
}
```

或者：

```json
{
  "model": "glm-5.1",
  "messages": [...]
}
```

至于 `glm-5.1` 实际要走 Claude CLI tmux 会话池，`deepseek-v4-flash` 实际要走 DeepSeek OpenAI-compatible API，这些复杂度全部由 LLM Proxy 内部处理。

## 1. 设计背景

当前项目已经有：

```text
src/interfaces/api/routes/llm_proxy.py
src/infrastructure/llm_proxy/service.py
src/infrastructure/llm_proxy/tmux_backend.py
```

现状能力：

| 能力 | 当前状态 |
|---|---|
| `/v1/chat/completions` | 已有，对外是 OpenAI-compatible |
| `/v1/embeddings` | 已有，转发远程 embedding 服务 |
| Claude CLI tmux pool | 已有，用于复用交互式 Claude 会话，规避 `claude -p` 风控 |
| Claude/GLM 订阅链路 | 已有，通过 Claude CLI 配置 Anthropic-compatible 后端 |
| 并发、缓存、冷却 | 已有雏形，但和 Claude 后端耦合较重 |

当前问题：

| 问题 | 后果 |
|---|---|
| `llm_proxy` 仍以 Claude 为中心命名 | 后续接 DeepSeek、OpenAI、GLM HTTP 会继续堆特殊分支 |
| 调用方可能开始关心 Provider 细节 | 业务代码会知道 tmux、Claude CLI、DeepSeek API 等内部实现 |
| 模型名和 Provider 绑定关系没有统一治理 | `glm5.1`、`deepseek-v4-flash`、`gpt-4.1` 等别名容易散落各处 |
| 模型名到供应商的映射没有统一规则 | 同一个模型可能在不同代码里走不同供应商，成本和效果不可控 |
| Provider 的限流、重试、错误、usage 处理不统一 | 业务层会被迫处理不同模型供应商差异 |

因此，LLM Proxy 必须升级为“统一模型网关”，而 DeepSeek 接入只是这个网关的一个 Provider。

## 2. 核心设计原则

### 2.1 统一入口

所有业务方统一调用：

```text
POST /v1/chat/completions
POST /v1/embeddings
GET  /api/llm-proxy/health
```

业务方不直接调用：

- Claude CLI。
- DeepSeek SDK。
- DeepSeek HTTP API。
- OpenAI SDK。
- GLM API。
- tmux。

### 2.2 模型名驱动路由

调用方只传模型名：

```json
{"model": "glm-5.1"}
```

或：

```json
{"model": "deepseek-v4-pro"}
```

LLM Proxy 根据配置把模型名路由到对应 Provider。

模型名是对外契约，Provider 是内部实现。

### 2.3 Provider 内部各自处理复杂度

不同 Provider 的实现机制可以完全不同：

| Provider | 内部机制 |
|---|---|
| `claude_tmux` | 启动/复用 Claude CLI tmux 会话，读取 Claude JSONL 输出，执行 `/clear` |
| `deepseek` | 直接 HTTP 调 DeepSeek OpenAI-compatible `/chat/completions` |
| `openai` | 直接 HTTP 调 OpenAI-compatible API |
| `local_vllm` | 调本地或内网 vLLM OpenAI-compatible API |

调用方不应该知道这些差异。

### 2.4 统一响应

无论底层 Provider 是什么，对外都返回 OpenAI-compatible response：

```json
{
  "id": "chatcmpl-xxx",
  "object": "chat.completion",
  "created": 1710000000,
  "model": "deepseek-v4-flash",
  "choices": [
    {
      "index": 0,
      "message": {"role": "assistant", "content": "..."},
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 100,
    "completion_tokens": 50,
    "total_tokens": 150
  },
  "_proxy": {
    "provider": "deepseek",
    "requested_model": "deepseek-v4-flash",
    "upstream_model": "deepseek-v4-flash",
    "route_reason": "model_exact",
    "cache_hit": false,
    "duration_ms": 1234
  }
}
```

业务方可以读取 `_proxy` 做调试，但业务逻辑不能依赖 Provider 细节。

## 3. 总体架构

### 3.1 逻辑架构

```text
interfaces/api/routes/llm_proxy.py
  - OpenAI-compatible HTTP 入参/出参
  - 不关心具体 Provider

application/service users
  - knowledge extraction
  - event extraction
  - agentic retrieval
  - task handlers
  - trading decision assistant

infrastructure/llm_proxy
  LLMGatewayService
    - model routing
    - provider registry
    - cache
    - global policy
    - health/runtime stats

  ModelRouter
    - model alias
    - model -> provider
    - provider priority
    - provider fallback

  Providers
    - ClaudeTmuxProvider
    - DeepSeekOpenAIProvider
    - future providers
```

### 3.2 目标目录结构

```text
src/infrastructure/llm_proxy/
  __init__.py
  service.py
  types.py
  router.py
  registry.py
  policies.py
  providers/
    __init__.py
    base.py
    claude_tmux.py
    deepseek_openai.py
  tmux_backend.py
```

职责：

| 文件 | 职责 |
|---|---|
| `types.py` | `LLMProxyRequest`、`LLMProxyResponse`、`LLMProxyError` |
| `router.py` | 模型名、别名、Provider 优先级和 fallback 决策 |
| `registry.py` | Provider 注册和获取 |
| `policies.py` | 缓存、限流、重试、错误分类等通用策略 |
| `providers/base.py` | Provider 协议 |
| `providers/claude_tmux.py` | 包装现有 tmux backend |
| `providers/deepseek_openai.py` | DeepSeek HTTP Provider |
| `service.py` | LLMGatewayService，对外统一服务对象 |
| `tmux_backend.py` | 保留现有底层 tmux 会话池实现 |

第一版可以为了降低改动先保留旧 `ClaudeProxyRequest` 名称作为兼容 alias，但新设计文档和新增代码应使用 `LLMProxyRequest` 命名。

## 4. 模型路由设计

这一章只讨论 LLM Proxy 的职责：**已知调用方要使用哪个模型时，如何把这个模型请求转发到正确供应商或后端**。

LLM Proxy 不决定“知识图谱抽取应该用 flash 还是 pro”，也不决定“复杂问题应该用 GLM 还是 DeepSeek”。这些属于使用方的模型方案配置。

### 4.1 路由输入

路由器输入来自：

| 来源 | 示例 |
|---|---|
| request model | `deepseek-v4-flash`、`glm-5.1` |
| 环境变量 alias | `LLM_PROXY_MODEL_ALIASES_JSON` |
| 环境变量 model routes | `LLM_PROXY_MODEL_ROUTES_JSON` |
| 环境变量 provider priority | 同一模型可以配置优先走哪个 Provider |
| 环境变量 fallback | 主 Provider 不可用时是否允许降级到另一个 Provider |

### 4.2 路由优先级

LLM Proxy 不做业务模型选择，只做模型解析和 Provider 路由。

路由优先级：

```text
1. request.model
2. model alias normalization
3. explicit model route
4. model provider priority
5. provider fallback policy
6. default provider
```

如果调用方没有传 `model`：

```text
使用 LLM_PROXY_DEFAULT_MODEL
```

但这只是“默认模型兜底”，不是业务场景模型决策。

### 4.3 模型路由配置

建议新增：

```env
LLM_PROXY_DEFAULT_PROVIDER=claude_tmux
LLM_PROXY_DEFAULT_MODEL=glm-5.1

LLM_PROXY_MODEL_ROUTES_JSON={
  "glm-5.1": ["claude_tmux", "glm_http"],
  "sonnet": ["claude_tmux"],
  "deepseek-v4-flash": ["deepseek"],
  "deepseek-v4-pro": ["deepseek"]
}

LLM_PROXY_MODEL_ALIASES_JSON={
  "glm5.1": "glm-5.1",
  "GLM-5.1": "glm-5.1",
  "deepseek-flash": "deepseek-v4-flash",
  "deepseek-pro": "deepseek-v4-pro",
  "gpt-4.1": "glm-5.1",
  "gpt-4o": "glm-5.1"
}
```

这里的关键点是：

- `glm-5.1` 对外看起来是模型名。
- 内部可以配置优先 route 到 `claude_tmux`，也可以配置优先 route 到某个 `glm_http` 供应商。
- 同一个模型名可以有多个候选 Provider，按配置顺序选择。
- `claude_tmux` Provider 再根据 Claude CLI 配置使用 GLM Anthropic-compatible 后端或订阅机制。
- 调用方不用知道这个链路。
- fallback 只在同一个 resolved model 的候选 Provider 之间发生，不能把 `glm-5.1` 偷偷换成 `deepseek-v4-pro` 这类业务模型替换。

### 4.4 LLM Proxy 不做的事情

LLM Proxy 不负责：

- 不根据 `task_type` 判断该用哪个模型。
- 不根据业务复杂度选择 `flash/pro`。
- 不替知识图谱做“测试阶段固定模型”。
- 不把业务方案写入 Provider 路由层。

这些都应该由使用方，比如知识图谱、事件抽取、交易决策，在自己的配置层决定。

## 5. Provider 设计

### 5.1 Provider 协议

Provider 统一实现：

```text
LLMProvider.generate(request, route) -> LLMProxyResponse
LLMProvider.health() -> dict
LLMProvider.runtime_stats() -> dict
LLMProvider.supports(model) -> bool
```

Provider 不处理：

- FastAPI request/response。
- 业务 DTO。
- 知识图谱节点、边、证据。
- HTTP 状态码。

Provider 负责：

- 调上游。
- 处理 Provider 自己的认证。
- 处理 Provider 自己的请求格式。
- 处理 Provider 自己的错误和重试。
- 归一 usage。
- 返回脱敏后的 raw summary。

### 5.2 ClaudeTmuxProvider

用途：

- `glm-5.1`。
- `sonnet`。
- 通过 Claude CLI 订阅机制或 Anthropic-compatible 配置可用的模型。
- 复杂 Agent 类任务，或希望复用 Claude Code 能力的任务。

内部机制：

```text
LLMProxyRequest
  -> render prompt
  -> TmuxClaudePool.run()
  -> read ~/.claude/projects/*.jsonl
  -> parse assistant text / usage / tool_calls
  -> /clear
  -> LLMProxyResponse
```

该 Provider 继续保留：

- tmux session pool。
- sandbox home/workdir。
- 长 prompt 写入文件。
- 自动确认 TUI 弹窗。
- `/clear` 复用会话。
- Claude CLI JSONL 解析。

外部调用方完全不感知这些。

### 5.3 DeepSeekOpenAIProvider

用途：

- `deepseek-v4-flash`。
- `deepseek-v4-pro`。
- 高并发结构化抽取。
- 需要低延迟、低成本的非工具型任务。

内部机制：

```text
LLMProxyRequest
  -> OpenAI-compatible request body
  -> POST https://api.deepseek.com/chat/completions
  -> normalize response
  -> LLMProxyResponse
```

DeepSeek 配置：

```env
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_API_KEY=${YOUR_DEEPSEEK_API_KEY}
DEEPSEEK_DEFAULT_MODEL=deepseek-v4-flash
DEEPSEEK_FAST_MODEL=deepseek-v4-flash
DEEPSEEK_PRO_MODEL=deepseek-v4-pro
DEEPSEEK_TIMEOUT=180
DEEPSEEK_MAX_CONCURRENCY=5
DEEPSEEK_RATE_LIMIT_COOLDOWN_SECONDS=60
```

DeepSeek Provider 必须支持：

- OpenAI-compatible chat completions。
- `response_format={"type":"json_object"}`。
- usage 归一。
- 429 冷却。
- 500/503/网络超时有限重试。
- API key 脱敏。

### 5.4 未来 Provider

未来新增模型时不改业务层，只新增 Provider 或 route：

| Provider | 路由示例 |
|---|---|
| `openai` | `gpt-4.1`、`gpt-4.1-mini` |
| `glm_http` | `glm-5.1-http` |
| `local_vllm` | `qwen3-local`、`deepseek-local` |
| `anthropic_http` | `claude-sonnet-4.5` |

## 6. DeepSeek 官方能力和约束

根据 DeepSeek 官方文档：

- DeepSeek 支持 OpenAI-compatible API，`base_url` 为 `https://api.deepseek.com`。
- DeepSeek 也支持 Anthropic-compatible API，`base_url` 为 `https://api.deepseek.com/anthropic`。
- 当前主要模型名为 `deepseek-v4-flash` 和 `deepseek-v4-pro`。
- `deepseek-chat` 和 `deepseek-reasoner` 将于 **2026-07-24** 弃用，只能作为兼容别名，不应作为新方案主模型名。
- Chat completions 路径是 `POST /chat/completions`。
- JSON Output 需要设置 `response_format={"type":"json_object"}`，并且 prompt 中必须明确包含 `json` 字样和输出格式示例。
- DeepSeek 会动态限制并发，到达并发上限会返回 HTTP 429。

参考：

- https://api-docs.deepseek.com/zh-cn/
- https://api-docs.deepseek.com/zh-cn/api/create-chat-completion
- https://api-docs.deepseek.com/zh-cn/guides/json_mode
- https://api-docs.deepseek.com/zh-cn/quick_start/rate_limit
- https://api-docs.deepseek.com/zh-cn/quick_start/error_codes
- https://api-docs.deepseek.com/zh-cn/guides/anthropic_api

## 7. 使用方边界

LLM Proxy 不维护任何业务场景的模型方案。

正确分工是：

| 层 | 职责 |
|---|---|
| 使用方 | 根据自己的业务方案决定最终模型名 |
| LLM Proxy | 根据最终模型名转发到对应 Provider |
| Provider | 处理具体供应商协议、认证、限流、重试和响应归一 |

例如知识图谱可以在自己的文档和配置中决定：

```text
simple_extraction -> deepseek-v4-flash
complex_extraction -> glm-5.1
```

但调用 LLM Proxy 时只能传最终模型名：

```json
{"model": "deepseek-v4-flash", "messages": [...]}
```

知识图谱自己的模型方案单独维护在：

- [9. 知识图谱LLM模型方案配置设计方案.md](./9.%20知识图谱LLM模型方案配置设计方案.md)

## 8. 请求转换设计

### 8.1 统一内部请求

```text
LLMProxyRequest
  model
  messages
  system_prompt
  prompt
  temperature
  max_tokens
  response_format
  json_schema
  metadata
  timeout
  stream
```

内部可以兼容当前 `ClaudeProxyRequest(prompt, system_prompt)`，但长期应以 Chat Messages 为标准。

### 8.2 ClaudeTmuxProvider 转换

Claude CLI 不是真正 HTTP Chat Completions，因此 Provider 内部需要把 messages 渲染为交互式 prompt。

要求：

- 不再向用户暴露 `SYSTEM:\n... USER:\n...` 这种实现细节。
- 长上下文超过阈值时，继续写入 sandbox 文件，让 Claude CLI 用 Read 工具渐进读取。
- JSON 输出任务要追加明确 schema 和“只输出 JSON”的约束。
- 每次请求后执行 `/clear`，保留会话但清上下文。

### 8.3 DeepSeekProvider 转换

DeepSeek 直接使用 Chat Completions：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "temperature": 0.0,
  "max_tokens": 2000,
  "stream": false,
  "response_format": {"type": "json_object"}
}
```

JSON Output 要求：

- request 带 `response_format={"type":"json_object"}`。
- prompt 中必须明确包含 `JSON` 或 `json`。
- 有 schema 时追加 schema。
- `finish_reason=length` 视为失败。

## 10. Health 和可观测性

`GET /api/llm-proxy/health` 应返回：

```json
{
  "status": "ok",
  "default_provider": "claude_tmux",
  "default_model": "glm-5.1",
  "model_routes": {
    "glm-5.1": ["claude_tmux", "glm_http"],
    "deepseek-v4-flash": ["deepseek"],
    "deepseek-v4-pro": ["deepseek"]
  },
  "providers": {
    "claude_tmux": {
      "enabled": true,
      "backend": "tmux_pool",
      "pool_size": 10,
      "runtime": {}
    },
    "deepseek": {
      "enabled": true,
      "base_url": "https://api.deepseek.com",
      "api_key_configured": true,
      "default_model": "deepseek-v4-flash",
      "fast_model": "deepseek-v4-flash",
      "pro_model": "deepseek-v4-pro"
    }
  }
}
```

必须避免：

- 输出 API key。
- 输出 Claude config 原文。
- 输出上游 Authorization header。

每次调用 `_proxy` 中应包含：

| 字段 | 作用 |
|---|---|
| `provider` | 实际 Provider |
| `requested_model` | 调用方传入模型 |
| `resolved_model` | alias 后的模型 |
| `upstream_model` | Provider 实际发送给上游的模型 |
| `route_reason` | `model_exact/alias/default/fallback` |
| `cache_hit` | 是否命中缓存 |
| `duration_ms` | 总耗时 |
| `retry_count` | 重试次数 |

## 11. 错误、重试、限流

### 11.1 统一错误类型

内部错误应统一分类：

| 错误类型 | 示例 |
|---|---|
| `bad_request` | 请求参数错误、json schema 不支持 |
| `auth_error` | API key 错误 |
| `quota_error` | 余额不足、订阅不可用 |
| `rate_limited` | 429、请求频率限制 |
| `upstream_unavailable` | 500、503、网络超时 |
| `output_invalid` | JSON parse 失败、schema 校验失败 |
| `timeout` | Provider 超时 |

HTTP route 再把内部错误映射为合适的 `HTTPException`。

### 11.2 Provider 独立限流

不同 Provider 限流互不影响：

```text
claude_tmux semaphore / cooldown
deepseek semaphore / cooldown
openai semaphore / cooldown
```

不要用一个全局 semaphore 把所有 Provider 卡死。

Gateway 可以有总并发保护，但 Provider 必须有自己的并发限制。

### 11.3 重试策略

| 错误 | 行为 |
|---|---|
| 400 / 参数错误 | 不重试 |
| 401 / auth | 不重试 |
| 402 / quota | 不重试 |
| 429 | 不立即重试，进入 Provider cooldown |
| 500 / 503 / 网络超时 | 最多重试 1 次 |
| JSON parse 失败 | 可强化 prompt 后重试 1 次 |
| Claude tmux 会话异常 | 换 session 重试 1 次 |

---

## 12. 与使用方的关系

LLM Proxy 是通用模型供应层，不是任何业务域的事实库、策略库或模型方案中心。

它只承诺：

- 接收统一请求。
- 按模型名路由到 Provider。
- 处理 Provider 差异。
- 返回统一响应。

它不承诺：

- 不判断某个业务任务应该用哪个模型。
- 不保存知识图谱、事件抽取、交易决策的模型方案。
- 不验证业务输出是否可以入库。
- 不替业务方决定成本、质量、速度之间的取舍。

知识图谱、事件抽取、交易决策等使用方必须在自己的设计文档和配置里维护模型使用策略。

## 15. 风险和约束

| 风险 | 处理 |
|---|---|
| Provider 逻辑侵入业务层 | 业务层只调用统一 Gateway |
| 模型 alias 散落各处 | alias 只在 ModelRouter 管理 |
| API key 泄露 | health/log/test 禁止输出 key |
| LLM Proxy 混入业务模型策略 | LLM Proxy 只按 model 路由，业务策略留在使用方配置 |
| DeepSeek 429 | DeepSeek Provider 独立 semaphore + cooldown |
| Claude tmux 会话污染 | 每次请求后 `/clear`，长上下文写 sandbox 文件 |
| 不同 Provider usage 口径不同 | Gateway 归一 usage，同时保留脱敏 raw summary |
| JSON 输出不稳定 | Provider 级 JSON mode + schema 校验 + 一次重试 |

## 16. 最终结论

LLM Proxy 应成为整个项目的统一模型网关。

最终边界是：

```text
业务方只关心：
  model
  messages
  response_format

LLM Proxy 负责：
  模型路由
  Provider 选择
  Claude tmux / DeepSeek HTTP 等底层差异
  认证
  限流
  缓存
  重试
  错误归一
  usage 归一
  health 和可观测性
```

这样未来新增任意模型供应商，都不应该再改知识图谱、事件抽取、交易决策等业务代码，只需要在 LLM Proxy 中新增 Provider 或路由配置。

同时，某个业务场景“简单任务用哪个模型、复杂任务用哪个模型、测试阶段是否统一用便宜模型”，应该由该业务场景自己的模型方案配置决定，而不是写入 LLM Proxy。
