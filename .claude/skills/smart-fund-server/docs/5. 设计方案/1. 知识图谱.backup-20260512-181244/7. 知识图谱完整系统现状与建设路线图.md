# 知识图谱完整系统现状与建设路线图

> 本文档是知识图谱后续建设的主文档。
> 原 `Milvus 向量检索引入设计方案` 已合并到本文，不再作为独立设计维护。Milvus / embedding / hybrid search 不是旁路优化，而是完整知识图谱投研搜索系统的一部分。

---

## 0. 核心结论

当前系统已经跑通了 **KG 写入和弱检索闭环**，但还不是完整的投研搜索系统。

当前能力更准确地说是：

```text
业务源表
  -> Financial Adapter
  -> kg_nodes / kg_edges / kg_evidence
  -> kg_wiki_pages / kg_graph_adjacency / kg_evidence_chunks
  -> 本地 keyword/ngram 驱动的 graph/wiki/chunk 上下文拼装
```

完整系统应该是：

```text
业务源表
  -> Source Mapping
  -> Adapter Compile
  -> Fact Store
  -> Wiki / Graph / Milvus Hybrid Index
  -> Agentic A-RAG / Deterministic Plan
  -> Evidence-bounded Research Context
  -> Review / Feedback / Bad Case Replay
  -> Incremental Update
```

最关键的变化是：

- 交互式投研问答默认支持 **Agentic A-RAG**，让模型在工具白名单和预算约束内自主决定检索步骤。
- 直接采用 A-RAG 参考文章后半段推荐的 **Milvus 工程化混合检索方案**：`dense_vector + sparse_vector(BM25) + hybrid_search + RRF`。
- Milvus 不是单纯的 dense vector search，而是 **dense semantic + sparse BM25 + RRF** 的 hybrid retrieval。
- 独立 `keyword_search` 不进入正式主链路；实体和代码精确匹配归 `entity_resolve`，文本关键词匹配归 Milvus sparse BM25。
- Deterministic Plan 不是主搜索体验的替代品，而是用于 baseline 对照、fallback、批处理、低延迟接口和硬逻辑边界。
- Agentic A-RAG 的评测回放必须基于 Agentic trace，而不是用 Deterministic Plan 替代。
- 所有检索结果必须回到 `kg_*` 事实库和 evidence，不能让 Milvus、Wiki 或 Agent 输出成为事实源。

---

## 0.1 本轮讨论后的设计结论

本文档按以下结论作为后续实现准则：

1. **直接采用 Milvus Hybrid Search 作为唯一正式文本召回层**
   - 使用 dense vector 做语义召回。
   - 使用 sparse vector + BM25 做关键词和专有词召回。
   - 使用 Milvus `hybrid_search` + RRF 做融合。
   - 不再单独维护本地 `keyword_search` 作为正式工具。

2. **独立 `keyword_search` 从主链路移除**
   - 股票代码、基金代码、实体名、alias 由 `entity_resolve` 负责。
   - 文本关键词、政策名、专有短语由 Milvus sparse BM25 负责。
   - 语义相似和自然语言描述由 Milvus dense vector 负责。
   - 这样避免同时维护“本地 keyword/ngram”和“Milvus sparse BM25”两套文本检索。

3. **Agentic A-RAG 是交互式投研主路径**
   - Agent 自主决定是否查实体、查 Milvus hybrid、查图、查 Wiki、读 chunk、继续检索或停止。
   - Milvus hybrid 只解决“文本检索时不用在 keyword 和 semantic 之间二选一”。
   - A-RAG 仍负责多轮工具调用、证据观察和检索策略调整。

4. **Deterministic Plan 不是 Agentic 评测替代品**
   - Agentic A-RAG 的评测回放必须记录并回放 Agentic trace。
   - Deterministic Plan 只作为 baseline 对照、fallback、低延迟接口、批处理和 hard-logic path。
   - 不能用 deterministic plan 的结果代表 Agentic A-RAG 的真实效果。

5. **KG 仍然是系统差异化核心**
   - Milvus hybrid 负责“搜得到材料”。
   - KG graph 负责“结构关系和影响链”。
   - Agentic A-RAG 负责“怎么一步步查清楚”。
   - Evidence 机制负责“答案可追溯”。

## 2. 当前缺口

### 2.1 缺少 Milvus Hybrid Retrieval

完整目标不是继续维护一套本地 `keyword_search`，而是把文本召回统一收敛到 Milvus Hybrid Retrieval。

当前实际仍是：

```text
keyword + graph + keyword wiki + chunk_read
```

问题：

- `semantic_search` 仍为空。
- 关键词检索依赖中文 ngram，效果不稳定。
- query 和原文表达不一致时容易漏召回。
- graph search 缺少 seed 时无法展开。

必须补的是：

```text
Milvus hybrid_search
  = dense semantic search
  + sparse BM25 keyword search
  + RRF fusion
```

旧 `keyword_search` 的职责迁移：

| 旧职责 | 新归属 |
|---|---|
| 股票代码、基金代码、实体名、alias | `entity_resolve` |
| 文本关键词、政策名、专有短语 | Milvus sparse BM25 |
| 语义相似、自然语言描述 | Milvus dense vector |
| dense/sparse 融合 | Milvus hybrid_search + RRF |

### 2.2 缺少 Agentic A-RAG

完整投研问答不应该只靠固定流程。A-RAG 的核心价值是：

```text
Agent 根据问题和已观察到的结果，自主决定：
  用哪个工具
  调几次
  是否继续深挖
  何时停止
```

当前系统没有 Agentic Retrieval Controller，只能一次性运行固定检索逻辑。

### 2.3 缺少 Query Planner

即使支持 Agentic A-RAG，也仍然需要 Query Planner。Planner 的作用是为系统提供可复现的结构化解释和 deterministic 执行路径。

例如：

```text
宁德时代 300750 最近受哪些事件影响
```

应解析为：

```json
{
  "intent": "impact_events_for_entity",
  "entities": [
    {"text": "宁德时代", "type_hint": "stock"},
    {"text": "300750", "type_hint": "stock"}
  ],
  "direction": "incoming",
  "relation_filters": ["affects", "benefits_from", "risks", "mentions"],
  "time_range": "recent",
  "steps": ["entity_resolve", "graph_search", "semantic_hybrid_search", "chunk_read"]
}
```

Planner 主要用于：

- 批处理。
- deterministic baseline 对照。
- Agentic 失败或超预算时 fallback。
- 低延迟 API。
- 交易硬逻辑前置筛选。
- Agentic 检索的初始提示和工具约束。

### 2.4 缺少完整工具化检索层

当前工具还不完整：

| 工具 | 当前状态 | 完整系统要求 |
|---|---|---|
| `entity_resolve` | 有金融实体解析雏形 | 成为 Agent / Planner 可调用工具 |
| `semantic_hybrid_search` | 无 | Milvus dense + sparse + RRF |
| `graph_search` | 有基础 | 支持方向、关系类型、时间过滤 |
| `wiki_search` | 有基础 | 支持 page type、topic、语义召回 |
| `chunk_read` | 有基础 | 支持 chunk_id / evidence_id / source_id |

### 2.5 缺少质量闭环

当前没有固定 bad case 集，因此每次修复都依赖人工临时试 query。

完整系统必须有：

- bad case dataset。
- replay runner。
- retrieval trace。
- expected evidence / node / edge。
- forbidden evidence / node / edge。
- channel 命中统计。
- Agentic trace 评估。

## 3. 完整目标架构

### 3.1 总体架构

```text
Source Layer
  ft_news / ft_market_flow / ft_market_cache / ft_sentiment / ft_macro_indicators / ft_events

Compile Layer
  Source Mapping
  Financial Adapter
  LLM Extraction
  Relation Compiler
  Evidence Binder

Fact Store
  kg_nodes
  kg_edges
  kg_evidence
  kg_edge_evidence
  kg_versions
  kg_review_items

Index Layer
  kg_wiki_pages
  kg_graph_adjacency
  kg_evidence_chunks
  Milvus dense/sparse hybrid collection
  Text index

Retrieval Layer
  Agentic A-RAG
  Deterministic Plan
  Tool Registry
  RRF / rerank / dedupe

Output Layer
  answer_context
  matched_nodes
  matched_edges
  evidence_refs
  retrieval_trace
  warnings

Feedback Layer
  bad case replay
  review queue
  feedback_record
  incremental rebuild
```

### 3.2 两种检索模式

完整系统必须同时支持两种模式。

| 模式 | 默认场景 | 特点 |
|---|---|---|
| Agentic A-RAG | 交互式投研、复杂归因、多跳探索 | Agent 自主选择工具、迭代读取证据、准确度优先 |
| Deterministic Plan | baseline 对照、fallback、批处理、低延迟 API、硬逻辑边界 | 固定 plan、可复现、可压测、可审计 |

二者不是互斥关系：

- Agentic A-RAG 是投研搜索体验主路径。
- Agentic A-RAG 的评测回放基于 Agentic trace。
- Deterministic Plan 是 baseline、fallback 和硬边界保障。
- Agentic 模式可以使用 Planner 生成初始 plan，也可以偏离 plan 继续探索。
- Deterministic 模式不能调用自由 Agent 循环。

## 4. Milvus Hybrid Retrieval 设计

### 4.1 为什么引入 Milvus

不接 embedding / vector index，系统只能靠 keyword、alias、规则和图路径。它能查结构化事实，但无法稳定处理自然语言语义召回。

Milvus 的角色是：

```text
Postgres kg_* = 事实源
Milvus = 可删除、可重建的文本召回索引
```

Milvus 不替代：

- `kg_nodes`
- `kg_edges`
- `kg_evidence`
- `kg_evidence_chunks`
- 关系置信度
- hard-consume policy

Milvus 只返回候选 chunk / evidence。

### 4.2 为什么不是只做 dense vector

A-RAG 参考方案说明了三层检索工具：

```text
keyword_search   精确匹配专有词、代码、名称
semantic_search  语义匹配自然语言描述
chunk_read       精读完整证据
```

本文档采用文章后半段推荐的 Milvus 工程化方案，把 `keyword_search` 和 `semantic_search` 合并为一个正式文本召回工具：

```text
semantic_hybrid_search
  = Milvus dense semantic search
  + Milvus sparse BM25 keyword search
  + RRF fusion
```

因此，Agent 不再需要在 `keyword_search` 和 `semantic_search` 之间做二选一。

只做 dense vector 会漏掉：

- 股票代码。
- 基金代码。
- 政策名。
- 专有名词。
- 短语精确匹配。

所以 Milvus 侧应直接做 hybrid：

```text
dense_vector   -> semantic search
sparse_vector  -> BM25 keyword search
hybrid_search  -> RRF fusion
```

### 4.3 Collection 设计

第一阶段使用一个 collection：

```text
kg_evidence_chunk_vectors
```

字段建议：

| 字段 | 类型 | 说明 |
|---|---|---|
| `chunk_id` | VarChar primary key | 对应 `kg_evidence_chunks.chunk_id` |
| `evidence_id` | VarChar | 对应 `kg_evidence.evidence_id` |
| `adapter_name` | VarChar | 例如 `financial` |
| `target` | VarChar | `prod` / `test` |
| `source_type` | VarChar | `news_articles` / `derived_signal` 等 |
| `source_id` | VarChar | 原始业务 source id |
| `text` | VarChar | chunk 文本，用于 BM25 sparse 生成 |
| `dense_vector` | FloatVector | embedding 向量 |
| `sparse_vector` | SparseFloatVector | BM25 Function 自动生成 |
| `observed_at` | Int64 / VarChar | 用于时间过滤 |
| `published_at` | Int64 / VarChar | 用于新闻时间过滤 |
| `content_hash` | VarChar | 判断 chunk 是否变化 |
| `embedding_model` | VarChar | embedding 模型版本 |
| `kg_version` | VarChar | KG 版本 |

Milvus 只保存检索必要字段。展示完整内容和 payload 时必须回读 Postgres。

### 4.4 写入流程

```text
kg_evidence
  -> kg_evidence_chunks
  -> embed(chunk.content)
  -> insert/upsert Milvus:
       text
       dense_vector
       metadata
       sparse_vector 由 BM25 Function 自动生成
```

第一版可以全量重建：

1. 重建 `kg_evidence_chunks`。
2. 删除 Milvus 中当前 `adapter_name + target` 范围的旧数据。
3. 批量 embedding。
4. 批量 insert/upsert Milvus。

后续增量：

```text
new/changed chunk
  -> content_hash changed
  -> embed
  -> upsert Milvus

deprecated evidence
  -> delete Milvus chunk vectors
```

### 4.5 查询流程

```text
query_text
  -> embed(query_text)
  -> dense AnnSearchRequest
  -> sparse AnnSearchRequest(query_text)
  -> Milvus hybrid_search(reqs=[dense, sparse], ranker=RRFRanker)
  -> chunk_id / evidence_id
  -> 回读 Postgres
  -> RetrievalHit(hit_type="semantic_hybrid")
```

过滤条件至少包含：

```text
adapter_name == "financial"
target == "prod"
```

可扩展过滤：

```text
source_type in [...]
published_at >= ...
observed_at >= ...
kg_version == ...
```

### 4.6 配置项

Milvus hybrid retrieval 是知识图谱投研检索的强依赖，不允许通过环境变量关闭。

| 配置 | 默认值 | 说明 |
|---|---|---|
| `MILVUS_URI` | `./data/milvus/kg_vectors.db` | Lite 文件路径或 Server URI |
| `MILVUS_TOKEN` | 空 | Server token |
| `MILVUS_COLLECTION` | `kg_evidence_chunk_vectors` | collection 名称 |
| `MILVUS_METRIC_TYPE` | `COSINE` | dense 距离度量 |
| `MILVUS_RRF_K` | `60` | RRF 参数 |
| `MILVUS_BATCH_SIZE` | `128` | 写入 batch size |
| `EMBEDDING_DIM` | 现有配置 | 向量维度 |
| `EMBEDDING_MODEL` | 现有配置或新增 | embedding 模型版本 |

本地 Lite 模式必须安装：

```text
pymilvus[milvus_lite]>=2.6
```

Milvus 不可用时，系统必须直接报错，不允许退回本地 keyword/ngram 主链路，也不允许静默跳过 `semantic_hybrid_search`。这保证失败原因可见，避免把残缺检索误认为完整投研搜索。

## 5. Agentic A-RAG 设计

### 5.1 Agent 可用工具

Agentic A-RAG 暴露固定工具集合：

| 工具 | 作用 |
|---|---|
| `entity_resolve` | 解析股票、基金、行业、概念、政策、事件等实体 |
| `semantic_hybrid_search` | Milvus dense + sparse + RRF 混合召回 |
| `graph_search` | 多跳关系、方向关系、影响链 |
| `wiki_search` | 读取已沉淀的实体页、主题页、时间线页 |
| `chunk_read` | 根据 chunk_id / evidence_id 精读完整证据 |

### 5.2 Agent 执行方式

Agent 可以自主决定：

- 是否先解析实体。
- 是否先做 semantic hybrid search。
- 是否沿图扩展。
- 是否读取 Wiki。
- 是否读取更多 chunk。
- 是否停止并输出上下文。

示例：

```text
query: 宁德时代 300750 最近受哪些事件影响

step 1: entity_resolve("宁德时代 300750")
step 2: graph_search(target=stock:300750, direction=incoming, relations=affects, depth=2)
step 3: semantic_hybrid_search("宁德时代 最近 事件 影响")
step 4: chunk_read(evidence_ids=[...])
step 5: stop, return evidence-bounded context
```

### 5.3 Agent 约束

Agent 不能自由访问数据库，也不能生成任意 SQL。所有工具必须：

- 白名单。
- 参数化。
- 只读。
- 有超时。
- 有预算。
- 有 trace。
- 输出绑定 evidence refs。

预算建议：

| 约束 | 第一版默认 |
|---|---|
| 最大工具调用次数 | 8 |
| 最大 graph depth | 3 |
| 最大 chunk_read 数 | 20 |
| 最大 context chars | 5000 |
| 最大 agent turns | 6 |
| 最大单工具耗时 | 按工具配置 |

### 5.4 Agentic Trace

每次 Agentic 检索必须返回 trace：

```json
{
  "mode": "agentic_arag",
  "steps": [
    {
      "tool": "entity_resolve",
      "input": {"query": "宁德时代 300750"},
      "output_refs": ["kg:financial:stock:..."],
      "duration_ms": 35
    }
  ],
  "selected_evidence_refs": ["kg_ev:..."],
  "warnings": []
}
```

trace 用于：

- 调试。
- 复盘。
- bad case replay。
- 比较 agentic 和 deterministic 结果。

## 6. Deterministic Plan 设计

Deterministic Plan 用于 baseline 对照、fallback、批处理、低延迟 API 和硬逻辑边界。它不是 Agentic A-RAG 的评测替代品。

Agentic A-RAG 的真实评测必须基于 Agentic trace：

```text
query
  -> agent tool calls
  -> observations
  -> selected evidence
  -> stop reason
```

Deterministic Plan 的价值是提供一个稳定对照组，帮助判断 Agentic A-RAG 相比固定流程是否真的提升了召回和证据覆盖。

### 6.1 RetrievalPlan

建议结构：

```json
{
  "mode": "deterministic_plan",
  "intent": "impact_events_for_entity",
  "entities": [],
  "time_range": {},
  "relation_filters": [],
  "direction": "incoming",
  "steps": [
```

## 7. 完整系统工作包

### P0：暴露当前检索状态

目标：避免把当前弱检索误认为完整搜索。

必须做：

- API / CLI / Notebook 输出检索模式。
- 返回 `retrieval_channels_enabled`。
- 返回 `retrieval_channels_used`。
- 返回 `semantic_enabled`。
- 返回 `agentic_enabled`。
- 返回 `planner_enabled`。
- 当 Milvus / Agentic / Planner 未启用时返回 warning。

验收：

```text
用户能从结果中看出：
- 是否启用 Milvus hybrid search
- 是否启用 Agentic A-RAG
- 是否启用 Deterministic Planner
- 每个 hit 来自哪个 channel
```

### P1：Milvus Hybrid Retrieval

目标：补齐 dense + sparse 文本召回。

必须做：

- 引入 `pymilvus`。
- 增加 Milvus Lite 配置。
- 新增 `MilvusHybridStore`。
- 创建 `kg_evidence_chunk_vectors` collection。
- 支持 `dense_vector`。
- 支持 `sparse_vector` + BM25 Function。
- 支持 `hybrid_search` + RRF。
- `rebuild_indexes` 支持 `vector_chunks` 或 `hybrid_chunks`。
- 调用现有 embedding client 批量 embed chunks。
- Milvus 不可用时直接报错，不能降级到本地 keyword/ngram 或 Postgres text fallback。

验收 query：

```text
并购重组对哪些行业有影响
哪些方向受资本市场改革影响
低利率环境利好什么资产
海外产能兑现会影响哪些公司
中东冲突影响哪些资产
```

验收标准：

- 不依赖完全相同关键词，也能召回相关 evidence chunk。
- 精确词、股票代码、政策名不会被 dense vector 淹没。
- 每个 hit 能回到 `kg_evidence`。
- 关闭或缺失 Milvus 后系统必须失败并输出明确错误。

### P2：Retrieval Tool Registry

目标：把检索能力变成 Agent 和 Planner 都能调用的工具。

必须做：

- `entity_resolve`
- `semantic_hybrid_search`
- `graph_search`
- `wiki_search`
- `chunk_read`

每个工具必须有：

- 输入 schema。
- 输出 schema。
- 超时。
- 最大返回条数。
- evidence refs。
- trace metadata。

### P3：Agentic Retrieval Controller

目标：实现真正 A-RAG 主路径。

必须做：

- 定义 Agent 工具说明。
- 定义约束和预算。
- 支持多轮 tool use。
- 支持根据 observation 决定下一步。
- 支持停止条件：
  - evidence 足够。
  - 预算耗尽。
  - 多轮无新增信息。
  - 达到最大 turns。
- 输出 `AgenticRetrievalTrace`。

验收：

```text
同一 query 能看到 Agent 的检索路径：
entity_resolve -> graph_search -> semantic_hybrid_search -> chunk_read -> stop
```

### P4：FinancialQueryPlanner / Deterministic Plan

目标：支持可复现检索。

必须做：

- 定义 `RetrievalPlan` DTO。
- 定义 intent enum。
- 实现时间解析。
- 实现关系方向解析。
- 实现规则 planner。
- 实现 LLM planner 兜底，输出严格 JSON。
- 实现 `execute_plan(plan)`。

验收：

```text
宁德时代 300750 最近受哪些事件影响
```

必须生成：

- target entity。
- time_range。
- direction。
- relation_filters。
- retrieval steps。

### P5：Graph Search 增强

目标：让图检索能服务影响链。

必须做：

- 支持方向：
  - incoming。
  - outgoing。
  - undirected。
- 支持 relation filters。
- 支持 max depth。
- 支持时间过滤。
- 支持从 semantic hit 反推 seed nodes。
- 支持返回 path，而不只是边列表。

### P6：Wiki 增强

目标：让 Wiki 成为 Agent 可读索引。

必须做：

- entity page 增强：
  - 摘要。
  - 关键关系。
  - 近期 evidence。
  - 风险和冲突。
- topic page。
- timeline page。
- contradiction page。
- Wiki 页必须回链 evidence。

当前 “X is a concept node” 这种模板页不够用。

### P7：Agentic Trace Replay

目标：让 Agentic A-RAG 的每次检索都可复现、可对比、可评测。

必须做：

- 保存每次 Agentic 检索的 trace：
  - query。
  - retrieval_mode。
  - tool call 顺序。
  - tool input。
  - output refs。
  - stop_reason。
  - warnings。
- replay 时按原 trace 重放工具调用，比较命中 refs 和最终 context。
- bad case replay 可以选择实时重跑或 trace replay。
- trace replay 不负责生成答案，只验证检索路径和材料覆盖。

明确不做：

- 不建设 Postgres text fallback。
- 不恢复独立 `keyword_search` 主链路。
- 文本召回统一依赖 Milvus hybrid。

### P8：Quality and Bad Case Replay

  - expected edges。

  - forbidden refs。
  - expected intent。
- 增加 replay CLI。
- 比较 agentic 和 deterministic 两种结果。
- 输出 recall、evidence coverage、channel coverage、trace。

### P9：增量任务化

## 9. 验收标准

### 9.1 写入验收

- 真实业务数据可持续进入 KG。
- 重复编译幂等。
- active edge 必须有 evidence。
- LLM 抽取失败不污染主图。
- 编译失败能输出可定位原因。

### 9.2 索引验收

- Wiki、Graph、Evidence Chunk、Milvus Hybrid 都可从 Fact Store 重建。
- Milvus collection 可删除后重建。
- 索引版本和 embedding 模型版本可追踪。
- index rebuild 有任务状态和错误信息。

### 9.3 检索验收

必须稳定支持：

```text
实体影响类：
宁德时代 300750 最近受哪些事件影响

主题影响类：
并购重组影响哪些行业

资产传导类：
中东冲突对黄金和原油有什么影响

宏观环境类：
低利率环境利好哪些方向

路径解释类：
某政策通过什么链条影响新能源车

开放探索类：
最近有哪些可能影响成长股风险偏好的因素
```

每次返回必须包含：

- mode：`agentic_arag` 或 `deterministic_plan`。
- retrieval trace。
- channel hits。
- matched nodes。
- matched edges。
- evidence refs。
- context text。
- warnings。

### 9.4 Agentic 验收

Agentic A-RAG 必须满足：

- 能自主选择不同检索工具。
- 能基于上一轮 observation 决定下一步。
- 能在证据不足时继续检索。
- 能在证据充分时停止。
- 每一步有 trace。
- 最终上下文必须 evidence-bounded。

### 9.5 质量验收

- 有固定 bad case 集。
- 有 replay 结果。
- 有人工 review 入口。
- 有 feedback 回写。
- 有低置信关系隔离。
- Agentic 和 deterministic 结果可以对比。

## 10. 边界原则

### 10.1 Fact Store 是唯一事实源

以下都不是事实源：

- Milvus。
- Wiki。
- Graph adjacency。
- Agent 输出。
- Retrieval context。

它们都必须能回到：

```text
kg_nodes
kg_edges
kg_evidence
kg_edge_evidence
```

### 10.2 Agentic 输出不能直接进入 hard-consume

Agentic A-RAG 可以生成：

- 投研上下文。
- 候选证据。
- 可能关系。
- 复核建议。

不能直接生成：

- active hard-consume edge。
- 自动交易信号。
- 不带 evidence 的结构化事实。

如果 Agentic 结果要入图，必须走：

```text
feedback_record / candidate relation
  -> validation
  -> review
  -> compiler
  -> fact store
```

### 10.3 Milvus 是可重建索引

Milvus 数据损坏或模型切换时，应直接：

```text
drop collection
  -> rebuild from kg_evidence_chunks
```

不能把 Milvus 当唯一数据存储。

## 12. 最终判断

当前系统不是废的，但它只是 KG 基础设施的早期形态。

当前价值：

- Fact Store 已经成型。
- Financial Adapter 已经能把真实数据写入 KG。
- Evidence / Wiki / Graph / Chunk 基础材料已经存在。

- Milvus hybrid retrieval 缺失。
- Agentic A-RAG 缺失。
- Retrieval Tool Registry 缺失。
- Query Planner / Deterministic Plan 缺失。
- Wiki 内容薄。
- Bad Case Replay 缺失。
- 增量任务化缺失。

接下来不应该继续证明“最小闭环能跑”，而应该直接建设完整投研搜索系统：

```text
Milvus Hybrid Retrieval
Retrieval Tool Registry
Agentic Retrieval Controller
FinancialQueryPlanner
Bad Case Replay
```

这几件没完成之前，不能把系统称为完整可用的投研搜索系统。
