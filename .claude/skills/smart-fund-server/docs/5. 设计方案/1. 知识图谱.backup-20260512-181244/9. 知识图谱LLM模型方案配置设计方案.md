# 知识图谱 LLM 模型方案配置设计方案

> 本文档只讨论知识图谱作为 LLM Proxy 使用方时，如何配置不同任务使用哪个模型。
>
> LLM Proxy 只负责根据最终模型名把请求转发到对应 Provider，不负责判断知识图谱哪个场景该用哪个模型。

---

## 0. 一句话说清楚

知识图谱需要一层自己的模型方案配置：

```text
知识图谱任务
  -> KG LLM Plan 解析出最终模型名
  -> LLM Proxy
  -> Provider / 供应商 / tmux / API
```

例如：

```text
simple_extraction -> deepseek-v4-flash
complex_extraction -> deepseek-v4-pro
query_planning -> glm-5.1
```

知识图谱只把最终模型名传给 LLM Proxy：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [...]
}
```

LLM Proxy 再决定 `deepseek-v4-flash` 具体走哪个供应商，`glm-5.1` 具体走 `claude_tmux` 订阅链路还是未来某个 `glm_http` 供应商。

---

## 1. 为什么要单独做模型方案

知识图谱的 LLM 使用不是单一模型调用，而是一组不同风险、成本、延迟和质量要求的任务。

| 任务 | 特点 |
|---|---|
| 简单实体抽取 | 批量大、格式固定、成本敏感 |
| 复杂关系抽取 | 需要理解上下文，错误会污染候选关系 |
| Query Planning | 需要根据问题选择检索步骤 |
| Agentic A-RAG | 需要多步观察和调整 |
| 投研总结 | 输入长，结论需要稳 |
| 质量复核解释 | 需要解释冲突、缺证据和风险 |

这些任务不应该都写死同一个模型，也不应该把“任务到模型”的选择写进 LLM Proxy。

正确边界：

| 层 | 职责 |
|---|---|
| 知识图谱 | 决定任务使用哪个模型名 |
| LLM Proxy | 根据模型名路由到 Provider |
| Provider | 处理供应商协议和调用细节 |

## 2. 模型方案配置

建议新增知识图谱专用配置：

```env
KG_LLM_PLAN=deepseek_balanced
KG_LLM_PLANS_JSON={
  "deepseek_cheap": {
    "simple_extraction": "deepseek-v4-flash",
    "complex_extraction": "deepseek-v4-flash",
    "query_planning": "deepseek-v4-flash",
    "agentic_planning": "deepseek-v4-flash",
    "summarization": "deepseek-v4-flash",
    "quality_review": "deepseek-v4-flash"
  },
  "deepseek_balanced": {
    "simple_extraction": "deepseek-v4-flash",
    "complex_extraction": "deepseek-v4-pro",
    "query_planning": "deepseek-v4-pro",
    "agentic_planning": "deepseek-v4-pro",
    "summarization": "deepseek-v4-pro",
    "quality_review": "deepseek-v4-pro"
  },
  "glm_reasoning": {
    "simple_extraction": "deepseek-v4-flash",
    "complex_extraction": "glm-5.1",
    "query_planning": "glm-5.1",
    "agentic_planning": "glm-5.1",
    "summarization": "glm-5.1",
    "quality_review": "glm-5.1"
  }
}
```

### 2.1 方案含义

| 方案 | 用途 |
|---|---|
| `deepseek_cheap` | 前期测试、压测、低成本验证，所有任务都用 `deepseek-v4-flash` |
| `deepseek_balanced` | 简单任务用 flash，复杂任务用 pro |
| `glm_reasoning` | 简单任务用 flash，复杂推理走 `glm-5.1` |

### 2.2 为什么不是强制模型

这不是 LLM Proxy 的全局强制模型，而是知识图谱自己的方案选择。

区别：

| 类型 | 所属层 | 含义 |
|---|---|---|
| `KG_LLM_PLAN=deepseek_cheap` | 知识图谱 | 知识图谱所有任务按 cheap 方案选模型 |
| `model=deepseek-v4-flash` | LLM Proxy 请求 | 已经选好的最终模型名 |
| `LLM_PROXY_MODEL_ROUTES_JSON` | LLM Proxy | 这个模型名应该转发给哪个 Provider |

这样可以做到：

- 前期测试知识图谱全部走便宜模型。
- 上线后知识图谱切换到 balanced 或 glm_reasoning。
- LLM Proxy 不知道知识图谱的任务分类。
- 未来事件抽取也可以有自己的 `EVENT_LLM_PLAN`，互不耦合。

## 3. 任务类型定义

第一版知识图谱至少需要这些任务类型：

| 任务类型 | 用途 | 默认模型建议 |
|---|---|---|
| `simple_extraction` | 简单实体、代码、别名、明确字段抽取 | `deepseek-v4-flash` |
| `complex_extraction` | 新闻、公告、研报中的复杂实体关系候选抽取 | `deepseek-v4-pro` 或 `glm-5.1` |
| `query_planning` | 将用户问题拆成检索计划 | `deepseek-v4-pro` 或 `glm-5.1` |
| `agentic_planning` | Agentic A-RAG 多步工具选择 | `deepseek-v4-pro` 或 `glm-5.1` |
| `summarization` | evidence-bounded 投研总结 | `deepseek-v4-pro` 或 `glm-5.1` |
| `quality_review` | 质量扫描问题解释、复核建议 | `deepseek-v4-pro` 或 `glm-5.1` |

任务类型是知识图谱内部概念，不传给 LLM Proxy 做路由。

## 4. DeepSeek 模型分层参考

| 模型 | 定位 |
|---|---|
| `deepseek-v4-flash` | 快速、便宜、适合批量和简单结构化任务 |
| `deepseek-v4-pro` | 更强、适合复杂推理、长上下文、多步规划 |

建议使用方式：

| 场景 | 默认模型 | 原因 |
|---|---|---|
| 简单 JSON schema 抽取 | `deepseek-v4-flash` | 格式固定，成本敏感 |
| 金融新闻普通实体候选抽取 | `deepseek-v4-flash` 起步 | 先便宜验证，bad case 多时切换 |
| 复杂关系候选抽取 | `deepseek-v4-pro` | 需要更强上下文理解 |
| Query Planning | `deepseek-v4-pro` | 需要拆解问题和控制检索步骤 |
| Agentic A-RAG | `deepseek-v4-pro` | 需要根据观察结果多步决策 |
| 投研总结 | `deepseek-v4-pro` | 信息密度高，错误成本高 |
| 质量复核解释 | `deepseek-v4-pro` | 需要解释证据不足、冲突和风险 |

## 5. GLM / ClaudeTmux 使用参考

`glm-5.1` 对知识图谱来说只是一个模型名。

它背后具体可以由 LLM Proxy 路由到：

```text
glm-5.1 -> claude_tmux
```

也可以未来改成：

```text
glm-5.1 -> glm_http
```

知识图谱不关心。

适合使用 `glm-5.1` 的场景：

- Claude CLI tmux 链路成本更低。
- 复杂推理效果更稳定。
- 对延迟不极致敏感。
- 需要和历史 Claude CLI 任务效果保持一致。

## 6. 调用流程

知识图谱内部调用流程：

```text
任务类型
  -> 读取 KG_LLM_PLAN
  -> 从 KG_LLM_PLANS_JSON 找模型名
  -> 构造 OpenAI-compatible messages
  -> 调 LLM Proxy /v1/chat/completions
  -> 校验输出 schema
  -> 绑定 evidence
  -> 进入 Compiler / Review
```

伪流程：

```text
task_type = "complex_extraction"
model = kg_model_plan.resolve(task_type)

llm_proxy.chat(
  model=model,
  messages=messages,
  response_format={"type": "json_object"}
)
```

禁止：

- 知识图谱直接 import DeepSeek Provider。
- 知识图谱直接调用 DeepSeek API。
- 知识图谱直接操作 Claude tmux。
- 知识图谱把 Provider 名称作为业务逻辑条件。

---

## 7. 输出治理

不管模型方案怎么切，知识图谱输出治理不变：

- LLM 输出必须做 JSON/schema 校验。
- LLM 输出不能绕过 Adapter / Compiler 直接写 `kg_*`。
- LLM 推断关系默认是 `candidate` 或 `review_required`。
- LLM 生成的总结不能成为事实源，必须回溯到 evidence。
- 结构化数据能确定的关系仍优先走规则，不交给 LLM 重判。
- bad case 必须记录使用的 `KG_LLM_PLAN`、任务类型和最终模型名。

## 8. 测试方案

### 8.1 单元测试

建议新增：

```text
tests/unit/knowledge/test_kg_llm_plan.py
```

覆盖：

- `KG_LLM_PLAN=deepseek_cheap` 时所有任务解析为 `deepseek-v4-flash`。
- `KG_LLM_PLAN=deepseek_balanced` 时简单任务为 flash，复杂任务为 pro。
- `KG_LLM_PLAN=glm_reasoning` 时复杂任务为 `glm-5.1`。
- 未知 plan 报配置错误。
- 未知 task_type 报配置错误，不能静默 fallback。
- 解析结果只返回模型名，不返回 Provider。

### 8.2 集成测试

建议新增：

```text
tests/integration/knowledge/test_kg_llm_plan_with_proxy.py
```

覆盖：

- 知识图谱根据方案解析模型名。
- 调用 LLM Proxy 时 request body 只包含最终模型名。
- `deepseek-v4-flash` 路由到 DeepSeek Provider。
- `glm-5.1` 路由到 ClaudeTmux Provider。
- 不泄露 API key。

### 8.3 业务回归

每套模型方案至少跑一组小样本：

| 方案 | 必测 |
|---|---|
| `deepseek_cheap` | 基础抽取链路、JSON 合法性、成本和速度 |
| `deepseek_balanced` | 抽取质量、复杂关系 bad case |
| `glm_reasoning` | 复杂推理质量、tmux 稳定性、耗时 |

回归链路：

```text
source records
  -> LLM extraction
  -> KG compile dry-run
  -> KG compile test DB
  -> rebuild wiki/index
  -> research-context
  -> quality-scan
```

## 9. 最终结论

知识图谱需要自己的 LLM 模型方案配置，LLM Proxy 不应该承担这部分业务策略。

最终边界：

```text
知识图谱：
  task_type -> model
  schema 校验
  evidence 绑定
  Compiler / Review

LLM Proxy：
  model -> provider
  供应商调用
  限流 / 重试 / usage / health
```

这样后续切换知识图谱模型策略时，只改知识图谱方案配置；切换某个模型背后的供应商时，只改 LLM Proxy 路由配置。两件事互不耦合。
