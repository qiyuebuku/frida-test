# 数据源投影与 Source Record 设计方案

## 1. 本文解决什么问题

本文说明业务数据库中的原始数据如何变成知识图谱统一输入 `Source Record`。

知识编译器不能直接读取 `ft_news`、`ft_market_flow`、`ft_market_cache`、`ft_sentiment`、`ft_macro_indicators` 这些业务表并猜测字段含义。业务表是采集层和业务层的数据形态，字段结构、JSON 内容和更新语义各不相同；知识图谱需要的是稳定、可审计、可增量处理的输入协议。

因此在知识编译之前必须先有一层“数据源投影”：把每张业务表中的原始行转换成统一 Source Record。Source Record 是知识编译的唯一输入入口。

这不是一个全新概念。早期金融适配器方案中已经定义过 Source Mapping：`ft_news` 投影为 `news_articles` / `policy_news`，`ft_market_flow`、`ft_market_cache`、`ft_sentiment`、`ft_macro_indicators` 投影为 `derived_signal`。当前代码中 `ft_news` 投影已经有第一版实现，其他四类数据源需要在此基础上补齐。

## 2. 本文不解决什么问题

本文不负责把 Source Record 编译成实体、关系和证据；这是“知识编译与写入”模块的职责。

本文不定义实体类型、关系类型和领域语义；这是“知识建模与领域适配”模块的职责。

本文不处理实体标准化和去重规则；这是“实体标准化与去重治理”模块的职责。

本文不讨论检索、Wiki、API 和消费场景。

## 3. 核心业务对象

### 3.1 Raw Row

Raw Row 是业务表中的一行原始数据，例如一条新闻、一条资金流记录、一个市场快照、一条情绪记录或一个宏观指标。

Raw Row 不能直接进入知识编译器，因为不同表的字段含义不一致，JSONB 内容也可能随采集源变化。

### 3.2 Source Record

Source Record 是知识图谱统一输入。它必须包含来源标识、内容形态、业务时间、原始文本或结构化 payload、来源可信度和元数据。

Source Record 的作用是把业务数据格式和知识编译格式解耦。

Source Record 不能因为业务来源不同而变成多套协议。新闻、政策、资金流、市场快照、情绪和宏观指标都必须输出同一种 Source Record 结构。`source_type` 只是领域标签，用于告诉领域适配器“这条标准输入应该如何解释”，不能让编译核心反向耦合具体业务表。

### 3.3 Projection

Projection 是从 Raw Row 到 Source Record 的转换规则。它不做深度知识抽取，只做输入标准化、字段归位、来源标识、时间归位和元数据整理。

Projection 可以做轻量预处理，例如拼接标题和摘要、抽取 JSONB 中的 code/name、标记内容形态和 source type，但不能在这一层直接创建主图实体关系。

Projection 还必须区分“强事实字段”和“弱提示字段”。业务表中的 `related_stocks`、明确股票代码、指标代码这类结构化字段可以作为强线索写入 Source Record；资讯平台的 `tags`、栏目、主题标签、来源侧关键词只能作为弱提示保留在 Source Record metadata 中，不能在投影层升级为主图事实。

## 4. 输入和输出

### 4.1 输入

第一阶段必须支持这些业务表：

```sql
select * from ft_news order by created_at desc limit 100;
select * from ft_market_flow order by created_at desc limit 100;
select * from ft_market_cache order by created_at desc limit 100;
select * from ft_sentiment order by created_at desc limit 100;
select * from ft_macro_indicators order by created_at desc limit 100;
```

### 4.2 输出

输出统一为 Source Record 列表。后续知识编译器只消费 Source Record，不直接消费业务表行。

Source Record 输出必须区分两类信息：

1. 通用协议字段：来源标识、内容形态、业务时间、文本、payload、metadata。编译核心只依赖这部分。
2. 领域语义标签：例如 `news_articles`、`policy_news`、`market_flow.*`、`sentiment.*`、`macro_indicator`。这些标签只由领域适配器解释，不能成为编译核心的硬编码分支。

内容形态用于描述“这条输入是什么形式”，第一阶段至少包括：

- 文本材料。
- 结构化信号。
- 实体快照。
- 关系断言。
- 事件断言。

## 5. 数据源投影规则

### 5.1 `ft_news`

`ft_news` 是非结构化新闻和政策文本来源。

投影结果：

- `source_id`: `ft_news:{id}`
- `source_table`: `ft_news`
- `source_pk`: `id`
- 内容形态：文本材料
- `source_type`: 根据 `category`、`source`、标题和正文判断为 `news_articles` 或 `policy_news`，作为金融适配器的领域标签
- `event_time`: 优先使用 `published_at`
- `raw_text`: `title + summary + content`
- `metadata`: `source`、`source_name`、`source_reliability`、`category`、`url`、`tags`、`related_stocks`、`fingerprint`

投影职责：

- 保留原文和摘要。
- 保留新闻来源和可信度。
- 保留相关股票线索。
- 保留平台 tags，但默认作为弱提示，不直接等同于正文核心实体。
- 不直接判断最终事件类型，不直接写入主图。

source type 判断口径：

`news_articles` 和 `policy_news` 的区别不是“有没有提到政策”，而是这条材料的主语义是否是政策、监管、宏观口径或官方制度变化。

判断优先级如下：

1. `category` 是可用时的强信号，但不能作为必需字段。
   - `policy`、`macro` 优先投影为 `policy_news`。
   - `company`、`industry`、`market`、`global`、`stock` 等优先投影为 `news_articles`。
   - 当前真实库中大量 `ft_news.category` 为空，因此分类规则必须在没有 `category` 的情况下仍可运行。
2. `source` / `source_name` 是 category 缺失时的主要信号。
   - 国务院、发改委、财政部、央行、证监会、交易所、统计局、地方政府等官方或监管来源，优先投影为 `policy_news`。
   - 财经媒体、券商研报、资讯聚合源、行情源，默认投影为 `news_articles`。
3. 标题和正文是 category 缺失、来源不明确时的补充信号。
   - 标题或正文以“发布、印发、通知、意见、办法、规划、监管、改革、政策、措施、细则、征求意见”等制度性表达为主，且主语是政府、监管机构或官方组织时，可投影为 `policy_news`。
   - 如果只是新闻报道中提到了政策，但文章主线是公司、行业、市场行情或地缘事件，仍然投影为 `news_articles`，后续编译阶段可以抽取 policy 节点或 policy 相关关系。
4. 冲突或不确定时默认 `news_articles`。
   - 投影层不应该为了追求召回把大量普通新闻误标为 `policy_news`。
   - 不确定原因应写入 metadata，便于后续模块识别这条 Source Record 的分类来源。

第一版规则池必须尽量覆盖真实库中常见来源和标题模式，避免因为 `category` 为空导致全部落到普通新闻。

2026-05-13 对真实库 `ft_news` 全量统计的结论：

- 总记录数：17820。
- `category` 为空：13379。
- `category = company`：2248。
- `category = industry`：1362。
- `category = policy`：512。
- `category = macro`：319。
- 空 `category` 中最高频来源包括：同花顺、雪球、环球市场播报、市场资讯、新浪财经、新浪港股、睿见Economy、每日经济新闻、证券时报网、证券日报、央视、新华社等。

普通新闻的负向信号包括：

- 行情播报：午评、收评、盘中、开盘、尾盘、涨停、跌停、异动、拉升、跳水、主力资金、资金流向、成交额、指数涨跌。
- 公司事件：业绩预告、年报点评、季报点评、订单、产能、收购个案、回购、减持、增持、调研、评级、目标价。
- 行业和主题报道：产业链机会、板块轮动、主题投资、概念走强、需求改善、价格上涨、供需变化。
- 地缘和海外新闻：冲突、战争、军演、谈判、制裁、选举、外交表态、事故、自然灾害。除非来源是官方公告且主题是制度措施，否则默认普通新闻。
- 研报和评论：点评、简评、深度、策略、周报、月报、展望、观点、看好、建议关注。

冲突处理原则：

- `category = policy/macro` 和官方来源可以直接判为 `policy_news`。
- 媒体来源 + 政策关键词不一定是 `policy_news`，必须看主语义是否是制度发布。
- 普通新闻中抽取出的政策实体，应该在编译阶段成为 policy 节点或关系线索，而不是把整条新闻投影为 `policy_news`。
- 每次判断都要记录 `source_type_reason`，例如 `category_policy`、`official_source_pbc`、`title_policy_document_keyword`、`default_news_media_source`、`uncertain_default_news`。

这些判断结果不是临时日志，必须随 Source Record 写入 metadata：

- `source_type_reason`: 最终判定原因。
- `source_type_matched_rules`: 命中的规则列表。
- `source_type_confidence`: 分类置信度。
- `source_type_uncertain`: 是否存在不确定性。
- `source_type_candidates`: 可选，记录候选分类及理由。

后续模块不应该重新猜测当时为什么这样分类，而应该直接读取 Source Record metadata 中的分类原因、命中规则和不确定标记。

#### 5.1.1 tags 与 related_stocks 的分层投影

`ft_news.tags` 不能简单删除，也不能无脑转成 `mentioned_entities`。真实新闻源里的 tags 有时是有价值的主题线索，有时只是资讯平台的栏目标签或分发标签，例如 `A股`、`港股`、`美股`。如果投影层直接把这类泛化标签写成实体提示，会把来源侧弱标签误当成正文核心对象。

第一版采用分层策略：

- `related_stocks`、明确股票代码、明确基金代码这类结构化金融标识，是强线索。投影层可以把它们整理为后续编译可使用的实体提示。
- `tags`、栏目、频道、来源侧主题词，是弱线索。投影层必须原样保存在 metadata 中，并标记为弱提示。
- 投影层可以记录 tag 是否出现在标题或正文中，但不能据此直接生成主图实体、关系或最终事件。
- 泛化市场标签，例如 `A股`、`港股`、`美股`、`市场`、`板块`，在投影层只能作为来源侧标签保留，不能默认写入 `mentioned_entities`。

这条规则的目标不是降低信息保留，而是避免投影层把来源侧弱标签误变成强事实。弱标签后续如何参与抽取或升级，不属于本文职责，应在知识编译和实体治理设计中定义。

### 5.1.2 第一版暂不处理历史矫正

source type 误判确实会影响后续领域解释，但第一版目标是先跑通完整链路，不建设复杂的历史矫正系统。

第一版处理原则：

- 投影时尽量提高分类规则覆盖率。
- 把分类原因、命中规则和不确定标记写入 Source Record metadata。
- 不在投影层自动迁移历史数据。
- 正式的重投影和历史数据矫正，放到后续治理阶段。

当前状态：

- 已有第一版实现：`src/application/services/financial_news_projection.py`。
- 当前实现会读取 `ft_news`，结合 `category`、`source/source_name`、标题和正文关键词判断 `news_articles` 或 `policy_news`，并把分类原因、命中规则和不确定标记写入 metadata。
- 当前实现已按弱信号分层原则处理 `related_stocks` 和 `tags`：`related_stocks` 可作为强结构化线索进入 `mentioned_entities`，`tags` 仅保存在 metadata，并额外记录为 `weak_entity_hints`。
- 后续需要继续把该能力从“新闻专用投影”扩展为统一数据源投影服务，并基于真实库统计结果持续补充来源和标题模式规则池。

### 5.2 `ft_market_flow`

`ft_market_flow` 是资金流历史数据，按 `data_type + trade_date` 累积。

典型 `data_type` 包括：

- `northbound`
- `sector_flow`
- `stock_flow`
- `dragon_tiger`

投影结果：

- `source_id`: `ft_market_flow:{id}`
- `source_table`: `ft_market_flow`
- `source_pk`: `id`
- 内容形态：结构化信号
- `source_type`: `derived_signal`，作为金融适配器的领域标签
- `event_time`: `trade_date`
- `payload`: `target_ref`、`signal_type`、`observed_at`、`value`、`window`、`data`
- `metadata`: `data_type`、`trade_date`、`signal_source_type = market_flow.{data_type}`

投影职责：

- 保留资金流原始 JSONB。
- 从 `data_type` 标识这是北向、板块、个股还是龙虎榜数据。
- 不在投影层直接推断“利好/利空”，只提供可编译输入。

设计定位：

- 按早期金融适配器方案，这类数据的领域标签是 `derived_signal`，但它仍然使用统一 Source Record 协议。
- 第一版默认不调用 AI。
- 编译阶段再根据 `data_type` 和 payload 生成 signal/event node、mentions 或 related_to edge、structured/rule evidence。

### 5.3 `ft_market_cache`

`ft_market_cache` 是覆盖式市场快照缓存，每个 `data_type` 只保留最新快照。

投影结果：

- `source_id`: `ft_market_cache:{data_type}:{id}`
- `source_table`: `ft_market_cache`
- `source_pk`: `id`
- 内容形态：结构化信号
- `source_type`: `derived_signal`，作为金融适配器的领域标签
- `event_time`: `created_at`
- `payload`: `target_ref`、`signal_type`、`observed_at`、`value`、`window`、`data`
- `metadata`: `data_type`、`expires_at`、`signal_source_type = market_snapshot.{data_type}`

投影职责：

- 标识这是快照，不是历史流水。
- 保留快照过期时间。
- 对覆盖式数据生成可追踪 source id，避免最新快照覆盖后无法回放。

设计定位：

- 按早期金融适配器方案，这类数据的领域标签也是 `derived_signal`，但它仍然使用统一 Source Record 协议。
- 和 `ft_market_flow` 的区别是：`ft_market_cache` 是覆盖式快照，不是历史流水。
- 如果需要历史回放，投影层必须保留快照生成时间，否则仅靠 `data_type` 会丢失回放语义。

### 5.4 `ft_sentiment`

`ft_sentiment` 是舆情和市场情绪来源，按 `data_type + trade_date` 存储。

投影结果：

- `source_id`: `ft_sentiment:{id}`
- `source_table`: `ft_sentiment`
- `source_pk`: `id`
- 内容形态：结构化信号
- `source_type`: `derived_signal`，作为金融适配器的领域标签
- `event_time`: `trade_date`
- `payload`: `target_ref`、`signal_type`、`observed_at`、`value`、`window`、`data`
- `metadata`: `data_type`、`trade_date`、`signal_source_type = sentiment.{data_type}`

投影职责：

- 保留股吧、雪球、涨停、人气等来源数据。
- 标识情绪来源类型。
- 不在投影层直接生成交易结论。

设计定位：

- 按早期金融适配器方案，这类数据的领域标签是 `derived_signal`，但它仍然使用统一 Source Record 协议。
- 第一版应该先保留结构化情绪 payload，由编译阶段生成信号节点和证据。
- 是否进一步归纳为市场情绪事件，应由编译或领域适配器决定，不在投影层完成。

### 5.5 `ft_macro_indicators`

`ft_macro_indicators` 是宏观指标来源。

投影结果：

- `source_id`: `ft_macro_indicators:{indicator}:{period}:{source}`
- `source_table`: `ft_macro_indicators`
- `source_pk`: `id`
- 内容形态：结构化信号
- `source_type`: `derived_signal`，作为金融适配器的领域标签
- `event_time`: 优先使用 `published_at`，否则使用 `created_at`
- `payload`: `target_ref`、`signal_type`、`observed_at`、`value`、`unit`、`prev_value`、`yoy`、`mom`、`dim_tag`
- `metadata`: `source`、`indicator`、`period`、`signal_source_type = macro_indicator`

投影职责：

- 把宏观指标变成可编译的结构化 Source Record。
- 保留同比、环比、维度标签。
- 不在投影层直接判断宏观 regime。

设计定位：

- 按早期金融适配器方案，这类数据的领域标签是 `derived_signal`，但它仍然使用统一 Source Record 协议。
- 第一版应输出 `target_ref`、`signal_type`、`observed_at`、`value` 等编译所需字段。
- 宏观 regime 判断属于更高层的派生逻辑，不应混在投影层。

## 6. 核心设计决策

### 6.1 Source Record 是知识编译唯一入口

知识编译器不能直接读业务表。所有业务表必须先经过投影层。

投影层输出的是统一 Source Record 协议，而不是按业务来源拆出的多套输入格式。业务来源差异只能体现在 metadata 和领域标签中。

### 6.2 投影层不做深度语义判断

投影层只做格式标准化和来源保真，不做实体归一、关系判断和投资结论生成。

投影层可以标记内容形态和 source type，但不能替领域适配器完成深度解释。例如它可以把一条新闻标记为文本材料，把一条资金流标记为结构化信号；但它不应该在投影阶段决定最终实体归属、事件主线和投资影响结论。

### 6.3 投影结果必须可幂等

同一条原始数据多次投影，应该生成同一个 source id。这样知识编译可以安全重跑。

幂等不只依赖 source id，还需要内容 fingerprint。投影层需要为同一原始行输出稳定的来源标识和内容指纹：

- 如果同一 `source_table + source_pk/source_id` 的内容没有变化，重复投影应得到相同 fingerprint。
- 如果来源相同但正文、摘要、结构化 payload 发生变化，投影层应输出新的 fingerprint。
- 投影层只负责输出 source id、业务时间和 fingerprint，不负责判断这些字段在写入阶段如何使用。

这项设计的边界是输入稳定性，不是写入策略。

### 6.4 覆盖式快照必须保留回放语义

`ft_market_cache` 是覆盖式缓存。投影时必须明确它和历史流水不同，否则后续回放会误以为它是完整历史数据。

## 7. 模块边界

本模块负责：

- 从业务表读取 Raw Row。
- 转换为 Source Record。
- 标记内容形态和领域 source type。
- 保留来源、时间、原始 payload 和元数据。
- 区分强事实线索和弱提示线索。
- 输出稳定 source id 和内容 fingerprint。
- 统一后续编译输入。

本模块不负责：

- 实体抽取。
- 关系抽取。
- 标准化合并。
- 证据写入。
- 决定编译核心如何处理某个业务 source type。
- 检索消费。

## 8. 和其他模块的关系

数据源投影是知识图谱入口。它的输出 Source Record 会交给“知识编译与写入”模块。

如果投影层缺失，后续编译器只能直接耦合业务表，这会导致每新增一个来源都要侵入编译器，系统不可维护。

如果投影层把不同来源输出成不同协议，编译器也会被迫理解每个来源的格式。因此投影层必须把业务差异收敛到统一 Source Record 协议中，再把领域差异留给领域适配器处理。

## 9. 验收口径

该设计成立的标准是：

- 五张核心业务表都能投影为 Source Record。
- 每条 Source Record 都能追溯到原始表和主键。
- 不同业务来源共享同一种 Source Record 协议。
- 业务 source type 只作为领域标签，不作为编译核心协议。
- 同一原始行重复投影结果幂等。
- 同一原始行内容不变时，source id 和 fingerprint 保持稳定。
- 同一原始行内容变化时，fingerprint 能反映变化。
- tags 等弱提示不会默认变成主图实体；强结构化标识和弱标签必须可区分。
- 投影层不直接写主图。
- 编译器不直接读取业务表。
