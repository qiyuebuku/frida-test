# 知识建模与领域适配设计方案

## 1. 本文解决什么问题

本文说明知识图谱如何表达知识，以及为什么要把底层知识基础设施和上层领域适配器拆开。

知识图谱不能只做成金融专用系统。当前项目第一阶段服务金融投研，但后续可能接入其他业务场景。如果底层实体、关系、抽取策略、检索策略都写死为金融语义，系统很快会变成只能服务单一场景的业务脚本。

因此本设计把系统分为通用知识模型和领域适配器两层：通用层提供稳定的知识基础设施，领域适配器负责解释具体业务含义。

## 2. 本文不解决什么问题

本文不讨论原始数据如何投影为 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论同义词、别名、重复实体和规则维护闭环；这属于“实体标准化与去重治理”模块。

本文不讨论如何检索、排序、生成 Wiki 和拼装问答上下文；这属于“检索、Wiki与消费场景”模块。

本文不列具体数据库字段和代码类名；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Node

Node 表示知识图谱中的实体。实体可以是股票、基金、行业、政策、事件、机构、地区、商品、主题，也可以是其他领域中的自定义对象。

通用层只关心 Node 是一个可识别、可引用、可挂载属性、可参与关系的对象。它不直接判断“新能源车产业链”到底应该是行业还是主题，这类判断由领域适配器和治理规则完成。

### 3.2 Edge

Edge 表示实体之间的关系。关系必须有方向、类型、来源证据和置信边界。

关系不是简单的文本描述。它决定后续检索、路径扩展、策略解释和事件影响传导，因此关系类型必须由领域适配器约束，不能让 LLM 任意生成。

### 3.3 Evidence

Evidence 表示事实来源。每条关系都应该能追踪到证据；没有证据的关系只能作为候选或推断，不能作为强事实消费。

### 3.4 Domain Adapter

Domain Adapter 是领域适配器。它负责定义某个领域的实体类型、关系类型、抽取策略、置信度规则和消费边界。

金融适配器是第一个领域适配器，但不是通用层的一部分。

## 4. 输入和输出

### 4.1 输入

本模块接收已经标准化为 Source Record 的业务数据，以及领域适配器提供的本体规则。

输入包括：

- 业务来源类型。
- 候选实体和候选关系。
- 领域实体类型定义。
- 领域关系类型定义。
- 置信度和消费规则。

### 4.2 输出

本模块输出可进入编译链路的知识草稿：

- 实体草稿。
- 关系草稿。
- 证据引用。
- 置信来源。
- 消费边界。
- 校验结果。

## 5. 核心设计决策

### 5.1 通用层不写死金融字段

通用层只定义知识图谱的基础能力：实体、关系、证据、版本、Wiki、索引、检索上下文、质量治理。

金融字段、金融关系、金融事件类型都由金融适配器定义，不能渗透到通用模型里。

### 5.2 领域适配器决定业务语义

领域适配器负责回答这些问题：

- 这个领域有哪些实体类型。
- 哪些关系是合法关系。
- 哪些来源可以生成高置信事实。
- 哪些事实只能用于解释，不能用于硬评分。
- 哪些文本需要 LLM 抽取。
- 哪些数据可以规则抽取。

这样通用层可以保持稳定，领域层可以持续迭代。

### 5.3 金融适配器第一版聚焦投研闭环

金融适配器第一版不追求覆盖所有金融知识。它应该优先覆盖事件驱动交易最需要的实体和关系：

- 资产：股票、基金、商品。
- 业务分类：行业、概念、主题。
- 外部影响：政策、事件、地区、机构。
- 传导关系：影响、提及、归属、持有、相关。

第一版目标是支撑新闻入图、事件上下文检索、行业/资产影响传导和投研问答，而不是构建完整金融百科。

### 5.4 关系类型必须受控

LLM 可以提出关系候选，但不能发明无限关系类型。关系类型必须在领域适配器中定义，否则后续检索、路径扩展和策略消费会失控。

对金融场景而言，第一版应该限制在少量稳定关系上，并通过质量回放逐步扩展。

### 5.5 事实消费需要分层

不是所有事实都能进入同一消费层。结构化高置信事实可以进入硬消费，LLM 抽取结果更适合进入候选、解释或问答上下文。

金融决策链路尤其需要区分：

- 可以参与硬评分的确定性关系。
- 只能作为解释和辅助判断的语义关系。
- 需要进一步验证的候选关系。

## 6. 模块边界

本模块负责：

- 定义通用知识模型的业务含义。
- 定义领域适配器的职责边界。
- 定义金融适配器第一版覆盖范围。
- 定义实体类型、关系类型和消费分层的设计原则。

本模块不负责：

- 从数据库读取原始数据。
- 维护实体标准化规则表。
- 实现检索排序和上下文拼装。
- 编写具体代码、接口和数据库表结构。

## 7. 和其他模块的关系

“知识编译与写入”依赖本模块提供的实体和关系定义，否则无法判断 Source Record 应该编译成什么知识。

“实体标准化与去重治理”依赖本模块提供的类型边界，否则无法判断同名不同类型、近义不同名、主题和行业冲突等问题。

“检索、Wiki与消费场景”依赖本模块提供的事实语义，否则检索结果无法解释，也无法判断哪些关系能进入策略决策。

## 8. 验收口径

该设计成立的标准是：

- 通用层不包含金融专用字段。
- 新领域可以通过新增领域适配器接入，而不是重写通用基础设施。
- 金融适配器可以表达第一版投研场景需要的实体和关系。
- 关系类型受控，不允许 LLM 任意扩展关系语义。
- 不同置信来源的事实有清晰消费边界。
