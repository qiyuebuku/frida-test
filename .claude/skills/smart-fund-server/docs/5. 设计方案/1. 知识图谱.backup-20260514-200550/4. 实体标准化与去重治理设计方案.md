# 实体标准化与去重治理设计方案

## 1. 本文解决什么问题

本文说明知识图谱如何避免实体重复、类型冲突、别名混乱和错误合并。

当前真实数据进入知识图谱后，已经暴露出典型问题：同一个概念可能出现多个节点，同名实体可能被打成不同类型，主题和行业边界不清，事件标题略有差异就生成多个事件节点。如果不治理，检索虽然能找到结果，但结果会越来越脏，后续问答、事件归因、策略解释都会被污染。

实体治理不能依赖人工逐条审批，因为数据量会持续增长。正确方向是在写入前完成自动标准化判断，让规则、历史数据和 LLM 协同工作，并把规则沉淀到数据库中持续演进。

## 2. 本文不解决什么问题

本文不定义所有金融实体类型；实体类型边界属于“知识建模与领域适配”模块。

本文不讨论原始数据如何投影为 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论 Source Record 如何抽取候选实体和关系；这属于“知识编译与写入”模块。

本文不讨论检索排序和结果展示；这属于“检索、Wiki与消费场景”模块。

本文不写规则表结构、迁移 SQL 和具体算法；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Canonical Entity

Canonical Entity 是标准实体。它代表系统最终认可的实体身份，例如“宁德时代”“并购重组”“低利率环境”。

所有别名、近义说法和来源表达都应该尽量映射到标准实体，而不是反复创建新节点。

### 3.2 Alias

Alias 是实体别名或等价表达。例如“宁德时代新能源科技股份有限公司”和“宁德时代”可以指向同一标准实体。

别名不是简单字符串替换，它需要考虑类型、领域、上下文和证据来源。

### 3.3 Normalization Rule

Normalization Rule 是实体标准化规则。规则必须落库，不能只写死在代码中。

规则既可以来自初始种子，也可以来自写入过程中的 LLM 候选建议、定期扫描和质量回放。

### 3.4 Merge Audit

Merge Audit 是合并审计记录。自动合并、软合并、阻断合并都需要可回溯，方便后续定位规则为什么产生、影响了哪些数据、是否需要整改。

## 4. 输入和输出

### 4.1 输入

实体标准化的输入包括：

- 候选实体名称。
- 候选实体类型。
- 来源文本和证据。
- 上下文实体和关系。
- 已有标准实体。
- 已有归一化规则。
- 历史合并记录和质量问题。

### 4.2 输出

实体标准化输出这些结果：

- 命中已有标准实体。
- 创建新标准实体。
- 生成新规则候选。
- 触发软合并。
- 阻断强合并并记录质量问题。
- 标记后续扫描和迁移任务。

## 5. 核心设计决策

### 5.1 不允许空规则启动

系统不能在完全没有规则的情况下直接写入主图。首次启动时必须具备一批基础规则种子，例如金融常见实体类型、行业/概念边界、常见资产别名、政策和事件命名原则。

如果数据库没有规则，系统应该自动初始化基础规则，而不是让第一批数据自由生长。

### 5.2 标准化发生在写入前

实体治理不能主要依赖事后扫描。事后扫描只能补救，不能作为主路径。

正确流程是在实体写入前，先拿候选实体和已有规则、已有实体、上下文证据进行匹配。能命中已有标准实体就复用，不能命中才创建新实体或生成新规则候选。

### 5.3 LLM 参与规则维护，但不能绕过校验

LLM 适合处理近义名称、主题边界、上下文歧义和新规则候选。例如“高股息”“高股息资产”“红利资产”是否应该归并，纯字符串规则很难稳定判断。

但 LLM 不能直接决定最终主键，也不能绕过规则校验直接修改主图。LLM 的输出必须变成结构化候选，再经过规则冲突检查、类型合法性检查和证据检查。

### 5.4 自动治理优先，人工只做抽样和规则评估

系统数据量大，不能设计成人工逐条审批。

人工角色只保留在离线抽样、规则质量评估、坏例集维护和高风险规则干预上。主流程必须自动完成匹配、规则生成、规则落库、质量扫描和迁移建议。

### 5.5 合并分为强合并和软合并

强合并用于高置信、低风险场景，例如明确股票代码相同、权威外部 ID 相同、规则明确的别名。

软合并用于中等置信场景，例如近义主题、上下文高度相关但类型边界不完全确定的概念。软合并可以在检索侧合并展示，但不一定立即改写主图。

### 5.6 冲突必须显式记录

当规则、类型、证据或上下文冲突时，系统应该阻断强合并，并写入质量问题或合并审计记录。

最坏情况不是“多几个重复节点”，而是错误合并导致事实污染：错误关系被继承、检索上下文混乱、策略解释引用错误证据。因此冲突必须可见。

## 6. 模块边界

本模块负责：

- 定义实体标准化和去重治理原则。
- 定义规则必须落库和自动初始化的要求。
- 定义 LLM 参与规则维护的边界。
- 定义强合并、软合并、阻断合并的业务语义。
- 定义事后扫描和迁移的治理定位。

本模块不负责：

- 编写具体规则表字段。
- 实现具体相似度算法。
- 设计 LLM prompt 和输出 schema。
- 设计检索排序算法。

## 7. 和其他模块的关系

知识编译与写入在写入实体前必须调用本模块的标准化能力。

知识建模与领域适配为本模块提供类型边界和关系合法性边界。

检索、Wiki与消费场景需要消费本模块的标准实体、软合并结果和质量告警，以减少重复结果和错误上下文。

## 8. 验收口径

该设计成立的标准是：

- 系统首次运行时自动具备基础标准化规则。
- 新实体写入前必须经过标准化判断。
- LLM 可以生成新规则候选，但不能直接污染主图。
- 同义实体和重复主题逐步减少。
- 类型冲突不会静默进入强合并。
- 合并、阻断、迁移都有审计记录。
