# 检索、Wiki与消费场景设计方案

## 1. 本文解决什么问题

本文说明知识图谱如何被使用。

知识图谱的价值不在于“把节点和边存起来”，而在于能为事件抽取、投研问答、策略解释和复盘提供稳定上下文。检索模块需要把实体命中、关系扩展、语义搜索、Wiki 摘要和证据回读组合起来，让使用方拿到可解释、可引用、可追踪的上下文。

Wiki 是知识图谱面向阅读和问答的摘要层。它不是事实源，而是从事实库生成的可重建解释材料。

## 2. 本文不解决什么问题

本文不讨论原始业务表如何变成 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论 Source Record 如何编译写入主图；这属于“知识编译与写入”模块。

本文不定义实体和关系类型；这属于“知识建模与领域适配”模块。

本文不处理实体归一和合并规则；这属于“实体标准化与去重治理”模块。

本文不写具体 API 字段、CLI 参数和索引实现；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Query Context

Query Context 是检索输出给使用方的上下文包。它应该包含命中的实体、关系、证据、Wiki 摘要、来源引用、检索路径和质量告警。

使用方不应该直接拼数据库表或向量结果，而应该消费统一的 Query Context。

### 3.2 Knowledge Wiki

Knowledge Wiki 是根据事实库生成的摘要页面。它可以面向实体、关系、事件主线、主题和时间线。

Wiki 用于提高阅读效率和问答上下文质量，但不能替代原始证据和主图事实。

### 3.3 Retrieval Channel

Retrieval Channel 是检索通道。第一版至少需要覆盖：

- 实体解析。
- 图关系扩展。
- 语义检索。
- Wiki 搜索。
- 证据回读。

不同查询可以组合不同通道，不应该只有单一向量检索。

### 3.4 Consumer

Consumer 是知识图谱的使用方，包括投研问答、L1 事件识别、L2 事件流、L3 决策解释、复盘和质量回放。

不同 Consumer 对上下文的要求不同：问答需要可读性，策略解释需要证据链，事件识别需要实体和历史关系，回放需要可重复检索结果。

## 4. 输入和输出

### 4.1 输入

检索输入包括：

- 用户自然语言问题。
- 事件抽取任务上下文。
- 资产、行业、政策、主题等结构化查询条件。
- 检索模式，例如确定性检索、语义检索、混合检索。
- 上下文预算和证据要求。

### 4.2 输出

检索输出包括：

- 命中实体。
- 相关关系。
- 证据引用。
- Wiki 摘要。
- 路径或传导链。
- 质量告警。
- 可供 LLM 或业务模块使用的上下文包。

## 5. 核心设计决策

### 5.1 检索必须混合多通道

单纯向量检索无法稳定解决金融场景问题。比如“宁德时代最近受哪些事件影响”需要先识别资产，再沿图找事件和影响关系，再回读证据。

因此检索应组合实体解析、图搜索、语义检索、Wiki 搜索和证据回读。

### 5.2 确定性检索优先覆盖核心场景

核心投研场景不能完全依赖 Agent 自由规划。第一版应优先提供确定性检索计划，保证真实库回放可重复、质量基线可比较。

Agentic 检索可以作为增强，但不能替代确定性基线。

### 5.3 Wiki 是派生层，不是事实源

Wiki 页面可以帮助人和 LLM 快速理解实体、事件和主题，但事实判断必须回到主图和证据。

如果 Wiki 和事实库冲突，以事实库和证据为准。Wiki 可以重建，事实库不能被 Wiki 反向覆盖。

### 5.4 检索结果必须可解释

检索输出不能只有一组相似文本。它必须说明为什么命中、命中了哪些实体和关系、对应哪些证据、用了哪些检索通道。

这对金融场景尤其重要，因为后续策略解释和复盘必须知道结论来源。

### 5.5 检索侧也要做去重和质量提示

即使写入侧已经做治理，检索侧仍然需要合并重复结果、提示类型冲突、过滤低质量证据。

检索侧去重不能替代主图治理，但可以降低使用方看到脏结果的概率。

## 6. 模块边界

本模块负责：

- 定义知识图谱的消费方式。
- 定义 Query Context 的业务含义。
- 定义 Wiki 的定位。
- 定义混合检索的通道组合。
- 定义不同使用方的上下文需求。

本模块不负责：

- 从原始数据生成事实。
- 决定实体最终标准化结果。
- 定义数据库和索引字段。
- 编写 API 和 CLI 细节。

## 7. 和其他模块的关系

检索和 Wiki 消费事实库、标准实体、关系和证据。它依赖前三个模块提供干净、可追踪、可解释的数据。

检索模块发现的坏例和重复结果应该反馈给实体治理和知识编译模块，形成质量闭环。

## 8. 验收口径

该设计成立的标准是：

- 典型投研问题能返回实体、关系、证据和 Wiki 摘要。
- 检索结果能说明使用了哪些通道。
- 核心场景支持确定性回放。
- Wiki 可以重建，且不作为唯一事实源。
- 检索侧能暴露重复实体、类型冲突和低质量证据。
