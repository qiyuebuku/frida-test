# 知识编译与写入设计方案

## 1. 本文解决什么问题

本文说明 Source Record 如何被编译并写入知识图谱。

业务表中的原始数据不会直接进入知识编译器。它们必须先由“数据源投影与 Source Record”模块转换为统一 Source Record。知识编译器只负责消费 Source Record，并将其变成可追踪、可治理、可检索的知识事实。

知识编译的目标是把 Source Record 转成实体、关系、证据和版本。它不是简单的数据搬运，而是把“标准输入”变成“可进入主图的事实”。

## 2. 本文不解决什么问题

本文不负责从业务表生成 Source Record；这是“数据源投影与 Source Record”模块的职责。

本文不定义实体类型全集，也不定义金融领域的完整本体；这些属于“知识模型与领域适配”模块。

本文不讨论实体归一、重复合并和规则维护细节；这些属于“实体标准化与去重治理”模块。

本文不讨论检索策略、Query Context、Wiki 页面和问答消费；这些属于“检索与 Query Context”和“Wiki 与消费场景”模块。

本文不写数据库表字段、接口参数、类名和测试代码；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Source Record

Source Record 是知识编译的统一标准输入。它代表一条可被编译的业务材料，例如一条文本材料、一条结构化信号、一个实体快照、一条关系断言或一个事件断言。

Source Record 已经由投影层生成。编译核心不关心它来自哪张业务表，也不应该直接理解 `news_articles`、`policy_news`、`market_flow.*` 这类业务标签的含义。编译核心只关心统一协议中的内容类型、文本、结构化 payload、时间、来源和元数据。

`source_type` 是领域适配器解释的语义标签，不是新的输入协议。无论是新闻、政策、资金流、市场快照还是宏观指标，都必须先被投影成同一种 Source Record 协议。

### 3.2 Evidence

Evidence 是事实的证据载体。任何进入主图的关系都必须能追溯到证据，不能只保存一个没有来源的结论。

证据的价值不只是“证明这个事实从哪里来”，还包括支持后续问答引用、质量回放、错误定位和规则审计。

### 3.3 Knowledge Fact

Knowledge Fact 是编译后的知识结果，主要包括实体和关系。实体表达“谁或什么东西存在”，关系表达“它们之间发生了什么联系”。

编译链路不应该把所有结果都视为同等可信。结构化数据、规则抽取、LLM 抽取、外部来源和推断结果应该有不同的置信来源和消费边界。

## 4. 输入和输出

### 4.1 输入

第一阶段只接受统一 Source Record 协议。不同业务来源不能绕过协议直接进入编译器。

Source Record 至少需要表达五类信息：

1. 来源标识：这条材料来自哪里，以及如何回溯到原始数据。
2. 内容形态：它是文本材料、结构化信号、实体快照、关系断言还是事件断言。
3. 业务时间：这条材料描述的事实发生或被观测到的时间。
4. 内容载体：文本、结构化 payload 或二者组合。
5. 领域标签：由投影层给出的 `source_type`、可信度、分类原因和其他 metadata。

第一阶段重点支持的内容形态包括：

1. 文本材料：新闻、政策、公告、研报摘要等。
2. 结构化信号：资金流、市场快照、情绪、宏观指标等。
3. 实体快照：股票、基金、行业、概念等基础资料。
4. 关系断言：基金持仓、行业成分、概念成分等可由结构化数据直接确定的关系。
5. 事件断言：上游系统已经明确产出的事件类输入。

`news_articles`、`policy_news`、`market_flow.*`、`market_snapshot.*`、`sentiment.*`、`macro_indicator` 等名称只是领域标签。它们用于帮助领域适配器选择处理策略，不应成为编译核心的硬编码分支。

### 4.2 输出

知识编译输出四类结果：

1. 实体候选
   - 例如股票、行业、政策、事件、地区、商品、主题。

2. 关系候选
   - 例如 mentions、affects、belongs_to、holds、causes、supports。

3. 证据记录
   - 保存来源、片段、时间、可信度和引用路径。

4. 编译结果
   - 包含写入成功、跳过、失败、质量告警和索引刷新结果。

## 5. 核心设计决策

### 5.1 编译器只消费统一 Source Record

Source Record 是唯一编译输入。编译器不能直接读取 `ft_news`、`ft_market_flow`、`ft_market_cache`、`ft_sentiment`、`ft_macro_indicators` 等业务表。

这样做的原因是：业务表字段、外部来源格式、采集逻辑都会变化，但知识编译需要稳定的输入边界。

同时，编译核心不能把业务来源标签写死成核心逻辑。它应该按 Source Record 的通用内容形态选择基础流程，再把领域语义交给领域适配器解释。

### 5.2 编译核心和领域适配器解耦

知识编译分成两层：

1. 编译核心：负责通用流程，包括接收 Source Record、创建证据、调度适配器、执行基础校验、汇总结果、交给写入层。
2. 领域适配器：负责领域语义，包括理解 `source_type`、选择抽取策略、应用领域本体、产出实体候选和关系候选。

编译核心不能出现类似“如果 source_type 是某个金融新闻类型，就执行某段金融逻辑”的设计。新增领域、替换金融适配器或增加新的业务来源时，应该扩展领域适配器，而不是修改编译核心。

### 5.3 结构化关系优先规则抽取

能从结构化数据确定的关系应该由规则生成。例如股票代码对应股票实体，基金持仓对应基金和股票之间的持有关系，行业成分对应股票和行业之间的归属关系。

LLM 不应该负责这些确定性关系，否则会增加成本、延迟和不确定性。

### 5.4 语义不确定场景允许 LLM 参与

新闻、政策、公告、研报摘要这类文本需要语义理解。后续其他类型的 Source Record 也可能出现语义不确定、规则无法稳定判断的情况。LLM 的职责不是“直接生成最终图谱”，而是在领域适配器的约束下，把这些不确定输入转成可校验的候选事实。

LLM 在知识编译链路中的位置如下：

```text
Raw Row
  -> 数据源投影 Projection
  -> 标准 Source Record
  -> Knowledge Compiler Core
  -> Domain Adapter
  -> 规则前置分流：判断是否语义确定
     -> 规则确定：规则生成候选事实
     -> 语义不确定：LLM 生成候选事实
     -> 不可处理：跳过或失败
  -> 实体标准化与去重
  -> 关系合法性校验
  -> 证据绑定
  -> 置信度和质量门禁
  -> 写入主图
```

在本模块内，重点只定义编译链路的责任边界：

1. 数据源投影阶段不调用 LLM。它只负责把业务表 Raw Row 转成统一 Source Record。
2. 编译核心不直接调用 LLM。它只负责通用编排、证据草稿、适配器调度、结果汇总和写入前流程。
3. 领域适配器可以调用 LLM，但调用条件、输入约束、输出候选结构和允许的实体/关系类型由“知识模型与领域适配”模块定义。
4. LLM 调用之后必须进入后处理链路，不能直接写入 `kg_nodes`、`kg_edges` 或 `kg_evidence`。
5. 结构化数据能通过规则确定的实体和关系，不进入 LLM 抽取链路；只有规则无法稳定判断、需要语义解释或歧义消解时，才允许领域适配器调用 LLM。

因此，本模块只关心一件事：无论候选事实来自规则还是 LLM，都必须在写入前经过实体标准化、关系合法性校验、证据绑定、置信度判断和必要的降级处理。没有通过校验的候选只能进入告警、审计或丢弃，不能静默进入主图。

### 5.5 编译必须增量化

知识图谱不能依赖全量重建。新增 Source Record 进入时，应该只编译新增或变更的 Source Record，并增量刷新相关索引和 Wiki。

全量重建只用于规则大改、数据清理、索引损坏、质量基线重跑等明确场景。

### 5.6 写入必须支持证据幂等和版本治理

同一条业务来源材料可能被重复投影、重复编译和重复写入。写入层不能因为脚本重跑或任务重试就不断生成新的 evidence、edge 和索引内容，否则知识图谱会持续积累重复证据，检索结果也会被历史重复版本污染。

写入层必须基于 Source Record 提供的来源标识和内容 fingerprint 做幂等判断：

1. 同一 `adapter + source_type + source_id + fingerprint` 已经写入过时，重复编译应复用已有 evidence 或跳过重复写入。
2. 同一 `adapter + source_type + source_id` 的 fingerprint 发生变化时，可以生成新版本 evidence。
3. 旧版本如何保留、降级或标记为 superseded，必须由写入层明确处理，不能让多个版本都以同等 active 状态参与默认消费。
4. 默认检索和消费应该优先使用 active/latest evidence；历史版本用于审计、回放和差异分析。
5. 关系和索引刷新也要跟随 evidence 版本状态，否则旧关系会继续污染图谱邻居和检索召回。

这项能力属于知识编译与写入模块，不属于数据源投影模块。投影层只负责输出稳定 source id、业务时间和 fingerprint；写入层负责判断是否复用、是否创建新版本、旧版本如何处置。

### 5.7 弱提示字段不能直接进入主图

Source Record 可能包含强线索和弱提示。强线索通常来自结构化标识，例如股票代码、基金代码、行业代码、外部事件 ID；弱提示通常来自 tags、栏目、频道、来源侧主题词或平台分发标签。

领域适配器可以读取弱提示，但弱提示不能直接等价为主图事实：

1. 弱提示可以作为 LLM 抽取上下文、候选召回线索或歧义消解辅助。
2. 弱提示要升级为候选实体或候选关系，必须能在标题、正文、结构化 payload 或其他证据字段中找到支撑。
3. 弱提示生成的候选仍然必须经过实体标准化、关系合法性校验、证据绑定和置信度判断。
4. 泛化市场标签，例如 `A股`、`港股`、`美股`、`市场`、`板块`，不能因为出现在 metadata tags 中就自动成为 `mentioned_entities`。
5. 如果弱提示无法获得证据支撑，应保留在 evidence metadata 或抽取诊断中，而不是写入 `kg_nodes` 和 `kg_edges`。

这条规则是为了避免投影层弱标签污染主图，同时保留 tags 在后续语义理解中的潜在价值。

## 6. 模块边界

本模块负责：

- 定义 Source Record 到实体、关系、证据的编译职责。
- 定义编译核心和领域适配器之间的解耦边界。
- 定义写入前必须完成的基础校验。
- 定义增量写入和全量重建的业务边界。

本模块不负责：

- 从数据库读取原始数据并投影为 Source Record。
- 决定一个实体最终属于哪个标准实体。
- 定义所有领域实体类型和关系类型。
- 在编译核心中硬编码某个业务来源或领域 source type 的处理逻辑。
- 设计检索排序和上下文拼装策略。
- 设计 HTTP API 和 CLI 细节。

## 7. 和其他模块的关系

知识编译与写入位于数据源投影之后。它依赖“数据源投影与 Source Record”提供统一输入，依赖“知识模型与领域适配”解释领域语义和提供实体关系定义，依赖“实体标准化与去重治理”保证写入前质量，最终产出的事实被“检索与 Query Context”和“Wiki 与消费场景”消费。

如果编译层把脏数据直接写入主图，后续模块只能被动补救。因此该模块必须把质量门槛前移。

如果编译核心直接理解某个业务来源标签，系统会重新和数据源投影耦合，后续新增数据源或迁移到其他领域时会变成修改核心代码。因此业务标签只能由领域适配器消费，不能成为编译核心协议。

## 8. 验收口径

该设计成立的标准是：

- 编译器只消费统一 Source Record，不直接读取业务表。
- 编译核心只理解通用内容形态，不硬编码金融 source type。
- 同一条 Source Record 可以稳定生成可追踪证据。
- 结构化关系可以不依赖 LLM 生成。
- 非结构化文本抽取结果必须经过校验后才能进入主图。
- 新增 Source Record 可以增量进入知识图谱，不需要每次全量重建。
