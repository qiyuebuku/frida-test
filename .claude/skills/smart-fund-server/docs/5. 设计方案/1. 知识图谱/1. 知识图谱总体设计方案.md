# 通用知识基础设施与金融知识图谱总体设计方案

> 本文档的核心修正：我们不是要写一套只能服务金融投研的知识图谱系统，而是要建设一套可复用的 **Knowledge Infrastructure**。
> 金融知识图谱只是第一个落地场景，通过 `Financial KG Adapter` 接入。未来如果换成代码知识库、企业知识库、法务知识库、个人长期记忆，不应重写底层，只应替换领域适配器。

---

## 0. 一句话说清楚

最终架构分两层：

```text
通用知识基础设施
  Knowledge Compiler
  Fact Store
  Evidence / Version / Review
  Knowledge Wiki
  Hybrid Retrieval Runtime
  Graph Analytics / Quality Governance

领域适配器
  Financial KG Adapter
  未来可替换为 Code / Enterprise / Legal / Medical / Personal Memory Adapter
```

金融场景只负责定义：

- 金融有哪些实体。
- 金融有哪些关系。
- 哪些数据源能产生这些实体和关系。
- 哪些关系可以用于交易硬逻辑。
- L1/L2/L3 如何消费这些知识。

底层基础设施负责：

- 任意领域的原始材料如何标准化。
- 实体如何归一。
- 关系如何编译。
- 证据如何绑定。
- 置信度和版本如何管理。
- Wiki、图索引、全文索引、向量索引如何生成。
- 查询时如何进行 keyword / semantic / graph / wiki / chunk_read 混合召回。

---

## 1. 设计目标

### 1.1 平台目标

本项目首先要沉淀一套通用知识基础设施，而不是把金融规则写死在每个环节里。

平台层必须满足：

1. **领域无关**
   - 不出现股票、基金、行业、政策等硬编码业务概念。
   - 只理解通用概念：节点、边、证据、版本、置信度、来源、索引、查询。

2. **适配器驱动**
   - 任何领域都通过 Adapter 提供 ontology、规则、数据源映射和消费策略。
   - 金融只是第一个 Adapter。

3. **证据优先**
   - 节点和边不能只是模型总结，必须能回到原始记录、原文片段、规则输出或人工确认。

4. **可重建**
   - Fact Store 是源头。
   - Wiki、向量索引、全文索引、graphify 导出、图算法结果都必须可以从事实库重建。

5. **可增量**
   - 新数据进入后，只更新相关节点、边、证据和索引。
   - 支持旧事实废弃、降权、合并、拆分和版本迁移。

6. **可复用**
   - 金融 KG 做完后，同一套基础设施能服务投研问答、项目知识库、代码知识库、agent 长期记忆等场景。

### 1.2 金融落地目标

金融适配器的目标是把现有新闻、行情、资金、情绪、宏观、行业概念、基金持仓和事件流水线接到通用基础设施上，形成金融知识图谱。

金融层要解决：

1. L1 事件识别之前有稳定实体和关系规范。
2. L2 事件流不再只靠标签重叠，而能利用图路径、社区和证据链。
3. L3 基金映射能沿“事件 -> 概念/行业 -> 股票 -> 基金持仓”传播影响。
4. 投研问答可以同时使用关键词、语义、图路径、Wiki 和原文证据。
5. 交易相关逻辑能区分确定事实、候选事实、推断事实和歧义事实。

## 2. 两层架构

### 2.1 通用知识基础设施

| 模块 | 是否通用 | 职责 |
|---|---|---|
| Knowledge Compiler | 是 | 把原始材料编译成节点、边、证据、置信度和版本 |
| Fact Store | 是 | 保存 `nodes` / `edges` / `evidence` / `versions` / `reviews` |
| Entity Resolution | 是 | 根据强 ID、alias、规则、图邻域和人工反馈做实体归一 |
| Relation Compiler | 是 | 把确定关系、文本关系、统计关系、模型推断关系分层写入 |
| Evidence Manager | 是 | 管理原文片段、结构化字段、规则输出、LLM 输出、人工确认 |
| Text Extraction Pipeline | 是 | 提供文本抽取执行、LLM 调用、JSON 解析、证据绑定的通用管线，不内置领域规则 |
| Knowledge Wiki | 是 | 生成实体页、主题页、社区页、比较页、矛盾页 |
| Hybrid Retrieval Runtime | 是 | keyword + semantic + graph + wiki + chunk_read 混合召回 |
| Graph Analytics | 是 | 社区发现、路径分析、中心性、孤岛检测、弱边治理 |
| Adapter SDK | 是 | 约束领域适配器必须提供的 ontology、规则、输入映射和消费策略 |

平台层不应该知道“宁德时代是什么”“液冷是什么”“基金持仓是什么”。文本抽取管线也只提供执行机制，具体抽哪些实体和关系由 Adapter 决定。

### 2.2 领域适配器

领域适配器负责把业务世界翻译成平台能理解的协议。

| Adapter | 实体示例 | 关系示例 |
|---|---|---|
| Financial KG Adapter | 股票、基金、行业、概念、事件、政策 | 持有、属于、受益、受损、上游、下游、影响 |
| Code KG Adapter | 仓库、文件、模块、函数、类、Issue、PR | 定义、调用、导入、修改、依赖、修复 |
| Enterprise KG Adapter | 人、团队、项目、文档、会议、决策 | 负责、阻塞、引用、决策、替代 |
| Legal KG Adapter | 法条、案件、主体、义务、风险、合同 | 约束、适用、违反、引用、承担 |
| Personal Memory Adapter | 人、事件、地点、偏好、任务、笔记 | 发生于、相关、提醒、偏好、后续行动 |

这意味着，未来换场景时应该替换 Adapter，而不是重写 Compiler、Fact Store、Wiki 和 Retrieval。

## 3. 为什么不能做成金融专用

如果把当前系统直接写成金融专用，会产生几个长期问题：

| 问题 | 后果 |
|---|---|
| ontology 写死在代码里 | 换场景必须重写实体、关系、索引和查询逻辑 |
| L1/L2/L3 各自维护金融规则 | 规则重复、结果不一致、反馈无法复用 |
| 事实库字段只服务金融 | 未来做项目知识库、代码知识库时无法复用 |
| Wiki 只生成金融页面 | 无法沉淀成通用 agent 可读知识层 |
| 检索逻辑绑定交易场景 | 投研问答以外的场景无法使用 |

正确做法是：

```text
平台层定义稳定协议
金融层只实现协议
```

金融适配器可以很专业，但它不能污染平台边界。

## 4. 与外部方案的关系

### 4.1 不再采用 Microsoft GraphRAG 作为主路径

实测和讨论后，Microsoft GraphRAG 不适合作为生产主路径：

- 索引阶段 LLM 调用重。
- 社区报告生成慢。
- 查询链路复杂。
- 数据模型不适合作为我们的事实源。
- 对事件驱动交易场景来说，很多关系需要稳定证据、版本和业务置信度，而不是一次性图摘要。

因此它不进入主技术方案，只可作为离线实验或参考。

### 4.2 吸收 LightRAG / A-RAG / llm-wiki 的思想

| 来源 | 可吸收思想 | 不照搬原因 |
|---|---|---|
| LightRAG | 轻量图增强召回、实体关系索引、低成本查询 | 不能直接接管金融事实库和版本治理 |
| A-RAG | query planner、多路检索、rerank、工具化 RAG | 不需要完整照搬 Milvus 等外部栈 |
| llm-wiki / harness | 写入时沉淀 Wiki、让 agent 渐进读取知识 | 需要接入我们的 evidence、version、adapter 协议 |
| graphify | NetworkX、社区、Wiki、HTML、MCP、本地导航 | 代码抽取器不适合金融数据，不能作为事实源 |

结论：

> 外部项目作为参考实现和设计来源，不作为我们的主框架。主框架是自研 Knowledge Infrastructure。

## 5. 核心数据流

### 5.1 通用数据流

```text
Raw Inputs
  -> Adapter.normalize()
  -> Adapter extraction strategy
  -> Knowledge Compiler
  -> Entity Resolution
  -> Relation Compile
  -> Evidence Binding
  -> Confidence / Version
  -> Fact Store
  -> Wiki / FTS / Vector / Graph Index
  -> Hybrid Retrieval Runtime
  -> LLM / Agent / Business Consumers
```

### 5.2 金融数据流

```text
业务侧将新闻 / 公告 / 政策 / 行情 / 资金 / 情绪 / 基金持仓映射成标准 source records
  -> Financial KG Adapter
  -> 金融新闻/政策/信号抽取策略
  -> 通用 Knowledge Compiler
  -> 金融 KG Fact Store
  -> 金融 Wiki / 图索引 / 混合检索
  -> L1 事件识别 / L2 事件流 / L3 基金映射 / 投研问答
```

金融数据流只是通用数据流的一个实例。

## 6. 参考方案取舍

本方案吸收外部项目的思想，但不把任何一个外部项目作为生产主框架。

| 参考来源 | 保留什么 | 不采用什么 |
|---|---|---|
| Microsoft GraphRAG | 图结构能增强跨文档推理；社区视角适合离线分析 | 不作为生产主路径，不把社区报告作为事实源，不把重 LLM 索引放入主链路 |
| LightRAG | 增量图索引、实体/关系合并、低层/高层双层检索、轻量查询 | 不直接接管事实库，不照搬其存储模型 |
| A-RAG | `keyword_search`、`semantic_search`、`chunk_read` 这类分层检索工具；必要时让 Agent 迭代检索 | 不把每次查询都变成高成本 Agent 推理；常规查询优先走确定性混合召回 |
| llm-wiki / harness | 写入时把知识编译成可复用 Wiki；查询结果可沉淀；周期性 lint | 不让 LLM 生成的 Wiki 成为事实源；Wiki 必须能回溯到 evidence |
| qmd | 本地 Markdown 的 BM25 + vector + rerank + MCP 工具形态 | 不直接替代 PostgreSQL 事实库和平台检索协议 |
| graphify | 本地图导航、NetworkX 分析、Wiki/HTML/MCP 调试 | 不作为事实源，不承担生产编译逻辑 |

最终取舍：

```text
事实源：PostgreSQL kg_* 表
写入侧：Adapter + Compiler + Evidence + Version
索引侧：Wiki / FTS / Vector / Graph Index，可删除重建
查询侧：Hybrid Retrieval Runtime，必要时提供 Agentic 工具接口
```

关键原则：

1. **写入时编译，查询时复用**：能在 ingest/compile 阶段沉淀的实体、关系、Wiki、索引，不要每次查询重新推理。
2. **确定性优先，Agentic 兜底**：常规查询先走 keyword / semantic / graph / wiki 并行召回和 RRF 融合；复杂问题再暴露工具给 Agent 迭代探索。
3. **结构化事实优先于 LLM 总结**：结构化数据能确定的节点和边，不交给 LLM 重判；LLM 只处理语义抽取、歧义解释、候选关系和 Wiki 文本。
4. **Wiki 是可读索引，不是事实源**：Wiki 可以让 Agent 渐进读取知识，但每段关键结论必须能回到 `evidence`。
5. **增量更新必须是一等能力**：新增文档、事件、持仓、人工反馈时，只更新相关节点、边、证据、Wiki 和索引，不默认全量重建。

| 文档 | 定位 |
|---|---|
| `1. 知识图谱总体设计方案.md` | 总体设计，说明通用基础设施与金融适配器的关系 |
| `2. 通用知识基础设施设计方案.md` | 只写平台层：Compiler、Fact Store、Evidence、Wiki、Retrieval、Graph Quality |
| `3. 自定义领域适配器设计方案.md` | 只写 Adapter 协议：任何领域如何接入平台 |
| `4. 金融领域适配器设计方案.md` | 只写金融 Adapter：金融实体、关系、数据源、L1/L2/L3 接入 |
| `5. 知识图谱对外服务接口设计方案.md` | 只写服务入口：HTTP API、CLI、任务状态、错误码和接口级验收 |

后续实施方案也应按这个顺序写：

1. 先实现通用基础设施最小闭环。
2. 再实现 Adapter 协议。
3. 再实现 Financial KG Adapter。
4. 然后把核心能力封装成 HTTP API 和 CLI。
5. 最后接入 L1/L2/L3 和投研问答。

## 8. 第一阶段边界

第一阶段不能试图一次性做完所有能力。正确边界是：

### 8.1 平台层必须先完成

- 通用节点、边、证据、版本、置信度模型。
- 通用输入材料协议。
- 通用 Adapter 接口。
- 基础实体归一和关系编译。
- PostgreSQL 事实库。
- 最小 keyword / graph / wiki 检索。
- 可从事实库导出 graphify 或 NetworkX 分析图。

### 8.2 金融层只做最小可验证闭环

- 股票、行业、概念、基金、事件、政策六类核心实体。
- `belongs_to`、`holds`、`mentions`、`affects`、`benefits_from`、`related_to` 等核心关系。
- 新闻/公告/政策到事件和实体的编译。
- 基金持仓到股票影响链。
- L1/L2/L3 只做消费 KG 的设计，不急着全面改造。

---

## 9. 成功标准

这套方案成立的标准不是“金融 KG 能不能跑一个 demo”，而是：

1. 换一个领域 Adapter 后，平台层不需要重写。
2. 金融规则只存在于 Financial KG Adapter 和金融消费策略里。
3. 节点、边、证据、版本、Wiki、检索索引都遵守通用协议。
4. 金融 KG 可以服务 L1/L2/L3，但 L1/L2/L3 不反向污染平台层。
5. 后续可以基于同一套基础设施做代码 KG、企业 KG、个人记忆 KG。

---

## 10. 设计结论

最终选择：

> **自研通用 Knowledge Infrastructure，把金融知识图谱作为第一个领域适配器落地。**

不是：

```text
写一套金融专用 KG 系统
```

而是：

```text
写一套通用知识基础设施
  + 实现 Financial KG Adapter
  + 用金融投研场景验证这套基础设施
```

这个边界必须在实施前定死，否则后面会继续把平台能力写成金融专用逻辑。
