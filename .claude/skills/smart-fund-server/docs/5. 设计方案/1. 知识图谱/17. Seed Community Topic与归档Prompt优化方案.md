# Seed Community Topic 与归档 Prompt 优化方案

## 1. 本文定位

本文记录 Community Topic 当前最新优化结论。

目标不是把系统改成固定分类法，而是在保留 LLM 自动发现新主题能力的前提下，给它一批高质量的长期主题种子，帮助它稳定判断 L0 Community 的粒度。

```text
Cognitive Card
  -> topic_intents
  -> 从 Milvus 召回 seed / emergent community candidates
  -> Assignment LLM 裁决 attach / create
  -> Community Card
```

## 2. 为什么需要 Seed Community

完全依赖 LLM 自动新建 Community，会遇到一个稳定性问题：

```text
第一批数据没有历史 community 可参考；
LLM 只能根据单条新闻或单个 chunk 推断主题粒度；
它容易把具体新闻标题、公司动作、单一项目或短期行情包装成 L0。
```

这不是 LLM 格式问题，而是上下文问题。模型在第一条资料进入系统时，看不到未来会有多少类似资料，也看不到我们希望交易认知层关注哪些长期主线。

Seed Community 的作用是提供“优秀种子”：

- 给 LLM 参考什么样的主题粒度适合成为 L0。
- 提高相关资料挂入长期主线的概率。
- 降低同类主题被拆成多个平行 L0 的概率。
- 保留不匹配时自动创建 emergent community 的能力。

Seed 不是强制分类，也不是穷举目录。

```text
seed community = 人工预置的高质量业务主线
emergent community = LLM 自动发现的新主题
```

两者只在来源上不同，归档裁决仍由 Assignment LLM 完成。

Seed Community 必须作为真实 Community 进入系统，而不是运行时硬塞进 prompt 的固定上下文。

```text
seed community
  -> 写入 PG: kg_graph_communities
  -> 写入 Milvus: community semantic document
  -> 后续通过 RAG 召回成为 candidate
  -> Assignment LLM 和 emergent community 一起裁决
```

这样 seed 才具备真实生命周期：

- 可以被语义召回命中。
- 可以被新资料持续更新。
- 可以和 emergent community 进入同一套合并、重命名、升级、统计流程。
- 可以被查询侧直接作为高级索引使用。
- 可以通过数据库和向量索引验证召回质量。

不允许只在代码中维护 8 条 seed，然后每次直接拼进 Assignment prompt。那会绕开 RAG 主链路，导致 seed 无法演化，也无法和自动发现的主题统一治理。

## 3. Seed 的定义原则

Seed 的粒度要满足：

| 原则 | 说明 |
|---|---|
| 比单条事件更宽 | 不能是公司项目、单笔交易、单次行情、单份公告。 |
| 比通用分类更窄 | 不能只是“科技”“政策”“风险”“公司动态”。 |
| 与交易认知相关 | 应能帮助自动交易系统理解主线、风险、驱动、产业链和资金变化。 |
| 能承接未来材料 | 未来可以挂入多条不同来源、不同时间、不同主体的新闻。 |
| 可继续细分 | 资料变多后可以拆出 L1 / L2 子主题。 |
| 不限制新主题 | 不匹配 seed 时，LLM 必须可以创建 emergent community。 |

合适的 Seed 应像“图书馆里的长期书架”，而不是一本书的标题。

## 4. Seed Community 应定义哪些内容

每个 Seed Community 至少需要定义以下内容：

| 内容 | 作用 |
|---|---|
| title | 对外展示和向量召回使用的大词标题。 |
| scope | 这个主题未来可以承接什么类型的信息。 |
| include_rules | 哪些资料应该优先挂入。 |
| exclude_rules | 哪些资料看起来相似但不应该挂入。 |
| canonical_labels | 召回和归一化使用的别名、近义表达。 |
| granularity_note | 告诉 LLM 这个主题为什么是 L0，而不是更细或更粗。 |
| origin | 固定为 seed，用于和 emergent 区分来源。 |

`include_rules` 和 `exclude_rules` 不是死规则，不参与系统硬判定。它们是给 Assignment LLM 的判断上下文，最终仍由 LLM 裁决。

不建议在全局 system prompt 中写大量真实主题示例。真实业务主题应作为候选 community 的内容输入，而不是塞进固定 prompt，避免模型输出过度贴近示例。

## 4.1 Seed 的存储和导入方式

Seed 应写入正式 Community 表，而不是单独做一套旁路存储。

第一版不需要新增 seed 专表，直接使用：

```text
kg_graph_communities.metrics.origin = "seed"
```

Seed 写入时应同时生成 Milvus community 文档。这样 Assignment 阶段仍然只依赖统一的候选召回流程：

```text
topic_intent
  -> embedding / hybrid recall
  -> seed + emergent candidates
  -> Assignment LLM 裁决
```

Seed 导入应是幂等动作：

- seed 不存在时创建正式 `kg_graph_communities` 记录。
- seed 已存在但还没有引用资料时，更新 seed metadata。
- seed 已经挂入资料时，不能清空 `evidence_ids / chunk_ids / source_ids / assignments`。
- seed 的 `scope / include_rules / exclude_rules / canonical_labels / granularity_note` 可以随定义更新。
- seed 对应 Milvus 文档应同步 upsert。

Seed 的导入时机：

```text
compile / community assignment 前自动 ensure seed communities；
同时保留一个手动 seed bootstrap 入口，便于开发和重建索引。
```

Demo 或测试清理必须保护 seed：

- 不得因为清理 demo source 删除 `origin=seed` 的 community。
- 不得使用 adapter/target 级别的 Milvus `delete_scope` 清空全部 community 向量。
- 只能删除 demo 关联的 target_ids。
- seed 的 PG 记录和 Milvus 文档必须保留。

## 5. Seed Topic 生成方式

Seed Topic 不应只靠经验手写。

正式 seed 应来自三类输入：

| 来源 | 作用 |
|---|---|
| ft_news 样本统计 | 反映系统真实会处理的新闻分布。 |
| Cognitive Card 统计 | 复盘 LLM 已抽取出的 parent_themes、broad_topics、event_thread、risk_type 等底层信号。 |
| 现有 Community 复盘 | 发现已经聚合成功的主题、重复拆分的主题和过细标题。 |

当前目录下提供只读分析脚本：

```text
docs/6. 使用说明/知识图谱/9_seed_topic_analysis.py
```

它读取：

```text
ft_news
kg_cognitive_cards
kg_community_assignments
kg_graph_communities
```

并输出：

```text
generated_seed_topic_candidates.json
generated_seed_topic_candidates.md
```

脚本只生成候选，不直接写入 seed。正式 seed 需要经过人工确认后进入 seed bootstrap 定义，再由 bootstrap 流程写入 PG 和 Milvus。

### 5.1 Seed 候选筛选指标

候选 seed 至少应观察：

| 指标 | 说明 |
|---|---|
| source_count | 覆盖多少不同新闻来源。 |
| occurrence | 在 Cognitive Card 信号中出现次数。 |
| field_counts | 出现在 parent_themes / broad_topics / event_thread / risk_type 等字段中的情况。 |
| date_count | 是否跨多个日期持续出现。 |
| co_labels | 与哪些主题信号共同出现。 |
| existing_community_support | 是否已有 Community 能证明它能承载多条资料。 |

优先级更高的候选：

```text
source_count 高；
出现在 parent_themes / broad_topics / event_thread 中；
跨日期或跨主体出现；
能解释已有多个 emergent community 的拆分；
不是泛词，也不是单点事实。
```

### 5.2 第一批建议 Seed Topic 草案

本草案基于 `9_seed_topic_analysis.py` 对当前库中 17820 条 `ft_news` 的原始新闻统计，同时参考已有 40 张 Cognitive Card 和 27 条 active Community。

第一批 seed 不追求覆盖所有新闻，而是给 Assignment LLM 提供一批高质量 L0 粒度范例。

核心目标：

```text
让 AI 看到什么样的主题才适合作为长期书架；
让 AI 学会 L0 应该如何命名、如何收纳、如何保留边界；
不要把边界尚未想清楚的主题混进第一批 seed。
```

正式落库前仍需要人工审核 `scope / include_rules / exclude_rules / canonical_labels / granularity_note`。

#### 5.2.1 建议直接进入第一批 seed

这些主题在当前 `ft_news` 中覆盖面足够大，且与交易认知强相关。

| Seed Topic | ft_news 命中 | 覆盖日期 | 为什么进入第一批 | 边界说明 |

| 公司业绩与产业景气 | 3816 | 51 | 财报、订单、利润、行业景气是交易判断基础。 | 承接业绩增长、亏损、订单、营收、景气变化；不承接单纯公司公告流水。 |
| AI算力链 | 2172 | 47 | AI、算力、芯片、数据中心、服务器、液冷等高频出现。 | 承接 AI 芯片、算力硬件、光模块、数据中心、液冷、服务器；不承接泛 AI 应用营销。 |

#### 5.2.2 不进入第一批 seed，后续观察升级

这些主题有数据支撑，但不进入第一批 seed。

原因不是它们没有价值，而是不适合作为第一批“高质量示范种子”。如果把边界尚未想清楚的主题也放进 seed，会让 LLM 学到模糊主题也可以成为 L0，反而降低上下文质量。

| Seed Topic | ft_news 命中 | 覆盖日期 | 当前判断 |
|---|---:|---:|---|
| 消费与服务业修复 | 1024 | 47 | 内部较分散，包含消费、餐饮、文旅、外卖、服务业政策，第一批先不上。 |
| 半导体国产替代 | 664 | 37 | 与 AI算力链 交叉较强，第一批先让它挂入 AI算力链 或由 LLM 自动创建 emergent。 |
| 电力系统与能源转型 | 559 | 48 | 与 新能源出海 / 大宗商品供需冲击 / 政策监管与产业扶持 交叉明显，第一批先不上。 |
| A股并购重组 | 475 | 38 | 与 资本市场改革 关系很近，第一批先归入资本市场改革；如果后续持续高频，再升级为 seed。 |

第一批正式 seed 只包含 8 个。其他主题不写入 seed，只作为后续升级观察对象。

#### 5.2.3 暂不建议作为第一批 seed

这些主题不是没有价值，而是不适合现在直接写成 seed。

| Topic | 原因 |
|---|---|
| A股市场 | 太泛，容易变成垃圾桶。 |
| 美股市场 | 太泛，除非后续单独做海外市场指数 / 风险主线。 |
| 上市公司 | 太泛，应拆到业绩、监管、并购、融资等更具体主线。 |
| 政策驱动 | 太泛，应落到政策监管、产业扶持、资本市场改革等具体主线。 |
| 科技行业 | 太泛，应落到 AI算力链、半导体国产替代、软件应用等具体主线。 |

这些 seed 不是最终目录。运行过程中如果出现新的稳定主线，例如新的地缘事件、产业技术路线、监管专题或区域经济主题，系统应创建 emergent community。

当某个 emergent community 长期活跃、跨 source 支撑充分、业务价值明确时，可以升级为 seed。

## 6. LLM 自动新建 Community 的原则

Seed Community 只能提供高质量参考，不能替代 LLM 自动发现新主题。

当所有 seed / emergent 候选都不能合理承接当前 `topic_intent` 时，Assignment LLM 必须允许创建新的 emergent L0 Community。

但 `create_new` 不是“候选没有完全命中”就新建。LLM 必须先完成主题层级裁决。

### 6.1 create_new 前必须判断什么

LLM 只有在以下条件同时成立时，才应该 `create_new`：

| 判断项 | 要求 |
|---|---|
| 候选无法承接 | 已召回的 seed / emergent candidates 都不能作为当前 intent 的父级目录。 |
| 不是已有主题的新材料 | 如果只是已有主题的新子方向、新案例、新风险点、新主体，应 `attach_existing`。 |
| 不是单点事实 | 不能只是单条新闻、单家公司动作、单个项目、单笔交易、单次行情、单个产品或单个数据点。 |
| 不是过粗分类 | 不能只是“科技”“政策”“风险”“市场动态”“公司动态”这类通用分类。 |
| 有未来承接价值 | 未来可以承接多条不同来源、不同时间、不同主体的资料。 |
| 可继续细分 | 资料变多后可以自然拆出 L1 / L2 子主题。 |
| 边界清晰 | 能说清楚它和已有候选 community 的边界。 |

### 6.2 create_new 的标题应该是什么

新建 L0 的标题应该是长期可复用的主题名。

合适的标题形态：

```text
产业主线
政策主线
风险主线
资本市场主线
宏观变量主线
事件长期线索
```

不合适的标题形态：

```text
新闻标题
单一公司项目
单笔交易
单次行情
单个产品
单次监管动作
单个数据点
泛泛分类
```

标题不能为了显得宽而退化成空泛分类。`科技`、`政策`、`风险` 这类词太粗，不能作为有效 L0。

### 6.3 create_new 必须在 reason 中说明什么

当 LLM 输出 `create_new` 时，`reason` 必须说明：

```text
为什么已有候选不能承接；
为什么这个标题不是单点事实；
为什么它不是过粗分类；
它未来可以承接哪些类型的资料；
它和最相近候选的边界在哪里。
```

这不是让系统用规则拦截 LLM，而是要求 LLM 显式完成“是否值得新建 L0”的业务裁决。

系统只校验结构，不用关键词规则改写 LLM 的裁决。

## 7. Assignment Prompt 优化方向

Assignment LLM 的核心职责仍然是：

```text
对每个 topic_intent 判断：
  -> 挂入已有 seed / emergent community
  -> 或创建新的 emergent L0 community
```

Prompt 需要补充以下判断原则。

### 7.1 Seed 不是硬分类

Assignment Prompt 必须明确：

```text
origin=seed 表示高质量长期主题种子；
它是强参考，不是强制归档；
如果 seed scope 可以承接当前 intent，应优先 attach；
如果所有 seed 和候选都不能合理承接，必须允许 create_new。
```

不能因为 seed 存在，就把不相关资料硬塞进去。

### 7.2 新建 L0 必须说明未来承接范围

当 LLM 输出 `create_new` 时，必须说明：

```text
为什么已有候选不能承接；
为什么这个新标题不是单条新闻标题；
它未来可以承接哪些类型的资料；
它和当前候选的边界在哪里。
```

这不是让系统用规则拦截 LLM，而是要求 LLM 自己完成主题层级裁决。

### 7.3 不盲目使用 broad_topics

`broad_topics` 是 Cognitive Card 的候选信号，不是最终 L0 指令。

Assignment LLM 必须同时参考：

```text
raw_theme
title_candidate
broad_topics
mid_topics
specific_topics
driver
impact_target
risk_type
event_thread
actors
candidate community scope
```

如果 `broad_topics` 太泛，不能直接拿来创建 L0。
如果 `specific_topics` 实际只是已有主题的新材料，应挂入已有主题，而不是创建平行 L0。

### 7.4 允许一条资料进入多个 Community

一条新闻可能同时属于多个主题。

例如一条公司上市新闻可能同时涉及：

```text
科技企业上市
AI算力链
资本市场融资
```

系统不使用 primary / secondary，只用 `weight` 表达归属强弱。

低 weight 不等于不能创建或不能挂入。只要这个主题本身有未来承接价值，就可以成为独立 Community。

### 7.5 修正 L0 / L1 / L2 表述

当前主链路以 L0 Community 为主。

Prompt 不应让模型误以为单条新消息可以直接创建 L1 / L2。更准确的表达是：

```text
候选可能来自已有 L0 / L1 / L2；
新建时第一阶段只创建 L0；
mid_topics / specific_topics 作为社区内部信号保留；
未来由 Community Maintenance 从 L0 已积累材料中拆出 L1 / L2。
```

## 8. Candidate 输入优化

给 Assignment LLM 的候选 community 应包含：

| 字段 | 说明 |
|---|---|
| alias | 短 ID，例如 c1 / c2，避免长 ID 干扰模型。 |
| title | Community 标题。 |
| origin | seed / emergent。 |
| scope | 主题承接范围。 |
| canonical_labels | 近义表达和别名。 |
| maturity | single_evidence / multi_evidence / mature_topic。 |
| source_count | 支撑来源数量。 |
| recent_examples | 最近挂入的简短 intent 摘要。 |

不要把完整 source_id、trace_id、schema_version、长 hash、完整原文放入 Assignment prompt。

候选来自统一的 community RAG 召回。seed 和 emergent 都必须作为真实 community document 被召回，不应由应用层绕过召回流程直接塞入 prompt。

候选召回结果只是给 LLM 的候选集，不是业务裁决结果。

## 8.1 Candidate 精排

Community candidate 召回应拆成两层：

```text
topic_intent
  -> Milvus broad recall
  -> Reranker 精排
  -> Assignment LLM 裁决
```

Milvus 的职责是尽量召回可能相关的 seed / emergent community，优先保证 recall，不负责最终边界判断。

Reranker 的职责是减少候选噪声，把最可能承接当前 `topic_intent` 的 community 排到前面。它是候选质量层，不是业务裁决层。

推荐第一版策略：

| 阶段 | 建议 |
|---|---|
| Milvus broad recall | 去重后保留 30-50 个候选。 |
| Reranker 输入 | `topic_intent` compact text + candidate community compact text。 |
| Reranker 输出 | rerank score 和重排后的候选列表。 |
| Assignment 输入 | 保留 Top 12-20 个候选给 LLM。 |
| 候选较少 | 如果候选少于 8 个，可跳过 rerank。 |
| Trace | 记录 raw_candidates、reranked_candidates、dropped_candidates、rerank_score。 |

精排不能做：

- 不能决定 `attach_existing / create_new`。
- 不能改写 community title。
- 不能因为 seed 存在而强制归档。
- 不能用业务规则替代 LLM 判断。
- 不能把低分候选当成业务否决，只能作为排序和截断依据。

最终职责边界：

```text
Milvus：召回候选，追求不漏。
Reranker：重排候选，降低 prompt 噪声。
Assignment LLM：最终裁决归档和新建。
```

加入精排的原因：

- seed 和 emergent 都物化后，候选数量会增加。
- Milvus 向量相似度不一定能稳定表达主题边界。
- Assignment LLM 会受到候选顺序和候选噪声影响。
- 精排能提高进入 prompt 的候选质量，同时保持 LLM 的最终裁决权。

## 9. 系统行为边界

允许系统做：

- 从 Milvus 召回 seed / emergent candidates。
- 对召回候选做 rerank，提高进入 Assignment prompt 的候选质量。
- 把被召回的 seed candidates 作为高质量候选提供给 LLM。
- 幂等创建或更新 seed community 的 PG 记录和 Milvus 文档。
- 校验 LLM 输出是否符合 schema。
- 校验 attach 的 community alias 是否存在。
- 校验 create_new 是否引用了合法 new community。
- JSON / schema 不合格时让 LLM proxy 继续追问修复。

不允许系统做：

- 用关键词规则把 LLM 的 create_new 改成 attach_existing。
- 用硬编码规则改写 LLM 生成的 community title。
- 因为 seed 存在而强制归档到 seed。
- 只在代码中硬塞 seed prompt，不把 seed 写入正式 community 表和向量索引。
- 用 rerank score 直接决定 attach / create。
- 因为某个主题低 weight 就自动丢弃。
- 用固定行业白名单判断 L0 是否合理。
- 用 fallback 规则生成假 community。

最终原则：

```text
LLM 负责业务裁决；
系统负责候选召回、结构校验、证据追溯和索引写入；
Seed 负责提供高质量主题参考，但不剥夺 LLM 创建新主题的能力。
```

## 10. 验收口径

优化完成后，应重点观察：

| 指标 | 目标 |
|---|---|
| seed attach rate | 明显相关的资料能稳定挂入 seed。 |
| emergent create rate | 不匹配 seed 的资料仍能创建新主题。 |
| duplicate L0 rate | AI算力链 / AI芯片产业 / AI算力硬件 这类近邻主题重复率下降。 |
| over-broad rate | 科技 / 政策 / 风险 / 市场动态 这类空泛 L0 不应增加。 |
| multi-assignment quality | 一条资料能合理进入多个 community，weight 能表达强弱。 |
| prompt cache | system prompt 稳定，动态内容靠后，减少缓存失效。 |

第一轮验证不要求 seed 覆盖所有资料，只要求：

```text
相关资料更容易进入长期主线；
不相关资料仍能自动创建 emergent community；
新建 L0 的标题粒度比无 seed 时更稳定。
```
