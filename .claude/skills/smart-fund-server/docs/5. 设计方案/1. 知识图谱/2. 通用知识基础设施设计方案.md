# 通用知识基础设施设计方案

> 本文档只讨论平台层，不讨论具体金融实体和金融业务规则。
> 平台层的目标是为任意领域提供一套可审计、可增量、可检索、可复用的知识基础设施。

---

## 0. 一句话说清楚

通用知识基础设施负责把任意领域的原始材料编译成：

```text
nodes + edges + evidence + confidence + version + indexes
```

它不关心节点是股票、函数、合同条款还是项目决策。它只关心：

- 实体是否稳定。
- 关系是否有证据。
- 事实是否有版本。
- 置信度是否可解释。
- 索引是否可重建。
- 查询上下文是否可控。

---

## 1. 平台层模块

| 模块 | 职责 |
|---|---|
| Knowledge Compiler | 将标准化输入编译成节点、边、证据和版本 |
| Entity Resolution | 处理实体归一、alias、合并、拆分和歧义 |
| Relation Compiler | 处理确定关系、文本关系、统计关系和推断关系 |
| Evidence Manager | 绑定原始记录、原文片段、规则输出、LLM 输出、人工确认 |
| Text Extraction Pipeline | 提供通用文本抽取执行框架，不内置任何领域规则 |
| Fact Store | 保存事实源，其他索引都从这里重建 |
| Version Manager | 管理 schema、规则、prompt、数据批次和人工修正版本 |
| Review Queue | 管理候选事实、冲突事实、高风险关系和人工复核 |
| Knowledge Wiki | 将高复用知识编译成可读页面 |
| Hybrid Retrieval Runtime | 组合 keyword、semantic、graph、wiki、chunk_read |
| Graph Quality | 社区发现、路径分析、弱边治理、孤岛检测、冲突发现 |

---

## 2. 通用输入协议

任何 Adapter 输入平台前，都要转换为统一材料类型：

| 类型 | 含义 |
|---|---|
| `structured_record` | 有明确字段和主键的结构化记录 |
| `semi_structured_record` | 有字段但语义需要解释的记录 |
| `document_chunk` | 长文本切片 |
| `event_record` | 已识别出的事件 |
| `derived_signal` | 统计、算法或外部系统产生的信号 |
| `feedback_record` | 人工复核、用户反馈、历史验证、复盘结论 |

每条输入必须具备：

- `source_type`
- `source_id`
- `observed_at`
- `payload`
- `raw_text` 或可回溯原始字段
- `adapter_name`
- `adapter_version`

## 3. 通用事实模型

### 3.1 Node

节点表达稳定实体：

- `node_id`
- `node_type`
- `canonical_name`
- `aliases`
- `external_ids`
- `properties`
- `status`
- `created_at`
- `updated_at`
- `version`

节点状态：

| 状态 | 含义 |
|---|---|
| `active` | 当前有效 |
| `candidate` | 候选实体 |
| `ambiguous` | 歧义实体 |
| `merged` | 已合并到其他实体 |
| `deprecated` | 已废弃 |

### 3.2 Edge

边表达实体关系：

- `edge_id`
- `source_node_id`
- `target_node_id`
- `relation_type`
- `properties`
- `confidence_label`
- `confidence_score`
- `evidence_refs`
- `valid_from`
- `valid_to`
- `status`
- `version`

边状态：

| 状态 | 含义 |
|---|---|
| `active` | 当前有效 |
| `candidate` | 候选关系 |
| `review_required` | 需要复核 |
| `conflict` | 存在冲突 |
| `deprecated` | 已废弃 |

### 3.3 Evidence

证据表达事实依据：

- 结构化字段。
- 原文片段。
- 文档位置。
- 规则输出。
- LLM 输出。
- 人工确认。
- 历史验证。

平台只规定证据协议，不规定业务含义。

---

### 3.4 Text Extraction Pipeline

通用知识基础设施可以提供一套文本抽取管线，但它不是“新闻业务模块”，也不理解金融、代码、法务或企业知识。

它只负责通用执行机制：

- 接收 `raw_text`、`source_id`、`source_type`、`observed_at`。
- 调用 Adapter 提供的领域抽取策略。
- 管理 LLM 调用、超时、重试、限流和批量大小。
- 解析结构化 JSON 输出。
- 校验输出是否符合 Adapter schema。
- 把抽取结果绑定到 evidence span 或原始 source。
- 将失败记录为 warning 或 failed record，而不是直接污染主图。

平台层不能写入任何领域 prompt，也不能硬编码实体类型。例如平台层不能知道什么是 `stock`、`industry`、`contract_clause` 或 `python_function`。

正确分层是：

```text
Text Extraction Pipeline
  -> 执行抽取流程、解析和证据绑定

Domain Adapter Extraction Strategy
  -> 定义抽什么、怎么 prompt、如何校验、如何赋置信度
```

因此，通用层提供的是“抽取管线插槽”，不是“通用新闻抽取业务”。

---

## 4. 置信度协议

通用置信标签：

| 标签 | 含义 |
|---|---|
| `EXTRACTED` | 从结构化数据或原文明确抽取 |
| `INFERRED` | 由模型、统计、图邻域推断 |
| `AMBIGUOUS` | 有歧义，不能用于硬逻辑 |
| `HUMAN_VERIFIED` | 人工确认 |
| `REJECTED` | 已否定 |

平台负责保存和传播置信度；具体哪些置信度可以被业务使用，由 Adapter 定义。

---

## 5. Knowledge Compiler

Compiler 的通用流程：

```text
normalized input
  -> candidate mentions
  -> entity resolution
  -> relation candidates
  -> evidence binding
  -> confidence assignment
  -> ontology validation
  -> versioned upsert
```

Compiler 不写领域规则。它调用 Adapter 提供的：

- entity schema。
- relation schema。
- resolver rules。
- relation rules。
- confidence policy。
- validation policy。

---

## 6. 写入侧编译策略

平台层的核心不是“查询时临时 RAG”，而是“写入时编译，查询时复用”。

### 6.1 编译对象

每次 compile 至少产出四类结果：

| 结果 | 是否事实源 | 说明 |
|---|---|---|
| node | 是 | 稳定实体或候选实体 |
| edge | 是 | 有方向、有类型、有置信度的关系 |
| evidence | 是 | 支撑 node/edge 的来源、字段、片段、人工记录 |
| index material | 否 | Wiki 页面、全文索引、向量索引、图分析结果 |

### 6.2 编译优先级

同一条知识可能来自结构化数据、文本、统计信号和人工反馈。平台层按来源类型分层处理：

| 来源 | 编译方式 | 默认结果 |
|---|---|---|
| 强 ID 结构化字段 | 规则编译 | active node / active edge |
| 官方或可信结构化关系 | 规则编译 | active edge |
| 原文明确陈述 | 抽取 + evidence | active 或 candidate edge |
| 多文档共现或统计信号 | 统计编译 | candidate edge |
| LLM 语义推断 | 语义编译 | candidate 或 review_required edge |
| 人工确认 | 人工反馈编译 | active 或 rejected |

这不是金融规则，而是通用知识平台的质量原则：确定事实不应该被 LLM 重判，语义关系也不能伪装成确定事实。

### 6.3 增量更新原则

平台必须支持增量更新：

- 新 source 只触发相关 node、edge、evidence 的 upsert。
- 被影响的 Wiki 页面和索引局部重建。
- 实体合并、拆分、废弃必须保留迁移记录。
- 删除或更新 source 时，不物理删除历史事实，先通过版本和状态表达。
- 全量重建只能作为校准和灾备手段，不是日常链路。

## 7. Knowledge Wiki

Wiki 是平台层能力，但页面类型应通用：

| 页面 | 通用含义 |
|---|---|
| entity page | 一个实体的摘要、关系、证据、历史变化 |
| topic page | 一组实体或事件形成的主题 |
| community page | 图社区摘要 |
| comparison page | 两个或多个实体/主题的差异 |
| contradiction page | 冲突事实和待复核问题 |
| timeline page | 时间顺序上的事实变化 |

Wiki 不是事实源。它是由事实库生成的可读索引，允许人工补充，但人工补充也要反向形成证据或备注。

### 7.1 Wiki 的作用

Wiki 解决的是 llm-wiki / harness 方案强调的问题：知识不能每次查询都从原始 chunk 重新拼装，应该在写入侧持续沉淀。

平台 Wiki 至少承担四个职责：

1. **渐进式披露**：Agent 可以先读 index，再读页面，再读 evidence，而不是一次塞入长上下文。
2. **跨来源综合**：同一实体、主题、矛盾、时间线提前沉淀为页面。
3. **查询复用**：高价值问答、对比分析、专题总结可以保存为 Wiki 页面，后续复用。
4. **质量检查入口**：孤立页、陈旧页、冲突页、低置信页能被 lint 发现。

### 7.2 Wiki 的约束

- Wiki 页面必须记录来源和关联 evidence。
- Wiki 页面不能直接生成 active edge。
- Wiki 中的人工补充如果要进入事实库，必须转成 `feedback_record`。
- Wiki 可以被删除并从 Fact Store 重建。
- Wiki 允许面向 Agent 优化结构，不要求作为人类最终报告。

## 8. Hybrid Retrieval Runtime

Runtime 提供通用混合召回：

| 工具 | 作用 |
|---|---|
| `keyword_search` | 精确词、名称、ID、短语命中 |
| `semantic_search` | 相似语义和历史类比 |
| `graph_search` | 路径、邻居、社区、多跳关系 |
| `wiki_search` | 读取已编译知识页面 |
| `chunk_read` | 精读原文和证据片段 |

Runtime 的职责不是替业务做判断，而是构造可控上下文：

```text
query
  -> query classification
  -> multi-retrieval
  -> rank fusion
  -> dedupe
  -> context budget
  -> structured context
```

### 8.1 检索路径

平台检索不是单一路径，而是多路召回后统一融合：

| 路径 | 参考思想 | 适用问题 |
|---|---|---|
| keyword | A-RAG / qmd | 名称、代码、简称、ID、精确短语 |
| semantic | LightRAG / qmd | 表述不一致、语义相近、历史类比 |
| graph | LightRAG / GraphRAG | 多跳关系、邻域、路径、社区 |
| wiki | llm-wiki | 已沉淀实体页、主题页、对比页、时间线 |
| chunk_read | A-RAG | 精读原文证据、相邻片段、完整 source |

### 8.2 查询模式

Runtime 第一版应同时支持两类模式：

| 模式 | 说明 | 默认使用场景 |
|---|---|---|
| deterministic hybrid | keyword / semantic / graph / wiki 并行召回，RRF 或加权融合 | 线上常规查询 |
| agentic retrieval | 给 Agent 暴露 search/read 工具，允许多轮探索 | 复杂投研、长链路分析、人工交互 |

常规线上链路默认使用 deterministic hybrid，避免每次查询都消耗额外 LLM 决策成本。
Agentic retrieval 是能力上限，不是默认成本。

### 8.3 上下文输出协议

Runtime 输出给 LLM 或业务系统的不是散乱文本，而是结构化上下文：

```text
answer_context
  query_intent
  matched_nodes
  matched_edges
  graph_paths
  wiki_pages
  evidence_chunks
  rejected_or_low_confidence_items
  budget_usage
```

每个上下文片段必须带：

- 来源类型。
- 来源 ID。
- confidence。
- evidence 引用。
- 可消费范围。

## 9. 图质量治理

平台层提供通用质量治理能力：

| 问题 | 治理方式 |
|---|---|
| 过度合并 | 拆分节点，保留迁移历史 |
| 弱边泛滥 | 限制候选边入主图，做时间衰减 |
| 孤岛节点 | 补充关系、降权或废弃 |
| 冲突事实 | 进入 review queue |
| 证据缺失 | 禁止入主图 |
| 社区异常 | 用图算法发现混乱主题 |

graphify 可以用于本地导航、HTML 导出、NetworkX 分析和 agent 调试，但不能作为事实源。

质量治理不能只靠事后看图，而要嵌入写入链路：

| 时机 | 检查 |
|---|---|
| compile 前 | source 是否可解析、是否重复、是否缺主键 |
| compile 中 | ontology 是否允许、active 边是否有 evidence、关系方向是否正确 |
| upsert 前 | 是否与已有事实冲突、是否需要 review |
| upsert 后 | 是否产生孤岛、超级节点、弱边泛滥 |
| 查询后 | 用户反馈、Bad Case、错误路径是否回写 |

## 10. 平台层验收闭环

平台层不是“表建好了就完成”，必须能跑通完整闭环：

```text
toy raw records
  -> toy adapter
  -> compiler
  -> fact store
  -> wiki
  -> keyword / graph / chunk_read
  -> quality lint
```

最小验收：

1. 同一 fixture 重复编译幂等。
2. active edge 全部有 evidence。
3. 删除 Wiki 和索引后可从 Fact Store 重建。
4. keyword、graph、wiki、chunk_read 能围绕同一事实返回一致证据。
5. 低置信、冲突、无证据关系不会进入 hard-consume 结果。

---

## 11. 平台层非目标

平台层不做：

- 不定义金融、代码、法务等领域概念。
- 不判断某条业务关系能不能用于交易。
- 不绑定 Microsoft GraphRAG、LightRAG、A-RAG 或 graphify。
- 不把 embedding 当成事实。
- 不允许无证据的 LLM 总结直接进入主图。

---

## 12. 验收标准

平台层设计完成的标准：

1. 换一个 Adapter 后，不需要改 Fact Store 和 Runtime 主协议。
2. 节点、边、证据、版本、置信度模型不含金融专用字段。
3. Wiki 和 Retrieval 能从事实库重建。
4. LLM 输出只能作为有证据、有版本的候选知识进入系统。
5. graphify、向量索引、全文索引都是可替换索引，不是事实源。
