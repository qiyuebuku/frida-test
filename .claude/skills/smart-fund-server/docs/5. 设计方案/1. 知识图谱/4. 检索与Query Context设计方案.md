# 检索与 Query Context 设计方案

## 1. 本文解决什么问题

本文说明知识图谱如何把事实库中的实体、关系、证据和派生摘要组织成可消费的检索上下文。

知识图谱的价值不只是“存储节点和边”，而是能够在投研问答、事件抽取、策略解释和复盘中提供稳定、可解释、可引用的上下文。检索模块需要组合实体解析、图关系扩展、语义搜索、Wiki 搜索、证据回读和候选重排，让使用方拿到统一的 Query Context，而不是直接拼接数据库结果或向量结果。

## 2. 本文不解决什么问题

本文不讨论原始业务表如何变成 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论 Source Record 如何编译写入主图；这属于“知识编译、标准化与写入”模块。

本文不定义实体和关系类型；这属于“知识模型与领域适配”模块。

本文不处理实体归一和合并规则；这属于“知识编译、标准化与写入”模块。

本文不讨论 Wiki 页面如何生成和维护；这属于“Wiki 与消费场景”模块。

本文不写具体 API 字段、CLI 参数、索引表结构和重排算法实现；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Query Context

Query Context 是检索输出给使用方的上下文包。它应该包含命中的实体、关系、证据、路径、检索通道、质量告警和上下文预算信息。

使用方不应该直接消费向量库 hit、图邻接表或数据库查询结果，而应该消费统一 Query Context。

### 3.2 Retrieval Channel

Retrieval Channel 是检索通道。第一版至少需要覆盖：

- 实体解析。
- 图关系扩展。
- 语义检索。
- Wiki 搜索。
- 证据回读。

不同查询可以组合不同通道，不应该只有单一向量检索。

### 3.3 Query Anchor

Query Anchor 是一次查询中最应该被保护的核心约束。它不是简单关键词，而是 query 的中心对象、中心事件、时间范围、主题边界和关系意图。

例如查询“俄就波法联合军演发出警告：欧洲对俄全面对抗正在回归”时，Anchor 应该围绕“俄波法联合军演”“欧洲对俄全面对抗”“俄罗斯/欧洲/波兰/法国”等事件和实体，而不是被全库语义检索扩散到宁德时代、固态电池或其他金融事件。

Query Anchor 的作用是给后续候选裁判和图谱扩展提供边界：候选可以语义相似，但如果无法覆盖核心 Anchor，就不能直接进入最终 Query Context。

Query Anchor 的最终语义判断以 LLM Anchor Parser 的结构化输出为准。确定性规则不负责完整理解 query，只负责提取不会错的强约束和候选上下文，例如 source id、evidence id、代码、日期、query 原文中的长短语、已知实体精确匹配。系统再把这些强约束交给 LLM，帮助 LLM 稳定识别核心事件、核心实体、主题、关系意图和排除边界。

Anchor Validator 不重新解释 query，也不和 LLM 抢语义决策权。它只负责校验 LLM 输出是否保留强约束、是否凭空加入 query 外无依据实体、是否改写代码/source id/日期等硬约束，并在必要时补漏、降级、告警或触发重试。

### 3.4 Candidate Rerank / Judge

Candidate Rerank 是候选重排和裁判层。它负责在多通道宽召回之后判断候选是否真正回答当前问题，并降低语义相似但业务无关的噪声。

重排层必须是通用能力，不能在知识库核心层硬编码金融表名、业务 source id 或某个数据源的特殊规则。

Candidate Judge 是 Candidate Rerank 中更强的一类判断。它不仅调整排序，还需要明确给出候选是否保留、是否可作为图扩展种子、是否只能作为低置信背景、是否应该丢弃。

### 3.5 Chunk Context

Chunk Context 是围绕命中片段补齐的上下文。向量检索通常只能命中某个片段，但业务判断往往需要标题、摘要、相邻段落、父文档、证据来源、相关实体和关系。

Query Context 不能只返回孤立 chunk。命中片段之后必须有上下文扩展机制，否则会出现“局部片段命中但语义不完整”或“真正相关内容落在相邻片段而没有被召回”的问题。

### 3.6 Agentic Retrieval Loop

Agentic Retrieval Loop 是复杂查询的深度检索模式。它不是替代确定性检索基线，而是在信息不足、候选冲突、上下文污染或长文档需要精读时，让模型通过受控工具循环继续查找、定位、打开和压缩证据。

该模式参考企业级 AgenticRAG 的思想：模型不应该在第一次召回后就被迫回答，而应该可以判断“信息是否足够、是否需要换查询、是否需要打开文档精读、是否需要压缩上下文”。但在本系统中，Agentic Retrieval 必须受 Query Anchor、Candidate Judge、证据引用和回放 trace 约束，不能变成不可审计的自由搜索。

### 3.7 Query Routing Decision

Query Routing Decision 是检索入口对本次查询选择执行路径的决策结果。它负责回答：本次查询应该先走确定性检索，还是直接进入 Agentic 检索；如果先走确定性检索，什么时候应该自动升级。

路由决策不是业务方手写 if/else，也不是让模型无约束自由决定。它必须基于 Query Anchor、强约束、复杂度信号和上一轮检索质量指标共同判断，并把决策原因写入 Query Context，便于回放和排查。

## 4. 输入和输出

### 4.1 输入

检索输入包括：

- 用户自然语言问题。
- 事件抽取任务上下文。
- 资产、行业、政策、主题等结构化查询条件。
- 检索模式，例如确定性检索、语义检索、混合检索、Agentic 检索。
- 复杂度路由信号，例如是否需要深度检索、是否允许多轮工具调用、最大工具调用次数。
- 上下文预算和证据要求。
- 可选的结构化过滤条件。
- 可选的回放评估条件，包括必须命中的证据、禁止出现的噪声主题、禁止出现的实体或关系。

### 4.2 输出

检索输出包括：

- 命中实体。
- 相关关系。
- 证据引用。
- Wiki 摘要引用。
- 路径或传导链。
- 质量告警。
- 检索通道和重排解释。
- Query Anchor 和候选裁判结果。
- Query Routing Decision，包括初始路由、升级原因、置信度和预算。
- 被丢弃候选和丢弃原因。
- Agentic Retrieval 的工具调用 trace、引用证据和停止原因。
- 可供 LLM 或业务模块使用的上下文包。

## 5. 核心设计决策

### 5.1 检索必须混合多通道

单纯向量检索无法稳定解决投研类问题。比如“宁德时代最近受哪些事件影响”需要先识别资产，再沿图找事件和影响关系，再回读证据。

因此检索应组合实体解析、图搜索、语义检索、Wiki 搜索和证据回读。

### 5.2 检索路由采用三段式决策

核心场景不能完全依赖 Agent 自由规划。第一版应优先提供确定性检索计划，保证真实库回放可重复、质量基线可比较。

Agentic 检索可以作为增强，但不能替代确定性基线。最终方案不是“只用规则”或“只用 LLM”，而是三段式路由：

1. **Fast Router**：先用确定性规则识别强约束和显著复杂度信号。
2. **LLM Router**：只在 Fast Router 无法明确判断时，由 LLM 基于 query、Query Anchor 和强约束给出路由建议。
3. **Post-check Router**：如果 deterministic_plan 的实际检索质量不达标，自动升级到 `agentic_arag`。

这套方案的决策规则如下：

- 用户显式指定检索模式时，显式指定优先。
- query 中存在 source id、evidence id、领域内强标识代码、精确标题片段等强约束时，优先走 `deterministic_plan`，先用低成本路径验证可命中性。
- query 明确包含复杂意图时，直接进入 `agentic_arag`。复杂意图包括但不限于：为什么、如何影响、传导、归因、对比、复盘、分别影响、受益对象、受损对象、多跳推理、候选冲突、长文档精读。
- Fast Router 无法判断时，调用 LLM Router。LLM Router 只负责判断查询复杂度和推荐执行模式，不负责检索事实、不直接决定最终答案。
- LLM Router 输出低置信时，不直接进入高成本 Agentic 检索，而是先走 `deterministic_plan`，再由 Post-check Router 根据实际质量决定是否升级。

LLM Router 的输入必须包含原始 query、Query Anchor、Guard Extractor 提取的强约束和可用预算。输出必须是结构化路由建议，至少包括推荐模式、复杂度、置信度、原因和最大工具调用预算。置信度低于阈值时，系统按保守策略先执行 `deterministic_plan`。

Post-check Router 是防止确定性检索“看似命中但上下文污染”的关键。`deterministic_plan` 执行后必须产出质量指标，例如：

- Query Anchor 覆盖度。
- 保留候选数量。
- 候选丢弃比例。
- evidence 覆盖数量。
- 是否存在主题冲突。
- 是否出现禁止命中的实体、主题或 evidence。
- 上下文纯度。

只要出现以下任一情况，就应自动升级到 `agentic_arag`：

- 没有可用 evidence。
- 没有候选通过 Candidate Judge。
- Query Anchor 覆盖度过低。
- 候选丢弃比例过高，说明宽召回噪声较重。
- 出现主题冲突或禁止命中的噪声。
- 上下文纯度低于可接受阈值。
- Query Anchor 本身置信度不足，需要进一步搜索和精读。

因此最终原则是：明确简单问题走 `deterministic_plan`，明确复杂问题走 `agentic_arag`，不确定问题先让 LLM Router 判断；LLM Router 仍不确定时先低成本执行 `deterministic_plan`，再用 Post-check Router 根据真实检索质量自动升级。

### 5.3 检索必须先识别 Query Anchor

多通道检索不能从 query 字符串直接跳到全库召回。系统必须先识别 Query Anchor，明确本次查询最核心的事件、实体、主题、时间和关系意图。

Query Anchor 不是为了硬过滤所有结果，而是为了给候选裁判提供判断依据。一个候选是否相关，不能只看向量相似度或 BM25 得分，还要看它是否覆盖或解释 Query Anchor。

第一版 Query Anchor 采用“Guard Extractor + LLM Anchor Parser + Anchor Validator”的混合方案。

Guard Extractor 只提取强约束，不做语义判断。它负责把 query 中相对确定的信息交给 LLM，例如：

- source id 和 evidence id。
- 领域内强标识代码，例如金融适配器中的证券代码、基金代码等。
- 日期和时间范围。
- query 原文中的长短语和标题片段。
- query 中精确匹配到的已有实体名。

LLM Anchor Parser 是 Query Anchor 的语义理解主力。它基于原始 query 和 Guard Extractor 提供的上下文，输出最终 Anchor，包括核心事件、核心实体、核心主题、关系意图、时间边界和排除边界。

Anchor Validator 是最后的程序校验层。它不重新做语义理解，只做以下事情：

- 如果 LLM 漏掉 Guard Extractor 提取的强约束，自动补回并记录 warning。
- 如果 LLM 输出 query 中没有依据、也不在候选实体中的内容，将其降级为弱提示或推断提示，不能作为强 Anchor。
- 如果 LLM 改写 source id、代码、日期等硬约束，触发重试或降级。
- 如果 LLM 输出低置信度 Anchor，允许保留可校验部分，但必须提示候选裁判降低该 Anchor 权重。

因此，本模块的设计原则是：LLM 负责理解，规则负责提供上下文和校验边界；以 LLM 输出为准，但必须通过程序校验后才能成为 Query Anchor。

### 5.4 多通道召回之后必须有通用候选裁判

多通道宽召回会提高召回率，但也会带来噪声。真实回放中已经出现过目标新闻可以命中，但同时混入语义相似、业务无关的 demo/CATL 内容的情况。

当前已经完成的数据投影、知识编译和写入治理，主要解决的是“如何把数据组织成可治理事实”。它还不等于完整 KG-RAG。只要检索侧仍然以全库向量/BM25 召回为主，并且没有在图谱扩展前判断候选是否真的相关，图谱就只是改善了数据组织方式，还没有成为检索阶段的强约束和裁判机制。

正确方向不是在通用 runtime 中硬编码 `ft_news:*` 这类数据源规则，而是增加通用候选重排层：

- 第一阶段识别 Query Anchor。
- 第二阶段保持多通道宽召回。
- 第三阶段统一评估候选 evidence、node、edge、wiki 和路径是否真正回答 query。
- 必要时由 LLM 参与 top-K 候选裁判。
- 只有通过裁判的候选才能继续触发图谱扩展和证据回读，避免无关 evidence 带出自己的 node/edge。
- 调用方如果有明确过滤条件，应通过结构化参数传入，而不是依赖自然语言 query 中的特殊字符串。

候选裁判至少需要回答：

- 候选是否覆盖 query 的核心事件或核心实体。
- 候选是否覆盖 Query Anchor 中的中心主题和关系意图。
- 候选是否只是语义相似但主题偏移。
- 候选 evidence 是否能解释当前问题。
- 候选 node/edge 是否由相关 evidence 支撑。
- 候选是否应该进入最终 Query Context，还是仅作为低置信噪声记录。

### 5.5 图谱扩展必须建立在通过裁判的候选之上

图谱扩展不是越多越好。图谱扩展的前提应该是 seed candidate 已经被 Query Anchor 和 Candidate Judge 判定为相关。

当前问题的根源之一是：全库语义召回命中无关 evidence 后，chunk read 会回读 evidence，evidence 又带出自己的 edges 和 nodes，导致一个无关候选被放大成一组无关实体和关系。正确策略是：

- semantic / wiki / graph / entity 通道都可以提供候选。
- 候选先进入统一裁判层。
- 只有 `keep` 或满足阈值的 `weak_keep` 候选可以成为图谱扩展 seed。
- 被判定为 `drop` 的候选不能继续扩展 node、edge、wiki 或 sibling chunk。
- 最终 Query Context 应保留裁判解释，方便定位为什么某个候选被保留或丢弃。

这条规则必须是通用能力，不能通过写死金融 source_id、表名或 demo 前缀来解决噪声。

### 5.6 Chunk 不能作为孤立上下文消费

向量数据库需要面向 chunk 建索引，但业务消费不能只拿命中的孤立 chunk。否则当文档被切分后，目标信息可能分散在标题、摘要、前后段落或同一 evidence 的其他片段中，单个 chunk 无法表达完整语义。

合理的检索结构应该至少区分三层：

1. 文档级召回：使用标题、摘要、核心实体、事件摘要和来源信息，解决“整篇材料相关但局部片段没命中”的问题。
2. 片段级召回：使用正文段落或语义段落，解决“文档太大导致语义稀释”的问题。
3. 上下文扩展：命中片段后回读父 evidence、相邻片段、相关 node/edge 和必要的 Wiki 摘要，形成完整 Query Context。

因此，chunk 是索引单元，不是最终消费单元。最终返回给使用方的应该是经过扩展、去重、裁判和预算控制后的上下文包。

### 5.7 复杂查询需要 Agentic Retrieval Loop

传统 RAG 和当前 deterministic_plan 的共同问题是：第一次检索后候选集基本被锁死，模型没有机会判断信息不足并主动回到知识库继续查找。企业级 AgenticRAG 的关键启发是，复杂问题需要让模型以工具调用方式迭代检索，而不是只接受一次召回结果。

本系统的 Agentic Retrieval Loop 应提供四类通用工具能力：

1. `search`：面向知识库做多查询宽召回，可组合实体、图、语义、Wiki 和证据通道。
2. `find`：在指定 evidence、Wiki、文档或候选集合内做精确定位，类似增强版文档内查找。
3. `open`：按窗口打开父 evidence、相邻 chunk、Wiki 页面、图谱路径或完整证据内容。
4. `summarize`：当上下文接近预算上限时压缩历史检索过程，但保留引用证据和关键判断。

Agentic Retrieval Loop 必须满足以下约束：

- 起点仍然是 Query Anchor，而不是让模型自由改写问题。
- 每次 `search/find/open` 的结果仍要进入 Candidate Judge。
- 只有通过裁判的候选可以进入最终 Query Context 或继续图谱扩展。
- 每轮工具调用必须记录 trace，包括输入、输出、保留证据、丢弃候选和停止原因。
- 达到最大工具调用次数、上下文预算或证据充分条件时必须停止。
- 如果工具调用失败或超时，应回退到 deterministic_plan 的可用上下文。

这意味着 Agentic Retrieval 不是“更自由的 RAG”，而是“有 Anchor、有工具、有裁判、有引用、有停止条件的深度检索模式”。

Agentic Retrieval 的工具调用必须有硬预算。第一版默认最多 6 次工具调用，高复杂度查询最多 10 次。允许的工具只包括知识检索相关能力，例如 `search`、`find`、`open`、`summarize`。如果连续两轮没有新增有效证据，或者 Candidate Judge 判断证据已经足够，应立即停止，不允许继续扩大搜索范围。

### 5.8 Demo 和回放不能只验证“是否命中”

真实检索质量不能只看目标 evidence 是否被命中。目标命中但上下文混入大量无关证据、实体和关系，也应该被视为质量问题。

回放评估至少需要区分：

- 必须命中的 evidence、node、edge。
- 不应该出现的噪声实体、主题或 evidence。
- 候选裁判前后的候选数量变化。
- 被丢弃候选的原因。
- Query Context 的上下文纯度。

因此 Demo 和 bad case replay 必须从“命中率评估”升级为“命中率 + 上下文纯度 + 噪声抑制”的评估。

### 5.9 检索结果必须可解释

检索输出不能只有一组相似文本。它必须说明为什么命中、命中了哪些实体和关系、对应哪些证据、用了哪些检索通道。

这对投研场景尤其重要，因为后续策略解释和复盘必须知道结论来源。

Agentic Retrieval 模式下尤其需要可解释。系统不仅要返回最终 Query Context，还要能说明模型为什么继续搜索、为什么打开某份 evidence、为什么停止、哪些候选被丢弃、哪些证据支撑最终上下文。

### 5.10 检索侧也要做去重和质量提示

即使写入侧已经做治理，检索侧仍然需要合并重复结果、提示类型冲突、过滤低质量证据。

检索侧去重不能替代主图治理，但可以降低使用方看到脏结果的概率。

## 6. 模块边界

本模块负责：

- 定义 Query Context 的业务含义。
- 定义混合检索通道组合。
- 定义 Query Anchor 的业务定位。
- 定义检索路由决策和自动升级原则。
- 定义 chunk、父 evidence、相邻片段和图谱上下文的关系。
- 定义候选重排和相关性裁判的定位。
- 定义图谱扩展必须受候选裁判约束。
- 定义 Agentic Retrieval Loop 的业务定位、工具边界和停止条件。
- 定义检索结果可解释和质量告警要求。
- 定义回放评估的上下文纯度要求。

本模块不负责：

- 从原始数据生成事实。
- 决定实体最终标准化结果。
- 生成 Wiki 页面。
- 定义数据库和索引字段。
- 编写 API、CLI 和重排算法实现细节。
- 让 Agent 直接执行业务动作或修改主图事实。

## 7. 和其他模块的关系

检索消费事实库、标准实体、关系、证据和 Wiki 派生页面。它依赖数据源投影、知识编译、领域适配和实体治理提供干净、可追踪、可解释的数据。

检索模块发现的坏例、重复结果和相关性噪声应该反馈给实体治理、知识编译和质量回放，形成治理闭环。

## 8. 验收口径

该设计成立的标准是：

- 典型投研问题能返回实体、关系、证据和可读上下文。
- 检索结果能说明使用了哪些通道。
- 核心场景支持确定性回放。
- 多通道召回后的候选噪声有重排或质量提示机制。
- Query Anchor 能约束候选裁判和后续图谱扩展。
- 检索入口能产出 Query Routing Decision，并说明为什么选择 deterministic_plan 或 agentic_arag。
- deterministic_plan 低质量时能根据上下文纯度、Anchor 覆盖度、候选裁判结果和 evidence 覆盖自动升级到 agentic_arag。
- 无关候选不能因为命中语义检索而继续扩展出自己的 node/edge。
- 命中 chunk 后能补齐父 evidence、相邻片段或等价上下文，避免孤立片段被直接消费。
- 复杂查询可以进入 Agentic Retrieval Loop，并通过 search/find/open/summarize 工具补齐证据。
- Agentic Retrieval 的每一步都有 trace、引用证据和停止原因。
- 回放评估能识别“目标命中但上下文污染”的失败场景。
- 使用方消费统一 Query Context，而不是直接消费底层索引结果。
