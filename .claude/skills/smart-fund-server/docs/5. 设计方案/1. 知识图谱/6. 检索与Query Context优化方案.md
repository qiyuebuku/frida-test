# 检索与 Query Context 优化方案

> 本文是 `4. 检索与Query Context设计方案.md` 的专项优化方案。本文不引入独立的“字符串 guard / 关键词过滤”层；正式优化方向是 Query Anchor、图路径证据、关系意图、LLM Candidate Judge 和受控 Agentic Retrieval Loop 协同完成候选裁判与深度检索。确定性规则只保留为硬标识提取与校验能力。

## 1. 本文解决什么问题

本文解决知识图谱检索中的上下文污染问题。

真实回放中已经出现过这类结果：查询“宁德时代 300750 最近受哪些事件影响”时，系统能召回宁德时代相关事件，但最终 Query Context 里同时混入“波兰法国联合军事演习”“俄罗斯”“法国”“波兰”等无关内容。

这说明当前短板不是“召回不到”，而是“召回之后无法可靠判断候选是否真的回答当前问题”。如果只是依赖向量相似度、图上可达、关键词包含或字符串模糊匹配，系统仍然只是披着知识图谱外衣的弱 RAG。

本文的目标是把检索治理升级为真正的 KG-RAG 裁判与检索闭环：

- 候选是否相关，必须看它能否解释 Query Anchor。
- 图谱扩展是否继续，必须看路径、关系意图和证据支撑。
- LLM 可以参与候选裁判，也可以在复杂查询中作为受控检索控制器决定是否继续 search、find、open 或 summarize。
- LLM 不能直接改写主图事实，不能凭空生成未被召回和未被证据支撑的事实。
- 硬标识约束只能用于保留用户明确给出的代码、source id、evidence id、日期和精确标题，不能作为最终相关性判断。

## 2. 本文不解决什么问题

本文不讨论原始业务表如何投影为 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论 Source Record 如何抽取实体、关系和证据；这属于“知识编译、标准化与写入”模块。

本文不定义通用 Node、Edge、Evidence 和领域适配器协议；这属于“知识模型与领域适配”模块。

本文不替代“检索与 Query Context”总设计。第 4 篇负责说明检索总体架构，本文作为第 4 篇的优化方案，只聚焦候选裁判、图扩展治理、上下文污染控制和 auto 路由升级。

本文不写具体代码结构、接口字段、数据库表结构、Prompt 模板和测试命令。这些应放入对应实施方案。

## 3. 核心问题判断

### 3.1 当前问题不是简单噪声，而是候选裁判能力缺失

多通道检索会同时返回实体、边、证据、Wiki、chunk 和路径。只要其中一个无关候选被保留，它就可能通过 evidence 回读和图扩展带出一组无关 node/edge，最终污染 Query Context。

这类污染不能靠提高向量阈值解决，也不能靠硬编码黑名单解决。因为真实生产数据中，本来就会有相似主题、交叉实体、宽泛地区、市场概念和多事件共现。

真正缺失的是：候选进入最终上下文之前，需要有一个通用 Candidate Judge 判断它是否真的回答当前 query。

### 3.2 当前检索还缺少“重新检索和精读”的权利

仅有 Candidate Judge 仍然不够。Candidate Judge 可以把坏候选丢掉，但如果第一次召回本身不充分，系统仍然会陷入“只能在现有候选里挑”的局面。

企业级 AgenticRAG 的核心启发是：复杂查询不能在第一次搜索后就锁死候选集。模型需要有受控能力判断：

- 当前证据是否足够回答问题。
- 是否需要换一个查询表达重新 search。
- 是否需要在指定 evidence 或 Wiki 内 find。
- 是否需要 open 父文档、相邻 chunk 或完整证据精读。
- 是否需要 summarize 压缩过程上下文并保留引用证据。

因此本文的优化目标不是只增加 LLM rerank，而是让复杂查询进入受控 Agentic Retrieval Loop。LLM 在这个 loop 中不是事实源，而是检索控制器和候选裁判器。

### 3.3 不引入独立字符串过滤层，只保留硬标识约束

“最终上下文必须包含宁德时代/300750”这类字符串过滤，看起来可以快速挡住一部分明显无关候选，但不适合成为系统设计。它会引入一套额外的模糊匹配规则，规则越来越多，效果却并不可靠。

因此本文明确不设计独立的字符串 guard 层，也不把关键词包含、模糊匹配、黑名单、同义词扩展作为候选最终保留或丢弃的依据。

字符串过滤的问题很明确：

- 会误杀有效间接证据。证据本身可能不写“宁德时代”，但通过可信图路径支撑了宁德时代相关结论。
- 会放过偶然提及的噪声。一篇文章只要随口提到“宁德时代”，即使主题完全不相关，也可能被保留。
- 无法理解关系意图。查询“受哪些事件影响”时，关键是事件是否通过影响关系连接到目标，而不是文本里是否出现目标字符串。
- 无法处理多跳推理。复杂查询需要判断路径是否合理，而不是判断每个片段是否包含关键词。
- 会让检索链路变复杂。为了避免误杀，又要补同义词、别名、反例、白名单，最后变成一套难维护的伪语义规则。

需要保留的不是“字符串过滤”，而是低歧义的硬标识约束。它的价值只在于：

- 提取用户明确给出的证券代码、source id、evidence id、日期、精确引用标题。
- 把这些硬标识交给 LLM Anchor Parser，帮助 LLM 稳定理解查询对象。
- 校验 LLM 输出是否丢失或改写了用户明确给出的硬标识。
- 在候选包里标记“是否直接命中硬标识”或“是否通过可信图路径连接到硬标识”，作为 Candidate Judge 的输入特征。

硬标识约束不能单独决定候选最终保留或丢弃。最终相关性仍由 Candidate Package、图路径、关系意图和 LLM Candidate Judge 共同判断。

### 3.4 正式方案必须是“语义裁判 + 图路径裁判 + 受控检索循环”

正确的候选裁判不能只看文本相似，也不能只看图上是否连通。它必须同时回答：

- 候选是否覆盖 Query Anchor 的核心实体、事件、主题或时间范围。
- 候选是否符合 query 的关系意图，例如影响、受益、风险、传导、原因、对比。
- 候选是否有证据支撑，而不是只是图上可达。
- 候选路径是否合理，是否穿过宽泛 hub 节点造成主题漂移。
- 候选是直接回答、间接支撑、背景材料，还是无关噪声。

这意味着正式方案必须引入 LLM Candidate Judge。LLM 不负责全库搜索，也不直接写主图；它只对已经召回的 top-K 候选做语义裁判，并输出结构化判断。

对于复杂查询，LLM Candidate Judge 之后还必须允许系统继续检索。否则它只能判断“当前候选不够好”，却没有能力补证据。正式方案必须把 Candidate Judge 和 Agentic Retrieval Loop 连接起来：Judge 发现证据不足、路径冲突或主题漂移时，系统应该能继续 search、find、open 或 summarize，而不是直接返回低质量上下文。

## 4. 核心业务对象

### 4.1 Query Anchor

Query Anchor 是一次查询最核心的语义约束，包括核心实体、核心事件、主题、时间范围、关系意图和排除边界。

Query Anchor 不能只由字符串规则生成。合理方式是：

- Hard Constraint Extractor 提取不会错的硬约束，例如证券代码、source id、evidence id、日期和明确引用标题。
- LLM Anchor Parser 理解 query 的核心意图。
- Anchor Validator 校验 LLM 输出没有丢失硬约束、没有凭空加入无依据实体。

### 4.2 Candidate Package

Candidate Package 是交给候选裁判的完整候选包，不是单个 chunk 或单个 edge。

它至少应该包含：

- candidate 自身信息：类型、标题、摘要、来源通道、分数。
- 关联 node：source/target 名称、类型、别名、重要属性。
- 关联 edge：关系类型、方向、置信度、状态、支撑 evidence。
- 关联 evidence：标题、正文摘要、来源、时间、证据片段。
- 图路径信息：从 Query Anchor 到候选的路径、跳数、是否经过 hub。
- 候选与 Query Anchor 的初步匹配信号。

Candidate Judge 判断的是 Candidate Package，而不是孤立字符串。

### 4.3 Candidate Judge

Candidate Judge 是候选裁判层。它负责判断候选是否进入 Query Context、是否允许继续扩展、是否只作为背景、是否应丢弃。

裁判输出至少需要包括：

- `decision`：`keep`、`weak_keep`、`drop`。
- `role`：直接回答、间接支撑、背景、噪声。
- `relevance_reason`：为什么相关或为什么不相关。
- `anchor_coverage`：覆盖了哪些 Query Anchor。
- `intent_match`：是否符合 query 的关系意图。
- `path_validity`：图路径是否合理，是否穿过 hub 后漂移。
- `evidence_support`：证据是否足够。
- `can_expand_graph`：是否允许继续图扩展。
- `risk_flags`：主题漂移、偶然提及、证据不足、路径过宽等风险。

### 4.4 Expansion Seed

Expansion Seed 是允许继续触发图扩展、证据回读、Wiki 扩展和 sibling chunk 扩展的候选。

只有 Candidate Judge 判定为 `keep` 且 `can_expand_graph=true` 的候选才能成为 Expansion Seed。

`weak_keep` 只能进入低置信背景区，不能继续扩展。

### 4.5 Hub Node

Hub Node 是连接度高、语义宽泛、容易造成主题跳转的节点，例如泛化地区、宽泛行业、市场大类、通用政策词、热门概念。

Hub Node 不是不能出现，但不能默认继续 fan-out。通过 Hub Node 产生的二跳候选必须重新裁判，而且需要更高阈值。

### 4.6 Context Purity

Context Purity 是最终 Query Context 的纯度指标。它衡量上下文是否围绕 query，而不是只衡量有没有命中目标 evidence。

一个结果即使命中了目标 evidence，只要混入明显无关主题，也应该被判定为失败或触发更强检索模式。

### 4.7 Retrieval Controller

Retrieval Controller 是复杂查询中的检索控制器。它由 LLM 驱动，但受 Query Anchor、Candidate Judge、工具预算、证据引用和 trace 约束。

Retrieval Controller 负责决定下一步是否需要：

- `search`：重新组织查询，做多通道宽召回。
- `find`：在指定 evidence、Wiki、文档或候选集合内定位关键信息。
- `open`：打开父 evidence、相邻 chunk、完整证据或图谱路径做精读。
- `summarize`：在上下文接近预算时压缩过程信息，但保留引用证据和裁判结论。

Retrieval Controller 不能直接回答事实，不能写入主图，不能绕过 Candidate Judge。它每次工具调用后的结果都必须重新构建 Candidate Package 并进入 Candidate Judge。

Retrieval Controller 不能退化成“把原始 query 改写成另一句 search query”的薄封装。它的输出必须能实质影响后续检索行为，包括搜索目标、候选边界、证据期待、负向边界和停止条件。

因此 Retrieval Controller 的核心输出不是单个 `query_rewrite`，而是 Search Plan。Search Plan 至少需要说明：

- `answer_targets`：本轮希望回答或补齐的对象，例如事件、受影响行业、资产、原因、风险、传导路径。
- `query_rewrites`：多条互补检索表达，分别覆盖原始说法、同义表达、实体名、代码、关系意图和行业术语。
- `negative_boundaries`：本轮应避免混入的主题漂移方向，例如军事新闻、无关宏观主题、只共享地区的候选。
- `expected_evidence`：期望找到的证据类型，例如事件 evidence、影响关系、行业对象、资金流信号、政策原文或长文档段落。
- `relation_intent`：本轮检索关注的关系意图，例如 impact、beneficiary、cause、risk、comparison。
- `stop_condition`：什么情况下认为证据足够，什么情况下需要继续 find/open/search。

Search Plan 中的多条 `query_rewrites` 都应该被执行或被明确丢弃并记录原因，不能只取第一条。否则 controller 输出看似复杂，实际只影响一个字符串，无法体现 Agentic Retrieval 的价值。

但多 rewrite 不能理解成“每条 rewrite 都完整跑一遍所有重型通道”。语义向量检索、长文档读取、LLM judge 都是昂贵步骤，执行层必须按成本分层：

- 首条最高置信 rewrite 可以执行完整多通道召回。
- 后续 rewrite 默认只做轻量补召回，例如实体解析、图搜索、Wiki 或精确字段检索。
- 只有首轮候选明显不足、Anchor 覆盖不足或关系意图缺失时，才允许追加语义召回。
- 每条 rewrite 使用了哪些通道、哪些通道被跳过、跳过原因是什么，都必须写入 trace。

也就是说，Search Plan 的价值是让召回更有方向，而不是把一次查询线性放大成多次全库语义检索。

### 4.8 Retrieval Working Set

Retrieval Working Set 是 Agentic Retrieval Loop 中临时维护的证据工作集。

它保存：

- 已通过 Candidate Judge 的 evidence、node、edge、path。
- 被判定为 `weak_keep` 的低置信背景。
- 被丢弃候选及原因。
- 已打开过的文档窗口。
- 当前仍缺失的 Query Anchor 覆盖项。
- 停止检索或继续检索的原因。

Working Set 是临时查询态，不写入主图。它的价值是让 Agentic Loop 有记忆、有预算、有证据边界，而不是每一轮重新随机搜索。

## 5. 输入和输出

### 5.1 输入

本模块输入包括：

- 原始 query。
- Query Anchor。
- 多通道召回结果。
- Candidate Package。
- 图路径信息。
- 领域适配器提供的实体类型、关系类型和 hub 建议。
- 可选的历史 bad case 约束。
- 上下文预算。

### 5.2 输出

本模块输出包括：

- 候选裁判结果。
- 可进入 Query Context 的候选集合。
- 可继续扩展的 Expansion Seed 集合。
- 被丢弃候选及原因。
- 被截断路径和 hub 扩展原因。
- Context Purity 指标。
- 是否需要升级到 agentic_arag。
- Agentic Retrieval 的工具调用 trace。
- Retrieval Working Set 摘要。
- 停止检索原因。
- 可回放的裁判 trace。

## 6. 核心设计决策

### 6.1 Candidate Judge 必须成为检索主链路

候选裁判不是可选增强，而是检索主链路的一部分。

正式流程应为：

1. 识别 Query Anchor。
2. 多通道宽召回。
3. 构建 Candidate Package。
4. Candidate Judge 裁判候选。
5. 只使用 `keep` 候选构建 Query Context。
6. 只使用允许扩展的候选继续图扩展。
7. 对扩展结果再次裁判。
8. 生成最终 Query Context 和裁判 trace。

任何绕过 Candidate Judge 直接进入最终上下文的候选，都属于设计缺陷。

### 6.2 LLM Candidate Judge 必须参与语义相关性判断

确定性规则可以识别硬约束、关系类型、路径长度、hub 节点和明显冲突，但它无法可靠判断语义是否真的相关。

因此 LLM Candidate Judge 必须参与 top-K 候选裁判，尤其是以下场景：

- query 是自然语言语义问题，而不是精确 source/evidence 查询。
- 候选来自语义检索。
- 候选通过 hub 节点或二跳路径到达。
- 候选只间接关联 Query Anchor。
- deterministic judge 给出低置信或冲突信号。
- bad case replay 出现 forbidden hit。

LLM Judge 的职责是裁判候选，不是生成答案，也不是修改主图。它必须基于 Candidate Package 输出结构化判断。

### 6.3 复杂查询必须进入受控 Agentic Retrieval Loop

复杂查询不能只执行一次多通道召回。一次召回会过早锁死候选集，导致后续 LLM 只能在不完整候选里裁判，无法主动补证据。

以下场景必须进入或升级到 Agentic Retrieval Loop：

- query 涉及原因、影响链、传导、归因、对比、复盘、多跳推理。
- Candidate Judge 判断证据不足。
- deterministic_plan 命中目标 evidence 但 Context Purity 不足。
- 候选之间互相冲突。
- 需要打开长 evidence、Wiki 或 sibling chunk 才能判断。
- 多轮检索可能显著提升证据覆盖，而不是简单增加噪声。

Agentic Retrieval Loop 的核心不是“多搜几次”，而是让模型拥有受控的检索决策权：搜什么、打开哪里、什么时候证据足够、什么时候停止。

### 6.4 Agentic 工具必须围绕证据精读设计

第一版 Agentic 工具应保持少而清晰：

- `search` 用于重新组织查询并进行多通道召回。
- `find` 用于在指定候选、evidence、Wiki 或文档内定位关键内容。
- `open` 用于打开父 evidence、相邻 chunk、完整证据、Wiki 页面或图谱路径。
- `summarize` 用于压缩过程上下文，但必须保留引用证据、裁判结论和未覆盖 Anchor。

这些工具不是让 LLM 自由访问外部世界，而是让它在知识库内部完成可审计检索。每个工具输出都必须进入 Candidate Package 和 Candidate Judge。

### 6.5 硬约束规则负责校验，不负责语义裁判

硬约束规则仍然必要，但职责要收窄。

规则负责：

- source id、evidence id、证券代码、日期等硬约束提取。
- 检查 LLM 输出是否保留硬约束。
- 标记候选是否直接出现强约束。
- 标记候选是否通过图路径连接到强约束。
- 标记明显不合法路径或超预算路径。

规则不应该负责：

- 单独决定候选语义相关。
- 用字符串包含替代语义裁判。
- 用关键词、模糊匹配、黑名单或白名单替代语义裁判。
- 用硬编码业务表名或测试样本前缀判断候选。

最终相关性判断应由规则信号、图路径信号、关系意图信号和 LLM Judge 共同决定。

### 6.6 图路径必须作为证据，而不是简单可达性

图上可达不等于相关。图路径必须能解释 query。

路径裁判至少需要看：

- 起点是否是 Query Anchor 中的核心实体、事件或证据。
- 关系类型是否符合 query 意图。
- 跳数是否合理。
- 是否穿过 hub 节点。
- 每条边是否有 evidence 支撑。
- 路径上的 evidence 是否仍然围绕当前 query。

例如“宁德时代受哪些事件影响”中，`事件 -> affects -> 宁德时代` 是强路径；`宁德时代 -> 欧洲 -> 波兰法国军演` 是主题漂移路径，即使图上可达也不能进入最终上下文。

### 6.7 关系意图必须参与裁判

不同 query 对关系的要求不同。

- “受哪些事件影响”需要优先保留影响类路径，例如 `event -> affects -> entity`。
- “提到了哪些实体”可以保留 mentions。
- “为什么上涨”需要事件、信号、资金流、情绪、宏观因素之间的解释路径。
- “影响哪些行业”需要候选中存在行业/板块/概念对象，并且有影响类关系或明确证据描述。

因此 Candidate Judge 不能只看候选是否包含 anchor，还要判断候选是否满足关系意图。

### 6.8 weak_keep 不能继续扩展

`weak_keep` 的含义是“可能有背景价值，但不足以成为扩展依据”。

`weak_keep` 不能触发：

- evidence 回读。
- graph fan-out。
- sibling chunk 扩展。
- Wiki 扩展。
- 路径继续延伸。

如果 `weak_keep` 最终被展示，也必须标记为低置信背景，不能混入主答案证据链。

### 6.9 Hub Node 扩展必须二次裁判

Hub Node 可以帮助解释上下文，但不能默认作为继续扩展跳板。

通过 Hub Node 产生的候选必须进入 LLM Candidate Judge，并且需要满足更严格条件：

- 与 Query Anchor 仍然有明确语义关系。
- 路径上的关系类型符合 query 意图。
- 支撑 evidence 没有主题漂移。
- 不只是因为共享宽泛地区、宽泛行业或通用概念而连接。

### 6.10 Agentic Retrieval 必须强化裁判，而不是绕过裁判

auto 升级到 agentic_arag 的目的不是“换一种语义检索再捞一批候选”，而是让系统具备更强的检索、精读、裁判和去噪能力。

Agentic Retrieval 必须遵守：

- 每轮工具调用都以 Query Anchor 为约束。
- Retrieval Controller 每轮只能选择知识库内工具，不能直接生成主图事实。
- 每轮召回结果都构建 Candidate Package。
- 每轮候选都经过 Candidate Judge。
- 只有 `keep` 且 `can_expand_graph=true` 的候选能进入 Working Set 主证据区。
- `weak_keep` 只能作为背景，不能触发继续扩展。
- 工具调用 trace 记录保留、丢弃和继续检索原因。
- 停止条件必须明确，例如证据覆盖足够、预算耗尽、连续无新增有效证据或新增候选均为 drop。
- 如果上下文污染仍然存在，不能因为命中目标 evidence 就判定成功。

### 6.11 成本和质量通过路由平衡

Agentic Retrieval 会更慢、更贵，因此不能无差别用于所有查询。

本文的决策是：

- 简单、明确、可结构化的问题优先走 deterministic_plan。
- 自然语言投研分析、长文档精读、多跳推理、候选冲突和上下文污染场景走 agentic_arag。
- deterministic_plan 的质量不达标时自动升级。
- agentic_arag 必须有工具调用预算、上下文预算和停止条件。

成本控制不能通过降低裁判质量实现，而应该通过路由和预算实现。

### 6.12 LLM 调用必须预算化，不能每一步都问模型

LLM 在检索链路中的价值是语义理解、候选裁判和复杂检索策略，不是替代所有状态机判断。当前真实回放已经证明，如果每轮 controller、每轮 judge、最终 stop 都调用 LLM，单个普通 query 可能产生 5 次以上 LLM 调用，并把主要耗时集中在候选裁判和多余 controller 决策上。

本文明确：不是所有 Agentic Retrieval 步骤都必须用 LLM。默认策略应是“LLM 做关键语义判断，程序做确定性状态推进”。

LLM 应参与：

- 首轮 query 理解或 search rewrite，尤其是自然语言投研问题。
- top-K 候选语义裁判，判断候选是否真正回答 Query Anchor。
- 证据不足、候选冲突、长文档精读、多跳推理时的下一步检索策略。

LLM 不应参与：

- 已有足够高置信 keep evidence 后的普通 `open` 决策。
- 已满足停止条件后的 `stop` 决策。
- 对全部 30 个以上宽召回候选逐条裁判。
- 对同一批候选反复裁判，除非打开了新的 evidence 或补充了新的上下文。
- 用自然语言重复解释已经可由 Working Set 判断的状态。

这里的“1 次 controller + 1 次 judge”不是硬性上限，而是普通 query 的默认预算和优化目标。系统不能为了省 LLM 调用牺牲召回，也不能在复杂 query 上机械截断检索循环。是否继续进入第二轮，必须由质量门槛决定。

普通 query 的默认调用预算是：

1. 最多 1 次 Retrieval Controller，用于生成初始 search 或确认复杂检索策略。
2. 最多 1 次 LLM Candidate Judge，用于裁判程序预筛后的 top 10-15 个 Candidate Package。
3. 如果 LLM Judge 已经产生足够 `keep` evidence，系统应自动 `open` 核心 evidence，并由程序自动 `stop`。
4. 只有 evidence 不足、Anchor 覆盖不足、候选冲突或打开证据后发现缺口时，才允许进入第二轮 LLM controller 或 judge。

允许突破默认预算的条件包括：

- 第一轮没有 `keep` evidence。
- `keep` 候选只是背景或实体页，不能直接回答 query。
- Anchor coverage 低于阈值，例如只覆盖主题词，没有覆盖关系意图或关键对象。
- query 涉及多跳推理、归因、传导、对比、复盘或长文档精读。
- 候选之间存在冲突，需要打开证据或重新搜索验证。
- `open` 后发现 evidence 正文不足、引用不完整或仍缺少核心答案对象。
- LLM Judge 输出低置信，或大量候选为 `weak_keep`。
- 回放指标出现 topic conflict、forbidden hit 或 Context Purity 不足。

这意味着 Agentic Retrieval Loop 不是“每一步都交给 LLM 决策”，而是：

```text
LLM/规则生成初始 search
 -> 多通道召回
 -> 程序预筛 top 10-15
 -> LLM Candidate Judge
 -> 如果 keep evidence 足够：程序自动 open + 程序自动 stop
 -> 如果不足：再让 LLM Controller 决定补搜、find 或 open
```

top-K 预筛也不能简单按向量分数截断。正确做法是先宽召回 30-60 个候选，再做候选归并和多样性保留：

- 同一 evidence、node、edge、wiki 多通道命中要合并，不重复占用 top-K。
- 每类通道保留必要名额，避免 entity、graph、evidence、wiki、semantic 互相挤掉。
- 有 evidence 支撑、关系意图匹配、路径清晰的候选优先。
- 覆盖不同实体、事件、行业、资产或关系意图的候选优先。
- hub 节点、mention-only、无证据支撑或明显背景候选降权。
- 如果第一批 top-K 中 `keep` 很少或 Anchor 覆盖不足，允许补第二批候选进入 LLM Judge。

停止条件应优先由程序判断：

- `keep` evidence 数量达到查询类型要求。
- Anchor coverage 达标。
- core relation intent 已被支持，例如 impact / beneficiary / cause。
- 核心 evidence 已 open。
- 新增候选全部为 drop 或连续无新增有效 evidence。
- 工具调用或 LLM 调用预算耗尽。

LLM Controller 的职责是处理“下一步该怎么补证据”的复杂策略，而不是在证据已充分时再生成一段 stop 理由。

### 6.13 Retrieval Controller 必须产出 Search Plan，而不是单句 query rewrite

当前真实回放暴露出一个新的问题：首轮 Retrieval Controller 输出了多条 `query_rewrites`，但执行层只使用第一条。这导致 controller 看起来参与了检索规划，实际只是把原始 query 改写成一个近似搜索词，对后续结果质量没有实质提升。

本文明确：Retrieval Controller 的价值不在于“改写一句搜索词”，而在于生成受 Query Anchor 约束的 Search Plan，并让执行层按 plan 召回、归并和裁判候选。

Search Plan 的设计原则是：

- 多条 query rewrite 是互补召回策略，不是同义句装饰。
- 每条 query rewrite 应覆盖不同检索侧面，例如核心实体、代码、关系意图、行业对象、事件标题、证据类型。
- 执行层必须执行多条 rewrite 并归并候选，或记录为什么只执行其中一部分。
- 执行层必须按成本分层执行多条 rewrite，不能默认每条 rewrite 都触发完整语义向量检索。
- Search Plan 必须携带 `answer_targets` 和 `expected_evidence`，让 Candidate Judge 知道本轮要找什么。
- Search Plan 必须携带 `negative_boundaries`，让 Candidate Judge 明确哪些看似相似但不应进入上下文。
- Search Plan 不能替代 Candidate Judge。它只定义检索目标和边界，候选最终是否进入 Query Context 仍由 Candidate Judge 决定。

首轮 controller 在没有 observations 时仍然可以有价值，但前提是它必须完成查询规划，而不是只说“需要先搜索”。首轮 controller 应至少输出：

```text
Search Plan
 -> 本次要回答什么
 -> 哪些对象和关系必须覆盖
 -> 从哪些表达方式召回
 -> 预期 evidence 类型是什么
 -> 哪些主题边界需要排除
```

后续轮次 controller 则应基于 Working Set 和 Candidate Judge 结果决定：

- 已有 keep evidence 是否足够。
- 是否需要 open 已通过裁判的 evidence。
- 是否需要 find 指定 evidence 中的关键事实。
- 是否需要换一组 query rewrite 继续 search。
- 是否需要停止并输出当前 Query Context。

验收时不能只看 controller 是否返回了合法 JSON，还要看 Search Plan 是否真的改变了执行行为，例如多 query 召回是否产生了不同候选、negative boundary 是否降低主题漂移、expected evidence 是否帮助 judge 丢弃无证据候选。

### 6.14 Context Purity 必须成为一等质量指标

检索质量不能只看 recall。

Context Purity 应至少衡量：

- 最终 evidence 是否都能通过直接证据、图路径或 LLM 裁判解释与 query 的关系。
- top nodes 是否存在明显无关实体。
- top edges 是否符合 query 关系意图。
- 是否出现主题漂移。
- 是否有候选只是偶然提及 anchor。
- 是否混入 forbidden bad case 中的实体、主题或 evidence。

Context Purity 不应由字符串命中率计算，而应由 Candidate Judge、路径裁判和 bad case 指标共同决定。

## 7. 推荐检索治理流程

### 7.1 deterministic_plan

deterministic_plan 应保持可重复、低成本，但不能没有裁判。

流程：

1. Hard Constraint Extractor 提取硬约束。
2. Query Anchor Parser 生成语义 Anchor。
3. 多通道召回候选。
4. 构建 Candidate Package。
5. 使用确定性规则做初筛和风险标记。
6. 对高风险、二跳、hub、语义检索候选调用 LLM Candidate Judge。
7. 只保留通过裁判的候选。
8. 用通过裁判的候选构建 Query Context。

### 7.2 agentic_arag

agentic_arag 应用于复杂、多跳、低置信、候选冲突或 deterministic 结果污染的场景。

流程：

1. 读取 Query Anchor 和 deterministic 失败原因。
2. 初始化 Retrieval Working Set，记录已命中证据、噪声、缺口和预算。
3. Retrieval Controller 基于缺口选择工具，例如 search、find、open、summarize。
4. 每轮工具结果构建 Candidate Package。
5. LLM Candidate Judge 裁判候选。
6. 只把通过裁判的证据加入 Working Set 主证据区。
7. 如果 keep evidence 已足够，程序自动 open 核心 evidence，不再请求 LLM Controller 决定是否 open。
8. 对证据不足、候选冲突、长文档上下文缺失的情况继续 find/open/search。
9. 当证据充分、预算耗尽、连续无新增有效证据或新增候选均为 drop 时，由程序自动停止。
10. 输出最终 Query Context、Working Set 摘要和完整 trace。

## 8. 模块边界

### 8.1 与检索与 Query Context 的关系

第 4 篇定义检索总体架构；本文定义第 4 篇必须补上的治理能力。

### 8.2 与知识编译、标准化与写入的关系

写入模块负责主图事实质量。本文不修改主图事实，只决定某次查询中哪些事实适合进入 Query Context。

### 8.3 与领域适配器的关系

领域适配器可以提供：

- 关系类型的业务含义。
- 节点类型的重要性。
- hub 节点建议。
- query intent 与关系类型的偏好。

但领域适配器不能绕过 Candidate Judge，也不能把具体业务表名或测试样本硬编码进通用 runtime。

### 8.4 与 LLM 的关系

LLM 在本模块中的角色有三个：Anchor Parser、Candidate Judge 和复杂查询下的 Retrieval Controller。它不是事实源。

LLM 可以判断 query 意图、候选是否回答 query、路径是否漂移、证据是否充分，也可以在 Agentic Retrieval Loop 中决定下一步调用 search、find、open 或 summarize。但它不能直接决定主图写入，也不能凭空生成未被召回和未被证据支撑的事实。

### 8.5 与参考 AgenticRAG 思路的关系

本文吸收企业级 AgenticRAG 的核心思想：复杂查询不应被第一次搜索锁死候选集，模型应该能在受控工具循环中继续搜索、定位、打开和压缩证据。

但本文不照搬通用企业文档 QA。知识图谱场景必须增加额外约束：

- 工具结果必须转换为 Candidate Package。
- 每个候选必须经过 Candidate Judge。
- 图扩展必须从通过裁判的 Expansion Seed 出发。
- 最终上下文必须可追溯到 evidence、path 和 judgement。
- LLM 不能直接写主图事实。

## 9. 验收口径

本优化方案落地后，至少需要满足以下验收口径：

1. 查询“宁德时代 300750 最近受哪些事件影响”时，不应把军演新闻、俄罗斯、法国、波兰等无关上下文带入最终 Query Context。
2. 查询“俄就波法联合军演发出警告：欧洲对俄全面对抗正在回归”时，不应把宁德时代、固态电池、储能供应链等无关上下文带入最终 Query Context。
3. 查询“并购重组对哪些行业有影响”时，可以返回券商、半导体设备、新能源车产业链等候选，但不应混入宁德时代资金流等无关资产信号。
4. 目标 evidence 命中但上下文污染时，bad case replay 必须判定失败。
5. `weak_keep` 候选不能继续触发 evidence 回读和图谱扩展。
6. 通过 hub node 产生的二跳候选必须进入 LLM Candidate Judge，不能默认进入上下文。
7. Candidate Judge trace 必须能解释候选为何保留、弱保留或丢弃。
8. Context Purity 必须能反映上下文污染，不能因为字符串命中或目标 evidence 命中而虚高。
9. 治理策略不能依赖具体业务表名、source id 前缀、demo 数据前缀或某个测试样本硬编码。
10. 复杂查询或 deterministic 低质量结果必须进入 Agentic Retrieval Loop，不能只在一次召回结果里挑候选。
11. Agentic Retrieval 每轮工具调用必须产出 trace，并记录 search/find/open/summarize 的原因、候选裁判结果和停止原因。
12. 命中孤立 chunk 时必须能 open 父 evidence 或 sibling window；不能直接把孤立 chunk 当作完整证据消费。
13. Agentic Retrieval 不能绕过 Candidate Judge，也不能把 LLM 生成内容当成主图事实。
14. 普通 query 不应超过 1 次 controller + 1 次 judge；证据充分后的 open 和 stop 应由程序自动完成。
15. LLM Candidate Judge 默认只裁判程序预筛后的 top 10-15 个 Candidate Package，不能把全量宽召回候选直接塞给模型。
16. trace 应能看出每次 LLM 调用的原因、耗时、候选数量、keep/drop 结果，并能区分 LLM judgement 与 deterministic fallback。
