# Agentic 检索候选排序优化方案

## 1. 本文解决什么问题

本文是《6. 检索与 Query Context 优化方案》的后续专项设计，核心目标不是补日志，而是优化 Agentic 检索中 `recall_pool -> judge topK` 的候选排序策略。

当前最大风险是：多通道召回拿到 30 个候选后，系统用手写规则和通道原始分数预筛 8 个送给 LLM judge。如果好候选排在第 9 到第 30，LLM 永远看不到它，后续 prompt、judge、open、expand 和 stop 再怎么优化也补不回来。

本文聚焦五个问题：

1. 缺少系统级 Retrieval Quality Evaluation，导致召回、预筛、judge、open/expand 和 stop 的质量只能靠单次日志人工判断，不能持续量化。
2. 写入期缺少面向检索的结构化增强字段，导致查询阶段再怎么优化也只能在贫弱索引上召回。
3. 现有 topK 预筛过度依赖规则排序，规则本身没有经过持续评估，容易漏掉好候选。
4. 不同召回通道的 score 含义不同，不能直接混排，需要引入行业常见的多路融合、覆盖感知和二阶段 rerank。
5. `retrieval_controller` 输出的 `search_plan` 应该实质参与召回、融合、排序和停止判断，而不是只出现在日志里。

## 2. 前置原则：写入期检索增强优先，其次建设质量评估

本文采用测试结果优先原则：实际检索质量是判断方案好坏的唯一标准。既有 Source Record、知识编译和写入设计只作为识别风险、评估迁移成本和避免事实污染的参考，不作为限制新方案的硬约束。

如果测试证明某个检索增强字段、排序策略、索引结构或写入链路调整显著提升 `recall@k`、`preselect_recall@k`、`answer_coverage` 或降低 `false_stop`，则应优先采用该方案。反之，即使方案符合旧设计，如果测试效果不好，也不应继续保留。

本文有两个前置地基，但实施优先级不同：

1. `Ingestion Search Enrichment`：先在数据录入、知识编译和索引刷新阶段生成可检索、可排序、可解释的字段。
2. `Retrieval Quality Evaluation`：再持续判断召回、预筛、judge、open/expand、stop 到底好不好。

这两个能力互相依赖：

- 没有写入期增强，后面的 Keyword/BM25、Rank Fusion、Feature Rerank 只能在贫弱索引上调参，评估也只能证明“数据本身不好搜”。
- 没有质量评估，就不知道写入期增强是否真的提升了召回，也无法持续比较不同增强版本。

因此它们都不是后置优化项，而是所有检索优化的前置条件。但第一优先级必须是写入期检索增强，因为检索质量的上限首先由入库后的可检索形态决定。排序只能优化已经进入召回池的候选，不能凭空找回写入期没有整理、索引里没有表达的语义。

如果写入期没有做好，以下问题无法靠查询阶段补救：

- 原文里有事实，但没有标准实体、别名或代码，实体召回不稳定。
- 关系已经存在于图谱里，但没有可读关系文本，Keyword/BM25 无法命中“影响”“利好”“风险”等关系表达。
- 事件有证据，但没有 event_type、impact_direction、asset_classes、source_type_tags，排序无法判断它是否适合作为 answer。
- evidence 有发布时间，但没有归一化 time_tags，近期、本周、2026 年以来等时间约束只能靠查询时猜。
- 同一事实缺少 evidence_summary，候选包和 LLM judge 只能看到冷冰冰的 id 或不完整片段。

没有 Retrieval Quality Evaluation，则无法判断下面任何改动是否真实有效：

- 写入期检索增强是否提升了召回。
- Keyword/BM25 是否补齐了精确词召回。
- Rank Fusion 是否比当前规则排序更稳。
- Feature Rerank 是否把业务相关候选提前。
- Coverage Selector 是否减少 30 选 8 的漏召。
- 二批 judge 是否补齐了 stop condition 缺口。
- Stop Verifier 是否减少误停。

因此，本文要求先把 `Retrieval Quality Evaluation` 作为系统功能建设，而不是临时 replay 脚本。它至少要持续记录：

| 对象 | 说明 |
| --- | --- |
| Query Trace | query、anchor、controller decision、search_plan。 |
| Recall Pool Snapshot | 每个候选的 id、type、title、source_channel、score、evidence_refs、matched_terms、matched_fields。 |
| Preselect Snapshot | 进入 judge 的 topK、未进入 judge 的高潜候选、选择原因。 |
| Judge Snapshot | LLM judge 的输入、输出、role、score、expand 和系统归一化结果。 |
| Context Snapshot | 打开的 evidence、最终 Query Context、stop reason。 |
| Human Labels | 人工标注的好候选、answer 候选、关键 evidence、应覆盖项、失败阶段。 |
| Metric Snapshot | recall@k、coverage@k、wasted slots、MRR、NDCG、失败归因。 |

同时，本文要求先把 `Ingestion Search Enrichment` 放入写入链路，而不是等查询时临时理解全文。这里的“写入期”不是单指 Source Record 投影层，而是覆盖投影、编译、索引刷新的完整入库链路。

最优边界是“事实层稳定、检索层可实验”：

| 层级 | 主要职责 | 测试方式 |
| --- | --- | --- |
| Projection Hint | 保留强线索和弱提示，例如代码、related_stocks、tags、source_type_reason。 | 验证输入线索是否完整保留。 |
| Compile Enrichment | 生成 Candidate Fact Package、event、relation、direction、summary，并通过写入门禁。 | 验证事实抽取准确率和证据绑定。 |
| Retrieval Document | 生成 search_text、key_phrases、readable_relations、evidence_summary、facets 等检索索引文档。 | 验证 keyword/BM25、semantic、rerank 和 coverage 指标。 |

写入期至少应生成：

| 字段 | 说明 |
| --- | --- |
| search_text | 面向全文检索和 BM25 的综合文本。 |
| key_phrases | 事件短语、行业术语、公告关键词和金融方向词。 |
| aliases | 公司简称、英文名、代码、同义词和别名。 |
| event_type | 产能扩张、资金流、监管处罚、合同订单、政策影响等。 |
| relation_intents | impact、beneficiary、risk、cause、supply_chain 等。 |
| impact_direction | 利好、利空、中性、混合或风险暴露。 |
| asset_classes | 股票、债券、商品、货币、行业、概念等。 |
| time_tags | 发布时间、事件时间、季度、近期、本周等归一化标签。 |
| source_type_tags | 新闻、公告、研报、市场信号、政策、传闻等。 |
| readable_relations | 面向检索和 LLM 的自然语言关系表达。 |
| evidence_summary | 面向召回和候选包的短证据摘要。 |
| answer_candidate_type | 写入期预估候选更适合作为 answer、support 还是 background，仅作为排序特征。 |

只有在“写入期增强 + 评估闭环”都存在后，后续排序策略替换才既有索引基础，也有判断依据。否则优化会退化成“看一条日志感觉更好”，无法证明是否提升整体检索质量，也无法弥补数据入库时没有被整理好的语义缺口。

本文的主线是：

`ingestion_search_enrichment -> retrieval_document -> keyword_retrieval -> recall_pool -> retrieval_quality_evaluation -> candidate_package -> rank_fusion -> feature_rerank -> coverage_mmr_select -> judge_preselect -> LLM judge -> evidence_open/expand -> stop_verifier -> controller_next_action`

其中排序链路部分：

- `rank_fusion` 解决多通道、多 query 召回结果如何合并。
- `feature_rerank` 解决业务相关性和 `search_plan` 如何进入排序。
- `coverage_mmr_select` 解决 30 选 8 时不能只选同质候选，要覆盖事件、证据、关系意图和 stop condition。
- `judge_preselect` 不是最终判断，只是把更可能有价值的候选送给 LLM。

## 3. 本文不解决什么问题

本文不以重写知识编译、实体标准化和主事实表为第一目标，但如果测试证明现有事实模型或索引模型限制了召回质量，可以新增独立的检索索引表、Retrieval Document、BM25 索引或派生字段。主事实层是否调整，由质量评估结果决定，而不是由历史设计决定。

本文不把神经 reranker 作为第一版必选依赖。神经 reranker 指 cross-encoder、ColBERT/late interaction、LLM batch pre-judge 或 learning-to-rank 这类对 `query + candidate` 成对打相关性分的模型化精排器。它的价值是补足规则特征对复杂语义相关性的判断能力，但它依赖稳定的候选包、标注集、评估指标和成本预算。

第一版必须先完成写入期检索增强、Keyword/BM25、Rank Fusion、Feature Rerank、Coverage Selector 和 Stop Verifier。排序层同时预留 `reranker` 接口；当固定评估集显示仍存在明显 `feature_miss`、`coverage_miss` 或语义难例时，再用同一套 trace 和人工标签比较 cross-encoder、LLM batch pre-judge 或 learning-to-rank 是否值得上线。

本文不把 LLM judge 当成万能排序器。LLM judge 只处理经过预筛的人类可读候选，不负责直接从原始 30 个混合召回结果中盲选全部相关项。

本文不把“可解释日志”作为最终目标。日志必须服务于排序质量评估，例如判断当前 preselect 是否漏召、是否被 wiki/edge 挤占、是否没有覆盖 search_plan 的子目标。

## 4. 参考文章带来的设计启发

### 4.1 A-RAG：工具分层必须和融合排序配套

参考《A-RAG 解读：能做好混合检索策略的 RAG，才是真 Agentic RAG》。

A-RAG 的关键价值不是简单多搜几次，而是给 Agent 暴露不同粒度的信息工具：关键词精确匹配、语义检索、完整 chunk 读取。映射到当前系统：

| A-RAG 工具 | 当前系统对应能力 | 设计要求 |
| --- | --- | --- |
| keyword_search | 当前仅有 entity_resolve、wiki_search，缺少真正 BM25/全文检索 | 处理股票代码、实体名、专有名词、公告关键词、事件关键词。 |
| semantic_search | semantic_hybrid_search | 处理自然语言、模糊语义和概念扩展。 |
| chunk_read | open evidence / open candidate | 对已命中证据做精读，不把片段当完整事实。 |

对当前系统最直接的启发是：不同召回通道的原始 score 不可直接比较。需要在召回后增加统一的融合排序层，优先采用 RRF 或加权 RRF，再叠加业务特征 rerank，而不是让 `entity_resolve`、`graph`、`wiki`、`semantic` 的原始分数自然混排。

同时必须明确：当前系统的 `keyword_search` 能力并不完整。`entity_resolve` 只能解决实体名、代码和别名解析；`wiki_search` 检索的是派生页，不等价于原始证据、节点、边和正文的全文关键词检索。缺少 BM25/全文检索会导致精确短语、公告关键词、事件关键词、利好利空词、时间词和专有名词无法稳定进入 `recall_pool`。排序只能优化已召回候选，召回池缺失的好候选无法通过 rerank 补救。

因此，补齐关键词检索不是排序优化的可选项，而是 `rank_fusion` 的前置能力。第一阶段必须先让 `keyword_search` 成为与 semantic、graph、entity 并列的独立召回通道。

### 4.2 LightRAG：候选必须先变成人类可读的 Key/Value 表达

参考《AI 答疑助手优化实践：从 RAG 到 LightRAG 的全链路升级》。

LightRAG 的工程启发是用轻量的实体、关系、Key/Value 表达替代重型社区摘要。这个思想不只适用于查询阶段的 `Candidate Package`，也应该前移到数据录入和知识编译阶段。

当前系统在数据录入时已经引入 AI，因此不应该等到用户查询时才临时理解全文。更合理的做法是在写入前就生成一批检索增强字段，例如关键词、别名、事件类型、关系意图、时间标签、影响方向、资产类别、证据摘要和可读关系文本。这样数据库里的事实本身就带有更适合 keyword、BM25、semantic 和 graph 检索的结构化表达。

这意味着写入期检索增强不是“附带优化”，而是 Agentic 检索排序的第一块地基。LightRAG 的 Key/Value 思路如果只在查询阶段临时生成，会带来三个问题：

- 每次查询都重复理解同一批 evidence，成本高且不稳定。
- Keyword/BM25 和向量索引无法提前利用 key phrases、aliases、readable relations。
- 30 选 topK 时，ranker 只能看到贫弱候选，无法判断 event、policy、asset、industry、evidence-parent 哪些更适合作为 answer。

因此，写入期必须先把原始 evidence 和结构化事实整理成可检索文档，再让召回和排序消费这些文档。

查询阶段仍然应把每个 node、edge、wiki、evidence、semantic hit 统一转换成 `Candidate Package`，再进入排序和 judge。

候选包必须包含：

| 字段 | 含义 |
| --- | --- |
| `candidate_key` | 给 LLM 使用的短标识，如 C1、C2，避免 LLM 直接输出数据库 id。 |
| `candidate_id` | 系统内部 id，仅用于回填和执行 open/expand。 |
| `title` | 人类可读标题。 |
| `type` | node、edge、wiki、evidence、path 等候选类型。 |
| `meaning` | 候选的业务含义，不能只打印 id。 |
| `evidence` | 支撑证据来源和摘录。 |
| `relations` | 候选相关图关系，要求可读化。 |
| `source_channel` | 候选来自哪个召回通道。 |
| `rank_features` | 排序特征和分数组成。 |
| `judge_result` | LLM judge 后的 role、decision、score、expand、code。 |

### 4.3 GraphRAG 实践：TopK 排序要引入业务权重

参考《从 RAG 到 GraphRAG：货拉拉元数据检索应用实践》。

该实践中，实体排序不仅依赖向量相似度，还引入实体权重、业务热度、人工 boost、字段使用频次等业务特征。金融知识图谱同样不能只依赖通道原始 score。第一版应至少引入这些业务排序特征：

| 特征 | 说明 |
| --- | --- |
| `exact_entity_match` | 是否命中 Query Anchor 中的强实体，如“宁德时代”“300750”。 |
| `instrument_code_match` | 是否命中股票代码、基金代码、债券代码等硬标识。 |
| `answer_type_match` | 候选类型是否符合问题需要，如“受哪些事件影响”优先 event、policy、evidence。 |
| `relation_intent_match` | 是否命中 `impact`、`beneficiary`、`cause`、`risk` 等关系意图。 |
| `evidence_supported` | 是否有原始 evidence 支撑。 |
| `source_type_match` | 是否符合预期证据类型，如新闻、公告、研报、市场信号。 |
| `time_hint_match` | 是否满足“近期”“本周”“2026 年以来”等时间约束。 |
| `negative_boundary_hit` | 是否踩中 controller 给出的负边界。 |
| `graph_path_quality` | 图路径是否能形成可解释的实体-关系-证据链。 |

### 4.4 企业级 AgenticRAG：停止权应由“验证器 + Agent”共同决定

参考《RAG 又进化了！微软整了个企业级 AgenticRAG》。

AgenticRAG 的关键不是固定流程，而是模型可以决定“继续搜索、精读、定位或停止”。但在企业级系统中，不能完全依赖模型自评是否足够。当前系统应采用两层停止机制：

1. `stop_verifier` 做硬性校验，判断数量、枚举覆盖、实体覆盖、时间覆盖、证据类型覆盖是否满足。
2. `retrieval_controller` 在 verifier 未满足时决定下一步工具调用，在 verifier 满足时可以停止。

自动停止必须记录：

- 当前 stop condition。
- 已满足的条件。
- 未满足的条件。
- 是否还有 controller 预算。
- 如果停止，为什么可以停止。
- 如果不停止，下一步应该补什么证据。

### 4.5 行业排序范式：召回和排序必须分层

综合 A-RAG、LightRAG、GraphRAG 实践和企业级 AgenticRAG，适合当前系统的排序范式不是“手写规则直接选 topK”，而是多阶段排序级联：

| 阶段 | 目标 | 适合方案 |
| --- | --- | --- |
| 大召回 | 尽量不漏候选 | 多 query、多通道、keyword/BM25、entity、graph、wiki、semantic。 |
| Rank Fusion | 融合不同通道和不同 query 的排名 | RRF、加权 RRF、按 query 子目标聚合。 |
| Candidate Package | 把候选变成可读、可打分对象 | LightRAG 式 Key/Value、证据摘录、关系文本化。 |
| Feature Rerank | 引入业务相关性 | anchor、事件类型、证据、关系意图、时间、负边界、来源可信度。 |
| Coverage/Diversity Select | 从 30 选 8/12/15 时降低漏召 | MMR、xQuAD 思路、按 answer target 和 evidence type 配额。 |
| LLM Judge | 做语义裁判 | answer/support/background/drop/expand。 |
| Stop Verifier | 判断是否够了 | 数量、枚举、时间、方向、证据覆盖。 |

因此第一版排序优化不应该只写更多规则，而应该把现有规则降级为特征之一，并增加融合排序和覆盖感知选择。

### 4.6 LLM Wiki：派生文本不能替代原始证据

参考《llm-wiki.md》。

Wiki、摘要、node description、edge meaning 都是导航和压缩层，不是事实源。Agentic 检索最终进入 answer context 的内容必须能回到原始 `kg_ev:*` 或结构化事实。

因此日志必须区分：

| 层级 | 是否事实源 | 作用 |
| --- | --- | --- |
| raw evidence | 是 | 最终回答的证据依据。 |
| graph node / edge | 是，需有 evidence 链 | 结构化事实和关系路径。 |
| wiki page | 否 | 聚合导航、语义扩展和可读摘要。 |
| candidate package | 否 | 给 judge 和日志使用的候选视图。 |
| LLM judgement | 否 | 检索决策，不新增事实。 |

## 5. 核心业务对象

### 5.1 Ingestion Search Enrichment

`Ingestion Search Enrichment` 是数据录入、知识编译和索引刷新阶段生成的检索增强层。它回答“这条事实进入检索系统前，是否已经被整理成更容易召回、排序、解释和评估的形态”。

它是本文第一优先级对象。原因是检索质量的上限首先由写入后的可检索形态决定：如果入库时没有别名、关键词、可读关系、事件类型、影响方向、时间标签和证据摘要，查询阶段只能在贫弱索引上做补救。

本文不要求所有增强字段都进入主事实表。第一版推荐将检索增强结果写入独立的 `Retrieval Document` 或等价索引文档中，使它可以被重建、A/B 测试和版本化。只有经过长期测试证明稳定、有事实语义价值的字段，才考虑提升为 node、edge 或 evidence 的主属性。

这个边界不是为了兼容旧设计，而是为了实验效率和事实治理：

- 检索增强 prompt、字段和权重可以快速迭代，不需要迁移主图事实。
- AI 生成的 key phrases、impact direction、asset classes 出错时，只影响召回排序，不污染事实库。
- 同一条 evidence 可以生成多版 retrieval document，用同一批 query trace 做离线对比。
- 最终 answer context 仍能回到原始 `kg_ev:*` 或结构化事实，避免索引文本变成事实源。

写入期增强覆盖三个阶段：

| 阶段 | 产物 | 说明 |
| --- | --- | --- |
| Projection Hint | raw_text、payload、强实体线索、弱标签、source_type_reason | 保留原始业务线索，不直接生成最终检索文档。 |
| Compile Enrichment | Candidate Fact Package、event、relation、direction、summary、evidence binding | 形成可校验的候选事实和关系，进入事实层写入门禁。 |
| Retrieval Document | search_text、key_phrases、aliases、readable_relations、evidence_summary、facets | 从已写入事实和 evidence 派生，用于 keyword/BM25、semantic、rerank、coverage。 |

当前系统已经在录入和知识编译阶段使用 AI，因此应在该阶段预生成以下字段：

| 字段 | 用途 |
| --- | --- |
| `search_text` | 面向全文检索和 BM25 的综合文本，包含标题、摘要、实体、关系、关键词。 |
| `key_phrases` | 事件短语、行业术语、金融方向词、公告关键词。 |
| `aliases` | 公司简称、英文名、股票代码、别名、同义词。 |
| `event_type` | 产能扩张、资金流、监管处罚、合同订单、业绩变化等事件类型。 |
| `relation_intents` | impact、beneficiary、risk、cause、supply_chain、sentiment 等关系意图。 |
| `impact_direction` | positive、negative、mixed、neutral 或领域内利好/利空表达。 |
| `asset_classes` | 股票、债券、商品、货币、行业、概念等资产或主题类别。 |
| `time_tags` | published_at、事件发生时间、财报期、近期/本周/本月等归一化时间标签。 |
| `source_type_tags` | 新闻、公告、研报、市场信号、政策、传闻等来源类型。 |
| `readable_relations` | 面向检索和 LLM 的自然语言关系表达，如“海外产能扩张 affects 宁德时代”。 |
| `evidence_summary` | 面向召回和候选包的短证据摘要，不替代原始 evidence。 |
| `answer_candidate_type` | 写入期预估候选更适合作为 answer、support 还是 background，仅作为排序特征。 |

这些字段必须可回溯到原始 `Evidence` 和结构化事实。它们是检索索引，不是新的事实源。

字段落点建议：

| 字段类型 | 推荐落点 | 原因 |
| --- | --- | --- |
| 强事实字段 | node / edge / evidence 主属性 | 例如股票代码、标准实体、已校验关系。 |
| 弱语义增强 | Retrieval Document metadata | 例如 key_phrases、asset_classes、source_type_tags。 |
| 可读拼接文本 | Retrieval Document text | 例如 search_text、readable_relations、evidence_summary。 |
| 实验性字段 | Retrieval Document versioned metadata | 便于 A/B 测试，不影响主图。 |
| 已长期验证稳定的字段 | 评估后再提升为主属性 | 由质量指标决定是否固化。 |

写入期增强还必须服务关系检索。Keyword/BM25 本身只能做词项匹配，不能理解结构化关系；因此 Retrieval Document 要把结构化边转成可读关系文本，并保留 graph refs：

```text
事件：宁德时代海外产能扩张带动储能供应链订单
关系：该事件 affects 宁德时代
关系：该事件 affects 新能源车产业链
证据摘要：宁德时代推进欧洲和东南亚海外产能扩张...
```

这样 Keyword/BM25 可以命中“宁德时代 影响 事件”，graph_search 可以确认 `event --affects--> stock` 的结构化关系，semantic/vector 可以补充表达不同但语义相近的候选，Feature Rerank 再把三者融合。

### 5.2 Retrieval Quality Evaluation

`Retrieval Quality Evaluation` 是系统级质量评估能力。它不应该替代写入期增强，但必须紧跟写入期增强建设，用来证明增强字段、索引和排序策略是否真的有效。

它必须支持：

- 线上和回放查询采样。
- 完整 trace 快照保存。
- 人工标注。
- 多策略回放对比。
- 指标计算。
- 失败归因。
- 质量趋势追踪。

它不直接参与单次检索排序，但决定哪些写入期增强字段有效、哪些召回通道需要补齐、哪些排序策略可以上线。

### 5.3 Recall Pool

`Recall Pool` 是所有召回通道合并去重后的候选池。它回答“系统一共找到了哪些可能相关的东西”。

要求：

- 保留召回通道。
- 保留通道原始分数。
- 保留原始命中顺序。
- 保留证据引用。
- 保留 matched_terms 和 matched_fields。
- 不直接进入 LLM judge。

### 5.4 Candidate Package

`Candidate Package` 是面向排序、judge 和日志的人类可读候选表达。它回答“这个候选到底是什么，为什么可能相关”。

设计要求：

- LLM judge 只看 `candidate_key` 和人类可读内容。
- 系统内部保留 `candidate_id` 做回填。
- edge 候选必须打印可读关系两端，不能只打印 `kg_edge:*`。
- wiki 候选必须明确“这是派生页，不是原始证据”。
- evidence 候选必须打印来源和摘录。
- 优先复用录入阶段生成的 `search_text`、`key_phrases`、`readable_relations` 和 `evidence_summary`，避免查询时重复做语义整理。

### 5.5 Keyword Retrieval

`Keyword Retrieval` 是独立于 entity、graph、wiki、semantic 的精确关键词召回通道。它回答“用户问题里的精确词、代码、短语、事件词是否能稳定命中原始事实和证据”。

Keyword Retrieval 不是完整关系理解方案。普通倒排索引或数据库全文检索只能说明“哪些文档包含这些词”，不能独立判断“哪个事件通过什么关系影响哪个对象”。关系理解必须由四层共同完成：

| 层 | 作用 |
| --- | --- |
| `Retrieval Document.readable_relations` | 把结构化关系提前文本化，让 keyword/BM25 能命中“影响、利好、风险、供应链”等关系表达。 |
| `graph_search` | 验证结构化边、路径方向和 evidence 绑定，例如 `event --affects--> 宁德时代`。 |
| `semantic/vector` | 召回表达不同但语义相近的候选，例如“订单预期改善”和“供应链需求提升”。 |
| `Feature Rerank` | 将 keyword 命中、graph path、relation intent、evidence support 综合排序。 |

因此，Keyword Retrieval 的目标不是替代图检索或向量检索，而是补齐精确词项召回缺口，并为 Rank Fusion 提供一个和 semantic/vector 性质不同的强信号。

第一版关键词检索至少覆盖：

| 索引对象 | 检索字段 |
| --- | --- |
| Node | name、aliases、type、properties 中的 code/ticker/exchange、summary、search_text、key_phrases。 |
| Edge | relation、source/target 的可读名称、edge properties、readable_relations、evidence 摘要。 |
| Evidence | source_id、title、raw_text、summary、evidence_summary、published_at、source_type、source_type_tags。 |
| Wiki | title、key phrases、summary，但 wiki 只能作为派生导航。 |
| Candidate Package 派生文本 | meaning、support_relations、evidence excerpt，可复用录入期增强字段。 |

关键词检索重点处理：

- 股票代码和证券标识：`300750`、`CATL`。
- 公司简称、别名和中英文名：`宁德时代`、`宁德时代新能源科技股份有限公司`。
- 精确事件短语：`海外产能扩张`、`资金净流入`、`监管处罚`、`重大合同`。
- 金融方向词：`利好`、`利空`、`风险`、`估值修复`、`订单改善`。
- 时间词：`2026`、`近期`、`本周`、`一季度`。
- 来源词：`公告`、`研报`、`新闻`、`市场传闻`。

第一版 Keyword Retrieval 固定采用 PostgreSQL `pg_trgm` 词项/短语匹配实现独立 lexical 通道。索引对象是 `kg_retrieval_documents`，检索字段是 `search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary` 等写入期增强字段。通道输出必须包含 `matched_terms`、`matched_fields`、`source_channel=keyword` 和通道内局部 rank。

Milvus 在第一版中只承担 semantic/vector 通道，不承载 Keyword Retrieval。这样职责边界固定：

| 通道 | 第一版实现 | 职责 |
| --- | --- | --- |
| keyword | PostgreSQL `pg_trgm` lexical index | 精确词、代码、标题、事件短语、可读关系文本。 |
| semantic/vector | Milvus dense vector | 语义相近、表达不同的候选。 |
| graph | PostgreSQL 图邻接/边表 | 结构化关系、路径方向、evidence 绑定。 |

普通 dense vector search 不能替代 Keyword Retrieval，原因是：

- 它不保证稳定命中股票代码、source_id、公告关键词和精确事件短语。
- 它通常不能解释命中了哪些 `matched_terms` 和 `matched_fields`。
- 它和 semantic_hybrid 的信号高度重叠，无法为 RRF 提供足够不同的召回视角。

### 5.6 Rank Fusion

`Rank Fusion` 是召回后、业务特征重排前的多路融合层。它回答“多个 query、多个通道召回的候选如何合并为一个稳定候选池”。

第一版建议采用 RRF 或加权 RRF：

- 不直接比较不同通道的原始 score。
- 按每个通道内的排名给候选加分。
- 同一候选被多个 query 或多个通道命中时自然加权。
- 可以给关键通道配置权重，例如强实体命中、BM25 精确匹配、semantic 语义匹配、graph 路径命中。

RRF 解决的是“跨通道分数不可比”的问题，不解决业务语义最终判断。因此它后面还需要 Feature Rerank 和 LLM Judge。

如果没有独立 Keyword Retrieval，Rank Fusion 的输入就是残缺的。此时即使 RRF 逻辑正确，也只能融合 entity、graph、wiki、semantic 四类结果，无法补上精确关键词召回缺口。

### 5.7 Feature Rerank

`Feature Rerank` 是进入 LLM judge 前的业务排序层。它回答“这个候选为什么比另一个候选更值得送给 judge”。

第一版不是纯规则硬过滤，而是可调权重的特征打分。规则只作为特征输入，不应该一票否决候选，除非是硬约束，如股票代码完全冲突、时间明确不满足、来源不可用。

Feature Rerank 的输入是 `Candidate Package`，输出是带分数组成的 `Ranked Candidate`。

建议第一版使用线性加权：

`rank_score = fusion_score + anchor_score + answer_type_score + evidence_score + relation_score + plan_score + time_score + source_score - negative_penalty - duplication_penalty`

后续可替换为：

- 学习排序模型。
- cross-encoder / reranker。
- LLM batch pre-judge。
- 领域适配器自定义排序器。

这些模型化 reranker 是可替换实现，不是第一版的先决条件。它们的接入前提是：已有稳定 `Candidate Package`、人工标签、`preselect_recall@k`、`wasted_slots@k`、`coverage@k` 和成本统计。否则无法判断模型 reranker 真正改善了排序，还是掩盖了写入期增强、keyword 召回或 candidate package 的缺陷。

### 5.8 Coverage / Diversity Selector

`Coverage / Diversity Selector` 是从 ranked candidates 中选 judge topK 的选择器。它回答“30 选 8 时如何避免全是同一类候选”。

当前纯 topK 最大的问题是：如果前 8 个被 anchor、wiki、edge 或同一个 evidence 的重复候选占满，真正有价值的事件或类别候选会被挤出。

第一版应采用覆盖感知选择：

- 至少保留核心 anchor 候选 1 个。
- 优先保留 answer-type 候选，如 event、policy、asset、industry、evidence-parent。
- 每个 `answer_target` 至少尝试保留 1 个候选。
- 每个 `expected_evidence` 类型至少尝试保留 1 个候选。
- 对同一 evidence、同一父事件、同一 wiki 派生页做去重或降权。
- edge 默认进入 support 配额，不能挤占 answer 配额。
- wiki 默认进入 background 配额，不能挤占 answer 配额。

如果候选文本相似度高或 evidence 完全相同，应采用 MMR 思路降低重复候选优先级。

### 5.9 Judge Preselect

`Judge Preselect` 是从排序后的候选池中选择进入 LLM judge 的候选集合。

设计要求：

- 简单锚点问题默认 8 个。
- 复杂枚举、广义“哪些/影响哪些/覆盖哪些”问题默认 12 个。
- stop condition 未满足且还有预算时，允许对剩余候选做第二批 judge。
- 日志必须打印未进入 judge 的候选样本，避免 topK 误杀不可见。

### 5.10 LLM Candidate Judge

`LLM Candidate Judge` 是语义裁判层，判断候选和问题的关系。

输出角色：

| role | 含义 |
| --- | --- |
| `answer` | 可以直接构成答案主体的事件、政策、资产、行业、主题、证据映射实体。 |
| `support` | 支撑答案或 anchor 的候选，可以用于扩展和证据链补强。 |
| `background` | 背景信息，可进入上下文但不扩展。 |
| `drop` | 无关、漂移、证据不足或违反边界。 |

约束：

- 大多数 `kg_edge:*` 不能作为 `answer`，默认只能是 `support`。
- `wiki` 默认不是 `answer`，除非能映射到明确原始 evidence 或实体。
- `answer` 必须能回到原始 evidence 或结构化事实。

### 5.11 Stop Verifier

`Stop Verifier` 是自动停止前的硬性校验层。

它不负责生成答案，只负责判断当前 working set 是否满足问题要求。

必须支持：

- 数量型条件：至少 N 个事件、N 条证据。
- 枚举型条件：覆盖股票、债券、商品、货币等指定类别。
- 方向型条件：利好/利空、风险/机会、上涨/下跌。
- 时间型条件：近期、本周、本月、2026 年以来。
- 证据型条件：公告、新闻、研报、市场信号。
- 实体型条件：必须覆盖 Query Anchor 中的核心实体。

### 5.12 Trace Event

`Trace Event` 是面向调试和人工审计的日志单元。

它必须同时提供：

- 机器可解析字段。
- `human_summary`。
- 分阶段计时。
- 输入输出数量。
- 关键决策原因。

日志的目标不是越多越好，而是每一条日志都能回答一个具体问题。

## 6. 输入和输出

### 6.1 输入

| 输入 | 来源 |
| --- | --- |
| 用户 query | 研究上下文请求。 |
| Query Anchor | 规则和轻量解析得到的强实体、主题、关系意图、时间提示、负边界。 |
| Retrieval Controller Decision | LLM 产出的 `query_rewrites`、`search_plan`、`expected_gain`、`stop_condition`。 |
| Ingestion Search Enrichment | 写入链路预生成的 Retrieval Document、search_text、key_phrases、aliases、event_type、relation_intents、time_tags 等检索增强字段。 |
| Recall Hits | keyword/BM25、entity、graph、wiki、semantic 等召回通道。 |
| Working Set | 已接受候选、已打开证据、历史观察、预算状态。 |

### 6.2 输出

| 输出 | 用途 |
| --- | --- |
| `recall_pool` | 记录所有召回候选和通道来源。 |
| `candidate_packages` | 统一候选表达，供排序、judge、日志使用。 |
| `ingestion_enrichment_coverage` | 记录候选是否带有 Retrieval Document 和写入期增强字段，以及缺失哪些字段。 |
| `rank_fused_candidates` | 多 query、多通道融合后的候选列表。 |
| `reranked_candidates` | 叠加业务特征和 search_plan 后的候选列表。 |
| `judge_preselect_candidates` | 经过覆盖感知选择后送入 LLM judge 的 topK。 |
| `judge_candidates` | 本轮送入 LLM judge 的 topK。 |
| `judge_results` | answer/support/background/drop/expand。 |
| `opened_evidence` | 被打开的原始证据窗口。 |
| `stop_verification` | 自动停止判断结果和未满足条件。 |
| `retrieval_quality_evaluation` | 当前检索策略的 recall@k、coverage@k、wasted slots、失败归因和策略对比结果。 |
| `next_action` | stop、search、find、open、summarize。 |

## 7. 核心设计决策

本章所有决策都以实际测试结果为优先级最高的判断依据。旧的投影、编译、写入设计可以帮助识别事实污染、迁移成本和模块边界风险，但不能阻止更优检索方案落地。只要评估结果证明新方案提升召回、预筛、覆盖或停止判断质量，就应该优先采用；如果新方案带来事实治理风险，则通过 Retrieval Document、版本化索引和可回滚实验隔离风险，而不是放弃优化。

### 7.1 30 选 8 是质量闸口，必须按排序问题治理

当前系统中，`candidate_judge` 只看 preselect 后的 8 个候选。这个位置不是普通日志展示问题，而是整个 Agentic 检索链路的质量闸口。

如果 30 个候选中有 5 个好候选，但规则只选中 2 个，后续 LLM judge 再强也只能在错误候选集合里判断。因此必须把 `judge_preselect` 当成独立排序模块评估，而不是把它隐藏在检索流程内部。

第一版目标不是追求最终回答一次 PASS，而是先保证：

- 好候选尽量进入 judge topK。
- topK 中重复候选、纯背景候选、错误 edge 候选少占坑。
- topK 覆盖 search_plan 的核心子目标。
- stop condition 需要的类别和方向不被预筛阶段漏掉。

### 7.2 检索质量评估必须成为系统功能

本节是第 2 章前置原则的落地要求。当前规则预筛漏召率评估不应是临时脚本，而应是知识图谱检索模块的一等功能。原因是检索质量不是一次性调参问题，而是会随着数据源、写入期抽取、索引策略、召回通道、排序权重、模型版本和业务问题类型持续变化。

系统必须长期记录以下对象：

| 对象 | 说明 |
| --- | --- |
| Query Trace | query、anchor、controller decision、search_plan。 |
| Recall Pool Snapshot | 每个候选的 id、type、title、source_channel、score、evidence_refs、matched_terms。 |
| Preselect Snapshot | 进入 judge 的 topK、未进入 judge 的高潜候选、选择原因。 |
| Judge Snapshot | LLM judge 的输入、输出、role、score、expand 和系统归一化结果。 |
| Context Snapshot | 打开的 evidence、最终 Query Context、stop reason。 |
| Human Labels | 人工标注的好候选、answer 候选、关键 evidence、应覆盖项、失败阶段。 |
| Metric Snapshot | recall@k、coverage@k、wasted slots、MRR、NDCG、失败归因。 |

当前启发式排序至少要作为 baseline 输出以下指标：

| 指标 | 说明 |
| --- | --- |
| `preselect_recall@8` | 人工标注的好候选有多少进入当前 top8。 |
| `answer_recall@8` | answer 级候选有多少进入当前 top8。 |
| `evidence_recall@8` | 关键 evidence 或其父事实是否进入 top8。 |
| `coverage@8` | top8 是否覆盖 search_plan 的 answer_targets 和 expected_evidence。 |
| `wasted_slots@8` | top8 中 background、drop、重复候选占比。 |
| `missed_good_candidates` | 排在 top8 外但人工认为应进入 judge 的候选列表。 |

评估对象必须是完整 `recall_pool=30`，不能只看已经送入 judge 的 8 个。否则无法判断“规则到底漏了什么”。

评估功能的输出应进入检索治理闭环：

- 新增召回通道前后，比较 `recall_pool_quality`。
- 调整排序权重前后，比较 `preselect_recall@k` 和 `wasted_slots@k`。
- 修改 judge prompt 前后，比较 judge 误判率。
- 修改 stop verifier 后，比较误停率和过度搜索率。
- 写入期增强字段变更后，比较 keyword hit rate 和 ingestion enrichment miss。

### 7.3 关键词召回是排序优化前置条件

排序优化建立在候选池足够完整的前提上。如果缺少关键词检索，以下类型的好候选很容易在召回阶段就丢失：

- 精确股票代码和证券标识。
- 公告、研报、新闻标题中的短语。
- 事件名和事件类型词。
- 金融方向词，如利好、利空、订单改善、估值修复。
- 时间表达和来源表达。

因此排序优化的第一阶段必须补齐 Keyword Retrieval，并将其纳入 recall pool 和 Rank Fusion。否则 `preselect_recall@k` 的上限会被召回缺口限制，后续 Feature Rerank、Coverage Selector 和 LLM judge 都只能在残缺候选池上工作。

验收要求：

- 对同一个 query，日志能区分 keyword、entity、graph、wiki、semantic 各自召回数量。
- keyword 命中的候选必须进入 `recall_pool`，并保留 matched_terms。
- keyword 通道结果参与 Rank Fusion，而不是在 semantic 之后做补充展示。
- 对股票代码、公司简称、事件短语、公告关键词的测试用例必须稳定命中。

### 7.4 写入期必须预生成检索增强字段

检索阶段不应该承担所有语义理解工作。当前系统在数据录入和知识编译阶段已经引入 AI，因此应把稳定、可复用、面向检索的语义处理前移到入库链路。

这里的目标不是为了维护旧的 Source Record 边界，而是为了让检索质量在真实测试中可提升、可回滚、可对比。最优方案是把事实层和检索层分离：

- 事实层保存可追溯的 Node、Edge、Evidence。
- 检索层保存可实验的 Retrieval Document 和 facets。
- Retrieval Document 可以快速重建和版本化。
- 如果测试证明某些字段长期稳定，再考虑提升为主事实属性。

写入期适合做：

| 预处理 | 说明 |
| --- | --- |
| 实体别名和代码归一 | 公司简称、英文名、股票代码、交易所、同义词。 |
| 事件类型识别 | 产能扩张、资金流、合同订单、监管处罚、政策影响等。 |
| 关系意图识别 | impact、beneficiary、risk、cause、supply_chain 等。 |
| 影响方向识别 | 利好、利空、中性、混合、风险暴露。 |
| 关键词和短语提取 | 供 keyword/BM25 精确召回使用。 |
| 时间标签归一 | published_at、事件时间、季度、近期、本周等。 |
| 资产和主题分类 | 股票、债券、商品、货币、行业、概念、区域。 |
| 可读关系生成 | 把 edge 转成自然语言关系文本。 |
| 证据摘要生成 | 生成短摘要用于召回、候选包和 judge，但不替代原文。 |
| search_text 拼接 | 把标题、实体、别名、关键词、关系、摘要合成为检索文本。 |
| answer 候选类型预估 | 预估该对象更像 answer、support 还是 background，只作为排序特征。 |

这些字段进入 Retrieval Document 或等价索引后，检索阶段可以直接按字段召回和排序，减少每次查询时重复让 LLM 理解全文的成本。

边界：

- 写入期增强字段优先是索引辅助，不是事实源。
- 所有增强字段必须能追溯到原始 evidence 或结构化事实。
- 影响方向、事件类型、关系意图这类 AI 生成字段需要保留置信度和来源。
- 不确定字段可以进入候选索引，但不能直接作为强事实输出。
- Retrieval Document 的版本、prompt、字段和权重都必须能参与离线回放评估。
- 质量指标优先于历史设计边界。如果测试证明某个增强字段应该固化为主属性，可以通过新的设计变更提升。

### 7.5 写入期增强和检索期排序的分工

写入期负责“把事实整理成更容易被找出来的形态”，检索期负责“根据当前问题选择最合适的候选”。

| 阶段 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Projection Hint | 保留 raw_text、payload、强实体线索、弱标签和来源分类原因。 | 深度语义判断和主图事实生成。 |
| Compile Enrichment | 生成 Candidate Fact Package、event、relation、direction、summary，并通过写入门禁。 | 为当前用户 query 做相关性判断。 |
| Retrieval Document | 生成 search_text、key_phrases、facets、readable_relations、evidence_summary、answer_candidate_type。 | 作为最终事实源直接回答问题。 |
| 检索期 | 多通道召回、Rank Fusion、Feature Rerank、Coverage Select、LLM Judge。 | 每次查询时重新抽取所有事实的关键词和关系。 |
| Stop Verifier | 检查当前 working set 是否满足 stop condition。 | 生成新事实。 |

这能降低查询阶段的 token 和延迟，也能让 BM25/全文检索、RRF 和业务排序有更稳定的输入。

### 7.6 通道原始 score 不能跨通道直接比较，第一层应做 Rank Fusion

不同召回通道的 score 语义不同：

| 通道 | 原始 score 含义 | 是否可跨通道直接比较 |
| --- | --- | --- |
| keyword/BM25 | 关键词、短语、代码、标题和正文匹配。 | 否 |
| entity_resolve | 实体名、代码、查询 token 命中程度。 | 否 |
| graph_search | 边置信度、路径置信度或图邻接相关度。 | 否 |
| wiki_search | wiki 文本匹配或固定召回分。 | 否 |
| semantic_hybrid | 向量或混合检索相似度。 | 否 |

因此第一层排序不应该用 `hit.score` 直接混排，而应采用 RRF 或加权 RRF：

- 每个 query rewrite 下，每个通道内部先形成局部排名。
- 候选在多个 query、多通道中重复出现时加分。
- keyword/BM25、精确实体、semantic、graph 可以有不同通道权重。
- 原始 score 只在同一通道内作为 tie-break，不直接跨通道比较。

建议公式：

`fusion_score = sum(channel_weight / (rrf_k + rank_in_channel))`

第一版 `rrf_k` 可取 60，后续根据回放集调参。

### 7.7 Feature Rerank 是业务相关性排序，不是硬规则过滤

RRF 只能说明“多个检索通道都认为它值得看”，不能说明候选是否真正回答问题。因此需要第二层 Feature Rerank。

Feature Rerank 使用 `Candidate Package` 和 `search_plan` 计算业务相关性：

| 字段 | 示例含义 |
| --- | --- |
| `fusion_score` | RRF 或加权 RRF 融合分。 |
| `anchor_score` | 是否命中 Query Anchor。 |
| `answer_type_score` | 是否是事件、政策、资产、行业、证据父事实等 answer 类型。 |
| `evidence_score` | 是否有原始证据支撑。 |
| `relation_score` | 是否匹配 impact 等关系意图。 |
| `plan_score` | 是否匹配 answer_targets、expected_evidence。 |
| `time_score` | 是否满足时间提示。 |
| `source_score` | 来源类型是否可信或符合预期。 |
| `negative_penalty` | 是否踩中负边界。 |
| `duplication_penalty` | 是否和更高排名候选共用同一父事实或 evidence。 |

关键原则：

- 规则作为特征，不作为默认硬过滤。
- 硬过滤只用于确定性错误，如股票代码冲突、时间明确不满足、来源不可用。
- edge/wiki 不能被完全丢弃，但必须进入对应配额，不能挤占 answer 配额。
- 分数权重必须可配置、可回放、可对比。

### 7.8 30 选 8 不能只按分数截断，必须覆盖感知选择

纯 topK 的问题是容易选出一组同质候选。例如同一 evidence 的 node、wiki、edge 同时出现，或者 anchor 及其背景节点占满前 8，导致真正的 answer 候选被挤出。

第一版 `coverage_mmr_select` 应采用“分数 + 覆盖 + 去重”的选择策略：

1. 先按 `rerank_score` 排序。
2. 维护已覆盖的 answer target、evidence type、relation intent、父 evidence、父事件。
3. 每次选择候选时，计算 `select_score = rerank_score + coverage_bonus - redundancy_penalty`。
4. 优先补齐未覆盖的 search_plan 子目标。
5. 对重复 evidence、重复父事件、同类 wiki 背景进行降权。

建议配额：

| 配额 | 说明 |
| --- | --- |
| answer quota | 至少 50% topK 给 event、policy、asset、industry、evidence-parent。 |
| support quota | 保留 anchor、关键 edge、关键 relation path。 |
| evidence quota | 至少保留直接 evidence 或能映射 evidence 的父候选。 |
| background quota | wiki/background 数量受限，默认不超过 20%。 |
| diversity quota | 多个 answer_targets 或 expected_evidence 不能只覆盖一个。 |

这个选择器比“规则打分后取前 8”更适合广义“哪些/影响哪些/覆盖哪些”问题。

### 7.9 Search Plan 必须变成排序目标，而不是日志文本

`retrieval_controller` 输出的 `search_plan` 必须被结构化消费：

| search_plan 字段 | 排序使用方式 |
| --- | --- |
| `answer_targets` | 作为覆盖目标，影响 coverage bonus。 |
| `expected_evidence` | 作为证据类型目标，影响 evidence/source score。 |
| `relation_intents` | 影响 relation score 和 graph path quality。 |
| `negative_boundaries` | 作为 penalty 或硬过滤条件。 |
| `stop_condition` | 转换为 Stop Verifier 的 coverage requirement。 |
| `query_rewrites` | 每条 query 都进入 keyword/entity/graph/wiki/semantic 多通道召回。 |

如果 search_plan 写得好但没有影响 topK，等于 controller 没有真正参与检索。验收时必须能看到每个 topK 候选命中了哪些 plan 目标，哪些 plan 目标还没有候选覆盖。

### 7.10 对广义枚举问题启用二批 judge

固定 top8 对单实体问题可以接受，但对“哪些事件”“影响哪些资产和行业”“利好利空方向”这类枚举问题风险很高。

建议策略：

1. 第一批 judge 看覆盖选择后的 topK。
2. Stop Verifier 检查是否满足数量、枚举、方向、时间和证据类型。
3. 如果未满足且剩余候选中仍有潜在覆盖项，启动第二批 judge。
4. 第二批候选从 `remaining_ranked_candidates` 中按缺口选择，而不是简单取 9 到 16。

第二批 judge 的触发条件：

- `missing_coverage_terms` 非空。
- `answer_count` 小于 stop_condition 要求。
- `expected_evidence` 尚未覆盖。
- topK 中 `wasted_slots` 过高。
- controller 预算仍允许。

### 7.11 神经 reranker 是后续增强，不是第一版前置依赖

行业最佳实践中，cross-encoder、ColBERT 类 late interaction、专用 reranker 都可以提升 query-candidate 相关性判断。但当前系统的第一问题是写入期检索增强、候选结构和评估闭环还没建立。直接引入模型 rerank 会让问题更难定位：如果好候选没被写入期字段表达、没被 keyword/BM25 或 graph 召回，模型 reranker 没有候选可排；如果没有固定评估集，也无法证明模型带来的净收益。

排序接口应预留：

| reranker | 适用时机 |
| --- | --- |
| rule_feature_reranker | 第一版默认，实现快、可控、便于调试。 |
| llm_batch_prejudge | 对 30 个 candidate package 做轻量 yes/no/score，成本较高但语义强。 |
| cross_encoder_reranker | 有训练数据或可用中文金融 reranker 时引入。 |
| learning_to_rank | 有足够人工标注 bad case 后引入。 |

短期不应把排序质量寄托在更强模型上，而应先把 Retrieval Document、Keyword/BM25、`preselect_recall@k` 评估和可替换排序架构做出来。模型化 reranker 只能作为后续可插拔增强，不能替代写入期增强、图关系验证和 Stop Verifier。

### 7.12 Edge 默认是 support，不是 answer

`kg_edge:*` 表示关系，不是答案实体。它可以解释为什么某个事件影响某个股票，也可以支撑路径扩展，但不应轻易作为答案主体。

默认规则：

- `edge` 可以是 `support`。
- `edge` 可以触发 open evidence。
- `edge` 不参与 distinct answer 计数。
- 如果 LLM judge 把 edge 判成 `answer`，系统应降级为 `support`，并记录 `role_normalized=edge_answer_to_support`。

例外情况必须由领域适配器显式声明，例如某些关系本身就是用户要查询的对象。

### 7.13 Evidence 作为 answer 时应映射回父事件或事实

如果 LLM judge 把 `kg_ev:*` 判成 `answer`，Stop Verifier 不能简单把 evidence id 当成一个答案计数。更合理的逻辑是：

1. 优先映射到承载该证据的事件、政策、行业、资产或主题节点。
2. 找不到父候选时，才把 evidence 作为独立答案。
3. 日志必须打印 `answer_normalization`，说明 evidence 映射到了哪个父候选。

这样可以避免同一事件的多个 evidence 被重复计数，也可以避免有效 answer 被低估。

### 7.14 自动停止必须先过 Stop Verifier

自动停止不能只看“已有 answer 数量”和“anchor coverage”。必须按 query 类型校验。

示例：

| query 类型 | 必须验证 |
| --- | --- |
| “宁德时代最近受哪些事件影响” | 至少 N 个事件或明确说明当前知识库只覆盖 N 个；每个事件有 evidence；事件和宁德时代有 impact 或 support 关系。 |
| “中东冲突影响哪些资产和行业” | 资产类别和行业类别都要覆盖；如 stop_condition 指定股票、债券、商品、货币，则四类都要有候选或明确缺口。 |
| “利率下降利好利空哪些方向” | 利好和利空方向不能只覆盖一边。 |
| “2026 年以来...” | evidence 或事件时间必须满足 2026 年以来。 |

Verifier 未满足时，不允许 `auto_stop_context_sufficient`。应记录 `auto_stop_skipped`，并把缺口交给 controller 决定下一步。

### 7.15 LLM judge 的输入数量应按问题复杂度动态调整

简单锚点问题可以送 8 个候选给 judge，但广义枚举问题不应该固定 8 个。

建议第一版：

| 问题类型 | judge topK |
| --- | --- |
| 单实体、单关系、明确目标 | 8 |
| “哪些/影响哪些/覆盖哪些” | 12 |
| 枚举覆盖、多资产、多行业、多方向 | 15 |
| 第一批 judge 后 stop condition 未满足 | 允许第二批 judge，优先看剩余 ranked candidates。 |

日志必须打印：

- `judge_top_k_requested`
- `judge_top_k_reason`
- `remaining_candidates_count`
- `second_batch_judge_needed`

### 7.16 LLM 不应输出数据库 id，系统负责 key-id 映射

给 LLM 的候选标识应是 `C1/C2/C3`，不是 `kg:*`。原因是：

- LLM 更擅长语言理解，不擅长记忆和生成长 id。
- 长 id 增加 token 成本，也降低输出稳定性。
- 系统可以通过 `candidate_key -> candidate_id` 映射完成执行。

日志可以打印数据库 id，但人类可读日志必须优先展示标题、类型、含义、证据和关系。

### 7.17 日志只作为排序评估和调试手段

日志不能成为本方案的主目标，但必须服务排序评估。当前 `agentic_tool event`、`agentic_auto_open event`、`agentic_auto_stop event` 容易让人误以为都在请求模型，排序日志也无法判断候选为什么进入或没进入 judge。

日志事件必须明确分类：

| event_type | 含义 |
| --- | --- |
| `llm_request` | 即将请求模型。 |
| `llm_response` | 模型返回结果。 |
| `tool_execution` | search/find/open/summarize 工具执行。 |
| `program_decision` | 程序根据规则自动 open、expand、stop、skip。 |
| `ranker_event` | 特征排序和 topK 预筛。 |
| `verifier_event` | stop condition 校验。 |

每个事件都必须带 `human_summary`，避免只打印 JSON。

排序相关日志必须额外打印：

- 当前排序策略名称。
- fusion score、rerank score、coverage bonus、redundancy penalty。
- topK 外的高潜候选。
- missed coverage target。
- second batch judge 是否触发。

### 7.18 性能日志和业务日志分层

性能排查日志要保留，但默认不要污染业务判断。

建议分层：

| 日志级别 | 内容 |
| --- | --- |
| INFO | 业务关键事件：controller 决策、召回概要、rank topK、judge 结果、open/expand、stop verifier、最终 context。 |
| DEBUG | 数据库耗时、Milvus client、embedding batch、repository upsert/list 细节。 |
| WARNING | 网络异常、Milvus reconnect、LLM 超时、stop condition 未满足但预算耗尽。 |

INFO 日志要能让人读懂检索过程，DEBUG 日志用于性能诊断。

## 8. 推荐排序流程

### 8.1 首轮搜索和融合

0. 写入期已经为 node、edge、evidence 生成 search_text、key_phrases、aliases、event_type、relation_intents、time_tags 等增强字段。
1. 解析 Query Anchor。
2. 请求 retrieval_controller。
3. 执行 controller 输出的所有 `query_rewrites`。
4. 每条 query 走多通道召回，其中 keyword/BM25 是必选通道，不是 future enhancement。
5. keyword/BM25 直接检索写入期生成的 search_text、key_phrases、aliases、readable_relations 和 evidence_summary。
6. 合并去重形成 `recall_pool`。
7. 包装成 `candidate_packages`，优先复用写入期增强字段。
8. 对每个 query/channel 内部排名。
9. 使用 RRF 或加权 RRF 做 `rank_fusion`。

### 8.2 业务重排和覆盖选择

1. 使用 Feature Rerank 计算业务相关性。
2. 使用 search_plan 生成 coverage targets。
3. 使用 Coverage / Diversity Selector 选择 judge topK。
4. 记录 topK 和未进入 topK 的高潜候选。
5. 进入 LLM judge。

### 8.3 Judge 后处理

1. LLM 返回 answer/support/background/drop。
2. 系统归一化异常角色，如 edge answer 降级为 support。
3. answer/support 且 `expand=True` 的候选进入 auto expand。
4. 有 evidence 的 keep 候选进入 auto open。
5. 更新 working set。
6. 执行 Stop Verifier。

### 8.4 是否继续和是否第二批 judge

Stop Verifier 满足时：

- 允许自动 stop。
- 记录满足哪些条件。
- 输出最终 Query Context。

Stop Verifier 不满足时：

- 如果剩余候选中存在能补缺口的高潜候选，优先第二批 judge。
- 如果候选池缺口明显，把缺口写入 observations。
- controller 决定继续 search、find、open 或 summarize。
- 如果预算耗尽，记录 `budget_stop_condition_unmet`，最终结果带 warning。

## 9. 检索质量评估功能设计

### 9.1 标注对象

检索质量评估必须支持可回放的评估集和线上抽样标注。每个 bad case 或抽样 case 至少标注：

- query。
- search_plan。
- recall_pool 全部候选。
- 人工认为应进入 judge 的候选。
- 人工认为可作为 answer 的候选。
- 关键 evidence。
- 应覆盖的枚举项、方向、时间和证据类型。
- 关键词召回应命中的术语、代码、事件短语和来源词。
- 写入期增强字段是否覆盖了这些术语、代码、事件短语和关系意图。

标注不只服务排序，也服务召回、写入期增强、judge 和 stop verifier 的治理。

### 9.2 系统记录对象

每次被采样的检索请求应保存以下快照：

| 快照 | 内容 |
| --- | --- |
| `query_snapshot` | query、anchor、search_plan、constraints、controller 输出。 |
| `recall_snapshot` | 每个通道召回候选、matched_terms、原始 score、rank、耗时。 |
| `package_snapshot` | 候选包文本、meaning、evidence、relations、写入期增强字段覆盖情况。 |
| `ranking_snapshot` | fusion score、feature score、coverage bonus、topK 选择过程。 |
| `judge_snapshot` | judge 输入、输出、role、decision、score、expand、归一化结果。 |
| `context_snapshot` | open/expand 后的 evidence、最终 context、stop verifier 结果。 |
| `label_snapshot` | 人工标签、失败阶段、备注。 |

这些记录必须落库保存，作为系统级评估功能的一部分，不能绑定某个临时 replay 脚本。

### 9.3 策略对比实验

每次改排序策略，至少对比：

| 策略 | 说明 |
| --- | --- |
| `baseline_rule_priority` | 当前规则排序。 |
| `keyword_added_baseline` | 补齐 keyword/BM25 召回后，仍使用当前规则排序。 |
| `rrf_only` | 只做多通道 rank fusion。 |
| `rrf_feature_rerank` | RRF 后叠加业务特征。 |
| `rrf_feature_coverage` | RRF + 业务特征 + 覆盖感知选择。 |
| `oracle_topk` | 人工理想 topK，用作上限参考。 |

同一批 trace 必须可以回放不同策略，否则无法判断排序优化是否真实有效。

### 9.4 评估指标

必须输出：

- `preselect_recall@8/12/15`
- `answer_recall@8/12/15`
- `evidence_recall@8/12/15`
- `coverage@8/12/15`
- `wasted_slots@8/12/15`
- `ndcg@8/12/15`
- `mrr`
- 平均 judge token 成本。
- 平均 LLM 调用次数。

### 9.5 失败归因

如果新策略仍然漏候选，必须归因到具体阶段：

| 失败阶段 | 说明 |
| --- | --- |
| ingestion enrichment miss | 写入期没有生成必要的 key_phrases、aliases、event_type、relation_intents、time_tags 等增强字段。 |
| recall miss | 30 个召回池里本来就没有好候选。 |
| keyword miss | 精确代码、术语、事件短语或正文关键词没有被 keyword/BM25 通道命中。 |
| package miss | 候选包装丢失语义或证据，导致排序/LLM 看不懂。 |
| fusion miss | 多通道融合没有把好候选提上来。 |
| feature miss | 业务特征权重不合理。 |
| coverage miss | topK 选择没有覆盖子目标或证据类型。 |
| judge miss | LLM judge 误判。 |
| stop miss | stop verifier 误停或误判缺口。 |

### 9.6 趋势和回归

评估功能必须能按以下维度看趋势：

- 检索策略版本。
- LLM prompt/model 版本。
- 数据源类型。
- 问题类型，如单实体、枚举、多资产、多行业、时间约束。
- 召回通道组合。
- 写入期增强字段版本。

每次改动召回、排序、judge 或 stop verifier，都应跑同一批评估集，防止局部优化导致其他问题类型回退。

### 9.7 日志要求

日志要求服务评估，不是替代评估。必须能从日志重建：

- recall_pool。
- rank_fusion 排序。
- feature_rerank 排序。
- coverage 选择过程。
- judge topK。
- topK 外高潜候选。
- stop verifier 缺口。

## 10. 模块边界

### 10.1 与 Retrieval Controller 的关系

Retrieval Controller 负责提出检索计划和下一步工具意图，但不负责最终排序，也不直接决定业务事实真伪。

Rank Fusion、Feature Rerank、Coverage Selector 和 Stop Verifier 必须消费 controller 输出的 `search_plan`，否则 controller 只是“写了计划但没有执行”。

### 10.2 与 Candidate Judge 的关系

排序级联是 judge 前的预筛，Candidate Judge 是 judge 后的语义裁判。

两者不能混淆：

- 排序级联优化“应该给 LLM 看哪些候选”。
- Candidate Judge 解释“这个候选和问题是什么关系”。

### 10.3 与 Query Context 的关系

Query Context 只能消费已经通过 judge、open、stop verifier 校验的内容。

`wiki`、`edge`、`background` 可以进入辅助上下文，但不能无约束地污染 answer context。

### 10.4 与知识编译的关系

本文会反向要求编译和索引产物更适合检索。知识编译不能只生成主图事实，还应为检索增强提供结构化输入；索引刷新阶段应生成独立的 Retrieval Document。

- node/edge/evidence 必须有可读字段。
- edge 必须能解释 source、target、relation 和 evidence。
- evidence 必须能映射回 source record 和父事实。
- 写入链路应生成 Retrieval Document，包括 search_text、key_phrases、aliases、event_type、relation_intents、impact_direction、asset_classes、time_tags、source_type_tags、readable_relations、evidence_summary 和 answer_candidate_type。
- AI 生成的增强字段必须保留来源和置信度，不能静默变成事实。
- Retrieval Document 必须可重建、可版本化、可回放对比，不能和主事实表强耦合。
- 如果评估证明某些增强字段长期稳定且具备事实语义，可以再通过设计变更提升为主图属性。

### 10.5 与性能治理的关系

性能问题通过 DEBUG 级 profile 日志排查，不应压缩业务 INFO 日志的表达。

如果 Milvus、数据库、embedding 服务出现网络慢或重连，应在性能日志中明确记录，但业务日志仍要保持“检索链路可读”。

### 10.6 与质量治理的关系

Retrieval Quality Evaluation 是质量治理模块的一部分。它不是某个测试脚本，也不是只给开发调试用的临时输出。

它应提供：

- 质量指标口径。
- bad case 标注入口。
- 策略对比入口。
- 失败归因数据。
- 版本趋势数据。

后续如果建设质量看板，检索质量评估应成为核心数据来源。

## 11. 验收口径

### 11.1 排序质量验收

第一版排序优化必须证明新策略优于当前规则 baseline。验收方式不是只看日志，而是跑固定 bad case 评估集。

最低要求：

- 写入期增强字段对事件短语、实体别名、关系意图、时间和来源类型的覆盖率可统计。
- keyword/BM25 召回补齐后，`recall_pool` 对精确代码、实体短语、事件关键词的命中率高于当前 baseline。
- `preselect_recall@8` 不低于 baseline。
- `answer_recall@8` 高于 baseline。
- `wasted_slots@8` 低于 baseline。
- 枚举型问题的 `coverage@12/15` 高于 baseline。
- 不能通过简单扩大 topK 掩盖排序质量问题。

### 11.2 典型问题验收

以“宁德时代 300750 最近受哪些事件影响”为例：

- event/evidence 候选应优先于纯 wiki 背景候选。
- `宁德时代资金净流入改善` 和 `宁德时代海外产能扩张带动储能供应链订单` 应进入 judge。
- `belongs_to`、`mentions` 等 edge 不应作为 answer。
- 与中东冲突、俄罗斯警告等主题漂移候选应被 drop 或强惩罚。
- 如果这两个好候选在 recall_pool 中但没有进入 judge topK，必须归因为 fusion、feature 或 coverage selector 问题。

### 11.3 Stop Verifier 验收

以“中东冲突影响哪些资产和行业”为例：

- 如果 stop condition 要求覆盖股票、债券、商品、货币，则缺任何一类都不能自动停止。
- 如果只找到商品和能源，日志必须打印 missing coverage。
- 如果预算耗尽但条件未满足，最终结果必须带 warning，而不是伪装成 context sufficient。

### 11.4 Search Plan 使用验收

- `query_rewrites` 必须执行，不能只取第一条。
- 每条 `query_rewrite` 必须进入 keyword/BM25、entity、graph、wiki、semantic 的多通道召回策略，除非配置明确关闭某通道。
- keyword/BM25 必须使用写入期增强字段，不应只搜原始 raw_text。
- `answer_targets` 必须影响 coverage selector。
- `expected_evidence` 必须影响 evidence/source score。
- `relation_intents` 必须影响 relation score。
- `negative_boundaries` 必须作为 penalty 或硬过滤。
- `stop_condition` 必须进入 Stop Verifier。

### 11.5 日志层级验收

- INFO 日志只保留业务关键链路和人工可读摘要。
- DEBUG 日志保留 repository、Milvus、embedding、batch、upsert/list 等性能细节。
- WARNING 日志记录网络异常、连接恢复失败、预算耗尽和 stop condition 未满足。

### 11.6 LLM 输入验收

候选 judge 请求中：

- 不应要求 LLM 输出数据库 id。
- 候选必须有 title、type、meaning、evidence、relations。
- edge 候选必须展示可读关系两端。
- evidence 候选必须展示来源和摘录。

## 12. 分阶段落地建议

### 12.1 第一阶段：写入期检索增强和 Retrieval Document

优先实现：

- 在知识编译/索引刷新阶段生成独立的 Retrieval Document。
- Retrieval Document 第一版包含 search_text、key_phrases、aliases、event_type、relation_intents、impact_direction、asset_classes、time_tags、source_type_tags、readable_relations、evidence_summary 和 answer_candidate_type。
- 为 AI 生成增强字段记录来源、置信度和可追溯 evidence。
- 将这些字段写入可被 keyword/BM25、semantic 和 graph 检索消费的位置。
- 保存 Retrieval Document 版本、生成 prompt、字段覆盖率和回放指标，便于后续删除、替换或提升为主事实属性。
- 将结构化 edge 生成 readable_relations，既服务 keyword/BM25 命中，也保留 graph refs 供图检索验证。

没有这一阶段，后续 Keyword Retrieval、Rank Fusion、Feature Rerank 都缺少足够好的索引基础。

### 12.2 第二阶段：建设 Retrieval Quality Evaluation

实现：

- 采样保存 query、recall_pool、preselect、judge、context、stop verifier 快照。
- 支持人工标注好候选、answer 候选、关键 evidence、覆盖项和失败阶段。
- 对当前规则 preselect 输出 `preselect_recall@k`、`answer_recall@k`、`wasted_slots@k`。
- 固定一批 bad case 作为排序评估集。
- 支持同一批 trace 回放不同排序策略。
- 记录 ingestion enrichment miss、keyword miss、recall miss、fusion miss、feature miss、coverage miss、judge miss、stop miss。

这一阶段用于证明第一阶段的写入期增强是否有效，并为后续排序替换提供判断依据。

### 12.3 第三阶段：补齐 Keyword Retrieval

实现：

- 独立 keyword 召回通道，第一版固定基于 PostgreSQL `pg_trgm` 词项/短语匹配实现。
- 覆盖 Node、Edge、Evidence、Wiki、Candidate Package 派生文本和写入期增强字段。
- 保存 matched_terms、matched_fields、source_channel。
- 针对股票代码、实体名、公告关键词、事件短语、利好利空词建立测试用例。
- 将 keyword/BM25 结果纳入 recall_pool，而不是仅作为补充展示。
- Milvus 只承担 semantic/vector 通道；普通 dense vector search 不能替代 keyword 通道。

### 12.4 第四阶段：候选包标准化

实现：

- 完整保存 recall_pool 30 个候选。
- 构建 Candidate Package，让每个候选可读、可标注、可排序。

### 12.5 第五阶段：Rank Fusion

实现：

- 按 query/channel 记录局部排名。
- RRF 或加权 RRF 融合。
- 多 query 命中加权。
- 通道权重可配置。
- 与 baseline 对比 `preselect_recall@k`。

### 12.6 第六阶段：Feature Rerank

实现：

- anchor match。
- answer type。
- evidence support。
- relation intent。
- search_plan match。
- source/time match。
- negative boundary penalty。
- duplication penalty。
- 权重可配置和回放。

### 12.7 第七阶段：Coverage Selector 和二批 judge

实现：

- MMR 或覆盖感知 topK 选择。
- answer/support/background 配额。
- answer_targets 和 expected_evidence 覆盖。
- 同 evidence、同父事实去重降权。
- stop condition 未满足时第二批 judge。

### 12.8 第八阶段：更强 reranker

在写入期增强、质量评估、Keyword/BM25、RRF、Feature Rerank 和 Coverage Selector 稳定后再考虑：

- LLM batch pre-judge。
- 引入轻量神经 reranker、cross-encoder 或 ColBERT/late interaction。
- 基于人工标注 bad case 的 learning-to-rank。
- 将 query rewrite 分解为更结构化的子目标检索。

更强 reranker 必须用同一批评估集证明它相对 `rrf_feature_coverage` 有净收益，并评估延迟、token 或推理成本。不能用它替代写入期增强、Keyword/BM25 或 Stop Verifier。
