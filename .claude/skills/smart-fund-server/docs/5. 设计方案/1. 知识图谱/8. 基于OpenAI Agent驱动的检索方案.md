# 基于 OpenAI Agent 驱动的检索方案

## 1. 本文解决什么问题

本文设计一条新的 `OpenAI Agent A-RAG` 检索路径。它不替换现有投影、编译、标准化、写入、检索文档和索引刷新链路，而是在现有知识库检索能力之上新增一个真正由 OpenAI Agent 调度工具的检索运行时。

当前 `agentic_arag` 已经积累了大量有效能力：query anchor、keyword retrieval、semantic hybrid、graph search、wiki search、open evidence、候选包、RRF/feature/coverage 排序、LLM judge、auto expand、stop verifier、trace replay 和质量基线。但当前运行方式仍然偏固定工作流：

`controller -> search -> ranker preselect -> judge -> open -> expand -> stop`

这条链路中，LLM 主要在固定节点做判断，整体流程、工具顺序、停止条件和扩展策略仍由代码写死。它能稳定复现，但不像一个真正的 agent：agent 应该能根据问题、已有证据、失败原因和预算，自主决定调用哪些工具、何时扩大召回、何时精读证据、何时验证覆盖、何时停止。

本文目标是把现有检索系统沉淀成 `Tool Kernel`，再新增 `OpenAI Agent Retrieval Runtime`：

- 现有能力继续保留，作为可调用工具和可对比基线。
- 新路径只负责 agent 编排，不改写主事实、不重建写入模型。
- 新旧两条路径用同一批 replay case、trace 和质量指标做 A/B 对比。
- 如果 agent 方案效果不好，可以关闭新路由，不影响现有稳定链路。

## 2. 本文不解决什么问题

本文不重写知识图谱事实模型，不改变 Node、Edge、Evidence、Source Record、Domain Adapter 的含义。

本文不改变写入期检索增强的优先级。`kg_retrieval_documents.search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary`、embedding、wiki 和 graph adjacency 仍然是 OpenAI Agent 检索能力的基础。写入数据质量不够时，OpenAI Agent 只能更聪明地调用工具，不能凭空找回没有入库、没有索引、没有证据绑定的事实。

本文不删除当前 `agentic_arag` 固定工作流。现有链路作为 `v1` 基线继续存在，新链路作为 `v2` 纯新增能力灰度。

本文不允许 agent 直接写数据库、直接修改主图事实或绕过证据生成结论。agent 只能通过白名单工具读取、检索、评分、验证和返回结果。

本文不把所有确定性约束一次性移除。现有 query anchor、候选去重、family 合并、证据约束和 stop verifier 需要保留；其中候选级硬限制统一放在 rerank 前的 hygiene 阶段处理，不能等 rerank 后再过滤。candidate judge 只保留给 v1 基线和离线诊断，不能在 `openai_agents_arag` 的 Agent 最终输出之后再做二次语义过滤。

本文新增 reranker 只负责检索候选重排和候选池诊断，不负责事实生成，也不替代 evidence-bound 校验。Reranker 的分数是同一 query 内的相对相关性信号，不能跨 query 比较，也不能单独作为丢弃证据的绝对阈值。

## 3. OpenAI Agent 能力依据

第一版明确使用 `openai-agents-python` 作为 OpenAI Agent 运行时。

原因是本文要解决的不是“发起一次结构化 LLM 请求”，而是“让模型在一套工具、上下文、权限和停止条件中持续工作”。`openai-agents-python` 的定位是轻量但完整的多 agent workflow 框架，核心概念包含 agents、tools、handoffs、guardrails、sessions 和 tracing。这些能力正好对应我们要新增的 OpenAI Agent 检索运行时。

OpenAI 工具文档说明，模型可以通过工具访问额外数据和能力；在 Agents SDK 中，工具语义不变，但 wiring 移到 agent definition 和 workflow design。文档也明确支持把本地逻辑包装成 function tool，以及把 specialist agent 暴露成工具。这和我们的 Tool Kernel 边界一致：检索、排序、open、graph expand、stop verify 都在我们自己的服务里执行，agent 只决定何时调用和如何利用结果。

Responses API 文档说明，新项目推荐使用 Responses；它是面向 agent-like 应用的统一接口，支持工具调用、多轮状态、`previous_response_id` 链接上下文，以及结构化输出。`openai-agents-python` 可以作为更高层的编排框架承载这些能力。

因此，本方案的技术判断是：

| 组件 | 角色 |
| --- | --- |
| 知识图谱事实库 | 唯一事实源。 |
| Retrieval Document / Wiki / Vector / Graph Index | 可重建检索索引。 |
| Tool Kernel | 把现有检索、排序、打开、验证能力封装为白名单工具。 |
| `openai-agents-python` | v2 的 OpenAI Agent 运行时，负责工具选择、多轮状态、guardrail、session、trace 和 agent loop。 |
| DeepSeek | 可作为 OpenAI 兼容 Chat Completions provider 接入 agent 模型层；如果某些 Agents SDK 能力不兼容，则通过本地 adapter 降级为同一套 Tool Kernel 调度。 |
| Replay Evaluation | 判断新旧方案谁更好。 |

- OpenAI Agents SDK: `https://developers.openai.com/api/docs/libraries#use-the-agents-sdk`

### 3.1 参考文章带来的修正结论

参考文章对本文有三个直接约束。

第一，A-RAG 的价值不是“暴露越多工具越 agent”，而是给模型提供层级化检索接口：精确检索、语义检索、完整证据读取。映射到当前系统后，不应该把 entity、keyword、semantic、graph、wiki 全部原样暴露给 OpenAI Agent，而应该封装为 `kg_search`、`kg_search_more`、`kg_open` 这类高层工具。OpenAI Agent 决定“补哪类信息”，Tool Kernel 决定底层怎么融合、去重、排序和返回。

第二，Anthropic Contextual Retrieval 说明写入期上下文增强是检索质量地基。我们已经建设的 `kg_retrieval_documents.search_text`、`key_phrases`、`aliases`、`readable_relations`、`evidence_summary` 不只是普通索引字段，而是金融领域的 contextual chunk 表达。OpenAI Agent 版本不能绕过这层，反而要更依赖这层，否则 agent 会把成本浪费在弥补入库时缺失的上下文。

第三，TrustGraph 的 Context Core 思路说明，检索输出不能只是一组临时命中的 chunks，而应该是可版本化、可追踪、可回放的上下文包。本文中的 `AnswerContext` / `RetrievalTrace` 需要继续保留 retrieval document version、tool contract version、index version、source evidence lineage、stop check 和成本画像。这样 v1/v2 才能可靠 A/B 对比，也能在后续回放中解释为什么当时 agent 会停。

因此本文不采用“把所有工具直接交给 agent”的方案，而采用：

`OpenAI Agent 决策 -> 高层工具 -> Tool Kernel -> 多通道检索/排序/校验 -> 可追踪上下文包`

### 3.2 首轮召回策略修正

OpenAI Agent 版本不再把“LLM query rewrite / search plan”放在检索第一步。首轮必须先由系统执行一次不依赖 LLM 的 bootstrap recall，再把召回观察交给 OpenAI Agent。

原因是当前真实 replay 已经暴露出一个稳定问题：对“新闻标题 + 涉及哪些主体、行业或资产影响”这类查询，原始标题本身就是最强 anchor。LLM 在没有任何证据上下文时生成的 rewrite 往往会加入“主体、行业、资产影响、分析文章”等泛词，扩大候选池，但不一定提高有效召回。日志中多次出现 exact evidence 已经能被原始标题命中，而 rewrite 后的候选仍由 keyword 主导，`semantic_only_added` 没有明显独立增益，反而引入其他新闻的噪声。

因此第一版 v2 的设计决策是：

- 首轮使用原始 query 和规则化 anchor 做 `bootstrap` 召回，不先调用 LLM。
- bootstrap 结果必须返回 exact title/source 命中、strong/weak anchor、通道贡献、候选 family、覆盖缺口和高噪声提示。
- OpenAI Agent 接收 `query + bootstrap_observation` 后再决定下一步。
- LLM query rewrite 只能作为“基于已观察召回缺口的补救动作”，不能作为默认第一步。
- 如果 bootstrap 已经找到 strong anchor evidence，Agent 应优先 `kg_open` 精读证据，而不是继续泛化 query。

### 3.3 模型 Provider 与 Chat 缓存策略

`openai-agents-python` 是 agent 编排框架，不等于模型只能使用 OpenAI 官方模型。第一版模型层采用 provider 抽象：

- 默认 provider 可以是 OpenAI。
- DeepSeek 通过 OpenAI 兼容 Chat Completions API 接入，用于低成本调度、候选判断和 JSON 结构化输出。
- Tool Kernel、bootstrap recall、stop verifier、trace 和 replay 不依赖具体 provider。
- 如果 provider 不支持某个 OpenAI Agents SDK 特性，运行时只在模型调用层降级，不改变业务工具协议。

Agent 多轮检索必须使用 chat/messages 形态构造请求，而不是每轮重新拼一个完整大 prompt。构造原则是：

- system instructions、工具说明、输出协议、guardrail 和固定策略保持稳定，作为最长公共前缀。
- 第一条 user message 只放稳定任务上下文：原始 query、运行时日期、预算、工具契约版本、bootstrap 策略说明。
- 每次工具调用结果作为后续 message 追加，不修改历史 message。
- 不重复发送已经在前文稳定说明过的规则，只追加新增 observation、缺口和下一步问题。
- 本地 LLM cache 的 key 必须包含完整 messages、provider、model、tools、schema 和 prompt 版本；DeepSeek 服务端前缀缓存则依赖 messages 前缀完全一致。

这条策略的目标是让 agent 在多次工具调用中同时吃到两类缓存：

- 本地文件缓存：相同 messages 的完整请求直接命中，不再请求远端。
- provider 前缀缓存：历史消息前缀不变时，远端只需要处理新增 observation，降低输入成本和延迟。

因此，任何 agent runtime 实现都禁止在第二轮、第三轮重写历史 system/user 内容。只能追加新 message；如果需要修正规则，必须提升 prompt version，让 replay 能解释缓存失效原因。

## 4. 现有系统已经具备的能力

### 4.1 写入和索引基础

| 能力 | 当前价值 | Agent 化后的定位 |
| --- | --- | --- |
| Source Record 投影 | 把业务表转换为知识编译统一输入。 | 保持不变，agent 不参与。 |
| 知识编译与标准化 | 生成 node、edge、evidence，并做证据绑定和质量门禁。 | 保持不变，agent 不绕过。 |
| 写入期检索增强 | 生成 search_text、key_phrases、aliases、readable_relations、evidence_summary。 | OpenAI Agent 检索的 contextual retrieval 基础，不允许查询时临时替代。 |
| `kg_retrieval_documents` | 面向 keyword、semantic、reranker 的检索文档。 | 金融领域的 contextual chunk / retrieval document，是 `kg_search` 的主要候选来源。 |
| semantic hybrid index | 提供语义召回。 | agent 可按需调用，不再只作为固定分支。 |
| Reranker 排序服务 | 对召回候选做 listwise 语义重排。 | 作为独立接入能力，见“Reranker 如何接入当前系统”。 |
| graph adjacency | 提供从 node/evidence 反查关系和邻居。 | agent 可按需展开局部图。 |
| wiki page | 提供背景解释和派生知识页。 | agent 只能作为 background/support 使用，不能替代 evidence。 |
| embedding file cache | 降低索引和 query embedding 成本。 | agent 工具内部继续复用。 |

### 4.2 检索能力适配评估

现有能力不能原样全部暴露给 OpenAI Agent。A-RAG 参考文章强调层级检索接口，而不是底层工具数量。Agent 工具的设计原则是：工具数量少、动作语义清晰、输入输出稳定、每次调用能产生可判断的增益。entity、keyword、semantic、graph、wiki 这些更适合作为 Tool Kernel 内部能力，由少量高层工具统一调度。

| 现有能力 | 是否直接暴露给 OpenAI Agent | 处理方式 | 需要保留的信息 |
| --- | --- | --- | --- |
| entity resolve | 否 | 作为 `kg_search` 和 `kg_search_more` 的内部 anchor 解析步骤。 | matched entity、source fields、anchor strength、weak_anchor_only。 |
| keyword search | 否 | 作为 `kg_search` 默认通道；需要补精确词时通过 `kg_search_more(channel=keyword)` 调用。 | matched_terms、matched_fields、local_rank、source_channel。 |
| semantic hybrid search | 否 | 作为 `kg_search` 默认通道；keyword 不足或需要语义扩展时通过 `kg_search_more(channel=semantic_hybrid)` 调用。 | semantic_score、source document、semantic_only_added。 |
| graph search | 否 | 不暴露裸 graph search，只暴露目标明确的 `kg_expand_graph(seed, goal)`。 | seed、path、relation、direction、evidence_refs、expand_goal。 |
| wiki search | 限制暴露 | 只通过 `kg_search_more(channel=wiki, role=background)` 使用，并限制不能触发 graph expand。 | wiki title、source evidence、background 限制。 |
| open evidence | 是 | 暴露为 `kg_open`，只允许打开 evidence key 或 candidate key。 | evidence excerpt、source_id、source_type、时间、opened_reason。 |
| find in evidence | 暂不独立暴露 | 第一版合并进 `kg_open` 的可选参数；后续发现长 evidence 定位成本高时再拆。 | matched terms 和片段。 |
| candidate package | 否 | 不是工具，是 Tool Kernel 输出规范和候选池数据结构。 | candidate_key、title、meaning、evidence_keys、relations、channel_summary。 |

需要新增或改造的能力：

| 能力 | 定位 | 原因 |
| --- | --- | --- |
| `kg_search` | 第一轮综合召回工具。 | 让 OpenAI Agent 不需要知道所有底层通道细节，先拿到可判断的候选池。 |
| `kg_search_more` | 定向补召回工具。 | 当 agent 发现 keyword、semantic、graph、wiki 某类信息不足时，能扩大特定通道，而不是重复全量搜索。 |
| `kg_rerank_candidates` | 语义重排工具。 | 对当前候选池或指定候选子集调用 Reranker 排序服务；详细接入见“Reranker 如何接入当前系统”。 |
| pre-rerank candidate hygiene | 候选池清洗能力。 | 不是 Agent 工具；在 rerank 前做过滤、去重、family 合并、多样性检查和无效候选降级。 |
| `kg_open` | 精读证据工具。 | agent 必须基于 evidence 判断，不能只看候选摘要。 |
| `kg_expand_graph` | 目标化图扩展工具。 | graph 扩展必须有 seed 和 goal，避免无边界扩散。 |
| `kg_verify_stop` | 停止校验工具。 | agent 准备结束前必须验证覆盖和证据充分性。 |
| `kg_finish` | 最终输出工具。 | 统一输出 Query Context，并由运行时做 evidence-bound 校验。 |

因此，4.2 的结论是：现有能力基本适合作为 OpenAI Agent 的底层 Tool Kernel，但不适合全部直接成为 agent tool。第一版应该删减直接工具面，把底层能力合并成 7 到 8 个高层工具。

这也是 A-RAG 与工程实现之间的折中：A-RAG 证明 keyword、semantic、chunk_read 都有必要；但在我们的系统里，keyword、semantic、graph、wiki 的底层选择和融合应尽量由 Tool Kernel 完成。OpenAI Agent 只在“需要补哪类信息”这个层面做决策，减少无效工具选择成本。

Reranker 是这里的新增中间层。它不替代 keyword、semantic、graph、wiki 召回，也不替代 Agent 的语义判断；它负责在“广撒网拿到候选”之后做 listwise 语义排序。完整接入方式单独放在“Reranker 如何接入当前系统”章节。

### 4.3 清洗、判断和停止基础

这些能力仍然需要保留，但不再以 v1 的固定排序流程形态强制执行。OpenAI Agent 负责决定“是否需要继续打开证据、是否补召回、是否准备停止”；系统只保留候选清洗、证据约束和停止校验，帮助 agent 快速做正确决策，但不在 Agent 结束后再替它重判最终候选。

| 能力 | 当前价值 | Agent 化后的定位 |
| --- | --- | --- |
| pre-rerank candidate hygiene | 解决候选去重、family 合并、多样性检查和无效候选降级。 | 作为 Tool Kernel 内部步骤，不暴露为排序工具，也不输出语义排序。 |
| Reranker 排序服务 | 解决固定规则难以理解语义相近候选差异的问题。 | v2 的排序入口；bootstrap 默认重排，后续通过 `kg_rerank_candidates` 由 agent 主动重排。 |
| candidate judge | 判断候选 answer/support/background/drop。 | v2 不把它作为 Agent 后处理器。候选角色由 OpenAI Agent 在 `kg_finish` 中直接给出；系统只做 JSON schema、ID 存在性、evidence-bound 结构校验。candidate judge 可作为 v1 A/B 对照，但不能覆盖 Agent 的最终选择。 |
| stop verifier | 判断证据覆盖是否满足问题。 | 封装为 `kg_verify_stop`。OpenAI Agent 可以决定“准备停止”，但停止前必须调用该工具；工具返回 satisfied、missing_items、weak_items 和 recommended_next_tools。 |
| trace log | 记录请求、响应、工具调用、case summary。 | 继续作为 replay 和调试依据。 |
| replay quality baseline | 固定问题集评估检索效果。 | v1/v2 对比的验收入口。 |
| profile log | 定位慢点，如 anchor_filter、load_edges、load_nodes。 | agent 工具性能治理依据。 |

因此，停止逻辑的最终边界是：

- OpenAI Agent 决定何时尝试停止。
- `kg_verify_stop` 快速判断是否满足证据和覆盖条件。
- `kg_verify_stop.satisfied=false` 时，OpenAI Agent 必须继续检索、打开证据、扩图，或明确返回 `insufficient_context`。
- `kg_finish` 只接受已经通过 `kg_verify_stop` 的上下文。

## 5. 新增架构

新增架构分三层：

```text
User Query
  -> Retrieval Route
    -> v1 agentic_arag fixed workflow
    -> v2 openai_agents_arag
        -> Bootstrap Recall + Rerank
        -> OpenAI Agent Runtime
            -> Tool Kernel
                -> HybridRetrievalRuntime
                -> RerankerClient
                -> RetrievalToolRegistry
                -> Candidate Hygiene / Reranker / Judge / Stop Verifier
                -> Repository / Index / Vector Store
```

### 5.1 Tool Kernel

Tool Kernel 是对现有能力的稳定封装，不包含 agent 策略。它的职责是：

- 暴露白名单工具。
- 返回结构化、小体积、可追踪的工具结果。
- 保留 evidence id、candidate id、source_channel、matched_terms、matched_fields、score breakdown。
- 避免把大段重复 excerpt 直接塞给 agent。
- 提供 profile 和 trace 事件。

第一版 Tool Kernel 不直接暴露几十个底层工具，而是采用“粗粒度工具 + 定向补召回 + 诊断信息”的方式：

| 工具 | 职责 | 说明 |
| --- | --- | --- |
| `kg_search` | 多通道召回。 | 支持 `mode=bootstrap` 和普通搜索。bootstrap 模式由运行时在进入 agent 前自动执行，使用原始 query 和规则化 anchor，不调用 LLM rewrite；bootstrap 结果默认进入一次 rerank。 |
| `kg_search_more` | 指定通道补召回。 | 仅当 agent 判断某通道缺失时调用，例如补 keyword、semantic_hybrid、graph 或 wiki。 |
| `kg_rerank_candidates` | 候选语义重排。 | 调用 Reranker 排序服务，对清洗后的候选池或指定 candidate keys 进行 listwise 重排，返回 rerank_score、rank_delta、top_n 和 usage。 |
| `kg_open` | 精读 evidence 或 candidate。 | 返回去重后的 evidence excerpt 和 evidence key。 |
| `kg_expand_graph` | 对指定 candidate/evidence 做局部图扩展。 | 必须传 seed 和目标，不允许无边界扩展。 |
| `kg_verify_stop` | 快速校验证据覆盖和停止条件。 | OpenAI Agent 准备停止时必须调用；返回是否满足、缺什么、下一步建议。 |
| `kg_finish` | 返回最终检索上下文。 | 由运行时校验 evidence-bound。 |

不再规划把 `keyword_search`、`semantic_hybrid_search`、`graph_search`、`wiki_search` 原样暴露给 OpenAI Agent。原因是工具面过宽会增加错误调度概率，也会让 prompt 变长。OpenAI Agent 需要的是“补哪类信息”的决策权，不是直接操作所有底层索引的自由度。

Reranker 工具不暴露底层 HTTP 细节。候选文本构造、分数解释、缓存和失败处理统一放在“Reranker 如何接入当前系统”章节。

### 5.2 OpenAI Agent Runtime

OpenAI Agent Runtime 是纯新增模块，命名为 `OpenAIAgentsRetrievalRuntime`。它负责：

- 构造 agent instructions。
- 注册 Tool Kernel function tools。
- 让 `openai-agents-python` 负责单次 query 的 agent loop、session 和工具上下文。
- 在 stop 前强制运行 `kg_verify_stop`。
- 把 OpenAI Agent trace 映射回现有 retrieval trace。
- 输出与 v1 兼容的 `AnswerContext` / `RetrievalTrace`。

OpenAI Agent Runtime 不直接访问 repository，也不直接操作数据库。所有读操作通过工具完成。

系统只保留两个检索运行时：现有手写 `agentic_arag` 和新增 `openai_agents_arag`。

### 5.3 系统侧观测状态

本文不再设计一套手写 `Agent State`。OpenAI Agent 的会话、上下文和工具调用过程由 `openai-agents-python` 管理。系统侧只保留可观测、可回放、可评估的运行记录，用于调试和 A/B 对比，而不是驱动 agent 决策。

系统侧至少记录：

| 记录对象 | 用途 |
| --- | --- |
| `query` | 用户原始问题。 |
| `tool_calls` | OpenAI Agent 实际调用了哪些工具、参数是什么、耗时多少。 |
| `tool_results` | 每个工具返回的候选摘要、证据 key、通道贡献、缺口提示。 |
| `opened_evidence` | 已精读证据及其 source_id、source_type、excerpt。 |
| `candidate_roles` | OpenAI Agent 最终接受的 answer/support/background/drop 判断。 |
| `stop_check` | `kg_verify_stop` 的 satisfied、missing_items、weak_items、recommended_next_tools。 |
| `final_context` | 输出给下游的 Query Context。 |
| `context_versions` | retrieval document version、index version、tool contract version、agent prompt version。 |
| `source_lineage` | 最终上下文对应的 node、edge、evidence、source record 溯源。 |
| `cost_profile` | LLM 调用、工具调用、embedding、数据库读取的耗时和成本。 |
| `message_cache_profile` | provider prompt cache 命中、miss token、本地 cache hit、prompt version。 |

这些记录不作为手写状态机使用，只作为 trace、replay、质量评估和问题排查的事实依据。

## 6. Agent 应如何调度工具

### 6.1 标准检索策略

OpenAI Agent 不再从空上下文开始规划。运行时先执行一次系统级 bootstrap recall：

```text
raw query
  -> kg_search(mode=bootstrap, query=raw query, rewrite=false)
  -> pre-rerank hygiene
  -> kg_rerank_candidates(trigger=system_bootstrap, candidates=clean_bootstrap_pool)
  -> bootstrap_observation
  -> OpenAI Agent loop
```

这里的 `kg_rerank_candidates(trigger=system_bootstrap)` 不是由 LLM 决定，而是运行时默认执行。rerank 前必须先做去重、family 合并、多样性检查和无效候选处理；模型 rerank 只接收清洗后的候选池。这样可以在 Agent 介入前减少纯规则权重和脏候选的影响，让后续上下文更接近 query 的真实意图。

`bootstrap_observation` 至少包含：

- exact title、source_id、stock code、company name、policy name 等 strong anchor 命中情况。
- `entity_resolve`、`keyword`、`semantic_hybrid`、`graph`、`wiki` 的候选数量和有效样例。
- 候选 family 去重结果，避免同一 evidence 的 node/edge/evidence 重复占满上下文。
- 当前覆盖缺口，例如主体、行业、资产影响、时间、关系链。
- 噪声提示，例如 only weak anchor、topic drift、keyword 过度主导、semantic 无独立增益。
- reranker 排序结果，例如 `rerank_score`、`rank_delta`、`top_reranked_candidates`、`low_confidence` 和 `usage.latency_ms`。

Agent 看到 bootstrap 结果后，默认遵循以下目标，但具体调用顺序由 agent 自己决定：

1. 如果 bootstrap 已有 strong anchor evidence，优先调用 `kg_open` 精读证据。
2. 如果 strong anchor 候选不足，调用 `kg_search_more(channel=keyword)` 补精确词或别名。
3. 如果 exact evidence 不足，调用 `kg_search_more(channel=semantic_hybrid)` 做语义补召回。
4. 如果已找到核心 node/evidence，但关系、主体或影响链不完整，调用 `kg_expand_graph`。
5. 如果补召回后候选池变化较大，先由 Tool Kernel 做候选清洗，再调用 `kg_rerank_candidates` 对当前池/子集做语义重排。
6. 只有当 bootstrap 或后续工具结果显示召回缺口明确时，才生成新的 query rewrite 并调用 `kg_search_more`。
7. 打开最关键的 evidence，而不是打开所有高分候选。
8. 当 coverage ledger 看起来满足时，调用 `kg_verify_stop`。
9. `kg_verify_stop` 通过后才允许 `kg_finish`。

这不是固定代码流程，而是 agent instructions。运行时只约束预算、工具白名单和 stop guardrail。

关键约束是：query rewrite 不是入口能力，而是基于召回观察的后续动作。Agent 必须能解释为什么需要改写，例如“原始 query 只命中 weak anchor”“exact title 未命中”“语义通道无结果”“主体覆盖缺失”。如果不能说明缺口，就不应为了形式上 agentic 而改写 query。

### 6.2 停止条件

agent 不能只凭“看起来够了”停止。停止必须满足：

- 已打开至少一个直接回答问题的 evidence，除非 query 本身只要求背景解释。
- strong anchor 问题必须有 anchor 命中的 evidence 或 node。
- 多项枚举问题必须覆盖 bootstrap 观察和 agent 后续确认的 coverage targets，例如主体、行业、资产、关系或时间维度。
- `kg_verify_stop` 返回 `satisfied=true`。
- 如果 `kg_verify_stop` 返回 missing items，agent 必须继续检索、打开证据，或明确返回“不足以回答”的 trace。

### 6.3 候选进入上下文的规则

agent 可以决定候选角色，但最终上下文仍必须证据约束：

| role | 可进入上下文 | 可触发 graph expand | 说明 |
| --- | --- | --- | --- |
| answer | 是 | 是 | 直接回答问题。 |
| support | 是 | 是 | 支撑 answer 或补关系链。 |
| background | 是 | 否 | 只解释背景，不能扩展。 |
| drop | 否 | 否 | 明确偏题或无证据。 |

这条规则应作为 guardrail，而不是交给 agent 自由发挥。

## 7. Reranker 如何接入当前系统

Reranker 是检索链路中的语义重排层，不是新的召回通道，也不是新的事实判断器。它接收已经由 `kg_search`、`kg_search_more` 或 graph expand 得到且完成 hygiene 的候选池，用模型语义理解能力对候选做 listwise 排序，解决固定规则难以稳定判断“哪个候选更贴近当前 query”的问题。

当前服务接口见 `docs/7. 接口文档/Reranker排序服务.md`。服务能力边界是：

- `/v1/rerank`：输入 query 和最多 100 条 document，返回按相关性排序的结果。
- `/v1/score`：输入 query 和单条 document，返回单候选相关性分数。
- 分数只在同一 query、同一候选池内做相对比较，不能跨 query 比较，也不能作为固定绝对阈值。
- 60 条候选 rerank 约 1 秒，适合放在 bootstrap 后作为默认排序增强。

### 7.1 接入目标

接入 reranker 要解决三个问题：

1. 首轮广撒网后，候选池里会同时出现 node、edge、evidence、wiki、keyword 命中和 semantic 命中，规则分数容易把同源候选、泛概念和具体证据混在一起。
2. 现有 RRF、feature、coverage、anchor strength 可解释，但语义泛化能力弱；人工权重调得过强时，keyword 容易长期压制 semantic/graph 候选。因此 v2 暂不延续这类规则排序。
3. Agent 不应该在完全未排序的候选池上消耗工具预算；它需要一个“语义上更可能相关”的候选顺序，用来决定先 open 哪些 evidence、是否需要补召回、是否需要扩图。

因此 reranker 的定位是：在召回和 Agent 决策之间增加一层语义排序信号。它只改变候选的优先级，不删除候选，不生成事实，不替代证据打开和停止校验。

### 7.2 接入位置

Reranker 接入两个位置。

第一个位置是 bootstrap 默认重排：

```text
raw query
  -> kg_search(mode=bootstrap, query=raw query, rewrite=false)
  -> pre-rerank hygiene: dedupe, family merge, diversity check, invalid candidate filtering
  -> kg_rerank_candidates(trigger=system_bootstrap, candidates=clean_bootstrap_pool)
  -> bootstrap_observation
  -> OpenAI Agent loop
```

这里的 rerank 不是由 LLM 决定，而是运行时默认执行。但 rerank 之前必须先做候选清洗。原因是模型 rerank 只负责语义排序，不负责替系统修复脏候选池；如果把重复候选、同源候选、无证据候选、background wiki、明显无效候选直接交给模型，reranker 只能在噪声中排序，既浪费请求成本，也会降低排序质量。

bootstrap 的正确顺序是：

1. `kg_search(mode=bootstrap)` 广撒网召回。
2. Tool Kernel 做 pre-rerank hygiene。
3. 对清洗后的候选池构造 query-aware document。
4. 调用 `kg_rerank_candidates(trigger=system_bootstrap)` 做模型语义主排序。
5. rerank 后只做结果结构校验和 trace 记录，不再过滤候选。
6. 把 hygiene 结果、rerank 排序、覆盖缺口和候选 family 摘要写入 `bootstrap_observation`。

先 rerank 一次，可以让 Agent 初始观察看到模型语义排序和候选清洗结果。

第二个位置是 Agent 主动工具调用：

```text
OpenAI Agent
  -> kg_rerank_candidates(trigger=agent_requested, candidate_keys=[...], reason=...)
```

Agent 可以在以下场景主动调用：

- 候选过多，且当前 topK 被同一 source family 或 keyword 命中占满。
- semantic/graph 候选被 keyword 候选挤出，但 query 明显需要语义或关系理解。
- 同一证据下有多个 node/edge/evidence，需要决定优先打开哪一个。
- 补召回后需要把新增候选和旧候选重新混排。

### 7.3 候选文本构造

候选文本构造发生在 pre-rerank hygiene 之后。也就是说，先清洗和压缩候选池，再把保留下来的候选转换成 reranker documents。

pre-rerank hygiene 至少包含：

| 步骤 | 作用 |
| --- | --- |
| ID 去重 | 同一个 node、edge、evidence、wiki 只保留一个候选对象，合并多通道来源。 |
| source/evidence family 合并 | 同一 source/evidence 下的 node、edge、evidence 聚成 family，避免同一新闻占满 rerank 输入。 |
| 证据有效性检查 | 无 `evidence_key/source_id` 的候选标记为弱候选；除非 query 是背景类问题，否则不能进入强证据排序池。 |
| role 预标记 | wiki/background 预标记为 background，不和 evidence-backed answer 候选直接竞争。 |
| 多样性检查 | 保证候选池里至少包含 evidence、核心 node、关键 edge、semantic-only/graph-confirmed 等不同类型候选。 |
| 明显噪声过滤 | 去掉 only weak anchor、跨主题、空 title、空 snippet、无 source lineage 的候选；不能确定的候选只降级，不直接删除。 |
| family 配额 | 对同一 source/evidence family 设置软上限，保留最高质量代表和少量关键关系候选。 |

这一步的目标不是做语义排序，而是保证交给 reranker 的候选池干净、可比较、有多样性。模型 reranker 应该处理“这批有效候选谁更相关”，不应该处理“哪些候选是重复垃圾数据”。

Reranker 不直接接收完整原文，也不接收数据库对象。Tool Kernel 负责把候选转换成短 document，并维护 `candidate_key -> 原始候选` 的映射。

这里不能只拼 `title + meaning`。如果候选文本只包含人工摘要字段，reranker 会丢掉原始证据里的关键限定条件，例如时间、主体、行业、资产影响、涨跌方向、政策动作、source_id 和命中词上下文。候选文本必须是 query-aware 的证据压缩包，而不是纯展示摘要。

候选 document 分三层构造。

第一层是必带核心字段：

| 字段 | 作用 |
| --- | --- |
| `candidate_key` | 保持 reranker 结果可回填，不让模型输出数据库 ID。 |
| `type` | 区分 node、edge、evidence、wiki，避免把背景页排成 answer。 |
| `title` | 候选标题或关系可读标题。 |
| `meaning` | 候选和 query 的关系说明，不能只是重复 title。 |
| `source_id/evidence_key` | 保留证据来源和可追溯性。 |
| `anchor_match` | 说明是否命中新闻标题、股票代码、机构名、政策名等 strong anchor。 |

第二层是证据相关字段，默认也必须带：

| 字段 | 作用 |
| --- | --- |
| `matched_snippets` | 从原始证据或 retrieval document 中截取的 query 命中上下文，优先包含 matched_terms 周围文本。 |
| `evidence_summary` | 候选绑定证据的短摘要，用于补充 matched snippet 不完整的问题。 |
| `support_relations` | 候选相关的关键关系，限制条数，优先保留和 query 意图相关的关系。 |
| `matched_fields` | 标记命中来自 title、search_text、key_phrases、readable_relations、evidence_summary 还是 source text。 |

第三层是诊断字段，按预算补充：

| 字段 | 作用 |
| --- | --- |
| `channel_summary` | 命中通道、source_channel、semantic/keyword/graph/wiki 信息。 |
| `hygiene_flags` | 清洗和硬约束信号，例如 exact anchor、coverage、anchor strength、是否 weak_anchor_only、是否 no_evidence_key。 |
| `family_summary` | 同一 source/evidence family 的聚合信息，避免同一新闻多个候选互相挤占。 |
| `time/entity hints` | 时间、主体、资产、行业、方向性词等 query 相关结构化提示。 |

因此，给 reranker 的单条 document 应接近下面这种信息密度：

```text
C5 | type=edge | title=A股并购重组市场呈现三方面新变化 mentions 半导体
meaning=该候选说明这条并购重组新闻提到半导体行业，可能回答“涉及哪些行业”
source=ft_news:83904 evidence=E1 anchor=strong_title
matched_snippets=“资源要素加速向新质生产力领域集聚...半导体、高端装备制造、生物医药...”
support_relations=A股并购重组市场呈现三方面新变化 --mentions--> 半导体
matched_fields=title, readable_relations, evidence_summary
channels=keyword, graph, semantic_hybrid
```

不应把完整原文塞给 reranker，但也不能只塞标题。正确做法是：每个候选最多带 1 到 3 个 query-aware snippets，每个 snippet 控制长度；优先保留包含 query anchor、候选实体、关系词和影响方向的句子。如果没有 matched snippet，才退回 `evidence_summary + support_relations`。

候选文本构造必须有质量检查：

- 如果候选没有 `source_id/evidence_key`，需要标记为 `no_evidence_key`，排序时不能被当成强证据候选。
- 如果 `meaning` 与 `title` 几乎相同，必须用 support relation 或 evidence snippet 重写 meaning。
- 如果多个候选使用完全相同的 snippets，需要记录 family 重复，避免 reranker 只是在相同文本上排序。
- 如果 query 要求“主体、行业、资产影响”，snippet 必须优先覆盖这些字段；缺哪个字段就在 document 中显式标记 `missing=industry/assets/...`，让 reranker 和 Agent 都能看到缺口。
- 如果候选来自 wiki/background，document 必须标记 `role_hint=background`，不能让背景页和证据候选混淆。

默认输入规模：

- bootstrap rerank：使用 bootstrap 候选池，通常 60 条，最多 100 条。
- Agent 主动 rerank：使用指定 `candidate_keys` 或当前候选池子集。
- `top_n` 默认不小于 Agent 初始观察需要的候选数量；不能只返回极小 topK 导致候选视野被过早截断。

### 7.4 工具契约

`kg_rerank_candidates` 是 Agent 可见工具，但它不暴露 HTTP 地址、模型名称和底层批处理细节。

输入字段：

| 字段 | 说明 |
| --- | --- |
| `query` | 当前 query，默认使用原始用户 query。 |
| `trigger` | `system_bootstrap` 或 `agent_requested`，表示本次 rerank 是系统默认触发还是 Agent 主动触发。 |
| `candidate_keys` | 可选。为空时使用当前候选池。 |
| `top_n` | 可选。控制返回多少条重排结果。 |
| `reason` | Agent 主动调用时必须填写，用于 trace 解释为什么需要重排。 |

输出字段：

| 字段 | 说明 |
| --- | --- |
| `reranked_candidates` | 按 reranker 排序后的候选摘要。 |
| `rerank_score` | 同一 query 内的相对相关性分数。 |
| `rank_delta` | rerank 排名相对清洗后候选初始顺序的变化，仅用于观察 reranker 对召回顺序的调整幅度。 |
| `top_n` | 本次返回数量。 |
| `usage.latency_ms` | reranker 调用耗时。 |
| `rerank_unavailable` | 仅用于错误报告。第一版默认 fail-fast，不把失败伪装成正常排序结果。 |

trace 必须记录 rerank 前后的候选顺序、分数、`rank_delta`、输入候选数量、输出数量、耗时和调用原因。这样后续才能判断 reranker 是否真的提升了有效候选排序。

### 7.5 和候选清洗的关系

v2 暂时不保留规则排序工具。默认关系是：

```text
候选池
  -> pre-rerank hygiene 负责过滤、去重、合并、多样性检查和硬限制处理
  -> 模型 rerank 负责语义排序
  -> result validation 只做结构校验和 trace 记录，不过滤候选
  -> Agent 基于排序、证据和 stop verifier 决策
```

原因是规则排序中很多语义权重本质上是猜测，例如某个 relation type 是否更重要、某个 coverage bonus 是否该压过 semantic、keyword 命中是否应该比 graph 命中更高。这类规则泛化性差，后续也很难维护。当前阶段不继续做规则排序。所有确定性候选约束都必须前置到 pre-rerank hygiene，避免模型在无效候选上浪费排序能力。

系统侧只在自己能确定的地方生效：

| 能力 | 主要职责 |
| --- | --- |
| pre-rerank hygiene | 过滤无效候选、合并重复候选、控制同源 family、多样性检查、background 预标记、无证据候选处理、ID/source lineage 检查。 |
| 模型 Reranker | 对清洗后的候选池做语义排序。 |
| result validation | 校验 reranker 返回的 index、candidate_key、score、数量和 trace 字段是否完整；不改变候选集合和顺序。 |
| Agent | 综合模型排序、opened evidence 和 stop verifier，决定继续检索、打开证据、扩图或停止。 |

这意味着下面这些规则排序逻辑暂不进入 v2：

- 给 relation type 固定加权。
- 用 keyword 命中数量压制 semantic/graph 候选。
- 用 coverage bonus 改变候选排序。
- 用不可解释的 feature score 作为最终排序依据。

如果后续 replay 证明某类确定性规则确实稳定有效，也应该先作为 pre-rerank hygiene 加入，而不是恢复一套和模型 rerank 并列竞争的规则排序器。

### 7.6 缓存、失败和性能

Reranker 应做短期本地缓存，缓存 key 至少包含：

- query。
- reranker model version。
- `top_n`。
- 候选 document 文本摘要及其顺序无关 hash。

缓存命中时不请求 reranker 服务。缓存未命中时，trace 记录真实调用耗时。

失败处理原则：

- bootstrap rerank 失败时，第一版默认让当前 query 失败，并把 `rerank_unavailable`、请求规模、候选 keys 和错误原因写入 trace。
- Agent 主动 rerank 失败时，工具调用失败应向 Agent Runtime 抛出结构化错误，并进入当前 query 的失败记录；不允许静默改用规则排序。
- 如果后续需要“诊断模式继续跑”，必须通过显式配置开启，并在 trace 中标记 `rerank_skipped=true`；不能作为默认行为。
- reranker 分数不能做固定绝对阈值；候选过滤发生在 pre-rerank hygiene，最终输出合法性由 evidence-bound、stop verifier 和 Agent 最终选择共同约束。

### 7.7 评估口径

接入 reranker 后，Replay A/B 至少需要新增以下指标：

| 指标 | 说明 |
| --- | --- |
| `rerank_gain` | reranker 是否把最终有效候选提前到更高位置。 |
| `hygiene_block_count` | pre-rerank hygiene 过滤、降级、标记的候选数量。 |
| `rerank_open_gain` | 因 reranker 提前打开的 evidence 是否更快满足 coverage。 |
| `rerank_latency_ms` | bootstrap rerank 和 Agent 主动 rerank 的耗时。 |
| `rerank_unavailable_count` | 服务失败或跳过次数。 |

验收标准不是“reranker 分数看起来更高”，而是 replay 中能看到有效候选排名提前、wasted slots 降低或 Agent 打开证据次数减少。如果没有这些收益，reranker 不能作为默认排序入口。

## 8. 现有设计中不适合 Agent 模式的地方

### 8.1 `search` 工具过于黑盒

当前 `RetrievalToolRegistry.search` 内部固定执行 entity、keyword、graph、wiki、semantic，再 dedupe。对固定工作流是好事，但对 agent 来说，它无法明确表达“这次只想补 semantic”或“这次只想从某个 evidence 反向扩 graph”。

整改方向：

- 保留 `kg_search` 作为默认粗粒度工具。
- 新增 `kg_search_more` 允许指定 `keyword`、`semantic_hybrid`、`graph`、`wiki`。
- 每次工具结果必须返回 `pre_dedupe_counts`、`merged_channel_counts`、`selected_primary_source_counts`、`source_samples`。

### 8.2 ranker 当前承担了过多不确定语义排序

当前 v1 中，ranker 决定哪些候选进入 judge，其中包含不少人工猜测的语义权重。v2 当前阶段不保留规则排序工具，语义排序交给模型 reranker，确定性候选逻辑只放在 rerank 前的 hygiene 中：

- rerank 前：过滤无效候选、合并重复候选、控制同源 family、多样性检查。
- evidence-bound、wiki/background 限制、ID 存在性、source lineage、role 预标记都必须在 rerank 前完成。
- 不再给 relation type、keyword 命中数、coverage bonus、feature score 做语义排序权重。

默认排序由 `kg_rerank_candidates` 给出；hygiene 只负责清洗，不负责生成另一个 topK。

### 8.3 候选包对 agent 不够友好

当前候选包曾出现 excerpt 重复、candidate 与 meaning 重复、support_relations 为 None、evidence_refs 为空、同一文章不同 node 占满 topK 等问题。Agent 模式下这些问题会放大 token 浪费。

整改方向：

- candidate 只传 `candidate_key`、`type`、`title`、`meaning`、`evidence_keys`、`support_relations`、`channel_summary`。
- excerpt 放到独立 `evidence_map`，候选只引用 `E1/E2`。
- 相同 source/evidence 的 node、edge、evidence 必须聚合为一个 candidate family。
- `meaning` 必须解释候选和 query 的关系，不能只是重复 title。

### 8.4 stop verifier 需要更像工具

当前 stop verifier 能识别 coverage，但日志显示过“preselect missed coverage 很多，最终 stop 却 satisfied”的风险。Agent 模式下，stop verifier 必须变成可调用、可解释、可追问的工具：

- 输入：query、bootstrap_observation、agent coverage targets、accepted candidates、opened evidence、coverage ledger。
- 输出：satisfied、missing_items、weak_items、recommended_next_tools、reason。
- 如果不满足，必须给出下一步建议，例如“补 graph expansion around C3”或“open E2/E5”。

### 8.5 broad anchor 需要工具级约束

像“中国”“影响”“行业”这类泛词容易把无关新闻拉进来。Agent 模式下不能只依赖 prompt 约束，工具层也要返回 anchor strength：

- `strong_anchor`: 股票代码、公司名、新闻标题、source_id。
- `medium_anchor`: 政策名、机构名、行业名。
- `weak_anchor`: 中国、影响、涉及、市场、资产等泛词。

当 query 有 strong anchor 时，工具结果中只命中 weak anchor 的候选必须降权或标记为 `weak_anchor_only`。

## 10. 版本边界

本文明确只设计 OpenAI Agent 驱动的 v2 检索路径。`openai-agents-python` 是唯一新增的 Agent 框架依赖。原因是它已经提供 agents、tools、handoffs、guardrails、sessions、tracing 等 agent workflow 基础能力，并且是 Python 框架，和当前 `smart-fund-server` 技术栈更容易集成。

最终只保留两个版本：

- `agentic_arag`：现有基于 LLM controller、手写工具循环、手写 ranker/expand/stop 的 v1 基线。
- `openai_agents_arag`：新增基于 `openai-agents-python` 的 v2 OpenAI Agent 检索运行时。

除上述两个版本外，本文不规划第三套检索运行时，也不做其他 Agent 框架预留实现分支。DeepSeek 可以继续用于现有抽取、judge、JSON 修复，也可以作为 `openai_agents_arag` 的 OpenAI 兼容模型 provider；但它只承担模型调用，不承担 Tool Kernel、guardrail、trace、replay 等运行时职责。

核心边界是：知识库检索能力属于我们自己的 Tool Kernel，`openai-agents-python` 只是 OpenAI Agent 编排层。

生产接入时必须使用服务端 API key 或企业允许的鉴权方式。agent 运行时只接收工具结果和结构化状态，不直接读取本地 `.env`、数据库连接串或敏感配置。

## 11. 缓存和上下文策略

Agent 模式必须显式设计缓存，否则会比 v1 更贵。

| 缓存对象 | 策略 |
| --- | --- |
| 写入期 LLM 抽取 | 保持现有本地文件缓存。 |
| embedding | 保持现有本地文件缓存。 |
| reranker | 对同一 query、候选文本摘要、top_n 和 reranker model version 做短期缓存。 |
| OpenAI Agent 多轮状态 | 使用 `openai-agents-python` 的 session 管理；DeepSeek 兼容模式用 messages 追加模拟同一 chat 线程。 |
| 本地 LLM cache | key 必须包含 provider、model、完整 messages、工具定义版本、instructions 版本、schema 版本。 |
| 工具结果 cache | 对 query embedding、keyword search、semantic search、open evidence 可做短期缓存。 |

为了利用前缀缓存，agent instructions、工具说明、schema 和固定系统规则必须稳定。每轮追加的是工具结果和追问，不应重写历史消息。对于 DeepSeek，只有前缀 message 内容逐字一致时，服务端 prompt cache 才能稳定命中；因此 agent runtime 必须把动态 observation 放在尾部追加，不要把 observation 插入到前面的固定 prompt 中。

写入期 contextual enrichment 也必须有版本。只要 `search_text`、`key_phrases`、`readable_relations`、`evidence_summary` 的生成逻辑变化，就必须生成新的 retrieval document version，并在 `RetrievalContextPackage` 中记录。否则后续 replay 无法判断效果变化来自 OpenAI Agent 调度，还是来自索引文档变化。

## 12. 质量评估和 A/B 对比

新方案必须和 v1 使用同一批 replay cases。最低比较指标：

| 指标 | 说明 |
| --- | --- |
| `exact_evidence_recall@k` | 已知 source_id 的新闻能否召回。 |
| `answer_coverage` | 主体、行业、资产、关系、时间是否覆盖。 |
| `false_stop_rate` | stop verifier 未满足却停止的比例。 |
| `wasted_slots` | judge/open 中明显偏题候选占比。 |
| `semantic_only_added` | semantic 是否贡献 keyword 找不到的有效候选。 |
| `rerank_gain` | reranker 是否把最终有效候选提前到更高位置。 |
| `hygiene_block_count` | pre-rerank hygiene 过滤、降级、标记的候选数量。 |
| `graph_confirmed` | graph 是否补全关系和证据链。 |
| `bootstrap_exact_hit` | 首轮无 LLM bootstrap 是否命中已知 source/evidence 或 strong anchor。 |
| `rewrite_gain` | agent 后续改写 query 是否带来新增有效候选。 |
| `rewrite_noise` | query rewrite 是否引入 only weak anchor 或偏题候选。 |
| `opened_evidence_count` | 精读证据数量是否合理。 |
| `tool_call_count` | agent 调度成本。 |
| `llm_cost / latency` | 总成本和耗时。 |
| `trace_replayable` | 是否能复盘每次工具调用和停止原因。 |

验收不是“agent 看起来更智能”，而是 v2 在固定评估集上至少满足：

- exact-news 问题不能比 v1 更差。
- false stop 低于 v1。
- wasted slots 低于 v1。
- semantic/graph 至少在一部分 case 中产生独立有效增益。
- reranker 至少在一部分 case 中降低 wasted slots 或提升有效候选排名；如果没有增益，不能把 reranker 作为默认排序入口。
- bootstrap exact hit 不能低于 v1 的首轮 raw query 命中能力。
- rewrite_gain 必须能覆盖 rewrite_noise，否则 query rewrite 不能作为默认动作。
- case summary 能一屏说明本次检索为什么停止。

## 13. 分阶段实施方案

### 阶段 1：整理 OpenAI Agent Tool Contract

目标是先把现有能力整理成 OpenAI Agent 可用的工具协议，不接入 `openai-agents-python`。

- 定义 `kg_search`、`kg_search_more`、`kg_rerank_candidates`、`kg_open`、`kg_expand_graph`、`kg_verify_stop`、`kg_finish` 的输入输出。
- 明确 `kg_search(mode=bootstrap)` 的输入输出：使用原始 query、规则化 anchor、多通道首轮召回和候选 family 去重，不调用 LLM rewrite。
- 定义 `kg_rerank_candidates` 的输入输出：输入 query、candidate_keys 或当前候选池、top_n、trigger；输出 rerank 后的 candidate keys、`rerank_score`、`rank_delta`、`top_n`、`usage.latency_ms` 和 `rerank_unavailable` 错误态。
- 明确 bootstrap rerank 合同：`kg_search(mode=bootstrap)` 返回广撒网候选后，先执行 pre-rerank hygiene，再调用 `kg_rerank_candidates(trigger=system_bootstrap)`；Agent 进入 loop 时看到的是清洗结果和模型 rerank 顺序。
- 统一 candidate key、evidence key、candidate family、channel summary。
- 修复 candidate package 中重复 excerpt、空 evidence_refs、meaning 重复 title 的问题。
- stop verifier 输出 recommended_next_tools。

### 阶段 2：新增 OpenAI Agent Runtime

目标是引入一个 OpenAI manager agent，不做 multi-agent handoff。

- agent instructions 固定。
- 注册 Tool Kernel。
- 进入 OpenAI Agent loop 前，由运行时自动执行 `kg_search(mode=bootstrap)`、pre-rerank hygiene 和 `kg_rerank_candidates(trigger=system_bootstrap)`，并把带有 rerank 信号的 `bootstrap_observation` 注入 agent 初始上下文。
- query rewrite 作为 agent 看到 bootstrap 缺口后的可选动作实现，不作为默认前置 controller。
- 使用 feature flag 增加 `openai_agents_arag` route。
- 输出与 v1 兼容的 `AnswerContext`。
- trace 写入现有 `generated_retrieval_llm_trace.log`。

### 阶段 3：强制 Guardrail

目标是保证 agent 不乱停、不乱答。

- `kg_finish` 前自动运行 `kg_verify_stop`。
- 未满足 coverage 时禁止正常 finish，只允许返回 insufficient_context。
- 工具预算、打开证据数量、最大扩展深度必须可配置。
- 背景 wiki 不能触发 graph expansion。

### 阶段 4：Replay A/B

目标是证明 v2 是否更好。

- 同一批真实 `ft_news` replay cases 跑 v1/v2。
- 输出对比报告。
- 对每个失败 case 标注失败阶段：recall、hygiene、rerank、open、judge、stop、agent_tool_choice。
- 增加 reranker 专项统计：bootstrap rerank 耗时、`rerank_gain`、`hygiene_block_count`、reranker 前后 topK 有效候选变化，以及 Agent 主动二次 rerank 的次数和收益。
- 只有指标达标后，才考虑扩大 v2 流量。

### 阶段 5：可选 multi-agent / handoff

当单 agent 稳定后，再拆 specialist：

| specialist | 职责 |
| --- | --- |
| Query Planner | 在 bootstrap 观察基础上拆 coverage schema。 |
| Recall Agent | 决定 keyword/semantic/graph/wiki 的召回组合。 |
| Evidence Auditor | 判断 evidence 是否足以支撑结论。 |
| Graph Explorer | 局部扩图和关系链验证。 |

第一版不建议直接多 agent。当前系统最大问题仍是工具接口、候选包、stop guardrail 和评估闭环；过早多 agent 会增加 trace 和成本复杂度。

## 14. 最终设计决策

1. 投影、编译、写入和索引刷新流程不变。
2. 当前 `agentic_arag` 固定工作流保留为 v1 基线。
3. 新增 `openai_agents_arag` 作为 v2 route，不影响 v1。
4. v2 首轮先执行无 LLM 的 `kg_search(mode=bootstrap)`。
5. bootstrap 广撒网召回后默认执行一次 `kg_rerank_candidates(trigger=system_bootstrap)`，作为 Agent 初始观察的一部分。
6. `kg_rerank_candidates` 是 v2 主排序工具；v2 当前阶段不保留规则排序工具，候选硬限制统一在 pre-rerank hygiene 中处理。
7. `kg_rerank_candidates` 暴露给 Agent，允许 Agent 在候选噪声高、补召回后需要重排、或需要同源候选内排序时主动调用。
8. Reranker 只提供同一 query 内的排序信号，不做事实生成，不做绝对阈值过滤，也不替代打开证据和 stop verifier。
9. query rewrite 只能作为后续补召回动作，不能作为默认入口。
10. 现有检索能力先沉淀为 Tool Kernel，再交给 agent 调度。
11. stop verifier 保留为 guardrail；candidate judge 只保留给 v1 基线和诊断，不作为 v2 后处理裁判。
12. agent 可以决定工具顺序、是否补召回和最终候选选择，但不能绕过 evidence-bound 和 stop verifier。
13. 新方案必须通过 replay A/B 证明效果，再考虑替换默认路由。

## 15. 验收口径

设计完成后的第一版实现必须满足：

- 可以通过配置在 v1 和 v2 间切换。
- v2 不修改写入链路和主图事实。
- v2 的每个工具调用都有结构化 trace。
- v2 trace 必须区分 bootstrap recall、bootstrap rerank、agent 后续 search_more、agent 主动 rerank、query rewrite，并统计 rewrite_gain / rewrite_noise。
- bootstrap observation 必须包含 reranker 的 top candidates、`rerank_score`、`rank_delta`、调用耗时和 unavailable 错误态。
- replay 报告必须统计 `rerank_gain` 和 `hygiene_block_count`；当 hygiene 过滤或降级候选时，trace 必须能看到原因。
- v2 的最终停止一定有 `kg_verify_stop` 结果。
- v2 输出的 Query Context 与现有消费方兼容。
- v1/v2 可以在同一批 replay cases 上生成对比报告。

如果达不到这些条件，不能把 `openai_agents_arag` 作为默认检索路径。
