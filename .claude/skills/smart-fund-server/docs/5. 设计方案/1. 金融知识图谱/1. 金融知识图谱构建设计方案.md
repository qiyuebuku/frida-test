# 金融知识图谱构建设计方案

> 本文档的定位：**逻辑上位于 L1 事件识别、L2 事件流、L3 决策打分之前**的基础设施方案。  
> 虽然当前 L1/L2 文档已经先写了一版，但这不是历史包袱。本方案按“知识图谱先行”的正确顺序重新定义地基，后续 L1/L2/L3 需要反向适配这份设计。  
> 目标不是为了某一个 L2 聚类场景临时加能力，而是把采集到的新闻、行情、资金、情绪、宏观、行业和概念数据沉淀成可持续复用的金融知识图谱。

---

## 0. 一句话说清楚

> **先建立一套领域受控的“金融知识编译器”：把股票、行业、概念、新闻、事件、宏观、资金、情绪和基金持仓统一编译成“实体 + 关系 + 证据 + 置信度 + 版本”的知识图谱；再把这张图导出给 Microsoft GraphRAG 做生产级 GraphRAG 检索，导出给 graphify 做本地导航、调试、Wiki 和 agent 导航。**

这件事的核心价值不是“让 L2 少调几次 LLM”，而是：

- 让系统知道“实体之间如何连接”，而不是只知道一堆扁平标签。
- 让后续问题可以通过图遍历和多跳推理回答，例如“算力需求爆发为什么可能影响液冷和电源设备”。
- 让 AI 检索不再只依赖 embedding 相似度，而是同时具备图索引、向量索引、全文索引。
- 让事件抽取、事件聚类、基金匹配、历史类比、复盘反馈都能共享同一套语义资产。

**核心决策**：

| 层 | 决策 |
|---|---|
| 领域图谱事实库 | 自建，采用 PostgreSQL 存 `kg_nodes` / `kg_edges` / evidence / version |
| 抽取与标准化 | 自研金融 KG compiler，不直接把原始数据全交给通用 GraphRAG/graphify 抽 |
| 生产 GraphRAG 检索 | 前期即纳入系统设计，采用 Microsoft GraphRAG 的 Bring Your Own Graph 路线 |
| 本地可视化与 agent 导航 | 复用 graphify 的 NetworkX、社区、Wiki、MCP、HTML 导出能力 |
| 向量检索 | 当前采用 PostgreSQL + `pgvector`，不单独引入专用向量库 |
| GraphRAG completion | 通过统一 LLM Proxy 接入真实 Claude CLI tmux 会话池，不使用 `claude -p` |
| GraphRAG embedding | 通过统一 `/v1/embeddings` 接入 `.env` 配置的远程 Qwen3-Embedding 服务，不使用 mock |
| L1/L2/L3 关系 | KG 是前置地基，L1/L2/L3 消费 KG，不在各层临时补语义规则 |

## 1. 背景与问题

### 1.1 现有事件体系的缺口

当前事件体系已经有清晰分层：

| 层级 | 目标 |
|---|---|
| L1 | 把原始数据抽成 `ft_events` |
| L2 | 把散点事件聚合成事件流和主线 |
| L3 | 把事件流映射到基金和交易信号 |
| L4 | 执行、回填和复盘 |

但如果没有知识图谱，L1/L2/L3 都会反复遇到同一个问题：**语义关系只能靠局部字段硬猜**。

典型问题：

| 场景 | 没有图谱时的问题 | 有图谱后的能力 |
|---|---|---|
| L1 概念标准化 | “AI 算力”“算力基建”“数据中心”可能被抽成三个孤立概念 | 通过 alias、co_occurs、related_to 归入同一语义邻域 |
| L2 主线聚类 | Union-Find 只能看标签直接重叠 | 图社区可以把 2-3 跳内强相关事件聚成主题 |
| L3 基金匹配 | 只能看基金重仓股是否直接命中事件股票 | 可以沿“事件 -> 概念 -> 行业 -> 股票 -> 基金持仓”传播影响 |
| AI 检索问答 | embedding 容易漏掉多实体、多跳问题 | GraphRAG 可以召回相关子图、路径和社区摘要 |
| 反馈闭环 | 高频误合并、漏合并只能人工总结 | 可沉淀为别名边、同义边、歧义边和知识缺口 |

### 1.2 为什么要在 L1 之前设计图谱

L1 不是简单的“把新闻变 JSON”。它抽取出的 `affected_stocks`、`affected_industries`、`affected_concepts` 会成为后面所有层的语义入口。

如果没有先定义图谱的实体规范和关系规范，L1 会产生几个长期问题：

1. **实体 ID 不稳定**：同一个概念每天可能被写成不同字符串。
2. **别名无法收敛**：例如“机器人”“人形机器人”“具身智能”有交集但不是完全等价。
3. **证据丢失**：后续不知道一条关系来自公告、新闻、规则还是模型推断。
4. **置信度混乱**：显式事实和模型猜测混在一起，难以用于交易决策。
5. **L2 被迫补语义债**：聚类阶段会不断写特殊规则弥补 L1 输出不规范。

所以知识图谱不是 L2 的优化项，而是 L1 输出契约的一部分。

## 2. 目标、原则与非目标

### 2.1 目标

1. **建立金融领域实体层**
   - 股票、行业、概念、机构、政策、宏观指标、事件、情绪信号、资金信号。

2. **建立可审计关系层**
   - 每条边都有 `relation_type`、`confidence_label`、`confidence_score`、`evidence_refs`、`source`。

3. **支持增量更新**
   - 新新闻、新事件、新行情信号进入后，只更新相关节点和边。
   - 定期全量校准，避免图谱漂移。

4. **支持图算法**
   - 社区发现、中心节点、跨社区连接、最短路径、邻居扩展、知识缺口发现。

5. **支持 GraphRAG**
   - 图索引 + 向量索引 + 全文索引组合召回。
   - 能生成 Wiki 风格的社区摘要，供 agent 和人类复用。

6. **与现有事件流水线兼容**
   - 不推翻 `ft_events`，而是让 `ft_events` 成为图谱的一类证据和动态事件节点。

### 2.2 地基原则

这部分必须在项目开始时定死，否则后面会因为“先跑起来再补”产生很难修复的数据债。

| 原则 | 说明 |
|---|---|
| 先定 ontology，再写 L1 prompt | L1 抽取必须服从已定义的实体类型、关系类型、ID 规则和置信度规则 |
| 先定 evidence contract，再谈模型能力 | 每个节点/边必须能追溯来源；没有证据的模型输出不能进入主图 |
| 先定版本和迁移策略 | prompt、规则、词表、schema、图构建算法都要有版本号 |
| 图谱事实库与检索引擎解耦 | PostgreSQL 里的事实图是源头，GraphRAG/graphify/向量库都是可重建索引 |
| 先单库，后拆分 | 在容量和并发没有证明成为瓶颈前，事实、全文、向量优先放在 PostgreSQL 统一维护 |
| 前期即按 GraphRAG 目标能力设计 | Local / Global / DRIFT、community reports、text_units、entities、relationships 从一开始就进入系统设计 |
| 抽取不是“规则 vs LLM”二选一 | 结构化事实用确定性编译；非结构化文本用 LLM 读取；所有结果都按同一 evidence/置信度协议入图 |
| 初始覆盖要“schema 完整、实例可渐进” | 一开始不需要填满所有金融知识，但必须把未来扩展需要的实体/关系/证据/版本机制预留好 |

### 2.3 关于“不要把所有关系都交给 LLM 抽”的修正

原说法“能从结构化数据确定的关系必须用规则抽，LLM 只处理语义关系和歧义关系”方向是对的，但表达不够准确。

更准确的决策是：

> **LLM 可以参与所有非结构化文本的理解，但 LLM 不能成为关系成立的唯一依据；关系能否进入主图，取决于证据、来源、置信度、关系类型和校验规则。**

也就是说，不是简单地规定“某类关系只能规则抽、某类关系只能 LLM 抽”，而是按证据等级分层：

| 关系来源 | 例子 | 入图方式 | 置信度 |
|---|---|---|---|
| 结构化确定事实 | 基金持仓、股票行业、概念成分股 | 程序直接编译 | `EXTRACTED` |
| 原文明确陈述 | 新闻写明“某政策支持低空经济” | LLM/规则从文本抽取，但证据是原文 | `EXTRACTED` 或高置信 `INFERRED` |
| 统计共现 | 多条事件中“AI服务器”和“液冷”频繁共现 | 程序生成候选边 | `INFERRED` |
| 语义同义/近义 | “人形机器人”和“具身智能” | LLM 判断 + 图邻域 + 人工/反馈确认 | `INFERRED` / `AMBIGUOUS` |
| 因果链推断 | “算力需求 -> 数据中心扩容 -> 液冷订单” | LLM 生成候选，必须保留推理链和证据 | `INFERRED` / `AMBIGUOUS` |

关键限制：

1. LLM 抽出的边必须带 `evidence_refs`，不能只带一句模型总结。
2. LLM 推断的因果边默认不能直接触发交易，只能进入解释、候选和加权项。
3. 对交易影响大的 `alias_of`、`causal_hint`、`benefits_from` 必须有复核或历史验证通道。
4. 结构化事实不应交给 LLM 重判，否则会引入无意义波动。

### 2.4 关于“不要一开始覆盖所有金融知识”的修正

原说法“不追求一开始覆盖所有金融知识，从事件驱动交易最需要的实体和关系开始”容易被误解成“先随便做一小块，以后再补”。这是危险的。

正确原则是：

> **第一版不要求填满所有金融知识实例，但必须设计完整的金融 KG 扩展框架。**

第一版必须一次性想清楚：

- 节点类型如何扩展：股票、行业、概念、基金、机构、政策、商品、宏观指标、海外资产、人物、地域。
- 关系类型如何扩展：属于、持有、供应链、受益、受损、替代、竞争、上游、下游、政策影响、宏观敏感。
- 时间如何表达：静态事实、阶段性事实、事件性事实、可衰减动态关系。
- 证据如何表达：表字段、新闻片段、公告原文、规则运行、LLM 输出、人工确认、历史验证。
- 错误如何修正：合并、拆分、废弃、降权、版本迁移。

第一版可以只导入最关键的实例，但不能用一个窄 schema 把未来堵死。

### 2.5 非目标

| 非目标 | 原因 |
|---|---|
| 不把 GraphRAG/graphify 当作源数据库 | 它们是索引与查询层，金融事实图必须由我们自己的 schema 管住 |
| 不直接使用 graphify 的代码 AST 抽取器处理金融数据 | `extract.py` 面向代码文件，不适合数据库和金融事件流 |
| 不直接把原始新闻全丢给 Microsoft GraphRAG 默认索引作为主图 | 默认流程适合非结构化语料探索，不适合作为交易系统的受控事实库 |
| 当前不引入 Neo4j | 当前重点是 ontology、证据、版本、抽取质量；图数据库不是最先的瓶颈 |
| 当前不引入专用向量库 | 在事实、全文、向量统一放在 PostgreSQL 前提下，一致性和运维复杂度更可控 |
| 不把 embedding 当成图谱本体 | embedding 是召回索引，不是可审计的事实关系 |

## 3. 总体架构

### 3.1 分层架构

本系统不能把“知识图谱构建工具”和“金融知识图谱本体”混为一谈。正确分层如下：

| 层 | 职责 | 技术选择 |
|---|---|---|
| 金融 KG compiler | 把数据库、新闻、公告、事件、持仓编译成受控实体/关系/证据 | 自研 |
| KG fact store | 保存稳定节点、边、证据、版本、审核状态 | PostgreSQL |
| 图算法运行时 | 社区发现、中心性、路径、子图导出 | NetworkX / Leiden |
| 生产 GraphRAG 查询 | Local / Global / DRIFT、社区报告、混合检索 | Microsoft GraphRAG BYOG |
| 本地 agent 导航 | 快速图查询、Wiki、HTML、MCP、本地调试 | graphify |
| 混合召回层 | 关键词、语义、图路径、chunk 精读的统一召回与融合 | PostgreSQL + `pgvector` + PostgreSQL FTS + RRF |

### 3.3 Microsoft GraphRAG vs graphify 选型

这个项目不应该问“到底用 Microsoft GraphRAG 还是 graphify”，而应该问：**哪一层用谁**。

#### Microsoft GraphRAG 的定位

Microsoft GraphRAG 是生产级 GraphRAG 检索框架。它的默认 pipeline 会把文档切成 text units，再用 LLM 抽实体、关系、claims，做 Leiden 社区发现，生成 community reports，并为查询提供 Local Search、Global Search、DRIFT Search 等能力。

它的优势：

- 有正式的 knowledge model：documents、text_units、entities、relationships、communities、community_reports。
- 有成熟查询模式：Local 适合实体问题，Global 适合全局总结，DRIFT 结合社区信息扩展局部查询。
- 有 Bring Your Own Graph：可以跳过默认 LLM 抽图，直接提供 entities/relationships/text_units。
- 有 parquet 输出和 embedding workflow，适合作为生产 GraphRAG 检索层。

它的风险：

- 默认索引流程高度依赖 LLM 抽实体和关系，成本高，并且会把金融事实库交给通用抽取器。
- 默认 entity title/type 合并策略不等于金融主键体系，可能导致股票、概念、机构别名合并不稳定。
- 默认 relation 是自然语言 description，不等于交易系统需要的强类型关系。
- 对盘中增量事件流、交易级可审计、边置信度分层，还需要我们自己包一层。

这里需要明确一个判断：

> **GraphRAG 不是后期增强项，而是前期就应进入系统目标架构的能力层。**

原因不是“它更时髦”，而是我们最终要解决的问题天然就是：

- Local Search：围绕具体股票、概念、事件做实体级推理
- Global Search：对整个市场阶段进行主题总结
- DRIFT Search：回答“为什么会沿这条链条传导”的问题

这些问题即使不用官方 GraphRAG，也仍然需要：

- LLM 调用
- prompt tuning
- token 成本
- 多阶段查询链路

因此，这些成本不是是否采用 GraphRAG 的否决理由，而是这类能力本身的固有成本。  
真正应该做的不是回避成本，而是让成本围绕统一知识模型、统一 community reports 和统一查询链路沉淀下来。

#### graphify 的定位

graphify 是轻量图谱工具和 agent 导航工具。它的优势是本地、简单、NetworkX、Wiki、HTML、MCP、`shortest_path`、`get_neighbors`，非常适合在 repo 内快速调试和让 agent 读图。

它的优势：

- 已经在项目内，复用成本低。
- `build.py` / `cluster.py` / `analyze.py` / `wiki.py` / `serve.py` 都是小模块，容易改。
- 适合生成 `GRAPH_REPORT.md`、wiki、HTML 和 MCP 工具，让 agent 快速理解图结构。
- 适合 L2 开发阶段快速验证社区发现、路径和主线解释。

它的限制：

- 原始抽取器面向代码、文件和多模态资料，不是金融数据库流。
- 查询能力偏 BFS/DFS/邻居/路径，不是完整 GraphRAG query engine。
- 没有 Microsoft GraphRAG 那样成熟的 Local/Global/DRIFT、parquet knowledge model、community report query 工作流。
- 更适合作为开发工具和轻量服务，不适合作为生产 GraphRAG 主引擎。

#### 最终选型

| 问题 | 结论 |
|---|---|
| 核心图谱是否直接交给 Microsoft GraphRAG 抽 | 不交。核心图谱由金融 KG compiler 自建 |
| 是否使用 Microsoft GraphRAG | 使用，前期即按 BYOG 路线接入，并把 Local / Global / DRIFT 作为目标查询能力 |
| 是否使用 graphify | 使用，但作为本地图运行时、可视化、Wiki、MCP 和开发调试层 |
| 谁是事实源 | PostgreSQL `kg_*` 表 |
| 谁可以被重建 | GraphRAG parquet、graphify graph.json、向量库、全文索引 |

最终架构：

```
PostgreSQL KG facts
      │
      ├─ export_graphrag_parquet()
      │       └─ Microsoft GraphRAG: communities / reports / Local / Global / DRIFT
      │
      ├─ export_graphify_json()
      │       └─ graphify: graph.html / wiki / MCP / local navigation / debug
      │
      └─ export_vector_fts_indexes()
              └─ contextual chunks / BM25 / rerank
```

### 3.4 graphify 的复用边界

graphify 原始定位是“把文件、代码、论文、图片构造成知识图谱”。我们要复用的是它的**图管线和 agent 工具层**，不是直接复用它的**输入抽取器**。

| graphify 模块 | 是否复用 | 用法 |
|---|---:|---|
| `build.py` | 是 | 把金融 KG 导出结果 `{nodes, edges}` 组装为 NetworkX 图 |
| `cluster.py` | 是 | 本地/开发阶段做 Leiden/Louvain 社区发现 |
| `analyze.py` | 是 | 中心节点、跨社区连接、知识缺口，用于盘后复盘和调试 |
| `wiki.py` | 是 | 为社区和核心节点生成 Markdown Wiki，供 agent 渐进式读取 |
| `serve.py` | 是 | 暴露 `query_graph`、`shortest_path`、`get_neighbors` 等 MCP 工具 |
| `export.py` | 可选 | 导出 HTML、GraphML、Neo4j Cypher |
| `extract.py` | 否 | 代码 AST 抽取器，不适合金融数据 |
| `detect.py` / `ingest.py` | 否 | 文件语料入口，不适合数据库增量流 |

决策：

> **自研 `financial_kg_compiler`，输出受控 `kg_nodes` / `kg_edges`；再分别导出 graphify JSON 和 Microsoft GraphRAG parquet。**

## 4. 实体模型

### 4.1 节点类型

| 节点类型 | ID 规则 | 来源 | 示例 |
|---|---|---|---|

## 5. 关系模型

### 5.1 置信度分层

沿用 graphify 的思想，但增加数值分数：

| 标签 | 含义 | 可否直接用于交易 |
|---|---|---|
| `EXTRACTED` | 结构化表、公告、新闻原文中明确出现 | 可以，但仍需看证据来源 |
| `INFERRED` | 由规则、图算法或 LLM 合理推断 | 可以作为辅助因子，不单独触发交易 |
| `AMBIGUOUS` | 有歧义，待人工或后续数据确认 | 只用于提示和复核，不进入强信号 |

每条边还要有 `confidence_score`：

```
EXTRACTED: 0.85 - 1.00
INFERRED:  0.50 - 0.85
AMBIGUOUS: 0.20 - 0.60
```

### 5.2 核心关系类型

| 关系类型 | 源节点 -> 目标节点 | 来源 | 置信度 |
|---|---|---|---|
| `belongs_to_industry` | stock -> industry | 行业映射 | EXTRACTED |
| `belongs_to_concept` | stock -> concept | 概念成分股 | EXTRACTED |
| `industry_parent_of` | industry -> industry | 行业层级 | EXTRACTED |
| `alias_of` | concept/org -> concept/org | 人工词库 + LLM 复核 | EXTRACTED/INFERRED |
| `related_to` | concept -> concept | 共现、图社区、LLM | INFERRED |
| `causal_hint` | concept/event -> concept/industry | LLM + 历史验证 | INFERRED/AMBIGUOUS |
| `event_affects_stock` | event -> stock | `ft_events.affected_stocks` | EXTRACTED |
| `event_affects_industry` | event -> industry | `ft_events.affected_industries` | EXTRACTED |
| `event_relates_to_concept` | event -> concept | `ft_events.affected_concepts` | EXTRACTED |
| `event_supported_by_doc` | event -> document | `evidence_refs` | EXTRACTED |
| `policy_affects_industry` | policy -> industry | L1 抽取 + 规则 | EXTRACTED/INFERRED |
| `macro_affects_industry` | macro_indicator -> industry | 规则库 + 历史统计 | INFERRED |
| `fund_holds_stock` | fund -> stock | 基金持仓 | EXTRACTED |
| `stream_contains_event` | event_stream -> event | L2 聚类产物 | EXTRACTED |
| `community_contains_node` | community -> any | 图社区发现 | INFERRED |

### 5.3 边属性

| 属性 | 含义 |
|---|---|
| `edge_id` | 稳定主键 |
| `source_node_id` / `target_node_id` | 起止节点 |
| `relation_type` | 关系类型 |
| `direction` | 关系方向，`directed` / `undirected` |
| `weight` | 图算法权重 |
| `confidence_label` | EXTRACTED / INFERRED / AMBIGUOUS |
| `confidence_score` | 0-1 |
| `evidence_count` | 支持证据数量 |
| `first_seen_at` / `last_seen_at` | 生命周期 |
| `decay_factor` | 动态关系的时间衰减 |
| `metadata` | 方向、强度、时间窗、规则版本等 |

## 6. 存储设计

### 6.1 选型决策

当前设计固定为：**PostgreSQL 作为图谱事实库，NetworkX 作为图算法运行时。**

这里的 `PG` 指的就是 `PostgreSQL`。在本方案里，它不是临时过渡，也不是“先凑合用一下”，而是当前明确选定的事实存储层。

原因：

1. 当前项目已经以 PostgreSQL 为主存储，接入成本最低。
2. 金融图谱需要强审计能力，关系证据、版本和来源比图遍历性能更重要。
3. 当前规模可以通过增量子图 + 定时全图构建解决，没必要提前引入 Neo4j。
4. Microsoft GraphRAG 和 graphify 都可以消费导出产物，不要求把事实库迁移到图数据库。

补充说明：

| 能力 | 当前选型 |
|---|---|
| 事实节点/边存储 | PostgreSQL |
| 证据与版本管理 | PostgreSQL |
| 向量召回 | PostgreSQL + `pgvector` |
| 全文召回 | PostgreSQL FTS |
| 图遍历/社区 | 导出到 NetworkX / GraphRAG 运行 |

这样做的原因不是“专用向量库不专业”，而是当前阶段单库收益更大：

1. 事实、元数据、向量、全文可以放在同一事务和同一备份体系里。
2. 向量检索可以和 JSONB 过滤、时间过滤、权限过滤、全文过滤直接写在一条 SQL 里。
3. 避免 PostgreSQL 与 Milvus/Pinecone/Weaviate 双写带来的一致性和运维成本。
4. 当前知识图谱系统的首要难题是 ontology、evidence、incremental update，不是向量库极限性能。
5. 当规模走到十亿级向量或极高并发时，再拆专用向量库仍然来得及。

后续引入 Neo4j 的条件：

- 节点数量超过 100 万，边数量超过 1000 万。
- 在线路径查询成为高频 API，而不是离线分析和 agent 查询。
- PostgreSQL 递归查询与 NetworkX / GraphRAG 快照构建成为明确瓶颈。

### 6.3 Microsoft GraphRAG parquet 索引

PostgreSQL 是事实库，但生产 GraphRAG 查询层需要符合 Microsoft GraphRAG knowledge model 的导出表。

第一阶段至少导出：

```
graphrag-out/financial-kg/input/
├── entities.parquet
├── relationships.parquet
└── text_units.parquet
```

映射规则：

| KG fact store | GraphRAG 表 | 说明 |
|---|---|---|
| `kg_nodes` | `entities.parquet` | `node_id` 映射为 entity id，`label`/`description` 用于检索 |
| `kg_edges` | `relationships.parquet` | `source`/`target`/`description`/`weight` 对齐 GraphRAG |
| `kg_edge_evidence` + 原文 | `text_units.parquet` | 作为关系和实体的证据来源 |
| `kg_communities` | GraphRAG 自生成或导入 | 社区可以让 GraphRAG 重算，也可用于对齐 |

使用方式：

- 不使用默认 GraphRAG 从原始文本全量抽关系作为主图。
- 使用 Bring Your Own Graph 路线，让 GraphRAG 假设实体和关系已经抽取完成。
- 只让 GraphRAG 负责社区、community reports、Local/Global/DRIFT 查询和嵌入索引。
- GraphRAG 输出是索引产物，任何时候都可从 `kg_*` 表重建。

### 6.4 graphify JSON 快照

PostgreSQL 是事实库，但 graphify 需要 `graph.json` 进行本地图遍历、导出和 MCP 服务。

因此每次构建后生成：

```
graphify-out/financial-kg/
├── graph.json
├── graph.html
├── GRAPH_REPORT.md
├── wiki/
│   ├── index.md
│   └── *.md
└── snapshots/
    └── {graph_version}.json
```

规则：

- `kg_nodes` / `kg_edges` 是 source of truth。
- `graph.json` 是可重建产物，不手工编辑。
- `kg_build_runs.graph_version` 记录每次快照版本。
- MCP 服务读取最新稳定版本，不读取构建中的临时文件。

### 6.5 索引产物的主从关系

| 产物 | 是否事实源 | 可否删除重建 | 用途 |
|---|---:|---:|---|
| `kg_nodes` / `kg_edges` / `kg_edge_evidence` | 是 | 否 | 金融知识图谱事实库 |
| `graphrag-out/**/*.parquet` | 否 | 是 | Microsoft GraphRAG 查询索引 |
| `graphify-out/financial-kg/graph.json` | 否 | 是 | 本地图遍历、MCP、HTML |
| `graphify-out/financial-kg/wiki/*.md` | 否 | 是 | agent/human 渐进式读取 |
| `pgvector` index | 否 | 是 | 语义召回和历史类比 |
| PostgreSQL FTS index | 否 | 是 | 精确证据召回 |

## 7. 构建流程

### 7.1 V0 冷启动

在正确的工程顺序里，V0 图谱必须在 L1 正式启动前完成。当前虽然已经先写了 L1/L2 文档，但后续要按这个顺序重写：

```
KG ontology / node_id / relation_id / evidence contract
    -> V0 基础图谱
    -> L1 图谱感知事件抽取
    -> L2 图社区事件流
    -> L3 图路径基金匹配
```

V0 冷启动先用确定性数据构建基础图谱：

| 数据 | 产出 |
|---|---|
| 股票基础信息 | `stock` 节点 |
| 行业板块 | `industry` 节点，`stock -> industry` 边 |
| 概念板块 | `concept` 节点，`stock -> concept` 边 |
| 热门板块、涨停原因 | `concept` / `industry` 热度属性和共现边 |
| 宏观指标表 | `macro_indicator` 节点 |
| 情绪、资金流指标 | `sentiment_signal` / `fund_flow_signal` 节点 |
| 已采集新闻标题 | `document` 节点，初步抽取 org/concept 共现边 |
| 基金持仓 | `fund` 节点，`fund -> stock` 边 |
| 政策/监管机构词表 | `organization` / `policy` 节点，别名和层级边 |

V0 的目标不是完美，而是给 L1 提供：

- 标准实体词表。
- 概念别名候选。
- 行业、概念、股票的基础连接。
- 抽取时可引用的图谱上下文。
- L1 输出 `node_id` 的候选空间。
- L2/L3 可以使用的路径和社区基础结构。

V0 的验收标准：

| 验收项 | 要求 |
|---|---|
| 股票覆盖 | A 股股票节点可按代码稳定查询 |
| 行业覆盖 | 股票至少有一个行业路径 |
| 概念覆盖 | 高频概念板块有稳定 `concept:{canonical_name}` |
| 基金覆盖 | 可从基金追溯到持仓股票 |
| 证据覆盖 | 每条基础边有来源表或来源接口 |
| 导出覆盖 | 同一事实图能导出 GraphRAG parquet 和 graphify JSON |

### 7.2 L1 运行后的增量构建

L1 每产出一条 `ft_events`，同步生成图谱增量：

```
ft_events
  -> event 节点
  -> event_affects_stock 边
  -> event_affects_industry 边
  -> event_relates_to_concept 边
  -> event_supported_by_doc 边
  -> 必要时产生 alias_of / related_to / AMBIGUOUS 候选边
```

增量更新策略：

| 触发 | 处理 |
|---|---|
| 新事件入库 | upsert event 节点和显式边 |
| 新概念出现 | 先建 `concept` 节点，状态 `active`，置信度按来源确定 |
| 概念疑似别名 | 写 `alias_of` 候选边，`confidence_label=AMBIGUOUS` |
| 同一概念多次共现 | 提升 `related_to` 边权重 |
| 人工确认 | 将 AMBIGUOUS 边升级为 EXTRACTED 或废弃 |

### 7.3 批处理与校准

| 任务 | 频率 | 内容 |
|---|---|---|
| `kg_incremental_update` | 每 5 分钟 | 消费新增事件和新增结构化信号 |
| `kg_cluster_refresh` | 每 30 分钟 | 对活跃子图重新社区发现 |
| `kg_export_graphify` | 每 30 分钟/按需 | 导出 graphify JSON、HTML、MCP 图 |
| `kg_export_graphrag` | 盘后/按需 | 导出 GraphRAG parquet 并刷新 community reports |
| `kg_full_rebuild` | 每日盘后 | 从事实库重建全量 NetworkX 图 |
| `kg_wiki_refresh` | 每日盘后 | 生成社区 Wiki 和 GRAPH_REPORT |
| `kg_quality_review` | 每日盘后 | 输出 AMBIGUOUS 边、孤立节点、异常社区 |

## 8. 抽取与标准化策略

### 8.1 KG compiler 的处理阶段

金融知识图谱构建不是一次 prompt，也不是一次 SQL 导出，而是一条 compiler pipeline：

```
raw records
  -> normalize entities
  -> resolve node identity
  -> extract / compile relations
  -> attach evidence
  -> score confidence
  -> validate against ontology
  -> upsert facts
  -> export indexes
```

每个阶段都必须可重放、可测试、可版本化。

| 阶段 | 输入 | 输出 | 是否可用 LLM |
|---|---|---|---|
| entity normalization | 文本、结构化字段 | canonical label / aliases | 可以 |
| node identity resolution | canonical label + 类型 + 外部 ID | `node_id` | 少量辅助 |
| deterministic relation compile | 结构化表 | EXTRACTED 边 | 不需要 |
| textual relation extraction | 新闻、公告、研报 | 带证据的事件/关系 | 需要 |
| relation candidate mining | 共现、路径、历史表现 | 候选边 | 可选 |
| confidence scoring | 证据、来源、模型分、历史验证 | `confidence_label/score` | 可选 |
| ontology validation | 节点/边 | 通过、降级、拒绝 | 不需要 |
| index export | `kg_*` 表 | GraphRAG/graphify/vector/FTS | 不需要 |

### 8.2 实体规范化

实体规范化是图谱质量的核心。

处理顺序：

1. **精确 ID 优先**
   - 股票代码、基金代码、行业代码、宏观指标代码直接作为主键。

2. **别名词典匹配**
   - 对组织、概念、政策使用 `kg_aliases` 或 `kg_nodes.aliases`。

3. **归一化规则**
   - 去除空格、全半角差异、常见后缀、英文大小写差异。

4. **图邻域辅助**
   - 如果两个概念共享大量股票、行业和事件，提升合并候选分。

5. **LLM 复核**
   - 只对高价值、高频、歧义实体调用 LLM。

6. **人工确认**
   - 对影响交易链路的同义词和因果边，需要留人工确认入口。

### 8.3 关系抽取分层

| 层 | 方法 | 示例 |
|---|---|---|
| 结构化抽取 | 从表字段直接生成边 | 股票属于行业、基金持有股票 |
| 事件抽取 | 从 `ft_events` 生成边 | 事件影响某股票、事件关联某概念 |
| 共现统计 | 时间窗内高频共现生成候选边 | “AI 算力”和“液冷”在多事件共现 |
| 图算法推断 | 社区、路径、中心性生成语义邻域 | 多个概念归入同一算力基础设施社区 |
| LLM 判定 | 对歧义边做语义判断 | “具身智能”和“人形机器人”是否等价 |
| 复盘反馈 | 交易结果和人工审核反哺边权重 | 某概念链条多次验证有效，提高权重 |

关系抽取的关键不是少用 LLM，而是**禁止没有证据、没有类型、没有版本的关系进入主图**。

### 8.4 边权重设计

边权重不等于置信度。权重用于图算法，置信度用于审计和决策。

建议公式：

```
weight =
  base_relation_weight
  * confidence_score
  * evidence_factor
  * recency_factor
  * source_quality_factor
```

其中：

| 因子 | 含义 |
|---|---|
| `base_relation_weight` | 关系类型基础权重，例如 `belongs_to_industry` 高于普通共现 |
| `confidence_score` | 关系可信度 |
| `evidence_factor` | 证据数量的对数压缩 |
| `recency_factor` | 动态事件关系随时间衰减 |
| `source_quality_factor` | 官方公告、交易所、权威媒体高于普通转述 |

## 9. 图算法与索引集成

### 9.1 Microsoft GraphRAG 集成

生产 GraphRAG 层采用 Microsoft GraphRAG，并从前期开始按 Bring Your Own Graph 路线接入：

```
kg_nodes / kg_edges / kg_edge_evidence
   -> entities.parquet
   -> relationships.parquet
   -> text_units.parquet
   -> GraphRAG workflows:
        create_communities
        create_community_reports
        generate_text_embeddings
   -> Local / Global / DRIFT Search
```

#### 为什么不用默认 GraphRAG 直接抽主图

默认 GraphRAG 的强项是从大规模非结构化文档中发现实体、关系、社区和报告；但交易系统需要更强的类型约束和审计能力：

| 维度 | 默认 GraphRAG 抽图 | 金融 KG compiler |
|---|---|---|
| 实体 ID | title/type 合并，偏语义 | 股票代码、基金代码、行业代码、canonical concept |
| 关系类型 | 自然语言 relationship description | 强类型 relation_type |
| 证据 | text_unit 级引用 | source_table/source_pk/excerpt/rule_version/prompt_version |
| 置信度 | LM 描述和权重 | EXTRACTED/INFERRED/AMBIGUOUS + score |
| 增量盘中 | 非主场景 | 必须支持 |
| 交易可审计 | 需要额外建设 | 从 schema 开始内置 |

所以默认 GraphRAG 可以作为探索工具，但不能作为交易主图的事实源。

#### GraphRAG 在本系统中的职责

| GraphRAG 能力 | 用途 |
|---|---|
| hierarchical Leiden communities | 生成多层社区视图 |
| community reports | 为主题社区生成高密度摘要 |
| Local Search | 回答某个股票、概念、事件相关的问题 |
| Global Search | 回答“最近市场主线是什么”这类全局问题 |
| DRIFT Search | 在局部实体问题中引入社区上下文，扩大召回 |
| embeddings | 对 text_units、entity descriptions、community reports 做语义召回 |

这里的定位不是“先导出兼容格式，未来再决定要不要真正使用官方查询层”，而是：

> **KG facts、GraphRAG knowledge model、community reports 和 Local / Global / DRIFT 查询能力，从前期就按同一目标架构设计。**

允许分阶段落地的，是实现深度和调优程度；不是方向本身。

#### 当前接入实测结论

截至当前预检，GraphRAG 技术接入已经验证出以下事实：

| 项 | 结论 |
|---|---|
| completion provider | 可通过统一 LLM Proxy 调用真实 Claude CLI tmux 会话池 |
| `claude -p` | 当前 GLM-5.1 路线下会触发 429 风控，不能作为主路径 |
| tmux pool | `pool_size=10` / `max_concurrency=10` 可启动并处理 GraphRAG 查询 |
| 长 prompt | 不应直接完整粘贴进 TUI；超过阈值写入任务文件，让 Claude 用 `Read` 读取 |
| embedding | `/v1/embeddings` 已接远程 Qwen3-Embedding，返回 1024 维真实向量 |
| mock embedding | 已从 GraphRAG 预检路线中移除 |
| 查询链路 | Global / Local / Basic 查询已用真实 embedding 跑通；Local 查询已验证长上下文文件策略 |
| DRIFT | 能启动并调用真实 embedding，但默认链路较重，需要单独做预算、top-k、并发和超时调优 |

这个结论不会改变“主图必须由金融 KG compiler 管住”的设计，只说明 GraphRAG 作为查询层的工程接入已经具备继续推进的基础。

#### LLM Proxy 工程约束

GraphRAG 的 `extract_graph`、`create_community_reports`、Local / Global / DRIFT 查询都会产生较长 prompt。由于当前 completion 后端是 Claude Code TUI，而不是原生 SDK，必须遵守以下约束：

1. **对 Claude 的提示词必须中性**
   - 不写“你是 OpenAI-compatible API 后端”。
   - 不写“纯 LLM 后端”。
   - 只描述当前任务和输出格式。

2. **长上下文必须文件化**
   - 代理层通过 `CLAUDE_PROXY_FILE_CONTEXT_THRESHOLD_CHARS` 控制阈值。
   - 超过阈值后，将完整任务写入 `/tmp/smart-fund-claude-proxy/request-contexts/*.md`。
   - TUI 中只发送短指令，让 Claude 使用 `Read` 工具读取该任务文件。

3. **并发必须按上游限流调优**
   - `pool_size=10` 说明本地会话池可以支撑并发，不代表上游模型一定允许满速并发。
   - 多会话并发下已观察到上游 `429 code=1302`。
   - 代理层当前可能将后端失败包装成 HTTP 502，后续需要区分 429、超时、无有效输出等错误类型。

4. **embedding 不是瓶颈**
   - 当前真实 embedding 调用耗时远低于 completion。
   - 性能优化重点应放在 GraphRAG completion 调用次数、community reports 复用、查询模式预算和缓存上。

### 9.2 graphify 集成

graphify 用于本地调试、agent 导航和轻量可视化。

它不替代 GraphRAG，也不替代 `kg_*` 事实库。

### 9.3 NetworkX 图构建

将 `kg_nodes` / `kg_edges` 转成 graphify 标准输入：

```json
{
  "nodes": [
    {
      "id": "concept:AI算力",
      "label": "AI算力",
      "source_file": "kg_nodes",
      "source_location": "node_id=concept:AI算力",
      "node_type": "concept"
    }
  ],
  "edges": [
    {
      "source": "event:xxx",
      "target": "concept:AI算力",
      "relation": "event_relates_to_concept",
      "confidence": "EXTRACTED",
      "weight": 0.92
    }
  ]
}
```

注意：

- graphify 的 `source_file` / `source_location` 在金融场景里映射为表名和主键。
- `confidence` 使用 graphify 的三档标签。
- 金融侧额外属性保留在 `metadata`，用于 L2/L3。

### 9.4 社区发现

本地开发和 L2 快速验证可以使用 graphify `cluster.py`：

- 优先 Leiden。
- 没有 graspologic 时 fallback 到 NetworkX Louvain。
- 大社区自动二次拆分。
- 孤立节点单独成社区。

金融侧需要额外处理：

1. **动态图时间窗**
   - L2 使用最近 72 小时活跃子图。
   - 长期知识图谱使用全量或 180 天窗口。

2. **关系类型权重**
   - `belongs_to_industry` 是稳定基础边，但不能让所有股票把行业社区撑得过大。
   - `event_relates_to_concept`、`related_to`、`causal_hint` 对主题社区更重要。

3. **社区命名**
   - 用社区内 top concept / top industry / top event 自动生成 label。
   - 例如“AI算力-数据中心-液冷”。

生产 GraphRAG 层则使用 Microsoft GraphRAG 的 hierarchical Leiden communities，并生成 community reports。两边都应从同一个 `kg_edges.weight` 派生权重，避免社区结果语义分裂。

### 9.5 图分析

复用 graphify `analyze.py`，但金融侧解释要重写：

| 分析项 | 金融含义 |
|---|---|
| god nodes | 当前市场最核心的概念、行业、股票或政策 |
| surprising connections | 跨行业、跨概念、跨事件类型的异常连接 |
| knowledge gaps | 高频孤立概念、缺少行业映射的股票、无证据的推断边 |
| shortest path | 两个概念、股票、行业之间的影响链 |

示例：

```
shortest_path("AI算力", "液冷")
AI算力 -> 数据中心 -> 高功率服务器 -> 液冷
```

### 9.6 Wiki 输出

每日盘后生成：

- graphify wiki：本地 agent 和人类快速导航。
- GraphRAG community reports：生产 GraphRAG 查询上下文。
- `wiki/index.md`：图谱总入口。
- 每个社区一篇 Wiki/report：主题、核心节点、跨社区关系、证据概览。
- 每个 god node 一篇 Wiki：连接关系和证据来源。

Wiki 的用途：

1. 人类复盘：快速看今天市场主线和隐藏连接。
2. Agent 检索：不用直接解析巨大的 `graph.json`。
3. L1 prompt 上下文：给高频概念提供标准解释和别名。
4. L2 主线解释：为 EventStream 的 reason_chain 提供结构化背景。
5. GraphRAG 全局查询：作为 Global/DRIFT Search 的社区摘要基础。

## 10. 与 L1/L2/L3 的关系

### 10.1 对 L1 的影响

L1 事件抽取应该变成“图谱感知”的抽取：

| L1 步骤 | 图谱参与方式 |
|---|---|
| 新闻分类 | 用已知政策、行业、概念词表做前置匹配 |
| 实体抽取 | 输出标准 `node_id`，而不是只输出字符串 |
| 概念归一 | 先查 `kg_nodes` / `kg_aliases`，未命中才新建候选 |
| 影响面判断 | 结合股票-行业-概念图谱，避免凭空扩散 |
| 质量标记 | 新概念、低置信度概念、歧义别名写入 `quality_flags` |

L1 输出建议增加：

```json
{
  "affected_node_ids": [
    "stock:300750",
    "industry:sw:电力设备",
    "concept:AI算力"
  ],
  "kg_edge_candidates": [
    {
      "source": "concept:AI算力",
      "target": "concept:液冷",
      "relation": "related_to",
      "confidence_label": "AMBIGUOUS",
      "evidence": "同一批事件中多次共现"
    }
  ]
}
```

### 10.2 对 L2 的影响

L2 的聚类逻辑从“扁平标签匹配”升级为“图上事件社区发现”。

旧逻辑：

```
event A affected_concepts ∩ event B affected_concepts != empty
=> 认为相关
```

新逻辑：

```
event A -> concept/stock/industry 子图
event B -> concept/stock/industry 子图
如果两者在图上距离短、路径强、社区一致
=> 认为属于同一主线候选
```

关键能力：

- 事件不共享同一标签，但通过 2-3 跳强路径连接，也能聚合。
- 孤立事件可通过最短路径接入已有主线。
- AMBIGUOUS 边不直接合并，只作为“待复核候选”。
- EventStream 的 `reason_chain` 可以写出路径，而不是只写“标签重合”。

### 10.3 对 L3 的影响

L3 可以从图谱获得：

| 能力 | 示例 |
|---|---|
| 事件到基金的多跳映射 | event -> concept -> stock -> fund |
| 间接受益链 | 政策 -> 行业 -> 上游材料 -> 个股 |
| 风险扩散链 | 海外制裁 -> 半导体设备 -> 国产替代 -> 相关基金 |
| 历史类比入口 | 当前社区 -> 历史相似社区 -> 当时涨跌路径 |
| 解释链 | 为什么推荐某基金，沿图路径给证据 |

L3 不应该直接相信所有图边：

- `EXTRACTED` 边可进入硬逻辑。
- `INFERRED` 边进入加分项。
- `AMBIGUOUS` 边只用于提示，不触发买入。

## 11. GraphRAG 检索设计

参考文章的共同结论是：单一向量检索不足以处理复杂知识问题，生产级 RAG 应该混合多种索引。

### 11.1 三类索引

| 索引 | 用途 | 示例 |
|---|---|---|
| 图索引 | 多跳关系、路径、社区 | “AI算力为什么影响液冷” |
| 向量索引 | 语义近似、历史类比 | “类似这次政策的历史事件” |
| 全文索引 | 精确词、代码、文件、公告号 | “国常会 2026-04-23 原文” |

### 11.2 A-RAG 对本方案的修正

`A-RAG` 这类思路提醒我们：真正有用的 RAG 不是“把 query 向量化后取 Top-K”，而是要同时具备多种检索粒度，并能按问题类型组合使用。

对本系统来说，不能把 GraphRAG 理解成唯一检索入口，也不能把 `pgvector` / embedding 当成万能召回。金融问答和交易链路至少需要四类工具能力：

| 工具能力 | 作用 | 本系统实现 |
|---|---|---|
| `keyword_search` | 精确命中股票代码、公告号、政策名、机构名、专有概念 | PostgreSQL FTS / trigram / 结构化字段过滤 |
| `semantic_search` | 召回语义相近新闻、历史事件、相似政策 | `pgvector`，后续可替换专用向量库 |
| `graph_search` | 查邻居、路径、社区、影响链 | `kg_edges` / NetworkX / GraphRAG Local/DRIFT |
| `chunk_read` | 读取完整新闻、公告、研报、community report | `text_units` / 原始 document / wiki report |

这里的关键不是让 LLM 每次都自己决定调用哪个工具。A-RAG 的价值在于证明“单一路径不够”，但如果所有选择都交给 LLM，会带来额外 token、延迟和不可控性。

本系统采用更适合生产交易系统的折中：

> **底层永远准备好多路召回；查询层先用规则和轻量分类决定默认召回组合；必要时再让 agent 追加工具调用。**

### 11.3 混合召回与 Rank Fusion

GraphRAG Local / Global / DRIFT 是生产查询的核心能力，但它不应独占所有召回。系统需要一个统一的 `retrieval_context_builder`，把不同来源的候选证据合并成有限上下文。

推荐流程：

```text
query
  -> query classify:
       entity / global_theme / causal_chain / evidence_lookup / history_analogy
  -> parallel retrieval:
       graph candidates
       keyword candidates
       semantic candidates
       community reports
  -> rank fusion:
       RRF / weighted merge / dedupe
  -> context budget:
       path first, evidence second, summary third
  -> LLM answer or downstream structured consumer
```

RRF 的价值在于：关键词召回和语义召回的分数尺度不同，不能简单相加；按排名融合更稳。第一版可以在应用层实现 RRF，不要求数据库原生支持。

候选优先级建议：

| 问题类型 | 默认召回组合 | 说明 |
|---|---|---|
| 精确实体问题 | keyword + graph + Local Search | 先命中标准实体，再扩展邻居 |
| 市场主线总结 | community reports + Global Search + semantic | 先看社区报告，再补充相似事件 |
| 影响链/传导问题 | graph path + DRIFT + chunk_read | 路径优先，证据跟随 |
| 原文证据查找 | keyword + chunk_read | 不让向量召回覆盖精确证据 |
| 历史类比 | semantic + graph community + time filter | 相似事件必须带时间和图社区约束 |

### 11.4 PostgreSQL 与 Milvus 的边界

参考文章里 Milvus 的启发是：关键词稀疏向量和语义稠密向量应该在同一套检索流程里并行融合，而不是让 agent 运行时反复决定“要不要关键词检索”。

但这不等于当前阶段要立刻引入 Milvus。当前方案仍保持：

> **事实库、全文索引、向量索引优先放在 PostgreSQL；等规模或性能证明必要后，再把混合召回层迁移到 Milvus / 其他专用检索引擎。**

原因：

1. 金融 KG 的第一阶段瓶颈是 ontology、证据、版本和数据质量，不是向量库性能。
2. PostgreSQL 已经能同时承载结构化过滤、FTS、JSONB、时间过滤和 `pgvector`。
3. 过早引入 Milvus 会产生双写、一致性和运维成本。
4. 只要 `retrieval_context_builder` 的接口设计正确，底层从 PostgreSQL 换到 Milvus 不影响 GraphRAG / L1 / L2 / L3。

后续引入 Milvus 或类似专用检索引擎的条件：

| 条件 | 说明 |
|---|---|
| 向量规模显著增长 | PostgreSQL `pgvector` 查询延迟或索引维护成为明确瓶颈 |
| 需要原生稀疏向量 BM25 + dense hybrid | PostgreSQL FTS + 应用层 RRF 无法满足召回质量或性能 |
| 高并发在线问答 | GraphRAG / L3 查询并发超过 PostgreSQL 可控范围 |
| 多模态或十亿级非结构化语料 | 专用向量库的工程收益超过双写成本 |

因此，A-RAG/Milvus 文章对本方案的结论是：

> **不是现在改用 Milvus，而是现在必须把混合召回协议设计好。**

### 11.5 在线检索流程

```
用户问题 / agent 问题
   │
   ├─ 实体识别：识别股票、行业、概念、政策、事件
   │
   ├─ 图召回：邻居、最短路径、社区摘要
   │
   ├─ 向量召回：相似事件、相似文档、历史案例
   │
   ├─ 全文召回：精确证据和原文
   │
   ├─ rank fusion：去重、排序、控制 token
   │
   ▼
LLM 生成回答 / L2-L3 消费
```

### 11.6 Microsoft GraphRAG 查询模式映射

| 查询模式 | 适合问题 | 金融示例 | 数据来源 |
|---|---|---|---|
| Local Search | 围绕特定实体的细节问题 | “宁德时代最近受哪些事件影响” | entity + relationship + text_units |
| Global Search | 数据集整体总结 | “过去两周市场主线有哪些” | community reports |
| DRIFT Search | 局部问题但需要社区扩展 | “AI服务器为什么带动液冷” | local entity + relevant community reports |
| Basic vector search | 对照基线和简单相似召回 | “找类似事件新闻” | text_units embeddings |

本系统默认查询策略：

1. 如果问题包含明确股票/基金/概念，先 Local Search。
2. 如果问题是市场主线、全局总结、阶段复盘，先 Global Search。
3. 如果问题包含“为什么、怎么传导、影响链、相关板块”，优先 DRIFT Search。
4. 所有回答都必须回链到 `kg_edge_evidence` 或 `text_units`。
5. 交易链路使用 GraphRAG 结果时，只取结构化路径和证据，不直接采纳生成式结论。

这里需要明确：

> **Microsoft GraphRAG 官方 query engine 是本系统的目标能力，而不是可有可无的后期附件。**

原因在于，Local / Global / DRIFT 正好对应本系统未来最核心的三类问题：

- 某个实体最近发生了什么
- 整个市场阶段的主要主题是什么
- 某个概念或事件为什么会沿特定链条扩散

### 11.7 为什么检索阶段仍然需要 LLM

GraphRAG 不是“图数据库 + 搜索框”，它解决的是**检索 + 聚合 + 推理 + 回答**的组合问题。

检索阶段仍然需要 LLM，原因不是系统设计多余，而是问题本身如此：

1. **Local Search 不是只找节点**
   - 它要把实体、关系、community reports、text units 组装成一个有限上下文，再生成针对问题的回答。

2. **Global Search 本质是全局总结**
   - 官方流程就是对 community reports 做 map-reduce 式中间结论生成和最终汇总。
   - 这类“全局主题总结”天然不是纯检索问题。

3. **DRIFT Search 本质是路径解释**
   - 它不是只把相关块找出来，而是借助社区信息扩展局部查询，回答“为什么沿这条链路传导”。

4. **不用 GraphRAG 也绕不过这些成本**
   - 如果改用 graphify、自研 community summary、自研 global aggregation，仍然需要 LLM、prompt tuning、token 和多阶段查询编排。

因此，本系统的立场应该是：

> **LLM 查询成本不是是否采用 GraphRAG 的否决理由，而是图谱型问答能力的固有成本。**

真正要优化的是：

- 同一份 community report 是否能复用到多类查询
- 哪些问题走工具型结果，哪些问题走完整生成式回答
- 如何把 graph/wiki/report/cache 沉淀成长期资产
- 如何控制 Local / Global / DRIFT 的 token 预算

### 11.8 当前性能与稳定性判断

预检样例显示：

- GraphRAG indexing 的主要耗时在 `extract_graph` 和 `create_community_reports`。
- GraphRAG query 的主要耗时在 completion，embedding 请求很快。
- `generate_text_embeddings` 不是主要瓶颈。
- `pool_size=10` 能提供更多本地会话，但小语料任务无法吃满 10 个会话。
- 如果 GraphRAG 同时触发多个长 prompt，上游 GLM-5.1 可能返回 `429 code=1302`。
- 代理层 HTTP 502 不一定代表 GraphRAG 或 Claude TUI 自身 502，很多时候是代理层把 tmux 调用失败、上游 429、超时等统一包装成 502。

因此后续优化方向不是简单“继续加会话数”，而是：

1. 为 GraphRAG indexing 和 query 分别设置 completion rate limit。
2. 将 GraphRAG 长 prompt 统一走任务文件 + `Read`。
3. 对 Local / Global / DRIFT 设置不同的 top-k、token budget 和超时。
4. 缓存 community reports 和稳定查询结果。
5. 将代理层错误码拆细，避免把上游限流误判成普通 502。

### 11.8 Contextual Retrieval 的用法

对于新闻、公告、研报等 document/chunk：

- 入向量库前补充上下文：公司、时间、事件类型、涉及概念、行业。
- 这些上下文可以直接来自图谱节点和边。
- 这样 chunk 不会失去“它是谁、发生在什么时候、关联什么实体”的身份。

示例：

```
原 chunk:
公司营收同比增长 38%，服务器业务贡献主要增量。

contextual chunk:
这是 2026Q1 某公司的业绩公告片段，主体为 stock:xxxx，所属行业为计算机设备，
关联概念为 AI服务器、算力基础设施。片段描述服务器业务拉动营收增长。
```

## 12. 质量控制

### 12.1 核心指标

| 指标 | 目标 |
|---|---|
| 实体标准化命中率 | L1 输出实体中，已命中 `kg_nodes` 的比例 |
| 新概念增长率 | 每日新增 concept 数，异常升高说明抽取漂移 |
| 孤立节点比例 | 无边或弱边节点比例 |
| AMBIGUOUS 边比例 | 高比例说明语义不稳定，需要复核 |
| 社区稳定性 | 同一主题跨构建版本的节点重合率 |
| 路径可解释率 | L2/L3 reason_chain 中能给出证据路径的比例 |
| 人工复核通过率 | LLM 推断边被确认的比例 |

### 12.2 常见坏图谱模式

| 坏模式 | 表现 | 处理 |
|---|---|---|
| 超级概念吞噬 | “新能源”“AI”连接过多，社区过大 | 降低泛概念边权，增加二级概念 |
| 字符串碎片化 | 同一概念多个写法 | alias 合并，L1 prompt 增加标准词表 |
| 虚假因果 | 共现被误判为因果 | `related_to` 和 `causal_hint` 严格区分 |
| 事件污染长期知识 | 一次性热点永久改变概念关系 | 动态边加时间衰减 |
| 证据缺失 | LLM 推断边没有来源 | 不允许无证据边进入主图，只进候选队列 |

### 12.3 人工复核入口

每日输出三类复核清单：

1. 高频 AMBIGUOUS 边。
2. 高频新概念和疑似别名。
3. 跨社区 surprising connections。

复核结果写回：

- 确认：提升为 EXTRACTED 或高置信 INFERRED。
- 否定：标记 rejected，后续抽取避免再次生成。
- 拆分：将过宽概念拆成多个子概念。

产出：

验收：

- 能回答“哪些关系可以用于交易硬逻辑，哪些只能用于提示”。
- 能回答“哪些事实进入主图，哪些只进入候选图/索引层”。
- 能回答“GraphRAG 和 graphify 分别消费什么导出物”。

### Phase 1：V0 图谱冷启动

产出：

- `kg_nodes` / `kg_edges` / `kg_edge_evidence` 基础表。
- 股票、行业、概念、宏观指标节点。
- 股票-行业、股票-概念基础边。
- 基金-持仓股票基础边。
- GraphRAG parquet 导出。
- graphify `graph.json` 快照。

验收：

- 能查询某股票的行业、概念邻居。
- 能查询某概念下关联股票和行业。
- 能从某基金追溯持仓股票，再追溯事件影响路径。
- 能用同一事实图生成 GraphRAG 输入和 graphify 图。
- 能生成 `GRAPH_REPORT.md`。

### Phase 2：事件图谱接入

产出：

- L1 写入 `ft_events` 后同步 upsert event 节点和事件边。
- `event -> stock/industry/concept/document` 边完整落库。
- 事件证据写入 `kg_edge_evidence`。

验收：

- 任意 `ft_events.id` 能展开成子图。
- 能从事件追溯到原始新闻和影响实体。

### Phase 3：GraphRAG / graphify 双索引

产出：

- Microsoft GraphRAG BYOG workflow。
- GraphRAG communities / community_reports。
- graphify wiki / HTML / MCP。
- PostgreSQL FTS + `pgvector` 的混合召回基线。
- 应用层 RRF / 去重 / token budget 控制。
- `retrieval_context_builder` 第一版。
- `kg_communities` 与外部社区报告版本对齐。

验收：

- Local / Global / DRIFT 能回答各自适合的问题。
- graphify MCP 能查邻居、路径和子图。
- 同一问题能同时从 keyword、semantic、graph 三路召回候选，并融合成有限上下文。
- 两套索引都能从 `kg_*` 表重建。

### Phase 4：L2 图社区改造

产出：

- L2 使用图社区、路径强度、时间衰减生成 EventStream 候选。
- EventStream 保存核心路径、核心社区、证据链。

验收：

- 不共享直接标签但图路径强相关的事件能进入同一候选主线。

- AMBIGUOUS 边不会直接导致主线合并。

### Phase 5：反馈闭环

产出：

- 人工复核队列。
- L3 和复盘结果反哺边权重。
- 高频误合并、漏合并转化为 alias 或 rejected 规则。

验收：

- AMBIGUOUS 边比例下降。
- L2/L3 的 reason_chain 可解释率上升。
- LLM 兜底调用量下降。

## 14. 关键设计决策

| 决策 | 结论 |
|---|---|
| 图谱在系统中的顺序 | KG 逻辑上先于 L1/L2/L3；现有 L1/L2 文档需要按 KG 方案重写 |
| 图谱存储 | PostgreSQL 为事实库，GraphRAG parquet / graphify JSON / `pgvector` / FTS 为可重建索引 |
| 是否引入 Neo4j | 当前不引入，等规模和查询压力证明必要后再考虑 |
| 是否引入专用向量库 | 当前不引入，先采用 PostgreSQL + `pgvector` |
| 是否引入 Milvus | 当前不引入；吸收其 hybrid search 思路，在 PostgreSQL 阶段先实现 keyword + semantic + graph 的统一 RRF 融合接口 |
| Microsoft GraphRAG 怎么用 | 固定采用 Bring Your Own Graph 作为生产 GraphRAG 查询层，从前期开始按 Local / Global / DRIFT 目标能力设计 |
| graphify 怎么用 | 作为本地开发、可视化、Wiki、MCP、路径调试工具，不作为生产 GraphRAG 主引擎 |
| A-RAG 对系统的启发 | 不把检索做成单次 Top-K；提供 keyword_search / semantic_search / graph_search / chunk_read 四类能力，并由 retrieval_context_builder 做混合召回 |
| 构建时机 | L1 前先做 V0 冷启动；L1 后持续增量更新；盘后全量校准 |
| LLM 用在哪里 | LLM 可读非结构化文本并生成候选关系，但关系入主图必须通过 evidence、ontology、confidence、version 校验 |
| 查询阶段为什么仍需要 LLM | 因为 Local / Global / DRIFT 处理的是检索 + 聚合 +推理 +回答，不是纯向量召回 |
| 规则用在哪里 | 结构化确定事实由程序编译，不交给 LLM 重判 |
| embedding 用在哪里 | 用于 GraphRAG 向量召回和历史类比，不作为图谱事实来源 |
| 交易决策如何用边 | EXTRACTED 可硬用，INFERRED 可加权，AMBIGUOUS 只提示 |
| 初始覆盖范围 | 第一版实例可聚焦事件驱动交易，但 ontology、证据、版本、迁移机制必须完整 |
| Wiki / community reports 是否必要 | 必要，它们是人类复盘、agent 低 token 检索和 GraphRAG 全局查询入口 |

## 16. 最小可行闭环

如果要最小成本先跑通，也不能跳过 ontology 和证据协议。建议第一版只做这些，但每一步都按未来可扩展方式实现：

1. 建 `kg_nodes` / `kg_edges` / `kg_edge_evidence`。
2. 定义稳定 node_id、relation_type、confidence、evidence、version。
3. 导入股票、行业、概念、基金持仓基础图。
4. 导出 graphify JSON，验证邻居、路径、社区、Wiki。
5. 导出 Microsoft GraphRAG BYOG parquet，验证 community reports 和 Local/Global/DRIFT 查询。
6. L1 事件入库时同步生成 event 节点和 3 类边：
   - `event_affects_stock`
   - `event_affects_industry`
   - `event_relates_to_concept`
7. 每 30 分钟导出活跃 72 小时子图，跑社区发现。
8. L2 读取社区结果生成 EventStream 候选。
9. 每日盘后生成 Wiki、community reports 和复核清单。

这条路径能最快验证：

- 图谱是否提升 L2 主线聚合质量。
- 图路径 reason_chain 是否比标签重合更可解释。
- 高频 AMBIGUOUS 边是否能反哺 L1 概念标准化。
- Microsoft GraphRAG BYOG、community reports、Local / Global / DRIFT 接入链路是否按预期工作。
- graphify 是否满足本地 agent 导航和调试需求。
