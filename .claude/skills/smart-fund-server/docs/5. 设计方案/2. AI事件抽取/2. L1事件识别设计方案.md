# L1 事件识别层 · 详细设计方案

> 本文档在全局方案 §3 的基础上展开，聚焦 L1 层的内部细节。
> 风格：概念设计，解释"为什么"和"数据怎么流动"，不包含代码。

> **阶段性说明**：本文档成稿时，L1 的语义标准化仍主要围绕 `ft_events` 字段展开，金融知识图谱尚未作为前置基础组件正式接入。
> 在 `../1. 知识图谱/1. 知识图谱总体设计方案.md` 确认之后，L1 的定位需要升级为“图谱感知的事件编译层”，届时本文档需要回头重构。
> 因此，当前版本适合用于理解现阶段 L1 双路径设计，但**不应视为最终版 L1 方案**。

## 1. 需求分析

### 1.1 L1 层的定位

L1 是整条事件流水线的"入口层"：把原始的异构数据（自由文本、结构化数值、情绪快照、资金流）转成**统一的、可聚合的 Event 记录**，供 L2 做去重合并、L3 做影响推理。

上游有两类数据：
- **非结构化文本**：`ft_news` 里的新闻、公告、研报摘要，必须经 LLM 理解语义才能抽成事件。
- **结构化数值**：`ft_market_flow` / `ft_macro_indicators` / `ft_sentiment` / `ft_market_cache`，本身是数字序列，必须结合"阈值/预期/历史分布"才能判断"这是否构成一个值得记录的事件"。

### 1.2 核心约束

| 约束 | 说明 |
|---|---|
| 数据量 | ~300 条新闻/天 + 数值流约 2000 条/天，峰值 9:30-10:00、14:55-15:00 |
| 延迟预算 | 从数据进库到事件产出 ≤ 5 分钟（高频段），≤ 15 分钟（低频段） |
| 成本预算 | LLM 调用日成本控制在 ≈18 万 tokens/天以内（prompt cache 复用后） |
| 可解释性 | 每条事件必须能追溯回原始记录（evidence_refs），便于人工复核 |
| 可重放 | Schema、prompt、规则阈值都要带版本号，旧事件可标记为"旧版本产物" |

### 1.3 复杂度判定

**复杂**。L1 同时涉及：
- LLM pipeline（分类 + 抽取 + 校验 + cache 优化）
- 规则引擎（阈值、差值、趋势三类逻辑 + 滚动窗口）
- 异构产出的 schema 统一
- 与 jettask 调度、planner API 深度集成

## 2. 整体设计

### 2.1 双路径架构

```
         ┌─────────────────────────────┐
         │   ft_news (自由文本)         │──► L1a · AI 抽取路径 ──┐
         └─────────────────────────────┘                        │
                                                                ▼
         ┌─────────────────────────────┐                 ┌────────────┐
         │   ft_market_flow             │                 │            │
         │   ft_macro_indicators        │──► L1b · 规则路径  ─►  ft_events │
         │   ft_sentiment               │                 │            │
         │   ft_market_cache            │                 └────────────┘
         └─────────────────────────────┘                        ▲
                                                                │
                                          source_type 区分  text/numeric
```

两条路径完全独立：独立的 jettask 任务、独立的资源池、独立的失败重试逻辑。
唯一的交汇点是 `ft_events` 表——两条路径都遵循同一份字段契约。

### 2.2 为什么要拆两条路径（而非"全丢给 LLM"）

- **成本**：规则能解决的问题，LLM 算一次 10 倍成本还不如一个 `if`。
- **准确性**：数值判定是严格可验证的（CPI 超预期 0.5σ 就是超预期），LLM 在数字比较上容易犯低级错误。
- **可解释性**：规则路径可以直接写清楚"因为北向净流入 152 亿 > 90 天 95 分位 148 亿，触发'北向资金大幅流入'事件"。
- **失败域隔离**：LLM 抖动不影响数值事件产出，反之亦然。

### 2.3 关键技术选型

| 选型点 | 决策 | 理由 |
|---|---|---|
| LLM 通道 | 复用 claude-planner tmux API（localhost:8899） | 已有 prompt cache 基础设施；避免自建 SDK 客户端 |
| 批处理粒度 | 每批 8-16 条同类新闻 | 既摊薄 system prompt cache，又控制单次响应长度 |
| 分类/抽取分离 | 两次独立 LLM 调用 | 分类用小模型/短 prompt，抽取用完整 prompt；降本且职责单一 |
| 规则阈值 | 90 天滚动 95 分位 | 适配市场状态漂移；避免硬编码在牛熊市都失真 |
| 事件粒度 | 一条新闻可产多事件 | 现实中一条公告常涉及多主体多方向，强行合并会丢信息 |
| 去重时机 | L1 只做"显式重复"去重，语义去重留给 L2 | 保持 L1 职责单一 |

## 3. 数据模型：Event Schema（统一契约）

L1a 和 L1b 都写入 `ft_events`，字段契约如下。字段分四组：**身份/溯源 / 语义 / 影响面 / 质量**。

### 3.1 身份与溯源字段

| 字段 | 类型 | 含义 | 取值说明 |
|---|---|---|---|
| `event_id` | string(pk) | 事件主键 | UUID v7，带时序前缀便于范围扫描 |
| `source_type` | enum | 来源路径 | `text` (L1a) / `numeric` (L1b) |
| `source_table` | string | 原始表名 | `ft_news` / `ft_market_flow` 等 |
| `evidence_refs` | jsonb | 证据引用 | 数组，每项 `{table, pk, excerpt}` |
| `created_at` | timestamp | L1 产出时间 | 自动填充 |
| `event_time` | timestamp | 事件发生/生效时间 | 新闻发布时间、指标公布时间或交易时刻 |
| `schema_version` | string | Schema 版本 | 如 `v1.0`，支持演进 |
| `extractor_version` | string | 抽取器版本 | L1a 填 prompt 版本，L1b 填规则版本 |

### 3.2 语义字段

| 字段 | 类型 | 含义 | 取值范围 |
|---|---|---|---|
| `event_type` | enum | 一级分类 | policy / earnings / m&a / announcement / shock / industry / macro_data / fund_flow / sentiment_extreme / price_action |
| `event_subtype` | string | 二级细分 | 如 `policy.monetary.rrr_cut`、`fund_flow.northbound.large_inflow` |
| `title` | string | 一句话标题 | ≤ 60 字，L1a 由 LLM 生成，L1b 由模板填充 |
| `summary` | text | 事件摘要 | ≤ 200 字 |
| `direction` | enum | 方向 | `positive` / `negative` / `neutral` |
| `strength` | float | 强度 | 0.0 – 1.0，相对量化，1.0 = 行业级冲击 |
| `sentiment` | float | 情感倾向 | -1.0 – 1.0 |
| `scope` | enum | 影响范围 | `macro` / `industry` / `concept` / `company` / `region` |
| `duration` | enum | 持续性 | `intraday` / `days` / `weeks` / `months` / `structural` |

### 3.3 影响面字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `affected_stocks` | jsonb | `[{code, name, role}]`，role ∈ 主体/关联/受益/受损 |
| `affected_industries` | jsonb | 申万二级行业代码数组 |
| `affected_concepts` | jsonb | 概念板块数组（政策主题/技术主题等） |
| `affected_regions` | jsonb | 地域标签（country/province/city） |

### 3.4 质量字段

| 字段 | 类型 | 含义 |
|---|---|---|
| `novelty` | float | 新颖度，0–1，与过去 N 天事件相似度倒推 |
| `certainty` | float | 可信度，0–1，来源权威性 + 语义明确度 |
| `quality_flags` | jsonb | 异常旗标数组（`low_confidence` / `json_repaired` / `missing_evidence`） |
| `dedup_key` | string | 粗粒度去重键，见 §6 |

> **设计取舍**：不把 `impact_score` 放进 L1。impact 是 L3 的事，L1 只给"原料"。

## 4. L1a · AI 抽取路径

### 4.1 分类器设计

#### 为什么要先分类

- 不同类型的事件关心的字段完全不同：政策事件关心"影响行业 + 方向"，并购事件关心"买方/卖方/金额"。统一 prompt 会让模型在 80% 情况下输出不相关字段。
- 分类后每类用**专属 prompt**，可以把字段定义、example、边界条件写得极其具体，显著提升抽取质量。
- 分桶后的同类新闻才能有效复用 system prompt cache。

#### 分类类别（L1a 一级事件类型）

| 类别 | 典型信号词 | 典型来源 |
|---|---|---|
| `policy` | 央行/发改委/证监会/降准/降息/补贴/试点 | 官方通告、新华社、财政部 |
| `earnings` | 净利润/营收/预告/业绩快报 | 交易所公告、业绩披露 |
| `m&a` | 收购/并购/重组/要约/易主 | 上市公司公告 |
| `announcement` | 股东减持/分红/股权激励/诉讼 | 上市公司公告（非 M&A） |
| `shock` | 爆炸/事故/制裁/地震/停产 | 突发类新闻 |
| `industry` | 渗透率/价格战/新产品/出货量 | 行业研报、产业链新闻 |
| `macro_data` | CPI/PPI/PMI/GDP/社融（文字版） | 统计局、央行通稿 |
| `other` | 未归类 | 兜底 |

#### 分类器实现思路

- **第一次调用**：纯文本输入（title + summary 前 200 字），输出仅 `{event_type, confidence}`。
- **模型选择**：用 Haiku 级别的轻量通道——一次分类只需几十个 token 输出。
- **置信度阈值**：`confidence < 0.6` 直接打 `other` 进人工复核队列，不进主流程抽取。
- **规则兜底**：在分类器之前加一层关键词前置分流，如 "xx 公司披露业绩" 直接判 `earnings`。这层兜底用于极省 tokens 的明确场景。

### 4.2 抽取 prompt 模板设计思路

每类都对应一份 prompt 模板，模板结构共享但"槽位"不同：

```
<system>
  [固定身份定义 + 输出 JSON schema + 通用规则]   ← 被 prompt cache 复用
  [本类别专属字段说明 + 典型 example 3-5 条]     ← 本桶复用
</system>
<user>
  本批新闻：[8-16 条，每条带临时 id 方便模型回引]
</user>
```

#### 每类的抽取重点

| 类别 | 必填字段重点 | 易错点 |
|---|---|---|
| `policy` | direction / scope / affected_industries / duration | 容易把"研究制定"当成"已出台"，要在 prompt 里强调"已生效 vs 征求意见" |
| `earnings` | 主体 stock / 同比变化 / 超预期与否 / direction | 预告 vs 快报 vs 正式报告的区分；分区间口径 |
| `m&a` | 买方 / 标的 / 金额 / 进度（意向/过会/完成） | 防止模型把"股东大会通过"视为"完成收购" |
| `announcement` | 主体 stock / 细分类型（减持/分红/激励） | 减持金额/比例必须抽全 |
| `shock` | affected_regions / scope / 冲击对象 | 强调不臆测"长期影响"，只抽事实 |
| `industry` | affected_industries / affected_concepts / 方向 | 避免把单家公司产品发布扩张为"全行业利好" |
| `macro_data` | 指标名 / 实际值 / 预期值 / 同比 | 数值比较留给 L1b 判定，L1a 只抽事实 |

### 4.3 批处理 pipeline 流程

```
ft_news (新增未处理)
   │
   ▼
(1) 拉取未处理批次 ──► 按 processed_at IS NULL 筛 + LIMIT 200
   │
   ▼
(2) 分类（单条并行） ──► event_type + confidence
   │
   ▼
(3) 分桶暂存 ──► 按 event_type 入内存/Redis 桶
   │
   ▼
(4) 触发抽取 ──► 桶达到 8 条 或 等待 > 60s
   │
   ▼
(5) 批量抽取 ──► planner API 同一会话连续发 N 批（复用 cache）
   │
   ▼
(6) JSON 校验 + 修复 ──► 单条失败不阻塞整批
   │
   ▼
(7) 初步去重 ──► dedup_key 查重
   │
   ▼
(8) 入库 ft_events + 标记 ft_news.processed_at
```

#### 每步的细节

- **(1) 拉取**：用 `processed_at IS NULL AND created_at > now() - 24h` 作为主查询条件，避免老数据重刷。
- **(2) 分类**：分类独立一个 jettask 子任务，失败的条走 `classify_failed` 状态而非回滚。
- **(3) 分桶**：桶维度 = `event_type`。每个桶有"最大等待时长 60s"，防止低频类别（如 `shock`）永远攒不满。
- **(4) 触发条件**：满 8 条或超时立即触发；同时设置硬上限 16 条，防止 prompt 过长撑爆上下文。
- **(5) 批量抽取**：向 planner API 发请求时，同一桶的多个批次走**同一 session_id**，让 system prompt 命中 cache。桶间切换时切 session。
- **(6) JSON 校验**：先尝试严格 JSON parse，失败时走"修复 pass"（单条重试 1 次），再失败则打 `json_repair_failed` 旗标但保留原始输出供人工复核。
- **(7) 初步去重**：见 §6，仅针对"显式重复"。
- **(8) 入库**：一次 INSERT 多条，开事务包住"写 ft_events + 更新 ft_news.processed_at"。

### 4.4 prompt cache 利用策略

核心思想：**让相同的前缀尽量被连续请求共享。**

- **层级一：system prompt 完全固定**。身份说明 + 输出 schema + 通用规则写成常量，不随批次变。这部分每类一份，约 1500-2500 tokens，是 cache 的主力。
- **层级二：同桶连续请求**。同一 event_type 的所有批次在一个 tmux 会话里顺序跑完，不穿插其他桶。tmux 会话保活期间 cache 自然复用。
- **层级三：桶切换时的决策**。如果某桶只有 3 条（低于 8），宁可让它多等 60s，也不要"硬凑"另一个桶的数据破坏 cache 前缀。
- **冷启动**：每天开盘前（8:55）用最常见的 3 类（policy / industry / earnings）预热一次 session，提前建立 cache。

#### 成本估算（对齐全局方案）

- 单条独立调用：约 8000 tokens × 300 条 = 2.4M tokens/天
- 批量 + cache：system prompt 约 2000 tokens × 命中率 95% = 有效 100 tokens，批内每条约 400 tokens，300 条总计 ≈ 150k~180k tokens/天。

### 4.5 L1a 失败与降级

| 失败类型 | 处理策略 |
|---|---|
| 分类失败 | 走 `other` 桶，用通用 prompt 抽取，打 `classify_fallback` 旗标 |
| 抽取 LLM 无响应 | 整批重试最多 2 次，仍失败则按单条打回重试队列 |
| JSON 解析失败 | 单条重试 1 次；仍失败打 `json_repair_failed` 保原文 |
| 输出包含未知 event_type | 强制归为 `other` 并打 `schema_violation` 旗标 |
| 全局 LLM 长时间不可用 | 熔断 L1a（不影响 L1b 继续），告警人工介入 |

## 5. L1b · 规则识别路径

### 5.1 规则类型

| 模式 | 形式 | 适用场景 |
|---|---|---|
| 单值阈值 | `value ⋛ threshold` | 绝对量级触发（北向资金、大单净额） |
| 差值对比 | `|actual − expected| ⋛ k·σ` | 超预期判定（CPI/PPI/PMI） |
| 趋势识别 | 连续 N 期同向 | LPR 连续下调、社融连续回落 |

### 5.2 阈值来源

**原则：阈值不硬编码，全部从历史滚动窗口算出来。**

- 单值阈值：取过去 90 天该指标的 95 分位作为"显著"门槛，99 分位作为"重大"门槛。
- 差值对比：用过去 12 期预期偏差的标准差 σ。
- 趋势识别：指定窗口长度（如连续 3 期），要求同向变化幅度 > 最小分辨率（避免噪声）。

阈值每日重算一次，写入 `ft_rule_thresholds` 配置表。规则执行时读这张表，而不是读代码常量。

### 5.3 每种数据源的规则明细

#### ft_market_flow（资金流）

| 规则名 | 逻辑 | 触发事件 |
|---|---|---|
| 北向大额净流入 | 日净流入 > 95分位 | `fund_flow.northbound.large_inflow` |
| 北向大额净流出 | 日净流出 > 95分位 | `fund_flow.northbound.large_outflow` |
| 板块资金异动 | 板块净流入 z-score > 2 | `fund_flow.sector.abnormal` |
| 龙虎榜异常 | 单股上榜且净买/卖 > 阈值 | `fund_flow.lhb.concentrated` |

#### ft_macro_indicators（宏观指标）

| 规则名 | 逻辑 | 触发事件 |
|---|---|---|
| CPI/PPI 超预期 | |actual − expected| > 0.5σ | `macro_data.cpi.surprise` |
| PMI 荣枯分界穿越 | 上期 <50 本期 >50 或反向 | `macro_data.pmi.cross` |
| 利率调整 | LPR/MLF/OMO 利率变化 | `policy.monetary.rate_change` |
| 社融/M2 连续偏离 | 连续 2 期偏离同比均值 > 阈值 | `macro_data.credit.deviation` |

#### ft_sentiment（情绪）

| 规则名 | 逻辑 | 触发事件 |
|---|---|---|
| 情绪极值 | 情绪指数 > 90 分位 或 < 10 分位 | `sentiment_extreme.{greed|fear}` |
| 情绪快速切换 | 24h 情绪指数变化 > 1σ | `sentiment_extreme.flip` |

#### ft_market_cache（市场快照）

| 规则名 | 逻辑 | 触发事件 |
|---|---|---|
| 涨停潮 | 涨停数 > 95 分位 | `price_action.limit_up_surge` |
| 跌停潮 | 跌停数 > 95 分位 | `price_action.limit_down_surge` |
| 成交量异动 | 大盘成交额 > 95 分位 | `price_action.volume_surge` |

### 5.4 L1b 规则识别流程

```
数据源更新完毕 (jettask 上游)
   │
   ▼
(1) 拉取增量（自上次检查点以来的记录）
   │
   ▼
(2) 读取规则配置 ft_rule_thresholds（缓存在内存，每日刷新）
   │
   ▼
(3) 逐规则评估 ──► 对每条增量记录应用所有相关规则
   │
   ▼
(4) 命中规则 ──► 构造 Event（标题/摘要用模板填充）
   │
   ▼
(5) 初步去重（见 §6）
   │
   ▼
(6) 入库 ft_events + 更新规则评估检查点
```

#### 模板化字段填充

规则命中后，Event 的 title/summary/direction/strength 全用模板化逻辑填，无需 LLM：

- `title`：如"北向资金单日净流入 152 亿（95分位阈值：148 亿）"
- `direction`：由规则自身语义决定（流入 → positive、流出 → negative）
- `strength`：用"实际值 / 99分位阈值"归一化到 0-1
- `affected_industries` / `affected_stocks`：直接从记录字段映射

## 6. 去重策略（L1 层）

### 6.1 L1 只做"显式重复"去重

L1 不承担语义去重（那是 L2 的职责），只处理以下三类显式重复：

1. **L1a 同一 ft_news 被重复抽取**：用 `source_table:pk` 作为幂等键，DB 唯一索引兜底。
2. **L1b 同一事件在短窗口内被规则多次触发**：如同一天内北向资金连续多次越过 95 分位，只记第一次，后续合并进 `evidence_refs`。
3. **L1a + L1b 双路径重叠**：新闻里提到"北向净流入 150 亿"和规则触发的北向事件可能是同一个事实。通过 `dedup_key` 发现后，保留规则版本（可信度更高），把新闻版本的 evidence 并入。

### 6.2 dedup_key 的构造

`dedup_key = hash(event_subtype + 主体ID + 窗口时段)`

- 窗口时段用 1 小时对齐（日频数据用日对齐）；
- 主体 ID：股票事件用股票代码，行业事件用行业代码，宏观事件用指标代码。

入库前先查 `dedup_key` 是否已存在：存在则 UPDATE `evidence_refs` 追加，不存在则 INSERT。

## 7. 质量监控

### 7.1 关键指标

| 指标 | 目标值 | 告警条件 |
|---|---|---|
| L1a 分类置信度均值 | > 0.8 | 连续 3 批 < 0.7 |
| L1a JSON 解析成功率 | > 99% | 单日 < 97% |
| L1a prompt cache 命中率 | > 85% | 单日 < 70% |
| L1b 规则触发频率 | 与历史均值偏差 < 2σ | 某规则 24h 无触发或触发爆炸 |
| 事件 evidence_refs 完整率 | = 100% | 出现空数组 |
| 端到端延迟 P95 | < 5 min | > 10 min |

### 7.2 异常旗标汇总

所有异常记录在 `quality_flags` 字段，便于 L2 过滤和人工复核：

- `classify_fallback` · `json_repaired` · `json_repair_failed`
- `low_confidence` · `schema_violation` · `missing_evidence`
- `rule_threshold_stale`（阈值表 > 24h 未刷新）

## 8. Jettask 任务编排

### 8.1 任务拆分

| Task 名称 | 触发 | 输入 | 输出 | 频率 |
|---|---|---|---|---|
| `l1a_classify_news` | ft_news 新增 | 未分类新闻 | 分类结果写入桶 | 3 min |
| `l1a_extract_bucket` | 桶触发（攒满/超时） | 同类新闻批次 | 事件写入 ft_events | 事件驱动 |
| `l1b_detect_fund_flow` | ft_market_flow 更新后 | 增量记录 | 事件写入 ft_events | 5 min |
| `l1b_detect_macro` | ft_macro_indicators 更新后 | 增量记录 | 事件写入 ft_events | 1 h |
| `l1b_detect_sentiment` | ft_sentiment 更新后 | 增量记录 | 事件写入 ft_events | 15 min |
| `l1b_detect_market` | ft_market_cache 更新后 | 增量记录 | 事件写入 ft_events | 1 min |
| `l1_refresh_thresholds` | 每日定时 | 历史数据 | 写入 ft_rule_thresholds | 每日 0:30 |
| `l1_quality_monitor` | 每小时 | ft_events 快照 | 监控指标 + 告警 | 1 h |

### 8.2 任务依赖关系

- `l1a_classify_news` 和 `l1a_extract_bucket` 通过桶（Redis list）解耦，不强依赖。
- `l1b_*` 任务的上游是现有的 `agg_*` 任务；在 jettask 里声明 `depends_on`，保证数据就绪后再评估规则。
- `l1_refresh_thresholds` 是所有 L1b 任务的前置，启动时检查阈值表时效性。

### 8.3 重试与幂等

- 所有任务幂等：用 `source_table:pk + extractor_version` 做幂等键。
- 失败重试：LLM 相关最多 3 次（指数退避 30s/2min/10min），规则相关最多 2 次。
- 连续失败触发告警但不阻塞：L1a 挂了 L1b 继续，反之亦然。

## 9. 风险与注意事项

1. **Prompt cache 失效风险**：system prompt 里任何一个字节的变化都会让 cache 全部 miss。修改 prompt 必须走版本化流程：改动 → 写入新版本号 → 双跑观察 1 天 → 切换主版本。
2. **分类偏差放大**：分类错了，抽取用的是错类别的 prompt，质量会断崖下降。一定要监控"各类别分布"，偏差过大立即人工复核。
3. **阈值漂移**：95 分位阈值在牛市会被拉高，导致熊市时规则触发过敏；反之亦然。每日刷新阈值是必须的。
4. **双路径重复入库**：一定要在 insert 前查 dedup_key，否则 ft_events 会被 L1a/L1b 各写一份相同事实的记录。
5. **LLM 长度失控**：批内 16 条 × 每条摘要 500 字 = 8000 字输入，再加 system prompt，接近上下文上限。必须对单条摘要截断到 500 字。
6. **事件时间 vs 抓取时间**：`event_time` 必须用新闻发布时间/指标公布时间，而不是 L1 处理时间。L2 聚合依赖 event_time 做时序对齐，搞错会直接破坏下游。
7. **冷启动数据不足**：阈值表需要至少 90 天数据；上线初期先用预设保守阈值（历史同类项目的经验值），等数据积累后切换。
8. **ft_news 同一条被多次更新**：如果 collect_news 阶段 content 会被补全更新，需要在 `processed_at` 之外再记一个 `content_hash`，内容变化时重新抽取。
