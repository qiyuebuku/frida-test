## 1. 需求分析

### 1.1 L2 在整体架构中的定位

L2 是整条流水线的"语义聚合层"，负责把 L1 抽出的**散点事件**重新组织成**可被决策层消费的信号单元**。它在五层架构中的作用可以用一句话概括：

> **L1 回答"发生了什么单个事件"，L2 回答"这些事件构成了什么主线"。**

从数据流上看：

```
L1  ft_events（~300~1000 条/天，散点、可能重复、彼此孤立）
      ↓ 语义去重 → 事件簇
      ↓ 跨源合并 → 统一事实
      ↓ 主题聚类 → EventStream
      ↓ 横向连接 → 资金/情绪/过热
      ↓ 势能计算 → strength/momentum/duration
      ↓ 时间衰减 → novelty 折损
L2  ft_event_streams（~20~80 条活跃主线，已打包、已评分、可排序）
      ↓
L3  硬过滤 → 加权打分 → 阈值触发 → ft_trade_signals
```

L3 不应该直接去读 ft_events 做聚合——那等于把同样的工作重复两遍，而且会让"主线"的概念漂移。**L2 产出的 EventStream 是 L3 打分的"原子输入"**，L3 只负责"这条主线是否满足入场条件 + 按加权打分排序"。

### 1.2 核心约束

| 约束 | 说明 |
|---|---|
| **延迟约束** | L1 → L2 聚合延迟 ≤ 10 分钟（盘中），≤ 30 分钟（盘后），否则 L3 信号滞后无法交易 |
| **幂等约束** | 同一事件 ID 不能被重复计入两条 EventStream，或反复在"活跃 → 关闭 → 活跃"之间抖动 |
| **可解释约束** | 每条 EventStream 必须能回溯到其底层事件列表（event_ids）和计算路径（reason_chain） |
| **增量约束** | 每次调度只处理"新增/变更事件"，不能每次全量重建（现在的实现是全量删+重建，必须改掉） |
| **资源约束** | embedding 余弦相似度是 O(N×M)，单次调度事件数需控制在 1000 以内；超出时走分桶或粗粒度过滤 |
| **概念稳定约束** | 同一条主线（例如"固态电池产业化"）在多轮调度中 stream_id 必须保持不变，否则下游 trade_signals 无法追踪 |

### 1.3 复杂度判定

**复杂度**：🔴 **复杂**（跨多模块、涉及算法选型、涉及状态机、有性能约束）

判定理由：
1. 涉及 **embedding 语义计算 + 图聚类 + 状态机 + 时间衰减** 多种机制的组合
2. 需要与 **ft_sentiment / ft_market_flow / ft_market_cache** 三张辅助信号表做横向连接
3. 需要替换现有 `get_leading_theme`（基于涨停原因）并设计**并行过渡路径**
4. 有**稳定 ID 绑定**需求：同一主线跨次调度 stream_id 不变（簇追踪问题）
5. 需要**增量更新**而非全量重建

因此拆 6 个可独立验证的实现步骤，每步都能单独跑起来并输出中间产物用于验收。

## 2. 整体设计

### 2.1 L2 的三个核心动作

L2 的本质是 **"三次收敛"**：

```
散点事件（~500条）
   ↓ ① 去重：语义相似的事件合并为事件簇
事件簇（~200个）
   ↓ ② 聚类：同主题的事件簇合并为 EventStream
EventStream（~20~80 条活跃主线）
   ↓ ③ 势能计算：为每条 EventStream 算 strength/momentum/duration
可排序的主线清单
```

这三次收敛是**递进的**，不能合并成一步：

- 去重是"识别同一事件的不同表达"，粒度最细（句子级）
- 聚类是"识别同一主题下的多个事件"，粒度中等（主题级）
- 势能计算是"评估主线的热度和方向"，粒度最粗（主线级）

如果跳过去重直接聚类，一条主线里会混入大量"同一则新闻的不同标题"，strength 会被虚假抬高；如果跳过聚类直接算势能，只能得到"单事件强度"而非"主题级强度"，决策层拿到的就是 L1 原样，等于白做一层。

### 2.2 数据流总览

```
┌─────────────────────────────────────────────────────┐
│  Input: ft_events (L1)                              │
│  - 最近 72h 新增/变更事件                            │
│  - 包含 embedding(bytea) + affected_* + sentiment   │
└──────────────────┬──────────────────────────────────┘
                   │
                   ↓  Step ① 语义去重
┌─────────────────────────────────────────────────────┐
│  事件簇（EventCluster · 内存中间态）                  │
│  - cluster_id: uuid                                 │
│  - primary_event_id: 代表事件                        │
│  - supporting_event_ids: [e2, e3, ...]              │
│  - merged_embedding: 簇心向量                        │
│  - 写回 ft_events.cluster_id 字段                    │
└──────────────────┬──────────────────────────────────┘
                   │
                   ↓  Step ② 主题聚类
┌─────────────────────────────────────────────────────┐
│  EventStream 候选（内存中间态）                       │
│  - 每个候选对应 1..N 个事件簇                         │
│  - 候选间通过 stream_id 稳定绑定机制映射到已有主线    │
└──────────────────┬──────────────────────────────────┘
                   │
                   ↓  Step ③ 横向连接 + 势能计算
┌─────────────────────────────────────────────────────┐
│  Output: ft_event_streams (L2)                      │
│  - topic/strength/momentum/duration/sentiment       │
│  - capital_flow/sentiment_by_code/is_overheated     │
│  - state: emerging/fermenting/peak/decaying/closed  │
│  - reason_chain: 决策可追溯链                        │
└─────────────────────────────────────────────────────┘
```

### 2.3 关键技术选型

| 决策点 | 选择 | 放弃的替代方案 | 理由 |
|---|---|---|---|
| 去重算法 | **embedding 相似度 + 实体重叠 + 时间窗口** 三元组合 | ① 纯关键词匹配 ② 纯 embedding ③ LLM 两两比对 | 关键词漏语义同义词（"涨价"vs"调价"）；纯 embedding 会把相反方向事件聚在一起；LLM 成本过高 |
| 聚类算法 | **graphify 社区发现 + 自研时间衰减/状态持久化** | ① 纯 KMeans（需预设 K）② 纯贪心（现有实现，丢失跨行业） ③ 纯 DBSCAN | 主线数量动态、跨行业、需要时间状态 → 社区发现最合适；graphify 提供 build/cluster，时间/状态自研 |
| 簇心向量 | **加权平均**（按事件 strength × novelty 加权） | ① 简单均值 ② 取最强事件的向量 | 弱事件会稀释簇心；单事件向量脆弱；加权平均稳定且反映主导事件 |
| Stream ID 稳定性 | **基于 topic slug + 前代匹配**两阶段绑定 | ① UUID 每次重发 ② 基于时间戳 | UUID 不稳定导致下游追踪断裂；slug 直接用语义标识，前代匹配处理主线漂移 |
| 增量更新 | **新增事件触发的局部重算 + 每 6h 全量校准** | ① 每次全量 ② 纯增量 | 纯全量无法支撑 5min 调度；纯增量会累积漂移；定期校准兜底 |
| 势能公式 | **指数时间衰减 + 对数压缩** | ① 线性衰减 ② 原始累加 | 线性衰减对突发事件不敏感；原始累加被老事件主导 |
| Novelty 衰减 | **事件级衰减（event.novelty × decay）** | ① 流级衰减 ② 不衰减 | 流级衰减把新老事件一视同仁；不衰减会让老题材反复发酵时被高估 |

## 3. 语义去重策略（Step ①）

### 3.1 L1 去重 vs L2 去重的分工

L1 的去重是**显式去重**：基于 `dedup_key = hash(event_subtype + 主体ID + 窗口时段)`，只能识别"同一主体 + 同一子类型 + 同一时间桶"的完全重复，例如：
- 同一篇财经快讯被不同渠道转发两次 → L1 识别并丢弃其一
- 同一公司同一天发布相同公告 → L1 识别并合并

L1 漏掉的，L2 必须补回来：

| 场景 | L1 识别？ | L2 必须识别 |
|---|---|---|
| 新华社原稿 + 财联社改写（不同 source，语义相同） | ❌ | ✅ |
| 央行公告（文本事件） + M2 数据发布（数值事件）指向同一事实 | ❌ | ✅ |
| "宁德时代与比亚迪签约" 被拆成两条事件（各以一方为主体） | ❌ | ✅ |
| 同一政策在早盘、午盘被两次点评（时间相近、角度不同） | ❌ | ✅ |

### 3.2 语义去重的三元组合判定

一对事件 `(ei, ej)` 是否视为同一事件，**同时满足**以下三个条件：

**条件 A · 向量相似度**：
```
cosine(ei.embedding, ej.embedding) ≥ 0.85
```
阈值建议：0.85（比聚类阈值 0.70 高一档，表示"几乎相同的表述"）。

**条件 B · 实体重叠**：
```
jaccard(ei.主体集合, ej.主体集合) ≥ 0.5
或
|ei.affected_stocks ∩ ej.affected_stocks| ≥ 1 且 role='primary'
```
主体集合定义：`affected_stocks(role='primary') ∪ affected_industries ∪ affected_concepts`。
至少要有一个主要主体重叠，防止"两条语义相似但说的是不同公司"的事件被误合。

**条件 C · 时间窗口**：
```
|ei.event_time - ej.event_time| ≤ 6 hours
```
时间窗口设为 6h（同一事件的多源报道通常在数小时内完成）。超过 6h 视为"续报"或"新进展"，应保留为独立事件。

### 3.3 跨源合并：文本事件 + 数值事件指向同一事实

L1a（文本）和 L1b（数值）的事件有时指向同一个经济事实：

| 文本事件（L1a） | 数值事件（L1b） | 判定 |
|---|---|---|
| "央行下调 MLF 利率 10bp" | macro_data: MLF 利率变化 -10bp | 同一事实 |
| "北向资金净流入 120 亿" | fund_flow: 北向净流入异常 | 同一事实 |
| "宁德时代一季报超预期" | price_action: 300750 涨停 | 相关但不同 |

跨源合并的判定规则（在 3.2 的基础上加一条）：

**条件 D · 跨源补充**：
```
if ei.source_type != ej.source_type:
    # 文本 + 数值
    要求主体重叠 ≥ 1（stock/industry/concept/macro_indicator）
    且 时间窗口 ≤ 2 hours（数值事件和文本报道的 lag 一般很短）
    且 方向一致（direction 相同或数值符号与文本方向一致）
```

合并后，**保留文本事件为 primary**（可解释性更好），数值事件作为 `supporting_event_ids` 存入 cluster。

### 3.4 事件簇（EventCluster）的概念

事件簇是 L2 内部的**中间态**，不持久化到独立表，但要把 `cluster_id` 写回 `ft_events.cluster_id`（需 L1 Schema 补充该字段）。

- 一个 EventCluster 包含 1..N 个 ft_events 行
- `primary_event_id`：代表事件（选择 strength × novelty × certainty 最大者）
- `supporting_event_ids`：其他同簇事件
- `merged_embedding`：按 strength × novelty 加权平均后归一化
- `merged_affected_*`：并集
- `merged_sentiment`：按 strength 加权平均

L3 打分时，策略是：
- 从 ft_event_streams 取主线
- 需要展开细节时，通过 stream.event_ids → ft_events → cluster_id 聚合出事件簇
- 展示给用户时，`supporting_news` 字段用 supporting_event_ids 填充

### 3.5 去重的计算优化

朴素两两比对是 O(N²)，500 事件 → 125000 次比对，即便每次 2ms 也要 4 分钟，不可接受。优化策略：

**预过滤 1 · 时间分桶**：把 72h 窗口按 6h 切 12 个桶，只比对相邻桶内的事件对。事件数摊薄为 O(N²/12)。

**预过滤 2 · 实体索引**：为每个事件建倒排索引 `stock_code → [event_ids]` / `industry_code → [event_ids]`，两两比对只发生在"至少共享一个主体"的事件对之间，进一步剪枝 80%+。

**预过滤 3 · embedding 粗筛**：可选的 ANN（HNSW）召回 topK=20 候选，再做精细相似度（跳过完全无关对）。N < 1000 时可不用，直接矩阵乘法（numpy/torch 几十毫秒搞定）。

## 4. EventStream 聚类算法（Step ②）

### 4.1 为什么不能用现有的 industry 分组+贪心聚类

现有 `EventStreamAggregator` 的问题：

| 问题 | 后果 |
|---|---|
| 先按 industry 分组再聚类 | 跨行业主线被分裂。例："AI+算力+数据中心"会被拆成计算机/通信/电子三个 stream |
| 一个事件 affected_industries 有多个行业 → 复制到多个组 | 事件计数重复，strength 被虚高 |
| 贪心聚类（第一个超阈值就合并） | 结果依赖遍历顺序，不稳定 |
| 每次全量删除 active streams 重建 | stream_id 不稳定，下游追踪断裂 |
| 无时间衰减 | 昨天的事件和一周前的事件等权，老题材主导 |

### 4.2 新聚类算法：图社区发现 + 稳定绑定

**步骤 1：构建事件簇相似度图**

节点：Step ① 产出的所有活跃事件簇（覆盖最近 72h，且 last_event_time ≥ now-48h）。

边：两个簇之间的相似度分数 `w(ci, cj)`，公式：

```
w(ci, cj) = 0.55 × cos_sim(ci.embedding, cj.embedding)
          + 0.25 × entity_overlap(ci, cj)
          + 0.15 × industry_overlap(ci, cj)
          + 0.05 × time_proximity(ci, cj)
```

其中：
- `cos_sim`：簇心向量余弦相似度（0~1）
- `entity_overlap`：股票/概念主体的 Jaccard 相似度（0~1）
- `industry_overlap`：申万二级行业的 Jaccard 相似度（0~1）
- `time_proximity`：时间邻近度，`exp(-|tc_i - tc_j| / 72h)`（0~1）

**阈值建边**：w ≥ 0.60 才建边（弱相似不应构成主题）。高于 0.95 视为应该在 Step ① 去重阶段合并，记录告警。

**步骤 2：调用 graphify.cluster 做社区发现**

使用 Louvain 算法（graphify 提供的 `cluster` 函数，默认算法）：
- 输入：上一步的相似度图
- 输出：每个节点的社区 ID

社区发现 vs KMeans/DBSCAN 的优势：
- 不需要预设 K（主线数量是动态的）
- 模块度优化天然处理"核心-边缘"结构（大主题套小主题）
- 对边权重敏感，反映真实语义结构

**步骤 3：社区后处理**
- **最小社区尺寸**：< 2 个事件簇的社区视为"孤立事件"，独立成 stream（state='emerging'）
- **巨型社区拆分**：> 15 个事件簇的社区尝试二阶聚类，用更高阈值（w ≥ 0.75）重做，防止"泛主题"污染
- **噪声节点**：模块度贡献 < 阈值（建议 0.01）的节点踢出，单独成 stream

### 4.3 graphify 集成边界

graphify 在 L2 中的角色是**纯函数工具**，严格遵守以下边界：

| L2 自研 | graphify 提供 |
|---|---|
| 数据模型（ft_event_streams） | ❌ 不用它 |
| 时间衰减、novelty 折损 | ❌ 不用它 |
| 状态机（emerging → ... → closed） | ❌ 不用它 |
| Stream ID 稳定绑定 | ❌ 不用它 |
| 相似度矩阵 → 图结构 | ✅ `build()` |
| 图合法性检查 | ✅ `validate()` |
| Louvain 社区发现 | ✅ `cluster()` |

**失败兜底**：如果 graphify.cluster 报错或返回空结果（极端情况），降级到贪心聚类（当前实现），告警但不中断任务。

### 4.4 主题命名与 topic slug 生成

每条社区输出后需要一个**人类可读的 topic 名称**，流程：

1. **候选关键词抽取**：从社区内所有事件的 title + summary 提取高频 n-gram（去停用词、去公司名）
2. **LLM 命名**（通过 claude-planner tmux API）：把候选关键词 + 代表事件的 title 传给 LLM，返回一个 ≤ 12 字的 topic（例："固态电池产业化"、"AI 算力基建"）
3. **slug 生成**：topic → pinyin 或 hash 前 8 位，作为 stream 的逻辑键

LLM 命名失败时，fallback 到"候选关键词 top3 拼接"。

### 4.5 Stream ID 稳定绑定机制

这是保证 L2 下游可追踪的关键。当本次调度产出一批候选 stream 时，**不直接分配新 ID**，而是先尝试与上一代 active stream 做匹配：

**匹配规则**：
- 簇重叠率 `|new.cluster_ids ∩ old.cluster_ids| / |old.cluster_ids| ≥ 0.4` → 匹配成功
- 或 topic slug 相同 → 匹配成功

**匹配结果处理**：
| 情况 | 处理 |
|---|---|
| 匹配到 1 个旧 stream | 继承 stream_id，更新内容（event_ids 合并、时间戳刷新） |
| 匹配到多个旧 stream（主线合并） | 继承最早创建的 stream_id，其他旧 stream 标记 `state='merged'`，记录 `merged_into` 字段 |
| 未匹配到（新主线） | 分配新 stream_id，state='emerging' |
| 旧 stream 未匹配到任何新候选 | 标记 `state='decaying'`，若 last_event_at > 72h 前则进一步 'closed' |

**主线分裂处理**：
如果一个旧 stream 的 cluster_ids 被拆到两个新候选中（重叠率都 > 0.3），判为"主题分化"。保留重叠率最高的为主线，另一个标记 `state='emerging'` 并设置 `parent_stream_id` 指向旧主线。

## 5. 主线势能计算（Step ③）

### 5.1 指标体系

每条 EventStream 输出以下势能指标，供 L3 加权打分使用：

| 指标 | 含义 | 值域 | 典型用途 |
|---|---|---|---|
| `strength` | 综合强度（累计权重） | 0~10 | 强度排序、入场阈值 |
| `strength_24h` | 最近 24h 强度 | 0~10 | 短线触发 |
| `strength_7d` | 最近 7d 强度 | 0~10 | 中线背景 |
| `momentum` | 加速度（24h 相对 7d 的升温比） | -1~+∞ | 升温/降温判定 |
| `momentum_state` | 离散态 | rising/stable/falling | 状态机输入 |
| `duration_days` | 首次到最新事件的天数 | 0~∞ | 成熟度 |
| `avg_sentiment` | 事件情感加权平均 | -1~+1 | 方向过滤 |
| `novelty_score` | 流级新颖度（事件级衰减后取均值） | 0~1 | 过热题材降权 |
| `direction_confidence` | 情感一致性 | 0~1 | 低置信度时降权 |

### 5.2 Strength 公式

**事件级权重**（每条事件的贡献度）：

```
weight(e, t) = e.strength
             × e.certainty
             × e.novelty
             × decay(t - e.event_time)
```

其中时间衰减函数：
```
decay(Δt) = exp(-Δt / τ)
```
- τ（半衰期相关）：盘中 τ = 12h，盘后 τ = 48h（盘后事件需要更长发酵期）
- Δt：事件距当前调度时刻的小时数

**流级强度**（对所有成员事件求和并对数压缩）：

```
strength_raw = Σ weight(e, now) for e in stream.events
strength = log(1 + strength_raw) × k_norm
```

其中 `k_norm` 是归一化系数，使得一条典型热门主线的 strength 落在 3~7 之间（便于 L3 设计阈值）。建议 k_norm = 2.0，冷启动时先人工校准。

**为什么用对数压缩**：
- 线性累加会让"百条平庸新闻"压过"一条重磅政策"
- 对数压缩后，强度差异从量级变为等级，更符合投研直觉

### 5.3 Momentum 公式

```
momentum = strength_24h / (strength_7d / 7 + ε)
```

其中 ε = 0.1 防除零。

离散化：
- `momentum ≥ 2.0` → `rising`（升温：24h 强度是 7 日日均的 2 倍以上）
- `0.5 < momentum < 2.0` → `stable`
- `momentum ≤ 0.5` → `falling`（降温）

边界情形：
- `strength_7d < 0.5` 的新主线（stream age < 1d）：momentum 直接标为 `rising`，跳过公式计算
- `strength_24h == 0` 的休眠主线：momentum = 0，state 推进到 decaying

### 5.4 Duration 与 State 状态机

`duration_days = (last_event_at - first_event_at) / 86400`

State 状态机（取代现有过于简单的实现）：

```
           ┌─────────┐
           │emerging │ ← 新创建（event_count ≤ 3 或 duration ≤ 1d）
           └────┬────┘
                │ event_count > 3 且 momentum=rising 且 duration > 1d
                ↓
           ┌────────────┐
           │ fermenting │ ← 成长中
           └────┬───────┘
                │ strength 达到近 7d 峰值 且 momentum ≥ 1.5
                ↓
           ┌─────────┐
           │  peak   │ ← 顶峰（警示：顶峰后需降权）
           └────┬────┘
                │ momentum=falling 连续两次调度
                ↓
           ┌──────────┐
           │ decaying │
           └────┬─────┘
                │ last_event_at > 72h 前
                ↓
           ┌─────────┐
           │ closed  │ → 不再更新，保留归档
           └─────────┘

特殊态：
- merged → 被合并到其他 stream（merged_into 字段指向）
- split  → 被分裂（parent_stream_id 字段，新 stream 从此派生）
```

**防抖机制**：状态转移需要**连续两次调度**满足条件才推进，防止在边界值反复抖动。由 `state_stable_count` 字段记录当前状态已维持的调度次数。

### 5.5 Novelty 流级衰减

**核心原则**：novelty 是事件级属性（L1 产出），流级 novelty 是成员事件 novelty 的加权平均。

```
stream.novelty_score = Σ (e.novelty × weight(e, now)) / Σ weight(e, now)
```

为什么不对流整体做衰减？因为同一主线可能反复出现：
- 如果流级衰减，第二次发酵时会被误判为"老题材直接丢弃"
- 事件级衰减 + 流级加权平均 → 每个事件各自按时间衰减 novelty，新事件自然贡献高权重，老事件权重低但不归零

**过热题材识别**（非直接丢弃，而是降权）：
- `stream.novelty_score < 0.3` 且 `state = fermenting/peak` → 标记 `overheat_by_novelty = true`
- L3 在打分时对此类 stream 加折损系数（例如 × 0.7）

## 6. 与辅助信号的横向连接（Step ③ 的一部分）

### 6.1 横向连接的目的

L2 独立产出的 EventStream 只回答了"新闻层面的主线"，但交易决策还需要：
- **资金是不是真的流进来了？**（资金流验证）
- **市场情绪是不是配合？**（情绪验证）
- **是不是过热了？**（风险提示）

因此每条 stream 在落库前都要 enrich 四个辅助信号字段。

### 6.2 四个横向信号的接入

**信号 1 · 资金流（capital_flow）**

数据源：`ft_market_flow` 表（已有，由 collect_fund_flow 5min 任务维护）。

映射逻辑：
```
for industry in stream.primary_industries[:3]:
    flow = query ft_market_flow WHERE industry_code = industry AND date = today
    累计净流入、主力资金占比

stream.capital_flow = {
    "net_inflow": 累计净流入（亿元）,
    "net_inflow_ratio": 净流入 / 成交额,
    "rank_in_sw1": 今日申万一级排名,
    "updated_at": ...
}
```

如果 stream 没有行业维度（纯宏观主线），capital_flow 记录北向/两融全市场数据。

**信号 2 · 个股情绪（sentiment_by_code）**

数据源：`ft_sentiment_signal`（已有）或调用 `get_sentiment_score(code)`。

映射逻辑：
```
for stock in stream.top_affected_stocks[:10]:
    sentiment = get_sentiment_score(stock.code)

stream.sentiment_by_code = {
    "300750": {"score": 0.73, "label": "bullish"},
    "002594": {"score": 0.55, "label": "neutral"},
    ...
}
```

top_affected_stocks 按事件中出现频次 × 事件 strength 排序，只取前 10（防止污染）。

**信号 3 · 过热标记（is_overheated）**

数据源：`get_overheat_set()`（已有，3 日涨幅 > 5% 的集合）。

映射逻辑：
```
overheat_stocks = stream.top_affected_stocks ∩ get_overheat_set('stock')
overheat_industries = stream.primary_industries ∩ get_overheat_set('industry')

stream.is_overheated = (
    len(overheat_stocks) / len(stream.top_affected_stocks) > 0.5
    or overheat_industries 非空
    or stream.novelty_score < 0.3
)
stream.overheat_reason = 具体触发原因（字符串）
```

is_overheated 不直接否决 stream，而是交给 L3 做加权降权。

**信号 4 · 市场温度（market_temperature）**

数据源：`get_market_temperature()`（已有，0-100 分）。

这个是全局信号，不单独存在每条 stream 上，而是 L2 调度结束时落到 `ft_event_streams_meta` 或 Redis，L3 调度时统一读取。作用：市场温度 < 30（冷清）时，rising 主线要求更高阈值才触发交易。

### 6.3 刷新策略

横向信号的实时性与事件不同：
- 资金流每 5min 刷新一次（盘中）
- 情绪信号每 30min 刷新
- 过热集合每天盘后重算

L2 任务调度时**按最近可用值取样**，不主动等待刷新。每条 stream 记录 `enrichment_time` 标注横向信号的时间戳，L3 消费时自行判断是否过期（> 15min 即视为 stale）。

## 7. EventStream Schema 升级

### 7.1 现有表的局限与升级方向

现有 `ft_event_streams` 只有 9 个核心字段（industry/state/momentum/event_ids/counts/strengths/sentiments/timestamps），远不够支撑 L2 的完整产出。需要扩展约 15 个字段。

### 7.2 升级后的完整 Schema（概念版）

```sql
CREATE TABLE ft_event_streams (
    -- ===== 身份 =====

    -- ===== 势能（新增完整指标）=====

    strength_24h            double precision DEFAULT 0,
    strength_7d             double precision DEFAULT 0,
    momentum                double precision DEFAULT 0, -- 数值形式
    momentum_state          varchar(16) DEFAULT 'stable', -- rising/stable/falling
    duration_days           double precision DEFAULT 0,
    avg_sentiment           double precision DEFAULT 0,
    direction_confidence    double precision DEFAULT 0, -- 情感一致性
    novelty_score           double precision DEFAULT 1.0,

    -- ===== 状态机 =====

        -- emerging/fermenting/peak/decaying/closed/merged/split

```

## 8. Jettask 任务编排

### 8.1 任务拆分

L2 的完整流程切分为 **3 个 jettask 任务**，职责分明、可独立重跑：

**任务 1 · `l2_dedup` · 语义去重**
- 触发频率：**5 min**（盘中）/ **15 min**（盘后）
- 输入：ft_events WHERE l2_processed_at IS NULL AND created_at > now() - 72h
- 输出：回填 ft_events.cluster_id
- 幂等：按 event_id 主键更新
- 锁：Redis 分布式锁 `lock:l2:dedup`，TTL 5min

**任务 2 · `l2_aggregate_streams` · 聚类 + 势能计算**
- 触发频率：**10 min**（盘中）/ **30 min**（盘后）
- 依赖：l2_dedup 完成
- 输入：ft_events WHERE cluster_id IS NOT NULL AND event_time > now() - 168h
- 输出：upsert ft_event_streams + 回填 ft_events.stream_id
- 锁：`lock:l2:aggregate`，TTL 15min
- 调用 graphify.cluster 可能有 10~30s 耗时

**任务 3 · `l2_enrich_streams` · 横向信号补充**
- 触发频率：**5 min**（跟随资金流刷新节奏）
- 依赖：l2_aggregate_streams 完成
- 输入：ft_event_streams WHERE state IN ('emerging','fermenting','peak')
- 输出：更新 capital_flow/sentiment_by_code/is_overheated/enrichment_time
- 锁：`lock:l2:enrich`

### 8.2 依赖与调度拓扑

```
L1a/L1b 完成事件抽取
          ↓
     l2_dedup（5min）
          ↓
l2_aggregate_streams（10min）
          ↓
l2_enrich_streams（5min）
          ↓
      L3 打分
```

**依赖检查**：l2_aggregate_streams 启动前检查 `l2_dedup.last_success_at > now() - 10min`，否则跳过本次并告警。

**盘后全量校准任务 · `l2_full_rebuild`**
- 触发频率：每天 **17:00** 一次
- 作用：扫描最近 7 天事件，全量重建活跃 streams，纠正增量漂移
- 特殊：允许 stream_id 重新匹配/合并

### 8.3 幂等与并发控制

每个任务在入口：
1. 获取 Redis 分布式锁
2. 记录 task_run（表 `ft_task_runs`）
3. 检查前置任务最新成功时间
4. 执行业务逻辑
5. 释放锁，更新 task_run.status

失败处理：
- 业务逻辑异常 → task_run.status='failed'，5min 后自动重试（最多 3 次）
- 锁超时 → 仅告警，不重试（避免惊群）
- graphify 异常 → 降级到贪心聚类 + 告警

## 9. Novelty 与事件生命周期（与 L1 的协作）

### 9.1 novelty 的来源与在 L2 的应用

novelty 由 L1 在抽取时计算（L1 设计方案 §X 已定义）：
- 新主题事件 → novelty ≈ 1.0
- 已有主题新进展 → novelty ≈ 0.7
- 老题材重提 → novelty ≈ 0.3

L2 不重新计算 novelty，但会**在势能计算中使用它**：
- 事件权重 = strength × certainty × **novelty** × decay
- 流级 novelty_score = 成员事件的加权平均
- novelty_score < 0.3 → overheat_by_novelty=true → L3 降权

### 9.2 老题材反复发酵的处理

典型场景：AI 题材 3 月炒过一次，6 月又来一次。

**错误做法**：直接用"该题材历史事件数"做衰减 → 第二次发酵时被误杀。

**正确做法**：
- novelty 是**事件级**，L1 在抽取每条事件时独立判断（看最近 30 天内该主题的事件密度）
- 6 月新事件的 novelty 会因"近 30d 活跃事件少" → 再次被判定为高 novelty（例如 0.8）
- 老的 3 月事件虽然在 ft_events 里，但距今 90d → decay 衰减为 0，不影响新发酵的强度

### 9.3 与 closed stream 的交互

当一个旧主线已 closed（如 3 月的 AI 主线），6 月同主题事件出现：
- Step ① 去重：不与 closed stream 的历史事件合并（时间窗口 72h 早已过）
- Step ② 聚类：closed stream 不参与稳定绑定匹配（只匹配 active streams）
- 结果：形成新的 stream_id，topic 可能复用（"AI 算力主线 · 第二轮"）

## 10. 质量监控与异常处理

### 10.1 关键指标

每次 L2 任务运行后落库到 `ft_monitoring_metrics`：

| 指标 | 含义 | 告警阈值 |
|---|---|---|
| `l2.dedup.merge_ratio` | 合并事件 / 总事件 | < 5% 或 > 50% 告警 |
| `l2.cluster.stream_count` | 活跃 stream 数 | < 5 或 > 200 告警 |
| `l2.cluster.avg_events_per_stream` | 平均事件数/stream | < 2 或 > 30 告警 |
| `l2.cluster.orphan_event_ratio` | 未聚入 stream 的孤立事件比例 | > 40% 告警 |
| `l2.binding.id_stability_ratio` | 本次 stream_id 复用率 | < 60% 告警（主线漂移异常） |
| `l2.enrich.stale_ratio` | 横向信号过期比例 | > 20% 告警 |
| `l2.latency.p95_ms` | 任务延迟 P95 | > 60s 告警 |

### 10.2 异常处理

| 异常 | 处理 |
|---|---|
| embedding 字段缺失 | 跳过该事件，记录告警，不中断任务 |
| graphify.cluster 报错 | 降级到贪心聚类 + 告警 |
| LLM topic 命名超时 | fallback 到关键词拼接 |
| 横向信号查询超时 | 使用上次缓存值，enrichment_time 不更新 |
| 数据库写冲突 | 重试 3 次，然后放弃该条 stream |
| 巨型社区（>50 事件） | 强制二阶聚类拆分，告警（可能是数据污染） |

### 10.3 可解释性：reason_chain 字段

每条 EventStream 的 `reason_chain` 记录关键计算步骤：

```
[
  {"step": "cluster", "algo": "louvain", "members": 8, "modularity": 0.42},
  {"step": "binding", "matched_old_stream": "uuid-xxx", "overlap_ratio": 0.67},
  {"step": "strength", "strength_raw": 12.3, "strength_normalized": 4.87},
  {"step": "momentum", "s24h": 6.2, "s7d": 9.8, "ratio": 4.43, "state": "rising"},
  {"step": "enrich", "capital_net_inflow": 23.5, "overheat": false},
  {"step": "state_transition", "from": "emerging", "to": "fermenting", "trigger": "event_count>3"}
]
```

L3 和用户界面都可以直接读取这个字段回答"为什么这条主线被标为 rising / 为什么 strength=4.87"。

## 11. 主线升级路径（从旧实现过渡）

### 11.1 旧 get_leading_theme 的现状

旧实现在 `sentiment.py`，基于涨停原因关键词统计：
- 数据源：`ft_sentiment`（涨跌停板块）
- 逻辑：统计当日涨停股的题材标签，取 top N

问题：
- 只能看到"已经涨停的题材"，不能识别"正在发酵但尚未涨停的主线"
- 完全依赖涨跌停数据，盘前/盘后无产出
- 无法跨行业聚合

### 11.2 并行过渡策略

不能一次性切换，否则风险大。采用**两套并行 + 互为验证**：

**阶段 1（灰度，2 周）**：
- L2 新实现产出 ft_event_streams
- 旧 get_leading_theme 继续作为独立函数
- 新增 `get_leading_theme_v2()` 调用 ft_event_streams，返回 top 5 by strength
- 两者结果并列输出，人工对比

**阶段 2（对齐验证，1 周）**：
- 每天盘后对比 v1 和 v2 的 top 5 主线
- 核心指标：
  - 重合率（jaccard）≥ 0.4 → 新旧大体一致
  - v2 发现了 v1 没有的主线 → 记录为"新增价值"
  - v1 有但 v2 没发现 → 查漏（可能是聚类阈值过紧）
- 调阈值直到重合率稳定

**阶段 3（切换）**：
- L3 决策链切换到 v2
- 旧 v1 保留为"涨停原因锚点"，专门用于**事后验证**（例如校准 momentum 定义）
- v1 不再参与决策链

### 11.3 涨停原因作为锚点验证

即便完全切到 v2，旧的"涨停原因关键词"依然有价值——它可以作为**后验校验**：

```
for stream in ft_event_streams WHERE state='peak':
    overlap = stream.primary_concepts ∩ today's 涨停原因 top concepts
    if overlap 为空:
        告警：peak 主线但涨停未响应，可能是"空头主线"或假信号
```

这个校验写到 `l2_anchor_validate` 任务（每天 15:30 盘后触发），结果落到 stream.reason_chain。

### Step 2: 语义去重（l2_dedup 任务）

**目标**：实现 §3 的去重算法，产出事件簇（cluster_id 回填 ft_events）。

**涉及文件**：
- `src/domain/extraction/services/l2/dedup.py`（新建）— 去重算法主逻辑

- `src/infrastructure/persistence/repositories/event_repository.py` — 加 `batch_update_cluster_ids()`
- `src/tasks/l2_dedup_task.py`（新建）— jettask 入口

**实现要点**：
- 预过滤流水线：时间分桶（6h）→ 实体倒排索引 → embedding 粗筛
- 三元判定：cos ≥ 0.85 AND entity_overlap AND time ≤ 6h
- 跨源合并规则单独走一条分支（文本+数值、cos ≥ 0.75、time ≤ 2h、方向一致）
- cluster 产出后，按 strength×novelty×certainty 选 primary_event
- 回填 ft_events.cluster_id + l2_processed_at
- Redis 锁防止并发
- 所有已处理事件标记 l2_processed_at，下次调度只处理新事件

**易错点**：
- embedding 存储是 bytea，读出后要先 `np.frombuffer(...)` 再归一化
- jaccard 计算空集时注意除零（两边都空返回 0，不是 1）
- 批量 update 要用 `WHERE event_id = ANY(...)` 而非 loop update

**测试用例**：

| 用例 | 输入 | 预期 |
|---|---|---|
| 完全相同事件 | 两条 L1 事件 title 完全一样、主体相同、时间差 10min | 合并到同一簇 |
| 语义改写 | "央行降准" vs "央行下调存款准备金率"（实体相同、时间差 1h） | 合并 |
| 相反方向 | "某药获批" vs "某药被拒"（cos 可能 0.9 但 direction 相反） | **不合并**（direction 不一致时加硬条件） |
| 跨源合并 | 文本"MLF 降 10bp" + 数值"MLF -10bp"（30min 差） | 合并，primary=文本 |
| 时间超窗 | 相似事件间隔 8h | 不合并 |
| 孤立事件 | 没有匹配的事件 | 独立成簇（cluster 只含自己） |

**验收标准**：
- [ ] 500 事件的单次调度耗时 < 30 秒
- [ ] 合并率（merged / total）落在 10%~30% 区间（脱离此区间告警但不阻塞）
- [ ] cluster 产出后，primary_event_id 非空且 strength 最大
- [ ] 重跑同一批事件结果稳定（cluster_id 可以变但合并关系不变）

### Step 4: 势能计算 + 状态机

**目标**：实现 §5 的全部势能指标和状态机。

**涉及文件**：
- `src/domain/extraction/services/l2/momentum.py`（新建）— 势能计算
- `src/domain/extraction/services/l2/state_machine.py`（新建）— 状态机
- 扩展 `l2_aggregate_streams_task.py` — 把势能计算嵌入主流程

**实现要点**：
- decay 半衰期：τ=12h（盘中）/ τ=48h（盘后），根据 `event_time` 自动判断
- strength 公式：`log(1 + Σ weights) × k_norm`，k_norm=2.0
- strength_24h / strength_7d 用同一公式但限定时间窗口
- momentum = s24h / (s7d / 7 + 0.1)
- 状态转移**连续两次调度满足条件才推进**（state_stable_count 计数）
- reason_chain 每步落字典
- 新 stream 首次计算时 strength_7d 可能很小 → 特殊处理直接给 rising

**易错点**：
- 时间衰减要用事件的 `event_time` 而非 `created_at`（避免处理延迟影响）
- stream.state 变更要同时更新 peak_at（若进入 peak）
- 状态机转移条件要严格写全（参考 §5.4 图）
- state_stable_count 只在状态**保持**时 +1，状态转移时重置为 0

**测试用例**：

| 用例 | 输入 | 预期 |
|---|---|---|
| 单条新事件 stream | 1 个事件，event_time=now | strength > 0，momentum 跳过公式直接 rising |
| 老主线衰退 | stream 最后事件在 48h 前 | strength_24h=0，momentum=0，state → decaying |
| 状态防抖 | stream 满足 rising 但只 1 次调度 | state 不变，state_stable_count=1 |
| 状态转移 | stream 连续 2 次调度满足 fermenting 条件 | state: emerging → fermenting |
| 势能极值 | 构造一条含 20 条强事件的 stream | strength 落在 5~8，不爆表 |

**验收标准**：
- [ ] 所有指标计算无 NaN/Inf
- [ ] 状态机转移有防抖（人工构造边界值验证）
- [ ] reason_chain 步骤完整，可读
- [ ] k_norm=2.0 时，热门主线 strength 分布在 3~7（统计验证）

**完成后检查点**：跑一周数据看 strength 分布直方图，调 k_norm 使分布合理。

## 14. 风险与注意事项

### 14.1 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| embedding 质量差 → 聚类结果漂移 | stream 不稳定，用户体验差 | 必须和 L1 协同，embedding 模型变更要通知 L2 重跑全量；定期人工 review 聚类样本 |
| graphify 升级 API 不兼容 | L2 任务失败 | 锁定 graphify 版本，升级需回归测试；降级路径保留贪心聚类 |
| LLM 命名不稳定（同主题命名漂移） | topic 跨天变化，用户困惑 | topic_slug 缓存机制：同一 stream_id 的 topic 不随便改，除非稳定绑定匹配到新主线 |
| 辅助信号表 schema 变更 | capital_flow / sentiment_by_code 写入失败 | enrichment 封装 Repository 层，schema 变化只改封装层；加字段兼容性测试 |
| 跨行业主线被拆成多个 stream | 用户看到的主线碎片化 | 聚类阈值可调参数化（建议初始 0.60，后续根据数据分布校准） |

### 14.2 业务风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 新 v2 主线和旧 v1 主线差异大 | 决策层切换后策略失效 | 强制 2 周灰度，对齐验证 |
| 老题材 novelty 误杀 | 第二轮发酵被错过 | novelty 是事件级不是流级；closed stream 不参与匹配，新事件自然形成新 stream |
| 过热标记误伤好主线 | 升温主线被降权 | is_overheated 只传信号给 L3，由 L3 决定降权比例，不在 L2 直接丢弃 |
| stream 合并时下游信号断裂 | L3 记录的 stream_id 找不到 | merged_into 字段支持追溯链，L3 查询时跟随 merged_into 跳转到目标 stream |
| 盘前盘后数据断档 | stream 在非交易时段死掉 | decay τ 盘后放宽到 48h；full_rebuild 在 17:00 重新拉活老主线 |

### 14.3 运维注意事项

- 每日盘后 17:00 固定 full_rebuild 任务，监控其耗时（>15min 告警）
- ft_event_streams 增长速率监控（理论上活跃 < 100，若膨胀到 500+ 说明有 bug）
- embedding 存储占用监控（bytea 大小 × 事件数），必要时清理历史事件 embedding
- 每周人工 review 10 条典型 stream 的 reason_chain，检查算法是否按预期工作
- LLM 命名调用量监控（避免爆 tmux API 配额）
- closed stream 归档任务要和活跃任务串行，避免并发写冲突

### 14.4 与下游（L3）的接口约定

虽然 L3 是下一阶段的工作，但 L2 产出必须满足以下契约：
- L3 只读 `ft_event_streams WHERE state IN ('emerging','fermenting','peak')`
- L3 打分字段取 strength / momentum / avg_sentiment / novelty_score / is_overheated
- L3 展开明细时走 event_ids → ft_events → cluster_id 聚合
- L3 记录的 stream_id 必须可通过 merged_into 链找到最新状态
- L3 禁止直接修改 ft_event_streams（只读）
