# Tasks 启动说明

本文说明 `src/interfaces/tasks` 这一套 jettask-rs 任务系统如何启动、初始化和排查，并包含任务运行所依赖的主 API 服务。知识图谱手工验证脚本和其他调试脚本不在本文范围内。

## 1. 当前任务系统组成

| 组件 | 作用 | 是否常驻 |
|---|---|---|
| `api` | FastAPI 主服务；提供业务接口及雪球采集依赖的 `/api/spy` 外部浏览器能力 | 是 |
| `persist` | 消费 jettask `_commands` 队列，将调度注册等命令落库 | 是 |
| `scheduler` | 从数据库读取 schedule，按时间向任务队列投递消息 | 是 |
| `worker` | 消费具体业务队列并执行任务函数 | 是 |
| `trigger` | 手动向队列投递一次性任务 | 否 |

当前任务系统负责数据采集、情绪信号物化，以及新闻入库后的知识图谱高维索引增量构建。旧 `ft_events -> ft_event_streams` 事件链路已经删除；事件抽取和高维索引由知识库链路负责。

核心入口：

| 文件 | 职责 |
|---|---|
| `src/interfaces/tasks/__init__.py` | 创建 `Jettask` app、初始化 `ft_raw_data`、注册任务 router |
| `src/interfaces/tasks/collection_tasks.py` | 注册数据采集 task handler |
| `src/interfaces/tasks/knowledge_tasks.py` | 注册知识图谱高维索引 task handler |
| `src/application/services/knowledge_news_ingestion_service.py` | 新增新闻入知识图谱的应用层编排 |
| `src/interfaces/cli/main.py` | 提供 `worker` / `scheduler` / `persist` / `trigger` / `init schedules` 命令 |
| `src/interfaces/cli/schedules.py` | 定时调度配置 |

## 2. 启动前检查

进入项目目录并激活环境：

```bash
cd /home/yuyang/frida-test/.claude/skills/smart-fund-server
/home/yuyang/anaconda3/bin/conda activate frida-test
```

配置来源：

- 配置优先级：环境变量 > `.env` > `src/infrastructure/config/settings.py` 默认值。
- `REDIS_URL` 用于 jettask 队列和 Redis 锁。
- `PG_URL` 用于 jettask scheduler / persist 的数据库连接。
- `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USER` / `DB_PASSWORD` 用于业务数据库。
- `JETTASK_PREFIX` 默认是 `fund_aggregator`，不同环境不要共用同一个 prefix。
- `SERVER_HOST` / `SERVER_PORT` 是主 API 的监听地址，默认端口为 `8900`。
- `SERVICE_BASE_URL` 是 Worker 回调主 API 的地址。启用雪球采集时必须与主 API 的实际地址一致，例如 `http://127.0.0.1:8900`。

首次部署或重建环境后，先执行：

```bash
python -m src.interfaces.cli init state
```

## 3. 推荐启动顺序

### 3.1 启动主 API

```bash
python -m src.interfaces.cli api
```

主 API 是项目唯一的 HTTP 服务入口，包含交易、采集、知识库、LLM Proxy、Graph Community Explorer，也包含雪球采集用于获取 `xq_a_token` 的 `/api/spy`。浏览器按首次雪球请求懒启动，不运行在 Worker 进程中。

| 能力 | 地址 |
|---|---|
| OpenAPI 文档 | `http://127.0.0.1:8900/docs` |
| Graph Community Explorer | `http://127.0.0.1:8900/api/kg/graph-viewer` |
| Graph Community API | `http://127.0.0.1:8900/api/kg/graph-communities` |
| Browser Spy 状态 | `http://127.0.0.1:8900/api/spy/status` |
| LLM Proxy 健康检查 | `http://127.0.0.1:8900/api/llm-proxy/health` |

不要为 Graph Community Explorer 或 Browser Spy 单独启动第二个 Uvicorn 实例。它们已经注册在同一个 `main:app` 中。

默认配置下可检查：

```bash
curl http://127.0.0.1:8900/api/spy/status
```

正常结果应包含：

```json
{"available":true,"started":false}
```

`started=false` 只表示浏览器尚未被首次请求唤起，不是故障。如果 `available=false`，说明 API 所在环境缺少 Camoufox。

如果显式修改 API 端口，必须同步修改 `SERVICE_BASE_URL`，然后再启动 Worker：

```bash
export SERVICE_BASE_URL=http://127.0.0.1:8000
python -m src.interfaces.cli api --port 8000
```

### 3.2 启动 Persist

```bash
python -m src.interfaces.cli persist
```

`persist` 负责把调度注册命令落库。它不执行业务采集，但没有它时，`init schedules` 发送的调度注册命令可能不会持久化。

如果是首次部署，启动 `persist` 后再注册调度：

```bash
python -m src.interfaces.cli init schedules
```

### 3.3 启动 Scheduler

```bash
python -m src.interfaces.cli scheduler
```

### 3.4 启动 Worker

默认 worker 只消费采集和信号物化队列：

```bash
python -m src.interfaces.cli worker -c 1
```

当前默认队列来自 `src/interfaces/cli/main.py`：

```text
collect_news
collect_fund_flow
collect_market
collect_macro
collect_sentiment
materialize_sentiment_signal
```

`collect_news` 覆盖雪球快讯；`collect_sentiment` 覆盖雪球热门话题、雪球热股、股吧、涨跌停池等情绪源。

知识图谱使用独立 Worker，避免 LLM、Embedding 和 reranker 阻塞采集：

```bash
python -m src.interfaces.cli knowledge-worker --stage card -c 1
python -m src.interfaces.cli knowledge-worker --stage relation -c 1
python -m src.interfaces.cli knowledge-worker --stage graph -c 1
```

开发环境也可以用一个进程消费全部知识队列：

```bash
python -m src.interfaces.cli knowledge-worker --stage all -c 1
```

生产环境应使用三个独立进程。`graph` 阶段保持单进程低并发；代码内部还会按 `adapter_name` 获取带续租的 Redis 锁。

如果要消费指定队列，直接把队列名写在命令后面：

```bash
python -m src.interfaces.cli worker -c 1 collect_sentiment
```

## 7. 新闻入知识图谱增量链路

`collect_news` 每次完成新闻采集后，会把真实新增的 `ft_news.id` 直接投递为 jettask 消息：

```text
queue=kg_news_ingest
kwargs={"news_ids": [ft_news.id, ...], "workflow_id": "kg_news_workflow:..."}
```

`kg_news_ingest` 只处理消息体里的 `news_ids`，不扫描数据库、不维护二级 Redis Stream。处理逻辑：

1. 获取 Redis 分布式锁 `kg:news_ingest`，锁 TTL 为 3 分钟。
2. 有 `news_ids` 时获取锁失败会抛异常，让 jettask-rs 重试当前消息；不能返回成功，否则消息会被 ack。
3. 获取锁成功后，每 30 秒续租一次锁。
4. 每批最多处理 30 个 `ft_news.id`。
5. 按 ID 读取 `ft_news`，投影成金融知识图谱输入记录。
6. 调用 `KnowledgeService.compile_kg()` 写入 Evidence、Chunk、Cognitive Card、同 Chunk Relation、Relation Probe 和 Milvus 索引。
7. Card 发布完成后投递 `kg_relation_discovery`。
8. 跨 Chunk 正关系写入正式 Edge 后投递 `kg_graph_changed`。
9. Graph Worker 只加载 Edge 端点所在的受影响关系闭包，重算对应连通分量，不全量刷新所有 Community。
10. 同一 adapter 的 Community 刷新由 Redis 锁串行化，锁每 30 秒续租；失去锁时任务失败并由 jettask-rs 重试。
11. 如果批处理异常，任务异常直接抛给 jettask-rs，由框架负责重试和恢复。

如果进程崩溃，锁会在 3 分钟后自动过期，jettask-rs 会把未完成消息恢复给后续 Worker 继续处理。

## 8. 日志与常见问题

### 8.1 雪球提示 `spy 访问雪球失败`

典型日志：

```text
xq_a_token 不存在，让 spy 访问雪球首页...
spy 访问雪球失败: All connection attempts failed
```

该错误表示 Worker 无法连接 `SERVICE_BASE_URL/api/spy`，不代表雪球公网不可访问。依次检查：

```bash
# 1. 主 API 是否监听在配置端口
ss -ltnp | grep 8900

# 2. Spy 路由是否可访问
curl http://127.0.0.1:8900/api/spy/status

# 3. SERVICE_BASE_URL 是否与实际端口一致
grep '^SERVICE_BASE_URL=' .env
```

只启动 `worker`、`scheduler` 和 `persist`，但没有启动 `api` 时，雪球 Cookie 初始化必然失败。首次成功访问雪球后，`XueqiuClient` 会在进程内缓存 Cookie 一小时；并发采集请求会等待同一次初始化，不会重复拉起浏览器。

### 8.2 `ft_raw_data` 分区初始化

Worker 进程不经过 FastAPI lifespan，所以 `src/interfaces/tasks/__init__.py` 会在导入时执行 `raw_data.init_raw_data_tables()`。

正常日志示例：

```text
ft_raw_data 分区已通过受控函数初始化
```

如果出现 `no partition of relation "ft_raw_data" found for row`，说明当前月份分区缺失，或数据库缺少 `public.ensure_ft_raw_data_partition(int, int)` 受控函数执行权限。

### 8.3 jettask 队列表分区初始化

jettask-rs 的持久化表使用月分区。`persist` 启动前会检查并初始化当前月份前后若干个月的分区。

当前会检查的框架表：

- `tasks`：按 `trigger_time` 分区。
- `task_runs`：按 `trigger_time` 分区。
- `task_metrics_minute`：按 `time_bucket` 分区。
- `task_runs_metrics_minute`：按 `time_bucket` 分区。

## 9. 历史回填与停机断档追赶

### 9.1 Worker 为什么默认只跑增量

Worker 每次启动都会读取共享数据库中的 `ft_collection_state`。已有 source 如果处于 `incremental`，
就从原 checkpoint 继续，不会因为进程重启而重新全量抓取。禁止通过 `init state --reset` 获取历史数据，
该命令会同时重置所有 source。

### 9.2 查看可回填的数据源

```bash
python -m src.interfaces.cli collection backfill-sources
python -m src.interfaces.cli collection backfill-sources --aggregator news
```

当前受控回填范围：

| aggregator | 支持范围 |
|---|---|
| `news` | 所有新闻 source |
| `macro` | 所有宏观 source |
| `fund_flow` | 仅 `northbound` |
| `market` | 不支持，属于实时快照 |
| `sentiment` | 不支持，主要依赖持续采样积累 |

### 9.3 定向回填

先预览：

```bash
python -m src.interfaces.cli collection backfill news ths \
  --start-date 2026-05-01 \
  --dry-run
```

确认后只调整该 source：

```bash
python -m src.interfaces.cli collection backfill news ths \
  --start-date 2026-05-01
```

命令会：

1. 获取与 Worker 相同的 `news:ths` Redis 源级锁；
2. 保留 `newest_time`、`oldest_time`、累计次数和累计入库量；
3. 将该 source 切换为 `backfill`；
4. 清空已完成状态并将 `last_run_at` 设为空；
5. 让下一次 `collect_news` 调度立即执行历史回填；
6. 达到目标日期后自动切回 `incremental`；
7. 数据源历史不足且时间不再前进时，以 `backfill_status=ceiling` 结束。

如果指定日期早于该源的配置覆盖范围，CLI 会给出警告，但允许继续尝试。最终能回填多远取决于上游接口，
例如雪球和财联社实时接口无法保证提供任意长的历史。

### 9.4 停机后的自动断档追赶

对支持历史追赶的新闻源和北向资金，Worker 会在每次 source 开跑前检查 `last_success_at`：

1. 如果距离上次成功时间不超过正常调度周期，不改变增量流程；
2. 如果超过 `max(两倍 source interval, 1 小时)`，判定存在停机或长期失败断档；
3. 使用停机前的 `newest_time` 作为追赶边界，并额外向前重叠一天；
4. 从当前数据向历史翻页，补齐断档后再恢复增量；
5. 重叠数据由唯一键或 fingerprint 幂等去重。

宏观源通常每次直接返回一段完整历史，不需要额外的断档追赶模式。市场快照和部分情绪源没有历史接口，
停机期间的瞬时快照无法补造；恢复后只能继续积累。即使支持回填，如果停机时间超过上游接口自身的历史保留
上限，也会以 `ceiling` 结束，并在日志中明确记录未达到目标日期。
