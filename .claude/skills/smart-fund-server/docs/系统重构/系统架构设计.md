# 智能基金服务 — 系统架构设计

基于简化 DDD 分层架构，清晰划分 接口 → 应用 → 领域 → 基础设施 四层。

---

## 1. 架构总览

```
smart-fund-server/
├── main.py                                    # 启动入口
├── src/
│
│   ┌──────────────────────────────────────────────────────────┐
│   │          src/interfaces/ — 接口层                         │
│   │   api/routes/     │ tasks/            │ cli/             │
│   │   (FastAPI 路由)   │ (jettask task)    │ (管理命令)       │
│   └────────────────────────┬─────────────────────────────────┘
│                            ↓
│   ┌──────────────────────────────────────────────────────────┐
│   │          src/application/ — 应用层                        │
│   │   ┌──────────────────┐  ┌──────────────────────────┐     │
│   │   │ services/         │  │ orchestrators/            │     │
│   │   │ (用例编排，无状态) │  │ (长驻进程，有状态)        │     │
│   │   │ AggregationSvc    │  │ TaskOrchestrator          │     │
│   │   │ TradeSvc          │  │ (tmux 会话生命周期)       │     │
│   │   │ QuerySvc          │  │                           │     │
│   │   └──────────────────┘  └──────────────────────────┘     │
│   └────────────────────────┬─────────────────────────────────┘
│                            ↓
│   ┌──────────────────────────────────────────────────────────┐
│   │          src/domain/ — 领域层                             │
│   │   aggregation/ ⭐ │ trading/  │ task/     │ (query)     │
│   │   (数据聚合)      │ (交易)    │ (任务)    │ (在 AppSvc) │
│   └────────────────────────┬─────────────────────────────────┘
│                            ↓
│   ┌──────────────────────────────────────────────────────────┐
│   │          src/infrastructure/ — 基础设施层                  │
│   │   clients/(10) │ db/(4) │ tools/ │ config/ │ tmux/      │
│   └──────────────────────────────────────────────────────────┘
│
│   src/common/ — 通用模块 (types, exceptions)
│
├── tests/
└── docs/
```

**依赖规则**：
- ✅ interfaces → application → domain
- ✅ 所有层 → infrastructure（基础设施被上层调用）
- ✅ 所有层 → common
- ❌ domain 不依赖 interfaces
- ❌ interfaces 不跳过 application 直接调 domain

## 2. 当前问题

### 2.1 目录结构混乱

```
当前结构（扁平，职责不清）：

smart-fund-server/
├── main.py                    ← 启动 + 生命周期，职责还行
├── config.py                  ← ✅ 刚刚统一的配置
├── routers/                   ← 接口层（但直接操作 DB、实例化 service）
│   ├── task.py                ← 直接 import task_db、executor
│   ├── trade.py               ← 直接构造 HTTP 请求
│   └── ...
├── services/                  ← 什么都往里塞
│   ├── task_executor.py       ← 600+ 行巨型文件（tmux + Claude + 状态管理）
│   ├── clients/               ← 基础设施层（10 个外部 API 客户端）
│   ├── aggregators/           ← 领域层（数据聚合业务逻辑）
│   ├── handlers/              ← 应用层（OCR、chat 处理）
│   ├── trade/                 ← 领域层（交易风控、指标）
│   ├── db/                    ← 基础设施层（数据库 CRUD）
│   └── tools/                 ← 基础设施层（OCR、调度器、浏览器）
├── tasks/                     ← 接口层（jettask task 入口）
└── tests/                     ← 测试
```

**核心问题**：
1. **services/ 混合了三个层**：clients(基础设施) + aggregators(领域) + handlers(应用) 平铺在一起
2. **routers 太厚**：直接操作 DB、构造请求，缺少应用层中转
3. **task_executor.py 是巨型单体**：tmux 管理 + Claude 交互 + 任务状态 + 模型切换全塞一个文件
4. **没有应用层**：router 直接调 service/db，跳过了用例编排

### 2.2 依赖混乱

```
当前依赖关系（网状）：

routers ──→ services/db (直接查 DB)
routers ──→ services/task_executor (直接操作执行器)
routers ──→ services/clients (直接调客户端)
services/aggregators ──→ services/clients (OK，但缺乏抽象)
services/trade ──→ services/db (直接查 DB)
services/handlers ──→ services/tools (OK)
```

应该是：
```
routers → AppService → Domain → Infrastructure
```

## 5. 分层职责

### 接口层 (interfaces/)

外部接入点。**薄层**，只做：
1. 参数校验（FastAPI Pydantic model）
2. 调用应用层 AppService
3. 格式化响应

```python
# src/interfaces/api/routes/query.py
from src.application.services.query_service import QueryService

@router.get("/api/fund/{code}")
async def get_fund(code: str):
    return await QueryService.get_fund_snapshot(code)
```

**禁止**：直接操作 DB、直接调用客户端、包含业务逻辑。

### 应用层 (application/)

用例编排。协调多个领域和基础设施完成一个完整用例。

两种模式：

| | Services（用例编排） | Orchestrators（进程编排） |
|--|---------|---------|
| 调用方式 | `await svc.method()` → 返回 | 长驻运行，管理生命周期 |
| 状态 | 无状态 | 有状态（tmux 会话池、shutdown） |
| 代表 | AggregationService, TradeService | TaskOrchestrator |

```python
# src/application/services/aggregation_service.py
class AggregationService:
    @staticmethod
    async def query_news(since: str = None, category: str = None):
        """查询已聚合的新闻（读结果表）"""
        return db.query_ft_news(since=since, category=category)

    @staticmethod
    async def replay_news(start: str, end: str):
        """历史重放：从 raw_data 重新聚合"""
        records = raw_data.query_raw(domain="news", start=start, end=end)
        ...
```

### 领域层 (domain/)

**纯业务逻辑**。不依赖任何框架（不 import FastAPI、jettask、psycopg2）。

```python
# src/domain/aggregation/news.py
SOURCES = [
    ("cls", cls.get_telegraph_since, 180, normalize_cls),
    ...
]

async def run():
    """新闻聚合核心逻辑"""
    for name, fetch_fn, interval, normalize_fn in SOURCES:
        if not should_fetch(name, interval):
            continue
        try:
            raw = await fetch_fn(get_checkpoint(name))
            items = normalize_fn(raw)
            save(items)
            mark_fetched(name)
        except Exception as e:
            logger.warning(f"[{name}] 失败: {e}")
```

### 基础设施层 (infrastructure/)

技术实现，可替换。提供领域层和应用层所需的外部能力。

| 模块 | 技术 | 职责 |
|------|------|------|
| `clients/` | httpx, curl_cffi | 10 个外部数据源 API 客户端 |
| `db/` | psycopg2 | PostgreSQL CRUD + 建表 |
| `tools/` | httpx, subprocess | OCR、浏览器、APScheduler |
| `tmux/` | subprocess | tmux 会话管理（从 task_executor 拆出） |

## 7. task_executor 拆分方案

当前 `services/task_executor.py`（600+ 行）是最大的技术债。拆分为三部分：

| 拆分后 | 层 | 职责 | 行数估计 |
|--------|---|------|---------|
| `src/application/orchestrators/task_orchestrator.py` | 应用层 | 任务生命周期：创建→执行→轮询→完成→清理 | ~200 |
| `src/infrastructure/tmux/session.py` | 基础设施 | tmux 会话：创建、发送命令、读取输出、清理 | ~150 |
| `src/domain/task/models.py` | 领域层 | 任务状态模型、同步任务类型判断 | ~50 |

原 `task_executor.py` 中的状态管理（`_active_tasks`、`_session_models`、`SESSION_IDLE_TIMEOUT`）归入 Orchestrator。
tmux 操作（`_create_session`、`_send_to_tmux`、`_read_output`）归入基础设施。

## 9. 与 jettask_v2 的对比

| 维度 | jettask_v2 | smart-fund-server |
|------|-----------|-------------------|
| 类型 | 通用框架 | 业务应用 |
| DI | dependency-injector 容器 | 简单 import（暂不引入 DI 框架） |
| 配置 | YAML + env + CLI → DI 注入 | config.py + env（够用） |
| 领域数 | 3（Worker/Task/Scheduler） | 4（Aggregation/Trading/Task/Query） |
| 协议 | 跨语言 Wire Protocol | 不需要（纯 Python 应用） |
| 事件总线 | Redis Stream 事件驱动 | 暂不需要（领域间直接调用即可） |

**设计取舍**：
- **不引入 DI 框架**：项目规模不大，简单 import 即可，避免过度工程
- **不引入事件总线**：领域间调用关系简单，直接调用比异步事件更易调试
- **不引入 Repository 抽象**：只用 PostgreSQL，不需要换数据库，直接调 db 模块
- **保留 config.py 模式**：比 YAML + DI 注入更简单直接

## 11. 与业务实施方案的对应关系

[基金自动化交易系统](../基金自动化交易系统/) 的实施方案定义了三个业务层：**客户端层 → 聚合层 → 业务层**。重构不改变业务分层，只是将代码按职责重新组织到 `src/` 的四层结构中。

### 业务层 → 代码层 映射

```
业务实施方案                          代码架构（src/）
─────────────                        ─────────────

                                     interfaces/
                                       api/routes/        ← API 入口
                                       tasks/             ← jettask task 入口
                                         ↓ 调用
                                     application/
                                       services/          ← 用例编排
                                         ↓ 调用
┌─ 业务层 ──────────────┐            domain/
│  决策引擎 / 风控 / 策略  │  ──→        trading/           ← 风控、指标、决策复盘
└───────────────────────┘               ↓ 读取
                                         ↓
┌─ 聚合层 ──────────────┐            domain/
│  6 个聚合服务           │  ──→        aggregation/        ← 采集、转换、去重、入库
│  新闻/资金流/宏观/...    │              ↓ 调用
└───────────────────────┘               ↓
                                     infrastructure/
┌─ 客户端层 ─────────────┐              clients/           ← 10 个外部 API 客户端
│  9 个客户端 + 缓存       │  ──→        db/                ← PostgreSQL + ft_raw_data
│  + ft_raw_data 原始归档  │              tools/             ← OCR、浏览器等
└───────────────────────┘              config/             ← 统一配置
```

### 两份架构文档的关系

| | [技术架构](../基金自动化交易系统/2.%20实施方案/0.%20技术架构.md) | 本文档（系统架构设计） |
|--|-------|-------|
| 视角 | **业务视角**：数据怎么流转 | **工程视角**：代码怎么组织 |
| 分层 | 客户端层 → 聚合层 → 业务层 | interfaces → application → domain → infrastructure |
| 关注点 | 采集什么数据、怎么聚合、怎么决策 | 文件放哪里、谁调谁、怎么迁移 |
| 稳定性 | 业务不变则不动 | 随项目规模演进 |

**重构不改变业务架构**：客户端层依然对接外部 API + 透明缓存 + ft_raw_data 归档，聚合层依然是每维度一个 jettask task 串行遍历源。改变的只是代码的目录组织方式。
