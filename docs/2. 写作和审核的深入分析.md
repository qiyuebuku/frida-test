审核 和 写作的上下文应该要区分开吧？否则就是自己审核自己了




对，这个点你抓得非常关键 👍 —— **审核上下文 和 写作上下文必须物理隔离**。
不然就会变成「作者自己给自己打分」，最终一定失真。

这其实是知识库设计里一个非常核心的架构问题：
**多角色上下文隔离（Multi-Context Architecture）**

我们可以深入拆开讲一下。

---

# 一、为什么必须隔离（本质原因）

如果不隔离，会发生 3 个必然问题：

### 1️⃣ 自证循环（self-confirmation loop）

写作模型看到的资料 = 审核模型看到的资料
→ 审核会被写作时的偏见污染

典型现象：

写作模型生成：

> 我们的产品行业第一

审核模型看到知识库里有：

> 市场排名：Top3

审核模型很可能会放过，因为上下文被同一检索污染了。

这叫：
**retrieval bias leakage（检索偏见泄露）**

---

### 2️⃣ 幻觉无法被抓到

如果两者共用上下文：

写作模型 hallucination
→ 审核模型检索同样的错误片段
→ 审核认为“有依据”

等于：
**错误被检索放大**

---

### 3️⃣ 无法实现真正的“对抗”

你真正想要的是：

作者 ✍️ VS 审稿人 🧑‍⚖️

而不是：

作者 ✍️ VS 作者的影子 👻

---

# 二、正确架构：三上下文体系

真正成熟的做法是 **3 套上下文池**

不是 2 套。

很多人会少做一套，这是常见坑。

---

## 🟦 Context A：写作知识库（Author KB）

给写作模型用
特点：**信息丰富、宽松、启发式**

包含：

* 产品资料
* 历史文章
* 品牌语气
* 可用卖点
* 市场信息
* FAQ
* 案例
* 营销素材

目的只有一个：

👉 **尽可能帮助写出好内容**

这里可以允许：

* 未完全验证的数据
* 营销话术
* 观点
* 推测

因为这是创作区。

---

## 🟥 Context B：审核知识库（Reviewer KB）

给审核模型用
特点：**严格、可验证、去营销**

这是最关键的。

必须只包含：

* 已验证事实（verified facts）
* 法务限制
* 合规规则
* 敏感词规则
* 不可说内容
* 数字白名单
* 官方规格
* 已批准 claim 列表

**这里不能放营销材料。**

这一点极其重要。

否则审核会被洗脑。

---

## 🟨 Context C：风格与规范库（Style & Policy KB）

这个很多团队会忽略。

这套同时给：

* 写作模型
* 审核模型

内容包括：

* 品牌语气
* 用词规范
* 格式规范
* SEO规则
* 文章结构规范
* 标题规范

它不是事实库，而是 **规则库**。

---

# 三、三者关系图

```
            Style KB
           (共享规则)
           /       \
          /         \
 Author KB         Reviewer KB
 (创作素材)        (事实与合规)
     ↓                  ↑
   写作模型  ——>  审核模型
```

注意信息流：

**只能单向：写作 → 审核**

审核不能把 Reviewer KB 反喂给写作。

否则写作会学会“绕审核”。

---

# 四、检索策略也必须不同

即使是 markdown + 目录方案，也必须分开索引。

### 写作检索（Creative Retrieval）

目标：找灵感、找素材

特点：

* topK 可以大
* 允许相似内容
* 允许重复观点
* 可以 fuzzy

像：

```
topK = 12
```

---

### 审核检索（Strict Retrieval）

目标：找证据、找违规

特点：

* 精确匹配优先
* 小 topK
* 高置信度
* 强关键词匹配

像：

```
topK = 3~5
```

这是 **两种完全不同的搜索哲学**。

---

# 五、审核时必须“禁止访问写作上下文”

这是一个非常关键的工程细节。

审核 prompt 必须像这样：

> 你不能相信作者给出的任何事实
> 你只能信任检索到的审核知识库

这叫：

**Assume the author may be wrong**

否则审核模型会“相信人类”。

模型非常容易这样。

---

# 六、推荐的执行流程（非常实用）

完整 pipeline：

### Step 1 — 写作

输入：

* 用户需求
* Author KB
* Style KB

输出：

* Draft v1

---

### Step 2 — 审核

输入：

* Draft v1
* Reviewer KB
* Style KB

输出：

* 问题清单

包括：

* 不可验证声明
* 违规风险
* 数据不匹配
* 夸大表达

---

### Step 3 — 修订（再写作）

输入：

* Draft v1
* 审核问题清单
* Author KB

输出：

* Draft v2

注意：
修订阶段仍然**不能访问 Reviewer KB**

---

### Step 4 — 二次审核（可选）

用于高风险内容。

---

# 七、一个关键认知

你构建的其实不是：

> 一个 RAG

而是：

> 一个 AI 内容生产流水线

里面有不同角色。

像公司一样：

* 作者
* 法务
* 审稿人
* 编辑

LLM 只是扮演角色。

---

# 总结（核心结论）

是的，你说的完全正确，而且非常关键：

**审核和写作必须上下文隔离。**

正确结构是：

* Author KB → 创作
* Reviewer KB → 审核
* Style KB → 共享规范

并且：

* 索引分开
* 检索策略分开
* 信息流单向

---

如果你愿意，我们下一步可以深入聊一个很实战的话题：
👉 Reviewer KB 里到底应该放哪些“可验证事实结构”？
这是落地时最难的一步。





这是我现在的写作skill，他现在会总结Context Bundle，但是对于 cene Plan + Style Anchors，这个步骤不会去落文档，而是在上下文记忆中，你觉得整个合理吗？









这个问题问得非常关键，因为它已经触及 **Skill 是否“工程化”** 的分水岭了。

先给结论：

**现在这样能跑，但不够稳定，也不利于进入循环修复阶段。**
👉 *Scene Plan + Style Anchors 必须落盘（materialize），不能只存在上下文里。*

而且这是一个**很典型的从 PoC → Production 的转折点**。

---

# 一、为什么“只存在上下文”在初期看起来没问题？

因为现在你是这样用的：

```
一次写一章
一次调用 Claude
上下文没丢
```

流程是单次调用闭环：

```
读KB → 生成Context Bundle → 生成Scene Plan → 写正文 → 结束
```

所以你会感觉：

> 不落文档也没问题啊 🤔

没错，在**单次生成**里完全没问题。

但一旦进入你刚刚确定的流程：

```
写作 → 审核 → 修复 → 再审核 → 再修复
```

问题就会立刻爆出来。

---

# 二、核心问题：你即将进入“多回合写作系统”

一旦进入循环，Writer 将被**反复重新调用**。

每一次重新调用，Claude 的世界会变成：

> “这是一次全新的任务”

它不会记得：

* 上一轮 Scene Plan
* 上一轮 Style Anchors
* 上一轮 Context Bundle 的细节

也就是说：

**你现在所有没落盘的中间产物，都会蒸发。**

这会导致一个很严重的问题：

## 修复时会发生“写作漂移”

真实会发生的情况：

### Round 1

生成：

* Context Bundle（内存）
* Scene Plan（内存）
* Style Anchors（内存）
* Draft v1（落盘）

Reviewer 给出 issues。

---

### Round 2（修复）

Writer 被重新调用，只看到：

* draft_v1
* issues

但看不到：

* 当初的 Scene Plan
* 当初的 Style Anchors

结果会变成：

> Writer 在“另一套计划”下修复旧文章

这就是写作系统最可怕的问题之一：

**Plan Drift（计划漂移）**

最终表现就是：

* 节奏突然变了
* 视角突然变了
* 角色说话风格变了
* 情绪递进被破坏

你现在已经在 T9 看到了苗头：
60% 相似度、情绪词直白化，其实就是漂移的早期信号。

---

# 三、Scene Plan 的本质是什么？

很多人以为 Scene Plan 是草稿，其实不是。

它其实是：

**章节的“设计图”**

就像：

| 领域  | 类比                  |
| --- | ------------------- |
| 编程  | architecture design |
| 写论文 | outline             |
| 拍电影 | 分镜脚本                |
| 小说  | Scene Plan          |

你现在的流程其实是：

```
设计图 → 建房子 → 丢掉设计图
```

然后下一轮要修房子时：

> “我当初为什么这么设计来着？”

没人知道了 😭

---

# 四、Style Anchors 更不能丢

Style Anchors 是什么？

它不是规则，而是：

**风格锚点样本**

例如：

* 原文对话范本
* 原文动作描写范本
* 原文节奏范本

这是防止模型“写成网文通用体”的**唯一硬锚**。

如果不落盘，修复时 Writer 会回到：

> 通用大模型写作模式

于是 Reviewer 会一遍遍报：

* 情绪词太直白
* 书面语
* 夸张动作

然后你进入无限循环。

---

# 五、进入循环系统后，必须落盘的中间产物

以后每章会变成一个“小工程”。

建议新增一个目录：

```
drafts/ch0004/
```

里面不再只有 draft.md，而是：

```
draft.md                ← 当前正文版本
context_bundle.md       ← 写作上下文包
scene_plan.md           ← 场景设计图 ⭐
style_anchors.md        ← 风格锚点 ⭐
issues_v1.json
issues_v2.json
verification.md
```

这是关键升级。

---

# 六、写作循环会变得极其稳定

之后流程变成：

### Round 1

Writer 生成并落盘：

* context_bundle.md
* scene_plan.md
* style_anchors.md
* draft_v1.md

---

### Round 2 修复

Writer 再调用时输入：

```
scene_plan.md
style_anchors.md
context_bundle.md
draft_v1.md
issues_v1.json
```

注意：

Writer 不再重新规划。
Writer 是在**既定设计图下施工修复**。

这就是工业写作 pipeline。

---

# 七、你现在的设计处于哪个阶段？

目前是：

**Stage 1：生成型 Skill**

你即将进入：

**Stage 2：工程化写作系统**

标志就是：

> 中间产物全部物化（materialized artifacts）

一旦你这么做：

* 循环会稳定
* 风格漂移会显著下降
* Reviewer 的建议会越来越少

这也是为什么很多团队最终都会走向：
**Markdown + 文件系统 = 状态机**

---

# 八、最终回答你的问题

> Scene Plan + Style Anchors 不落文档合理吗？

在 PoC 阶段：
✔ 可以

在你现在这个阶段（要做循环审核）：
❌ 必须落文档

而且这是一个**关键升级点**。
