# T4：角色层提取

> 状态：✅ 实现完成
> Skill 目录：`.claude/skills/kb-character-extract/`
> 输出目录：`{book-dir}/characters/`（通用，通过 `--book-dir` 参数指定）
> 测试：3 章数据端到端测试通过（7 次调用，2m54s），3 个核心角色 5 模块完整

---

## 目标

从章节摘要 + 原文中提取角色信息，构建完整的人物库。每个角色包含 5 个模块（基本设定、角色弧光、关系演化、个人时间轴、当前状态），另外生成人物索引和关系网。

角色层是决定"续写像不像原作"的关键。大模型最容易崩的地方是**人物行为不符合人设**，所以人物库必须非常重。

**通用性**：脚本通过 `--book-dir` 指定知识库目录，不绑定特定小说。

---

## 核心难题

| 难题 | 说明 | 解法 |
|------|------|------|
| 角色数量庞大 | 群像文可达 50-200+ 个有名角色 | 分级处理：核心角色精细建档，次要角色简化 |
| 信息极度分散 | 一个角色的信息碎片化在数百章中 | Python 预处理建立出场索引，再按角色回查 |
| 别名消歧 | 同一角色在不同场景有多种称呼 | Python 统计 + Claude 语义合并 |
| 关系是动态的 | 关系随剧情推进会变化 | 从 T2 "关系变化"字段逐章追踪 |
| 角色弧光需连贯 | 性格成长必须有明确的转折点 | 与 T3 弧划分联动 |
| "当前状态"精度 | 续写时 90% 会读这个 | 最后阶段专门从末尾章节精确提取 |

## 核心设计：Python 预处理 + Claude 深度分析

### 设计理念

原方案的阶段 1（全局角色扫描）需要 ~12 次 Claude 调用来分段扫描章节摘要提取角色信息。但实际数据表明，T2 摘要的角色字段**格式高度规范**，Python 正则可以直接解析。

**新方案将阶段 1 拆为两部分**：
- **Phase 0（Python 预处理）**：0 次 Claude 调用，纯脚本解析
- **Phase 1（别名合并）**：1-2 次 Claude 调用，只做语义理解（Python 无法做的事）

这将 Claude 调用总数从 ~50-75 次降至 ~30-57 次，且质量更高（Python 解析比 Claude 提取更稳定精确）。

---

## 五阶段 Pipeline 设计

```
阶段 0: Python 预处理 (Data Pre-processing)
  解析 T2 摘要的结构化字段 + T3 弧文件
  0 次 Claude 调用

阶段 1: 别名合并与分级 (Alias Merge & Classification)
  语义识别同一角色的不同称呼，确定分级
  1-2 次 Claude 调用

阶段 2: 角色深度分析 (Character Deep Dive)
  为每个核心/重要角色生成完整档案
  ~20-40 次 Claude 调用

阶段 3: 关系网构建 (Relationship Mapping)
  综合全部角色档案，构建全局关系网
  ~3-5 次 Claude 调用

阶段 4: 状态精修与索引 (Status Refinement & Index)
  从最新章节精确更新活跃角色状态，生成最终索引
  ~5-10 次 Claude 调用

总计: ~30-57 次 Claude 调用, ~20-40 min 全自动
```

### 阶段 1：别名合并与分级

**目标**：识别同一角色的不同称呼，合并条目，确定核心/重要/次要分级。

**为什么需要 Claude**：Python 无法判断"通崖"和"李通崖"是同一人，也无法判断"师父"在不同章节指的是不同人。这需要语义理解。

**调用次数**：1-2 次。

**输入**：
- `raw_census.json`（阶段 0 产出）
- `plot/outline/plot_lines.md`（主线核心角色）

**输出 JSON**（`characters/.build/census.json`）：

```json
{
  "characters": [
    {
      "canonical_name": "李木田",
      "aliases": ["木田", "李老爹"],
      "identity": "黎泾村农户，曾从军杀过人，四十岁回乡买地",
      "classification": "core",
      "first_appearance": "ch0002",
      "last_appearance": "ch0003",
      "appearance_count": 2,
      "associated_plotlines": ["李家危机"],
      "file_name": "li_mutian"
    },
    ...
  ],
  "alias_mapping": {
    "木田": "李木田",
    "李老爹": "李木田",
    ...
  },
  "classification_summary": {
    "core": ["陆江仙", "李项平", "李通崖", ...],
    "important": [...],
    "minor": [...]
  }
}
```

**分级标准**：
- **核心角色**：出场频次 ≥20 **或** 主线核心角色
- **重要角色**：出场频次 5-19
- **次要角色**：出场频次 1-4

**同时生成** `alias_mapping.json`（可手动审查修正）。

### 阶段 2：角色深度分析

**目标**：为每个核心/重要角色生成完整档案。

**方法**：逐角色处理。对于每个角色，Python 预先从 `raw_census.json` 中提取该角色的全部出场章节列表，然后只加载这些章节的完整摘要。

**每个角色的 Claude 调用输入**：
- 该角色出场的全部章节摘要（核心角色可能 100+ 章，~25K token）
- 弧划分信息（`arc_XX.md` 中该角色相关段落，~5K token）
- 主线追踪信息（~3K token）
- 角色在 `raw_census.json` 中的预提取数据（关系时间线、行为记录，~5K token）
- 其他相关角色列表（~3K token）
- 角色档案模板 + 指令（~5K token）

总计 ~45K token，安全。

**对于出场章节极多的角色**（>150 章，摘要 >40K token）：
- 按弧分批输入，每次 2-3 个弧
- 第一次生成初稿，后续增量更新

**核心角色**（5 模块）：
| 模块 | 数据来源 | 说明 |
|------|---------|------|
| 1. 基本设定 | 摘要中的"新登场角色"描述 + 可能需要回查 2-3 章原文 | 性格、价值观等需要从对话/心理描写中提炼 |
| 2. 角色弧光 | T3 弧划分 + 摘要中"已有角色出场"的状态变化 | 按弧分段追踪，确保成长连贯 |
| 3. 关系演化 | 摘要中"关系变化"字段（Python 预提取的时间线） | 最省力：数据已结构化 |
| 4. 个人时间轴 | 摘要中"关键事件"+"已有角色出场"字段 | Python 预提取后由 Claude 精炼 |
| 5. 当前状态 | 最后出场章节的摘要 | 阶段 4 专门精修 |

**重要角色**（简化 3 模块：基本设定 + 关键事件 + 当前状态）：一次调用完成。

### 阶段 3：关系网构建

**目标**：综合全部角色档案中的关系信息，生成全局关系网。

**输入**：
- Python 从 `raw_census.json` 预提取的 `relationship_timeline`（全部章节的关系变化，按时序排列）
- 全部角色档案中的"关系演化"段落（Python 预提取，~20K token）
- 弧划分信息（~5K token）

**产出**：
- `relationships.md`（分类关系网 + 关系演化重大转折）

**2-3 次调用**：
1. 生成关系网初稿（基于 Python 预提取数据）
2. 交叉验证（检查 A 档案和 B 档案中关于 A↔B 关系的描述是否一致）
3. 补充遗漏（如有需要）

### 阶段 4：状态精修与索引

**目标**：确保每个活跃角色的"当前状态"精确反映最新章节，生成最终的人物索引。

**方法**：
1. 读取最后 20 章的完整摘要
2. 识别活跃角色
3. 更新每个活跃角色档案的模块 5（当前状态）
4. 生成最终 `index.md`

**分批处理**：每批约 10 个角色。

## 别名合并：关键难点

长篇小说中同一角色可能被多种方式称呼：

| 场景 | 示例 |
|------|------|
| 姓名 vs 称号 | "张三" vs "剑仙" |
| 全名 vs 简称 | "李通崖" vs "通崖" |
| 不同关系的称呼 | "师父" vs "老头子" vs 真名 |
| 改名/化名 | 角色改名后前后期不一致 |

**解决方案**：

1. **阶段 0 Python 预处理**：统计每个名称的出场频次和首次出场章节
2. **阶段 1 Claude 语义合并**：
   - 输入全部角色名称列表 + 出场上下文
   - 识别跨段出现的同一角色，合并条目
   - 输出去重后的角色列表 + 别名映射表
3. **人工审查入口**：`characters/.build/alias_mapping.json` 可手动修正

## 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| T2 摘要格式不一致 | Python 正则解析失败 | 阶段 0 输出解析统计（成功率、失败章节列表），允许容错 |
| 别名合并错误 | 把两个人合并成一个 | alias_mapping.json 审查入口；合并 prompt 要求标注置信度 |
| 核心角色出场极多（>200 章） | 单次上下文放不下 | 按弧分批输入，增量构建档案 |
| 角色名重复 | 不同时期的同名角色 | 以首次出场章节 + 身份描述区分 |
| 关系描述矛盾 | A 档案和 B 档案不一致 | 阶段 3 交叉验证 |
| "关系变化"字段格式多样 | `A与B`、`A和B`、`A、B` 等不同连接词 | Python 正则支持多种模式 |
