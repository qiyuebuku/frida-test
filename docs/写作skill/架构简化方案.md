## 一、当前架构真实分析

### 1.1 完整依赖图

```
原文 (text/)
    │
    ├─→ T2 batch_summary.py ─→ plot/chapters/chXXXX.md (章节摘要)
    │       │
    │       ├─→ T3 batch_plot.py ─→ plot/outline/ (弧/主线/伏笔/时间线)
    │       │       │
    │       │       ├─→ T4 batch_character.py ─→ characters/ (角色档案/关系网)
    │       │       │       │
    │       │       │       └─→ T5 batch_world.py ─→ world/ (力量/地理/势力/规则)
    │       │       │
    │       │       └─→ T5 也直接读 T3 弧文件
    │       │
    │       └─→ T6 batch_reader.py ─→ reader/feedback/ (情绪/人气/投诉/期待)
    │                 ↑ 只读 reader/comments/，不读 T2 摘要
    │
    └─→ T7 batch_style.py ─→ style/ (叙事/用词/节奏)
              ↑ 读原文 text/ + T3 弧文件(仅用于抽样)
```

**关键链路**: T2 → T3 → T4 → T5（串行，最长路径 4 步）

### 1.2 各阶段内部子步骤一览

| 阶段 | 子步骤 | AI 调用 | 说明 |
|------|--------|---------|------|
| **T3** | phase 1: 段扫描 (12 段) | 12 | 100 章/段，提取事件/主线/弧候选/伏笔 |
| | phase 2: 全局合并 | 1 | 合并所有段 → 弧/主线/伏笔/时间线 |
| | phase 3a: 弧边界验证 | 1 | 检查弧起止章节 |
| | phase 3b: 弧内容充实 | N (~6) | 逐弧补充详细信息 |
| | phase 3c: 伏笔验证 | 1 | 验证伏笔一致性 |
| | phase 3d: 最终更新 | 1 | 应用验证结果（重复写文件） |
| **T4** | phase 0: Python 预处理 | 0 | 解析全部摘要 → raw_census.json |
| | phase 1: 别名合并 | ~3 | AI 去重角色名 + 分级 |
| | phase 2: 深度分析 | ~20 | 逐角色生成档案 |
| | phase 3: 关系网构建 | 2 | 构建 + 交叉验证 |
| | phase 4: 状态精修 | 1 | 更新活跃角色状态 + 生成 index |
| **T5** | phase 0: Python 预处理 | 0 | 解析摘要+弧+角色 → raw_world_data.json |
| | phase 1: 段分类 | 12 | 100 章/段，设定分类到 4 体系 |
| | phase 2: 全局合并 + AI 扩写 | ~4 | 去重 → 标注重要性 → 生成文件 |
| | phase 3: 实体精修 | ~5 | 对 high 实体做二次精修 |
| **总计** | **~20 个子步骤** | **~328** | |

### 1.3 真正的问题

| 问题 | 严重度 | 说明 |
|------|--------|------|
| **代码重复** | 高 | 6 个 batch 脚本共 ~9000 行，进度管理/Claude 调用/JSON 修复/文件锁等基础设施占比 >50%，且每个脚本独立实现 |
| **Python 预处理重复** | 高 | T3/T4/T5 各自 Python 解析相同的章节摘要文件，本质上是对同一批文件做不同字段的提取 |
| **AI 步骤可合并** | 高 | T3 段扫描和 T5 段分类处理模式完全一致（同输入、同分段），却分两次调 AI；T5 扩写+精修对同一批实体做了两遍 AI |
| **子步骤过多** | 中 | T3 精修 4 步中有冗余（3a+3c 可合并，3d 可去掉）；T4 关系+状态可合并 |
| **流程管理复杂** | 中 | 用户需要知道依赖顺序，分别执行 4-7 个命令 |
| **依赖链过长** | 中 | T3→T5 的串行依赖可通过段扫描合并来打断 |

### 1.4 之前"统一提取"方案为何不可行

之前方案提出"1 次 AI 调用/章同时提取摘要+剧情+角色+世界"。这忽略了一个根本事实：

```
T3 的弧检测 = 跨 100+ 章的全局结构分析
T4 的别名去重 = 跨全书的实体消歧
T5 的实体分类 = 跨全书的设定归纳

这些都不是 per-chapter 操作，而是全局聚合操作。
```

按章提取只能得到碎片信息，真正的价值在于全局合并。把 T3/T4/T5 塞进每章的提取中，不会减少全局合并的工作量，反而会降低质量（prompt 过于臃肿）。

## 二、简化方案

三条主线并行推进：**AI 步骤合并** + **共享预处理** + **基础设施抽取**。

### 2.1 AI 步骤合并（4 项）

#### 合并 1: T3 段扫描 + T5 段分类 → 统一段扫描

**现状**：两者处理模式完全一致，都是 100 章/段读摘要喂 AI，但分两轮调用。

| | T3 segment-scan | T5 segment-classify |
|---|---|---|
| 输入 | 100 章摘要 | 100 章摘要（**同一批**） |
| 提取 | 事件、主线进度、弧候选、伏笔 | 设定分类到 4 大体系 |
| AI 调用 | 12 次 | 12 次 |

**合并方案**：合并为 1 个 prompt，1 次 AI 调用同时提取剧情结构 + 世界设定。

```
旧 prompt 输出:
  T3: { major_events, plot_lines_progress, arc_candidates, foreshadowing, timeline_events }
  T5: { power_system: [...], geography: [...], factions: [...], rules: [...] }

新 prompt 输出（合并）:
  {
    plot: { major_events, plot_lines_progress, arc_candidates, foreshadowing, timeline_events },
    world: { power_system: [...], geography: [...], factions: [...], rules: [...] }
  }
```

**收益**：
- 省 12 次 AI 调用
- **打断 T3→T5 依赖链**：段扫描后 T3 合并和 T5 合并可以并行
- 不再需要 T5 的独立段分类阶段

**需改动的 prompt**: 合并 `plot_segment_scan.md` + `world_segment_classify.md` → `unified_segment_scan.md`

#### 合并 2: T3 精修 3a+3c → 统一验证，去掉 3d

**现状**：T3 精修拆了 4 步，其中 3a（弧边界验证）和 3c（伏笔验证）都是验证任务，输入相似。3d（最终更新）本质上是让 AI 重新读一遍再写一遍，冗余。

```
旧流程（4 步，3 次 AI）:
  3a 弧边界验证 (1次AI) → 3b 弧内容充实 (N次AI) → 3c 伏笔验证 (1次AI) → 3d 最终更新 (1次AI)

新流程（2 步，省 2 次 AI）:
  验证(边界+伏笔，1次AI) → 逐弧充实(N次AI，充实时直接写最终文件)
```

**收益**：省 ~2 次 AI 调用，4 个子步骤变 2 个

**改动**：
- 合并 `plot_arc_boundary_validate.md` + `plot_foreshadow_validate.md` → `plot_validate.md`
- 去掉 `plot_final_update.md`，3b 充实弧时直接写最终格式

#### 合并 3: T5 扩写(phase 2b) + 精修(phase 3) → 一次到位

**现状**：对同一批实体做了两遍 AI 处理。Phase 2b 标注重要性 + 粗扩写，Phase 3 对 high 实体再精修。

```
旧流程（2 轮 AI）:
  Phase 2b: AI 扩写全部实体 (4次AI, 按类别) → Phase 3: AI 精修 high 实体 (5次AI, 逐实体)

新流程（1 轮 AI）:
  统一扩写: AI 标注重要性 + 直接写出最终描述 (4次AI, 按类别)
  prompt 中对 high 实体要求输出更详细的描述和演化记录
```

**收益**：省 ~5 次 AI 调用，去掉整个 T5 phase 3

**改动**：
- 修改 `world_entity_expand.md`：增加对 high 实体的详细输出要求
- 去掉 `world_refine_entity.md`
- batch_world.py 去掉 phase_refine 函数

#### 合并 4: T4 关系网(phase 3) + 状态精修(phase 4) → 合并

**现状**：两者都是全局操作，都需要读角色档案 + 章节摘要。

```
旧流程（3 次 AI）:
  Phase 3: 构建关系网 (1次AI) → 交叉验证 (1次AI) → Phase 4: 更新状态 (1次AI)

新流程（2 次 AI）:
  构建关系网 + 更新状态 (1次AI，同时产出 relationships.md + 更新档案)
  → 交叉验证 (1次AI)
```

**收益**：省 ~1 次 AI 调用，5 个子步骤变 4 个

**改动**：
- 合并 `char_relationship_build.md` + `char_status_update.md`
- batch_character.py 合并 phase_relationship + phase_status_update

#### 合并汇总

| 合并项 | 省 AI 调用 | 减少子步骤 | 额外收益 |
|--------|-----------|-----------|---------|
| T3 段扫描 + T5 段分类 | ~12 | -1 个阶段 | **打断 T3→T5 依赖链** |
| T3 验证 3a+3c + 去掉 3d | ~2 | 4→2 步 | 流程更清晰 |
| T5 扩写 + 精修 | ~5 | -1 个阶段 | 少一轮 AI 处理 |
| T4 关系 + 状态 | ~1 | 5→4 步 | 少一轮档案读取 |
| **总计** | **~20** | **~20→~15 步** | 依赖链缩短 |

合并后 AI 调用：~328 → ~308（减少 ~6%），但子步骤和依赖结构大幅简化。

### 2.5 并行执行时间线

统一段扫描打断了 T3→T5 的串行依赖后，剧情合并/世界合并/角色分析可以并行：

```
时间 ──────────────────────────────────────────────────────→

T2 ■■■■■■■■■■■■■■■■■■■■■■■■■■■■■

T6 ■■■■■■■■■■■                        (与 T2 并行，读 comments/)

预处理 ■                                 (T2 完成后，<30s)

统一段扫描 ■■■■■■■■                      (12 段 × 1 次 AI)
           │
           ├── 剧情合并+精修 ■■■■■■■■     (全局合并 + 验证 + 弧充实)
           │
           ├── 世界合并+扩写 ■■■■          (去重 + 一次到位扩写)
           │
           ├── T4 角色层 ■■■■■■■■■■       (别名→深度→关系+状态)
           │
           └── T7 ■■■■                    (风格分析，独立)

旧最长路径: T2 → T3全部 → T4全部 → T5全部 (串行)
新最长路径: T2 → 统一段扫描 → T4全部 (T3合并/T5合并/T7 与 T4 并行)
```

## 五、对比总结

| 维度 | 旧架构 | 简化后 | 变化 |
|------|--------|--------|------|
| 子步骤数 | ~20 个 | ~15 个 | **减少 25%** |
| AI 调用量 | ~328 次 | ~308 次 | 减少 ~6% |
| 最长依赖链 | T2→T3→T4→T5 (串行 4 步) | T2→段扫描→T4 (3 步，T3/T5 并行) | **缩短 25%** |
| 总代码量 | ~8053 行 | ~5150 行 | **减少 36%** |
| Prompt 文件 | 23 个 | 20 个 (+3 新 -3 合并 -3 删除) | 略减 |
| 预处理 IO | 3600 次文件读取 | 1200 次 | **减少 67%** |
| 用户操作 | 手动按序执行 6 个命令 | 1 个命令自动编排 | **简化 83%** |
| 依赖管理 | 用户记忆 + 文档 | 自动检测 + 自动并行 | 完全自动化 |
| 增量更新 | 不支持 | 支持检测新增章节 | 新能力 |

### 核心理念

**合并冗余 AI 步骤，抽取公共基础设施，打断串行依赖链。**

- AI prompt 合并只发生在"处理相同数据、可复用上下文"的场景
- 不合并逻辑独立的步骤（如 T4 别名合并 vs 深度分析）
- 产出格式和目录结构保持不变，对下游 novel-write 透明
