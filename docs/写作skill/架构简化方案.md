## 一、当前架构问题分析

### 1.1 依赖关系图

```
原文 (text/)
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│  T2 (batch_summary.py)                                       │
│  产出: plot/chapters/chXXXX.md                               │
└─────────────────────────┬───────────────────────────────────┘
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
┌─────────────────┐ ┌───────────┐ ┌─────────────────────────────┐
│ T3 剧情层        │ │ T6 读者层 │ │ T4 角色层                    │
│ batch_plot.py   │ │           │ │ batch_character.py          │
│ 依赖: T2        │ │ 依赖: T2  │ │ 依赖: T2 + T3               │
└────────┬────────┘ └───────────┘ └──────────────┬──────────────┘
         │                                      │
         └──────────────────┬───────────────────┘
                            ▼
              ┌─────────────────────────────────┐
              │ T5 世界层                        │
              │ batch_world.py                  │
              │ 依赖: T2 + T3 + T4              │
              └─────────────────────────────────┘

T7 风格层 (batch_style.py) 依赖: T1 原文
```

### 1.2 核心问题

| 问题 | 描述 | 影响 |
|------|------|------|
| **依赖链过长** | T5 依赖 T2+T3+T4，用户需按顺序运行 4 个阶段 | 使用门槛高 |
| **重复读取** | T3/T4/T5 都要读取 T2 的 1000+ 个章节摘要 | IO 开销大 |
| **阶段拆分过细** | 7 个阶段，每个阶段又有 2-4 个子步骤 | 流程复杂 |
| **上下文不共享** | 每个阶段独立进程，无共享内存 | 无法利用缓存 |
| **增量更新困难** | 新增章节需要重跑整个流程 | 维护成本高 |

### 1.3 数据读取统计

假设 1200 章的小说，全量构建时：

| 阶段 | 读取文件 | 重复读取 |
|------|----------|----------|
| T2 | 1200 个原文文件 | - |
| T3 | 1200 个摘要文件 | 1200 |
| T4 | 1200 个摘要 + 6 个弧文件 | 1200+ |
| T5 | 1200 个摘要 + 6 个弧文件 + 15 个角色档案 | 1200+ |
| T6 | 1200 个摘要（提取评论情绪） | 1200 |
| **总计** | - | **4800+ 次重复读取** |

## 二、简化方案对比

### 方案 A：阶段合并（激进）

**思路**：将 T2+T3+T4+T5 合并为一个"内容提取"阶段

```
原文 → [统一提取器] → 摘要 + 剧情 + 角色 + 世界观
```

**优点**：
- 一次读取，无重复
- 流程最简单
- AI 可以综合理解上下文

**缺点**：
- 单次 AI 调用上下文太大（1200 章 × 3KB = 3.6MB）
- 失败后需要全部重跑
- 无法单独重跑某个层

**适用场景**：新书首次构建

---

### 方案 B：共享预处理层（渐进）

**思路**：增加预处理层，一次性读取所有数据，生成标准化的中间格式

```
原文 → [预处理] → unified_data.json
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
       [T3]        [T4]        [T5]
       剧情层      角色层      世界层
```

**中间格式** (`unified_data.json`)：
```json
{
  "chapters": [
    {
      "ch": "ch0001",
      "text": "原文内容...",
      "summary": {
        "characters": [...],
        "settings": [...],
        "items": [...],
        "plot_beats": [...]
      }
    }
  ],
  "arcs": [...],
  "stats": {...}
}
```

**优点**：
- 保留阶段独立性
- 大幅减少重复读取
- 支持增量更新（只处理新增章节）

**缺点**：
- 需要设计新的中间格式
- 增加存储空间（~2x）

---

### 方案 C：内存流水线

**思路**：在内存中传递数据，不落盘中间结果

```python
# 伪代码
chapters = load_all_chapters()  # 一次读取
summaries = batch_summarize(chapters)  # T2
arcs = extract_arcs(summaries)  # T3
characters = extract_characters(summaries, arcs)  # T4
world = extract_world(summaries, arcs, characters)  # T5
save_all(summaries, arcs, characters, world)  # 一次写入
```

**优点**：
- 无 IO 重复
- 流程清晰
- 代码简洁

**缺点**：
- 需要大内存（1200 章 × 10KB = 12MB，可接受）
- 失败后需要全部重跑
- 无法断点续传

---

### 方案 D：Agent Teams 蜂群模式

**思路**：利用 Agent Teams 创建并行队友，共享任务列表

```
┌─────────────────────────────────────────────────────────┐
│                    Lead Agent                            │
│  - 创建团队                                              │
│  - 分配任务（按章节范围）                                 │
│  - 收集结果                                              │
└───────────────────────┬─────────────────────────────────┘
                        │
┌───────────────────────┼─────────────────────────────────┐
│                   Agent Team                             │
├───────────────────────┼─────────────────────┬───────────┤
│  Teammate 1           │  Teammate 2         │  Teammate N│
│  ch001-100            │  ch101-200          │  ...       │
│  ┌─────────────────┐  │  ┌─────────────────┐│            │
│  │ T2: 摘要        │  │  │ T2: 摘要        ││            │
│  │ T3: 剧情片段    │  │  │ T3: 剧情片段    ││            │
│  │ T4: 角色提及    │  │  │ T4: 角色提及    ││            │
│  │ T5: 世界设定    │  │  │ T5: 世界设定    ││            │
│  └─────────────────┘  │  └─────────────────┘│            │
└───────────────────────┴─────────────────────┴───────────┘
                        │
                        ▼
              [汇总合并] → 最终知识库
```

**优点**：
- 天然并行
- 队友间可通信协调
- 支持 Agent Teams 的 Hooks 质量门控
- 更适合大规模任务

**缺点**：
- 需要 Agent Teams 支持（实验性功能）
- 汇总合并逻辑复杂
- Token 成本较高

## 三、推荐方案

### 3.1 短期：方案 B + C 混合

```
┌─────────────────────────────────────────────────────────────┐
│                     预处理层 (新增)                          │
│  - 一次性读取所有原文                                        │
│  - 生成 unified_chapters.json                               │
│  - 检测新增章节（增量更新）                                   │
└─────────────────────────┬───────────────────────────────────┘
                          │
                          ▼ unified_chapters.json
                          │
┌─────────────────────────┼───────────────────────────────────┐
│                  内存流水线处理                              │
│                                                             │
│  for each chapter in unified_chapters:                      │
│      summary = T2(chapter)      # 摘要                      │
│      plot_beats = T3(summary)   # 剧情点                   │
│      characters = T4(summary)   # 角色提及                 │
│      settings = T5(summary)     # 世界设定                 │
│                                                             │
│  global_merge(plot_beats)      # 全局剧情合并               │
│  global_merge(characters)      # 全局角色合并               │
│  global_merge(settings)        # 全局设定合并               │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**实施步骤**：

1. **新增 `preprocess.py`**：
   - 读取所有原文
   - 生成 `unified_chapters.json`
   - 检测增量章节

2. **改造 `batch_summary.py`**：
   - 从 `unified_chapters.json` 读取（而非逐个文件）
   - 支持增量模式

3. **新增 `unified_extract.py`**：
   - 合并 T3+T4+T5 的提取逻辑
   - 一次 AI 调用提取剧情+角色+设定
   - 减少上下文传递开销

4. **保留独立入口**：
   - 支持单独运行某个层（调试用）
   - 默认运行统一流程

### 3.2 长期：方案 D Agent Teams

当 Agent Teams 功能稳定后，可以进一步升级为蜂群模式：

```bash
# 一键全流程（蜂群模式）
/novel-kb-unified /path/to/kb --phase all --concurrency 8

# 8 个队友并行处理
# 每个队友负责 150 章
# 每个队友同时完成 T2+T3+T4+T5
# Lead Agent 汇总合并
```

## 四、新的目录结构

### 4.1 简化后的目录

```
novel_kb/{book_name}/
├── .cache/                     # 新增：预处理缓存
│   ├── unified_chapters.json   # 统一章节数据
│   └── .incremental.json       # 增量更新追踪

├── plot/                       # 剧情层（保持不变）
├── characters/                 # 角色层（保持不变）
├── world/                      # 世界层（保持不变）
```
