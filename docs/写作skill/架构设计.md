# AI 小说续写系统 — 架构设计

> 日期：2026-02-08
> 状态：**已实施**（全部代码完成，知识库内容待 T2 全量补跑）

---

## 一、问题定义

**目标**：让 AI 续写长篇小说，且续写质量接近原作。

**核心难点**：

1. **上下文容量**：百万字小说不可能一次性塞进 LLM 上下文
2. **风格漂移**：LLM 默认输出是训练语料均值，不是某本书的风格
3. **设定崩坏**：AI 不记得 200 章前的世界规则，容易自相矛盾
4. **质量不可控**：同一 prompt 每次生成结果不同，需要可量化的验证手段

**解法**：将问题拆为两步——**预处理**（把小说解构为结构化知识库）+ **运行时**（从知识库按需调度上下文来写作，并自动验证）。

```
续写质量 ≈ 预处理质量 × 上下文调度能力 × 验证反馈能力
```

---

## 二、设计原则

1. **通用性**：知识库结构是模板，适用于任意小说，不绑定某本书
2. **信息不丢失**：评论保留段落级粒度，保持与原文的精确映射关系
3. **可扩展**：百万字级小说的世界观、人物关系等信息量巨大，目录结构需支持多文件扩展
4. **导航式检索**：AI 通过索引文件层层展开上下文，而非一次性加载全部内容
5. **写审分离**：Writer 不自审，质量由独立 Reviewer 在隔离上下文中评判

## 四、核心模型：六层知识库

小说不等于文本。一部小说是多层结构的叠加，预处理的本质是**小说结构化建模**。

| 层 | 回答的问题 | 目录 | 核心文件 |
|----|-----------|------|----------|
| **剧情层** | 故事走到哪了 | `plot/` | outline/(弧+主线), chapters/(章节摘要), open_loops.md(伏笔) |
| **角色层** | 谁在参与，什么状态 | `characters/` | {name}.md(5 模块档案), relationships.md(关系网) |
| **世界层** | 什么能做什么不能做 | `world/` | power_system, geography, factions, rules |
| **读者层** | 市场想看什么 | `reader/` | feedback/(情绪/人气/不满/期待), comments/(段落级评论) |
| **风格层** | 怎么写才像原作 | `style/` | narrative, vocabulary, rhythm, anchors.md(原文锚点), .build/stats.json |
| **文本层** | 原始文字 | `text/` | ch{NNNN}.md(纯正文) |

**导航式检索**：AI 续写时从 `guide.md` 出发，按需层层展开——全局主线 → 当前弧 → 近章摘要 → 角色/设定 → 原文。不是一次加载全部，而是按场景类型选择性读取。

### 剧情层的三级递进

剧情层是最核心的一层，采用三级摘要结构：

```
全局主线 (plot_lines.md)     ← 方向感：接下来往哪走
    ↓
弧级摘要 (arc_XX.md)        ← 上下文：当前弧的核心冲突和转折
    ↓
章节摘要 (ch{NNNN}.md)      ← 细节：最近几章发生了什么
    ↓
原文 (text/ch{NNNN}.md)     ← 精确衔接：上一章最后几段
```

### 风格层的定量+定性

风格层同时包含两类数据，缺一不可：

- **定量基线** (`stats.json`)：平均句长 40.8 字、对话占比 41.5%、"道"系标签 84% —— 验证时用来画红线
- **定性分析** (`narrative/vocabulary/rhythm.md`)：叙事特征、禁忌词、节奏偏好 —— 写作时用来指导风格
- **原文锚点** (`anchors.md`)：从原文精选的示范段落 —— 给 LLM 具体的模仿对象

## 五、写作 Skill 架构

### 核心公式

```
续写 = Research（从 KB 提炼上下文）
     + Planning（写什么 + 怎么写）
     + Generation（在设计图下生成正文）
     + Verification（独立验证 + 反馈修复）
```

### 9 步流程

```
Research:   Step 1 读 guide → Step 2 生成 Context Bundle (~3KB)
Planning:   Step 3 大纲（写什么）→ Step 4 用户确认 → Step 5 Scene Plan（怎么写）
Generation: Step 6 写正文 → Step 7 保存
Verify:     Step 8 自动 L1 检测 → Step 9 根据结果询问用户
```

### 三个中间产物

写作质量的关键不是 prompt 多复杂，而是**中间产物的质量**：

| 产物 | 解决什么问题 | 体积 |
|------|-------------|------|
| **Context Bundle** | KB ~35KB 压缩为 ~3KB，Writer 只读 Bundle 不读原始 KB | ~3KB |
| **Scene Plan** | 大纲只规划"发生什么"，Scene Plan 规划"怎么写"（6 维度） | ~500 字/场景 |
| **Style Anchors** | 原文片段作为模仿对象，而非仅靠抽象规则 | 3-5 段原文 |

Scene Plan 的 6 维度：叙事视角距离、情绪表达方式、对话风格、节奏控制、细节来源、段落融合规划。

所有中间产物**落盘到 `drafts/`**，修复时重新加载，防止 Plan Drift（在"另一套计划"下修复旧文章）。

### Writer-Reviewer 隔离

```
Writer（当前 Claude 会话）         Reviewer（独立 claude -p 进程）
    │                                   │
    │  生成 drafts/ch{N}.md             │  读取 drafts/ch{N}.md
    │                                   │  + style/.build/stats.json
    │                                   │  + text/ch{N}.md (原文，如有)
    │                                   │  + guide.md (书籍规则)
    │                                   │
    │                                   │  → verification.md (报告)
    │                                   │  → feedback.md (修复建议)
    │  读取 feedback.md                 │
    │  在 Scene Plan 下修复              │
    │                                   │
    ←─── 信息流单向：审核→写作 ────────→
```

**为什么隔离**：同一上下文自审无效（"自己改卷"总会自证正确）。物理隔离后 Reviewer 看不到 Writer 的推理过程，Writer 看不到 Reviewer 的评分标准。

### 四层验证

| 层 | 本质 | 类比 | AI 调用 |
|----|------|------|---------|
| L1 | 定量指标 vs 基准线 | 编译器（格式检查） | 0 次，<5s |
| L2 | 风格分析 | 编辑（质量评价） | 1 次，~60s |
| L3 | 读者对齐（爽点/槽点/角色/期待） | 市场分析师 | 1 次，~60s |
| L4 | 跨章重复 + 角色一致 | 连续性校验 | 0 次 |
| — | 盲测校准（`--calibrate`） | 校准工具 | 1 次（仅校准用） |

**分层触发**：L1 每次写作后自动运行（Step 8）；L2/L3/L4 由用户手动触发（`--verify`）或自动循环（`--auto`）。盲测降级为 `--calibrate` 模式，仅在有原文时作为校准参考。

**评分**：

```
单章+读者数据：  L1×0.35 + L2×0.40 + L3×0.25
单章无读者数据：  L1×0.45 + L2×0.55（向后兼容）
多章+读者数据：  L1×0.25 + L2×0.35 + L3×0.20 + L4×0.20
多章无读者数据：  L1×0.40 + L2×0.45 + L4×0.15（向后兼容）
A (≥90) 优秀 | B (80-89) 良好 | C (70-79) 及格 | D (<70) 不合格
```

### 修复循环

修复不是"重写"，而是在**既定设计图下施工**：

```
feedback.md ──→ 提取问题清单（FAIL > WARN > 建议）
scene_plan  ──→ 约束不变（不改大纲、不改场景结构）
draft       ──→ 针对具体问题逐项修复
             ──→ 保存覆盖 → 再次验证
```

## 八、关键设计决策

### 为什么要六层而不是直接存原文？

百万字塞不进上下文。六层解构后，续写一章只需读 ~3KB Context Bundle + 相关角色/设定文件，总计 ~10KB，远小于原始 ~35KB 知识库或百万字原文。

### 为什么 `text/` 和 `reader/comments/` 分开？

- `text/`：AI 读故事时只看正文，不被评论干扰
- `reader/comments/`：需要参考读者反应时，精确定位"读者在对哪段话评论"
- 原始混合 markdown 仍保留在 `output/` 目录作为数据源

### 为什么 Scene Plan 独立于大纲？

大纲回答"发生什么"，Scene Plan 回答"怎么写"。小说不是写事件序列，而是写**怎么呈现事件**。缺少 Scene Plan 时，LLM 会退回训练语料均值（"肝胆俱裂"、"震惊失色"），有了 Scene Plan 后每个场景都有具体的视角距离、情绪表达方式、对话风格指引。

### 为什么 Writer 不自审？

同一上下文自审无效——Writer 知道自己要写什么，检查时会"自证正确"。物理隔离（`claude -p` 独立进程）后，Reviewer 不知道 Writer 的推理过程，只看到文本本身，评判更客观。

### 为什么 L1 自动运行而 L2 手动？

L1 是"编译器"——检查格式合法性（禁忌词 0 个？句长达标？），<5s，0 费用，**没有理由不跑**。
L2 是"编辑"——AI 深度分析，~90s + 费用，需要**用户按需决定**。
自动检测 ≠ 自动修复：Step 9 将结果呈现给用户，由用户决定是否修复。

### 为什么中间产物要落盘？

如果 Context Bundle 和 Scene Plan 只在上下文中，修复时它们会蒸发（上下文被压缩/新会话）。落盘到 `drafts/` 后，`--revise` 能重新加载完整设计图，在**同一套计划**下修复，而不是"另一套计划下改旧文章"（Plan Drift）。

### 为什么验证时注入书籍规则？

L2 Reviewer 不知道每本书的特殊规则。例如《玄鉴仙族》的穿越者角色允许在内心独白中使用"社畜""互联网"等现代词汇——如果不注入这条规则，Reviewer 会将其标记为"用词不当"。从 `guide.md` 提取书籍规则注入 L2 prompt，确保审核标准与写作规则一致。
