# 写作 Skill 方案：提取与索引构建

> 日期：2026-02-08
> 状态：**已实施**（代码/Skill/验证系统全部完成，知识库内容待 T2 全量补跑）
> 目标：构建通用的小说续写 Skill，从已采集的小说 markdown 数据中提取结构化信息，构建知识库，并配套独立的三层验证体系

---

## 一、设计原则

1. **通用性**：知识库结构是模板，适用于任意小说，不绑定某本书
2. **信息不丢失**：评论保留段落级粒度，保持与原文的精确映射关系
3. **可扩展**：百万字级小说的世界观、人物关系等信息量巨大，目录结构需支持多文件扩展
4. **导航式检索**：AI 通过索引文件层层展开上下文，而非一次性加载全部内容

---

## 二、核心模型：小说五层解构

小说不等于文本。一部小说是五层结构的叠加：

```
文本层（文字）       — 原始的文字内容
剧情层（发生了什么） — 故事是怎么一步步走到现在的
角色层（谁参与）     — 谁在参与，他们是什么样的人，处于什么状态
世界层（规则与设定） — 故事发生在什么世界，有什么规则和限制
读者层（读者期待）   — 读者想看什么，喜欢什么，讨厌什么
```

预处理就是把这五层全部抽出来，再加一层风格分析（怎么写才像原作）。

**续写能力 ≈ 预处理质量 × 上下文调度能力**。预处理是整个项目最难、最关键、最决定上限的阶段。它不是简单的摘要，而是**小说结构化建模**——把一部小说解构成 AI 可以理解的形态。

### 六大块与目录映射

```
剧情结构   → 故事走到哪      → plot/（outline/ + chapters/ + timeline/ + open_loops.md）
角色系统   → 谁在参与        → characters/
世界模型   → 能做什么不能做什么 → world/
读者模型   → 市场想看什么    → reader/（feedback/ + comments/）
风格模型   → 怎么写才像      → style/
```

> 注：「未完成事项」归入剧情结构，作为 `plot/open_loops.md` 存在。

这六大块完成后，AI 才算真正"读过这本小说"。

## 五、各层详细说明与模板

### 5.1 剧情层（Plot Layer）

这是最核心的一层。目标是让 AI 知道**故事是怎么一步步走到现在的**。注意：不是简单的摘要，而是**剧情结构化**。

剧情层采用三级递进的摘要结构，从宏观到微观：

| 级别 | 粒度 | 位置 | 说明 |
|------|------|------|------|
| **全局主线** | 全书 | `plot/outline/plot_lines.md` | 续写"方向感"的来源 |
| **弧级摘要** | 20~50 章 | `plot/outline/arc_XX.md` | 对续写极其重要 |
| **章节摘要** | 单章 | `plot/chapters/chNNNN.md` | 续写时最常读取 |

AI 续写时的查询路径：全局主线 → 找到当前所在弧 → 回顾最近章节摘要 → 需要时读原文。

#### 5.1.1 章节摘要模板（micro summary）

每章 150~300 字，**是结构化条目，不是叙述文**：

```markdown
# 第N章 {章节名}

## 关键事件
- 事件1
- 事件2

## 新登场角色
- 角色A：身份/特征简述

## 已有角色出场
- 角色B：本章做了什么
- 角色C：本章做了什么

## 关系变化
- A ↔ B：从陌生 → 初步信任

## 重要物品
- {物品名}：出现场景/用途

## 新增设定
- （如有新的世界观/修炼体系/势力信息）

## 伏笔/悬念
- （如有未解开的线索）

## 一句话摘要
{一句话概括本章核心}
```

#### 5.1.2 弧级摘要模板（arc summary）

每 20~50 章为一个 story arc（如"学院篇"、"战争篇"、"逃亡篇"），这对续写**极其重要**：

```markdown
# {弧名称}（ch{起始} ~ ch{结束}）

## 核心冲突
本弧的主要矛盾是什么

## 主角成长变化
主角从什么状态变成什么状态

## 重要转折点
- chXX：转折事件描述
- chXX：转折事件描述

## 新世界信息
本弧揭示的新设定/新区域/新势力

## 本弧结局
本弧如何收束，留下什么悬念
```

#### 5.1.3 全局主线模板（global plot lines）

这是续写"方向感"的来源。每条主线独立追踪：

```markdown
# 全局主线追踪

## 主线A：{主线名，如"主角成长"}
- 起点：chXX，起始状态描述
- 当前进展：已推进到 chXX，当前状态
- 未完成部分：还需要发生什么

## 主线B：{主线名，如"世界真相"}
- 起点：chXX，首次出现线索
- 当前进展：已揭示到什么程度
- 未完成部分：还有哪些谜团

## 主线C：{主线名，如"反派阴谋"}
- 起点：chXX，反派首次出现/暗示
- 当前进展：反派的计划推进到哪一步
- 未完成部分：最终对决尚未发生
```

#### 5.1.4 伏笔与未完成事项（`plot/open_loops.md`）

这是续写 agent 的"任务列表"，是续写剧情的燃料。单独维护：

```markdown
# 伏笔与未完成事项

## 未揭开的谜团
- chXX 提到的神秘组织身份未明
- ...

## 未兑现的承诺
- 主角在 chXX 答应过某角色的事
- ...

## 未完成的目标
- 主角寻找某物
- ...

## 预埋的伏笔
- chXX 出现的某个物品/线索尚未回收
- ...

## 未出场但被提及的角色
- chXX 提到的某人尚未正式出场
- ...
```

### 5.2 角色层（Character Layer）

这是决定"像不像原作"的关键。大模型最容易崩的地方就是**人物行为不符合人设**，所以人物库必须非常重。

每个角色抽取 5 个模块：

#### 角色档案模板

```markdown
# {角色名}

## 1. 基本设定（静态）

人物的"本质"，不随剧情变化：

- 性格：
- 价值观：
- 恐惧：
- 执念：
- 说话风格：

## 2. 角色弧光（成长轨迹）

如果没有这个，AI 会让角色"突然变人"——前一章还懦弱，后一章就无所畏惧：

- 初始状态：懦弱
- chXX：开始反抗
- chXX：主动承担责任
- 当前阶段：成长中期

## 3. 关系演化（动态）

不是"谁和谁是朋友"这种静态标签，而是**随时间变化的关系轨迹**。这是避免感情线崩坏的关键：

### {角色名} ↔ {另一角色}
- chXX 陌生
- chXX 同伴
- chXX 信任危机
- chXX 关系修复

### {角色名} ↔ {另一角色}
- ...

## 4. 个人时间轴

记录该角色经历的所有关键事件：

- chXX 觉醒能力
- chXX 重伤
- chXX 关键决定
- chXX 杀死某人

## 5. 当前状态（写作时 90% 会读取这一块）

- 位置：
- 身体状态：
- 心理状态：
- 与谁同行：
- 未完成目标：
```

#### 人物关系网模板（`relationships.md`）

```markdown
# 人物关系网

## 家族关系
- A 是 B 的父亲
- C 是 D 的师妹

## 盟友/同伴
- A ↔ B：同伴（chXX 起）

## 敌对关系
- A ↔ C：敌对（chXX 起，因为...）

## 暧昧/感情
- A ↔ D：chXX 开始有好感
```

### 5.3 世界层（World Model）

很多续写失败不是剧情问题，而是**设定崩坏**。世界观必须结构化。

#### 5.3.1 力量体系（`power_system.md`）

```markdown
# 力量体系

## 修炼等级
- 等级1：描述
- 等级2：描述
- ...

## 等级限制
每个等级能做什么、不能做什么

## 修炼代价
提升等级需要付出什么

## 能力上限
当前已知的最强存在是什么级别

## 已出现的重要能力/法术
- {能力名}：效果，使用者，首次出现章节
- ...
```

#### 5.3.2 地理空间（`geography.md`）

```markdown
# 地理空间

## 主要区域/国家
- {区域名}：简述

## 重要城市/地点
- {地点名}：位于哪里，有什么特殊之处

## 空间距离关系
- A 到 B：大约多远/多久的路程

## 已发生关键事件的地点
- {地点}：chXX 发生了什么
```

#### 5.3.3 组织势力（`factions.md`）

```markdown
# 组织势力

## {势力名}
- 目标：
- 立场：
- 与其他势力的敌对/合作关系：
- 已知成员：
- 在故事中扮演的角色：

## {势力名}
- ...
```

#### 5.3.4 规则与限制（`rules.md`）

这是**不能打破的世界规则**，续写时必须遵守：

```markdown
# 世界规则与限制

## 硬性规则（绝对不能违反）
- 例：死人不能复活
- 例：时间旅行只能一次
- 例：皇室不能公开出手

## 软性限制（通常情况下如此，但有例外）
- 例：筑基期不能飞行（但某特殊法器除外）

## 社会规则/禁忌
- 例：修士不得干预凡人国家
```

### 5.4 读者层（Reader Feedback）

评论数据是**杀手级资产**。从段落级评论中提炼四种信息，用于"市场反馈引导写作"。

#### 5.4.1 情绪触发点（`reader/feedback/emotions.md`）

为什么读者觉得爽/感动？续写时可以复用类似的手法：

```markdown
# 情绪触发点

## 读者最喜欢的场景类型
- 逆袭打脸（高赞典型：chXX 第N段，"终于等到这一刻"）
- 情感互动（高赞典型：chXX 第N段，"这段太甜了"）
- 热血燃向（高赞典型：...）

## 触发强烈情感的具体段落
- chXX 第N段：原文摘录... → 读者反应摘录...（👍 XXXX）
- ...
```

#### 5.4.2 高赞角色排行（`reader/feedback/popular_characters.md`）

这会影响续写时的角色出场频率：

```markdown
# 角色人气

## 最受欢迎角色
1. {角色名}：读者喜欢的原因
2. ...

## 最讨厌角色
1. {角色名}：读者讨厌的原因
2. ...

## 读者最关注的角色关系
- A ↔ B：读者对这对关系的态度
- ...
```

#### 5.4.3 读者不满点（`reader/feedback/complaints.md`）

续写时必须避的坑：

```markdown
# 读者不满点

## 节奏问题
- 例：chXX~chXX 这一段节奏太慢，大量读者抱怨

## 设定问题
- 例：战力体系在 chXX 之后出现崩坏

## 感情线问题
- 例：A 和 B 的感情线拖太久

## 角色行为问题
- 例：某角色在 chXX 的行为被认为不符合人设
```

#### 5.4.4 读者期待（`reader/feedback/expectations.md`）

这是"市场导向"，续写的方向参考：

```markdown
# 读者期待

## 剧情期待
- 希望揭开某个谜团
- 希望主角完成复仇

## 角色期待
- 希望某 CP 在一起
- 希望某角色回归

## 设定期待
- 希望了解更多世界真相
```

### 5.5 风格层（Style Model）

如果没有风格分析，续写出来的内容不像原作。很多人忽略这一层。

#### 5.5.1 叙事特征（`narrative.md`）

```markdown
# 叙事特征

## 叙事视角
第一人称 / 第三人称有限 / 第三人称全知 / 混合

## 句长分布
- 平均句长：约XX字
- 短句（<10字）占比：XX%
- 长句（>50字）占比：XX%
- 特点：（如"偏好短句营造紧张感"）

## 对话比例
- 对话占全文比例：约XX%
- 对话风格：（如"简短有力" / "长段独白较多"）

## 场景描写特征
- （如"重环境渲染" / "重心理描写" / "重动作描写"）
```

#### 5.5.2 用词特征（`vocabulary.md`）

```markdown
# 用词特征

## 文风标签
（如"古典典雅" / "口语化" / "冷峻克制" / "热血中二"）

## 常用意象
- 意象1：出现频率和典型用法
- 意象2：...

## 口头禅/特征用语
- 某角色常说的话
- 作者偏爱的表达方式

## 禁忌用词
原作中从不出现的现代词汇/不符合世界观的表达
```

#### 5.5.3 节奏特征（`rhythm.md`）

```markdown
# 节奏特征

## 场景切换频率
- （如"每章通常包含2~3个场景"）

## 高潮-低谷分布
- 典型模式：（如"每5~8章一个小高潮，每30~50章一个大高潮"）

## 章节结构习惯

### 5.7 关键设计决策

**为什么 `text/` 和 `reader/comments/` 都需要？**

- `text/`：AI 读故事时只看正文，不被评论干扰
- `reader/comments/`：AI 需要参考读者反应时，能精确定位到"读者在对哪段话评论"
- 两者通过章节编号（`ch0001`）互相关联
- 原始混合 markdown 仍保留在 `output/` 目录作为数据源，不重复存储

**为什么不预设 arc 分组？**

故事弧的划分需要通读全书后才能确定。`plot/chapters/` 先用扁平结构，Phase 3 提取大纲时再划分弧并生成 `plot/outline/arc_XX.md`。

**为什么世界观/人物/时间线/风格都用目录？**

百万字级小说的信息量巨大。以玄鉴仙族为例：群像文涉及几代人物、复杂的修炼体系和势力关系。单文件无法容纳，每个目录下有 `index.md` 作为入口提供导航。

### novel-write Skill 职责（Phase 4-5 实现）

**统一入口**：所有写作相关操作（续写、验证、修复、反哺）统一通过 `/novel-write` Skill 调用。Skill 内置了三层验证体系，写作和审核在同一 Skill 中完成，但通过独立进程实现上下文隔离。

#### 7 种模式

| 模式 | 命令 | 说明 |
|------|------|------|
| 正常续写 | `/novel-write KB --chapter N` | 9 步流程（含自动 L1 验证） |
| 带提示续写 | `/novel-write KB --hint "方向"` | 同上，用户提示融入大纲 |
| 修复 | `/novel-write KB --revise N` | 4 步：加载设计图+反馈 → 分析问题 → 修复正文 → 保存 |
| 验证 | `/novel-write KB --verify N` | 调用 `verify/batch_verify.py`（独立进程） |
| 自动循环 | `/novel-write KB --auto --chapter N` | 写作→验证→修复→验证，循环直到 ≥ B 或 3 轮 |
| 反哺 | `/novel-write KB --promote N` | 将验证通过的草稿纳入正式知识库 |
| 验证历史 | `/novel-write KB --history` | 查看验证历史记录 |

#### 9 步续写流程（v2 架构）

```
Step 1: 读 guide.md
Step 2: Research → 生成 Context Bundle（保存到文件）
Step 3: 大纲（写什么）
Step 4: 等待用户确认
Step 5: Scene Plan + Style Anchors（怎么写）（保存到文件）⭐
Step 6: 写正文
Step 7: 保存草稿
Step 8: 自动运行 Layer 1 定量检测 ⭐
Step 9: 根据结果询问用户 ⭐
```

| 步骤 | 说明 |
|------|------|
| Step 1 | 读 `guide.md`，如不存在则自动生成（知识库导航 + 续写铁则 + 场景加载策略） |
| Step 2 | **Research → Context Bundle**：读 KB ~35KB → 提炼 ~3KB 高密度写作上下文，保存到 `drafts/context_bundle_ch{NNNN}.md` |
| Step 3 | **大纲（只回答"写什么"）**：只读 Bundle，生成事件序列，不含写法指导 |
| Step 4 | **等待用户确认**：展示大纲，用户可调整 |
| Step 5 | **Scene Plan + Style Anchors（怎么写）**⭐：为每个场景生成 6 维度写法规划 + 从锚点库选取原文示范，保存到 `drafts/scene_plan_ch{NNNN}.md` |
| Step 6 | **写正文**：按材料优先级参照 Scene Plan → Style Anchors → Bundle S3 硬指标 → S4 禁忌清单 |
| Step 7 | **保存草稿**：`drafts/ch{NNNN}.md` |
| Step 8 | **自动 L1 验证**⭐：无需用户确认，自动运行 `batch_verify.py --layer 1`（<5s，0 次 AI 调用） |
| Step 9 | **根据结果询问用户**⭐：有 FAIL → 强提示修复；只有 WARN → 温和提示；全 PASS → 流程结束 |

**核心设计理念**：

- Step 1-7 是**写作流程**，Step 8-9 是**内置质量关卡**
- L1 是"编译器"（检查格式合法性），不是"编辑"（评价内容质量），必须每次自动运行
- L2/L3 是"编辑"（AI 深度分析，耗时 ~90s + 费用），由用户通过 `--verify` 手动触发
- 自动检测 ≠ 自动修复：Step 9 将检测结果交给用户决定是否修复

#### 三层保障（写作质量）

- **Context Bundle**：~35KB KB 压缩为 ~3KB，Writer 只读 Bundle，不直接读知识库原文
- **Scene Plan**：大纲回答"写什么"，Scene Plan 回答"怎么写"（视角距离/情绪表达/对话风格/节奏/细节/段落融合共 6 维度）
- **Style Anchors**：原文片段作为具体模仿对象（"写成这样"），而非仅靠抽象规则（"不要直白情感词"）

#### 中间产物落盘

所有中间产物保存到文件，支持修复循环时重新加载（防止 Plan Drift）：

| 文件 | 生成时机 | 用途 |
|------|----------|------|
| `drafts/context_bundle_ch{NNNN}.md` | Step 2 | 写作上下文包（~3KB） |
| `drafts/scene_plan_ch{NNNN}.md` | Step 5 | 场景设计图 + 风格锚点 |
| `drafts/ch{NNNN}.md` | Step 7 | 章节正文草稿 |
| `drafts/ch{NNNN}_verification.md` | --verify | 三层验证报告 |
| `drafts/ch{NNNN}_feedback.md` | --verify (C/D) | 修复反馈（评级 C/D 时生成） |
| `drafts/.verify_history.json` | --verify | 累积验证历史 |

#### 三层验证体系（已集成到 Skill 中）

验证系统通过 `verify/batch_verify.py` 实现，与写作流程同属 `/novel-write` Skill，但通过 `claude -p` 子进程在独立上下文中执行。

| 层级 | 内容 | AI 调用 | 耗时 |
|------|------|---------|------|
| Layer 1 | 纯 Python 定量检测（12 项指标 vs `stats.json` 基准线） | 0 次 | <5s |
| Layer 2 | 盲测对比 + 深度风格分析（注入 `guide.md` 书籍规则防误判） | 2 次 `claude -p` | ~90s |
| Layer 3 | 跨章一致性（重复表达 + 角色状态追踪，2+ 章时触发） | 0-1 次 | ~30s |

**评分系统**：

```
多章：总分 = L1 × 40% + L2 × 45% + L3 × 15%
单章：总分 = L1 × 45% + L2 × 55%
无原文时：L2 中风格分析独占 100%（不降权）

A (90-100) 优秀 | B (80-89) 良好 | C (70-79) 及格 | D (<70) 不合格
```

**验证模式分层**：

| 模式 | 触发方式 | 验证层级 | 用途 |
|------|----------|----------|------|
| 默认模式 | Step 8 自动执行 | 仅 L1 | 每次写作后自动检查格式合法性 |
| verify 模式 | `--verify N` 手动触发 | L1 + L2 + L3 | 深度质量评估 |
| auto 模式 | `--auto` | 全自动循环 | 写作→L1+L2验证→修复→再验证，≤3 轮 |

**关键修复（2026-02-08）**：

- L2 prompt 注入 `guide.md` 中的书籍特定规则，防止合法用词被误判（如穿越者角色的现代词汇）
- 无原文对比时（新章节），风格分析得分不再被盲测权重稀释

#### 上下文隔离

- Writer 和 Reviewer 在不同进程中工作（`verify/batch_verify.py` 通过 `claude -p` 子进程调用 AI）
- 信息流单向：审核 → 写作（feedback 文件），Writer 不能访问审核的评分标准和盲测细节
- Writer 不自审，质量审核完全由验证脚本独立完成
- Reviewer 加载 `guide.md` 书籍规则，避免将符合规则的内容误判为问题

#### 续写铁则

- **3 条通用规则**：每句多重信息、章首/尾匹配偏好、段落融合（对话与叙述必须交织）
- **书籍特定规则**：从 `style/` 文件动态提取（禁忌词、标签偏好、时间表达等），不在 Skill 中硬编码
- 验证时从 `guide.md` 提取书籍规则注入 L2 prompt，确保审核标准与写作规则一致

#### 修复流程

修复流程与正常续写完全不同——Writer 在**既定设计图下施工修复**，不重新规划：

1. 加载已保存的设计图（scene_plan + context_bundle + draft + feedback）
2. 从 feedback 提取问题清单（FAIL > WARN > AI 建议）
3. 在 Scene Plan 约束下修复正文（不改大纲、不改场景结构）
4. 保存修复后的草稿

#### 完整写作-审核循环

```
默认模式（推荐）：
  /novel-write KB --chapter N
  → Step 1-7 写作 → Step 8 自动 L1 → Step 9 询问用户
  → 如有 FAIL 且用户同意 → 自动修复 → 再次 L1
  → 满意后手动触发 L2：/novel-write KB --verify N

手动深度验证：
  /novel-write KB --verify N → 查看 verification.md

修复：
