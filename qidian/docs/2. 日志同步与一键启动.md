# 日志同步与一键启动

> 日期：2026-02-07
> 状态：**已完成** — RPC 轮询日志 + 一键启动脚本

---

## 一、方案概述

### 通信链路

```
Android App → 日志写入内存缓冲区（logBuffer, 最大 5000 条）
                              ↑ 自动，无需网络
WSL2 log_poller.py (127.0.0.1:12345) → ADB forward → RPC getLogs → 增量拉取 → 写入 logs/qdhook.log
```

WSL2 与 Windows 网络已打通，`adb forward` 端口可从 WSL2 直接访问 `127.0.0.1:12345`，无需任何中间桥接。

**优势：**
- 不需要额外 TCP 服务和 `adb reverse`
- 复用已有的 RPC 通道（`localabstract:qdhook_rpc`）
- 日志存在内存缓冲区，poller 断连不丢失（5000 条容量）
- 支持 `since` 增量拉取，不重复

## 二、关键组件

### 2.1 手机端：内存日志缓冲区

**文件**：`MainHook.java`

```java
// 缓冲区配置
private static final int MAX_LOG_BUFFER = 5000;
private static final LinkedList<String> logBuffer = new LinkedList<>();

// 所有日志统一写入缓冲区
private static void logRemote(String tag, String message) {
    String logJson = new JSONObject()
        .put("timestamp", System.currentTimeMillis())
        .put("tag", tag)
        .put("thread", Thread.currentThread().getName())
        .put("message", message)
        .toString();

    synchronized (logBuffer) {
        logBuffer.addLast(logJson);
        while (logBuffer.size() > MAX_LOG_BUFFER) {
            logBuffer.removeFirst();
        }
    }
}
```

### 2.2 RPC 命令：getLogs

**请求**：
```json
{"cmd": "getLogs", "limit": 500, "since": 1770364989680, "tag": ""}
```

**参数**：
| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| limit | int | 200 | 最多返回条数 |
| since | long | 0 | 只返回此时间戳之后的日志 |
| tag | string | "" | 过滤关键词（匹配 tag + message） |

**响应**：
```json
{
  "success": true,
  "count": 107,
  "total": 5000,
  "maxTimestamp": 1770365089342,
  "data": [
    {"timestamp": 1770364937269, "tag": "QDHook", "thread": "QDHook-Delay", "message": "=== 开始安装搜索 Hook ==="},
    ...
  ]
}
```

**关键设计决策**：日志按时间升序返回（最旧在前）。实现方式是先从缓冲区尾部向前收集，再反转后输出。

### 2.3 PC 端：log_poller.py

**文件**：`scripts/log_poller.py`

**运行环境**：WSL2 Python3（直连 ADB forward 端口）

**工作流程**：
1. 连接 `127.0.0.1:12345`（ADB forward 到手机 RPC）
2. 发送 `getLogs`，携带 `since` 参数实现增量拉取
3. 格式化日志行写入 `logs/qdhook.log`
4. 每 2 秒轮询一次
5. 固定文件名，每次启动覆盖写入

**日志输出格式**：
```
[2026-02-06 16:02:17.269] [QDHook-Delay] [QDHook] === 开始安装搜索 Hook ===
[2026-02-06 16:02:17.275] [DefaultDispatcher-worker-1] [QDProbe] NETWORK_CALL | enqueue | https://...
```

## 三、一键启动脚本

**文件**：`start.sh`（项目根目录）

```bash
./start.sh
```

**自动执行步骤**：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1/5 | `am force-stop` | 强制停止 App |
| 2/5 | `monkey` 启动 | 避免 `am start` 的 -92 错误 |
| 3/5 | `sleep 18` | 等待 360 加固脱壳 + Hook 初始化 |
| 4/5 | `adb forward` | 打通 RPC 通道 |
| 5/5 | 启动 log_poller | 持续同步日志到 `logs/qdhook.log` |

脚本在步骤 4 后会验证 RPC 连接，失败则报错退出。

**输出示例**：

## 四、踩坑记录

### 4.1 RPC JSON 紧凑格式（重要）

**问题**：`handleRpcCommand` 返回的 JSON 使用 `toString(1)` 格式化输出（便于调试），但 RPC 协议以 `\n` 作为消息分隔符。当响应是大 JSON（如章节列表，含数百个章节）时，格式化后的 JSON 包含换行符，客户端在第一个 `\n` 处就停止读取，导致 JSON 被截断。

**解决**：在 `handleClient()` 方法中，发送响应前将 JSON 转换为紧凑格式：
- 先尝试 `new JSONObject(response).toString()` 去除所有换行和缩进
- 失败时 fallback 为 `response.replace("\n", " ").replace("\r", "")`

**实现位置**：`MainHook.java:1641-1670` → `handleClient()` 方法

> **注意：此 fix 必须在 `handleClient()` 统一处理，而非每个 handler 单独处理。** 如果未来新增 RPC handler 返回格式化 JSON（`toString(1)`），`handleClient()` 会自动转换为紧凑格式，handler 不需要关心这个问题。但如果 handler 返回的不是合法 JSON（如纯文本错误消息），fallback 逻辑会用空格替换所有换行符。

### 4.2 getLogs 返回 0 字节

**现象**：`getStatus` 正常返回，但 `getLogs` 返回 0 字节。

**根因**：初版 `handleGetLogs` 使用 `LinkedList.get(i)` + 复杂索引逻辑，JSON 解析异常未被捕获导致方法静默崩溃。

**解决**：简化为 `ArrayList snapshot` + 快照拷贝 + 所有 JSON 操作包在 try-catch 内。

### 4.3 日志顺序反了

**现象**：日志文件中最新的在前面，不符合阅读习惯。

**根因**：`handleGetLogs` 从缓冲区尾部向前遍历，直接 `arr.put(obj)`。

**解决**：先收集到 `ArrayList<JSONObject> matched`，再从尾到头添加到 JSONArray，实现时间升序输出。

### 4.4 ADB forward 失效

**现象**：App 重启后 poller 报 "RPC connection failed"。

**原因**：`adb forward` 对应的 LocalSocket 在 App 进程死亡后失效，新进程的 socket 名称相同但 forward 映射需要重建。

**解决**：每次 App 重启后需重新执行 `adb forward`，`start.sh` 已自动处理。
