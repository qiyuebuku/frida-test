## 一、目标

通过 `bookId` 获取章节目录，再通过 `bookId + chapterId` 获取章节正文，实现完整的 **搜索 → 书籍详情 → 章节目录 → 阅读正文** 链路，**100% 免 UI**。

> **前置条件已消除** ✅：`bllVInstance` 在 App 启动时自动捕获（App 恢复阅读状态会触发 bll.v hook），`ChapterItem` 可通过章节列表 API 的 JSON 数据自动构造，**不再需要用户手动进入阅读页面**。

## 三、实际使用的 API 和解密方案

### 3.1 API 端点（已确认）

| 端点 | 方法 | 用途 | 参数 |
|------|------|------|------|
| `/argus/api/v3/chapterlist/chapterlist` | GET | 章节目录 | `bookId`, `timeStamp=0`, `requestSource=0`, `md5Signature=`, `extendchapterIds=` |
| `/argus/api/v2/bookcontent/safegetcontent` | GET | 章节内容（加密） | `bookId`, `chapterId` |

> 注意：不需要 `getkey` API，解密完全由 App 内部的 `bll.v` 类完成。

### 3.2 解密方案（方案 B：App 内部解密）

最终采用**方案 B**（触发 App 内部解密），而非方案 A（自行解密）。

**方案 A 被否决的原因**（重要，避免重复踩坑）：
- App **不使用** `javax.crypto.Cipher` 进行章节内容解密 — Cipher Hook 的 `trackedCiphersCount` 始终为 0
- 之前文档中记录的 `AES/CBC/PKCS5Padding`、`DESede/CBC/PKCS5Padding` 等 Cipher 操作用于**安全检测/设备指纹**等辅助功能，与章节解密无关
- `pf.cihai.search` 类在当前 App 版本中**已不存在**
- `getkey` API **不需要**调用，密钥获取和派生逻辑完全封装在 `bll.v` 内部，外部无法复制

**方案 B 被采用的原因**：
- 解密由 `bll.v` 类的内部方法链完成（L → K → R），可通过反射调用触发
- afterCall hook 可自动捕获解密后的明文
- 绕过了密钥获取/派生这一黑盒环节

### 3.3 `bll.v` 方法调用链（核心发现）

> **类全名**：`com.qidian.QDReader.component.bll.v`（混淆后名称）

App 正常读取章节时的调用顺序：

```
bll.v.L(bookId, ChapterItem)  → 返回 ChapterContentItem（检查/准备本地文件）
bll.v.K(bookId, ChapterItem)  → 返回 .qd 文件路径（获取加密文件路径）
bll.v.R(bookId, ChapterItem)  → 返回 .cc 文件路径（执行解密，生成缓存文件）
```

有时还会出现 B → K → R 的重试模式。

**关键点（必读）**：
- **三个方法必须按 L→K→R 顺序调用**，仅调用 R 返回 null
- **实际上是 L 内部触发了解密**：afterCall hook 在 L 方法返回前就已经捕获了明文内容
- R 方法只是返回解密后的缓存文件路径（.cc 文件），并不是执行解密的地方
- L、K、R 的参数签名相同：`(long bookId, ChapterItem item)` 或 `(int bookId, ChapterItem item)`（通过反射匹配）

### 3.4 解密后的数据格式

afterCall hook 从 `bll.v` 方法链返回的 `ChapterContentItem` 对象中提取 `Content` 字段，即为章节正文。

- 格式：纯文本
- 分段：`\r\n` 换行
- 缩进：全角空格（`\u3000`）
- 典型长度：2000-4000 字符/章

## 四、实际实施方案（方案 B：App 内部解密）

### `getChapterContent` 完整流程

```
1. 通过 OkHttpClient 调用 safegetcontent API 获取加密数据
2. 将加密数据保存到 App 的 .qd 文件路径
3. 克隆一个真实的 ChapterItem，修改 ChapterId 为目标章节
4. 按顺序调用 bll.v.L → bll.v.K → bll.v.R
5. afterCall hook 自动捕获 bll.v.R 返回的 ChapterContentItem 中的 Content
6. 从 capturedChapterContents 缓冲区读取解密后的明文
```

### 前置条件（全部自动完成，无需手动操作）

- `savedOkHttpClient` 已捕获（App 启动后自动从 API 请求中捕获）
- `bllVInstance` 已捕获（App 启动时恢复阅读状态会自动触发 bll.v hook，无需手动进入阅读页面）
- `ChapterItem` 可通过章节列表 API 的 JSON 数据自动构造（使用 `ChapterItem(JSONObject)` 构造函数），**不再需要 chapterItems 模板缓存**

### ChapterItem 的三种获取方式（按优先级排序）

| 方式 | 说明 | 使用场景 | 代码位置 |
|------|------|---------|----------|
| **API JSON 构造（推荐）** | 用章节列表 API 的 JSON 数据通过 `ChapterItem(JSONObject)` 构造函数创建 | 所有场景，100% 免 UI | `constructChapterItemFromApi()` |
| **模板克隆（旧方案）** | 从 `chapterItems` 缓存中取真实 ChapterItem，反射复制全部字段后改 ChapterId | App 中已打开过阅读页面时 | `cloneChapterItem()` |
| **自动捕获** | App 正常阅读时 beforeCall hook 自动保存 ChapterItem 到 `chapterItems` 缓存 | 被动模式（用户手动阅读时） | `MainHook.java:1020-1048` bll.v beforeCall hook |

> **重要**：当前 `getChapterContent` 命令优先使用 API JSON 构造方式。只有在 API 构造失败时才会 fallback 到模板克隆。

### 关键实现细节

1. **ChapterItem 克隆**（踩坑教训）：
   - 不能创建最小化的 fake ChapterItem（只设 chapterId），会导致 `bll.v` 方法返回错误类型或 null
   - 必须从已捕获的真实 ChapterItem 通过**反射复制全部字段**，仅修改 ChapterId
   - 实现位置：`MainHook.java` → `cloneChapterItem()` 方法（约 2523 行）

2. **L → K → R 调用顺序**（不可省略）：
   - L 准备本地文件状态（内部触发解密），K 确认文件路径，R 返回缓存路径
   - 跳过 L/K 会导致 R 返回 null
   - 实现位置：`MainHook.java` → `triggerAppDecrypt()` 方法（约 3167 行）

3. **afterCall hook 自动捕获（范围说明）**：
   - **Hook 了 bll.v 类的全部公共方法**（非仅 L/K/R），跳过 Object 基类方法（toString/hashCode 等）
   - 任何方法返回值类名包含 `ChapterContentItem` 就触发提取，不依赖方法名匹配
   - 这使得 Hook 对 App 版本更新（方法改名）有天然容错能力
   - 提取动作是**同步的**：在 afterCall 回调中立即提取 Content 字段并存入 `capturedChapterContents`
   - 捕获的内容存入 `capturedChapterContents`（以 chapterId 为 key 的 ConcurrentHashMap）
   - hook 安装位置：`MainHook.java:1000-1082`

4. **.qd 文件保存路径**（硬编码格式）：
   - 加密数据必须保存到 App 期望的路径：`/storage/emulated/0/Android/data/com.qidian.QDReader/files/QDReader/book/0/{bookId}/{chapterId}.qd`
   - 路径格式不正确会导致 L 方法找不到文件
   - 目录通过代码自动创建（`mkdirs()`）
   - 代码位置：`MainHook.java` → `triggerAppDecrypt()` 方法中的文件路径拼接

## 五、RPC 调用方式

### getChapterList

```json
{"cmd": "getChapterList", "bookId": "1010868264"}
```

返回全部章节信息，包含 ChapterId、ChapterName、IsVip（P 字段，0=免费）等。

> **注意：API 响应有两种格式**（见下方说明），代码中需同时支持。

#### 章节列表 API 响应双格式（重要）

不同书籍的章节列表 API 会返回两种不同的 JSON 结构：

| 格式 | JSON 路径 | 结构 | 示例书籍 |
|------|----------|------|---------|
| 卷-章节结构 | `Data.Vs[].Cs[]` | Vs 为卷数组，每卷包含 Cs 章节数组 | 诡秘之主 (1010868264) |
| 扁平章节列表 | `Data.Chapters[]` | Chapters 为扁平章节数组，无卷结构 | 斗破苍穹 (1004608738) |

两种格式中每个章节对象的字段名相同（`C`=ChapterId, `N`=ChapterName, `V`=IsVip 等），只是外层结构不同。实现位置：`MainHook.java` → `constructChapterItemFromApi()` 方法中同时支持两种格式。

### getChapterContent

```json
{"cmd": "getChapterContent", "bookId": "1045815697", "chapterId": "852855550"}
```

自动完成：下载加密数据 → 保存 .qd 文件 → 克隆 ChapterItem → L→K→R 解密 → 返回明文。

## 七、限制和注意事项

### 7.1 ~~需要用户先进入阅读页面~~（已解决 ✅）

> **此限制已消除。** 以下为历史记录。

原限制：`bllVInstance` 和 `chapterItems` 只在用户进入阅读页面后才会被捕获。

**解决方案（两个关键发现）**：

1. **bllVInstance 自动捕获**：App 启动时会恢复上次阅读状态（回到最后阅读的书籍），这个恢复过程会触发 `bll.v` 的实例化，hook 自动捕获 `bllVInstance`。如果 App 内没有阅读记录（全新安装），也可以通过 `createBllVInstance()` 方法反射创建实例
2. **ChapterItem 不再需要模板**：发现 `ChapterItem` 类有一个 `ChapterItem(JSONObject)` 构造函数，可以直接用章节列表 API 返回的 JSON 数据构造，完全不需要从已捕获的模板克隆。实现位置：`MainHook.java` → `constructChapterItemFromApi()` 方法

### 7.2 VIP 章节限制

本文档描述的 `safegetcontent` + `bll.v.L→K→R` 流程**仅适用于免费章节**。VIP 章节需要走不同的流程：`buyvipchapter` 购买 → `getvipcontent` 下载 → `bll.v.N` 解密。详见 `7. VIP 章节购买与解密方案.md`。

> `fetchChapter` RPC 命令已内部集成免费/VIP 的自动判断，调用方无需关心。

### 7.3 请求频率控制

建议：
- 章节间隔 2-5 秒随机延迟
- 单次会话不超过 50 章

### 7.4 OkHttpClient 依赖

所有 API 请求依赖 `savedOkHttpClient`（带签名拦截器），App 启动后自动从 `druidv6.if.qidian.com/argus` 域名的 API 请求中捕获。

### 7.5 safegetcontent 返回二进制数据

`safegetcontent` API 的响应体是加密的二进制数据（非 JSON），OkHttp interceptor 的日志打印需要过滤二进制响应，使用 `looksLikeBinary()` 检测避免日志乱码。

## 九、实施历程（关键发现记录）

按时间顺序记录探索过程中的关键发现，避免后续重复踩坑：

1. **方案 A 不可行**：App 不使用 `javax.crypto.Cipher` 进行章节解密，`trackedCiphersCount` 始终为 0。Cipher Hook 捕获的 AES/DESede 操作用于安全检测和设备指纹，与章节内容无关
2. **`pf.cihai.search` 类已不存在**：旧版本的解密入口已被移除，当前版本的解密逻辑已迁移到 `bll.v` 内部
3. **bll.v.R 单独调用返回 null**：必须先调用 L 和 K 进行准备，三步缺一不可
4. **ChapterItem 必须完整克隆**：最小化的 fake ChapterItem（仅设 chapterId）导致方法返回错误类型或 ClassCastException
5. **L → K → R 调用序列是关键突破**：通过对 `bll.v` 所有方法安装 probe hook，观察 App 正常读取章节时的调用日志，发现了这个固定模式
6. **L 才是真正的解密触发点**：afterCall hook 在 L 方法返回前就已经捕获了明文，R 只是返回缓存文件路径
7. **`getkey` API 不需要**：解密密钥获取完全在 `bll.v` 内部处理，无需外部 API 调用
8. **ChapterItem 可通过 API JSON 构造**：发现 `ChapterItem` 类有 `ChapterItem(JSONObject)` 构造函数，可直接用章节列表 API 的 JSON 数据构造有效的 ChapterItem 实例，无需从已捕获的模板克隆。这消除了"必须先进入阅读页面捕获模板"的前置条件
9. **bllVInstance 在 App 启动时自动捕获**：App 启动后会恢复上次阅读状态，此过程自动触发 `bll.v` 类的实例化和 hook 回调。即使没有阅读记录，也可通过 `createBllVInstance()` 反射创建实例
10. **章节列表 API 有两种响应格式**：`Data.Vs[].Cs[]`（卷-章节结构）和 `Data.Chapters[]`（扁平列表），代码中必须同时支持，否则某些书籍会解析失败
11. **bll.v.N 方法签名变化（2026-02-08）**：起点 App 更新后，`bll.v.N` 从 5 参数变为 6 参数（第 6 个参数为 boolean），代码已修改支持两种签名

## 十、故障排查指南

### 10.1 章节内容解密失败

**症状**：
```
正文获取失败: downloaded via getvipcontent but all decryption methods failed
```
或
```
CONTENT_EXTRACT_FAIL | chapterId=xxx | no content found in ChapterContentItem
```

**诊断步骤**：

1. **检查 ChapterContentItem 字段**（最直接）
   ```python
   from qidian_api import QidianAPI
   api = QidianAPI()
   logs = api.get_logs(limit=500)

   for log in logs.get('data', []):
       msg = log.get('message', '')
       if 'ChapterContentItem fields dump' in msg:
           # 打印关键字段
           for line in msg.split('\\n'):
               if 'chapterContent' in line or 'originalChapterContent' in line:
                   print(line)
   ```

   **预期结果**：
   - 免费章节（L→K→R）：`chapterContent [String(XXXX)]` 应有数千字符
   - VIP 章节（bll.v.N）：`chapterContent [String(XXXX)]` 应有数千字符
   - 失败情况：`chapterContent [String(2)]` 只有空白，或 `originalChapterContent [String(0)]` 为空

2. **检查 bll.v.N 方法签名**
   ```python
   for log in logs.get('data', []):
       msg = log.get('message', '')
       if 'METHOD_CALL' in msg and 'bll.v.N' in msg:
           print(msg)
   ```

   **检查点**：
   - 参数个数是 5 个还是 6 个？
   - 代码中 `tryFetchViaBllVN` 是否支持对应参数个数？

3. **确认 v 对象已捕获**
   ```python
   for log in logs.get('data', []):
       msg = log.get('message', '')
       if 'saved v' in msg or 'vObjects' in msg:
           print(msg)
   ```

   如果没有 v 对象记录，需要手动在 App 中打开一个 VIP 章节，让内容完全加载。

### 10.2 L→K→R vs bll.v.N 判断

**关键差异**：

| 方法 | 适用章节 | 验证方式 |
|------|---------|---------|
| L→K→R | 免费章节 | `chapterContent` 有内容 |
| bll.v.N | VIP 章节 | `chapterContent` 有内容 |

**验证方法**：
- 免费章节用 L→K→R 解密后，`chapterContent` 应该有 2000-5000 字符
- VIP 章节用 L→K→R 解密后，`chapterContent` 只有 2 个全角空格（`　　`）
- VIP 章节必须用 bll.v.N 才能获取正确内容

### 10.3 方法签名不匹配

**问题现象**：日志显示 `bll.v.N` 被调用，但 `tryFetchViaBllVN: method N(5 or 6 params) not found`

**解决方案**：

修改 `MainHook.java` 中 `tryFetchViaBllVN` 方法（约 2212-2265 行）：

```java
// 查找 N 方法 (支持 5 或 6 个参数版本)
Method methodN = null;
int paramCount = 0;
for (Method m : bllVClass.getDeclaredMethods()) {
    int pc = m.getParameterTypes().length;
    if ("N".equals(m.getName()) && (pc == 5 || pc == 6)) {
        methodN = m;
        paramCount = pc;
        break;
    }
}

// 调用时根据参数数量传递正确参数
if (paramCount == 6) {
```

### 10.5 评论采集 RPC 超时

**症状**：
```
评论获取失败: 分批获取评论失败: RPC 无响应
批次 6/6: 段落 5 个 → 批次 6 失败: RPC 无响应
```

**原因**：`handleGetAllParagraphComments` 在短时间内发起大量 HTTP 请求（100+ 段落 × 多页评论 × 回复），没有请求间隔控制，导致 App 主线程阻塞、RPC 服务器无响应。

**解决方案**：已在 `MainHook.java` 中添加 HTTP 请求节流（30ms 最小间隔），无需额外操作。如果仍然超时，可以：

1. 增加批次间延迟（`batch_delay` 参数，默认 3 秒）
2. 减小批次大小（`batch_size` 参数，默认 15）
3. 跳过评论过多的章节（使用 `--skip-comments`）

### 10.6 常见错误对照表

| 错误信息 | 原因 | 解决方案 |
|---------|------|---------|
| `method N(5 or 6 params) not found` | App 更新后方法签名变化 | 修改代码支持 5/6 参数 |
| `chapterContent [String(2)]` | L→K→R 用于 VIP 章节 | 使用 bll.v.N |

| `RPC 无响应`（评论采集） | HTTP 请求过于密集 | 已自动节流（30ms），如仍失败可调整批处理参数 |
