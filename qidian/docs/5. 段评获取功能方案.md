## 一、目标

获取起点小说章节中的**段落评论（段评）**数据，即读者针对某个段落发表的评论内容。

起点读书的"本章说"功能分为两种：
- **章评**：对整个章节的评论
- **段评**：对某个具体段落/句子的评论（用户选中段落后发表）

在阅读页面中，有评论的段落末尾会显示评论数气泡（如 `<22`），点击后弹出 `NewParagraphCommentListActivity`，展示该段落的全部评论，分为"全部"和"配音"两个 Tab。

## 二、已探测到的 App 端段评 API

通过手动点击段评气泡并捕获 logcat，发现 App 同时调用**三个 API**获取段评数据：

### 2.1 文字评论（核心 API）

```
GET /argus/api/v2/chapterreview/getparagraphscomments
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `bookId` | string | 书籍 ID |
| `chapterId` | string | 章节 ID |
| `paragraphId` | int | 段落 ID（从 `getchapterrepagesummary` 获取） |
| `pg` | int | 页码（从 1 开始） |
| `pz` | int | 每页数量（默认 20） |
| `type` | int | 评论类型（0=全部） |
| `anchorId` | int | 锚点 ID（0=从头开始） |
| `from` | int | 来源（0=默认） |

**实际捕获的请求示例**：
```
/argus/api/v2/chapterreview/getparagraphscomments?bookId=1045815697&chapterId=852525195&paragraphId=9&pg=1&pz=20&type=0&anchorId=0&from=0
```

### 2.2 配音评论

```
GET /argus/api/v1/chapterreview/getparagraphsaudiocomments
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `bookId` | string | 书籍 ID |
| `chapterId` | string | 章节 ID |
| `paragraphId` | int | 段落 ID |
| `pg` | int | 页码 |
| `pz` | int | 每页数量 |
| `roleId` | int | 角色 ID（0=全部角色） |

### 2.3 图片评论

```
GET /argus/api/v1/chapterreview/getparagraphsallimgreviews
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `bookId` | string | 书籍 ID |
| `chapterId` | string | 章节 ID |
| `paragraphId` | int | 段落 ID |
| `pg` | int | 页码 |
| `pz` | int | 每页数量 |
| `type` | int | 类型（1=图片） |

### 2.4 段评摘要（阅读页自动调用）

```
GET /argus/api/v1/chapterreview/getchapterrepagesummary
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `bookId` | string | 书籍 ID |
| `chapterId` | string | 章节 ID |
| `useImei` | int | 0 |
| `strategy` | int | 0 |

> 此 API 在阅读页加载时自动调用，返回各段落的评论数量。其中 `paragraphId` 就是后续调用 `getparagraphscomments` 所需的段落标识。同时也用于增量更新的第一级对比。

### 2.5 热门段评（进入阅读页时调用）

```
GET /argus/api/v1/chapterreview/hotsegments
```

| 参数 | 类型 | 说明 |
|------|------|------|
| `bookId` | string | 书籍 ID |
| `pg` | int | 页码 |

## 三、完整调用链路

```
1. getchapterrepagesummary(bookId, chapterId)
   └── 获取该章节各段落的 paragraphId 和评论数量

2. 对有评论的每个 paragraphId:
   └── getparagraphscomments(bookId, chapterId, paragraphId, pg=1, pz=20)
       └── 获取该段落的文字评论列表（含评论内容、用户名、时间、点赞数等）
       └── 可选：获取每条评论的回复（需 --with-replies 参数）

3. 可选：
   ├── getparagraphsaudiocomments(...) → 配音评论
   └── getparagraphsallimgreviews(...) → 图片评论
```

## 四、关键参数说明

### paragraphId 的含义

`paragraphId` 是段落在章节中的**序号标识**。从捕获的请求看，第一段"寒风中，少年哆嗦了一下，悠悠苏醒。"对应的 `paragraphId=9`。

> **注意**：paragraphId 可能不是从 1 开始的简单递增，需要从 `getchapterrepagesummary` 的响应中获取实际值。这与 Web 端的 `segmentId` 概念相同。

### paragraphId 的规律

- 不是简单递增的 1, 2, 3...
- 实际值包括：-1, 1, 2, 3, 4, 64, 71, 128, 129, 135 等
- `-1` 表示章评
- 必须从 `getchapterrepagesummary` 获取实际 paragraphId 值

### 分页机制

- `pg`：页码，从 1 开始
- `pz`：每页数量，默认 20
- `pz` 参数不严格限制返回数量（请求 pz=5 可能返回 8 条）
- `CommentCount` 与实际可获取数可能有 1-2 条差异（已删除/审核中的评论）
- `getAllParagraphComments` 使用 `items.length() < pageSize` 判断是否还有下一页，安全阀 50 页

## 五、RPC 命令

### 5.1 基础命令

| 命令 | 参数 | 说明 |
|------|------|------|
| `getChapterReviewSummary` | `bookId`, `chapterId` | 获取章节各段落的评论数量和 paragraphId（原始 API 响应） |
| `getCommentSummary` | `bookId`, `chapterId` | 轻量摘要，返回 totalComments + 各段 commentCount（增量检测专用） |
| `getParagraphComments` | `bookId`, `chapterId`, `paragraphId`, `page` | 获取某段落的文字评论列表 |
| `getAllParagraphComments` | `bookId`, `chapterId`, ... | 一次性获取该章节所有段评（内部先调摘要，再逐段获取） |

> `getCommentSummary` 与 `getChapterReviewSummary` 底层调用的是同一个 API，区别在于前者返回精简格式（只有 paragraphId 和 commentCount），后者返回原始 API 响应。

### 5.2 `getAllParagraphComments` 完整参数

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `bookId` | string | 必填 | 书籍 ID |
| `chapterId` | string | 必填 | 章节 ID |
| `pageSize` | int | 20 | 每页数量 |
| `type` | int | 0 | 评论类型 0=全部, 1=配图, 2=配音 |
| `includeChapterComments` | bool | false | 是否包含章评（ParagraphId=-1） |
| `fetchReplies` | bool | true | 是否获取评论回复 |
| `onlyParagraphs` | JSONArray | null | 非空时只获取指定段落 ID 的评论（增量模式） |
| `existingReplies` | JSONObject | null | key=评论Id字符串, value=ReviewCount；一致则跳过回复获取（增量模式） |

`onlyParagraphs` 和 `existingReplies` 均为可选，不传时行为与基础模式完全一致。

**关键发现**：

## 七、增量更新机制（`--update-comments`）

### 7.1 背景

评论会持续增长。默认模式下已有评论直接跳过，不会检测新增评论。开启 `--update-comments` 后启用**三级递进检测**：只在有变化时重新获取，最大限度减少 API 请求。

### 7.2 三级递进检测

**第一级：章节总评论数对比**
- 调用摘要 API（**1 次请求**），求和得到总评论数
- 与本地 `summaryTotalComments` 对比，一致 → 直接跳过（约 0.2s）
- 这是最常见的命中路径

**第二级：逐段评论数对比**
- 摘要中每段的 `CommentCount` vs 本地 `fetchedCount`
- 一致 → 复用旧数据；不一致 → 通过 `onlyParagraphs` 只获取变化段落

**第三级：评论回复数对比**（仅 `--with-replies` 时有意义）
- 变化段落中每条评论的 `ReviewCount` vs 旧数据
- 一致 → 从旧数据恢复 `replies`；不一致 → 重新请求回复 API

### 7.3 `summaryTotalComments` vs `totalComments`（重要陷阱）

| 字段 | 含义 | 来源 |
|------|------|------|
| `summaryTotalComments` | 摘要 API 返回的总评论数（含已删除/隐藏的） | 各段 CommentCount 之和 |
| `totalComments` | 实际获取到的评论条数 | 各段 fetchedCount 之和 |

两者通常有差异（差几条到几十条），因为 `CommentCount` 包含了已删除或审核中的评论。

**如果用 `totalComments` 做增量对比，会导致每次都误判为"有变化"，增量跳过永远不会生效。** 因此用独立的 `summaryTotalComments` 字段记录摘要原始总数。兼容旧数据——没有该字段时回退到 `totalComments`（第一次运行会触发一次增量更新来写入该字段）。

### 7.4 增量模式下的设计决策

**`onlyParagraphs` 过滤在 Java 端实现**：一次 RPC 请求内部只遍历变化段落，减少 WSL2→ADB→手机→API 的往返次数。

**`existingReplies` 传递精简映射**：只传 `{str(评论Id): ReviewCount}`，而非完整旧回复，避免 RPC 请求体过大。Java 端对比 ReviewCount，一致则不带 `replies` 字段返回，Python 端合并时从旧数据恢复。

**增量检测失败时的容错**：摘要 API 请求失败不丢弃已有数据，保留旧评论并打印警告。

### 7.5 性能对比

以 4 章测试（玄鉴仙族 #100-#103，各有 300-600 条评论）：

| 场景 | 耗时 | API 请求数 |
|------|------|-----------|
| 首次全量采集 | 约 40-60 秒/章 | 每段落 1+ 次 + 回复请求 |
| 增量更新（有变化，13 段） | 约 8 秒/章 | 摘要 1 次 + 变化段落 N 次 |
| 增量检测（无变化） | **0.2 秒/章** | **仅摘要 1 次** |

## 八、采集模式总结

| 参数组合 | 行为 |
|---------|------|
| 默认 | 只采集根评论，不采集回复；已有评论直接跳过 |
| `--with-replies` | 同时采集评论的回复 |
| `--update-comments` | 已有评论走增量检测，有变化时增量获取 |
| `--update-comments --with-replies` | 增量检测 + 回复采集，回复也支持增量复用 |
| `--force` | 无视已有数据，全部重新采集 |

## 十一、代码位置索引

### Java 端（`qidian/app/src/main/java/com/yuyang/qdhook/MainHook.java`）

| 方法 | 作用 |
|------|------|
| `executeGetRequest(url)` | 通用 GET 请求执行器，复用 savedOkHttpClient 带签名 |
| `handleGetChapterReviewSummary(bookId, chapterId)` | 调用 `getchapterrepagesummary` API，返回原始响应 |
| `handleGetCommentSummary(bookId, chapterId)` | 轻量摘要，返回 totalComments + 各段 commentCount |
| `handleGetParagraphComments(bookId, chapterId, paragraphId, page, pageSize)` | 调用 `getparagraphscomments` API |
| `handleGetAllParagraphComments(...)` | 组合调用：摘要 + 逐段获取 + 自动翻页 + 增量参数支持 |
| `fetchCommentReplies(...)` | 获取单条评论的所有回复（自动翻页，安全阀 10 页） |

### Python 端（`qidian/scripts/qidian_api.py`）

| 方法 | 作用 |
|------|------|
| `get_chapter_review_summary()` | 段评摘要（原始响应） |
| `get_comment_summary()` | 轻量摘要（增量检测用） |
| `get_paragraph_comments()` | 单段落评论 |
| `get_all_paragraph_comments()` | 全部段评（支持 `only_paragraphs` / `existing_replies` 增量参数） |

### 批量采集（`qidian/scripts/batch_fetch.py`）

| 函数 | 作用 |
|------|------|
| `fetch_one()` | 单章采集，含评论增量检测分支 |
| `_find_changed_paragraphs()` | 对比摘要与旧数据，返回变化段落 ID |
| `_build_replies_map()` | 从变化段落旧评论中提取 ReviewCount 映射 |
| `_build_old_replies_index()` | 构建旧评论 ID → replies 索引 |
| `_merge_comments()` | 合并未变化段落与变化段落的新数据 |

### 关键设计决策

1. **提取通用 `executeGetRequest()` 方法**：将重复的 OkHttp 反射调用代码抽成通用方法，简化后续 GET API 实现
2. **`getAllParagraphComments` 默认跳过 `ParagraphId=-1`**（章评），需要 `includeChapterComments=true` 才包含
3. **自动翻页 + 50 页安全阀**：防止异常数据导致无限请求
4. **回复采集默认关闭**（`batch_fetch.py` 中默认 `fetchReplies=false`），需 `--with-replies` 显式开启
5. **增量更新默认关闭**，需 `--update-comments` 显式开启
