## 一、概述

Python 工具链包含两层：

| 层级 | 文件 | 职责 |
|------|------|------|
| API 封装层 | `qidian/scripts/qidian_api.py` | 封装所有 RPC 调用为 Python 方法，可作为模块导入或 CLI 使用 |
| 采集工具层 | `qidian/scripts/batch_fetch.py` | 提供 search/list/fetch 三个子命令，管理输出和断点续传 |

### 通信链路

```
WSL2 Python (127.0.0.1:12345)
  │
  │ TCP（ADB forward 端口，WSL2 与 Windows 网络已打通）
  ▼
手机 LocalSocket "qdhook_rpc"
  │
  │ MainHook.java handleCommand()
  ▼
RPC 响应 (JSON + \n)
```

WSL2 直接通过 `127.0.0.1:12345` 连接 ADB forward 端口，无需任何中间桥接。

## 三、批量采集工具（batch_fetch.py）

### 3.1 三步工作流

**步骤 1：搜索书籍**

```
batch_fetch.py search 大奉打更人
```

- 显示编号列表，结果自动缓存到 `.last_search.json`
- 后续命令可用序号引用（如 `1` 代表第一本）

**步骤 2：查看章节目录**

```
batch_fetch.py list 1                  # 全部章节
batch_fetch.py list 1 --last 10        # 最后 10 章
batch_fetch.py list 1 --range 100-200  # 第 100~200 章
```

- 显示章节编号、VIP/免费标记、章节名、字数
- 支持直接传入 bookId（大于 100 的纯数字自动识别为 bookId）

**步骤 3：批量采集**

```
batch_fetch.py fetch 1 --last 5              # 采集最后 5 章
batch_fetch.py fetch 1 --range 100-110       # 采集第 100~110 章
batch_fetch.py fetch 1 --chapters 1,5,10-15  # 指定章节
batch_fetch.py fetch 1                       # 全部章节
batch_fetch.py fetch 1 --no-comments         # 只要正文，不采评论
batch_fetch.py fetch 1 --no-content          # 只要评论，不采正文
batch_fetch.py fetch 1 --with-replies        # 同时采集评论回复
batch_fetch.py fetch 1 --update-comments     # 增量更新已有评论
batch_fetch.py fetch 1 --force               # 强制重采所有章节
```

### 3.2 采集参数总结

| 参数 | 默认 | 说明 |
|------|------|------|
| `--no-content` | 关 | 不采集正文 |
| `--no-comments` | 关 | 不采集评论 |
| `--with-replies` | 关 | 同时采集评论的回复（默认只采根评论） |
| `--update-comments` | 关 | 已有评论走增量检测，有变化时增量获取 |
| `--force` | 关 | 无视已有数据，全部重新采集 |
| `--output-dir` | `output/` | 输出目录 |

### 3.3 断点续传与跳过逻辑

正文采集支持断点续传：已有有效正文的章节自动跳过，只重新采集缺失或失败的。

评论默认行为：已有评论直接跳过。加 `--update-comments` 后走增量检测（详见 `5. 段评获取功能方案.md` 第七节）。

**有效性判定**：
- **正文有效**：无 `contentError` 字段，且 `content` 非空、非纯空白（过滤全角空格 `\u3000`）
- **评论有效**：无 `commentsError` 字段，且 `comments` 字段存在

## 五、踩过的坑

### 5.1 大响应 TCP 接收不完整

**现象**：search 响应约 35KB~80KB，单次 `recv(65536)` 收不完整，JSON 截断。

**原因**：TCP 是流式协议，单次 recv 不保证收到完整消息。RPC 协议以 `\n` 为消息分隔符，大响应需多次 recv。

**解决方案**：recv 缓冲区 262144（256KB），deadline 模式循环 recv 直到 buf 中出现 `\n` 或超时。

### 5.2 RPC 响应格式不统一

不同命令的响应结构不一致：

| 命令类别 | 数据字段 | 说明 |
|----------|----------|------|
| 系统/诊断命令（ping, getStatus 等） | `data` | 直接包含业务数据 |
| API 透传命令（search, bookDetail 等） | `response` | 包含起点 API 的原始 JSON |
| 章节解密命令（fetchChapter 等） | `data` | 包含 bookId, chapterId, content |

`qidian_api.py` 中系统/诊断命令返回 `resp.get("data")`，API 透传命令返回完整 `resp`。

### 5.3 章节列表字段名与预期不同

| 字段 | 含义 |
|------|------|
| `C` | 章节 ID |
| `N` | 章节名 |
| `W` | 字数 |
| `T` | 时间戳 |
| `V` | VIP 标记（0=免费） |

`get_all_chapter_ids()` 按 `C` → `Id` → `id` 优先级取值，自动处理卷结构 `Data.Vs[].Cs[]` 和扁平列表 `Data.Chapters[]` 两种格式。

## 六、注意事项

### 6.1 请求频率

- 章节间默认间隔 0.3 秒
- 免费章节约 3-4 秒/章（下载 + 解密）
- VIP 章节约 6 秒/章（购买 + 下载 + 解密）

### 6.2 VIP 余额消耗

`fetchChapter` 透明处理 VIP 章节，**会自动购买并扣除账户余额**。大批量采集 VIP 章节前请确认余额充足。

### 6.3 文件名安全

章节名中的 `/`、`\`、`:` 等特殊字符会被替换为 `_`，章节名截取前 50 字符。

### 6.4 搜索缓存

搜索结果缓存在 `scripts/.last_search.json`，新的搜索会覆盖旧缓存。
