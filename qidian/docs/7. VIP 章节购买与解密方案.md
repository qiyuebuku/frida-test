# VIP 章节购买与解密方案

> 日期：2026-02-07 / 更新：2026-02-08
> 状态：**已完成** ✅
> 前置依赖：章节阅读功能（已完成）、OkHttpClient 捕获（已完成）

---

## 一、目标

实现 VIP 章节的**自动购买 + 下载 + 解密**全流程，使 `fetchChapter` RPC 命令能够透明地处理免费章节和 VIP 章节，调用方无需区分。

---

## 二、核心发现

### 2.1 免费章节 vs VIP 章节的解密差异（关键）

| 对比项 | 免费章节 | VIP 章节 |
|--------|---------|---------|
| 下载 API | `safegetcontent` (GET) | `getvipcontent` (POST) |
| 解密方法 | `bll.v.L→K→R` 方法链 | `bll.v.N` 方法 |
| 前置步骤 | 无 | **必须先调用 `buyvipchapter` 购买** |
| 返回数据 | 加密二进制（.qd 格式） | 加密二进制（.qd 格式） |

> **重要**：`bll.v.L→K→R` 方法链**只能解密免费章节**。用 L→K→R 解密 VIP 章节时，`chapterContent` 只有空白字符（全角空格 `\u3000`），不含实际内容。`bll.v.N` 是 VIP 解密的正确方法。

### 2.2 VIP 章节完整流程

```
1. buyvipchapter (POST)      → 购买/授权章节（扣除余额）
2. getvipcontent (POST)      → 下载加密的 VIP 内容
3. 保存为 .qd 文件            → 存入用户路径（非匿名路径）
4. bll.v.N (反射调用)         → 解密，返回 ChapterContentItem
```

### 2.3 buyvipchapter API 的发现过程（重要经验）

最初无法确定 `buyvipchapter` 的请求参数格式。尝试了多种参数组合（`bookId+chapterId`、`b+c`、各种附加字段）均返回错误码 -100001（"网络开小差了"），实际含义是参数格式错误。

**最终解决方案**：修改 OkHttp 拦截器，使其同时拦截 `subscription` 路径的请求体，然后让用户手动在 App 中打开一个 VIP 章节，从拦截日志中捕获了 App 的真实请求格式。

> 教训：当 API 参数格式无法通过猜测确定时，最可靠的方法是**拦截 App 的真实请求**。

## 三、API 端点详情

### 3.1 buyvipchapter — 购买 VIP 章节

| 项目 | 值 |
|------|------|
| URL | `https://druidv6.if.qidian.com/argus/api/v3/subscription/buyvipchapter` |
| 方法 | POST (FormBody) |
| 参数 | `bookId`, `consumeType=0`, `sp=`(空), `type=3`, `confirmType=0`, `chapterlist={chapterId}` |

**关键参数说明**：
- `chapterlist`（不是 `chapterId`）：**必须用此字段名**，否则返回 -100001 错误
- `consumeType=0`：使用默认消费方式
- `type=3`：VIP 章节购买类型
- `confirmType=0`：不需要二次确认

**响应码**：

| Result | 含义 | 后续操作 |
|--------|------|---------|
| 0 | 购买成功 | 继续调用 getvipcontent |
| -100010 | "要购买的vip章节不存在" | 章节已被购买过，可直接调用 getvipcontent |
| -100001 | "网络开小差了" | 参数格式错误（不应出现） |

> 当返回 -100010 时不视为错误，表示章节已购买，直接进入下载步骤。

### 3.2 getvipcontent — 下载 VIP 章节加密内容

| 项目 | 值 |
|------|------|
| URL | `https://druidv6.if.qidian.com/argus/api/v4/bookcontent/getvipcontent` |
| 方法 | POST (FormBody) |
| 参数 | `b-string=`(空), `b={bookId}`, `c={chapterId}`, `ui=0` |

**关键参数说明**：
- `b` 和 `c`（不是 `bookId`/`chapterId`）：使用简写参数名
- `ui=0`：固定为 0（不是用户 ID），由 App 真实请求确认

**响应格式**：
- 已购买：HTTP 200，返回加密二进制数据（与 safegetcontent 格式相同）
- 未购买：返回 JSON `{"Message":"未购买","Result":-100020}`

### 3.3 getunboughtchapterlist — 查询未购买章节

| 项目 | 值 |
|------|------|
| URL | `https://druidv6.if.qidian.com/argus/api/v2/subscription/getunboughtchapterlist?bookId={id}` |
| 方法 | GET |

响应包含 `Data.Chapter[]` 数组（每项含 `CId`, `CN`, `Price`）和 `Data.Balance`（余额）。此 API 用于批量采集时判断哪些章节需要购买。

### 3.4 getvipprice — 查询 VIP 价格

| 项目 | 值 |
|------|------|
| URL | `https://druidv6.if.qidian.com/argus/api/v2/subscription/getvipprice` |
| 方法 | POST (FormBody) |
| 参数 | `ChapterCount=-1`, `bookId`, `withoutLimitFree=0`, `UnitCount=1`, `chapterId` |

## 四、.qd 文件路径陷阱（重要）

VIP 章节的 .qd 文件**必须保存到用户路径**，不能使用匿名路径。

| 路径类型 | 格式 | 用途 |
|---------|------|------|
| 匿名路径 | `book/0/{bookId}/{chapterId}.qd` | 免费章节（L→K→R 使用） |
| 用户路径 | `book/{userId}/{bookId}/{chapterId}.qd` | VIP 章节（bll.v.N 使用） |

- `userId` 如 `406596110`，从 App 内部获取
- 必须先调用 `bll.v.K()` 获取正确路径再保存 .qd 文件
- **保存到匿名路径 `book/0/` 会导致 bll.v.N 解密失败**（返回 null）
- 书籍级密钥数据库 `book/{path}/{bookId}.qd`（约 196KB 的 SQLite 文件）在两个路径下内容不同

## 五、bll.v.N 解密方法

`bll.v.N` 是 VIP 章节的解密入口，与免费章节的 L→K→R 链不同。

- 参数：`(bll.v instance, bookId, ChapterItem)`
- 返回：`ChapterContentItem`（与 L→K→R 返回类型相同）
- 调用 `bllVInstance` 时可用 App 启动时自动捕获的实例，也可通过 `createBllVInstance()` 反射创建
- 关键验证：解密后必须检查 `chapterContent` 非空且非纯空白，才算有效内容

代码位置：`MainHook.java` → `handleFetchChapter()` 方法中的 VIP 处理分支

## 六、handleFetchChapter 完整逻辑

`fetchChapter` RPC 命令内部实现了免费/VIP 的自动判断和处理：

```
1. 尝试 safegetcontent (GET) 获取内容
2. 判断响应：
   - HTTP 200 + 二进制数据 → 免费章节 → 保存 .qd → L→K→R 解密
   - HTTP 非200 或 JSON 错误 → VIP 章节，进入步骤 3
3. VIP 流程：
   a. buyvipchapter (POST) → 购买章节（-100010 视为已购买，不报错）
   b. getvipcontent (POST) → 下载加密内容
   c. 保存 .qd 到用户路径
   d. bll.v.N 解密 → 提取 chapterContent
4. 返回解密后的明文
```

调用方只需发送 `{"cmd":"fetchChapter","bookId":"...","chapterId":"..."}` 即可，无需关心章节类型。

代码位置：`MainHook.java` → `handleFetchChapter()` 方法

## 八、已知限制

1. **余额依赖**：VIP 章节购买需要账户有足够余额，余额不足时 buyvipchapter 会返回错误
2. **每章约 6 秒**：包括购买 + 下载 + 解密的完整流程，比免费章节慢
3. **userId 路径依赖**：VIP .qd 文件必须保存到用户路径，需要正确获取 userId
4. **bllVInstance 依赖**：解密需要 bll.v 实例，App 启动时自动捕获，极端情况可反射创建

## 十、问题排查与修复记录

### 10.1 问题：2026-02-08 VIP 章节解密突然失效

**现象**：
```
正文获取失败: downloaded via getvipcontent but all decryption methods failed
```

**诊断过程**：

1. **检查日志确认流程**：通过 RPC 获取诊断日志，确认：
   - `buyvipchapter` 成功（Result=0）
   - `getvipcontent` 成功（HTTP 200，18800 字节）
   - `.qd` 文件已保存到正确路径
   - `bll.v.L→K→R` 被调用，但返回内容为空

2. **查看 ChapterContentItem 字段 dump**：
   ```
   免费章节（成功）：
   - chapterContent [String(4921)] = 　　"白麒麟果真不在！..."

   VIP 章节（失败）：
   - chapterContent [String(2)] = 　　（只有空白）
   - originalChapterContent [String(0)] = （空字符串）
   ```

3. **结论确认**：L→K→R 只能解密免费章节，VIP 章节必须用 bll.v.N

4. **深入检查 bll.v.N 调用**：发现日志中有 6 参数版本的调用：
   ```
   METHOD_CALL | bll.v.N(1035420986, ChapterItem@xxx, v@xxx, true, null, true)
   ```
   但代码中只查找 5 参数版本的方法！

**根本原因**：

起点 App 更新后，`bll.v.N` 方法签名从 5 个参数变为 6 个参数：

| 版本 | 参数签名 |
|------|---------|
| 旧版（5参数） | `(long, ChapterItem, v, boolean, Object)` |
| 新版（6参数） | `(long, ChapterItem, v, boolean, Object, boolean)` |

**修复方案**：

修改 `tryFetchViaBllVN` 方法，支持两种参数签名：

```java
// 查找 N 方法 (支持 5 或 6 个参数版本)
Method methodN = null;
int paramCount = 0;
for (Method m : bllVClass.getDeclaredMethods()) {
    int pc = m.getParameterTypes().length;
    if ("N".equals(m.getName()) && (pc == 5 || pc == 6)) {
        methodN = m;
        paramCount = pc;
        break;
    }
}

// 调用时根据参数数量传递正确参数
if (paramCount == 6) {
    result = methodN.invoke(bllVInstance, bookIdLong, chapterItem, vObj, true, null, true);
} else {
    result = methodN.invoke(bllVInstance, bookIdLong, chapterItem, vObj, true, null);
}
```

**代码位置**：`MainHook.java` 行 2212-2265（`tryFetchViaBllVN` 方法）

**验证结果**：

修复后 VIP 章节解密恢复正常：
- 章节 816877576（第九百八十六章 定甲）：4208 字符 ✅
- 章节 816987624（第九百八十七章 司宁去留）：6209 字符 ✅

### 10.2 经验教训

1. **方法签名变化检测**：当 App 更新导致 Hook 失效时，首先检查方法签名是否发生变化
2. **日志驱动调试**：通过 RPC 获取详细日志，比单步调试更高效
3. **向后兼容**：代码应同时支持多个版本的 API，以应对 App 渐进式更新
4. **手动配合验证**：让用户手动操作 App 触发真实调用，然后从日志中提取参数格式

### 10.4 问题：2026-02-08 评论采集 RPC 超时

**现象**：
```
评论获取失败: 分批获取评论失败: RPC 无响应
```

对于评论数量多的章节（如 1000+ 条评论），即使使用分批处理，RPC 仍会在几批之后无响应。

**诊断过程**：

1. **检查批处理日志**：
   ```
   批次 1/6: 段落 20 个 → 完成: 726 条评论, 43.4s
   批次 2/6: 段落 20 个 → 完成: 417 条评论, 29.3s
   ...
   批次 6/6: 段落 5 个 → 批次 6 失败: RPC 无响应
   ```

2. **分析问题根源**：
   - `handleGetAllParagraphComments` 在处理一个章节时会发起大量 HTTP 请求
   - 每个段落需要分页获取评论，每条评论可能还需要获取回复
   - 对于 100 个段落的章节，可能发起 500+ 个 HTTP 请求
   - 所有请求在短时间内密集发起，导致 App 主线程阻塞、RPC 服务器无响应

**根本原因**：

`executeGetRequest` 方法中没有任何请求间隔控制，导致：
- OkHttp 连接池被耗尽
- App 主线程被大量网络请求阻塞
- RPC 服务器线程无法及时响应心跳

**修复方案**：

在 `executeGetRequest` 方法中添加请求节流：

```java
// HTTP 请求节流：防止请求过于密集导致 App 无响应
private static volatile long lastRequestTime = 0;
private static final long MIN_REQUEST_INTERVAL_MS = 30;  // 每个请求最少间隔 30ms

private static String executeGetRequest(String url) throws Exception {
    // 请求节流：检查距离上次请求的时间
    long now = System.currentTimeMillis();
    long timeSinceLastRequest = now - lastRequestTime;
    if (lastRequestTime > 0 && timeSinceLastRequest < MIN_REQUEST_INTERVAL_MS) {
        long sleepTime = MIN_REQUEST_INTERVAL_MS - timeSinceLastRequest;
        try {
            Thread.sleep(sleepTime);
        } catch (InterruptedException ie) {
            Thread.currentThread().interrupt();
        }
    }

    // ... 原有的 HTTP 请求逻辑 ...

    // 请求完成后更新时间戳
    lastRequestTime = System.currentTimeMillis();
    // ...
}
```

**代码位置**：`MainHook.java`
- 字段声明：行 97-99
- 节流逻辑：行 4557-4569（请求前）、行 4590（请求后）

**验证结果**：

修复后评论采集恢复正常：
- 第一千二百二十三章（1290）：102 段落，562 条评论，7 批，106.4s ✅
- 第一千二百二十四章（1291）：85 段落，397 条评论，6 批，96.0s ✅
- 第一千二百二十五章（1292）：73 段落，401 条评论，5 批，69.4s ✅

### 10.5 经验教训

1. **密集请求控制**：当需要在短时间内发起大量 HTTP 请求时，必须添加请求间隔控制
2. **分批处理的局限**：批处理只能减少单次 RPC 的数据量，但不能解决内部 HTTP 请求密集的问题
3. **App 主线程保护**：RPC 回调中的网络请求会占用 App 主线程，过度密集会导致 App 卡死
4. **节流参数调优**：30ms 的间隔在保证成功率的同时，对总耗时影响较小（500 个请求仅增加 15 秒）
