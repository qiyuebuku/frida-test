# 同花顺刷新页推荐与热榜采集实施方案

## 1. 目标

采集同花顺 App“刷新”页面的推荐与热榜内容，并通过新闻统一入库链路写入 `ft_news`，供后续新闻查询、知识抽取和关系抽取工作流消费。

## 2. 数据范围

- 推荐页头条模块：标题、发布时间、详情地址和上游标识。
- 推荐信息流：作者、发布时间、标题、摘要或正文、图片关联信息、互动信息、关联股票和详情地址。
- 热榜话题：榜单标题、说明、话题代码、投票或关联股票信息和详情地址。
- 热门正文：标题、正文、发布时间、作者标识、关联股票和详情地址。

## 3. 采集链路

头条、热榜话题和热门正文使用同花顺 Hummer 页面声明的 HTTP 接口并发采集。推荐信息流需要 App 用户态，服务端通过本机 App HTTP 桥发送请求；Hook 在同花顺进程内调用 `HXJsBridge.getUserCookie()` 并只对推荐域名注入 Cookie。Cookie 不进入请求参数、响应、业务日志或数据库。

四类数据并发返回后统一归一化，按来源分别标记为：

- `ths_discover_headline`
- `ths_discover_recommend`
- `ths_discover_hot_topic`
- `ths_discover_hot_post`

稳定上游 ID 用于生成 `fingerprint`，关联股票写入 `related_stocks`，页面分区写入 `tags`。最终复用 `NewsAggregator.save_normalized_items()` 的标准去重与批量入库流程。

## 4. 调度与故障处理

`collect_news` 每 60 秒触发一次。各新闻源仍按自己的独立到期时间执行；`ths_discover` 的源间隔为 60 秒，因此提高调度频率不会让其他低频新闻源被重复请求。

四个页面接口并发读取列表，使用头条 `seq`、推荐 `itemId`、话题 `code` 和热门正文 `pid` 组成分区稳定 ID。Checkpoint 保存最近 3000 个已见 ID；只有首次出现的 ID 才进入正文归一化、批量入库和知识抽取投递。列表顺序变化但没有新增 ID 时直接结束，不写数据库，也不触发下游。允许单个分区暂时失败；只要其余分区有有效新增内容，就先保存成功部分并记录告警。全部分区失败时任务失败，由任务系统执行重试。

## 5. 测试用例

### 单元测试

- `test_normalize_ths_discover_recommendation_extracts_content_and_stock`：验证推荐卡片标题、正文、来源、时间和关联股票归一化。
- `test_normalize_ths_discover_hot_topic_preserves_description`：验证热榜话题说明、来源和关联股票归一化。
- `test_r5_news_source_configs_complete`：验证 `ths_discover` 已注册到新闻源配置。
- `test_fetch_ths_discover_only_returns_unseen_ids`：验证已见 ID 被列表门禁过滤，完全无新增时不进入入库链路。

### 集成验证

- 生产 App 桥请求推荐接口返回登录态成功响应，且 Cookie 不出 App 进程。
- 一次采集同时获得头条、推荐、热榜话题和热门正文。
- 新内容写入 `ft_news` 后返回新增 ID，可继续进入既有知识抽取工作流。
