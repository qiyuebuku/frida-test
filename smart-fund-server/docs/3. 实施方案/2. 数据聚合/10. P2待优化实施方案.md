## B. 2.1 ft_sentiment_signal 物化表

### B.1 需求分析

- **核心需求**：将 L2 派生信号（`market_temperature / overheat_set / leading_theme / sentiment_score`）每日一次物化到新表 `ft_sentiment_signal`，解决两类问题：
  1. **历史回溯**：Phase 4 决策引擎 / reflection 模块需要查询"过去某日的市场温度"。
  2. **读取性能**：高 QPS 下避免重复聚合 500 条 ft_sentiment 行。
- **边界条件**：
  - 当日读取**仍走**内存缓存（`_ensure_cache`），不改 hot path。
  - 快照表**只存 T-1 及更早**（当日数据未收盘前不稳定，避免频繁覆盖）。
  - 采用"每日定时任务 + 幂等 UPSERT"模式，允许手工补跑。
- **复杂度判定**：**中等**。新表 + 调度任务 + 仓储 + 读路径分叉，但逻辑简单。

### B.2 技术方案

**选型对比**：

| 维度 | 方案 A: 每日定时任务 UPSERT | 方案 B: 每次 SentimentAggregator 写入后 hook | 方案 C: 完全实时查表 |
|------|---------------------------|------------------------------------|---------------------|
| 写入时机 | 固定（收盘后 15:30） | 随 ft_sentiment 写入频繁触发 | 无写入 |
| 写入次数/日 | 1 | 每次聚合（十几~几十次） | 0 |
| 当日数据稳定性 | ✅ 收盘后快照稳定 | ❌ 盘中频繁覆盖 | N/A |
| 实现复杂度 | 低 | 中（耦合写路径） | 零 |
| 读取延迟 | 快照查询 O(1) | 快照查询 O(1) | 每次全量聚合 |

**✅ 选定方案 A**：每日定时任务（15:30 收盘后）调用 `SentimentAggregator.materialize_snapshot(trade_date)`，幂等 UPSERT 到 `ft_sentiment_signal`。

**理由**：
1. ft_sentiment_signal 语义是"日度快照"，与盘中实时信号分离；
2. 盘中 SentimentAggregator 无需变更，零回归风险；
3. 支持手工回补历史日期。

### B.3 数据模型

新增表 `ft_sentiment_signal`：

```sql
CREATE TABLE ft_sentiment_signal (
    snapshot_date        DATE PRIMARY KEY,
    market_temperature   INT NOT NULL,           -- 0-100
    market_level         VARCHAR(8) NOT NULL,    -- cold/cool/warm/hot/overheat
    market_trend         VARCHAR(16),            -- rising/falling/stable
    signals              JSONB NOT NULL,         -- get_market_temperature() 原始返回
    overheat_codes       JSONB,                  -- {codes: {code: penalty}, updated_at}
    leading_theme        JSONB,                  -- {theme, confidence}
    sentiment_agg        JSONB,                  -- {overall_score, industry_scores: {...}}
    contributors         JSONB,                  -- 解释性数据：top N 贡献来源
    created_at           TIMESTAMPTZ DEFAULT NOW(),
    updated_at           TIMESTAMPTZ DEFAULT NOW()
);

COMMENT ON TABLE ft_sentiment_signal IS
  'L2 情绪派生信号日度快照。每日收盘后由 SentimentAggregator.materialize_snapshot 写入。';

CREATE INDEX idx_sentiment_signal_date_desc ON ft_sentiment_signal (snapshot_date DESC);
```

**字段设计说明**：
- `snapshot_date` 为 PK 而非 `(snapshot_date, signal_type)`，每日一行即可覆盖所有 L2 输出。
- 标量字段（temperature/level/trend）单独落表便于 SQL 过滤（`WHERE market_level='overheat'`）。
- JSONB 字段保留完整原始输出，避免后续扩展需要 DDL。

#### Step B-4：SentimentAggregator.materialize_snapshot

**涉及文件**：
- `src/domain/collection/services/sentiment.py`

**实现要点**：

核心伪代码：
```python
async def materialize_snapshot(self, trade_date: date | None = None) -> dict:
    target_date = trade_date or self._get_today()

    # 关键：若指定历史日期，需让 _ensure_cache 基于该日期加载数据
    # 当前 _cache 按 trade_date key，可直接复用；但要防止污染当日缓存
    temp = await self.get_market_temperature(trade_date=target_date)
    overheat = await self.get_overheat_set(trade_date=target_date)
    theme = await self.get_leading_theme(trade_date=target_date)
    sentiment_overall = await self.get_sentiment_score(trade_date=target_date)

    payload = {
        "market_temperature": temp["temperature"],
        "market_level": temp["level"],
        "market_trend": temp.get("trend"),
        "signals": temp,
        "overheat_codes": overheat,
        "leading_theme": theme,
        "sentiment_agg": {"overall_score": sentiment_overall, "industry_scores": {...}},
        "contributors": self._build_contributors(temp, overheat, theme),
    }
    self._signal_repo.upsert_snapshot(snapshot_date=target_date, **payload)
    return payload
```

**易错点**：
- 🚨 `get_*` 方法当前可能**不接收 `trade_date` 参数**（上下文只说"按 trade_date 缓存"）。若接口签名不支持历史日期，需要先扩展 L2 方法签名以 `trade_date: date | None = None` 接收外部日期；`_ensure_cache` 需相应支持按 trade_date 参数查询而非 `self._get_today()`。[TODO: 需要补充 L2 方法当前是否支持 trade_date 入参；若不支持，需在本步骤内一并扩展]
- 不要污染 `_cache[today]`：历史回补时使用独立 key（如 `_cache[target_date]`）。
- 写入后不自动失效缓存：快照表是"写多读少"，与当日缓存独立。

## C. 3.1 sector_kline 数据源

### C.1 需求分析

- **核心需求**：在 `MarketAggregator` 新增 `data_type=sector_kline` 数据源（日 K 为主），写入 `ft_market_cache`，供 `EventFeedbackAggregator._compute_reaction` 回填：
  - `sector_change_1d`（T+1 日板块涨跌幅）
  - `sector_change_3d`（T+3 日板块涨跌幅）
  - `reaction_delay_minutes`（市场反应延迟，需要分钟 K，见下）
- **边界条件**：
  - 板块范围：与 `sector_ranking` 源一致（行业板块 + 概念板块，约 100~200 个）。
  - 日 K 回溯：60 天（对齐现有 `get_stock_kline` 默认 limit=60），足够覆盖 3d 回填。
  - `ft_market_cache` 是 KV 模式（每 data_type 只 1 行），所有板块 K 线**打包成一个 JSONB**。
  - **分钟 K 不入 ft_market_cache**（数据量过大，累加 N 天 JSONB 会膨胀到 MB 级）。采用"按需查询 + 短期 TTL 缓存"方案，见 Step C-5。
- **复杂度判定**：**复杂**。新增外部接口调用、数据结构设计、回填逻辑联动、分钟 K 特殊处理。

### C.2 技术方案

#### C.2.1 选型决策

**板块 K 线来源**：
- ✅ **使用 EM 的板块 K 线接口**（扩展 `clients.eastmoney`）。上下文已知 `get_stock_kline(code, period)` 存在；EM 板块代码形如 `90.BK0475`（industry）/ `90.BK0900`（concept），可复用同一接口，只需封装一层 `get_sector_kline(sector_code, period, limit)`。
- ❌ 不用 Sina：上下文只暴露了 `get_sector_ranking`（当日），无历史 K 线。
- [TODO: 需要验证 EM `get_stock_kline` 是否兼容 `BKxxxx` 板块代码；若不兼容，需单独新增 EM 板块 K 线端点 `push2his.eastmoney.com/api/qt/stock/kline/get?secid=90.BK...`，在 `clients/eastmoney.py` 中实现 `get_sector_kline`]

**板块映射**：
- `ft_events.related_sectors` 字段当前以"板块名称"（中文）存储（推测自 `sector_ranking` 的 `name` 字段）。[TODO: 需要补充 related_sectors 的实际存储格式，代码中直接 `grep -n "related_sectors" src/domain/extraction/`]

#### C.2.2 存储模型

**data_type=sector_kline，JSONB 结构**：

```json
{
  "updated_at": "2026-04-20T15:35:00+08:00",
  "trade_date": "2026-04-20",
  "sectors": {
    "BK0475": {
      "name": "半导体",
      "sector_type": "industry",
      "klines": [
        {"date": "2026-04-20", "open": 100.1, "close": 101.5, "high": 102.0, "low": 99.8, "volume": 12345678, "turnover": 987654321}
      ],
      "change_1d": 1.40,
      "change_3d": 3.80
    }
  }
}
```

**数据量估算**：
- 200 板块 × 60 天 × 7 字段 ≈ 84,000 数值 → JSONB 约 600~800KB（可接受，PostgreSQL JSONB 单行建议 < 1MB）。
- TTL：900s（15 分钟，比 market_overview 长，因日 K 变化频率低）。

#### C.2.3 分钟 K 线策略（reaction_delay_minutes）

分钟 K 单独处理：
- **不持久化到 ft_market_cache**：60 板块 × 240 分钟 × 60 天 ≈ 860,400 点，JSONB 会膨胀。
- **按事件触发查询**：EventFeedbackAggregator 回填时，针对事件关联板块调用 `get_sector_minute_kline(sector_code, trade_date)`，取当日分钟 K 计算 `reaction_delay_minutes`。
- **短期内存缓存**：MarketAggregator 增加一个 `_minute_kline_cache: dict[(sector_code, date), list]`，TTL 300s，避免同板块多事件重复拉取。

### C.3 数据模型

无新表。新增：
- `ft_market_cache` 新 `data_type='sector_kline'` 行。
- 无 schema 变更。

#### Step C-2：MarketAggregator — 新增 sector_kline source

**目标**：在 `MarketAggregator` 注册 `sector_kline` 数据源，每次采集时：
1. 读取最新 `sector_ranking`（含 bk_code，见 C.2.1），拿到板块列表。
2. 对每个板块并发调用 `get_sector_kline`。
3. 利用现有 `_calc_cumulative_change(klines, days)` 算 change_1d/3d。
4. 打包成 C.2.2 结构，UPSERT 到 `ft_market_cache`。

**涉及文件**：
- `src/domain/collection/services/market.py`

**实现要点**：

```python
# SourceDef 注册
SourceDef(
    data_type="sector_kline",
    ttl_seconds=900,
    fetcher=self._fetch_sector_kline,
)

async def _fetch_sector_kline(self) -> dict:
    # 1. 读取 sector_ranking（必须已经跑过一次，拿到 bk_code 列表）
    ranking = await self._repo.find_by_type("sector_ranking")
    if not ranking or "data" not in ranking:
        raise RuntimeError("sector_ranking not ready; run sector_ranking source first")

    sectors_list = self._extract_sectors_with_codes(ranking["data"])  # [(bk_code, name, type)]

    # 2. 并发拉 K 线（限流，避免打爆 EM）
    import asyncio
    semaphore = asyncio.Semaphore(10)

    async def fetch_one(bk_code, name, stype):
        async with semaphore:
            resp = await self._em.get_sector_kline(bk_code, period="101", limit=60)
            klines = resp.get("data", {}).get("klines", [])
            return bk_code, {
                "name": name,
                "sector_type": stype,
                "klines": klines,
                "change_1d": self._calc_cumulative_change(klines, 1),
                "change_3d": self._calc_cumulative_change(klines, 3),
            }

    results = await asyncio.gather(
        *[fetch_one(c, n, t) for c, n, t in sectors_list],
        return_exceptions=True,
    )

    # 3. 组装，异常板块记 log 但不整体失败
    sectors = {}
    for r in results:
        if isinstance(r, Exception):
            logger.warning("sector kline fetch failed", exc_info=r)
            continue
        bk_code, payload = r
        if payload["klines"]:
            sectors[bk_code] = payload

    return {
        "updated_at": datetime.now(TIMEZONE).isoformat(),
        "trade_date": str(date.today()),
        "sectors": sectors,
    }
```

**易错点**：
- 并发数 >10 会触发 EM 限流（429），保守设 10。
- `sector_ranking` 必须在 `sector_kline` **之前**运行；调度上要保证顺序，或在 `_fetch_sector_kline` 内先调 `_fetch_sector_ranking` 拿最新列表。
- `_calc_cumulative_change` 可复用（已存在），注意传入的 `klines` 最新在前/在后的顺序——必须与现有约定一致。
- 板块映射索引改为 `bk_code`（键），避免中文名称变动导致回填失败。

#### Step C-3：MarketAggregator — 分钟 K 内存缓存 & 按需查询

**目标**：新增 `get_sector_minute_kline(bk_code, trade_date)` 实例方法（**不**是 SourceDef），带 300s 内存 TTL。

**涉及文件**：
- `src/domain/collection/services/market.py`

**实现要点**：

```python
self._minute_kline_cache: dict[tuple[str, date], tuple[float, list]] = {}  # (code, date) -> (expire_at, klines)

async def get_sector_minute_kline(self, bk_code: str, trade_date: date) -> list:
    key = (bk_code, trade_date)
    now = time.time()
    cached = self._minute_kline_cache.get(key)
    if cached and cached[0] > now:
        return cached[1]

    resp = await self._em.get_sector_minute_kline(bk_code, trade_date)
    klines = resp.get("data", {}).get("klines", [])
    self._minute_kline_cache[key] = (now + 300, klines)
    return klines
```

- 缓存不跨进程共享（多 worker 会重复拉一次，但单 worker 内避免同板块重查）。
- 定期清理：可简单遍历 `_minute_kline_cache` 删除过期项，避免内存泄漏（事件回填场景下 key 数可控）。

async def _compute_reaction(self, event) -> dict:

    # 既有: north_flow_1d, sector_volume_change ...

    # 新增：sector_change_1d/3d
    sector_kline_cache = await self._market_repo.find_by_type("sector_kline")

    # 新增：reaction_delay_minutes

**`_calc_reaction_delay` 核心逻辑**：
```python
async def _calc_reaction_delay(self, event) -> int | None:
    # 1. 找到事件关联的第一个板块 bk_code
    bk_code = await self._resolve_bk_code(event.related_sectors[0])
    if not bk_code:
        return None

    # 2. 取事件发生当日分钟 K
    minute_klines = await self._market_agg.get_sector_minute_kline(bk_code, event.occurred_at.date())
    if not minute_klines:
        return None

    # 3. 以事件发生时刻为 t0，向后扫描分钟 K，找到第一根涨跌幅 > THRESHOLD 的 K 线
    THRESHOLD = 0.005  # 0.5%
    t0 = event.occurred_at
    for kline in minute_klines:
        bar_time = parse_bar_time(kline["date"])  # "2026-04-20 09:35"
        if bar_time < t0:
            continue
        change_pct = (kline["close"] - kline["open"]) / kline["open"]
        if abs(change_pct) >= THRESHOLD:
            return int((bar_time - t0).total_seconds() / 60)

    return None  # 全日未触发显著反应
```

**易错点**：
- `event.occurred_at` 可能为 TIMESTAMPTZ；分钟 K 时间需同一时区。
- 板块 K 线的 5 分钟粒度意味着 delay 精度为 5 分钟；若业务需要更精细可切 klt=1。
- 非交易时段事件（晚间新闻）：`_calc_reaction_delay` 返回 None 或用次日开盘分钟 K（建议 None，避免误导）。
- 移除原 TODO 注释"sector_change_1d/3d (涨跌幅) 需要 sector K 线数据..."
