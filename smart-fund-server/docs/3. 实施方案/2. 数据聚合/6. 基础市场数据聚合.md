# 基础市场数据聚合（重新设计）

## 1. 需求分析

### 1.1 核心需求拆解

**角色重定位**：基础市场数据聚合在 α 优先级中不直接产生信号，但承担两个不可替代的"地基职责"：

1. **决策上下文（市场环境）**：决策引擎做"该不该买"的判断时，必须知道当下的大盘冷热、板块结构、外部市场情绪、汇率/期货/海外指数。这些不是"周期性指标"（那是宏观聚合的事），而是**当前快照**——上证今天涨了多少、创业板分化如何、北向今天什么走向、纳斯达克隔夜怎么收的。
2. **执行回路（个股/基金画像）**：交易执行环节要知道"这只基金当前净值/重仓股估值"、"这只持仓股当前 PE/PB/所属板块"——这是**按需查询**，不是定时入库。

由此自然分裂为两种数据形态，本模块**统一管理但分别处理**：

- **定时快照（push 模式）**：8 个面向"市场全景"的 KV 数据项，按 1~15 分钟节奏覆盖刷新到 `ft_market_cache`。
- **按需查询（pull 模式）**：基金净值/持仓、个股详情、持仓估值——不进缓存，调用时实时打客户端，由聚合器统一暴露便捷方法供上游使用。

**关键差异化产出（决策引擎依赖）**：板块涨跌排行不仅有当日涨幅，还要带 **3 日 / 5 日累计涨幅 + 过热标记** —— 这是决策打分模型"避免追高过热板块"的硬性输入，必须在本模块完成。

### 1.2 边界与约束

1. **职责边界（与其他聚合的分工）**：
   - **vs 资金流聚合（collect_fund_flow）**：北向资金、龙虎榜、个股资金流向归 `collect_fund_flow` 累积入 `ft_market_flow`；本模块的 `market_overview` / `market_environment` 快照里**冗余**保留它们的最新切片仅为快查方便，不视作 SSOT，不重复历史化。
   - **vs 宏观聚合（collect_macro）**：USDCNY 中间价、SHIBOR、LPR 的**时序数据**归 `collect_macro` → `ft_macro_indicators`；本模块的 `forex` 快照保留实时报价（不止 USDCNY，含欧/日/英/港等），用途不同（最新行情 vs 时序）——**双写允许**。
   - **vs 情绪聚合（collect_sentiment）**：板块涨跌排行属客观行情，不属舆情；股吧热度、雪球榜在情绪模块。
2. **存储模型约束（KV 覆盖模式的本质）**：
   - `ft_market_cache` 唯一约束建在 `data_type` 列上（unique），每次写入是 `INSERT ... ON CONFLICT (data_type) DO UPDATE`。
   - **每个 data_type 永远只保留 1 行**——不是历史表，不能用来做时间序列查询。
   - 每行带 `expires_at`，业务读侧自行决定"过期是否还用"——**DB 层不淘汰**，只覆盖。
3. **采集间隔约束**：
   - 任务调度：`collect_market` 每 60 秒触发一次（最高频聚合任务）。
   - 单源间隔由 `SourceDef.interval` 控制，到点才打外部 API。当前最快 `market_overview` 120s、其余 300s。
   - 不得随意把 source `interval` 调到 60s 以下，免得把腾讯/新浪打挂。
4. **不做 normalize**：所有源都用 `_wrap_cache(data_type, raw, ttl)` 包一层，原始数据直接进 `data` JSONB 字段。**业务层读到什么结构由客户端决定**——这里不规范化。代价是契约性弱、好处是迭代成本低（客户端字段变更不需要改 normalize）。
5. **板块过热增强是本模块的"特异化"逻辑**：唯一在快照之上做派生计算的源；其他源全部透传。
6. **按需查询的方法不需要缓存**：`get_fund_snapshot` / `get_stock_detail` / `get_holdings_valuation` 是工具方法，调用频率由上游决定，自带 client 内部缓存（如有）。本模块不为其引入二级缓存——避免"缓存一致性 + 缓存淘汰"两个坑。

### 1.3 复杂度判定

**复杂度：中等（拆 4 步）**

- 不是简单 CRUD：涉及双模式（push 快照 + pull 查询）、板块派生增强、与其他聚合的边界划分；
- 不是复杂改造：基础设施（BaseAggregator / MarketCacheRepository / 7 客户端）已就位，绝大部分代码沿用统一模板。

### 2.2 关键技术选型及理由

| 决策点 | 选型 | 理由 |
|---|---|---|
| 存储模型 | KV 覆盖（unique on `data_type`） | 业务只关心"最新"；保留历史既无收益又增加表膨胀；用 `expires_at` 标注新鲜度即可 |
| 写入接口 | `MarketCacheRepositoryImpl.upsert(data_type, data, expires_at)` | 已有 SQLAlchemy 抽象 + `pg_insert.on_conflict_do_update`，子类 `_save` 直接调，避免裸 SQL |
| normalize 策略 | 全部透传 `_wrap_cache`，**不做字段标准化** | 8 个源结构差异极大且来自外部不稳定接口；规范化收益不抵维护成本；业务层按 data_type 各自解析即可 |
| 板块 3d/5d 累计涨幅 | 用**领涨股**的 EM 日 K 线代理板块涨幅（取最近 6 根 K 线计算） | EM 板块自身的 3d/5d 涨幅 API 不稳定；领涨股代理误差可控且实现简单；字段命名带 `_proxy` 后缀显式标注是估算 |
| 过热阈值 | `chg_3d_proxy > 5.0%` → `is_overheated=True` | 来源决策打分模型规约："板块近 3 天累计涨幅 > 5% 时降权或跳过"；阈值经验值，可后续回测调整 |
| 双模式聚合（push + pull） | 把 push 源放 `self.sources`（参与 tick 调度），pull 方法直接挂在 Aggregator 上（不进 `sources`） | 调度循环只迭代 `sources`，pull 方法不参与定时；语义清晰，互不干扰 |
| `_get_checkpoint` | 直接 `return None`（不做增量） | KV 覆盖模式没有"上次到哪"的概念，每次都是全量刷新一行；checkpoint 机制强行套上去反而增加状态噪声 |
| 任务节奏 | 60s tick + 源级 interval 节流 | 60s 是基础设施节奏（决策引擎 / 监控按秒级响应），source 自带 interval 防止过载外部 API |
| 与 ft_market_flow 双写 | 允许；不试图统一 | 二者用途不同（覆盖快查 vs 历史累积），强行合并会破坏 KV 模式 |

## 3. 数据模型

### 3.1 `ft_market_cache`（已存在，无需变更）

```sql
CREATE TABLE ft_market_cache (
    id          SERIAL PRIMARY KEY,
    data_type   VARCHAR(50) NOT NULL,            -- 业务键，UNIQUE
    data        JSONB       NOT NULL,            -- 原始结构透传
    expires_at  TIMESTAMP   NOT NULL,            -- 业务层读时自检"是否过期"
    created_at  TIMESTAMP   DEFAULT NOW()        -- UPSERT 时被覆盖
);

-- 唯一约束（实质上是覆盖键）
CREATE UNIQUE INDEX uniq_ft_market_cache_data_type
    ON ft_market_cache (data_type);
```

**关键性质**：
- `data_type` 是覆盖键。任何一个 data_type 永远只占 1 行，写入即"擦掉旧的"。
- `expires_at = now() + ttl`（TTL 由源定义提供：120s / 300s）。
- DB 不主动删过期行；业务读时自行判断 `expires_at > now()`。

### 3.2 8 个 data_type 全表

| data_type | 频率 | TTL | 客户端 | 数据形态 | 增强逻辑 | 状态 |
|---|---|---|---|---|---|---|
| `market_overview` | 120s | 120s | `clients.aggregator.get_market_overview()` | 大盘指数行情 + 涨跌家数 + 成交额 + 资金流向 + 涨跌停 + 大小盘对比 | 无 | ✅ |
| `market_environment` | 300s | 300s | `clients.aggregator.get_market_environment()` | 沪深300/创业板趋势 + 北向资金 + 融资融券 + 国债收益率 | 无 | ✅ |
| `global_index` | 300s | 300s | `clients.sina.get_global_index()` | 道琼斯/纳斯达克/标普/恒生/日经/台北等 | 无 | ✅ |
| `futures_domestic` | 300s | 300s | `clients.sina.get_futures()` | 上海金/铜/原油/白银/铁矿石等 | 无 | ✅ |
| `futures_intl` | 300s | 300s | `clients.tencent.get_intl_futures()` | 纽约金/银/原油/天然气/铜/大豆/玉米/小麦 | 无 | ✅ |
| `forex` | 300s | 300s | `clients.sina.get_forex()` | 美元/欧元/日元/英镑/港币 | 无 | ✅ |
| `sector_ranking` | 300s | 300s | `clients.sina.get_sector_ranking()` + `clients.eastmoney.get_stock_kline()` 多次 | 板块涨跌排行（topRise/topFall），**每个板块附 chg_3d_proxy / chg_5d_proxy / is_overheated** | ✅ 已实现 | ✅ |
| `sector_kline` | 900s | 900s | `clients.eastmoney.get_sector_list()` + `get_sector_kline()` 并发 | EM 行业+概念板块日 K 线（60天），含 `change_1d/3d`；附带 `name_map`（板块名→BK代码）和 `sector_map` 缓存 | ✅ 已实现 | ✅ |

### 3.3 sector_ranking 增强后的字段约定

```
sector_ranking.data = {
    topRise: [
        {
            name:           "人工智能",
            chg:            2.30,           // 当日涨幅 % （Sina 原值）
            leadStock:      {code: "sz000001", name: "...", ...},
            chg_3d_proxy:   6.85,           // 由领涨股 K 线 6 根算出（最近 4 根：今日 vs 3日前）
            chg_5d_proxy:   9.12,           // 由领涨股 K 线 6 根算出（最近 6 根：今日 vs 5日前）
            is_overheated:  true,           // chg_3d_proxy > 5.0
            ...原 Sina 字段透传
        },
        ...
    ],
    topFall: [...]
}
```

**字段命名约定**：`_proxy` 后缀强制标注"代理估算"，让消费方知道这不是板块本身真实累计涨幅而是领涨股估算——避免被误用作精确度量。

### 3.4 按需查询不入库

`get_fund_snapshot` / `get_stock_detail` / `get_holdings_valuation` **不写 ft_market_cache**，每次调用现打客户端，返回结构由客户端决定（见源码）。理由见 §1.2-6。

## 4. 接口设计

### 4.1 写侧（仅供 `tick` 内部调用）

```python
# MarketCacheRepositoryImpl
def upsert(self, data_type: str, data: dict, expires_at: datetime) -> None
```

子类 `MarketAggregator._save(items)` 遍历 items 调 `upsert`，items 由各 normalize 函数（统一为 `_wrap_cache`）产出，结构固定为 `{data_type, data, ttl}`。

### 4.2 读侧（业务层入口）

**模式 A 缓存读取**（统一从 `ft_market_cache` 取）：

```python
class MarketAggregator:
    async def query(data_type: str | None = None, limit: int = 50) -> list[dict]
        # 通用：按 data_type 拉行
    async def get_market_overview() -> dict | None
        # 取 data_type=market_overview 最新行的 data 字段
    async def get_global_markets() -> dict
        # 合并 global_index / futures_domestic / futures_intl / forex 四类
    async def get_sector_overview() -> dict | None
        # 取 sector_ranking 最新行
```

**模式 B 按需查询**（直接打客户端）：

```python
class MarketAggregator:
    async def get_fund_snapshot(fund_code: str) -> dict
        # THS: get_fund_detail + get_fund_base
    async def get_stock_detail(code: str) -> dict
        # Tencent: get_stock_quote + get_industry_rank + get_stock_plates
    async def get_holdings_valuation(fund_code: str) -> dict
        # 代理到 clients.aggregator.get_holdings_valuation
```

### 4.3 业务层使用约定

```sql
-- 业务层读"最新且未过期"的统一 SQL 模板
SELECT data FROM ft_market_cache
WHERE data_type = :type AND expires_at > NOW();

-- 过期处理策略由业务层决定（可选返回旧值 + 标记 stale）
SELECT data, expires_at < NOW() AS is_stale FROM ft_market_cache
WHERE data_type = :type;
```

### 4.4 与 BaseAggregator / Repository 的关系

- **不破坏 BaseAggregator 协议**：实现 `_save` / `_get_checkpoint` / `query` 三个必需接口。
- `_get_checkpoint` 返回 None：本模块不需要增量游标。
- `_compute_checkpoint` 沿用基类默认实现（基类会跳过 None 路径）。
- `tick()` 仍由基类提供：源级 interval 控制 / 分布式锁 / 失败重试 / `ft_collection_state` 写入全部复用。

### Step 1：8 个 data_type 快照入库 ✅ 已完成

**当前实现**：
- `MarketAggregator.sources` 含 8 个 `SourceDef`，每个走对应客户端方法 + `_wrap_cache` normalize。

- 失败单条静默 warning，不影响其他源；符合"覆盖式 KV 不应让单源拖垮整批"的预期。

**验收已通过**：
- `SELECT data_type, count(*) FROM ft_market_cache GROUP BY 1` 全部 = 1（覆盖语义生效）。
- `SELECT * FROM ft_market_cache ORDER BY created_at DESC` 显示 7 行，间隔符合 source interval。

---

### Step 2：板块过热增强（chg_3d/5d_proxy + is_overheated）✅ 已完成

**当前实现**（`_fetch_sector_ranking_enriched` + `_enrich_sector_with_change`）：

1. 先 `clients.sina.get_sector_ranking()` 拿原始板块排行（topRise / topFall 两组）；
2. 对每个板块抽取 `leadStock.code`，去掉 `sh/sz/bj` 前缀拿到纯 6 位代码；
3. 收集所有领涨股代码，**并发**调 `clients.eastmoney.get_stock_kline(code, period="101", limit=6)` 拉日 K 线；
4. `_calc_cumulative_change(klines, days)` 用最近 `days+1` 根 K 线的首尾收盘价算累计涨幅；
5. 每个 sector 写入：`chg_3d_proxy` / `chg_5d_proxy` / `is_overheated`（chg_3d > 5.0%）。

**关键实现细节**：
- 用 `asyncio.gather(*tasks, return_exceptions=True)` 防止单只领涨股请求失败拖垮整批；
- `kline.data.klines` 取不到时该板块的 proxy 字段为 `None`，`is_overheated` 为 `False`（保守降级）；
- K 线 dict 与 字符串两种格式都兼容（防止 EM 接口未来格式变化）。

**已知边界**：
- 领涨股 ≠ 板块本身——这是 proxy 命名的来由。当板块涨幅由"少数妖股带动"时 proxy 会偏高；当板块"普涨但领涨股回调"时 proxy 会偏低。
- 阈值 `5.0%` 来自决策模型经验值，未做回测。**记入 `9. 待优化.md`**：待决策引擎跑起来后用真实持仓收益回测调参。

### Step 3：按需查询方法 ✅ 已完成

**当前实现**：3 个 pull 方法直接挂在 `MarketAggregator`：

- `get_fund_snapshot(fund_code)` — 并 detail + base 两路 THS 调用，单条失败仅 debug 日志、不抛；

## 8. 风险与注意事项

| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 领涨股 K 线代理与板块真实涨幅偏差大 | 中 | 决策可能误判过热 | 字段命名带 `_proxy` 显式标注；待优化项里登记"用 EM 板块自身 K 线 API 替代代理"，回测后调阈值 |
| Sina/Tencent 接口字段重命名 | 中 | 业务层取 data 失败 | 因为不做 normalize，影响下沉到读侧；建议业务层用字段存在性兜底，并由数据 SLA 监控 source 失败率 |
| 60s tick 高频访问外部 API 被限流 | 中 | 数据更新不及时 | source `interval` 已统一 ≥120s，远小于 tick 频率，实际外部访问节奏可控 |
| `expires_at` 用 naive datetime（无时区） | 低 | 跨时区部署可能错位 | 当前模型 `DateTime(timezone=False)` 与 `datetime.now()` 一致，单时区部署无问题；多时区部署前需统一改 timezone-aware |
| sector_ranking 增强使单 tick 时长变长 | 中 | 锁占用时间延长 | `acquire(lock_name, ttl=600)` 已远超实际耗时；`asyncio.gather` 并发拉 K 线，单源耗时控制在 5s 内 |
| 业务层把 ft_market_cache 当历史表查 | 高（认知偏差） | 永远只能查到 1 行 | 文档显式声明 KV 覆盖语义；时序需求引导到 `ft_market_flow` / `ft_macro_indicators` |
| 按需查询并发太多触发外部限流 | 中 | 个股/基金详情失败率上升 | 由调用方限流，不在本模块加缓存（避免一致性坑）；如压力大，下沉到 client 层加 LRU |
| 与 `collect_fund_flow` 北向数据双写口径不一致 | 低 | market_overview 与 ft_market_flow 北向数值瞬时差异 | 两者刷新节奏不同（120s vs 300s），允许差异；业务以 ft_market_flow 为 SSOT |
| 新加 data_type 时忘记加 `SOURCE_CONFIGS` | 中 | `ft_collection_state` 缺记录、tick 抛异常 | 加新 source 必须三处同改：`SOURCE_CONFIGS` / `_init_sources` / 跑一次 `python -m src.interfaces.cli init state` |
| 板块过热阈值 5.0% 未回测 | 中 | 误过滤"健康强势"板块 / 漏过滤"温水青蛙"板块 | 记入 `9. 待优化.md`；Phase 4 决策引擎产生持仓收益数据后回测调参 |
