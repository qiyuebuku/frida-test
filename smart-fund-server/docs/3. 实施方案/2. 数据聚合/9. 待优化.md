## 待优化事项

### 0.5 生产环境未应用 ft_sentiment_signal DDL（2026-07-31 记录）

**问题：** ORM、Repository、物化任务和 15:30 调度均已存在，但生产库没有
`ft_sentiment_signal` 表。当前部署脚本只执行 watchlist 专用迁移，不会自动应用
`schema/01_collection.sql` 中后续增加的表结构，因此任务无法形成稳定的生产数据。

**最佳方案：** 使用可追踪、按版本顺序执行的数据库迁移体系，部署时自动应用所有
尚未执行的幂等迁移，并记录迁移版本。

**当前方案：** 已新增 `20260731_sentiment_signal.sql` 幂等迁移，并将部署脚本改为
按文件名顺序应用全部迁移。代码与部署能力已经补齐，但生产环境尚未执行本次部署和
历史物化，因此不能将综合市场情绪分数标记为生产可用；该派生指标也不进入只展示
客观市场数据的首页。

**整改条件：** 执行生产部署、确认表存在并完成至少一个交易日物化后整改。

**优先级：** P1

### 0.1 jettask-rs 本地 wheel 打包需规范化（2026-07-04 记录）

**问题：** `/home/yuyang/easy-task/backend/jettask-rs/bindings/python/dist/jettask_python-0.1.0-py3-none-any.whl` 原始 wheel 只包含 `cpython-311` 原生扩展，`frida-test` 当前 Python 3.12 环境安装后会出现 `ImportError: 无法加载 jettask 原生扩展`。

**最佳方案：** 在 `jettask-rs` 项目内修正正式打包流程，让 wheel 按目标 Python 版本正确包含对应 `.so`，或产出符合平台标签的 wheel。

**当前方案：** 已将 `cpython-312` 和 `cpython-314t` 原生扩展补入本地 wheel，并在 `smart-fund-server` 的 `pyproject.toml` 中用 `file://` 固定到该本地 wheel。

**整改条件：** `jettask-rs` 的 Python binding 发布流程修正后，替换为标准构建产物，不再依赖手工补包。

**优先级：** P1

### 0.2 ft_raw_data 分区维护需要 owner 权限（2026-07-05 记录）

**问题：** `ft_raw_data` 按 `fetched_at` 月分区，当前表 owner 是 `postgres`，运行采集任务的数据库用户是 `jettask`。worker 进程不具备创建新月份分区的 DDL 权限，跨月后如果 owner 未提前创建分区，会出现 `no partition of relation "ft_raw_data" found for row`。

**最佳方案：** 由数据库 owner 提供受控的分区维护机制，例如定时提前创建未来分区，或创建 `SECURITY DEFINER` 存储过程供应用用户调用。

**当前方案：** 数据库已由 owner 安装 `public.ensure_ft_raw_data_partition(int, int)` 受控函数，应用用户 `jettask` 可调用该函数创建目标月份分区。代码在 worker 启动和 `save_raw()` 写入时都会检查分区；如果既没有 DDL 权限也不能调用受控函数，才降级为输出一次明确的 owner DDL 修复语句。

**整改条件：** 后续如果切换数据库或重建表，需要同步安装受控分区函数；长期可再补充数据库侧定时任务提前创建未来分区。

**优先级：** P1

### 1. 宏观政策聚合（collect_macro）

### 1.2 regime 权重与阈值需回测

- **问题**：五维度权重、regime 切换阈值（±0.3）、multiplier 范围（0.6~1.2）均为经验值。
- **最佳方案**：用真实持仓收益回测，优化权重和阈值参数。
- **当前方案**：经验值 + clip 硬上下界防止极端。
- **整改条件**：Phase 4 决策引擎跑起来后，积累足够历史数据。
- **优先级**：P3

### 1.3 社融/AKShare 数据源依赖

- **问题**：社融数据通过 AKShare 库间接从商务部获取，增加了第三方依赖。AKShare 的 TLS 处理依赖 `urllib3` 的 `TLSAdapter`，且商务部 API 可能变更。
- **最佳方案**：直接调用商务部 API（需解决 TLS 握手问题）或接入其他稳定数据源。
- **当前方案**：通过 AKShare `macro_china_shrzgm()` 获取，在异步执行器中运行。
- **整改条件**：商务部 API 稳定后可自行实现 HTTP 客户端，或迁移到更稳定的源。
- **优先级**：P3

### 1.4 policy_score 关键词匹配仍粗糙（AI 依赖）

- **问题**：`_policy_score` 仍依赖关键词匹配，虽有噪声过滤但仍会误匹配非宏观新闻。
- **最佳方案**：使用 AI 事件抽取的 `ft_events.stance` 字段判断政策方向。
- **当前方案**：v1 关键词统计 + `_NOISE_PATTERNS` 噪声过滤。
- **整改条件**：Phase 3 AI 事件抽取完成后，与整体 AI 规划统一实施。
- **优先级**：P4（随 AI 整体规划推进）

## 2. 情绪舆情聚合（collect_sentiment）

- **问题**：guba_posts 当前只取帖子数量/长度作为热度代理，未分析正负面，只有"强度"没有"方向"。
- **最佳方案**：Phase 4 前接 AI 对 posts 做 batch 极性分类，合成单股"情绪方向"（非仅"情绪强度"）。
- **当前方案**：纯数值热度，不接 LLM。
- **整改条件**：Phase 3 AI 事件抽取链路稳定后，复用 AI 能力。
- **优先级**：P2

### 2.3 sentiment 权重 & 过热阈值回测

- **问题**：单股得分规则（+0.05 / +0.10 / +0.15）、过热命中条数→penalty 映射（3→0.15、4→0.30、5→0.45）均为经验值。
- **最佳方案**：用决策引擎真实持仓回测调参。
- **当前方案**：经验值 + clip 硬上下界防止极端。
- **整改条件**：Phase 4 决策引擎产生持仓收益数据后回测。
- **优先级**：P2

### 2.4 tencent_hot_stocks 空数据治理

- **问题**：tencent_hot_stocks 偶发返回 `{"5min":[], "1hour":[]}`，normalize 已过滤但应记录空返回率。
- **最佳方案**：记录空返回率；持续 > 50% 则考虑摘除该源。
- **当前方案**：normalize 前置判空过滤，不入库。
- **整改条件**：积累 2 周以上数据后统计空返回率。
- **优先级**：P3

### 2.5 guba_posts 动态源扩容策略

- **问题**：当前固定前 10 只 watchlist，决策引擎需要对更多 code 查 sentiment_score 时覆盖不全。
- **最佳方案**：扩容 watchlist 上限，或改为"决策引擎需要谁就拉谁"的按需采集。
- **当前方案**：固定前 10 只。
- **整改条件**：Phase 4 决策引擎确定需要覆盖的 code 范围。
- **优先级**：P2

### 2.6 leading_theme 跨源融合

- **问题**：当前只用 limit_pool 的涨停原因，雪球热话题仅作为 confidence 倍增。
- **最佳方案**：待 collect_news 的行业聚类稳定后，引入"新闻主题 × 涨停主题"的三路投票。
- **当前方案**：涨停原因集中度 + 雪球话题关键词交叉。
- **整改条件**：Phase 3 AI 事件抽取产出稳定的行业分类。
- **优先级**：P3

## 3. 事件反馈聚合（agg_event_feedback）

### 3.2 交易日历缺失导致节假日 T+1 错算

- **问题**：T+1 取 `event_time.date() + 1d`，遇到周末/节假日会取到非交易日，查表为空。
- **最佳方案**：引入交易日历工具（从 market_overview 或专业接口获取下一个交易日）。
- **当前方案**：v1 只跳周末（周五晚事件 → T+1 = 下周一）；节假日误差接受。
- **整改条件**：接入交易日历数据。
- **优先级**：P3

### 3.3 reaction_delay_minutes 阈值经验值

- **问题**：`reaction_delay_minutes` 计算中"显著波动"阈值 1.0% 为拍脑袋值。
- **最佳方案**：用历史样本做 ROC 曲线调参。
- **当前方案**：固定 1.0% 阈值。
- **整改条件**：sector_kline 源上线 + 积累足够样本后回测。
- **优先级**：P3

### 3.4 sentiment_trend 精度低（ILIKE 模糊匹配）

- **问题**：衰退检测的情绪趋势用 `data::text ILIKE '%industry%'` 匹配，噪声高（"军工"匹配"军工概念"也匹配"民工出行"）。
- **最佳方案**：改为按"事件关联股票代码"聚合情绪指标，精确到个股层面。
- **当前方案**：v1 ILIKE 模糊匹配。
- **整改条件**：建立 industry → stock_code 映射。
- **优先级**：P3

### 3.5 ft_news ILIKE 匹配噪声

- **问题**：news_count_24h 用 ILIKE 模糊匹配行业名，会匹配到不相关新闻。
- **最佳方案**：替换为事件级反向索引（`ft_events.industries` ARRAY 包含查询）。
- **当前方案**：ILIKE 模糊匹配。
- **整改条件**：ft_events 数据量足够且 industries 字段标准化。
- **优先级**：P3

### 3.7 衰退检测 4 信号权重经验值

- **问题**：news_density(0.25) / fund_flow(0.30) / stream_state(0.30) / sentiment_trend(0.15) 为经验值，未回测。
- **最佳方案**：用持仓数据跑起来后，以实际止损/复盘数据回测调参。
- **当前方案**：经验值权重。
- **整改条件**：Phase 4 决策引擎产生持仓收益数据后回测。
- **优先级**：P3

## 4. 行业市场快照与 Watchlist 调度

### 4.0 ETF 盘中申赎只能取得深市估算口径（2026-07-31 记录）

**问题：** 当前公开接口不能提供沪深全市场、经交易所确认的 ETF 盘中净申购。同花顺页面展示的是根据深市申购量、赎回量和 IOPV 计算的估算值，单只 ETF 排名还限定在同花顺合作 ETF 池。

**最佳方案：** 接入交易所或授权行情商提供的沪深 ETF 申赎清单、PCF 和盘中确认数据，并同时保留估算值与最终确认值用于偏差评估。

**当前方案：** 按同花顺 App 的能力边界保存深市 ETF 预估净流入分钟趋势和合作 ETF 池流入榜首；所有记录均标记 `value_type=estimated`、`coverage_market=szse_etf` 和 `is_official_subscription=false`，盘后仍以交易所官方日份额变化作为事实确认。

**整改条件：** 获得交易所授权接口或稳定覆盖沪深市场的商业数据服务后实施。

**优先级：** P2

### 4.1 跨 Provider 板块身份尚未完全标准化（2026-07-31 记录）

**问题：** 东方财富、同花顺和新浪对同一行业或概念使用不同代码与名称。直接按名称合并可能把相近但不同的板块错误视为同一对象。

**最佳方案：** 建立可审计的板块身份映射表，保存 Provider 原始身份、统一身份、映射依据、置信度和生效时间，并允许人工修订。

**当前方案：** 快照保留 Provider 原始板块代码和名称；无法确认映射时标记 `mapping_pending`，不做猜测式合并。

**整改条件：** 至少积累五个交易日的多源板块目录与成分数据，能够基于成分重合度评估映射质量后实施。

**优先级：** P2

### 4.2 市场快照尚未实施时间分区与自动留存（2026-07-31 记录）

**问题：** 30 秒和 60 秒全量快照会持续增加 `ft_market_snapshots` 的数据量。当前索引能够支持初期查询，但长期运行后会增加存储和索引维护成本。

**最佳方案：** 按 `observed_at` 对快照表进行月度时间分区，结合数据用途定义原始高频快照、降采样快照和日级聚合的分层留存周期。

**当前方案：** 使用批量 UPSERT、稳定时间桶和时间索引保存完整历史，不提前删除尚未验证价值的数据。

**整改条件：** 连续运行至少一个月并取得真实每日行数、查询模式和磁盘增长数据后，确定分区与留存参数。

**优先级：** P1

### 4.3 板块参考数据单任务耗时可能随目录规模增长（2026-07-31 记录）

**问题：** `market_reference_data` 会遍历板块目录并读取成分。板块数量持续增长或上游变慢时，单次任务可能执行过久。

**最佳方案：** 目录任务只负责发现板块，再按板块分批投递成分采集子任务；每批独立审计、重试和推进检查点。

**当前方案：** 现阶段由一个低频任务顺序完成目录与成分采集，功能完整，但任务运行时间与板块数量线性增长。

**整改条件：** 生产运行中单次任务超过 Worker 超时预算，或板块数量使任务长期占用 Worker 时拆分。

**优先级：** P2

### 4.4 旧市场聚合与知识投影仍依赖 `ft_market_cache`（2026-08-05 更新）

**问题：** 新市场观测链路已经以 `ft_market_snapshots` 为唯一事实来源并停止写入最新投影，但旧 `domain/collection/services/market.py` 聚合任务和金融知识源投影仍读取 `ft_market_cache`，暂时不能直接删除表。

**最佳方案：** 将旧市场聚合结果迁移为规范化快照或专用事实表；知识投影改读这些事实来源。需要短期读缓存时使用 Redis，并允许从 PostgreSQL 最新快照回源，最终删除 `ft_market_cache`。

**当前方案：** 市场观测看板、同花顺 ETF、期货、黄金、美股、板块和个股排行不再双写 `ft_market_cache`；股票排行接口已改为读取 `stock_ranking` 最新快照。旧聚合与知识投影维持原表，避免扩大本次迁移范围。

**整改条件：** 完成旧市场聚合 `data_type` 到快照/事实表的逐项映射，并完成金融知识源全量重建验证。

**优先级：** P2

### 4.5 生产连续运行验收尚未完成（2026-07-31 记录）

**问题：** 单元测试、集成测试和真实接口单次联调只能验证链路正确性，不能证明跨交易日、午休、夜盘、停机恢复和上游波动下的长期稳定性。

**最佳方案：** 连续运行五个交易日，逐项验收市场广度、板块快照、ETF 日份额、Watchlist 优先级、停机追赶、不可回填缺口和任务隔离。

**当前方案：** 代码链路和测试已完成，真实接口已完成单次联调；生产持续运行验收等待部署后的自然交易时段。

**整改条件：** 生产调度部署并跨越五个完整交易日。

**优先级：** P1

### 4.6 市场记录的新鲜度和字段语义尚不能直接作为 Agent 决策语义（2026-08-09 记录）

**问题：** 2026-08-09 直接请求生产 Market Observatory 发现：非交易日的部分宽度、
板块、ETF 和黄金记录仍可能标记 `realtime` 或使用当日 `trade_date`；Provider 历史列
在周末重新拉取后会更新 `observed_at/fetched_at`；任务全部成功或运行时，个别排行和
旧聚合维度仍可能停留在更早交易日；不同业务指标还可能复用 `change_pct` 等通用字段。
此外，`macro_regime` 抽样的 policy contributors 中出现个股评论性内容，说明派生信号
输入分类仍需质量校验。

**最佳方案：** 保留原始时间和 Provider 载荷，同时在规范化层增加
`time_basis`、`effective_session_date`、`source_time_available`、`is_new_fact`、
`is_carry_forward`、明确指标单位/口径和质量状态；新鲜度按交易日历、发布频率和事实
时间计算。任务健康、数据健康和决策可用性分别评估。派生信号保存算法版本和输入来源，
在分类或量纲异常时拒绝进入正式 Agent Frame。

**当前方案：** 原始快照、业务日期和 Provider 字段均已保留，前端能够展示采集结果；
但现有 `freshness_status` 和通用字段只能用于数据观测，未经 Agent 语义归一化和质量门禁
不能直接支持自动投资结论。

**整改条件：** 完成跨数据域时间语义矩阵、单位与指标字典、非交易日回归测试、旧数据
混合测试、派生信号 contributor 分类测试，并使用真实接口样本验收。

**优先级：** P1

### 同花顺实时流服务收到 SIGTERM 后退出超时（2026-08-08 记录）

**问题：** `smart-fund-ths-realtime-stream` 收到 systemd 的 SIGTERM 后，部分长期读取协程未在 `TimeoutStopSec` 内退出，服务重启需要等待 systemd 强制终止。

**最佳方案：** 实时流客户端的 stop 操作主动关闭 socket、唤醒所有阻塞读取，并由服务在固定短超时内取消仍未结束的 TaskGroup 子任务，确保可预测地优雅退出。

**当前方案：** 生产实时采集和单连接订阅已经恢复；本次部署使用 systemd 强制终止旧进程后启动新进程，没有把超时强杀包装成优雅退出修复。

**整改条件：** 为 `THSNativeRealtimeStreamClient.stop()` 和服务 TaskGroup 增加关闭故障注入测试后整改。

**优先级：** P1
