# 补充 · Text Extraction Pipeline 与 Financial News Extraction Strategy 技术实施方案

> 对应设计文档：`../../5. 设计方案/1. 知识图谱/2. 通用知识基础设施设计方案.md`、`../../5. 设计方案/1. 知识图谱/4. 金融领域适配器设计方案.md`  
> 关联步骤：Step 3 · Adapter 协议、Step 5 · Compiler、Step 8 · Financial KG Adapter  
> 本文补齐“真实新闻如何进入知识图谱”的正式实施方案。

---

## 0. 一句话说清楚

正式链路不是 Notebook 自己抽取金融关系，也不是通用知识层内置一个新闻业务模块。

正式链路是：

```text
ft_news / ft_market_flow / ft_market_cache / ft_sentiment / ft_macro_indicators
  -> 业务方 Source Mapper
  -> 标准 source records
  -> Financial Adapter
  -> Financial News Extraction Strategy
  -> Text Extraction Pipeline 执行抽取
  -> Knowledge Compiler
  -> kg_nodes / kg_edges / kg_evidence
```

Notebook 只能作为验证和演示入口。  
正式抽取能力必须沉到 Financial Adapter 的领域策略里。

---

## 1. 背景问题

当前 Notebook 可以把业务表投影成 Adapter records，再调用 `KnowledgeService.compile_kg` 写入 `kg_*`。

但如果 Notebook 自己长期负责：

- 判断新闻提到了谁。
- 判断新闻影响了谁。
- 调用 AI 抽取金融关系。
- 决定关系置信度和状态。

那么金融 Adapter 就会退化成搬运工具，知识图谱服务也会被 Notebook 临时代码绑死。

正确边界是：

| 层 | 负责什么 | 不负责什么 |
|---|---|---|
| 业务方 Source Mapper | 读取业务库，把具体表字段投影为标准 source record | 不决定金融关系，不直接写 `kg_*` |
| 通用 Text Extraction Pipeline | LLM 调用、重试、超时、JSON 解析、schema 校验、evidence span 绑定、失败降级 | 不知道股票、行业、概念、`ft_news` |
| Financial Extraction Strategy | 金融 ontology、金融 prompt、实体/关系候选、置信度和复核规则 | 不直接读业务表，不直接写数据库 |
| Knowledge Compiler | 编译 node/edge/evidence，写入 `kg_*` | 不做金融语义判断 |

---

## 2. 实施边界

### 2.1 通用层可以新增

新增通用抽取管道，但只能表达领域无关能力：

```text
TextExtractionInput
TextExtractionResult
ExtractedEntity
ExtractedRelation
EvidenceSpan
TextExtractionStrategy
TextExtractionPipeline
```

允许做：

- 拼装领域策略给出的 prompt。
- 调用 LLM gateway。
- 解析 JSON。
- 校验输出 schema。
- 校验 evidence span 能在原文中定位。
- 对失败结果生成 warning。
- 支持 batch、timeout、retry、dry-run。

禁止做：

- 内置 `stock/fund/industry/concept`。
- 内置 `ft_news` 字段。
- 内置金融关系类型。
- 根据通用规则判断 `benefits_from/hurt_by`。

### 2.2 Financial Adapter 必须新增

金融 Adapter 新增抽取策略：

```text
FinancialNewsExtractionStrategy
```

负责：

- 金融实体类型：`stock / fund / industry / concept / institution / macro_indicator`。
- 金融关系类型：`mentions / affects / benefits_from / hurt_by / causal_hint`。
- 金融 prompt。
- 金融别名和代码规则。
- 金融置信度规则。
- 哪些边可以 active，哪些只能 candidate 或 review_required。

### 2.3 Notebook 必须降级为入口

Notebook 保留：

- 读取业务表。
- 显示源表数量。
- 把源表投影成标准 source records。
- 调用 KG API/Service 编译。
- rebuild wiki/index。
- 查询和质量扫描。

Notebook 不应长期负责：

- 金融关系抽取 prompt。
- AI enrichment 主逻辑。
- 置信度规则。
- 关系状态规则。

## 3. Source Record 契约

### 3.1 news_articles

业务方从 `ft_news` 投影：

```text
ft_news.id           -> source_id = ft_news:{id}
ft_news.title        -> title
ft_news.summary      -> summary
ft_news.content      -> text
ft_news.published_at -> published_at
ft_news.source_name  -> source_name
ft_news.url          -> url
```

必填：

```text
source_id
title or text
published_at
```

可选：

```text
summary
source_name
url
symbols
language
```

### 3.2 policy_news

来自政策、公告、监管文件、公告类新闻。

输出默认可以生成：

- `policy` node。
- `mentions` edge。
- `affects` candidate edge。
- text evidence。

### 3.3 derived_signal

来自以下源表：

```text
ft_market_flow
ft_market_cache
ft_sentiment
ft_macro_indicators
```

默认不调用 AI。

必填：

```text
target_ref
signal_type
observed_at
value
```

输出：

- signal/event node。
- `mentions` 或弱关联 edge。
- structured/rule evidence。

### 3.4 l1_events

`l1_events` 不是冷启动输入。

它只用于后续 L1 已经运行之后，把事件抽取结果回写 KG：

```text
L1 result
  -> l1_events source record
  -> Financial Adapter
  -> Compiler
  -> kg_*
```

所以在“KG 先于 L1”的真实落地阶段，不能依赖 `ft_events` 或 L1 事件表。

## 5. Adapter 集成方式

金融 Adapter 处理 `news_articles` 时：

```text
news_articles source record
  -> validate source contract
  -> deterministic extraction
     - source_id
     - title/text evidence
     - explicit symbols
     - source_name/institution
  -> optional TextExtractionPipeline
     - FinancialNewsExtractionStrategy
     - mentioned_entities
     - affected_entities
     - relation_candidates
  -> NodeDraft / EdgeDraft / EvidenceDraft
```

必须保证：

- AI 失败不能导致整条 source record 无法编译。
- AI 结果没有 evidence span 时不能生成 active edge。
- 只靠 AI 推断的 `affects/benefits_from/hurt_by/causal_hint` 默认不能 active。
- 结构化字段已经能确定的事实不交给 AI 重新判断。

## 6. AI 输出 Schema

第一版要求 LLM 输出 JSON：

```json
{
  "mentioned_entities": [
    {
      "entity_type": "stock",
      "canonical_name": "宁德时代",
      "identifiers": {"symbol": "300750.SZ"},
      "confidence": 0.92,
      "evidence_spans": [
        {"field": "text", "text": "宁德时代", "start": 12, "end": 16}
      ]
    }
  ],
  "affected_entities": [
    {
      "entity_type": "industry",
      "canonical_name": "锂电池",
      "direction": "positive",
      "confidence": 0.78,
      "evidence_spans": [
        {"field": "summary", "text": "需求回暖", "start": 20, "end": 24}
      ]
    }
  ],
  "relation_candidates": [
    {
      "relation_type": "affects",
      "source": "event:source",
      "target": "industry:锂电池",
      "confidence": 0.78,
      "status_hint": "candidate",
      "evidence_spans": [
        {"field": "summary", "text": "需求回暖", "start": 20, "end": 24}
      ]
    }
  ],
  "quality_flags": []
}
```

校验失败策略：

| 情况 | 处理 |
|---|---|
| JSON 非法 | 记录 warning，保留确定性输出 |
| entity_type 不在金融 ontology | 丢弃该实体并记录 warning |
| relation_type 不在金融 ontology | 丢弃该关系并记录 warning |
| evidence span 找不到原文 | 降级 candidate 或丢弃关系 |
| confidence 过低 | 只保留为 candidate/review_required |

## 7. 金融置信和状态规则

第一版规则：

| 来源 | relation | 默认 status |
|---|---|---|
| 标题/正文显式提及 | `mentions` | active 或 candidate |
| 业务字段显式 symbol | `mentions` | active |
| 文本明确影响 | `affects` | candidate |
| 文本明确利好 | `benefits_from` | candidate/review_required |
| 文本明确利空 | `hurt_by` | candidate/review_required |
| 因果暗示 | `causal_hint` | review_required |
| 纯 LLM 推断、无 span | 不入图 | 不入图 |

active 条件：

- relation type 允许 active。
- evidence span 可定位。
- confidence 达到该 relation 的阈值。
- 不属于策略规定必须复核的高风险关系。

## 8. 分阶段实施计划

### Phase A：补齐通用抽取模型

目标：

- 新增 `TextExtractionInput/Result` 等模型。
- 新增 `TextExtractionStrategy` 协议。
- 新增 pipeline 骨架。
- 不接真实 LLM。

验收：

- 通用层没有金融词。
- schema 校验、span 校验有单元测试。

### Phase B：金融确定性抽取

目标：

- `news_articles` 支持显式 symbol、标题、正文 evidence。
- `policy_news` 支持 policy node 和 mentions edge。
- `derived_signal` 保持规则抽取。

验收：

- 不配置 LLM 也能编译新闻和信号。
- fixture 能稳定输出 nodes/edges/evidence。

### Phase C：金融 AI 抽取策略

目标：

- 实现 `FinancialNewsExtractionStrategy`。
- 实现 prompt、JSON schema、结果校验。
- feature flag 默认关闭。

验收：

- AI 打开时可补充 mentioned/affected/relation_candidates。
- AI 失败时 compile 不失败。
- 所有 AI 关系都有 evidence span 或被降级/丢弃。

### Phase D：接入编译链路

目标：

- `KnowledgeService.compile_kg` 可接收带抽取配置的 Financial Adapter。
- CLI/API 可以通过参数控制是否启用 AI 抽取。
- Notebook 只调用服务，不保留正式 prompt。

验收：

- 可从 `ft_news` 投影真实 records 后编译到 `kg_*`。
- 可 rebuild wiki/index。
- 可查询新闻到实体的路径。

### Phase E：清理 Notebook 临时代码

目标：

- Notebook 中 AI enrichment 标记为 deprecated 或删除。
- Notebook 只保留业务投影、编译、重建、查询。

验收：

- Notebook 不是抽取规则事实源。
- Financial Adapter 是金融新闻抽取规则事实源。

## 10. 验收标准

完成后必须满足：

1. 业务方只负责把业务表投影成标准 source records。
2. 通用 Text Extraction Pipeline 不含金融业务概念。
3. Financial Adapter 提供金融新闻抽取策略。
4. `ft_news` 可以通过 `news_articles` 进入 KG。
5. `ft_market_flow / ft_market_cache / ft_sentiment / ft_macro_indicators` 可以通过 `derived_signal` 进入 KG。
6. 冷启动阶段不依赖 `ft_events` 或 L1 结果。
7. AI 抽取失败不阻断编译。
8. LLM 生成的边必须有 evidence span，否则不能 active。
9. `kg_*` 仍然是唯一事实源。
10. Notebook 不再是正式抽取规则的承载位置。

## 11. 当前实现迁移说明

当前已经可以做的事情：

- 业务表投影为 `news_articles / policy_news / derived_signal`。
- 经 Financial Adapter 编译到 `kg_*`。
- rebuild wiki/index。
- 做路径查询、上下文查询、质量扫描。

当前需要调整的事情：

- Notebook 中临时 AI enrichment 只能保留为验证工具。
- 正式 AI 抽取应迁移到 `FinancialNewsExtractionStrategy`。
- `ft_events` 不能作为 KG 冷启动输入，只能作为 L1 后续回写输入。

迁移完成后的冷启动链路：

```text
ft_news
ft_market_flow
ft_market_cache
ft_sentiment
ft_macro_indicators
  -> business source mapper
  -> Financial Adapter
  -> Knowledge Compiler
  -> kg_*
  -> Wiki / Index
  -> L1/L2/L3 消费 KG
```
