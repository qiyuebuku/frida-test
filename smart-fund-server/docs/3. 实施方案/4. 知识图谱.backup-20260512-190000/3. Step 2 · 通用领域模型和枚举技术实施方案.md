## 0. 一句话说清楚

Step 2 的目标是把通用知识基础设施的平台语言定死：

```text
input -> node draft -> edge draft -> evidence draft -> compiled objects -> compile result
```

这一步只定义领域模型、枚举、稳定 ID 规则和纯内存校验。  
不连接数据库，不建表，不实现 Compiler 流程，不接 Adapter，不接 LLM，不接 embedding。

## 3. 技术选择

### 3.1 使用 Pydantic

本项目已有 FastAPI 和 Pydantic 使用基础，Step 2 建议使用 Pydantic v2 风格定义领域模型。

原因：

- 字段校验明确。
- 测试失败信息清楚。
- 后续 API 入参、compile result、fixture golden output 可复用同一套模型。
- 比裸 dataclass 更适合处理 `dict[str, Any]`、时间、枚举和额外字段策略。

约束：

- domain 模型不能 import FastAPI。
- domain 模型不能 import SQLAlchemy。
- domain 模型不能 import repository。
- Pydantic 只用于数据校验，不承担持久化职责。

### 3.2 文件划分

```text
src/domain/knowledge/enums.py
src/domain/knowledge/schemas.py
src/domain/knowledge/ids.py
```

职责：

| 文件 | 职责 |
|---|---|
| `enums.py` | 通用输入类型、状态、置信度、证据类型 |
| `schemas.py` | 输入材料、节点、边、证据、编译结果等领域模型 |
| `ids.py` | 稳定 ID 生成和 hash 工具 |

## 4. 枚举定义

### 4.1 InputType

```text
structured_record
semi_structured_record
document_chunk
event_record
derived_signal
feedback_record
```

含义：

| 枚举 | 含义 |
|---|---|
| `structured_record` | 有明确字段和主键的结构化记录 |
| `semi_structured_record` | 有字段但语义仍需解释的记录 |
| `document_chunk` | 长文本切片 |
| `event_record` | 已识别出的事件记录 |
| `derived_signal` | 统计、算法或外部系统产生的信号 |
| `feedback_record` | 人工复核、用户反馈、历史验证、复盘结论 |

### 4.2 NodeStatus

```text
active
candidate
ambiguous
merged
deprecated
```

### 4.3 EdgeStatus

```text
active
candidate
review_required
conflict
deprecated
```

### 4.4 ConfidenceLabel

```text
EXTRACTED
INFERRED
AMBIGUOUS
HUMAN_VERIFIED
REJECTED
```

### 4.5 EvidenceType

```text
structured_field
text_span
rule_output
llm_output
human_review
historical_validation
```

### 4.6 ValidationSeverity

建议新增：

```text
info
warning
error
critical
```

用途：

- Step 2 可先定义，Step 10 质量治理会复用。

## 5. 领域模型定义

### 5.1 KnowledgeInput

用途：Adapter normalize 后交给平台的统一输入材料。

字段：

```text
input_type: InputType
source_type: str
source_id: str
observed_at: datetime
adapter_name: str
adapter_version: str
payload: dict[str, Any]
raw_text: str | None
metadata: dict[str, Any]
```

校验规则：

- `source_type` 不能为空。
- `source_id` 不能为空。
- `adapter_name` 不能为空。
- `adapter_version` 不能为空。
- `observed_at` 必须是 `datetime`。
- `payload` 默认为 `{}`。
- `metadata` 默认为 `{}`。
- `raw_text` 可以为空，但如果 `payload` 也为空，应校验失败。

### 5.2 NodeDraft

用途：编译前的候选节点。

字段：

```text
node_type: str
stable_key: str
canonical_name: str
aliases: list[str]
external_ids: dict[str, str]
properties: dict[str, Any]
status: NodeStatus
source_refs: list[str]
```

校验规则：

- `node_type` 不能为空。
- `stable_key` 不能为空。
- `canonical_name` 不能为空。
- `node_type` 不做枚举限制，由 Adapter 定义。
- `aliases` 默认 `[]`。
- `external_ids` 默认 `{}`。
- `properties` 默认 `{}`。
- `status` 默认 `candidate`。

### 5.3 EdgeDraft

用途：编译前的候选边。

字段：

```text
source_ref: str
target_ref: str
relation_type: str
properties: dict[str, Any]
confidence_label: ConfidenceLabel
confidence_score: float
status: EdgeStatus
evidence_refs: list[str]
valid_from: datetime | None
valid_to: datetime | None
```

校验规则：

- `source_ref` 不能为空。
- `target_ref` 不能为空。
- `relation_type` 不能为空。
- `confidence_score` 范围为 `0.0 <= score <= 1.0`。
- `relation_type` 不做枚举限制，由 Adapter 定义。
- `status` 默认 `candidate`。
- 如果 `confidence_label == REJECTED`，`status` 不能是 `active`。
- 如果 `status == active`，`evidence_refs` 不能为空。

### 5.4 EvidenceDraft

用途：编译前的候选证据。

字段：

```text
evidence_type: EvidenceType
source_type: str
source_id: str
content: str | None
payload: dict[str, Any]
span_start: int | None
span_end: int | None
metadata: dict[str, Any]
```

校验规则：

- `source_type` 不能为空。
- `source_id` 不能为空。
- `payload` 默认 `{}`。
- `metadata` 默认 `{}`。
- `content` 和 `payload` 不能同时为空。
- 如果设置 `span_start` / `span_end`，必须满足 `0 <= span_start <= span_end`。

### 5.5 CompiledNode

用途：已经拥有稳定 ID、可写入事实库的节点对象。

字段：

```text
node_id: str
adapter_name: str
node_type: str
canonical_name: str
aliases: list[str]
external_ids: dict[str, str]
properties: dict[str, Any]
status: NodeStatus
version: str
```

校验规则：

- `node_id` 必须以 `kg:` 开头。
- `adapter_name` 不能为空。
- `version` 不能为空。

### 5.6 CompiledEdge

用途：已经拥有稳定 ID、可写入事实库的边对象。

字段：

```text
edge_id: str
adapter_name: str
source_node_id: str
target_node_id: str
relation_type: str
properties: dict[str, Any]
confidence_label: ConfidenceLabel
confidence_score: float
status: EdgeStatus
evidence_ids: list[str]
valid_from: datetime | None
valid_to: datetime | None
version: str
```

校验规则：

- `edge_id` 必须以 `kg_edge:` 开头。
- `source_node_id` 和 `target_node_id` 必须以 `kg:` 开头。
- `confidence_score` 范围为 `0.0 <= score <= 1.0`。
- `active` 边必须有 `evidence_ids`。
- `REJECTED` 边不能是 `active`。

### 5.7 CompiledEvidence

用途：已经拥有稳定 ID、可写入事实库的证据对象。

字段：

```text
evidence_id: str
adapter_name: str
evidence_type: EvidenceType
source_type: str
source_id: str
content: str | None
payload: dict[str, Any]
span_start: int | None
span_end: int | None
version: str
metadata: dict[str, Any]
```

校验规则：

- `evidence_id` 必须以 `kg_ev:` 开头。
- `adapter_name` 不能为空。
- `version` 不能为空。
- `content` 和 `payload` 不能同时为空。

### 5.8 CompileResult

用途：Compiler 一次运行的内存结果。

字段：

```text
run_id: str
adapter_name: str
adapter_version: str
version: str
nodes: list[CompiledNode]
edges: list[CompiledEdge]
evidence: list[CompiledEvidence]
failed_records: list[FailedRecord]
warnings: list[ValidationIssue]
```

校验规则：

- `run_id` 不能为空。
- `adapter_name` 不能为空。
- `version` 不能为空。
- 列表字段默认 `[]`。

### 5.9 FailedRecord

用途：单条输入失败时的错误说明，避免整个批次失败。

字段：

```text
source_type: str
source_id: str
reason: str
details: dict[str, Any]
```

### 5.10 ValidationIssue

用途：编译、质量治理、Adapter 校验的统一问题对象。

字段：

```text
severity: ValidationSeverity
message: str
object_type: str | None
object_ref: str | None
details: dict[str, Any]
```

## 6. 稳定 ID 规则

### 6.1 hash 规则

在 `src/domain/knowledge/ids.py` 中实现通用 hash 工具：

```text
stable_hash(value: Any) -> str
```

规则：

- JSON 序列化时 `sort_keys=True`。
- 使用 UTF-8。
- 使用 SHA256。
- 默认取前 16 位十六进制，足够短且稳定。
- 输入为字符串、数字、列表、字典时都应得到稳定结果。

### 6.2 node_id

函数：

```text
make_node_id(adapter_name: str, node_type: str, stable_key: str) -> str
```

格式：

```text
kg:{adapter_name}:{node_type}:{stable_hash(stable_key)}
```

规则：

- `adapter_name`、`node_type`、`stable_key` 不能为空。
- 同一输入必须生成同一 ID。
- 不同 adapter 下不能冲突。
- 不同 node_type 下不能冲突。

### 6.3 edge_id

函数：

```text
make_edge_id(
  adapter_name: str,
  relation_type: str,
  source_node_id: str,
  target_node_id: str,
  evidence_ids: list[str],
) -> str
```

格式：

```text
kg_edge:{adapter_name}:{relation_type}:{stable_hash(payload)}
```

payload 至少包含：

```text
source_node_id
target_node_id
sorted evidence_ids
```

规则：

- evidence ID 顺序不影响 edge_id。
- source 和 target 顺序影响 edge_id。
- 不同 relation_type 不冲突。

### 6.4 evidence_id

函数：

```text
make_evidence_id(
  adapter_name: str,
  source_type: str,
  source_id: str,
  evidence_type: EvidenceType,
  content: str | None,
  payload: dict[str, Any],
) -> str
```

格式：

```text
kg_ev:{adapter_name}:{source_type}:{source_id}:{stable_hash(payload)}
```

规则：

- 同一来源、同一内容生成同一 evidence_id。
- `content` 和 `payload` 都参与 hash。
- `evidence_type` 参与 hash。

## 7. 非目标和边界

### 7.1 不做 ontology 校验

Step 2 不校验某个 `node_type` 或 `relation_type` 是否被 Adapter 声明。

原因：

- Adapter 协议在 Step 3。
- Step 2 只保证平台对象本身合法。

### 7.2 不做数据库映射

Step 2 不定义 SQLAlchemy model，也不写 repository。

原因：

- 事实库在 Step 4。
- 领域模型不能被数据库字段反向污染。

### 7.3 不做业务消费限制

Step 2 只定义置信度标签，不决定哪些标签能被业务使用。

原因：

- 业务消费策略由 Adapter 定义。

## 8. 测试方案

### 8.1 测试文件

新增：

```text
tests/unit/knowledge/test_models.py

```

本步骤不需要集成测试。原因：

- 不连接数据库。
- 不启动 API。

- 不需要 fixture 文件。

### 8.2 test_models.py

测试项：

1. `KnowledgeInput` 缺少 `source_type` 时校验失败。
2. `KnowledgeInput` 缺少 `source_id` 时校验失败。
3. `KnowledgeInput` 缺少 `adapter_name` 时校验失败。
4. `KnowledgeInput` 的 `raw_text` 和 `payload` 同时为空时校验失败。
5. `NodeDraft` 允许任意 `node_type`。
6. `NodeDraft` 不允许空 `canonical_name`。
7. `EdgeDraft` 不允许空 `source_ref`。
8. `EdgeDraft` 不允许空 `target_ref`。
9. `EdgeDraft` 不允许空 `relation_type`。
10. `EdgeDraft.confidence_score` 小于 0 或大于 1 时校验失败。
11. `ConfidenceLabel.REJECTED` 的边不能是 `active`。
12. `EdgeStatus.active` 的边必须有 `evidence_refs`。
13. `EvidenceDraft` 的 `content` 和 `payload` 同时为空时校验失败。
14. `EvidenceDraft.span_start > span_end` 时校验失败。
15. `CompiledNode.node_id` 必须以 `kg:` 开头。
16. `CompiledEdge.edge_id` 必须以 `kg_edge:` 开头。
17. `CompiledEvidence.evidence_id` 必须以 `kg_ev:` 开头。

### 8.3 test_ids.py

测试项：

1. `stable_hash({"b": 2, "a": 1})` 和 `stable_hash({"a": 1, "b": 2})` 一致。
2. `make_node_id` 对同一输入稳定一致。
3. `make_node_id` 不同 adapter 不冲突。
4. `make_node_id` 不同 node_type 不冲突。
5. `make_edge_id` 中 `evidence_ids` 顺序不影响结果。
6. `make_edge_id` 中 source 和 target 对调后结果不同。
7. `make_evidence_id` 对同一来源和内容稳定一致。
8. 任意 ID 生成函数传入空关键字段时校验失败。

## 11. 失败判定

出现任一情况，Step 2 视为失败：

| 失败情况 | 原因 |
|---|---|
| `node_type` 被写成平台枚举 | 平台层开始绑定具体领域 |
| `relation_type` 被写成平台枚举 | Adapter 边界被破坏 |
| `schemas.py` import SQLAlchemy | 领域层被持久化污染 |
| `schemas.py` 出现领域专用字段 | 通用层被 Adapter 污染 |
| active 边可以没有 evidence | 证据协议失效 |
| rejected 边可以 active | 置信度和状态协议冲突 |
| ID 生成不稳定 | upsert 和版本治理无法可靠实现 |
| 测试需要数据库才能跑 | Step 2 边界越界 |
