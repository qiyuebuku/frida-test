# 数据源投影与 Source Record 技术方案

## 1. 模块目标

本模块负责把业务表 Raw Row 投影为知识图谱统一输入 Source Record。

第一版目标是先跑通完整链路：

```text
业务表 Raw Row
  -> Source Record
  -> Knowledge Compiler
  -> kg_evidence / kg_nodes / kg_edges
  -> Wiki / Index
  -> Retrieval
```

核心要求：

1. 知识编译器不直接读取业务表。
2. `ft_news` 已有投影能力必须保留，并升级 source type 判断能力。
3. 补齐 `ft_market_flow`、`ft_market_cache`、`ft_sentiment`、`ft_macro_indicators` 到 `derived_signal` Source Record 的投影。
4. 每条 Source Record 必须能追溯到原始表和主键。
5. 投影层不调用 LLM，不创建主图实体和关系。
6. 第一版暂不处理历史矫正，只记录分类原因和疑似误分信息，后续治理阶段再做矫正系统。

## 2. 模块边界

本模块覆盖：

- 从业务表读取最近数据。
- 将业务表行转换为 Source Record。
- 生成 `source_type`、`source_id`、`observed_at`、`payload`、`raw_text`、`metadata`。
- 维护 `ft_news` 的 `news_articles` / `policy_news` 分类规则。
- 维护结构化表到 `derived_signal` 的确定性投影。
- 将分类原因、命中规则和不确定标记写入 metadata。

本模块不覆盖：

- 实体抽取。
- 关系抽取。
- 实体标准化和去重。
- 证据写入。
- Wiki、索引和检索。
- 历史数据矫正和旧 evidence / edge 废弃。

## 3. 当前现状

### 3.1 已有能力

`ft_news` 已有第一版投影实现：

```text
src/application/services/financial_news_projection.py
```

当前能力：

- 读取 `ft_news`。
- 结合 `category`、`source/source_name`、标题和正文关键词判断 `policy_news` 或 `news_articles`。
- 生成 `source_id = ft_news:{id}`。
- 使用 `published_at` 或 `created_at` 作为 observed time。
- 将 `related_stocks` 等强结构化标识转为 `mentioned_entities`。
- 将 `tags` 保存在 metadata，并生成 `weak_entity_hints`，不在投影层转成主图实体。
- 输出 `source_type_reason`、`source_type_matched_rules`、`source_type_confidence`、`source_type_uncertain` 等分类诊断信息。
- 输出 Financial Adapter 可消费的 Source Record。

当前不足：

- 来源和标题模式规则池仍需要基于真实库统计持续补充。
- `tags` 只是弱提示，后续是否升级为实体由知识编译、实体治理和证据校验决定。
- Source Record metadata 的治理和历史矫正能力还未完整建设。

### 3.2 旧方案已定义但未统一落地

备份实施文档 `Step 8 · Financial KG Adapter第一版技术实施方案.md` 已经定义过三类输入：

- `news_articles`
- `policy_news`
- `derived_signal`

其中 `derived_signal` 的业务来源包括：

- `ft_market_flow`
- `ft_market_cache`
- `ft_sentiment`
- `ft_macro_indicators`

本方案不是重新设计 Source Mapping，而是把旧方案中的 mapping 独立成正式投影模块。

## 4. 架构对齐与目标模块划分

本模块必须遵循项目的简化 DDD 分层架构：

```text
interfaces -> application -> domain -> infrastructure
```

落地原则：

1. `interfaces` 只提供 HTTP / CLI / task 入口，不直接读业务表，不直接调用投影函数细节。
2. `application` 负责编排用例：选择数据来源、通过 repository 协议读取 Raw Row、调用领域投影器、返回 Source Record。
3. `domain` 保存纯业务规则：source type 分类、金融 Source Record contract、Raw Row 到 Source Record 的纯转换规则。
4. `infrastructure` 负责 SQLAlchemy model、repository、数据库 session 和受控 SQL。
5. `domain` 不读取数据库、不读取环境变量、不依赖 SQLAlchemy session。
6. Knowledge Compiler 只消费 Source Record，不直接读取 `ft_news` / `ft_market_flow` 等业务表。

### 4.1 目标模块

| 模块 | 职责 |
| --- | --- |
| `src/interfaces/api/routes/knowledge.py` | API 薄入口，只调用应用层 DTO / service。 |
| `src/interfaces/cli/knowledge.py` | CLI 薄入口，只调用应用层 DTO / service。 |
| `src/application/dto/knowledge_dto.py` | 增加投影相关 command/result DTO。 |
| `src/application/services/knowledge_source_projection_service.py` | 应用层统一投影用例，聚合多张业务表 Source Record。 |
| `src/application/services/knowledge_service.py` | 在 compile/bootstrap 场景中编排投影服务和编译服务，不直接写投影规则。 |
| `src/domain/knowledge/repositories/knowledge_source_projection_repository.py` | 定义读取 Raw Row 的 repository 协议，不包含 SQLAlchemy 实现。 |
| `src/domain/knowledge_adapters/financial/source_classification.py` | 纯规则：`news_articles` / `policy_news` 确定性分类。 |
| `src/domain/knowledge_adapters/financial/source_projection.py` | 纯转换：业务 Row dict 到金融 Source Record dict。 |
| `src/domain/knowledge_adapters/financial/sources.py` | 保留金融 source contract 和 required fields。 |

| `src/domain/knowledge_adapters/financial/adapter.py` | 生成 EvidenceDraft 时透传 Source Record metadata。 |

### 4.2 依赖方向

允许：

```text
interfaces -> application service
application service -> domain repository protocol
application service -> domain projector/classifier
domain financial projector -> domain source contract
domain financial adapter -> domain knowledge schemas
infrastructure repository impl -> domain repository protocol
infrastructure repository impl -> SQLAlchemy / DB session
```

禁止：

```text
interfaces -> repository / DB session
domain -> infrastructure repository
domain -> SQLAlchemy / get_session / env
compiler -> ft_news / ft_market_flow / business table
projection repository -> knowledge compiler
```

装配规则：

- 生产环境由 `create_knowledge_service()` 或同级工厂把 infrastructure repository implementation 注入 `KnowledgeSourceProjectionService`。
- 单元测试可以注入内存 repository / fake repository，避免为了测试投影规则依赖真实数据库。
- 后续如果接入消息队列、文件回放、外部数据湖，只新增 repository implementation，不修改领域投影器和 Knowledge Compiler。

### 4.3 与现有代码的兼容策略

当前已有：

```text
src/application/services/financial_news_projection.py
```

第一版编码可以保留该文件作为兼容入口，但内部应逐步改为：

```text
financial_news_projection.py
  -> KnowledgeSourceProjectionService / domain source_projection
```

不要继续在该文件中累积分类规则、数据库读取和多表聚合逻辑。新能力按上述分层落到目标模块中。

数据库读取原则：

- 优先使用 SQLAlchemy ORM。
- JSONB 结构动态、ORM 不适合表达时，可以使用受控 SQL。
- 如果使用受控 SQL，需要在代码注释或实施偏差中说明原因。

## 5. Source Record 协议

统一输出结构：

```text
{
  "source_type": string,
  "source_id": string,
  "observed_at": datetime string,
  "payload": dict,
  "raw_text": string | null,
  "metadata": dict
}
```

metadata 必须包含：

```text
source_table
source_pk
```

`ft_news` 额外 metadata：

```text
source
source_name
source_reliability
category
url
tags
related_stocks
fingerprint
source_type_reason
source_type_matched_rules
source_type_confidence
source_type_uncertain
source_type_candidates
```

结构化表额外 metadata：

```text
data_type
signal_source_type
trade_date / created_at / expires_at / period
```

## 6. ft_news 投影

### 6.1 数据流

```text
ft_news row
  -> classify_news_source_type(row)
  -> build raw_text
  -> build strong mentioned_entities from related_stocks
  -> preserve tags as metadata.weak_entity_hints
  -> build Source Record
```

### 6.2 source_id

```text
ft_news:{id}
```

要求同一条 `ft_news.id` 重复投影时 `source_id` 不变。

### 6.3 raw_text

按以下顺序拼接：

```text
title
summary
content
```

如果 `content` 为空，至少保留 `title`。

### 6.4 source_type 分类函数

分类逻辑必须封装为独立函数：

```text
classify_news_source_type(row) -> {
  source_type: news_articles | policy_news,
  reason: string,
  matched_rules: list[string],
  confidence: float,
  uncertain: bool,
  candidates: list[dict]
}
```

分类优先级：

1. `category` 强信号。
2. 官方、监管、交易所、统计机构等来源。
3. 标题和正文中的制度文件、政策动作、宏观监管口径。
4. 普通新闻负向信号。
5. 不确定时默认 `news_articles`，并记录 `uncertain_default_news`。

## 7. 结构化表到 derived_signal 投影

### 7.1 通用要求

四张结构化表统一输出：

```text
source_type = derived_signal
```

payload 必须至少包含：

```text
target_ref
signal_type
observed_at
value
```

允许附加：

```text
unit
window
data
prev_value
yoy
mom
dim_tag
```

如果无法从原始数据确定 `target_ref` 或 `value`，第一版不强行推理，跳过该行并记录 skipped reason。

### 7.2 ft_market_flow

输入：

```text
id
data_type
trade_date
data
created_at
```

投影：

```text
source_id = ft_market_flow:{id}
source_type = derived_signal
observed_at = trade_date
metadata.signal_source_type = market_flow.{data_type}
payload.data = data
```

第一版可支持：

- `northbound`
- `sector_flow`
- `stock_flow`
- `dragon_tiger`

### 7.3 ft_market_cache

输入：

```text
id
data_type
data
expires_at
created_at
```

投影：

```text
source_id = ft_market_cache:{data_type}:{id}
source_type = derived_signal
observed_at = created_at
metadata.signal_source_type = market_snapshot.{data_type}
metadata.expires_at = expires_at
payload.data = data
```

注意：

- `ft_market_cache` 是覆盖式快照，不是历史流水。
- 第一版只保证当前快照可入图，不承诺完整历史回放。

### 7.4 ft_sentiment

输入：

```text
id
data_type
trade_date
data
created_at
```

投影：

```text
source_id = ft_sentiment:{id}
source_type = derived_signal
observed_at = trade_date
metadata.signal_source_type = sentiment.{data_type}
payload.data = data
```

第一版不做 AI 情绪总结，只保留结构化信号。

### 7.5 ft_macro_indicators

输入：

```text
id
indicator
period
value
unit
prev_value
source
published_at
dim_tag
yoy
mom
created_at
```

投影：

```text
source_id = ft_macro_indicators:{indicator}:{period}:{source}
source_type = derived_signal
observed_at = published_at 或 created_at
metadata.signal_source_type = macro_indicator
payload.target_ref = macro_indicator:{indicator}
payload.signal_type = macro_indicator.{indicator}
payload.value = value
```

第一版不判断宏观 regime，只生成可编译的宏观指标信号。

## 8. 统一投影入口

统一投影入口属于应用层，不属于领域层，也不属于接口层。

建议新增 DTO：

```text
KnowledgeSourceProjectionCommand
  target: "prod" | "test"
  sources: list[str] | None
  limit: int
  include_skipped: bool

KnowledgeSourceProjectionResultDTO
  records: list[dict]
  total_records: int
  source_counts: dict[str, int]
  skipped: list[dict]
  warnings: list[str]
```

应用层服务方法：

```text
KnowledgeSourceProjectionService.project(command) -> KnowledgeSourceProjectionResultDTO
```

建议支持 sources：

```text
ft_news
ft_market_flow
ft_market_cache
ft_sentiment
ft_macro_indicators
```

职责：

1. 校验 command。
2. 调用 repository 协议读取 Raw Row，生产环境使用 infrastructure repository implementation。
3. 调用 domain financial projector/classifier 生成 Source Record。
4. 聚合 Source Record。
5. 汇总 skipped / warnings / source_counts。
6. 返回 DTO。
7. 不调用 compile，不写 KG。

接口层使用方式：

```text
HTTP / CLI
  -> KnowledgeSourceProjectionCommand
  -> KnowledgeSourceProjectionService.project()
  -> KnowledgeSourceProjectionResultDTO
```

compile 链路使用方式：

```text
KnowledgeService
  -> KnowledgeSourceProjectionService.project()
  -> KnowledgeCompileCommand(records=result.records)
  -> KnowledgeCompiler
```

这样可以保证：

- API / CLI 不绕过应用层。
- Knowledge Compiler 不读取业务表。
- 投影能力可以被 HTTP、CLI、定时任务、真实库回放脚本复用。
- 未来新增数据源时只扩展 repository 和 domain projector，不改 Compiler。

### 8.1 扩展点

未来新增来源时，只需要增加：

1. 通过 repository 协议读取该来源 Raw Row，生产环境由 infrastructure implementation 访问数据库。
2. domain projector 将 Raw Row 转为 Source Record。
3. application service 注册 sources 名称。
4. 单元测试和真实库 smoke test。

不允许新增来源时修改 Compiler 或接口层直接读表。

## 9. 错误处理与降级策略

1. 表不存在时返回空列表并记录 warning。
2. 单行缺少主键或时间时跳过，并记录 skipped reason。
3. JSONB payload 结构未知时保留原始 `data`，不在投影层强行解析。
4. 无法确定 `target_ref` / `value` 的结构化信号跳过，不交给 LLM 猜。
5. `ft_news` 分类不确定时默认 `news_articles`，写入 `source_type_uncertain = true`。
6. 第一版不做历史矫正；测试数据污染时允许清空测试 KG 后重跑。
7. 如果临时只完成部分来源，必须记录到 `9. 待优化.md`。

## 11. 验收标准

第一版完成必须满足：

1. 五张核心业务表都有投影策略。
2. `ft_news` 不再只依赖 `category` 判断 `source_type`。
3. 空 `category` 的新闻也能获得可解释的 `source_type_reason`。
4. `ft_news` 投影结果能被 Financial Adapter normalize。
5. 四张结构化表输出 `derived_signal`，且满足 `target_ref`、`signal_type`、`observed_at`、`value` 必填字段。
6. 投影层不调用 LLM。
7. 编译器不直接读取业务表。
8. `kg_evidence.metadata` 能看到投影分类原因。
9. 真实库前 100 条 smoke test 通过。
10. KG real replay 能从投影结果进入 compile 链路。
11. `interfaces` 不直接访问 repository、DB session 或 Compiler。
12. `domain` 投影和分类模块不依赖 infrastructure。
13. repository 只读 Raw Row，不生成 Source Record。
14. 新增来源时不需要修改 Knowledge Compiler。

## 12. 已知偏差与待优化

当前必须记录到 `9. 待优化.md` 的事项：

1. 结构化信号投影第一轮真实库覆盖已补齐；后续新增 `data_type` 或 coverage 出现 skipped 时，记录并补 mapping。
2. Source Record metadata 尚未透传到 `kg_evidence.metadata` 时，记录为 P1。
3. source type 历史矫正链路第一版暂缓实现，记录为 P3。

第一版不因为 source type 历史矫正缺失而阻塞主链路验证；结构化信号投影必须持续看 coverage，不能在新增数据类型后静默跳过。
