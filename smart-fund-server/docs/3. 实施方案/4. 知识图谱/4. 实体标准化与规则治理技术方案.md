# 实体标准化与规则治理技术方案

## 1. 模块目标

本模块负责实体标准化、去重、规则治理和审计。

核心目标：

1. 系统不允许空规则启动。
2. 写入主图前完成实体标准化判断。
3. LLM 可以生成规则候选，但不能绕过校验直接改主图。
4. 合并、软合并、阻断合并都可追踪。

## 2. 模块边界

本模块覆盖：

- 基础规则初始化。
- 写入前标准化决策。
- 规则候选生成。
- 规则落库。
- 合并审计和质量问题记录。
- 规则扫描和迁移建议。

本模块不覆盖：

- 原始文本抽取。
- 领域实体类型定义。
- 检索排序和上下文拼装。

## 4. 数据流

### 4.1 规则初始化

1. 系统启动或首次使用 KG 服务时检查规则表。
2. 如果规则为空，加载基础规则种子。
3. 基础规则写入数据库。
4. 后续标准化只读取数据库规则，不依赖临时 JSON fallback。

### 4.2 写入前标准化

1. Adapter 产生候选实体。
2. 标准化模块读取已有规则和已有实体。
3. 对候选实体进行强匹配、别名匹配、上下文匹配和类型检查。
4. 可确定时复用标准实体。
5. 不可确定时创建新实体或生成规则候选。
6. 冲突时阻断强合并，记录质量问题。

### 4.3 LLM 规则候选

LLM 参与这些场景：

- 近义词判断。
- 主题和行业边界判断。
- 同名不同类型歧义判断。
- 新规则候选说明。

LLM 输出必须结构化，经过规则冲突检查后才能落库。

### 4.4 规则扫描和迁移

定期扫描用于发现：

- 同名不同类型。
- 近义名称簇。
- 泛化 policy 或 concept。
- 重复主题。
- 事件主线重复。

扫描可以用统计、规则和 LLM 混合完成。发现问题后生成新规则候选和迁移建议，不能静默修改历史事实。

## 5. 错误处理与降级策略

1. 规则表为空时必须自动初始化，不能继续无规则写入。
2. 规则冲突时阻断强合并。
3. LLM 不可用时，只能执行确定性规则，无法判断的实体创建低置信候选并记录质量问题。
4. 规则迁移失败时，保留原事实并记录待迁移项。
5. 临时硬编码规则必须记录到 `9. 待优化.md`。

## 7. 验收标准

1. 新库首次运行自动写入基础规则。
2. 新实体写入前经过标准化决策。
3. 已知别名能命中同一标准实体。
4. 同名不同类型不会静默强合并。
5. LLM 规则候选必须先落为结构化候选，再经过校验。
6. 合并、阻断、迁移建议都有审计记录。

## 8. 已知偏差与待优化

当前模块如出现以下情况，必须补充到 `9. 待优化.md`：

- 使用代码硬编码规则代替数据库规则。
- 允许无规则启动。
- LLM 结果直接影响主图。
- 只在检索侧去重，不治理写入侧。
- 历史数据迁移只能手动脚本处理。
