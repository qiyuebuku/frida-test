# LLM Proxy统一模型网关技术实施方案

> 对应设计文档：`../../5. 设计方案/1. 知识图谱/6. LLM Proxy统一模型网关设计方案.md`
>
> 本方案目标是把当前以 Claude CLI tmux 为中心的 `llm_proxy` 改造成通用模型网关。调用方只传 `model` 和 OpenAI-compatible 请求参数；LLM Proxy 根据配置把模型请求转发到对应 Provider。

---

## 0. 一句话说清楚

本次实施不是重写业务抽取逻辑，也不是把知识图谱模型方案写进 LLM Proxy。

本次只做：

```text
OpenAI-compatible HTTP API
  -> LLMGatewayService
  -> ModelRouter
  -> ProviderRegistry
  -> ClaudeTmuxProvider / DeepSeekOpenAIProvider
  -> OpenAI-compatible response
```

业务使用方只关心最终模型名：

```json
{"model": "glm-5.1", "messages": [...]}
```

LLM Proxy 负责把 `glm-5.1` 路由到 `claude_tmux` 或未来 `glm_http`；把 `deepseek-v4-flash` 路由到 `deepseek`。

---

## 1. 实施目标

### 1.1 必须完成

| 能力 | 验收标准 |
|---|---|
| 统一类型 | 新增 `LLMProxyRequest/Response/Error`，旧 `ClaudeProxyRequest/Response` 兼容 |
| 模型路由 | `model -> provider`、alias、候选 Provider 优先级可配置 |
| Provider Registry | 可注册和获取 `claude_tmux`、`deepseek` Provider |
| Claude tmux 包装 | 现有 tmux pool 行为不破坏，`glm-5.1` 可路由到它 |
| DeepSeek Provider | `deepseek-v4-flash/pro` 可通过 HTTP API 调用 |
| API 保持兼容 | `/v1/chat/completions` 请求/响应结构保持 OpenAI-compatible |
| Health 升级 | `/api/llm-proxy/health` 能返回 provider registry 和 model routes |
| 测试用例 | 路由、Provider、API、脱敏、错误映射都有测试 |

### 1.2 暂不做

- 不实现知识图谱的 `KG_LLM_PLAN`。
- 不实现事件抽取的模型方案。
- 不实现 OpenAI / GLM HTTP / local vLLM Provider。
- 不实现 DeepSeek FIM。
- 不实现 DeepSeek Anthropic-compatible 主链路。
- 不让 LLM Proxy 根据 `task_type` 或业务复杂度选择模型。
- 不把 DeepSeek API key 写进文档、代码或测试 fixture。

## 4. Step 1 · 通用类型和兼容层

### 4.2 关键字段

| 字段 | 说明 |
|---|---|
| `text` | assistant 文本 |

| `usage` | 归一化 usage |
| `session_id` | tmux/Claude 会话 ID，HTTP Provider 可为空 |
| `duration_ms` | 总耗时 |
| `raw_payload` | 脱敏后的 Provider 摘要 |
| `cache_hit` | 是否命中缓存 |

## 5. Step 2 · ModelRouter

### 5.1 目标

实现纯路由器，只做：

```text
requested model
  -> alias normalization
  -> resolved model
  -> provider candidates
  -> route decision
```

不做：

- 不根据业务场景选择模型。
- 不根据 `task_type` 选择模型。
- 不把 `glm-5.1` 换成 `deepseek-v4-pro`。

### 5.2 配置

新增 settings：

```env
LLM_PROXY_DEFAULT_PROVIDER=claude_tmux
LLM_PROXY_DEFAULT_MODEL=glm-5.1
LLM_PROXY_MODEL_ROUTES_JSON={"glm-5.1":["claude_tmux","glm_http"],"deepseek-v4-flash":["deepseek"],"deepseek-v4-pro":["deepseek"]}
LLM_PROXY_MODEL_ALIASES_JSON={"glm5.1":"glm-5.1","GLM-5.1":"glm-5.1","deepseek-flash":"deepseek-v4-flash","deepseek-pro":"deepseek-v4-pro"}
```

### 5.3 RouteDecision

建议结构：

```text
LLMRouteDecision
  requested_model
  resolved_model
  provider_candidates
  selected_provider
  route_reason
  fallback_allowed
```

### 5.4 路由规则

| 输入 | 输出 |
|---|---|
| `deepseek-v4-flash` | resolved=`deepseek-v4-flash`，providers=`["deepseek"]` |
| `deepseek-flash` | resolved=`deepseek-v4-flash`，providers=`["deepseek"]` |
| `glm5.1` | resolved=`glm-5.1`，providers=`["claude_tmux","glm_http"]` |
| 空 model | resolved=`LLM_PROXY_DEFAULT_MODEL` |
| 未知 model | 如果无默认策略，报 `bad_request` |

### 5.5 测试用例

新增：

```text
tests/unit/llm_proxy/test_model_router.py
```

用例：

| 用例 | 验证 |
|---|---|
| `test_exact_model_route_deepseek_flash` | `deepseek-v4-flash -> deepseek` |
| `test_exact_model_route_deepseek_pro` | `deepseek-v4-pro -> deepseek` |
| `test_alias_route_glm51` | `glm5.1 -> glm-5.1 -> claude_tmux` |
| `test_model_route_provider_priority` | `glm-5.1` 候选 Provider 顺序保持 |
| `test_empty_model_uses_default_model` | 空模型使用默认模型 |
| `test_unknown_model_rejected_when_no_route` | 未知模型不静默乱路由 |
| `test_fallback_does_not_change_resolved_model` | fallback 只换 Provider，不换模型 |

### 8.3 请求转换

DeepSeek request：

```json
{
  "model": "deepseek-v4-flash",
  "messages": [
    {"role": "system", "content": "..."},
    {"role": "user", "content": "..."}
  ],
  "temperature": 0,
  "max_tokens": 2000,
  "stream": false,
  "response_format": {"type": "json_object"}
}
```

如果上游模型支持 `thinking` / `reasoning_effort`，只在 DeepSeek Provider 内处理，不暴露成业务路由逻辑。

### 8.4 错误映射

|---|---|---|

| 401 | `auth_error` | 否 |
| 402 | `quota_error` | 否 |
| 422 | `bad_request` | 否 |
| 429 | `rate_limited` | 否，进入 cooldown |
| 500 | `upstream_unavailable` | 最多 1 次 |
| 503 | `upstream_unavailable` | 最多 1 次 |
| timeout | `timeout` | 最多 1 次 |

## 9. Step 6 · Gateway Service 改造

### 9.1 目标

`service.py` 从 Claude 专用服务变成统一 Gateway：

```text
LLMGatewayService.generate(request)
  -> ModelRouter.resolve(request.model)
  -> ProviderRegistry.get(route.selected_provider)
  -> provider.generate(request, route)
  -> cache set/get
```

### 9.2 兼容导出

`__init__.py` 应同时导出：

```text
LLMProxyRequest
LLMProxyResponse
LLMProxyError
get_llm_gateway_service

ClaudeProxyRequest     # alias
ClaudeProxyResponse    # alias
get_claude_proxy_service  # alias
```

### 9.3 缓存 key

缓存 key 应包含：

| 字段 | 原因 |
|---|---|
| `resolved_model` | alias 后模型一致才能复用 |
| `provider` | 同模型不同 Provider 输出可能不同 |
| `messages/prompt` | 输入 |
| `temperature` | 输出随机性 |
| `max_tokens` | 截断影响输出 |
| `response_format/json_schema` | 输出格式 |
