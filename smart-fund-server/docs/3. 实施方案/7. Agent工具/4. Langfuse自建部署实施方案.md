# Langfuse 自建部署实施方案

## 1. 目标

在 Smart Fund 生产机上运行独立的 Langfuse v4（可观测平台），替代因云端套餐额度暂停的
Trace（追踪）写入目标。应用继续使用 Langfuse Python SDK（软件开发工具包）和 OTLP
（开放遥测协议），不实现第二套追踪链路。

官方将 Docker Compose（容器编排）定位为单机、低规模部署方案；当前生产机满足官方建议的
CPU、内存和磁盘要求。服务采用官方 v4 Web、Worker、PostgreSQL、Redis、ClickHouse 和
MinIO 组件。

参考：

- [Langfuse Docker Compose 部署](https://langfuse.com/self-hosting/deployment/docker-compose)
- [Langfuse v4](https://langfuse.com/docs/v4)
- [健康与就绪接口](https://langfuse.com/self-hosting/configuration/health-readiness-endpoints)
- [原生 OpenTelemetry 接入](https://langfuse.com/integrations/native/opentelemetry)

## 2. 部署边界

Compose Project（容器编排项目）名称为 `smart-fund-langfuse`。数据库、缓存、分析库和对象
存储只在独立 Docker 网络中通信，不映射到宿主机。以下端口用于外部访问：

| 端口 | 服务 | 用途 |
| --- | --- | --- |
| `0.0.0.0:3001` | Langfuse Web | UI、公共 API 和 OTLP 写入 |
| `127.0.0.1:3031` | Langfuse Worker | Worker 健康检查 |
| `0.0.0.0:9092` | MinIO | Trace 多媒体对象与预签名地址 |

Smart Fund 通过 `http://127.0.0.1:3001` 写入；FRP（快速反向代理）将公网服务器的 3001、
9092 TCP 端口映射到 Langfuse 主机，操作人员通过 `http://119.23.227.187:3001` 访问 UI。
阿里云安全组需要开放 TCP 3001 和 9092，3031 以及
内部数据库端口不得开放。当前公网入口为 HTTP（超文本传输协议），后续应通过域名和 HTTPS
（安全超文本传输协议）终止明文登录传输。

SSH 端口转发仍可作为不经过公网端口的维护方式：

```bash
ssh -p 1113 \
  -L 3001:127.0.0.1:3001 \
  -L 9092:127.0.0.1:9092 \
  yuyangruan@119.23.227.187
```

通过转发时浏览器打开 `http://127.0.0.1:3001`。管理员初始账号保存在远端权限为 `0600` 的
`/home/yuyangruan/smart-fund/config/langfuse.env`，通过
`./deployment/deploy_113.sh --langfuse-credentials` 查询，不在代码仓库保存明文密钥。

## 3. 初始化和配置

`./deployment/deploy_113.sh --langfuse` 执行以下幂等流程：

1. 只同步 `deployment/langfuse` 和 Langfuse 健康检查相关源码，不同步其他未提交代码。
2. 首次运行生成数据库、缓存、对象存储、会话、加密、项目和管理员密钥；后续运行保留原值。
3. 展开并校验 Compose 配置，创建具名持久化卷，启动六个服务。
4. 等待 Web 数据库健康检查和 Worker 健康检查通过。
5. 将生产 `LANGFUSE_BASE_URL`、`LANGFUSE_HOST` 和项目密钥切换到本机实例。
6. 重启读取生产 EnvironmentFile（环境文件）的 Smart Fund 服务。
7. 依次验证配置、认证和真实 OTLP 写入。

初始化项目名为 `Smart Fund Production`，默认数据保留期为 90 天。可在首次部署前通过
`.deployment.local.env` 的 `LANGFUSE_RETENTION_DAYS` 和 `LANGFUSE_ADMIN_EMAIL` 调整。

日常命令：

```bash
./deployment/deploy_113.sh --langfuse-status
./deployment/deploy_113.sh --langfuse-test
./deployment/deploy_113.sh --langfuse-logs web 100
./deployment/deploy_113.sh --langfuse-logs worker 100
./deployment/deploy_113.sh --langfuse-upgrade
```

普通 `--langfuse` 只拉取缺失镜像，避免仓库临时不可用影响幂等恢复；显式
`--langfuse-upgrade` 才拉取 v4 最新镜像并重建服务。

### 3.1 本地 Agent（智能体）接入

本地 Conda 环境通过公网地址连接自建实例，生产服务器则通过回环地址连接同一实例：

| 运行位置 | `LANGFUSE_BASE_URL` / `LANGFUSE_HOST` |
| --- | --- |
| 本地 WSL | `http://119.23.227.187:3001` |
| 生产服务器 | `http://127.0.0.1:3001` |

两处必须使用同一 Langfuse Project（项目）的 Public Key（公钥）和 Secret Key（密钥）。
密钥只写入本地 `.env` 或远端权限为 `0600` 的 EnvironmentFile（环境文件），不得写入示例配置、
脚本参数或文档。

### 3.2 Trace（链路）回读与导出

自建 Langfuse v4 使用 Observations API v2（观测记录接口），旧版
`/api/public/traces` 不再作为导出依赖。`scripts/fetch_langfuse_traces.py` 先读取
`/api/public/v2/observations`，再按 `traceId` 在本地重建 Trace（链路）：

```bash
# 下载一条已知 Trace
python scripts/fetch_langfuse_traces.py --trace-id TRACE_ID

# 查找指定名称的最新 Trace，并下载同一 Session（会话）
python scripts/fetch_langfuse_traces.py --name research-agent

# 下载指定 Session；默认只扫描最近 7 天，也可以显式扩大时间窗
python scripts/fetch_langfuse_traces.py \
  --session-id SESSION_ID \
  --from-timestamp 2026-08-01T00:00:00+00:00
```

按名称、标签或 Session 查询时，脚本强制使用有界时间窗，避免全表扫描 ClickHouse（分析库）。
按 `traceId` 查询走服务端精确过滤，不需要时间窗。导出文件包含 Input（输入）、Output（输出）、
Metadata（元数据）、Model（模型）、Usage（用量）和完整 Observation（观测记录）列表。

## 4. 健康状态契约

`python -m src.interfaces.cli agent check` 对 Langfuse 返回结构化状态：

- `configured`：开关、地址和两条项目密钥完整。
- `authenticated`：带 Basic Auth（基础认证）访问项目 API 返回 HTTP 200。
- `writable`：向 `/api/public/otel/v1/traces` 写入最小 OTLP JSON Span（跨度）返回 2xx。
- `status`：`disabled`、`unconfigured`、`authentication_failed`、`unavailable`、
  `suspended_quota`、`write_failed` 或 `writable`。

健康 Span 带 `langfuse.health_check=true`，可在 UI 中与业务 Trace 区分。检查使用
`x-langfuse-ingestion-version: 4`，确保 v4 直接写入而不是进入延迟传播路径。

## 5. Research Agent（研究智能体）业务 Trace

Research Agent 不直接展示 OpenAI Agents SDK 自动生成的 `mcp_tools`、`turn` 和 `response`
调试树。Runtime（运行时）关闭 SDK 自动 Trace，由 `AgentAuditHooks` 按研究语义创建
Langfuse Observation（观测记录）：

| 阶段 | Observation 名称 | 典型内容 |
| --- | --- | --- |
| 01 | 读取研究上下文 / 研究规划 | Context Pack（上下文包）、当前报告、运行状态和首轮研究计划 |
| 02 | 市场概览探索 | Market Frame（市场帧）、维度、主题和领域概览 |
| 03 | 板块与标的下钻 | 板块排名、板块详情、标的快照和历史数据 |
| 04 | 证据与关系核验 | Card（认知卡片）、Edge（关系证据）、市场证据和外部材料 |
| 05 | 记忆与历史复盘 | 角色记忆、历史结果、质量记录和账户暴露参考 |
| 06 | 综合分析与观点形成 | 中间模型轮次、假设比较、反证检查和观点组织 |
| 07 | 报告校验与提交 | Proposal（提案）参数、校验错误、修正轮次和最终提交结果 |

顶层 `Research Agent 研究运行` 保存精简的研究问题、触发原因、截止时间和运行模式；运行结束
后写入正式报告结果。详细追踪开启时，Generation（模型生成）和 Tool（工具）节点保存完整
输入输出。可恢复的报告校验退回标记为 `WARNING`，后续模型修正轮次命名为“07 报告修正”；
只有网络、模型、工具或运行本身不可恢复的失败才标记为 `ERROR`。

每个 Generation 还必须上报 `input`（输入词元）、`output`（输出词元）、`total`（总词元）、
`cached_input`（缓存输入词元，如提供方返回）和 `reasoning`（推理词元，如提供方返回）。这些
字段来自 OpenAI Agents SDK（OpenAI 智能体软件开发工具包）的实际 Usage（用量），写入
Langfuse 的 `usage_details`（用量明细），用于按模型轮次和整条 Trace 汇总消耗。

所有业务 Observation 使用顶层 Agent Observation 的 `trace_id` 和 `parent_span_id` 显式关联，
不跨异步回调持有 OpenTelemetry 当前上下文，因此支持并行工具调用。多次独立运行继续通过同一个
`session_id` 串联。
