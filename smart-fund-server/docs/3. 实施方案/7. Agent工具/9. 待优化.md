### THS token 自动上报：公网 cleartext HTTP 已验证可达，安全加固待 HTTPS（2026-08-17 记录，同日更新）

**问题：** token 自动上报链路（设备端捕获→POST /api/ths/token→入库→服务端自愈 import）已于 2026-08-17 部署到生产（119.23.227.187:8900，smart-fund-api systemd 服务）并真机验收：**THS App 的 network security config 放行明文 http 到公网 IP**（上报 `ok http=200 attempt=1`），可达性问题解除。剩余风险：token 明文走公网 http 理论上可被中间人截获（token 是券商交易登录凭证）。

**整改条件：** 域名与证书就绪时（或安全评估要求时）。

**优先级：** P2（可达性已验证，剩余为传输加密加固）

**写操作验收与压测（2026-08-18）：** 生产 E2E 买入 2 单全部执行成功（748/1029，操作 100% 生效）；撤单经真机路径 2/2 成功（code=0/状态错误判定正确）。**压测发现写响应回传缺陷（用户假设验证）**：写协议响应帧在分发总线上被 App 常驻观察者（委托刷新组件）竞争消费，自注册 observer 大概率收不到——查询协议无竞争者故稳定。已实现：①写响应旁路捕获（ixm/nxm receive hook 按 frameId 匹配 pending 登记，帧复制不参与竞争，via_bypass 标记）；②写超时自动查当日委托兜底（write_unconfirmed+followup_orders）。**AVD 上 cancel 仍不稳**（fluent 链挂死、H 链 30s 断连，真机两种链均正常）——根因待查（疑与写协议 25102 的会话绑定语义有关）。服务端写操作必须遵守：超时后查 today_order 定论，禁止盲目重发。

**架构改进方向（用户洞察，2026-08-18）**：当前交易实现是"长连接上的无状态请求-响应"（每次查询/写都临时注册 observer→发送→等待→注销），与行情采集的常驻订阅模式（搭 App 自身轮询便车、hook 常驻截获转发）不同。改进方向：读协议常驻订阅+缓冲读（HTTP 变纯读缓冲），写协议常驻旁路 hook（已完成第一步）——消除注册/等待/清理开销与观察者竞争。

**写操作不稳定根因解决（2026-08-18 晚，三重根因全部命中）：**
1. **写要求新鲜会话**：券商对写操作有会话新鲜度校验，老化会话上的写触发服务端安全重置（表现为写超时+随后的短暂全超时再自愈；查询无此校验故恒稳）。修复=写前强制登录（executeWriteWithConfirm 的 pre-write-login，force=true）。实测 BUY 从间歇超时变 115~151ms 响应直回（executed:true, confirmed_via:"response"）。
2. **增量 install staged 陷阱（部署总根因）**：进程运行时 `adb install -r`（增量）进入 staging 状态，**即使随后 force-stop 重启也不生效**（staged session 未 commit）——此前多轮"部署成功但行为不变"皆因此。正确流程=先 force-stop 再 `install -r --no-incremental`。
3. **HTTP 服务器 30s 读超时掐线**：慢 handler（pre-login+写+确认可达 90s+）期间被 SoTimeout 断连（客户端 30.0s "Server disconnected"）。修复=SoTimeout 180s，实测不再断连。
另：有状态确认重试（executeWriteWithConfirm：超时→查当日委托→买单不存在=确认未执行=安全重发；撤单状态含"已撤"=已执行）；ensure_error 登录成功后清除（不再残留陈旧错误）。

**cancel 时长待优化**：全流程（pre-login 35s 上限+两轮确认）最坏 ~150s，超客户端实用上限（实测 170s 客户端超时截断，但不再断连）。待办：pre-login 前查近期查询成功记录（30s 内有成功查询则跳过重登），可把会话良好时的写压缩到 ~2s。3378/1029 测试单已随收盘自动废单，无敞口。

**遗留（P2）：** ①cancel 时长优化（上述）；②冷启动首查 ~20s；③AVD 8 实例 ANR 重启风暴；④设备指纹依赖 SP/seed 文件；⑤同 token 互踢（真机生产期 role 关）。

**整改条件：** cancel 时长优化随下轮写操作回归（交易时段）一并做。

**优先级：** P2（核心已通）

### THS 设备端 ensureTradeRuntimeReady 可能长时间阻塞 HTTP handler（2026-08-17 记录，同日部分改善）

**问题：** App 被系统重启后（如息屏回收、内存压力），首个交易查询触发 `ensureTradeRuntimeReady` 时若账户仓库尚未加载（repoAccounts=0、`B()` 填充 0 个），App 内部调用（疑似 F(119) 或 n0s.B 的 synchronized 锁）可能**无限阻塞**——该 ensure 在设备端 HTTP handler 线程上同步执行且无看门狗，期间所有后续交易请求在 hook 服务器排队超时（实测 funds 3×60s 全超时）。临时恢复手段=force-stop + monkey 重启等预热。

**最佳方案：** 设备端给 ensureTradeRuntimeReady 加总体超时看门狗（如 60s 后放弃本次尝试返回错误，不占用 handler 线程）；或对 App 内部调用（F(119)/n0s.B）包一层 future + timeout。服务端已通过 30s HTTP 超时兜底（客户端 `THS_TRADE_TIMEOUT`），不会无限等。

**当前方案：** 服务端 THSTradeClient 30s 超时 + unavailable 降级（reason_code 透传）；设备端问题出现时人工 force-stop 重启。发生频率低（仅系统自动重启 + 仓库未加载竞态）。2026-08-17 部分改善：主动登录链引入 `tradeRuntimeLock` 专用锁（与类锁分离），登录长等待（最长 ~60s）不再阻塞主线程 hook 回调（此前主线程在 `captureTradeAccountManager` 上 BLOCKED 触发 Quality 监控告警，有 ANR 风险）；handler 线程同步执行 ensure 的根本问题仍未动。

**整改条件：** 下次修改 MainHook 探针时顺手加看门狗；或再次复现影响采集时。

**优先级：** P2

### THS 逆向：Pine 桩/真库双源与 zygisksu 体积限制（2026-08-16 记录）

**问题：** ths 项目源码里的 `Pine.java` 是 LSPosed XposedBridge 桥接桩（无 native 方法），而 libpine.so 的 JNI_OnLoad 需要注册真 Pine 类的 `init0(IZZZZZ)V`。真 Pine dex（`ths/zygisk/vendor/pine-classes.dex`）只能从 qdhook 项目手工复制，部署时若被 APK 自带 dex 覆盖会导致 UnsatisfiedLinkError、全部 hook 失效。另外 zygisksu（KernelSU 的 ZygiskNext）对模块 .so 有 ~356KB 预留地址空间限制，main.cpp 曾因 std::vector/std::sort 模板膨胀超限加载失败。
