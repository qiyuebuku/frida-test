# 待优化

本文件只记录尚未解决的实际偏差。Research Agent（研究智能体）MCP（模型上下文协议）的运行授权、
自动上下文准备、市场基线、交易日历、证据定位、记忆读取、结果提交和独立调度已经落地，不再列为待办。

### THS 交易端点 UI 依赖已闭环，静默重登耗时偏长（2026-08-17 记录，同日投影接线更新）

**问题：** 六个只读交易端点已实现零 UI 依赖（App force-stop 重启后不碰任何交易页面，等预热完成即可全部返回真实数据；账户恢复用 `n0s.s().B()` + `izr.a.x(fzr)`，登录态用 `x0s.F(false,false,14)` 静默重登 + `izr.a.l()` 轮询，params 全部静态模板化，见交接文档 §3.12）。遗留偏差：静默重登（token 链路）实测需 **2~3.5 分钟**才置位登录态，期间端点调用阻塞在登录门上（最多 45s/次）并返回错误；预热线程最多重试 6 次（约 6 分钟窗口），实测存在 6 次耗尽但按需路径随后自愈的情况（登录态在窗口边缘置位）。

**最佳方案：** 定位静默重登慢的具体环节（token 刷新/网络往返/重试间隔），必要时提前触发（如挂钩后立即而非等账户激活后）或缩短轮询周期。

**当前方案：** trade-warmup 后台线程循环重试 + HTTP 路径登录门（45s 轮询 + 3 次重登触发）返回明确错误码。服务端 Account Projection 已按**按需直调**设计落地（2026-08-17 用户决策：无调度无快照表，见《5. 券商账户投影按需直调实施方案》），重登窗口内调用返回 `unavailable` + `reason_code=trade_account_not_logged_in`，由上层提示等待或稍后重试，不重试轰炸设备。预热完成后的稳态调用 92~1865ms 全部正常。

**整改条件：** 实测发现重登窗口影响生产采集节奏时。

**优先级：** P2

### THS 设备端 ensureTradeRuntimeReady 可能长时间阻塞 HTTP handler（2026-08-17 记录）

**问题：** App 被系统重启后（如息屏回收、内存压力），首个交易查询触发 `ensureTradeRuntimeReady` 时若账户仓库尚未加载（repoAccounts=0、`B()` 填充 0 个），App 内部调用（疑似 F(119) 或 n0s.B 的 synchronized 锁）可能**无限阻塞**——该 ensure 在设备端 HTTP handler 线程上同步执行且无看门狗，期间所有后续交易请求在 hook 服务器排队超时（实测 funds 3×60s 全超时）。临时恢复手段=force-stop + monkey 重启等预热。

**最佳方案：** 设备端给 ensureTradeRuntimeReady 加总体超时看门狗（如 60s 后放弃本次尝试返回错误，不占用 handler 线程）；或对 App 内部调用（F(119)/n0s.B）包一层 future + timeout。服务端已通过 30s HTTP 超时兜底（客户端 `THS_TRADE_TIMEOUT`），不会无限等。

**当前方案：** 服务端 THSTradeClient 30s 超时 + unavailable 降级（reason_code 透传）；设备端问题出现时人工 force-stop 重启。发生频率低（仅系统自动重启 + 仓库未加载竞态）。

**整改条件：** 下次修改 MainHook 探针时顺手加看门狗；或再次复现影响采集时。

**优先级：** P2

### THS 零 UI 账户恢复依赖版本特定混淆名与单账户假设（2026-08-17 记录）

**问题：** ensureTradeRuntimeReady 的账户恢复链使用 11.58.03 混淆名（`n0s`/`B`/`izr`/`x`/`l`/`x0s`/`F`/`w5s`/`v`），且激活时取列表中**第一个 fzr**——多账户（同券商多股东号或多券商）场景下可能激活错账户。另 `x0s.F` 静默重登的是"上次登录成功账户"（其内部 `d` 字段），与激活的 fzr 理论上可能不同。

**最佳方案：** 与既有"混淆类名动态发现"待办（见下）合并处理：通过 MasterModuleBridge 锚点反查；多账户时用 `moh.a.WtAccountProvider_getLastSelectAccount_DEFAULT()` 对齐激活目标与重登目标。

**当前方案：** 测试环境单账户（川财模拟 3857）验证通过；多账户行为未验证。

**整改条件：** 接入第二个交易账户或 App 版本升级导致探针失效时。

**优先级：** P3

### THS 写交易：WSL curl 对 cancel 端点假性挂起（2026-08-16 记录）

**问题：** `POST /stock/trade/cancel` 服务端 84ms 完成响应（WDBG 日志证实），WSL curl `--noproxy '*'` 却 25 秒超时（EXIT 28）；同一端点 Python raw socket 0.34s 收全响应。疑似 curl 与 hook 服务器 keep-alive/分块传输交互问题。

### THS 逆向：Pine 桩/真库双源与 zygisksu 体积限制（2026-08-16 记录）

**问题：** ths 项目源码里的 `Pine.java` 是 LSPosed XposedBridge 桥接桩（无 native 方法），而 libpine.so 的 JNI_OnLoad 需要注册真 Pine 类的 `init0(IZZZZZ)V`。真 Pine dex（`ths/zygisk/vendor/pine-classes.dex`）只能从 qdhook 项目手工复制，部署时若被 APK 自带 dex 覆盖会导致 UnsatisfiedLinkError、全部 hook 失效。另外 zygisksu（KernelSU 的 ZygiskNext）对模块 .so 有 ~356KB 预留地址空间限制，main.cpp 曾因 std::vector/std::sort 模板膨胀超限加载失败。

**最佳方案：** 把真 Pine 源码（top.canyie.pine 全套）直接放进 ths 项目源码树或以 gradle 依赖引入，消除双源漂移；native 模块持续监控体积。

**当前方案：** vendor dex 固化在 `ths/zygisk/vendor/pine-classes.dex`（49320B），部署流程写死"只增量替换 classes3.dex、不动 classes.dex"；main.cpp 用纯 C 数组+插入排序+-Os 压到 346432B。依赖人工流程保证，无自动校验。

**整改条件：** 下次 Pine 或 libpine.so 升级时一次性迁移源码；或建立部署脚本自动比对 dex 内容。

**优先级：** P2

### THS 逆向：TRADE_TABLE_KEY_COLUMNS 键序映射需随版本校准（2026-08-16 记录）

**问题：** `StuffTableStruct.dataTable` 是列主序（外层 key=列号、内层数组=该列全部行值），且键序与 `tableHead` 展示序**不一致**（hist_order 实测：key0=代码、key1=名称，而 tableHead[0]=名称）。App 侧由各观察者私有的 `iArr`（`dzh.Y1` 的第二个参数）做键→列映射，stuff 本身不携带。MainHook 的 `TRADE_TABLE_KEY_COLUMNS` 是按 38 行真实数据人工校准的硬编码映射，协议升级或列增减后会错位。

**最佳方案：** hook `nxm` 构造或 `g(int,int,int[])` 时反射读取各观察者实例的 `e` 字段（iArr），自动建立 protocolId→键序映射，消除人工校准。

**当前方案：** 仅 1825（hist_order）有校准映射，输出 `key_columns` + `records`；其余协议输出 `columns`（tableHead）+ `rows`（键序位置数据），消费方需自行映射。1891（positions）、1810/1811/1824 等待有真实行数据后校准。

**整改条件：** 账户出现持仓或当日成交/委托数据时补充校准；或 App 协议升级导致 records 错位时。

**优先级：** P2

### Research 经验的语义归纳和历史回放门禁仍需增强（2026-08-15 更新）

**问题：** 到期结果评估、过程质量候选、预测结果候选、多案例与反例门槛、自动晋升、有效期和
只读召回已经形成生产闭环。当前 Predictive Outcome Memory（预测结果记忆）按对象类型、标准指标族
和方向做确定性聚合，尚不能自动归纳“在某种市场状态下为什么成立”的复杂语义机制，也尚未把独立
30例历史回放集作为每一条预测经验的额外晋升门禁。

**最佳方案：** 按预测验证窗口独立调度结果采集与评估；经验候选必须来自多个已评估案例，
通过适用条件、反例、样本数、时间衰减和历史重放门禁后才可晋升；失效经验保留历史而不再进入新运行上下文。

**当前方案：** 研究过程缺陷只有跨运行重复出现才晋升；预测经验必须至少三个真实到期案例且同时
包含支持和反例。单次模型反思仍然不能写入正式经验。确定性聚合只输出可审计样本统计，不伪造因果
机制；复杂机制经验在语义归纳和历史回放完成前保持候选或不生成。

**整改条件：** 正式到期预测积累到足以覆盖多个市场状态，并完成隔离的 Memory Curator
（记忆整理智能体）及逐条历史回放评测协议。

**优先级：** P1

### 自建 Langfuse 为单机部署，尚无高可用和自动异地备份（2026-08-10 记录）

**问题：** 当前 Langfuse（可观测平台）使用单机 Docker Compose（容器编排），持久化数据位于
本机 Docker Volume（容器卷）。主机或磁盘整体故障时，没有自动故障转移和经过验收的异地恢复链路。

**最佳方案：** 按官方生产规模方案迁移到 Kubernetes（容器编排集群）或云基础设施模板，使用托管
PostgreSQL、ClickHouse 和对象存储，并建立定期备份、异地复制、恢复演练及容量告警。

**当前方案：** 六个组件使用独立具名持久化卷，端口仅绑定回环地址，项目默认保留 90 天数据；该方案
已解决云端额度暂停并通过真实 OTLP 写入验收，但不声明具备高可用或灾难恢复能力。

**整改条件：** Langfuse 成为正式生产审计依赖、单日 Trace 量达到容量预警线，或业务提出恢复时间与
恢复点目标时，迁移并完成恢复演练。

**优先级：** P1

### Research 多轮工具历史仍造成较高模型输入成本（2026-08-12 记录）

**问题：** Research Agent（研究智能体）已经具备预算收敛、证据账本和提交前结构审计，
但 OpenAI Agents SDK（OpenAI 智能体软件开发工具包）仍会在后续模型调用中重放完整工具
历史。第 16 轮质量验收最终内容通过门禁，但 11 次模型调用累计约 23.6 万非缓存输入
Token（词元）；其中一次提案角色分类错误又触发整份结构化报告重写。

**最佳方案：** 在不破坏函数调用与结果配对、证据引用和模型自主研究路径的前提下，维护
确定性的 Research Notebook（研究笔记）：保留已打开证据的精确短引用、候选比较和未决
缺口，完成下钻后压缩早期导航输出；同时将可由 Schema（结构定义）表达的角色与状态约束
前置，目标是首次提案通过且总输入成本有稳定上限。

**当前方案：** 大目录、板块比较、证据账本和黄金数字列表已做有界投影；运行时在证据覆盖
充分时要求收敛，并在提交前检查事实/推断、时区、关键缺口、组合边界和数据质量假设角色。
尚未对历史函数调用结果做有损删除，避免因压缩错误让模型丢失真实证据或伪造结论。

**整改条件：** 用至少 20 次真实全市场研究回放验证 Notebook（研究笔记）的引用完整率为
100%，首次提案通过率和总 Token（词元）达到设定阈值后启用生产压缩。

**优先级：** P1

### 交易探针依赖版本特定混淆类名（2026-08-16 记录）

**问题：** 同花顺交易探针的关键挂钩点使用 11.58.03 版本的混淆短类名（`p0s`、`pzr`、`fzr`、`r9h`、`s9r`、`t9h`），App 升级重新混淆后全部失效；`r9h.d` 就绪检查也依赖字段名 `d`。

**最佳方案：** 以稳定锚点动态发现混淆名：例如通过 `libweituo.so` 唯一引用的 `com.hexin.android.mastermodule.MasterModuleBridge`（非混淆名）反查初始化器（扫描引用它的类），再从初始化器定位就绪标志字段；`p0s.F(119)` 可通过 `HxDebugTools.D7()` 的调用点反查。

**当前方案：** 直接硬编码当前版本类名，探针日志里保留 "not found (will retry)" 静默降级，升级后人工重新定位。

**整改条件：** 同花顺版本升级导致探针失效时，或第二块逆向（川财明佣独立 App）开始前。

**优先级：** P1

### 明文交易命令未在 Java 层捕获（2026-08-16 记录，已降级解决）

**问题：** `cmd=cmd_zijin_query` 等命令名由 libweituo.so 内部组装；Java 侧 Cipher 明文（AES/ECB 输入）不含 `cmd=` 字样，"页面 → 命令" 映射在纯 Java hook 下拿不到。

**最佳方案：** Hook `hrv.b`（SocketConnectionPool 帧解析）或 `asv.d().g(bArr)`（App 自带的 REQ_TRACE_SERVICE 请求追踪管道）获取解帧后结构；仍不行再上 native 层（frida stalker / libweituo 导出函数分析）。

**当前方案：** 只读调用器已用 Java 层查询 API（`uqv.e(true).H(pageId,protocolId,observer,params)`）直接实现，pageId/protocolId 可确定性区分各查询，cmd 映射不再阻塞（见文末"查询命令级映射降级"P3 条目）。

**整改条件：** 需要 cmd 级协议语义（跨版本协议对比）时再做 native 层分析。

**优先级：** P3

### 交易日志缓冲被账户对象高频调用刷屏（2026-08-16 记录）

**问题：** `recentTradeLogs` 上限 100 条，pzr 账户对象的 `d()/q()/e()` 等身份读取每次页面刷新高频触发（数十条/秒），把 r9h.o/receive 等关键事件挤出缓冲。

**最佳方案：** 交易事件分类限流：身份读取类（无参 getter）只计数不定长输出，请求/响应类事件保留全量。

**整改条件：** 下次触碰 MainHook 交易探针时顺手修复。

**优先级：** P2

### 查询命令级映射降级为 pageId/protocolId 映射（2026-08-16 记录）

**问题：** `cmd=cmd_zijin_query` 等原生命令名仍无法在 Java 层观测（native 内部组装）；但已定位 Java 层查询 API（`uqv.e(true).G(pageId, protocolId, callback, json)`，见交接文档 §7.0），pageId/protocolId 可确定性区分各查询。

**最佳方案：** 后续如需命令级语义（如跨版本协议对比），再对 libweituo.so 做 native 层分析。

**当前方案：** 以 pageId/protocolId/参数键名作为查询标识，满足只读调用器的确定性要求。

**整改条件：** App 升级导致 pageId/protocolId 语义漂移，或需要协议级兼容性验证时。

**优先级：** P3
