# 知识模型与领域适配设计方案

## 1. 本文解决什么问题

本文是知识图谱设计方案的开篇，先回答三个基础问题：

1. 知识图谱到底在系统里表达什么。
2. 为什么底层必须做成通用知识基础设施，而不是金融专用脚本。
3. 金融领域规则应该放在哪里，未来其他领域如何接入。

后续文档都会依赖本文的概念：数据源投影负责把业务表变成 Source Record，知识编译负责把 Source Record 写成 Node、Edge 和 Evidence，检索和 Wiki 负责消费这些事实。因此必须先定义“图谱能表达什么”和“领域语义由谁解释”。

当前第一阶段服务金融投研，但系统目标不是只构建一个金融知识图谱，而是构建一套可复用的知识基础设施。金融只是第一个领域适配器。

## 2. 本文不解决什么问题

本文不讨论原始数据如何投影为 Source Record；这属于“数据源投影与 Source Record”模块。

本文不讨论候选事实如何标准化、去重、写入和版本治理；这属于“知识编译、标准化与写入”模块。

本文不讨论如何检索、排序和拼装 Query Context；这属于“检索与 Query Context”模块。

本文不讨论如何生成 Wiki 或组织具体消费场景；这属于“Wiki 与消费场景”模块。

本文不列具体数据库字段、代码类名、接口和测试用例；这些属于实施方案。

## 3. 总体模型

知识图谱分为两层：

1. **通用知识基础设施**
   - 负责稳定表达 Node、Edge、Evidence、版本、索引、Wiki、Query Context 和质量治理。
   - 不直接写死金融字段、金融类型或金融关系。

2. **领域适配器**
   - 负责解释具体业务语义。
   - 定义本领域有哪些实体类型、关系类型、证据规则、抽取策略、置信边界和消费边界。
   - 当前第一版是金融适配器，未来可以替换或新增其他领域适配器。

通用层负责“知识图谱作为基础设施应该具备什么能力”，领域适配器负责“某个领域的数据应该如何解释成知识”。

## 4. 核心业务对象

### 4.1 Source Record

Source Record 是进入知识编译链路的标准输入。它不是原始业务表，也不是最终图谱事实。

Source Record 的详细投影规则由“数据源投影与 Source Record”模块定义。本文只强调一点：通用知识基础设施不直接读取 `ft_news`、`ft_market_flow`、`ft_sentiment` 等业务表，也不把某个业务表字段当成图谱模型的一部分。

### 4.2 Node

Node 表示知识图谱中的实体。实体可以是股票、基金、行业、政策、事件、机构、地区、商品、主题，也可以是其他领域中的自定义对象。

通用层只关心 Node 是一个可识别、可引用、可挂载属性、可参与关系的对象。它不直接判断“新能源车产业链”到底应该是行业、概念还是主题，这类判断由领域适配器和写入治理完成。

### 4.3 Edge

Edge 表示实体之间的关系。关系必须有方向、类型、来源证据和置信边界。

关系不是简单的文本描述。它决定后续检索、路径扩展、策略解释和事件影响传导，因此关系类型必须由领域适配器约束，不能让 LLM 任意生成。

### 4.4 Evidence

Evidence 表示事实来源。任何进入主图的关系都应该能追踪到证据。没有证据的关系只能作为候选、推断或质量问题，不能作为强事实消费。

Evidence 的价值不只是“证明这个事实从哪里来”，还包括支持问答引用、质量回放、错误定位、版本治理和规则审计。

### 4.5 Domain Adapter

Domain Adapter 是领域适配器。它不是业务脚本集合，而是通用知识基础设施和具体业务语义之间的协议层。

通用层不直接理解 `news_articles`、`policy_news`、`market_flow.*` 这类领域标签；这些标签必须由领域适配器解释。

### 4.6 Candidate Fact Package

Candidate Fact Package 是候选事实包。它是规则抽取、LLM 抽取和领域适配器之间交换候选知识的统一结构。

候选事实包不是金融新闻 payload 的内部字段，也不是最终主图事实。它必须能表达候选实体、候选事件、候选关系、证据片段、歧义说明和规则建议，并交给写入链路继续做标准化、关系校验、证据绑定和置信度门禁。

## 5. 核心设计决策

### 5.1 通用层不写死金融字段

通用层只定义知识图谱的基础能力。金融字段、金融关系、金融事件类型都由金融适配器定义，不能渗透到通用模型里。

这样做是为了避免系统只能服务金融场景。未来如果要接入法律、医药、供应链、企业情报或其他领域，应该新增领域适配器，而不是重写通用图谱基础设施。

### 5.2 领域适配器决定业务语义

领域适配器负责回答这些问题：

1. 这个领域有哪些实体类型。
2. 哪些关系是合法关系。
3. 哪些来源可以生成高置信事实。
4. 哪些事实只能用于解释，不能用于硬评分。
5. 哪些 Source Record 可以规则抽取。
6. 哪些 Source Record 存在语义不确定性，需要 LLM 生成候选。
7. 哪些 Source Record 缺少基础字段，只能跳过或降级。

这样通用层可以保持稳定，领域层可以持续迭代。

### 5.3 领域适配器协议必须稳定

领域适配器至少要提供四类能力：

1. 类型协议：定义本领域允许出现的实体类型、事件类型、关系类型和消费层级。
2. 解释协议：解释 Source Record 中的 `source_type`、metadata、来源可信度和内容形态。
3. 抽取协议：决定某条 Source Record 走规则抽取、LLM 候选抽取、混合抽取还是跳过。
4. 校验协议：判断候选实体和候选关系是否符合领域约束，并给出置信度、降级原因和质量告警。

通用编译核心只能调用这些协议，不能直接内置某个领域的业务判断。

### 5.4 “是否需要 LLM”由适配器先判断

“是否需要 LLM”本身不能由 LLM 判断，否则会变成每条数据都先调用一次模型，成本和链路复杂度都不可控。这个判断必须由领域适配器先用规则完成。

判断依据包括：

1. Source Record 是否具备强 ID，例如股票代码、基金代码、行业代码、外部事件 ID。
2. 关键字段是否完整，例如主体、客体、关系类型、时间、来源和证据内容。
3. 已有规则是否能唯一确定实体类型、关系类型和关系方向。
4. 名称是否存在多类型歧义，例如同一个词可能是政策、概念、行业、事件或公司。
5. 关系是否存在语义歧义，例如“利好”“承压”“驱动”“约束”等表达需要上下文判断影响对象和方向。
6. payload 是否只是结构化指标，还是包含需要解释的复杂嵌套语义。

如果规则能稳定解释 Source Record，就走规则路径；如果规则能明确指出存在语义歧义，才进入 LLM 候选抽取；如果缺少主键、来源、时间或证据等基础字段，则应该跳过或失败，而不是交给 LLM 兜底。

### 5.5 LLM 只生成候选事实包

LLM 可以参与实体识别、事件归纳、关系候选生成、证据片段标注和歧义说明，但不能直接决定最终主图事实。

LLM 输出必须是结构化候选包，而不是自然语言结论。候选包至少应该表达：

1. 候选实体：名称、类型、别名、出现位置、置信度。
2. 候选事件：事件标题、事件摘要、发生时间、相关实体、置信度。
3. 候选关系：关系类型、source、target、方向、证据片段、置信度。
4. 不确定项：歧义原因、可能候选、是否需要降级处理。

LLM 不负责生成最终稳定实体 ID，不负责决定实体最终归一到哪个标准实体，不允许绕过关系白名单创建新关系类型，也不能在没有证据片段的情况下创造事实。

Candidate Fact Package 必须是一等领域对象。领域适配器不能把 LLM 输出折回某个历史业务 payload 字段后再让编译器间接理解，例如不能把所有候选都塞进 `mentioned_entities`、`affected_entities` 这类金融新闻专用字段。旧字段可以作为兼容输入继续存在，但新抽取结果应该以候选事实包的形式进入适配器转换链路。

### 5.6 金融适配器第一版聚焦投研闭环

金融适配器第一版不追求覆盖所有金融知识。它应该优先覆盖事件驱动投研最需要的实体和关系：

1. 资产：股票、基金、商品。
2. 业务分类：行业、概念、主题。
3. 外部影响：政策、事件、地区、机构。
4. 传导关系：影响、提及、归属、持有、相关。

第一版目标是支撑新闻入图、事件上下文检索、行业/资产影响传导和投研问答，而不是构建完整金融百科。

### 5.7 事实消费需要分层

不是所有事实都能进入同一消费层。结构化高置信事实可以进入硬消费，LLM 抽取结果更适合进入候选、解释或问答上下文。

金融决策链路尤其需要区分：

1. 可以参与硬评分的确定性关系。
2. 只能作为解释和辅助判断的语义关系。
3. 需要进一步验证的候选关系。

## 6. 模块边界

本模块负责：

- 定义知识图谱的基础概念和总体分层。
- 定义通用层和领域适配器的职责边界。
- 定义领域适配器如何表达实体类型、关系类型、抽取策略和消费边界。
- 定义 Candidate Fact Package 和 LLM 在领域适配器中的候选事实角色。
- 定义金融适配器第一版的覆盖范围。

本模块不负责：

- 从数据库读取原始数据。
- 将原始数据投影成 Source Record。
- 维护实体标准化规则、去重规则和写入版本。
- 实现检索排序和上下文拼装。
- 编写具体代码、接口和数据库表结构。

## 7. 和其他模块的关系

“数据源投影与 Source Record”依赖本文的边界，确保业务表不会直接渗透进知识模型。

“知识编译、标准化与写入”依赖本文定义的 Node、Edge、Evidence 和领域适配器协议，把 Source Record 编译成可治理的主图事实。

“检索与 Query Context”依赖本文提供的事实语义，否则检索结果无法解释，也无法判断哪些关系能进入业务回答。

“Wiki 与消费场景”依赖本文提供的事实语义，否则 Wiki 摘要和业务解释无法保持证据边界。

## 8. 验收口径

该设计成立的标准是：

- 读者先读本文即可理解知识图谱的核心对象和总体分层。
- 通用层不包含金融专用字段。
- 新领域可以通过新增领域适配器接入，而不是重写通用基础设施。
- 金融适配器可以表达第一版投研场景需要的实体和关系。
- 关系类型受控，不允许 LLM 任意扩展关系语义。
- LLM 只生成 Candidate Fact Package，不能直接写入主图。
- 新抽取结果不能再依赖金融新闻历史字段作为唯一候选事实载体。
- 不同置信来源的事实有清晰消费边界。
