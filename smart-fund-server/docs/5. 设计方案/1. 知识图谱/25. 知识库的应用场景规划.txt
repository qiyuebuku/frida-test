 你的判断基本正确：现在已经有了“事实节点、关系边、关系社区”这套知识基座。下一步不应该急着批量生成大量固定报告，而是先建立一层 面向 Agent 的图谱检索与认知组装服务。

  核心定位

  现有数据分别解决不同问题：

  - Card：发生了什么。
  - Edge：两个事实为什么有关。
  - Community：哪些事实形成了相对稳定的关系网络。
  - 原文证据：事实和关系是否可信。

  Agent 真正需要的不是把整个 Community 全部塞进上下文，而是针对当前问题，从图里裁出一块最相关、证据完整的子图。

  推荐链路：

  Agent 问题
    ↓
  识别实体、资产、时间范围和分析目标
    ↓
  从 Card Summary / Focus Evidence 召回种子 Card
    ↓
  沿有效 Edge 扩展一至两跳
    ↓
  利用 Community 补充可能遗漏的重要节点
    ↓
  按相关性、时效性和证据强度裁剪
    ↓
  取回必要原文
    ↓
  组装金融认知上下文
    ↓
  Agent 分析、回答或形成条件性判断

  第一步应该做什么

  我建议先实现一个 Graph Context Builder，它不直接做投资决策，只负责向 Agent 交付高质量上下文。

  输入大致是：

  {
    "query": "近期存储芯片涨价会影响哪些A股公司？",
    "time_range": "90d",
    "max_cards": 20,
    "max_hops": 2
  }

  输出应该包含：

  {
    "direct_facts": [],
    "relation_chains": [],
    "community_context": [],
    "conflicting_evidence": [],
    "source_evidence": [],
    "coverage": {}
  }

  重点不是这些字段名称，而是让 Agent 一次获得：

  1. 直接命中的事实。
  2. 多篇新闻之间已经确认的关系链。
  3. 支持和冲突证据。
  4. 每个结论对应的原文。
  5. 哪些部分是事实，哪些只是推断。

  金融认知组装

  在拿到图谱上下文后，可以让 Agent 按金融传导链分析：

  事件或政策
    → 供给/需求变化
    → 产品价格与库存
    → 企业订单、收入或成本
    → 利润与现金流
    → 市场预期和估值
    → 潜在受益或受损资产

  最终输出不应只有“利好某行业”，而应包含：

  - 当前已经发生的事实。
  - 跨文档才能得到的关系。
  - 影响传导路径。
  - 受益方和受损方。
  - 尚未被证实的环节。
  - 需要继续观察的指标。
  - 判断成立和失效的条件。

  Community 的使用方式

  Community 更适合充当导航和召回边界，而不是直接充当答案。

  例如 Agent 命中一个“存储器价格上涨”Card 后：

  1. 先沿关系边找到产能、库存、需求、企业业绩等节点。
  2. 再通过所属 Community 补充附近的重要节点。
  3. 只将与问题相关的子图交给 Agent。
  4. 不要默认把整个 Community 全部总结。

  这可以避免重新走回“把大量弱相关内容放在一起强行写报告”的老路。

  后续能力

  基础检索稳定后，可以依次增加：

  1. 动态认知报告

     针对 Agent 当前问题实时生成，必要时缓存，不再无差别为全部 Community 生成固定报告。

  2. 事件时间线

     展示一个主题如何从早期信号发展到当前状态，特别适合政策、供需和企业经营分析。

  3. 条件性推演

     事实和预测严格分开：

     如果价格继续上涨且新增产能未释放，
     则上游厂商利润改善概率上升。

     验证指标：现货价格、库存、排产。
     失效条件：需求下降或产能提前释放。

  4. 主动监控与告警

     当某个 Community 出现高重要度节点、新增关键关系、冲突证据或关系密度快速上升时，主动通知 Agent。

  实施顺序

  我建议下一阶段只聚焦三件事：

  1. 建立 Agent 可调用的图谱检索 API/Tool。
  2. 实现从种子 Card 到相关子图的 Graph Context Builder。
  3. 建立真实金融问题评测集，验证检索结果是否真的帮助 Agent 得出更完整的判断。

  先不要直接做自动买卖建议，也不要再次批量生成全量 Community 报告。我们应先证明：**Agent 使用关系子图后，比只检索单条 Chunk 能多发现哪些可靠信息。**这一步验证通过后，再构建动态报告、预测和主动告警。

  这套机制不能只看“接口能不能返回数据”，需要分成 工具正确性、检索质量、Agent 最终收益 三层验收。

  一、工具正确性

  验证每个工具是否严格履行职责：

   工具                        核心验收
  ━━━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   kg_relation_graph_search    返回相关 Card，不返回失效 Card，不跨 target/adapter
  ──────────────────────────  ─────────────────────────────────────────────────────
   kg_card_expand              只返回真实存在的相邻 Edge，方向和跳数正确
  ──────────────────────────  ─────────────────────────────────────────────────────
   kg_community_expand         只沿正式跨社区关系展开
  ──────────────────────────  ─────────────────────────────────────────────────────
   kg_card_open                Summary、Focus Evidence、来源、时间准确完整
  ──────────────────────────  ─────────────────────────────────────────────────────
   kg_edge_open                两端 Card、关系方向、证据和 decision_class 一致
  ──────────────────────────  ─────────────────────────────────────────────────────
   kg_community_open           成员 Card、内部 Edge 和统计数量一致

  这一层主要依靠自动化测试和数据库一致性检查，目标应接近 100%。

  二、建立人工标注评测集

  不能只随机搜索看起来像不像，需要准备一批真实金融问题，并标注预期结果。

  例如：

  {
    "query": "存储芯片涨价的原因和潜在下游影响是什么？",
    "expected_card_ids": ["..."],
    "expected_edge_ids": ["..."],
    "expected_relation_kinds": [
      "causal_influence",
      "confirmation"
    ],
    "expected_evidence_ids": ["..."],
    "forbidden_card_ids": ["..."]
  }

  评测问题要覆盖：

  - 同一事件的后续进展。
  - 上游原因和下游影响。
  - 多来源相互印证。
  - 观点或事实冲突。
  - 跨市场联动。
  - 企业、产品、行业传导。
  - 没有有效关系的负样本。
  - 时间范围限制。
  - 容易被关键词误召回的硬负样本。

  第一批可以从现有数据库选 30～50 个案例，之后将线上坏例持续加入。

  三、工具级指标

  重点统计：

  - Card Recall@K：预期 Card 是否进入前 K 个结果。
  - Edge Recall：预期关系是否通过展开找到。
  - Graph Precision：展开结果中真正相关的关系比例。
  - Evidence Coverage：最终结果是否包含必要原文证据。
  - Forbidden Hit Rate：明确无关内容的进入比例。
  - Path Recall：预期传导链是否完整找出。
  - Community Navigation Recall：是否通过 Community 找到相关事件群。

  最重要的是 Recall。第一步漏掉了正确 Card，后续工具再准确也没有意义。

  四、端到端 A/B 测试

  使用相同模型、Prompt 和 Token 预算，对比四组：

  A：只检索原始 Chunk
  B：只检索 Card
  C：Card + Edge
  D：Card + Edge + Community

  然后评估最终回答：

  - 事实是否准确。
  - 是否发现跨文档关系。
  - 因果链是否完整。
  - 是否把推断写成事实。
  - 是否提供可核验证据。
  - 是否引入无关信息。
  - 时间顺序是否正确。
  - Token、耗时和工具调用次数。

  这里真正需要证明的是：

  > D 或 C 是否能比传统 Chunk RAG 多找出可靠的跨文档信息。

  如果只是回答更长，却没有增加有效认知，这套图谱工具就没有产生价值。

  五、Langfuse 观测

  每次评测使用同一个 Session，记录完整调用链：

  Agent Query
    → graph_search
    → card_open
    → card_expand
    → edge_open
    → Agent Answer

  每个 Tool Span 记录：

  - 输入参数。
  - 返回对象 ID。
  - 新增了哪些 Card/Edge。
  - 返回字符数。
  - 执行耗时。
  - Agent 是否实际采用这些内容。

  这样可以区分问题究竟出在召回、展开、证据读取，还是 Agent 没有正确使用工具。

  六、验收脚本

  后续实现时应同时增加一个只读测试脚本，例如：

  python scripts/知识图谱/02_relation_graph_agent_validation.py \
    --dataset relation_graph_agent_cases.json \
    --target prod \
    --limit 50

  它负责：

  - 批量执行评测案例。
  - 输出 Recall@K、Edge Recall、噪声比例等指标。
  - 将完整链路写入 Langfuse。
  - 保存 A/B 对比结果。
  - 支持只运行单个坏例反复调优。

  最终不能以“随机跑几次感觉不错”作为验收，而应以 关系图相较于纯 Chunk RAG，是否稳定提升跨文档问题的正确率和完整度 作为核心标准。
