# 知识编译、标准化与写入设计方案

## 1. 本文解决什么问题

本文说明 Source Record 如何被编译、标准化、去重并写入知识图谱事实层。

业务表中的原始数据不会直接进入知识编译器。它们必须先由“数据源投影与 Source Record”模块转换为统一 Source Record。知识编译器只负责消费 Source Record，并将其变成可追踪、可治理、可检索的 Node、Edge 和 Evidence。

本文把“实体标准化与去重治理”合并进写入链路中，因为标准化不是独立于写入之外的能力，而是写入前质量门禁。没有标准化、去重、关系校验和证据绑定，候选事实就不应该进入主图。

这里的“写入”特指事实层写入。面向检索的 Retrieval Document、BM25 文档、向量文档、facets、rerank features 是事实层之后的可重建派生数据，不直接并入 Node、Edge、Evidence 主事实。知识编译需要输出足够稳定的事实变更集合，供检索层重建这些派生索引。

## 2. 本文不解决什么问题

本文不负责从业务表生成 Source Record；这是“数据源投影与 Source Record”模块的职责。

本文不定义实体类型全集，也不定义金融领域完整本体；这些属于“知识模型与领域适配”模块。

本文不讨论检索排序、Query Context、Wiki 页面和问答消费；这些属于“检索与 Query Context”和“Wiki 与消费场景”模块。

本文不定义 Retrieval Document 的字段权重、BM25/向量文本生成策略和 rerank 规则；这些属于检索实施方案。但本文定义事实层与检索层的交接边界：检索层只能从已写入事实和 evidence 生成派生文档，不能反向污染主图事实。

本文不写数据库表字段、接口参数、类名、迁移 SQL 和测试代码；这些属于实施方案。

## 3. 核心业务对象

### 3.1 Source Record

Source Record 是知识编译的统一标准输入。它代表一条可被编译的业务材料，例如一条文本材料、一条结构化信号、一个实体快照、一条关系断言或一个事件断言。

编译核心不关心 Source Record 来自哪张业务表，也不应该直接理解 `news_articles`、`policy_news`、`market_flow.*` 这类业务标签的含义。`source_type` 是领域适配器解释的语义标签，不是编译核心的硬编码分支。

### 3.2 Candidate Fact

Candidate Fact 是候选事实，表示领域适配器从 Source Record 中抽取出的实体候选、关系候选、事件候选或证据候选。

候选事实不能直接写入主图。它必须经过标准化、去重、关系合法性校验、证据绑定、置信度判断和版本治理。

### 3.3 Candidate Fact Package

Candidate Fact Package 是候选事实集合。它统一承载候选实体、候选事件、候选关系、证据片段、歧义项和规则建议。

编译链路必须把候选事实包作为一等输入处理，而不是把它降级为某个领域历史 payload 字段。领域适配器负责把候选事实包转换为 NodeDraft、EdgeDraft 和 EvidenceDraft 所需信息，编译核心负责后续标准化、关系校验和写入治理。

### 3.4 Canonical Entity

Canonical Entity 是标准实体。它代表系统最终认可的实体身份，例如“宁德时代”“并购重组”“低利率环境”。

所有别名、近义说法和来源表达都应该尽量映射到标准实体，而不是反复创建新节点。

### 3.5 Normalization Rule

Normalization Rule 是实体标准化规则。规则必须落库，不能只写死在代码中。

规则既可以来自初始种子，也可以来自写入过程中的 LLM 候选建议、定期扫描和质量回放。

### 3.6 Merge Audit

Merge Audit 是合并审计记录。自动合并、软合并、阻断合并都需要可回溯，方便后续定位规则为什么产生、影响了哪些数据、是否需要整改。

### 3.7 Evidence

Evidence 是事实的证据载体。任何进入主图的关系都必须能追溯到证据，不能只保存一个没有来源的结论。

证据的价值不只是“证明这个事实从哪里来”，还包括支持后续问答引用、质量回放、错误定位和规则审计。

### 3.8 Changed Fact Set

Changed Fact Set 是知识编译写入后的事实变更集合。它包含本次新增、更新、失效或 supersede 的 node、edge、evidence 和版本信息。

Changed Fact Set 是事实层和检索层的交接对象。检索层根据它回读事实层并构建 Retrieval Document、BM25 文档、向量文档和 facets。它不包含最终检索文本和排序特征，避免检索层派生表达反向污染事实层。

## 4. 输入和输出

### 4.1 输入

本模块只接受统一 Source Record 协议。不同业务来源不能绕过协议直接进入编译器。

输入包括：

1. Source Record 的来源标识、内容形态、业务时间、内容载体和 metadata。
2. 领域适配器提供的实体类型、关系类型、抽取策略和置信规则。
3. 领域适配器或 LLM 产出的 Candidate Fact Package。
4. 已有标准实体、别名、标准化规则和历史合并记录。
5. 写入侧已有的 Evidence 版本、Node、Edge 和质量记录。

### 4.2 输出

本模块输出：

1. 写入或复用的标准实体。
2. 写入或复用的关系。
3. 写入或复用的证据。
4. 标准化命中、创建新实体、软合并、阻断合并和质量告警。
5. 写入成功、跳过、失败、版本变更和 Changed Fact Set。
6. 可供检索层增量刷新使用的 changed node IDs、changed edge IDs、changed evidence IDs 和 stale evidence IDs。

## 5. 核心设计决策

### 5.1 编译器只消费统一 Source Record

Source Record 是唯一编译输入。编译器不能直接读取 `ft_news`、`ft_market_flow`、`ft_market_cache`、`ft_sentiment`、`ft_macro_indicators` 等业务表。

这样做的原因是：业务表字段、外部来源格式、采集逻辑都会变化，但知识编译需要稳定的输入边界。

### 5.2 编译核心和领域适配器解耦

知识编译分成两层：

1. 编译核心：负责通用流程，包括接收 Source Record、创建证据草稿、调度适配器、执行基础校验、汇总结果、交给写入层。
2. 领域适配器：负责领域语义，包括理解 `source_type`、选择抽取策略、应用领域本体、产出实体候选和关系候选。

编译核心不能出现类似“如果 source type 是某个金融新闻类型，就执行某段金融逻辑”的设计。新增领域、替换金融适配器或增加新的业务来源时，应该扩展领域适配器，而不是修改编译核心。

### 5.3 结构化关系优先规则抽取

能从结构化数据确定的关系应该由规则生成。例如股票代码对应股票实体，基金持仓对应基金和股票之间的持有关系，行业成分对应股票和行业之间的归属关系。

LLM 不应该负责这些确定性关系，否则会增加成本、延迟和不确定性。

### 5.4 LLM 候选必须经过写入门禁

新闻、政策、公告、研报摘要这类文本需要语义理解。后续其他类型的 Source Record 也可能出现语义不确定、规则无法稳定判断的情况。LLM 的职责不是直接生成最终图谱，而是在领域适配器的约束下，把这些不确定输入转成可校验的候选事实。

LLM 输出必须先成为 Candidate Fact Package，再由领域适配器转换为 NodeDraft / EdgeDraft 所需信息。不能把 LLM 输出折回 `mentioned_entities`、`affected_entities` 等领域历史字段作为唯一编译入口，否则新领域适配器无法复用候选事实协议。

无论候选事实来自规则还是 LLM，都必须在写入前经过：

1. 实体标准化与去重。
2. 关系合法性校验。
3. 证据绑定。
4. 置信度和质量门禁。
5. 版本治理。

没有通过校验的候选只能进入告警、审计或丢弃，不能静默进入主图。

### 5.5 不允许空规则启动

系统不能在完全没有规则的情况下直接写入主图。首次启动时必须具备一批基础规则种子，例如常见实体类型、行业/概念边界、常见资产别名、政策和事件命名原则。

如果数据库没有规则，系统应该自动初始化基础规则，而不是让第一批数据自由生长。

### 5.6 标准化发生在写入前

实体治理不能主要依赖事后扫描。事后扫描只能补救，不能作为主路径。

正确流程是在实体写入前，先拿候选实体和已有规则、已有实体、上下文证据进行匹配。能命中已有标准实体就复用，不能命中才创建新实体或生成新规则候选。

### 5.7 LLM 可以参与规则维护，但不能绕过校验

LLM 适合处理近义名称、主题边界、上下文歧义和新规则候选。例如“高股息”“高股息资产”“红利资产”是否应该归并，纯字符串规则很难稳定判断。

但 LLM 不能直接决定最终主键，也不能绕过规则校验直接修改主图。LLM 的输出必须变成结构化候选，再经过规则冲突检查、类型合法性检查和证据检查。

### 5.8 合并分为强合并和软合并

强合并用于高置信、低风险场景，例如明确股票代码相同、权威外部 ID 相同、规则明确的别名。

软合并用于中等置信场景，例如近义主题、上下文高度相关但类型边界不完全确定的概念。软合并可以在检索侧合并展示，但不一定立即改写主图。

### 5.9 冲突必须显式记录

当规则、类型、证据或上下文冲突时，系统应该阻断强合并，并写入质量问题或合并审计记录。

最坏情况不是“多几个重复节点”，而是错误合并导致事实污染：错误关系被继承、检索上下文混乱、策略解释引用错误证据。因此冲突必须可见。

### 5.10 编译必须增量化

知识图谱不能依赖全量重建。新增 Source Record 进入时，应该只编译新增或变更的 Source Record，并增量刷新相关索引和 Wiki。

全量重建只用于规则大改、数据清理、索引损坏、质量基线重跑等明确场景。

### 5.11 写入必须支持证据幂等和版本治理

同一条业务来源材料可能被重复投影、重复编译和重复写入。写入层不能因为脚本重跑或任务重试就不断生成新的 evidence、edge 和索引内容，否则知识图谱会持续积累重复证据，检索结果也会被历史重复版本污染。

写入层必须基于 Source Record 提供的来源标识和内容 fingerprint 做幂等判断：

1. 同一 `adapter + source_type + source_id + fingerprint` 已经写入过时，重复编译应复用已有 evidence 或跳过重复写入。
2. 同一 `adapter + source_type + source_id` 的 fingerprint 发生变化时，可以生成新版本 evidence。
3. 旧版本如何保留、降级或标记为 superseded，必须由写入层明确处理，不能让多个版本都以同等 active 状态参与默认消费。
4. 默认检索和消费应该优先使用 active/latest evidence；历史版本用于审计、回放和差异分析。
5. 关系和索引刷新也要跟随 evidence 版本状态，否则旧关系会继续污染图谱邻居和检索召回。

### 5.12 弱提示字段不能直接进入主图

Source Record 可能包含强线索和弱提示。强线索通常来自结构化标识，例如股票代码、基金代码、行业代码、外部事件 ID；弱提示通常来自 tags、栏目、频道、来源侧主题词或平台分发标签。

领域适配器可以读取弱提示，但弱提示不能直接等价为主图事实：

1. 弱提示可以作为 LLM 抽取上下文、候选召回线索或歧义消解辅助。
2. 弱提示要升级为候选实体或候选关系，必须能在标题、正文、结构化 payload 或其他证据字段中找到支撑。
3. 弱提示生成的候选仍然必须经过实体标准化、关系合法性校验、证据绑定和置信度判断。
4. 泛化市场标签，例如 `A股`、`港股`、`美股`、`市场`、`板块`，不能因为出现在 metadata tags 中就自动成为 `mentioned_entities`。
5. 如果弱提示无法获得证据支撑，应保留在 evidence metadata 或抽取诊断中，而不是写入 Node 和 Edge。

### 5.13 检索增强字段不能污染事实层

写入链路必须区分事实属性和检索派生属性。

适合进入事实层的字段：

- 标准实体、稳定别名、强外部 ID。
- 已校验关系、关系方向、关系置信度。
- evidence content、payload、metadata、source fingerprint、版本状态。
- 经过证据绑定和质量门禁的 event_type、source_time、source_name 等稳定属性。

默认不进入事实层的字段：

- `search_text`
- `key_phrases`
- `readable_relations`
- `answer_candidate_type`
- BM25 text
- vector text
- rerank features
- coverage facets

这些字段应由检索层根据事实层和 evidence 生成 Retrieval Document。它们可以保存生成版本、prompt、置信度和来源 evidence，但不能被当成系统确认的事实。

如果真实回放和质量评估证明某个检索增强字段长期稳定，并且具有明确事实语义，可以通过新的设计变更提升为事实层属性；不能由索引模块静默回写主图。

## 6. 模块边界

本模块负责：

- 定义 Source Record 到候选事实的编译职责。
- 定义 Candidate Fact Package 作为一等编译输入的职责边界。
- 定义候选事实写入前的标准化、去重、关系校验和证据绑定原则。
- 定义规则必须落库和自动初始化的要求。
- 定义 LLM 参与抽取和规则维护的边界。
- 定义强合并、软合并、阻断合并的业务语义。
- 定义增量写入、证据幂等和版本治理的业务边界。
- 定义事实层与检索层的交接边界，输出 Changed Fact Set。

本模块不负责：

- 从数据库读取原始数据并投影为 Source Record。
- 定义所有领域实体类型和关系类型。
- 在编译核心中硬编码某个业务来源或领域 source type 的处理逻辑。
- 设计检索排序和上下文拼装策略。
- 生成 Retrieval Document、BM25 文档、向量文档和 rerank features。
- 设计 HTTP API、CLI、数据库表字段和具体算法。

## 7. 和其他模块的关系

本模块位于数据源投影之后。它依赖“数据源投影与 Source Record”提供统一输入，依赖“知识模型与领域适配”解释领域语义和提供实体关系定义，最终产出的事实被“检索与 Query Context”和“Wiki 与消费场景”消费。

本模块不直接生成最终检索文档，但必须输出可用于检索层增量刷新的 Changed Fact Set。检索层应根据 changed facts 回读事实层并构建 Retrieval Document，而不是要求编译层把检索文本直接写入主图事实。

如果编译层把脏数据直接写入主图，后续模块只能被动补救。因此实体标准化、去重、关系合法性和证据约束必须在写入链路中完成。

如果编译核心直接理解某个业务来源标签，系统会重新和数据源投影耦合，后续新增数据源或迁移到其他领域时会变成修改核心代码。因此业务标签只能由领域适配器消费，不能成为编译核心协议。

## 8. 验收口径

该设计成立的标准是：

- 编译器只消费统一 Source Record，不直接读取业务表。
- 编译核心只理解通用内容形态，不硬编码金融 source type。
- 同一条 Source Record 可以稳定生成可追踪证据。
- 结构化关系可以不依赖 LLM 生成。
- 非结构化文本抽取结果必须经过标准化、去重、关系校验和证据绑定后才能进入主图。
- LLM 或规则抽取的新候选事实必须以 Candidate Fact Package 进入适配器转换链路。
- 系统首次运行时自动具备基础标准化规则。
- 新实体写入前必须经过标准化判断。
- LLM 可以生成新规则候选，但不能直接污染主图。
- 类型冲突不会静默进入强合并。
- 合并、阻断、迁移都有审计记录。
- 新增 Source Record 可以增量进入知识图谱，不需要每次全量重建。
- 编译结果能输出 Changed Fact Set，供检索层重建 Retrieval Document。
- `search_text`、`key_phrases`、`readable_relations`、`answer_candidate_type`、rerank features 等 retrieval-only 字段不会写入 Node、Edge、Evidence 主事实。
