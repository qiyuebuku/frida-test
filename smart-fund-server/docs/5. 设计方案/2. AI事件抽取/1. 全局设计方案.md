## 0. 一句话说清楚

> **把每天 300 条原始新闻（`ft_news`）+ 多路结构化数据（资金/宏观/情绪/市场），经过"文本AI抽取 + 数值规则识别"双路径 → 事件聚合 → 主线识别 → 打分过滤，最终变成"可执行的交易信号"，并在重大事件发生时快速触发响应。**

## 1. 系统定位与当前位置

### 1.1 系统在做什么

这是一个 **"事件驱动 + 情绪/资金辅助" 的量化决策引擎**：
- **主信号源**：新闻与公告（事件驱动）+ 数值异常（资金拐点/宏观数据超预期）
- **辅信号源**：情绪、资金流、宏观环境、技术面（已有的 L2 聚合层）
- **输出**：一份可排序的"候选股+触发条件"清单，以及重大事件的即时推送

### 1.2 现在走到哪里了（地基已完成）

### 1.4 用户的核心困惑与本文档的答案

> "数据都采回来了，但我不知道下一步做什么。"

**答**：下一步有**两件事要同时做**——
1. **L1a**：让 AI 把 `ft_news` 读一遍，产出文本类事件（"央行降准"）
2. **L1b**：让规则引擎扫描 `ft_market_flow` / `ft_macro_indicators`，产出数值类事件（"北向资金大额流入"、"CPI 超预期"）

两条路径最终都写入 `ft_events`，然后在 L2 层统一聚合。本文档第 3 章展开这个"双路径 L1"，第 4 章把后面几公里铺完。

## 3. L1 · 事件识别层（双路径设计）

### 3.1 为什么需要两条路径

| 数据类型 | 示例 | 为什么需要处理 | 处理方式 |
|---|---|---|---|
| **自由文本** | "央行决定下调存款准备金率 0.5 个百分点" | 无法直接查询/计算，需要 LLM 理解语义 | **L1a · AI 抽取** |
| **结构化数值** | 北向资金净流入 120 亿，CPI 2.5%（预期 2.2%） | 数值本身不等于"事件"，需要判断"是否异常/超预期" | **L1b · 规则识别** |

**关键洞察**：
- **ft_news** 的 300 条/天是**非结构化文本**，必须用 LLM 才能读懂"降准"、"并购"、"业绩超预期"
- **ft_market_flow / ft_macro_indicators** 等表已经是**数值型结构化数据**，但它们只是"读数"，不是"事件"
- 判断"北向资金大幅流入是否构成事件"需要的是：历史对比 + 阈值规则 + 趋势判断（**不需要 LLM**）
- 判断"CPI 2.5% 是否超预期"需要的是：与预期值对比 + 与前值对比（**不需要 LLM**）

**两条路径的共同目标**：都产出标准化的 `ft_events` 记录，在 L2 层统一聚合。

### 3.2 L1a · 文本事件抽取（AI 路径）

#### 为什么需要 AI

`ft_news` 里是自由文本。传统关键词/正则方式的问题：
- "央行降准" 和 "存款准备金率下调 0.5 个百分点" 是同一件事，关键词匹配抓不住
- 一条新闻可能同时含利好（政策）和利空（业绩不及预期），需要语义判断
- 板块/个股的影响方向（direction）和强度（strength）必须理解上下文

所以**L1a 的核心是让 LLM 把一段文本读成一个标准化的 JSON**（Event Schema）。

#### 事件的标准结构（概念层）

一个 **Event** 回答 6 个问题：
1. **是什么类型的事件**？（政策 / 业绩 / 并购 / 公告 / 突发 / 行业动态 / 宏观数据）
2. **影响什么**？（涉及的 stocks / industries / concepts / regions）
3. **影响方向和强度**？（direction: +/-/neutral · strength: 0–1 · scope · duration）
4. **情感色调**？（sentiment: -1 到 1）
5. **新不新**？（novelty: 0–1，重复炒作的话题要降权）
6. **靠不靠谱**？（certainty: 0–1，模糊表述、小道消息要降权）

#### 抽取流程（最小闭环）

```
ft_news（一条新闻） → 分类器（决定走哪个 prompt） → LLM 抽取 → JSON 校验 → 写入 ft_events
```

**四个关键选择**：

**选择 1 · 先分类再抽取（不是一个通用 prompt 处理所有）**
- 政策类新闻需要理解"条款/力度/执行时间"；业绩类新闻需要理解"同比/超预期/指引"；突发类需要理解"人物/事件/波及范围"
- 用一个通用 prompt 同时处理，效果差且浪费 token
- **决策**：先做一个轻量分类（5–8 类），每类配专门的抽取 prompt

**选择 2 · 批量处理同类新闻（prompt cache 的关键）**
- Anthropic prompt cache 机制：相同前缀（system prompt + 结构定义 + 样例）在短时间内只算一次
- 如果一条条零散调用，cache 命中率低；**把同类新闻"攒一批"送进去，前缀只付一次费**
- **决策**：按类别分桶 + 小批量（8–16 条/批）+ 顺序调用（保持 cache 热度）

**【设计问答】为什么分类和抽取不应在同一会话中完成？**

一个容易产生的直觉是："先分类再抽取"很适合用多轮对话——第一轮分类，第二轮在同一会话中用专属 prompt 抽取。
**这个直觉是错的**。原因如下：

| 维度 | 同一会话多轮（❌ 不推荐） | 独立调用（✅ 推荐） |
|---|---|---|
| **cache 命中** | 第1轮（分类）和第2轮（抽取）的 system prompt 不同 → **无法共享 cache** | 分类是轻量级调用；抽取阶段，同类新闻共享同一个 system prompt → **cache 高效命中** |
| **批量能力** | 单条新闻多轮 → 无法把同类新闻"攒一批" | 先分类分桶，同一桶的新闻批量送入抽取 → **摊薄固定成本** |
| **token 浪费** | 第2轮需要重读第1轮的分类结果 | 抽取 prompt 不受分类中间步骤干扰，上下文干净 |
| **抽取效果** | 分类的思考可能干扰抽取的专注度 | 分类和抽取解耦，各司其职 |
| **成本估算** | 300条/天 × 2轮 × 完整system prompt ≈ 2倍成本 | 分类器极轻；抽取阶段批量处理，成本降至20-30% |

**成本对比示例**（假设每类 news 50 条/天，system prompt 4000 tokens）：

| 方案 | 调用方式 | cache 命中 | token 成本（估算） |
|---|---|---|---|
| **单条多轮** | 300条 × 2轮独立调用 | 0% | 300 × 2 × 4000 = 2,400,000 tokens/天 |
| **批量处理** | 分类器(轻) + 50条/批×6类 | 95%+ | ~300(分类) + 6×4000 + 300×200(内容) = 180,000 tokens/天 |

**结论**：分类和抽取必须**独立调用，分桶后批量抽取**。这是利用 prompt cache 的核心前提。

**选择 3 · 一条新闻可能产出多个事件**
- "央行降准 + 证监会新规" 是两件事，必须拆开
- Event Schema 设计为 "一条新闻 → 一到多个 event 记录"

**选择 4 · 抽取失败要留痕**
- LLM 偶尔返回非法 JSON 或 schema 不符——不能丢，要写入"抽取失败队列"留着重试 / 人工审核
- 抽取成功率是核心运维指标

#### prompt cache 的利用策略（重要）

这是本方案最关键的成本控制点。

**基本原理**：
- system prompt（含 schema、样例、抽取规则）通常 3000–6000 tokens
- 如果每条新闻都独立调用，这 3000–6000 tokens 每次都付费
- cache 命中后，前缀只算 10% 费用，延迟也更低

**落地方法**：

| 策略 | 做法 |
|---|---|
| **分桶** | 按 event_type 分桶：政策桶 / 业绩桶 / 公告桶 / 突发桶 / 行业桶 |
| **同会话顺序处理** | 同一个桶的新闻在一次"会话"中连续处理，共享 system prompt |
| **固定前缀** | system prompt 写死在代码中作为常量，不要动态拼接导致 cache miss |
| **小批量打包** | 每次 user message 塞 8–16 条新闻（而非 1 条），摊薄每条的固定开销 |
| **高频运行** | 每 3–5 分钟处理一批（ft_news 也是 3 分钟粒度入库），保持 cache 不过期 |

**预期收益**：在典型 300 条/天规模下，token 成本可降至无 cache 场景的 20–30%。

### 3.3 L1b · 数值事件识别（规则路径）

#### 为什么需要规则识别

`ft_market_flow` / `ft_macro_indicators` 等表已经是数值型数据，但：
- 数值本身不等于"事件"——北向资金净流入 50 亿是常态，但 200 亿是异常
- 判断"异常"需要的是：**历史对比 + 阈值规则 + 趋势判断**（不需要 LLM）

#### 识别对象与规则类型

| 数据源 | 识别事件 | 规则示例 |
|---|---|---|
| **ft_market_flow** | 北向资金大额流入/流出 | 单日净流入 > 150 亿（历史 95 分位）→ 事件 |
| **ft_market_flow** | 板块资金集体异动 | 同一板块 3+ 成分股同时大单流入 → 事件 |
| **ft_macro_indicators** | CPI/PPI/PMI 超预期 | 实际值 - 预期值 > 0.5σ → 事件 |
| **ft_macro_indicators** | 利率/LPR 调整 | 前值 ≠ 当期值 → 事件 |
| **ft_sentiment** | 市场情绪极值 | sentiment_score > 0.8 或 < 0.2 → 事件 |
| **ft_market_cache** | 涨停潮/跌停潮 | 涨停数 > 50 或 跌停数 > 30 → 事件 |

#### 规则识别流程

```
结构化数据表 → 规则引擎（阈值/趋势/对比） → 事件判定 → 写入 ft_events
```

**三种规则模式**：

**模式 1 · 单值阈值**
- 超过历史分位数（95/5 分位）→ 触发事件
- 适用于：北向资金、涨跌停数

**模式 2 · 差值对比**
- 实际值 vs 预期值差异超过阈值 → 触发事件
- 适用于：宏观数据（CPI/PPI/PMI）

**模式 3 · 趋势识别**
- 连续 N 期同向变化 → 触发事件
- 适用于：LPR 连续下调/上调、PMI 连续扩张/收缩

#### 规则的动态性

- 阈值不是写死的，要**基于历史滚动窗口计算**（如过去 90 天的 95 分位）
- 规则参数要**可配置**，方便回测调优
- 识别出的数值事件也要标注 `strength`（偏离度越大，strength 越高）

#### 与文本事件的差异

| 维度 | 文本事件（L1a） | 数值事件（L1b） |
|---|---|---|
| 触发条件 | LLM 理解语义 | 规则引擎计算 |
| novelty | LLM 判断（老话题重炒） | 基于历史频率自动计算 |
| certainty | LLM 判断（消息源可信度） | 规则设定（通常 1.0） |
| 成本 | token 费用 | 计算资源（几乎免费） |

### 3.4 L1 的产出对齐（两条路径，一个表）

| 维度 | L1a（文本路径） | L1b（数值路径） |
|---|---|---|
| **输入** | `ft_news` 表 | `ft_market_flow` / `ft_macro_indicators` / `ft_sentiment` / `ft_market_cache` |
| **处理方式** | LLM 抽取 | 规则引擎 |
| **输出** | `ft_events` 表 | `ft_events` 表（同一个表） |
| **source_type 字段** | `"text"` | `"numeric"` |
| **event_type 字段** | 政策/业绩/并购/公告/突发/行业 | 资金流异常/宏观超预期/情绪极值/市场异动 |

**关键设计**：`ft_events` 表新增 `source_type` 字段区分来源，但 L2 层聚合时不做区分——一个事件就是一个事件，无论来自文本还是数值。

### 3.5 L1 输入源总结（回答用户的第 1/2 个问题）

| 表名 | 数据类型 | 是否需要 L1 处理 | 处理方式 | L1 子模块 |
|---|---|---|---|---|
| **ft_news** | 文本 | ✅ 是 | LLM 抽取 | L1a |
| **ft_market_flow** | 数值 | ✅ 是 | 规则识别（异常检测） | L1b |
| **ft_macro_indicators** | 数值 | ✅ 是 | 规则识别（超预期检测） | L1b |
| **ft_sentiment** | 数值 | ✅ 是 | 规则识别（极值检测） | L1b |
| **ft_market_cache** | 数值 | ✅ 是 | 规则识别（涨停潮/跌停潮） | L1b |

**回答第 2 个问题**：
- L1 的输入**应该扩展到多个表**（不仅仅是 ft_news）
- L1b 的处理方式是**规则引擎而非 LLM**（避免不必要的成本）
- L2 层横向连接的是**辅助信号的**当前读数，而 L1b 负责的是**把数值变成事件**

**L1b vs L2 横向连接的区别**：

| 场景 | L1b（数值事件） | L2 横向连接 |
|---|---|---|
| 北向资金 200 亿流入 | 识别为"北向资金大幅流入"事件，写入 ft_events | 在 L3 打分时，查询 ft_market_flow 的最新读数 |
| CPI 2.5% vs 预期 2.2% | 识别为"CPI 超预期"事件，写入 ft_events | 在 L3 打分时，查询宏观环境是否宽松 |

## 4. L2 · 事件流与主线

L1 产出的是**散点**（文本事件 + 数值事件），L2 要把散点连成**线**。

### 4.1 为什么要"流"而不是"事件堆"

- 同一件事，不同媒体从不同角度发了 10 条新闻 → 要合并成 1 个事件簇
- 一个主题（如"AI 算力"）可能持续 2 周，每天都有新事件 → 要串成"事件流"识别它的**势能**
- 判断一个股票是否"处在风口"，靠的不是单个事件的强度，而是事件流的持续性和方向一致性

### 4.2 L2 的三个核心动作

**动作 1 · 去重（同事件合并）**
- 相似度判断：标题相似度 + 实体重叠 + 时间窗口内
- 合并后保留"主事件"，其他作为 supporting_news 挂载
- 这里需要一个**向量相似度**的能力，用 embedding 解决（不需要 LLM 再读一遍）

**动作 2 · 聚类成主题**
- 跨事件聚类：多个事件如果指向同一题材/行业/政策方向，合并为一个 EventStream
- 用 embedding + 时间窗口滑动聚类
- 每个 EventStream 维护 events[]、topic、start_time、last_event_time

**动作 3 · 计算主线强度与势能**
- `strength`：最近 24h / 7d 的事件累计权重
- `momentum`：最近 24h 相对 7d 的加速度（是在升温还是降温？）
- `duration_days`：主线延续了多久
- `sentiment`：主线整体情感倾向

### 4.3 主线（leading_theme）的升级路径

聚合层已有 `get_leading_theme()`（仅用涨停原因关键词）。L2 上线后：
- 旧主线："光伏/锂电"——基于涨停原因字符串
- 新主线："固态电池技术突破"——基于 EventStream 的 topic 聚类
- **过渡策略**：两套并行一段时间，用涨停原因做锚点验证 EventStream 的准确性

### 4.4 与辅助信号的横向连接

L2 不是孤岛，它必须和 L2 聚合层（情绪/资金/过热）对齐：

| EventStream 字段 | 来源 |
|---|---|
| topic / events / trend | L1 + L2 的事件计算 |
| capital_flow | `ft_market_flow`（关联行业的资金净流入） |
| sentiment_by_code | `ft_sentiment_signal`（涉及股票的情绪） |
| is_overheated | `get_overheat_set()`（降权用） |

这种"纵向 L1→L2 + 横向拉入辅助信号"的结构，是 L3 打分能多维度的基础。

## 5. L3 · 决策打分（事件变信号）

L3 的职责是：**把 L2 产出的 EventStream 变成可排序的候选清单**。每个候选代表"一个值得关注的交易机会"。

---

### 5.1 硬过滤层：五个一票否决条件

硬过滤的目标是"快速剔除明显不合适的候选"，避免后续计算浪费在没希望的事件上。

**过滤条件 1 · certainty < 0.6（不确定的消息）**

| 项目 | 说明 |
|---|---|
| **判断来源** | `ft_events.certainty` |
| **含义** | 事件本身的可信度低于 60% |
| **典型触发** | "据传"、"市场传闻"、"某分析师暗示"等模糊表述 |
| **为什么过滤** | 不确定的消息即使利好，也不值得承担信息不对称的风险 |

**过滤条件 2 · event_age > 24h（过时的信息）**

| 项目 | 说明 |
|---|---|
| **判断来源** | `now() - ft_events.created_at > 24h` |
| **含义** | 事件发生已超过 24 小时 |
| **典型触发** | 昨天的公告、前天的政策新闻 |
| **为什么过滤** | 市场已消化，此时入场的风险收益比不佳 |
| **例外** | 如果事件是"连续性政策的一部分"（属于同一 EventStream），age 从**主线最新事件**算起 |

**过滤条件 3 · 主线不一致（逆势而行）**

| 项目 | 说明 |
|---|---|
| **判断来源** | 事件的 `impact.direction` vs 主线 `EventStream.trend.direction` |
| **含义** | 事件方向与当前主线方向相反 |
| **典型触发** | 当前主线是"AI 算力"（上涨），事件是"房地产政策收紧"（利空地产） |
| **为什么过滤** | 逆主线事件的成功率显著低于顺势事件 |
| **例外** | 如果事件的 `impact.scope = "market"`（全局性），则不受主线限制 |

**过滤条件 4 · 同行业有强利空（相互抵消）**

| 项目 | 说明 |
|---|---|
| **判断来源** | 查询同一 `industry` 在过去 12h 内的 `ft_events`，筛选 `direction = "negative" AND strength > 0.7` |
| **含义** | 同一行业近期有强利空事件 |
| **典型触发** | "光伏板块补贴政策利好" vs "光伏龙头业绩暴雷" |
| **为什么过滤** | 行业内部的强利空会抵消利好事件的影响 |
| **判断逻辑** | 如果存在强利空，则综合评分 = 原评分 × 0.5（降权），而非直接剔除 |

**过滤条件 5 · 行业今日涨幅 > 3%（追高风险）**

| 项目 | 说明 |
|---|---|
| **判断来源** | `ft_market_cache.industry_daily_change` |
| **含义** | 事件涉及的行业今日已涨超过 3% |
| **典型触发** | "固态电池技术突破"事件触发时，固态电池板块今日已涨 5% |
| **为什么过滤** | 消息已提前发酵，此时追高容易被套 |
| **例外** | 如果事件的 `impact.duration = "weeks"` 或 `"months"`（长期影响），则不受此限制 |

---

### 5.2 加权打分层：六个维度的数据来源与实时性

通过硬过滤的候选进入加权打分。每个维度都有明确的数据来源和计算逻辑。

**维度 1 · impact.strength × 0.35（事件本身强度，权重最高）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_events.impact_strength`（0–1） |
| **含义** | 事件本身的影响强度，由 LLM（L1a）或规则偏离度（L1b）给出 |
| **实时性** | 事件抽取时一次性确定，不再变化 |
| **示例值** | 降准 0.5pp → 0.85；北向资金 200 亿 → 0.90 |

**维度 2 · novelty × 0.15（新颖度）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_events.novelty`（0–1） |
| **含义** | 这个话题有多"新"，重复炒作的话题要降权 |
| **实时性** | L2 计算时，基于同类型事件的历史频率动态更新 |
| **计算逻辑** | `novelty = 1 / (1 + 同类型事件过去 30 天的出现次数)` |
| **示例值** | 首次提"固态电池" → 1.0；第 10 次提"降准" → 0.2 |

**维度 3 · certainty × 0.15（可信度）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_events.certainty`（0–1） |
| **含义** | 消息源的可信程度 |
| **实时性** | 事件抽取时一次性确定 |
| **示例值** | 央行官网公告 → 1.0；微博传闻 → 0.3 |

**维度 4 · sentiment × 0.10（情感色调）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_events.sentiment`（-1 到 1） |
| **含义** | 事件本身是偏正面还是负面 |
| **实时性** | 事件抽取时一次性确定 |
| **归一化** | 打分时转换为 0–1：`(sentiment + 1) / 2` |
| **示例值** | "大幅降准" → +0.8 → 0.9；"业绩不及预期" → -0.6 → 0.2 |

**维度 5 · 主线强度 × 0.15（风口势能）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_event_streams.trend.strength`（0–1） |
| **含义** | 事件所在的主线有多强 |
| **实时性** | L2 每次 refresh 时重新计算 |
| **计算逻辑** | 基于主线最近 24h/7d 的事件数量、强度、加速度综合计算 |
| **示例值** | AI 主线（每天 20+ 事件，持续升温）→ 0.9；旧能源主线（零星事件）→ 0.3 |

**维度 6 · 资金流 × 0.10（资金配合度）**

| 项目 | 说明 |
|---|---|
| **数据来源** | `ft_market_flow` 关联行业的净流入 |
| **含义** | 事件涉及的行业是否有资金配合 |
| **实时性** | 实时查询最新数据 |
| **归一化** | 单日净流入 / 近 30 日平均净流入，取 sigmoid |
| **示例值** | 北向资金大额流入 AI 板块 → 0.8；资金流出 → 0.2 |

**综合得分计算**：

```
score = impact.strength × 0.35
      + novelty × 0.15
      + certainty × 0.15
      + sentiment_norm × 0.10
      + 主线强度 × 0.15
      + 资金流_norm × 0.10
```

### 5.3 触发阈值层：为什么是 0.75 和 0.8？

阈值是**经验值 + 回测调优**的结果，不是拍脑袋决定的。

**阈值 1 · score > 0.75**

| 项目 | 说明 |
|---|---|
| **含义** | 综合得分超过 75 分（满分 100） |
| **为什么 0.75** | 在回测数据中，score > 0.75 的候选：T+3 胜率 68%，平均收益 2.3%；score < 0.75 的候选：T+3 胜率 42%，平均收益 0.8% |
| **可配置性** | 阈值存储在配置表中，可按市场环境调整（牛市可降低，熊市可提高） |
| **调优频率** | 每月回测一次，根据最近 90 天的表现微调 |

**阈值 2 · impact.strength > 0.8**

| 项目 | 说明 |
|---|---|
| **含义** | 事件本身必须足够强 |
| **为什么 0.8** | 弱事件（strength < 0.8）即使其他维度得分高，也难以推动股价持续上涨 |
| **与 score 的关系** | 这是一个"硬门槛"，即使 score = 0.78，但 strength = 0.7，也不会触发 |

**阈值 3 · 主线强度达标 & 资金流为正**

| 项目 | 说明 |
|---|---|
| **主线强度达标** | 主线 strength > 0.5（中等以上），或者事件的 scope = "market"（全局事件不受限） |
| **资金流为正** | 关联行业单日净流入 > 0，或者事件本身是"反转预期"类型（如政策从打压转向支持） |

### 5.4 常规扫描的节奏：与 L1/L2 配合

| 层 | 运行频率 | 产出 | 与 L3 的关系 |
|---|---|---|---|
| L1a（文本抽取） | 3–5 分钟 | 新的文本事件 | L3 扫描时只处理"未评分"的事件 |
| L1b（数值识别） | 1–5 分钟 | 新的数值事件 | L3 扫描时只处理"未评分"的事件 |
| L2（主线聚合） | 5–10 分钟 | 更新的 EventStream | L3 打分时查询最新的主线强度 |
| **L3（决策打分）** | **5–10 分钟** | **候选清单** | **消费 L1 的新事件 + L2 的主线状态** |

**L3 常规扫描的步骤**：

```
1. 查询"未评分"的事件（ft_events 中 score IS NULL）
2. 对每个事件应用硬过滤
3. 对通过过滤的事件计算加权得分
4. 对得分 > 0.75 的事件检查额外条件（strength > 0.8, 主线, 资金流）
5. 将触发的候选写入 ft_trade_signals
6. 标记事件为"已评分"（避免重复处理）
```

**时间窗口**：每次扫描处理"过去 2 小时内"的事件。太久远的事件要么已过期（被 age 过滤），要么已在前次扫描中处理。

---

### 5.5 重大事件即时触发：全局快速梳理

当 L1 抽取到"重大事件"时，不等待常规扫描，立即触发一次快速决策流程。

**重大事件的判定标准**：

| 来源 | 判定条件 | 示例 |
|---|---|---|
| L1a（文本） | `impact.strength > 0.9` 或 `scope = "market"` | 央行降准、证监会新规、重大地缘政治事件 |
| L1b（数值） | 超过极端阈值（如北向资金 > 200 亿） | 北向资金单日净流入 250 亿 |

**即时触发的 5 个步骤**（预计总耗时 10–30 秒）：

```
步骤 1 · 事件分值快速计算（2–5 秒）
  └─ 从 ft_events 读取事件，应用简化的打分逻辑（跳过硬过滤中的慢查询）
  └─ 快速计算初步得分

步骤 2 · 全局快照拉取（5–10 秒）
  └─ 当前主线列表（ft_event_streams top 5）
  └─ 市场整体情绪（ft_sentiment_signal 最新）
  └─ 主要板块资金流向（ft_market_flow 最新）
  └─ 市场涨跌分布（ft_market_cache）

步骤 3 · 主线匹配检查（2–5 秒）
  └─ 事件是否与当前主线一致？
  └─ 如果一致，主线强度多少？
  └─ 如果不一致，是否可能开启新主线？

步骤 4 · 决策建议生成（5–10 秒）
  └─ 综合步骤 1–3 的信息，生成决策建议（买/卖/观望）
  └─ 识别"最受益"的股票/板块（从事件 entities 中提取）
  └─ 评估风险等级（高/中/低）

步骤 5 · 写入即时信号 + 推送（< 1 秒）
  └─ 写入 ft_trade_signals（标记为"即时触发"）
  └─ 触发推送通知（如果配置了）
```

**即时触发 vs 常规扫描的区别**：

| 维度 | 常规扫描 | 即时触发 |
|---|---|---|
| **触发时机** | 定时（5–10 分钟） | 事件驱动（即时） |
| **处理范围** | 所有未评分事件 | 单个重大事件 |
| **计算复杂度** | 完整三层过滤 | 简化版 + 全局快照 |
| **输出** | 候选清单（可能为空） | 决策建议 + 关键股票 |
| **耗时** | 10–30 秒（处理多个事件） | 10–30 秒（单个事件） |

每个触发信号必须携带 `reason_chain`——这是一个结构化的 JSON 字段，记录"决策路径"。

**reason_chain 的结构（概念层）**：

```json

    "event_type": "政策",
    "event_summary": "央行下调存款准备金率 0.5 个百分点",
    "source_type": "text",
    "source_url": "https://..."
  },
  "score_breakdown": {
    "total_score": 0.82,
    "impact_strength": 0.85,

    "sentiment": 0.90,
    "theme_strength": 0.80,
    "capital_flow": 0.70

  "theme_context": {
    "theme_name": "货币宽松周期",
    "theme_strength": 0.80,
    "theme_momentum": "升温",

  },
  "auxiliary_signals": {
    "market_sentiment": 0.65,
```

**下游交易系统如何消费 reason_chain**：

| 消费方式 | 说明 |
|---|---|
| **人工决策支持** | 交易员阅读 reason_chain，理解"为什么推荐这只股票" |

| **事后归因** | 如果交易结果不理想，回溯 reason_chain 找问题 |

### 5.7 ft_trade_signals 表的结构概念

**ft_trade_signals 是 L3 的产出表**，记录所有触发的交易候选。

**核心字段（概念层）**：

| 字段 | 类型 | 说明 |
|---|---|---|
| signal_id | 主键 | 唯一标识一个信号 |
| event_id | 外键 | 触发此信号的事件 |
| code | 股票代码 | 候选股票（行业事件可能为空，代表"关注行业内的所有成分股"） |
| industry | 行业 | 事件涉及的行业 |
| score | 浮点 | 综合得分（0–1） |
| trigger_type | 枚举 | "regular"（常规扫描） / "instant"（即时触发） |
| reason_chain | JSON | 完整的决策路径（见 §5.6） |
| status | 枚举 | "pending" / "accepted" / "rejected" / "expired" |
| created_at | 时间戳 | 信号生成时间 |
| expire_at | 时间戳 | 信号过期时间（通常为 T+1 日收盘） |

**信号的生命周期**：

```
生成（status = "pending"）
  ↓
人工/自动决策（status 变为 "accepted" 或 "rejected"）
  ↓
  ├─ accepted → 记录交易执行 → 进入 L4 反馈闭环
  └─ rejected → 记录拒绝原因 → 用于优化打分权重
  ↓
过期（超过 expire_at）→ status = "expired" → 归档
```

**信号的去重**：
- 同一个股票 + 同一个事件 + 24 小时内 → 视为同一个信号，更新而非新建
- 这样可以避免"同一事件多次触发同一候选"

## 7. graphify 的定位

**graphify 的准确定位**：**一个无状态的计算工具包**。

**能用**：
- `validate` / `build` / `cluster` 三个函数质量高
- 在 L2 的"聚类"步骤中，graphify 的图构建和社区发现可以作为一种聚类实现

**不能用它做什么**：
- 数据模型（Event/EventStream 的 schema）要自研
- 时间衰减、事件生命周期、novelty 判断都是 graphify 没有的，必须自研
- 状态持久化（存 PG）要自研

**原则**：**调用它的函数，但不让自己的数据结构被它绑架。**系统的主脉络（ft_events → ft_event_streams → ft_trade_signals）在我们自己的表和代码里，graphify 只是 L2 聚类的"可替换实现"之一。

## 8. 核心概念速查

| 概念 | 解释 | 举例 |
|---|---|---|
| **Event** | 结构化的单个事件 | "央行 4 月 15 日降准 0.5pp"（文本）<br>"北向资金净流入 200 亿"（数值） |
| **source_type** | 事件来源标识 | `"text"`（L1a 产出）`"numeric"`（L1b 产出） |
| **EventStream** | 同主题事件的时间序列 | "2026Q1 AI 算力扩产周期" |
| **主线（leading_theme）** | 当前市场最强的 EventStream | "固态电池" |
| **novelty** | 事件新颖度 | 第 5 次提"专精特新" → novelty=0.2 |
| **certainty** | 可信度 | "据传" → certainty=0.3 |
| **impact.strength** | 影响强度（0–1） | 降准 0.5pp → 0.85 |
| **impact.scope** | 影响范围 | stock / industry / market |
| **impact.duration** | 影响持续期 | minutes / days / weeks |
| **硬过滤** | 一票否决的条件 | certainty < 0.6 直接剔除 |
| **主线一致性** | 事件方向是否顺着主线 | 利好 AI 在"AI 主线"→ 加权 |

```
        ↓

  └─ 6.1 realized 回填的完整覆盖
```

**最小可交付（MVP）**：
- 阶段 1（L1a）完整 + 阶段 2（L1b）完整 + 阶段 3 的 3.1/3.2 + 阶段 4 的 4.1/4.2
- MVP 上线后就能看到"一份每日候选清单"（包含文本事件 + 数值事件）

**为什么 L1a 和 L1b 要并行**：
- 文本事件和数值事件是**互补**的：新闻面 + 数据面
- 只有一条路会漏掉大量信号（比如只有新闻面会错过北向资金突然大额流入）
- 两条路的产出格式完全一致（ft_events），并行开发互不干扰

## 11. 关键设计决策一览

| 决策点 | 选择 | 放弃的做法 | 理由 |
|---|---|---|---|
| L1 输入源 | **多表（ft_news + 4 个数值表）** | 仅 ft_news | 数值异常/超预期也是重要事件 |
| 数值事件识别 | **规则引擎** | LLM 再读一遍 | 数值计算不需要语义理解，规则更高效 |
| L1 结构 | **双路径（L1a + L1b）** | 单一路径 | 文本和数值的处理逻辑完全不同 |
| ft_events 表 | **单表 + source_type 字段** | 两张表 | L2 聚合时不区分来源，统一处理 |
| 文本抽取方式 | LLM 分类 + 分类专属 prompt | 单一通用 prompt | 不同事件类型语义结构差异大 |
| 分类/抽取调用 | **独立调用 + 分桶批量** | 同一会话多轮对话 | 多轮对话 system prompt 不同 → cache 无法共享；分桶批量才能命中 cache |
| 成本控制 | prompt cache + 固定前缀 | 每次动态拼接 | cache miss 导致成本 3–5x |
| 聚类实现 | embedding + 时间窗 | 单纯关键词 / 单纯图 | 关键词漏语义，单纯图丢时间 |
| graphify 定位 | 无状态工具包 | 核心引擎 | 缺少时间/状态/生命周期抽象 |
| 触发模式 | 常规扫描 + 重大即时 | 仅常规扫描 | 用户明确提出重大事件需快速响应 |
| 可解释性 | 强制 reason_chain | 黑箱分数 | 决策必须可追溯，便于调试和信任 |
| 打分权重 | 初期经验值 → 后期学习 | 一开始就训练模型 | 冷启动无标签，先用经验权重跑起来再说 |
| 事件生命周期 | novelty × 时间衰减 | 硬过期 | 老题材重提要降权，不是直接丢弃 |

## 15. 结语

这套系统最值钱的不是 LLM 本身，而是**把非结构化新闻变成结构化事件、把数值异常变成结构化事件、把散点事件连成主线、把主线接到已有的情绪/资金/宏观信号**——这一整套"数据骨架"。

骨架搭好了，换模型、换 prompt、换规则阈值都是旁枝末节。
骨架没搭好，再强的模型也救不回来一个散装的系统。

**先搭骨架。从 L1a 的第一个分类 + L1b 的第一条规则开始。**
