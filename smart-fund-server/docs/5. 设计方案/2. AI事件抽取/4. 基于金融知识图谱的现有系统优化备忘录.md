# 基于金融知识图谱的现有系统优化备忘录

> **文档定位**：这不是一份立即开工的实施方案，也不是代码改造清单。
> 它的作用是：在 `../1. 知识图谱/1. 知识图谱总体设计方案.md` 确认之后，作为回头优化 `1. 全局设计方案.md`、`2. L1事件识别设计方案.md`、`3. L2事件流与主线设计方案.md` 以及现有实现时的备忘录。
> 重点只写**业务逻辑要改什么、系统方向怎么调整、为什么值得改**，不展开代码细节。

---

## 0. 一句话说清楚

> **现有 AI 事件抽取体系已经能跑起来，但它还是“先抽事件，再在后面补语义”的思路；在金融知识图谱方案确认后，后续优化方向应改为“先用知识图谱定义语义地基，再让 L1/L2/L3 都围绕这张图工作”。**

这次优化的目标不是局部提效，而是把系统从：

```
原始数据 -> 抽成事件 -> 事件之间再想办法对齐
```

升级为：

```
原始数据 -> 对齐到知识图谱 -> 事件只是图上的动态事实
```

---

## 1. 为什么要写这份优化备忘录

当前 `AI事件抽取` 下的 3 份主文档，逻辑顺序是：

1. 先定义全局事件驱动引擎。
2. 再定义 L1 双路径事件识别。
3. 再定义 L2 事件流与主线。

这套顺序在“先把事件流水线跑起来”的阶段是合理的，但在引入金融知识图谱之后会暴露出一个明显问题：

> **L1 和 L2 都在自己承担语义对齐职责，而不是共享一套前置语义底座。**

因此，未来回头优化时，不能只做局部 patch，而要做**设计重心迁移**：

- 全局设计里，知识图谱要上移到 L1 之前。
- L1 设计里，抽取结果要从“字符串实体”升级为“图谱节点 + 证据 + 候选关系”。
- L2 设计里，聚类逻辑要从“字段重叠/embedding 相似”升级为“图社区 + 路径强度 + 证据链”。

这份文档就是为了把这件事先记清楚，避免后面只记得“要优化”，却忘了具体该怎么改。

补充说明：

- `1. 全局设计方案.md` 和 `2. L1事件识别设计方案.md` 已经形成阶段性设计，并且已有部分实现可以参考。
- `3. L2事件流与主线设计方案.md` **虽然已经写好，但尚未真正实施落地**。

这意味着后续针对 L2 的优化，原则上应按**重新设计**处理，而不是按“兼容既有实现”的局部改造处理。
换句话说，L2 是当前最适合直接按金融知识图谱方案重构的一层。

## 2. 这次优化的本质

### 2.1 不是重写一套系统

这次优化不是推翻现有事件驱动体系，而是给它补上原本缺失的**语义基础设施层**。

也就是说：

- `ft_news`、`ft_market_flow`、`ft_macro_indicators`、`ft_sentiment` 这些数据源不变。
- L1a/L1b 双路径不变。
- `ft_events` 仍然存在，仍然是统一事件表。
- L2/L3/L4 的大框架不变。

真正变化的是：

> **L1/L2/L3 的工作对象，不再只是事件表，而是“事件 + 知识图谱”组成的统一语义层。**

### 2.2 不是为了某一个场景提效

引入金融知识图谱以后，优化收益不会只体现在 L2 主线聚类。

它至少会影响 5 个层面：

1. **L1 抽取质量**
   - 实体更稳定，别名更少，概念更统一。

2. **L2 聚类质量**
   - 主线不再只靠标签直接重叠，而能通过 2-3 跳语义路径聚合。

3. **L3 影响推理**
   - 事件到基金的映射可以从“直接命中”变成“多跳传导”。

4. **GraphRAG 检索**
   - 系统可以回答更复杂的“为什么”“通过什么链条影响”的问题。

5. **反馈闭环**
   - 高频误抽、误合并、概念漂移可以沉淀成图谱更新，而不只是写临时规则。

## 3. 当前系统的主要短板

### 3.1 全局设计层的短板

当前全局设计把系统起点定义为：

```
L0 原始数据 -> L1 事件识别 -> L2 主线 -> L3 打分
```

问题在于：

- 语义标准化发生得太晚。
- L1 输出虽然结构化，但仍然是“事件中心”而不是“图谱中心”。
- L2 才开始承担主线语义聚合，导致 L2 压力过大。

### 3.2 L1 层的短板

当前 L1 的核心思路是：

- L1a 用 LLM 抽事件。
- L1b 用规则抽数值事件。
- 两条路径都写入 `ft_events`。

这套设计已经比原始文本强很多，但仍然有几个缺口：

1. **实体是“抽出来的字符串”，不是稳定 node_id**
2. **概念别名没有前置收敛**
3. **关系只隐含在字段里，没有显式图边**
4. **抽取结果虽然有 evidence_refs，但没有进入统一图谱事实层**
5. **L1 不知道哪些概念本来就在图上，哪些是全新候选**

### 3.3 L2 层的短板

当前 L2 文档仍然基于旧思路：

- 先做去重
- 再做 embedding/实体重叠聚类
- 再生成 EventStream

这在“没有图谱”的前提下是一个合理近似，但在有 KG 底座后，它会变成次优方案：

- 相似度只看局部，不看图路径
- 不共享图谱里的 alias / related_to / community 信息
- 主线解释更多依赖事件字段，而不是显式证据路径
- 会不断在 L2 补概念对齐规则，本质上是在还 L1 的语义债

## 4. 优化后系统应该变成什么样

### 4.1 正确的逻辑顺序

后续真正优化时，系统逻辑顺序应该调整为：

```
L0 原始数据
  -> KG 基础组件（ontology / entity normalization / relation compile）
  -> L1 事件识别（图谱感知）
  -> L2 事件流与主线（图社区感知）
  -> L3 决策打分（图路径感知）
```

也就是说，**知识图谱不再是下游能力，而是上游基础组件**。

### 4.2 系统角色的重新定义

优化后，各层角色应重新定义：

| 层 | 旧定位 | 新定位 |
|---|---|---|
| KG | 辅助能力/后续增强 | 前置语义地基 |
| L1a | 从文本抽事件 | 从文本抽“事件 + 节点 + 候选边” |
| L1b | 从数值抽异常事件 | 从数值编译“数值事件 + 图谱事实更新” |
| L2 | 负责主要语义聚合 | 负责基于图的主线发现和状态管理 |
| L3 | 直接消费事件流 | 消费“事件流 + 图路径 + 影响传播链” |

这里还需要把查询层的职责一并定死：

- **Microsoft GraphRAG**：作为生产 GraphRAG 检索与问答目标能力，围绕 Local / Global / DRIFT 展开。
- **graphify**：作为本地开发、调试、Wiki、MCP、路径查看工具。

后续优化时，不应再沿着“GraphRAG 只负责存储/导出兼容，正式查询继续走 graphify 或自建拼接逻辑”的方向展开。
正确方向应是：**同一事实图同时供 GraphRAG 和 graphify 消费，但生产查询目标能力归 Microsoft GraphRAG。**

## 5. 对现有 3 份设计文档的优化方向

### 5.1 对 `1. 全局设计方案.md` 的优化方向

全局方案后续需要做三类调整：

#### 调整 1：在系统总图中加入 KG 基础设施层

现有图里，L0 之后直接进入 L1。
优化后要改成：

```
L0 原始数据
  -> KG 基础组件
  -> L1 双路径事件识别
  -> L2 事件流
  -> L3 决策
```

#### 调整 2：重新描述 L1/L2 的职责边界

现有描述中，L1 更像“抽取层”，L2 更像“语义层”。
优化后要改成：

- L1 负责把原始数据接入到图谱语义层。
- L2 负责在图谱之上识别“活跃主线”和“事件社区”。

#### 调整 3：明确索引层与事实层分离

全局方案需要明确 3 层：

1. **事实层**：PostgreSQL 中的知识图谱事实库和 `ft_events`
2. **索引层**：GraphRAG parquet、graphify graph.json、`pgvector`、FTS
3. **应用层**：L1/L2/L3/L4

否则后面很容易把 GraphRAG、graphify、向量索引误当成“源数据库”。

---

### 5.2 对 `2. L1事件识别设计方案.md` 的优化方向

L1 是这次优化的核心。

#### 调整 1：L1 输出从“字段型事件”升级为“图谱感知事件”

未来 L1 的输出不能只包含：

- `affected_stocks`
- `affected_industries`
- `affected_concepts`

还应包含：

- 对应的稳定 `node_id`
- 该节点是否已存在于图谱
- 是否产生新的 alias/related_to/candidate edge
- 证据是否足以进入主图，还是只进入候选区

#### 调整 2：L1a 不再只是分类 + 抽取

L1a 的逻辑需要增加一个前置和一个后置：

前置：
- 用图谱词表和 alias 参与分类、实体识别和 prompt 上下文。

后置：
- 抽取结果进入 KG compiler 做标准化、关系候选判定、置信度分层。

因此，未来 L1a 的业务闭环应理解为：

```
新闻 -> 分类 -> 抽取 -> 实体标准化 -> 图谱对齐 -> 事件入库
```

而不是现在的：

```
新闻 -> 分类 -> 抽取 -> 事件入库
```

#### 调整 3：L1b 也要成为图谱编译入口

当前 L1b 的产出虽然是规则事件，但优化后它不应只是“把异常写到 `ft_events`”。

还应同步承担：

- 生成相关信号节点
- 更新 signal -> indicator / industry / concept 的关系
- 为后续 L2/L3 提供更丰富的数值语义边

#### 调整 4：L1 的“去重”职责要收缩

在有图谱之后，L1 只保留：

- 显式重复去重
- 同源重复合并

不要让 L1 继续承担过多“语义合并”责任。
语义上的收敛，应更多依靠 KG 和 L2 图社区。

---

### 5.3 对 `3. L2事件流与主线设计方案.md` 的优化方向

L2 的改动会最大。

先记一个很重要的判断：

> **由于 `3. L2事件流与主线设计方案.md` 已成文但尚未实施，后续优化时不应把“兼容旧 L2 实现”当作前提。**

这意味着：

- 不需要先落地旧版 embedding 主导聚类，再二次迁移到 KG 方案。
- 不需要为了兼容既有运行逻辑而保留过多过渡性结构。
- 可以直接把 L2 的主干设计切换到“图社区 + 路径强度 + 证据链”。

因此，L2 后续更适合视为**按新地基重写设计**，而不是“在旧设计上做增强”。

#### 调整 1：主线识别从“embedding 主导”改为“图社区主导”

旧思路：

- 看事件 embedding
- 看实体重叠
- 看时间窗

新思路：

- 看事件挂载到图上的节点子图
- 看事件之间的最短路径、路径强度、社区一致性
- embedding 退到辅助召回和历史类比层

#### 调整 2：主线解释从“标签重叠”改为“路径 reason chain”

未来 L2 需要能回答：

- 为什么这两个事件属于同一主线？
- 这条主线是通过哪些概念/行业/股票节点连接起来的？

所以主线解释要升级为：

```
事件 A -> 概念 X -> 行业 Y -> 概念 Z -> 事件 B
```

而不是只说：

```
因为都带了“AI算力”标签
```

#### 调整 3：L2 状态机要利用图谱活跃度

未来主线状态不应只由“事件数 + 时间”决定，还应参考：

- 社区活跃度
- 核心节点热度变化
- 新增事件对社区核心路径的增强程度

这会让 `emerging / fermenting / peak / decaying` 更贴近真实主线演化。

## 6. 对现有系统业务逻辑的优化方向

这一部分不谈代码文件，只谈系统级逻辑要怎么变。

### 6.1 事件生产逻辑

当前：

- 文本和数值事件分别生产，再合流到 `ft_events`

未来：

- 文本和数值事件不仅要写 `ft_events`
- 还要同步更新知识图谱事实层
- 事件变成图上的动态事实节点，而不是孤立记录

### 6.2 实体管理逻辑

当前：

- 实体主要以事件字段中的字符串存在

未来：

- 实体应由图谱统一管理
- L1 只是引用实体，不再自行“发明最终实体形态”
- 新实体只能以候选方式进入，经过对齐或复核再升级

### 6.3 主线发现逻辑

当前：

- 事件先写库，后续再做聚类

未来：

- 事件一落库就应具备图谱上下文
- L2 只需要在活跃子图上做主线发现，不必重新从头理解语义

### 6.4 检索与解释逻辑

当前：

- 解释更多依赖事件字段拼接

未来：

- 解释应优先来自图路径和证据链
- GraphRAG 和 graphify 都应围绕同一事实图工作
- 生产检索与问答目标能力应按 Microsoft GraphRAG 官方 query engine 设计
- graphify 负责本地导航、调试、路径查看和 agent 工具，不承担生产 GraphRAG 主查询职责

也就是说，后续优化不应把方向定义成：

```
KG facts -> GraphRAG parquet（只做兼容）
        -> graphify / 自建查询（承担正式查询）
```

而应定义成：

```
KG facts -> Microsoft GraphRAG BYOG -> Local / Global / DRIFT
        -> graphify -> 本地调试 / Wiki / MCP / 路径查看
```

## 7. 对系统收益的预期

### 7.1 质量收益

优化完成后，预期至少有 4 类质量收益：

1. **实体稳定性提升**
   - 同义概念不再频繁裂变。

2. **主线聚类更稳**
   - 不共享直接标签的事件也能通过图路径进入同一主线。

3. **解释性提升**
   - EventStream 和后续决策链能给出明确路径和证据。

4. **误抽的修复能力增强**
   - 错误不只是“下次 prompt 改一下”，而是能沉淀到图谱规则和别名管理中。

### 7.2 成本收益

引入 KG 后，长期会降低两类成本：

1. **LLM 成本**
   - 图谱词表、alias、community report 可以减少重复抽取和重复解释。

2. **规则复杂度成本**
   - 原本散落在 L1/L2 的语义修补规则，可以部分集中回 KG 层管理。

### 7.3 能力收益

真正大的收益不只是“L1/L2 更准”，而是：

- 后续 Microsoft GraphRAG 官方 query engine 有稳定事实层和 BYOG 输入可依赖
- L3 可以做多跳影响推理
- 历史类比和复盘可以回到同一张图上闭环

## 8. 未来回头优化时的改造顺序建议

虽然这次不实际修改，但回头动手时建议顺序如下：

### Step 1：先重写文档边界

先改文档，不要先改代码：

1. 先更新 `1. 全局设计方案.md`
2. 再更新 `2. L1事件识别设计方案.md`
3. 最后重写 `3. L2事件流与主线设计方案.md`

否则代码优化时仍会被旧文档误导。

### Step 2：先完成 KG 基础组件

在 `../1. 知识图谱/1. 知识图谱总体设计方案.md` 完成之前，不应急着改 L1/L2 业务逻辑。
因为：

- node_id 规则还可能变化
- 关系类型还可能变化
- 证据和置信度协议还可能变化

### Step 3：优先改 L1，再改 L2

原因很简单：

- L2 的很多问题，本质是 L1 没有共享统一语义底座
- 如果 L1 还输出旧格式，L2 再怎么补都只是弥补

### Step 4：最后再考虑 L3/L4 的增强

L3/L4 的图路径推理、复盘反馈都应在 L1/L2 新语义层稳定之后再做。

## 9. 这份备忘录不解决什么

为了避免以后回头看时误解，这里明确一下不在本备忘录范围内的内容：

1. **不讨论具体表结构变更**
2. **不讨论具体任务拆分和调度细节**
3. **不讨论具体代码文件怎么改**
4. **不讨论具体 prompt 怎么写**
5. **不讨论具体 GraphRAG/graphify 导出实现**

但需要记住一个已经确定的方向前提：

- **讨论实现细节时可以延后，但架构方向已经确定为 GraphRAG 前期纳入设计，生产查询目标能力采用 Microsoft GraphRAG BYOG + 官方 query engine。**
- **graphify 的定位是本地开发与调试工具，不是生产查询主路径。**

这些内容等 `../1. 知识图谱/1. 知识图谱总体设计方案.md` 冻结之后，再分别进入实现方案。

## 10. 到时候回头做优化时，最重要的检查问题

未来真正开始优化时，先用这几个问题检查方向有没有偏：

1. 当前修改是在**减少 L1/L2 自己维护语义规则**，还是在继续堆补丁？
2. 当前修改有没有把**实体管理权上收给知识图谱**？
3. 当前修改有没有把**解释链从字段拼接升级为图路径**？
4. 当前修改有没有让 GraphRAG / graphify / L2 / L3 **共享同一事实图**？
5. 当前修改有没有继续把 **graphify / 自建查询** 当成生产查询主路径？
6. 当前修改是在**把复杂度集中到 KG 基础组件**，还是把复杂度继续散落在各层？

如果这几个问题的答案不够明确，就说明优化方向还没走正。

## 11. 最终结论

现有 `AI事件抽取` 方案不是错，而是**缺少前置知识图谱地基时的合理阶段性方案**。

在金融知识图谱方案确定之后，未来的优化方向应该非常明确：

> **不是继续增强“事件表本身的聪明程度”，而是把事件系统整体迁移到“知识图谱先行”的架构上。**

后续真正回头优化时，最重要的不是某个 prompt、某个阈值、某个聚类参数，而是这三件事：
