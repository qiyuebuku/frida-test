## 2. 密码登录根因与用法（核心知识）

**根因**：不是密码预处理——是 g6m builder 字段放错位。真机探针捕获证实
App 实际构造 `g6m.b=R(交易密码)`（线上 tag3，券商密码校验位）、
`g6m.c=S("")`（tag4 恒空）。旧代码 `S(密码)/R("0")` 让券商把 "0" 当密码
→ "[120047]客户交易密码错误"。

**登录线上 tag 布局**（s3s.b，buf 首字节 0x13）：
tag1=T("0") / tag2=N(资金账号) / **tag3=R(密码)** / tag4=S(空) /
tag5=Q(空) / tag6=U(yyb串"2393#16#1#1#")。密码明文，无任何加密
（getCommonPwd=记住密码取存储、tfm=安全键盘UI、w0s=改密码专用、
yjm RSA=查账号，全部排除，勿重复查）。

**login 端点用法**（`POST /stock/trade/login`，body 可组合）：
- `{}` — token 优先、过期自动密码 fallback、已登录短路
- `{"force":true}` — 绕过 already_logged_in 强制重登（被踢后恢复）
- `{"method":"pwd"}` — 跳过 token 直接密码登录（最强重建）
- `{"password":"..."}` — 一次性密码

实测：pwd 直登 21s / force 恢复 14ms / funds 1.8s。
密码存储：AVD `files/thshook_pwd.json`；账号、密码与券商 qsid 均按生产 Secret
管理，文档不得记录明文值。

### 5.1 写暗丢根因与 v12 修复（2026-08-19 追加）

生产直连 `127.0.0.1:49500` 复现过一次 BUY 15 秒超时且券商侧无新增委托，
可排除 8900/旧 LB 混流。触发窗口是 App 重启后交易旁路 hook 或 CBAS 尚未稳定，
写请求可能发往死连接；写路径又不能在状态不明时盲重发。

排查同时发现原“超时后查当日委托再安全重发”存在确定性判定缺陷：
`orderListContains` 只按代码和价格搜索，会命中当天早先使用相同回归价格产生的旧委托，
从而把本次暗丢误判为已经执行，第二轮安全重发不会发生。

v12 修复口径：

1. BUY 发送前必须成功查询 `today_order` 并记录合同号集合；基线不可用则 fail closed，
   不发送真实委托。
2. 超时后只有“代码和价格匹配且合同号不在发送前基线中”的记录才能证明本次已执行。
3. 首次未发现新增合同号时，间隔 4 秒再次查询；仍无新增才允许强制登录后安全重发一次，
   防止券商状态延迟落库造成重复单。
4. `tradingSdkBridgeHooked=false` 时写端点直接拒绝发送；`/health` 新增
   `trade_hook_ready`、`cbas_reconnecting`、`cbas_ready_age_ms`，调用方必须以
   `trade_hook_ready=true` 作为写前门禁。
5. 客户端写请求超时必须覆盖设备端两轮“发送—查单定论—安全重发”流程；客户端提前断开
   不代表设备端 handler 已停止，禁止在未查清合同号前由客户端再次提交。

## 8. App 内交易运行时自愈接口（2026-08-19 晚）

生产 Hook `20260819-trade-runtime-v13` 已增加无 UI、幂等的运行时接口：

```bash
curl --noproxy "*" http://127.0.0.1:49500/stock/trade/runtime/status
curl --noproxy "*" -X POST http://127.0.0.1:49500/stock/trade/runtime/ensure \
  -H "Content-Type: application/json" -d '{}'
```

`status` 只读取进程内状态，不触发登录。`ensure` 在同花顺 App 进程内依次启动
`CommunicationService`、恢复 MasterModule/账户、恢复交易会话并执行 positions 只读探针；
不调用下单、撤单或转账协议。并发初始化由 `tradeRuntimeLock` 单飞串行，已经 READY 且只读探针
未超过 5 分钟时返回 `actions=["already_ready"]`，生产实测耗时 0ms。

写能力必须以 `write_ready=true` 为门禁，它同时要求：交易模块、响应旁路 Hook、账户、券商会话
及最近一次真实只读探针全部正常。冷启动生产实测从 `HOOK_NOT_READY` 到 `READY` 约 35～62 秒，
完成后 positions 返回手工保留的 `000001` 100 股持仓。

服务端 `THSTradeClient` 已实现 `runtime_status()` / `ensure_runtime()`，并在每次交易请求前先检查
状态，仅在异常时触发 ensure。生产 `THS_TRADE_BASE_URL` 已从错误的采集 LB `49350` 修正为交易
专口 `http://127.0.0.1:49500`。

注意：采集 Bridge 的 `switch-user` 会触发 Android
`killBackgroundUserProcessesWithAudioRecordPermission`，杀死持有录音权限的 user 0 同花顺进程。
在采集启动彻底移除前台用户切换前，不允许同时启动 users 10–17 的恢复流程。当前为保护交易链，
生产采集 Bridge/watchdog 已暂停，users 10–17 仅停止运行、未删除用户或数据。
