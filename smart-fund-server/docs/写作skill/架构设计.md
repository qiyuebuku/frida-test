# AI 小说续写系统 — 架构设计

> 日期：2026-02-11
> 状态：**已实施**（三 Subagent 极简架构完成，知识库内容待 T2 全量补跑）

---

## 一、问题定义

**目标**：让 AI 续写长篇小说，且续写质量接近原作。

**核心难点**：

1. **上下文容量**：百万字小说不可能一次性塞进 LLM 上下文
2. **风格漂移**：LLM 默认输出是训练语料均值，不是某本书的风格
3. **设定崩坏**：AI 不记得 200 章前的世界规则，容易自相矛盾
4. **质量不可控**：同一 prompt 每次生成结果不同，需要可量化的验证手段

**解法**：将问题拆为两步——**预处理**（把小说解构为结构化知识库）+ **运行时**（从知识库按需调度上下文来写作，并自动验证）。

```
续写质量 ≈ 预处理质量 × 上下文调度能力 × 验证反馈能力
```

---

## 二、设计原则

1. **通用性**：知识库结构是模板，适用于任意小说，不绑定某本书
2. **信息不丢失**：评论保留段落级粒度，保持与原文的精确映射关系
3. **可扩展**：百万字级小说的世界观、人物关系等信息量巨大，目录结构需支持多文件扩展
4. **导航式检索**：AI 通过索引文件层层展开上下文，而非一次性加载全部内容
5. **写审分离**：Writer 不自审，质量由独立 Reviewer 在隔离上下文中评判
6. **上下文极简**：主 Agent 上下文只保留有效信息（~7-9K），KB 搜索由 subagent 执行后释放

## 四、核心模型：六层知识库

小说不等于文本。一部小说是多层结构的叠加，预处理的本质是**小说结构化建模**。

| 层 | 回答的问题 | 目录 | 核心文件 |
|----|-----------|------|----------|
| **剧情层** | 故事走到哪了 | `plot/` | outline/(弧+主线), chapters/(章节摘要), open_loops.md(伏笔) |
| **角色层** | 谁在参与，什么状态 | `characters/` | {name}.md(5 模块档案), relationships.md(关系网) |
| **世界层** | 什么能做什么不能做 | `world/` | power_system, geography, factions, rules |
| **读者层** | 市场想看什么 | `reader/` | feedback/(情绪/人气/不满/期待), comments/(段落级评论) |
| **风格层** | 怎么写才像原作 | `style/` | narrative, vocabulary, rhythm, anchors.md(原文锚点), .build/stats.json |
| **文本层** | 原始文字 | `text/` | ch{NNNN}.md(纯正文) |

**导航式检索**：AI 续写时从 `guide.md` 出发，按需层层展开——全局主线 → 当前弧 → 近章摘要 → 角色/设定 → 原文。不是一次加载全部，而是按场景类型选择性读取。

### 剧情层的三级递进

剧情层是最核心的一层，采用三级摘要结构：

```
全局主线 (plot_lines.md)     ← 方向感：接下来往哪走
    ↓
弧级摘要 (arc_XX.md)        ← 上下文：当前弧的核心冲突和转折
    ↓
章节摘要 (ch{NNNN}.md)      ← 细节：最近几章发生了什么
    ↓
原文 (text/ch{NNNN}.md)     ← 精确衔接：上一章最后几段
```

### 风格层的定量+定性

风格层同时包含两类数据，缺一不可：

- **定量基线** (`stats.json`)：平均句长 40.8 字、对话占比 41.5%、"道"系标签 84% —— 验证时用来画红线
- **定性分析** (`narrative/vocabulary/rhythm.md`)：叙事特征、禁忌词、节奏偏好 —— 写作时用来指导风格
- **原文锚点** (`anchors.md`)：从原文精选的示范段落 —— 给 LLM 具体的模仿对象

## 五、写作 Skill 架构

### 核心公式

```
续写 = Research（从 KB 提炼上下文 + 大纲 + 名词清单）
     + Enrichment（按名词搜 KB → 角色/世界设定补全 → Scene Plan）
     + Generation（主 Agent 在干净上下文下写全章正文）
     + Verification（独立验证 + 反馈修复）
```

### 7 步流程（三 Subagent 极简架构）

```
Research:   Step 1 读 guide
            Step 2 Task(sonnet) Researcher → Bundle + 大纲 + 名词清单（落盘）
Enrichment: Step 3 Task(sonnet) Enricher → 按名词搜 KB → Scene Plan（落盘）
            Step 4 展示大纲+Plan → 用户确认
Writing:    Step 5 主 Agent 直接写全章正文（上下文 ~7-9K）
Verify:     Step 6 Task(sonnet) Reviewer → Bash L1 + L2/L3 → 评级
            Step 7 展示评级 → 询问用户
```

### 与旧架构（四级 Subagent）的对比

| | 旧架构（四级） | 新架构（三 Subagent） |
|---|---|---|
| **Subagent 数量** | Researcher + Planner + N×SceneWriter + Reviewer | Researcher + Enricher + Reviewer |
| **正文生成** | N 个 opus SceneWriter subagent 分场景写 | 主 Agent 直接写全章 |
| **信息补全** | Planner 同时做"怎么写" + 搜 KB | Enricher 专注按名词清单搜 KB |
| **主 Agent 上下文** | 累积所有 subagent 交互 | 极度干净（~7-9K 有效信息） |
| **核心问题** | 信息传递断裂、场景缺失 | 名词清单驱动，不遗漏 |

### 三个中间产物

写作质量的关键不是 prompt 多复杂，而是**中间产物的质量**：

| 产物 | 解决什么问题 | 体积 |
|------|-------------|------|
| **Context Bundle** | KB ~35KB 压缩为 ~3KB，Writer 只读 Bundle 不读原始 KB | ~3KB |
| **大纲 + 名词清单** | 规划"写什么" + 列出需要补全的专有名词 | ~1KB |
| **Scene Plan** | 角色设定+世界设定+风格锚点+写作注意事项 | ~3-5KB |

Scene Plan 的新格式（取代旧的 6 维度）：角色设定摘要、世界设定摘要、未在 KB 中找到的名词、风格锚点、写作注意事项。

所有中间产物**落盘到 `drafts/`**，修复时重新加载，防止 Plan Drift（在"另一套计划"下修复旧文章）。

### Writer-Reviewer 隔离（Subagent 级）

```
主 Agent（编排器 + Writer）          Task(sonnet) Reviewer
    │                                    │
    │  读取：                             │  Step 0: Bash 跑 L1 Python
    │  - context_bundle                  │  读取：
    │  - outline + 名词清单              │  - drafts/ch{N}.md
    │  - scene_plan                      │  - style/*.md + stats.json
    │                                    │  - text/ch{N-1}.md (原文)
    │  不读取：                           │  - reader/feedback/ (如有)
    │  - reviewer_agent.md               │
    │  - 评分权重/盲测方法               │  不读取：
    │                                    │  - scene_plan
    │  产出：正文                         │  - context_bundle
    │                                    │  - outline
    │                                    │  产出：verification.md
    │                                    │        feedback.md
    │                                    │
    └─── 信息流单向：feedback → Writer ──┘
```

**为什么隔离**：同一上下文自审无效（"自己改卷"总会自证正确）。Subagent 架构下每个角色在独立上下文中执行，用完即释放。Writer 看不到 `reviewer_agent.md` 中的评分标准和盲测细节，Reviewer 看不到 Writer 的 scene_plan 和推理过程。

### 验证架构（Reviewer Subagent 内部 L1 + L2/L3）

| 层 | 执行方式 | 本质 | AI 调用 |
|----|----------|------|---------|
| L1 | Reviewer 内部 Bash `batch_verify.py --layer 1` | 定量指标 vs 基准线（编译器） | 0 次，<5s |
| L2 | Reviewer subagent AI 分析 | 盲测对比 + 风格分析（编辑） | Task(sonnet) |
| L3 | Reviewer subagent AI 分析 | 读者对齐（市场分析师，可选） | 同上 |

**触发方式**：Reviewer subagent 内部先 Bash 跑 L1（纯 Python，无成本），再基于 L1 结果做 L2/L3 深度分析。L1 输出和审核推理过程全部留在 subagent 上下文中，释放后消失，不污染主 Agent。

**评分**（由 Reviewer subagent 内部计算，详见 `reviewer_agent.md`）：

```
有读者数据：  L1×0.35 + L2×0.40 + L3×0.25
无读者数据：  L1×0.45 + L2×0.55
A (≥90) 优秀 | B (80-89) 良好 | C (70-79) 及格 | D (<70) 不合格
```

### 修复循环

修复不是"重写"，而是在**既定设计图下施工**：

```
feedback.md ──→ 提取问题清单（FAIL > WARN > 建议）
scene_plan  ──→ 约束不变（不改大纲、不改场景结构）
draft       ──→ 针对具体问题逐项修复
             ──→ 保存覆盖 → 再次验证
```

## 七、Skill 模式总览

`/novel-write` 是**唯一入口**，通过参数切换模式：

| 模式 | 命令 | 做什么 |

## 八、关键设计决策

### 为什么从四级 Subagent 改为三 Subagent 极简架构？

旧架构（Researcher→Planner→N×SceneWriter→Reviewer）的核心问题是**信息传递断裂**：
- Planner 同时做"怎么写" + 搜 KB，职责混杂
- N 个 SceneWriter subagent 分场景写，场景间信息传递靠 Scene Memory（压缩后信息丢失）
- 每个 SceneWriter 需要独立读 KB，重复工作且可能搜索不完整

新架构的解法：
- **Enricher 专注信息补全**：按名词清单逐项搜 KB，确保不遗漏
- **主 Agent 直接写全章**：上下文只有 ~7-9K 有效信息（Bundle+大纲+Scene Plan），没有中间传递损耗
- **名词清单驱动**：Researcher 生成名词清单 → Enricher 逐项搜索，形成闭环

### 为什么要六层而不是直接存原文？

百万字塞不进上下文。六层解构后，续写一章只需读 ~3KB Context Bundle + 相关角色/设定文件，总计 ~10KB，远小于原始 ~35KB 知识库或百万字原文。

### 为什么 `text/` 和 `reader/comments/` 分开？

- `text/`：AI 读故事时只看正文，不被评论干扰
- `reader/comments/`：需要参考读者反应时，精确定位"读者在对哪段话评论"
- 原始混合 markdown 仍保留在 `output/` 目录作为数据源

### 为什么 Scene Plan 独立于大纲？

大纲回答"发生什么"，Scene Plan 回答"用什么信息写"。新架构下 Scene Plan 的核心价值是**信息完备性**——把角色档案、世界设定从 KB 中摘录出来，让主 Agent 写作时不需要再去搜索 KB。

### 为什么 Writer 不自审？

同一上下文自审无效——Writer 知道自己要写什么，检查时会"自证正确"。Subagent 架构下 Writer 和 Reviewer 在独立的 Task 上下文中执行，上下文用完即释放。Writer 看不到 `reviewer_agent.md` 中的评分标准和盲测细节，Reviewer 看不到 Writer 的 scene_plan 和推理过程。

### 为什么 L1 放在 Reviewer subagent 内部？

旧架构中 L1 在主 Agent Bash 执行，L1 输出需要通过参数传入 Reviewer subagent。新架构中 Reviewer 自己 Bash 跑 L1，好处：
- L1 输出不经过主 Agent 上下文（减少噪音）
- Reviewer 直接获取 L1 原始数据，无信息损失
- 主 Agent 只看到最终评级，不看中间过程

### 为什么中间产物要落盘？

如果 Context Bundle 和 Scene Plan 只在上下文中，修复时它们会蒸发（上下文被压缩/新会话）。落盘到 `drafts/` 后，`--revise` 能重新加载完整设计图，在**同一套计划**下修复，而不是"另一套计划下改旧文章"（Plan Drift）。

### 为什么验证时注入书籍规则？

Reviewer subagent 不知道每本书的特殊规则。例如《玄鉴仙族》的穿越者角色允许在内心独白中使用"社畜""互联网"等现代词汇——如果不注入这条规则，Reviewer 会将其标记为"用词不当"。`reviewer_agent.md` 指示 Reviewer 读取 `style/narrative.md` 和 `style/vocabulary.md` 中的书籍特定规则，确保审核标准与写作规则一致。
