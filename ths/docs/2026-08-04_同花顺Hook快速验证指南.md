## 1. 代码边界

同花顺 App 逆向相关代码统一维护在 `ths`：

| 目录 | 职责 |
|---|---|
| `app/src/main/java/com/yuyang/thshook` | App 进程内 Hook、原生方法调用和 `THSSTREAM/1` 服务 |
| `zygisk` | Zygisk 注入与动态 DEX 运行材料 |
| `deployment/android-emulator` | 生产 Android 虚拟机及宿主机桥接 |
| `scripts` | 协议探索、录制、回放和验收工具 |
| `fixtures/native_stream` | 从真机录制并脱敏后的协议响应 |
| `docs` | 同花顺专项逆向记录和运行指南 |

`smart-fund-server` 不实现第二套 App 协议。它负责连接 `THSSTREAM/1`、解析业务数据、持久化、调度和提供 API。

## 2. 验证分层

旧链路把逻辑测试和真实 App 验收绑定在一起：

```text
修改代码 -> 编译 -> 签名 -> 安装 -> 重启 App -> 等待 Hook -> 部署服务端 -> 请求验证
```

新流程分为四层：

```text
L1 本地协议模拟与单元测试
  -> L2 真实响应录制回放
  -> L3 真机 Hook 集成验收
  -> L4 生产虚拟机最终验收
```

只有修改 App 内类名、反射签名、原生请求模型或 Hook 时，才需要执行 L3。生产环境只承担最终验收，不再作为开发调试环境。

### 3.1 排查输出预算

本地排查必须控制单次输出量。命令本身执行很快并不代表整个排查过程很快：如果一次读取上千行 `git diff`，或并行向会话输入数万行日志、反编译结果，后续分析仍会长时间显示 `Working`。这属于检查方式导致的分析阻塞，不是 Git 或 Hook 构建耗时。

必须按以下顺序收敛问题：

1. 先看变更范围：`git diff --stat` 和 `git status --short`；
2. 再用 `rg -n '<pattern>' <target-file>` 定位精确符号和行号；
3. 只读取目标附近的小范围：`sed -n '<start>,<end>p' <target-file>`；
4. 只查看目标文件的局部差异：`git diff -- <target-file>`，必要时再结合函数名缩小范围；
5. 日志先用关键词、时间窗口和 `tail` 过滤，不得默认读取完整服务日志；
6. 反编译结果先搜索类名、方法名、Frame ID 或协议字符串，不得将整个类或整个 DEX 输出到会话。

禁止使用以下方式作为常规检查：

```bash
git diff -- <many-files> | sed -n '1,1400p'
journalctl ...                    # 不限时间、行数或关键词
jadx ...                          # 直接输出大块反编译内容
```

若确实需要完整输出，应将结果保存为本地临时产物，再通过 `rg`、统计脚本或分页精确读取，不将完整内容注入当前会话。

## 4. 本地协议模拟器

启动示例回放服务：

```bash
python scripts/ths_dev.py serve \
  --scenario fixtures/native_stream/example.json \
  --port 49310
```

请求模拟器：

```bash
python scripts/ths_dev.py request \
  --host 127.0.0.1 \
  --port 49310 \
  --route unified \
  --payload '{"onlineId":"example"}'
```

模拟器与生产使用相同的换行 JSON 协议，支持握手、订阅、事件、心跳以及由 `request_id` 关联的 Unified、Hurricane、Ranking 请求响应。

Fixture 的 `match` 是请求 Payload 的递归子集。只保留决定响应类型的稳定字段，避免时间戳和动态标识破坏回放。

## 5. 真机响应录制与回放

真机 Hook 就绪后录制真实响应：

```bash
python scripts/ths_dev.py record \
  --host 127.0.0.1 \
  --port 18900 \
  --route unified \
  --payload-file /tmp/request.json \
  --output fixtures/native_stream/market_label.json
```

同一路由可以录制多组请求。录制文件保存稳定请求 Payload 和 App 返回的完整业务 Payload，不保存 TCP `request_id`。

提交 Fixture 前必须清除账号、Cookie、Token、设备标识和其他认证数据。原始未脱敏响应只能保存在本地临时目录。

## 6. 真机快速验收

任何真机或生产部署前，必须先执行统一门禁：

```bash
python scripts/ths_dev.py predeploy
```

该命令会运行 `ths/tests`、服务端协议契约测试和 Hook APK 增量构建。任一环节失败时不得部署。

### 6.1 等待 Hook 就绪

```bash
python scripts/ths_dev.py wait-device --serial <serial> --timeout 45
```

命令自动建立 ADB forward，并通过 `THSSTREAM/1` 握手判断 Hook 是否就绪，不使用固定等待时间。

### 6.2 增量构建

```bash
python scripts/ths_dev.py build
```

Gradle 使用现有缓存增量构建，不清理构建目录。

### 6.3 安全覆盖 Hook

```bash
python scripts/ths_dev.py deploy-device --serial <serial>
```

部署命令依次执行：

1. 强制运行完整 `predeploy` 门禁；
2. 增量构建 Hook；
3. 拉取设备已安装 Hook APK；
4. 比较已安装 APK 与待安装 APK 的证书 SHA-256；
5. 仅在签名一致时执行 `adb install -r`；
6. 从构建 APK 中定位实际包含 `MainHook` 的 DEX，并同步到 Zygisk 模块的 `dex/classes.dex`；
7. 校验设备端 APK 与 Zygisk DEX 哈希；
8. 重启目标 App。

签名不同会立即终止。命令不会调用 `adb uninstall`，不会主动破坏 LSPosed 模块状态和作用域。

### 6.4 长连接订阅验收口径

Unified 订阅必须区分两个时间点：

- `subscribed ACK`：只表示 Bridge 接受了订阅命令，不证明 App 原生初始化 Frame 已释放；
- 首个行情事件：表示上游已经返回业务数据，可能比 ACK 晚数秒或数十秒。

是否能仅凭 ACK 初始化下一路，必须由目标 App 版本的交叉并发实验决定。当前同花顺生产版本的五路 Unified 事件订阅共享 App 全局初始化 Frame；仅按 ACK 连发会让这些订阅返回 `-131 请求超时`。正确流程是前一路收到首个 Native 成功响应后立即初始化下一路，失败时只重试当前一路，全部完成后再注册普通行情订阅。该流程由回调驱动，不使用固定等待时间。真机验收必须分别记录命令 ACK、Native 首个成功响应和后续事件时间。

## 7. 推荐流程

### Python Client、路由、重试或解析改动

```text
修改 smart-fund-server -> ths_dev.py test -> Fixture 回放
```

### App 内 Hook 或原生调用改动

```text
修改 MainHook.java
  -> ths_dev.py predeploy
  -> ths_dev.py deploy-device
  -> ths_dev.py wait-device
  -> 真机 request/record
```

真机验收通过后，才部署到生产虚拟机。

### App 版本升级

必须先在真机重新验证 Hook 注入点、反射签名、三类请求参数、响应结构和长连接恢复。生产 App 与真机验证版本必须一致，不长期维护两套版本协议。

## 8. 完成标准

| 改动类型 | 最低验收层级 |
|---|---|
| Python 路由与解析 | L1 + L2 |
| 常驻连接生命周期 | L1 + 真机断线恢复 |
| Hook 反射调用 | L1 + L3 |
| App 版本升级 | L1 + L2 + L3 + L4 |
| 生产采集链路 | 全部四层 |

模拟器和 Fixture 用于缩短反馈周期，不能代替最终真机和生产验收。
