# redroid 容器化待优化记录

### 交易密码自动登录卡在 sessionType=1 会话检查（2026-08-20 记录）

**问题：** 容器已自动启动 CommunicationService，CBAS 9528 TCP 可持续
双向收发，账户和密码包也已按 App 官方 builder 构造，但密码登录在
hrv.r(sessionType=1) -> hrv.u(aqv$c) 后无回调，实例未达到 write_ready。

**最佳方案：** 完整追踪 sessionType=1 的回调与 q9m/s8m/e2s 拦截器链，
恢复 App 原生无头交易会话，并以 funds/positions/today_order 三项真实查询
作为容器健康门禁。

**当前方案：** 已将 CommunicationService extra、CBAS 地址注入、Docker Secret
密码注入和登录参数构造固化；服务器实验镜像 1.2.9 仍未通过交易门禁，
不作为可用版发布。

**整改条件：** sessionType=1 回调链完成定位并通过冷启动三查询验收。

**优先级：** P1

### Hook release lint 依赖未锁定（2026-08-22 记录）

**问题：** Android Gradle Plugin 的 `lintVitalAnalyzeRelease` 仍会在构建时从 Maven
下载未进入仓库校验清单的 Groovy/HTTP 依赖；本地网络发生 TLS handshake 中断时，
即使 Java 编译已通过，release assemble 仍会失败。这不符合完整离线灾难恢复要求。

**最佳方案：** 为 Gradle 启用 dependency verification，固定 wrapper、plugin、
lint 和所有 Maven artifact checksum，并将依赖缓存作为可校验构建制品保存在私有
制品仓库；PR 单独执行 lint，镜像发布使用相同锁定缓存。

**当前方案：** CI 的 APK 编译与签名显式跳过 `lintVitalAnalyzeRelease`，Java 编译、
资源处理、部署契约和运行 canary 仍是阻塞门禁。该状态只表示镜像可构建，不表示
Android lint 已完成。

**整改条件：** Gradle dependency verification metadata 和私有 Maven 构建缓存
落地后，恢复阻塞式 `lintRelease`。

**优先级：** P1

### 自动部署仍依赖服务器现场构建制品（2026-08-21 记录）

**问题：** 当前已将生产部署入口限制为 `push main` 触发的 GitHub Actions，并要求
部署 revision 等于事件 `github.sha`；但 Smart Fund Server 镜像和 THS Hook APK 仍由
生产服务器基于该 revision 现场构建，Redroid 黄金镜像也尚未进入 CI 制品发布链路。
同一 Git commit 的源码可追溯，但构建环境、基础镜像缓存和服务器独有模板仍可能造成
制品不可复现。

**最佳方案：** GitHub Actions 在测试后构建并签名不可变制品，以 commit SHA 和
内容 digest 推送到私有 Registry/制品仓库；生产服务器只按 digest 拉取并启动，部署状态
同时记录 Git SHA、镜像 digest、workflow run ID，并支持按上一成功 digest 回滚。

**当前方案：** 第一阶段先完成 Git 主线门禁、自动触发、串行部署、SSH host key 校验和
工作区未跟踪文件拒绝；保留现有服务器构建流程，待生产服务器恢复并导出黄金模板、签名
材料和现存镜像后再迁移构建链路。

**整改条件：** 生产服务器恢复，完成服务器/本地源码与镜像取证对齐，并建立可访问的
私有 Registry 与受保护制品存储后。

**优先级：** P1

### 交易实例必须保持 Activity 前台导致 CPU 偏高（2026-08-21 记录）

**问题：** redroid 虚拟显示无法通过 Android 电源键进入 OFF。同花顺 Activity
在前台时多个 RenderThread 持续绘制，交易实例约占用 70%～90% 单核。把 Activity
切到桌面可降至约 10%，但 App 会在约 30 秒内主动释放交易 session，导致
`write_ready=false` 和守护循环恢复，不能用于生产。

**最佳方案：** Hook 同花顺 Activity 的后台生命周期中关闭交易 session 的调用，
或在保持 resumed/session 状态的前提下阻断 Choreographer/页面渲染，再验证资金、
持仓、委托、买卖撤全链路。

**当前方案：** `1.2.50-headless` 对 collector 在 ready 后切换静态桌面，将单实例
空闲 CPU 降至约 3%～7%；trade 仅关闭蓝牙、NFC、定位扫描、打印、相机、音乐和
动态壁纸等外围能力，并保持同花顺前台，优先保证 `write_ready=true`。

**整改条件：** 完成交易 session 释放方法定位与 Hook，并通过冷启动和至少 30 分钟
交易只读/写入回归。

**优先级：** P1

### realtime 固定路由首次预热较慢（2026-08-20 更新）

**问题：** redroid 启动后 unified 通常第二次请求即可成功；realtime 的固定
6004/1006 路由在部分实例需要数分钟和多次请求才能收到首次回调。重复请求失败后
会增加路由恢复时间。

**最佳方案：** 在 THSHook 内增加 realtime 通信会话状态机，等待 9528 通道稳定、
一次请求超时后完整注销并等待路由释放，再执行下一次预热。

**当前方案：** 2026-08-20 已改为 THSHook 内部主动初始化：Application.onCreate 后
直接启动 CommunicationService、创建 realtime total client 并派发 unified bridge；
Docker 只轮询 `/native/runtime/status`。最终门禁要求 unified 连续两次真实成功，并在
统一调用层对首次失败自动重建 bridge 重试一次，以规避 `removeRequest()` 的共享路由
清理竞争。collector9 空卷冷启动实测 27 秒进入 healthy，其中 Hook 主动初始化
3.687 秒；healthy 后连续 5 次业务 unified 全部成功，已消除此前 70–90 秒外部退避。

**整改条件：** 将容器端口切换给 smart-fund-server 前，补充 24 小时重启回放，
据此确定 realtime watchdog 的退避参数。

**优先级：** P1

### redroid DNS 转发依赖宿主机规则（2026-08-20 记录）

**问题：** redroid Ethernet 会把 LinkProperties DNS 固定为 `8.8.8.8`，当前
服务器无法稳定直连该解析器；App 的 push 请求会在 10 秒后触发异常退出。

**最佳方案：** 构建镜像时让 Ethernet tracker 使用部署环境提供的 DNS，避免
依赖固定公网解析器。

**当前方案：** 宿主机 systemd oneshot 将 Docker bridge 发往 `8.8.8.8:53`
的 TCP/UDP 流量 DNAT 到 `10.168.1.3`，并在容器内关闭 captive portal 探针。

**整改条件：** 镜像 Dockerfile 化时一并修改网络默认配置。

**优先级：** P2

### 镜像构建链不可复现（2026-08-22 整改中）

**问题：** `redroid:11.0.0_riru6` 是 6 次 `docker commit` 叠出的（rc 修改、
wrapper、rirud 补丁、LSPosed 布局），无 Dockerfile，不可重复构建。

**最佳方案：** 固化为 Dockerfile + 补丁文件仓库化（rirud smali 补丁、
start-rirud.sh、bootanim.rc 均已有源文件在 `~/redroid-poc/stack/`）。

**当前方案：** 已移除黄金 `/data` 和 `redroid:11.0.0_riru6` 作为构建输入，改为
固定官方 Redroid digest，并从通过 SHA-256 校验的 Native Bridge、Magisk、
Riru/LSPosed 静态制品和 THS APK 重建。Hook 每次从 Git SHA 构建并使用 production
Environment keystore 签名。新卷初始化、LSPosed scope、空卷 canary、按 digest
滚动部署和单实例回滚已经代码化。生产机公网 HTTPS 被中途设备截断，因此 Actions
通过 SSH 隧道把镜像推入仅绑定回环地址的 digest-pinned Registry；部署前强制校验
其 manifest digest 与 Docker Hub 发布 digest 一致。尚未在独立宿主机完成首次空卷运行验收，也尚未
让新 workflow 实际替换生产 1+8 容器，因此不能标记为整改完成。

**整改条件：** Actions 成功构建并推送镜像；隔离
空卷 canary 达到 healthy；1+8 滚动发布与回滚演练通过；在第二台干净宿主机完成
从 Git、私有 Release 和 Docker registry 的恢复演练。

**优先级：** P1

### 实例仍共享部分设备指纹（2026-08-20 更新）

**问题：** 9 个数据卷 `cp -a` 自同一基线。`android_id` 已按实例固定唯一，解决了
行情服务器会话互相挤占，但 Build fingerprint、网卡和部分 App 内生成标识仍相同。

**最佳方案：** 克隆后随机化 android_id（`settings put secure android_id`），
并以生产"脱敏黄金模板"机制重新导出/恢复。

**当前方案：** 启动脚本为 trade 与 collector1-8 写入确定性的唯一
`settings secure android_id`，其余指纹暂未随机化。

**整改条件：** 出现同设备风控特征时。

**优先级：** P2

### 无 watchdog / 进程守护（2026-08-19 记录）

**问题：** 容器重启后 Android 自动 boot，但 THS App 与 LSPosed daemon 之后的
健康检查、自动拉起、崩溃重启均未接管（生产有 ths-android-watchdog +
collector-bridge 体系）。

**最佳方案：** docker restart policy + systemd 单元 + 健康探测脚本。

**当前方案：** 2026-08-20 新镜像已内置 Android init 管理器、Docker HEALTHCHECK、
`unless-stopped` 和无破坏恢复（仅 `am start` + 重预热，禁止 force-stop/swipe）。
collector9 的首次启动及容器重启均已验证。原 1+8 容器尚未滚动迁移到新镜像。

**整改条件：** collector9 完成交易时段 realtime 真数据回放后，将原 1+8 容器
滚动迁移到新镜像；交易实例另需提供受控账户 seed/token/password Secret。

**优先级：** P2
